## "내가 쓴 코드가 아닌데, 왜 내 서비스가 뚫렸을까?"

얼마 전, 보안 커뮤니티에서 꽤 큰 이슈가 된 Trivy 공급망 공격 소식을 접했을 때, 나도 모르게 이런 생각이 들었어요. 오픈소스 스캐너인 Trivy가 공격당했다니, 우리 CI/CD 파이프라인에도 뭔가 구멍이 있지 않을까? 결국 우리 서비스도 영향을 받을 수 있지 않을까? 

이 사건은 단순히 한 툴의 문제를 넘어, 소스 코드 관리(SCM)와 배포 파이프라인 전반의 보안 취약점을 다시 한번 고민하게 만들었습니다. 오늘은 그 사건을 통해 우리가 배워야 할 점과, 백엔드 엔지니어 입장에서 어떻게 대응할 수 있을지 현실적인 방안을 공유해보려 합니다.

---

## Trivy 공급망 공격, 왜 이렇게 위험했나?

Trivy는 컨테이너 이미지 취약점 스캐너로, 많은 기업이 CI/CD 과정에서 필수로 사용하고 있죠. 그런데 공격자는 이 Trivy의 배포 프로세스에 침투해 악성 코드를 포함시켰습니다. 이 악성 코드는 Trivy가 실행될 때 백도어를 설치하고, 내부 네트워크에 접근하는 데 악용됐죠.

공급망 공격의 가장 무서운 점은 바로 ‘신뢰의 사슬’을 깨뜨린다는 겁니다. 우리가 신뢰하는 오픈소스 툴이나 라이브러리가 공격받으면, 그걸 쓰는 모든 서비스가 위험에 노출됩니다. 특히 Trivy처럼 자동화된 파이프라인에서 쓰이는 도구는 한 번 감염되면 수많은 빌드와 배포에 영향을 미치기 때문에 피해가 커질 수밖에 없어요.

이 사건을 계기로, SCM 파이프라인 보안에 대한 근본적인 재점검이 필요하다는 걸 절감했습니다.


## SCM 파이프라인에서 흔히 간과하는 보안 구멍들

우리 팀도 CI/CD 파이프라인을 운영하면서 꽤나 신경 쓴다고 생각했는데, 막상 이번 사건을 보니 놓친 부분이 많더라고요.

- **의존성 검증 부재**: Trivy처럼 외부 바이너리나 라이브러리를 다운받아 쓰는 경우, 해시 검증이나 서명 검증이 없으면 악성 변조를 바로 잡아내기 어렵습니다.

- **빌드 환경 격리 미흡**: 빌드 서버가 내부 네트워크에 직접 연결돼 있으면, 악성 코드가 침투했을 때 피해가 확산됩니다. 격리된 환경에서 빌드가 이뤄져야 하는데, 현실은 그렇지 않은 경우가 많죠.

- **자동화된 권한 관리 부족**: 파이프라인에 접근 권한이 너무 넓거나, 토큰이 노출되면 공격자가 빌드 프로세스를 조작할 수 있습니다.

- **로그와 모니터링 미비**: 공격 흔적을 빠르게 감지하지 못하면 대응이 늦어지고 피해가 커집니다.

이런 구멍들이 모여서 결국 공급망 공격의 발판이 되죠.


## 실무에서 바로 적용 가능한 SCM 파이프라인 보안 강화법

내가 직접 겪은 경험과 여러 사례를 참고해, 백엔드 엔지니어가 당장 할 수 있는 몇 가지 방법을 정리해봤어요.

### 1. 외부 바이너리와 라이브러리는 무조건 서명 검증부터

Trivy 공격도 결국 배포 파일이 변조된 게 핵심이었죠. 그래서 우리 팀은 모든 외부 바이너리 다운로드 시 SHA256 해시를 미리 저장해두고, 다운로드 후 해시 검증을 반드시 거칩니다. 

```bash
EXPECTED_HASH="abc123..."
DOWNLOAD_URL="https://example.com/tool.tar.gz"
curl -sL $DOWNLOAD_URL -o tool.tar.gz
ACTUAL_HASH=$(sha256sum tool.tar.gz | awk '{print $1}')
if [ "$EXPECTED_HASH" != "$ACTUAL_HASH" ]; then
  echo "해시 불일치! 다운로드 파일이 변조된 것 같습니다."
  exit 1
fi
```

이렇게 간단한 스크립트라도 넣으면, 변조된 파일을 바로 걸러낼 수 있습니다. 물론 해시값은 신뢰할 수 있는 출처에서 받아야 하겠죠.

### 2. 빌드 환경은 최대한 격리하고 최소 권한 원칙 준수

우리 CI 서버는 빌드 시 내부 네트워크와 분리된 별도의 네트워크 세그먼트에서 실행합니다. 그리고 빌드 프로세스가 접근할 수 있는 리소스 권한도 꼭 필요한 것만 줍니다. 예를 들어, 빌드용 토큰은 배포 권한이 없는 별도의 계정을 사용하도록 했죠.

이렇게 하면 혹시 악성 코드가 침투해도 피해 확산을 어느 정도 막을 수 있습니다.

### 3. 파이프라인 접근 권한과 토큰은 주기적으로 회전

오래된 토큰이나 권한 남용은 공격자가 침투하는 지름길입니다. 우리 팀은 매달 파이프라인 관련 토큰을 새로 발급하고, 사용하지 않는 권한은 바로 제거합니다. 자동화 스크립트로 권한 현황을 점검하는 것도 큰 도움이 됐어요.

### 4. 빌드 및 배포 로그는 중앙에서 실시간 모니터링

로그를 쌓기만 하고 보지 않으면 무용지물입니다. 우리 팀은 ELK 스택을 이용해 빌드 로그를 중앙 집중화하고, 이상 징후(예: 예상치 못한 외부 네트워크 호출 등)를 탐지하는 알림을 걸어놓았습니다. 이 덕분에 비정상적인 동작을 빠르게 발견할 수 있었죠.


## Trivy 공격 이후, 백엔드 API 설계에도 영향을 준 점

사실 SCM 파이프라인 보안만큼 중요한 게 API 계약 안정성입니다. 오픈AI API 문서에 따르면, AI 모델 릴리즈 시 API 응답 스키마나 지연시간, 비용 같은 백엔드 계약을 함께 점검해야 한다고 하죠([OpenAI API Documentation](https://platform.openai.com/docs/overview)).

우리도 Trivy 공격 이후, 외부 의존성 변화에 따른 API 영향도를 더 꼼꼼히 체크하기 시작했습니다. 예를 들어, 모델 게이트웨이 계층에서 fallback 모델과 타임아웃 정책을 분리해 장애 전파를 줄인다는 Anthropic 가이드도 참고했어요([Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)).

이처럼 공급망 공격은 단순히 툴 문제에 그치지 않고, 전체 아키텍처 신뢰성 강화로 이어져야 한다는 걸 깨달았습니다.


## 내가 직접 겪은 한 가지 실전 팁: GitHub Actions에서 서명 검증 자동화하기

우리 팀은 Trivy를 GitHub Actions 워크플로우에서 사용합니다. 그래서 워크플로우에 아래처럼 서명 검증 단계를 추가했어요.

```yaml
name: CI
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Download Trivy
        run: |
          curl -sfL https://github.com/aquasecurity/trivy/releases/latest/download/trivy_0.41.0_Linux-64bit.tar.gz -o trivy.tar.gz
          echo "EXPECTED_HASH=abcd1234..." > expected_hash.txt
          ACTUAL_HASH=$(sha256sum trivy.tar.gz | awk '{print $1}')
          EXPECTED_HASH=$(cat expected_hash.txt)
          if [ "$ACTUAL_HASH" != "$EXPECTED_HASH" ]; then
            echo "Trivy 해시 검증 실패!"
            exit 1
          fi
          tar zxvf trivy.tar.gz
      - name: Run Trivy scan
        run: ./trivy image my-image:latest
```

처음엔 이게 별거 아닌 것 같지만, 실제로 공격 사례가 터지고 나니 이런 작은 방어선이 얼마나 중요한지 절감했습니다.


## 마무리하며: 공급망 공격은 끝나지 않는 전쟁

Trivy 공급망 공격은 우리에게 SCM 파이프라인 보안이 얼마나 중요한지, 그리고 단순히 ‘툴만 믿고 쓰는 시대는 끝났다는 걸 다시 한번 일깨워줬습니다. 

실제로 겪어보면, 작은 자동화 스크립트 하나, 빌드 환경 분리, 권한 관리 강화 같은 조치들이 모여 큰 차이를 만듭니다. 물론 완벽한 방어는 없지만, 꾸준한 점검과 개선이 피해를 최소화하는 유일한 길이에요.

여러분도 지금 당장 자신의 SCM 파이프라인을 한번 점검해보세요. 그리고 작은 방어선을 하나씩 쌓아가는 게 결국 우리 서비스와 고객을 지키는 길입니다.
