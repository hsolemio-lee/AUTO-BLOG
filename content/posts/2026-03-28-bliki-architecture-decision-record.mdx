## "왜 이걸 선택했지?"라는 질문에 답할 수 있어야 한다

프로젝트를 하다 보면, 어느 순간 "왜 우리가 이 아키텍처를 선택했지?"라는 질문이 불쑥 튀어나올 때가 있어요. 특히 팀원이 바뀌거나, 시간이 꽤 지난 후라면 더더욱 그렇죠. 이때마다 구글 드라이브, 슬랙 메시지, 회의록을 뒤적거리는 건 정말 비효율입니다. 저도 이런 경험을 여러 번 했는데, 그때마다 "아키텍처 결정 기록(Architecture Decision Records, ADR)"이 큰 도움이 됐어요.

ADR은 단순히 "이렇게 하자"를 적는 게 아니라, 왜 그렇게 결정했는지, 어떤 대안들이 있었는지, 그리고 그 결정이 앞으로 어떤 영향을 미칠지까지 체계적으로 정리하는 문서입니다. 특히 백엔드와 클라우드 플랫폼 같이 복잡한 시스템에서는 이게 없으면 기술 부채가 쌓이고, 마이그레이션이나 운영 중에 예상치 못한 문제가 터지기 쉽죠.


## ADR이 실제 프로젝트에서 어떻게 쓰이는지

우리 팀은 클라우드 플랫폼을 설계하면서 ADR을 적극 활용했는데, 몇 가지 인상 깊은 경험이 있습니다. 예를 들어, 마이크로서비스로 분할하는 과정에서 각 서비스의 경계와 통신 방식을 결정할 때, ADR에 각 선택지의 장단점과 운영 제약 조건을 꼼꼼히 기록했어요. 덕분에 나중에 서비스 일부를 AWS Lambda로 옮기거나, Kubernetes로 배포 전략을 바꿀 때, "왜 처음에 이 방식을 선택했는지"를 쉽게 파악할 수 있었습니다.

이런 기록 덕분에 마이그레이션 경로가 명확해져서, 점진적으로 서비스를 이전하는 과정에서 리스크를 크게 줄일 수 있었죠. Microsoft의 클라우드 디자인 패턴 문서에서도 ADR이 이런 복잡한 마이그레이션과 운영 제약 조건을 관리하는 데 필수적이라고 강조합니다[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/).


## ADR과 CI/CD 파이프라인을 연결하면 좋은 점

처음엔 ADR을 단순한 문서로만 생각했는데, CI/CD 파이프라인과 연계하면 훨씬 강력해집니다. 예를 들어, 아키텍처 변경 사항이 코드 변경과 함께 ADR 문서에 반영되도록 GitHub Actions 같은 자동화 도구를 활용할 수 있어요. 이렇게 하면 빌드와 테스트 과정에서 아키텍처 결정의 영향도를 추적할 수 있고, 변경 시점에 관련 문서가 최신 상태인지도 자동으로 검증할 수 있습니다.

아래는 GitHub Actions 워크플로우 예시입니다. `adr/` 폴더 내 문서가 변경되면, ADR 문서에 특정 형식(예: 제목, 상태)이 맞는지 체크하는 간단한 스크립트를 실행합니다.

```yaml
name: Validate ADRs

on:
  push:
    paths:
      - 'adr/**'

jobs:
  check-adr-format:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Validate ADR markdown format
        run: |
          for file in adr/*.md; do
            if ! grep -q '^# ' "$file"; then
              echo "Error: $file missing title"
              exit 1
            fi
          done
```

이런 자동화는 아키텍처 결정이 코드와 따로 놀지 않도록 만들어 줍니다. Martin Fowler도 지속적 통합(Continuous Integration)과 ADR의 결합이 아키텍처 품질 유지에 도움된다고 언급했죠[Martin Fowler - Continuous Integration](https://martinfowler.com/articles/continuousIntegration.html).


## ADR 작성 시 꼭 포함해야 하는 내용과 현실적인 팁

실제로 ADR을 쓸 때는 다음 내용을 꼭 포함하는 게 좋아요:

- **제목과 날짜**: 언제 어떤 결정인지 명확히
- **상태(Status)**: 제안됨(Proposed), 승인됨(Approved), 폐기됨(Deprecated) 등
- **배경(Background)**: 왜 이 결정을 내려야 했는지 상황 설명
- **결정(Decision)**: 구체적으로 어떤 선택을 했는지
- **대안(Alternatives)**: 고려했던 다른 옵션과 그 이유
- **결과(Consequences)**: 이 결정이 앞으로 미칠 영향과 트레이드오프

이 중에서 특히 '대안'과 '결과' 부분을 소홀히 하면, 나중에 왜 이걸 선택했는지 이해하기 어렵습니다. 처음엔 "이거 쓰는 게 귀찮네" 싶지만, 시간이 지나면 이 부분이 가장 큰 도움이 되더라고요.

또 하나 팁을 드리자면, ADR 문서는 너무 길게 쓰지 않는 게 좋아요. 1~2페이지 분량으로 핵심만 간결하게 정리하는 게 실무에서 유지하기 편합니다.


## ADR을 도입하며 겪은 현실적인 어려움과 극복법

우리 팀도 처음엔 "문서만 늘어나는 거 아니야?"라는 회의적인 시선이 많았어요. 그리고 꾸준히 기록하는 게 쉽지 않아, 몇몇 중요한 결정만 기록하다가 중단된 적도 있죠. 하지만 다음 두 가지 방법으로 극복했습니다:

1. **코드 리뷰 프로세스에 ADR 확인을 포함**: PR을 올릴 때 관련 ADR 문서가 최신인지 반드시 검토하도록 했어요.
2. **자동화 도구 활용**: 위에서 소개한 GitHub Actions 같은 CI 도구로 ADR 문서 형식과 상태를 자동 점검했습니다.

이 과정을 통해 ADR이 단순 문서가 아니라, 팀 내 의사소통과 협업의 핵심 자산이 됐습니다. GitHub 엔지니어링 블로그에서도 ADR을 통해 기술 부채와 운영 제약 조건을 명확히 하여 장기 유지보수에 성공한 사례를 볼 수 있습니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

### 마무리하며: ADR을 시작할 때 꼭 기억할 점

- **완벽하지 않아도 괜찮다**: 처음부터 모든 결정을 다 기록하려고 하면 금방 지칩니다. 중요한 결정부터 차근차근 기록하세요.
- **팀 문화로 자리잡아야 한다**: ADR은 문서 작업이 아니라 팀 내 의사결정 문화를 바꾸는 일입니다.
- **자동화와 연계하면 유지보수가 쉬워진다**: CI/CD 파이프라인과 결합해 문서 품질을 지속적으로 관리하세요.
- **운영 중 발생하는 제약과 기술 부채도 기록하자**: 단순 설계 결정뿐 아니라 현장의 현실도 ADR에 담아야 미래에 큰 도움이 됩니다.

실제로 ADR을 도입하고 나면, "왜 이걸 선택했지?"라는 질문에 당황하지 않고, 팀원 누구나 빠르게 이해할 수 있는 환경이 만들어집니다. 그리고 복잡한 클라우드 마이그레이션이나 서비스 분할도 훨씬 수월해지고요. 여러분 팀에도 꼭 추천합니다!
