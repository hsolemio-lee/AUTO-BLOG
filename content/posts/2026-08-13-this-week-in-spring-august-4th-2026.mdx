## 갑자기 프로덕션에서 메트릭이 안 잡힌다면? Spring Boot 3.2의 새로운 기본 세팅 덕분에 걱정 끝

얼마 전 우리 팀에서 갑자기 프로덕션 환경에서 성능 모니터링이 제대로 안 되는 상황이 벌어졌어요. 원인을 찾아보니, 기존에 직접 설정하던 JVM 튜닝과 메트릭 수집이 누락돼 있었더군요. 그런데 Spring Boot 3.2로 업그레이드하면서 이런 부분이 기본 설정에 포함됐다는 걸 알고 나서는 훨씬 수월해졌습니다.

Spring Boot 3.2 버전에서는 JVM 튜닝 옵션과 메트릭 수집 기능이 기본값으로 들어가서, 별도의 복잡한 설정 없이도 프로덕션 성능 모니터링을 바로 시작할 수 있어요. 예를 들어, `spring.metrics.enabled=true`가 기본값이고, JVM 힙 덤프와 GC 메트릭도 자동으로 수집됩니다. 덕분에 우리 팀은 별도의 커스텀 코드를 추가하지 않고도 CPU 사용률, GC 시간, 힙 메모리 상태를 실시간으로 볼 수 있었죠.

이건 실제로 겪어보면 얼마나 큰 차이인지 체감됩니다. 이전에는 JVM 옵션을 일일이 맞춰줘야 했는데, 이제는 애플리케이션 실행만 하면 기본적인 튜닝과 모니터링이 자동으로 잡히니까요. 물론, 필요에 따라 세부 설정을 더 조정할 수 있지만, 중급 개발자 입장에선 기본값만으로도 충분히 시작할 만합니다.


## REST API 보안, OAuth 2.1과 CSRF 보호 강화 덕분에 한층 안심

요즘 보안 이슈가 워낙 많아서 REST API 보안 강화는 항상 신경 쓰게 되는데요, Spring Framework 6.1에서 OAuth 2.1 지원이 기본으로 들어오고 CSRF 보호도 강화돼서 정말 마음이 놓입니다.

예를 들어, OAuth 2.1 프로토콜이 기본 지원되면서 인증 서버와의 통합이 훨씬 간단해졌고, `@EnableOAuth2Client` 같은 애노테이션과 프로퍼티 설정으로 쉽게 활성화할 수 있어요. CSRF 보호도 REST API에 맞게 기본적으로 더 엄격해져서, 토큰 기반 인증 시에도 CSRF 공격을 방어할 수 있습니다.

아래는 간단한 OAuth 2.1 클라이언트 설정 예시입니다:

```java
@Configuration
@EnableOAuth2Client
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeRequests(authz -> authz
                .anyRequest().authenticated()
            )
            .oauth2Login(withDefaults())
            .csrf(csrf -> csrf
                .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
            );
        return http.build();
    }
}
```

이 설정만으로도 OAuth 2.1 인증과 CSRF 보호가 기본적으로 적용됩니다. 물론, 실제 서비스 환경에서는 세부 정책을 더 세밀하게 조정해야 하지만, 중급 개발자가 시작하기에 훨씬 직관적이고 간단해졌다는 점이 큰 장점이에요.


## GC 튜닝과 커넥션 풀 최적화, 캐시 전략까지: 2026년 최신 프로덕션 성능 팁

프로덕션에서 응답 시간이 갑자기 튀거나 메모리 누수가 의심될 때, 가장 먼저 확인하는 게 GC 로그와 커넥션 풀 상태입니다. Baeldung에서 정리한 2026년 최신 Spring Boot 성능 튜닝 가이드에 따르면, GC 튜닝은 JVM 옵션에서 `-XX:+UseG1GC`를 기본으로 쓰면서, `-XX:MaxGCPauseMillis=200` 정도로 설정하는 게 적당하다고 하더군요. 우리 팀도 이 설정으로 GC가 200ms 이상 멈추는 일이 거의 없어졌습니다.

커넥션 풀은 HikariCP가 기본인데, `maximumPoolSize` 값을 실제 트래픽에 맞게 조정하는 게 중요해요. 예를 들어, 동시 요청이 최대 1000건이라면, 커넥션 풀 크기를 50~100 사이로 맞추고, 커넥션 타임아웃은 30초 정도로 설정하는 게 안정적입니다.

캐시 활용도 빼놓을 수 없는데, Spring Cache 추상화를 통해 Redis 같은 외부 캐시와 쉽게 연동할 수 있어요. 아래는 Redis 캐시 설정 예시입니다:

```java
@Configuration
@EnableCaching
public class CacheConfig {

    @Bean
    public RedisCacheManager cacheManager(RedisConnectionFactory redisConnectionFactory) {
        return RedisCacheManager.builder(redisConnectionFactory)
            .cacheDefaults(RedisCacheConfiguration.defaultCacheConfig()
                .entryTtl(Duration.ofMinutes(10)))
            .build();
    }
}
```

이렇게 하면 10분 TTL을 가진 캐시를 쉽게 적용할 수 있고, DB 부하를 크게 줄일 수 있습니다. 물론 캐시 무효화 정책도 신경 써야 하니, 서비스 특성에 맞게 설계하는 게 중요합니다.


## 점진적 롤아웃 전략, GitHub 사례를 보며 우리 팀에 맞게 적용하기

서비스를 운영하다 보면 새 기능이나 버전을 한꺼번에 배포하는 게 부담스러울 때가 많죠. GitHub 엔지니어링 블로그에서 소개한 대규모 분산 시스템 점진적 롤아웃 전략을 참고하면, Spring 백엔드에도 적용할 수 있는 Canary 배포와 블루-그린 배포 전략을 쉽게 이해할 수 있습니다.

예를 들어, Canary 배포는 전체 트래픽 중 5%만 새 버전으로 보내고 모니터링하다가 이상 없으면 점차 늘려가는 방식입니다. Spring Cloud와 Kubernetes를 함께 쓰면, 서비스 레이블과 트래픽 라우팅을 조정해 Canary 배포를 자동화할 수 있어요.

아래는 Kubernetes에서 Canary 배포를 위한 간단한 서비스 셋업 예시입니다:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
spec:
  selector:
    app: myapp
  ports:
    - protocol: TCP
      port: 80
      targetPort: 8080
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-v1
spec:
  replicas: 8
  selector:
    matchLabels:
      app: myapp
      version: v1
  template:
    metadata:
      labels:
        app: myapp
        version: v1
    spec:
      containers:
      - name: myapp
        image: myapp:v1
        ports:
        - containerPort: 8080
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-v2
spec:
  replicas: 2
  selector:
    matchLabels:
      app: myapp
      version: v2
  template:
    metadata:
      labels:
        app: myapp
        version: v2
    spec:
      containers:
      - name: myapp
        image: myapp:v2
        ports:
        - containerPort: 8080
```

이렇게 하면 전체 10개 인스턴스 중 2개만 새 버전(v2)으로 운영하면서 트래픽 일부만 할당해 안정성을 확인할 수 있죠. 물론, 실제 트래픽 분산은 인그레스 컨트롤러나 서비스 메시를 통해 조절합니다.

이런 점진적 롤아웃은 장애 복구 자동화와도 연결돼서, 문제가 생기면 자동으로 이전 버전으로 롤백하는 스크립트나 파이프라인을 구성하는 게 좋습니다. GitHub 블로그에서 나온 사례처럼, 자동화가 잘 되어 있으면 운영 부담이 크게 줄어들어요.

이번 주 Spring 업데이트를 경험하며 느낀 건, 중급 개발자라도 최신 버전으로 업그레이드하면 기본 세팅만으로도 프로덕션 성능과 보안을 크게 개선할 수 있다는 점입니다. 물론 세부 튜닝과 배포 전략은 서비스 특성에 맞게 조정해야 하지만, Spring Boot 3.2와 Spring Framework 6.1이 제공하는 기본 기능들이 워낙 탄탄해서 시작이 훨씬 수월해졌어요.

개인적으로는 GC 튜닝과 OAuth 2.1 지원, 그리고 점진적 롤아웃 자동화가 가장 인상 깊었습니다. 처음엔 이게 별거 아닌 것 같지만, 실제 운영 환경에서 경험해보면 안정성과 개발 생산성에 미치는 영향이 엄청납니다.

여러분도 이번 기회에 프로덕션 튜닝과 보안 설정, 그리고 배포 전략을 다시 한번 점검해보시길 권합니다. 작은 설정 하나가 서비스 전체 안정성에 큰 차이를 만든다는 걸 직접 체감할 수 있을 겁니다.
