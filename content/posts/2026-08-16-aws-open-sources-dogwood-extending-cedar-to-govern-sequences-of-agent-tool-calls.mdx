### "에이전트 도구 호출이 꼬여서 디버깅만 몇 시간째..." 이런 경험, 다들 있죠?

복잡한 백엔드 시스템에서 여러 에이전트 도구가 순차적으로 호출되고, 실패 시 대체 경로가 필요하며, 조건에 따라 반복 실행도 해야 하는 상황. 이걸 코드로 관리하면 금세 spaghetti 코드가 되기 십상입니다. AWS가 최근 오픈소스로 공개한 Dogwood는 이런 문제를 해결하기 위해 Cedar 정책 언어를 확장한 프레임워크인데요, 직접 써보니 생각보다 쓸모가 많고, 운영 관점에서 명확한 이점이 있더라고요.

---

## Dogwood가 왜 필요한지, Cedar와 뭐가 다른지

기존 Cedar는 AWS에서 만든 정책 언어로, 보안이나 접근 제어 같은 단일 이벤트 중심 정책에 강점이 있었습니다. 그런데 에이전트 도구 호출처럼 "순서"와 "시퀀스"가 중요한 워크플로우를 관리하려면 기본 Cedar로는 한계가 있었죠. 그래서 Dogwood는 Cedar를 확장해 호출 순서, 조건부 분기, 실패 처리, 반복 실행 같은 시퀀스 제어 기능을 추가했습니다.

실제로 Dogwood를 도입하면 이런 식으로 정책 언어로 워크플로우를 정의할 수 있습니다. 예를 들어, 에이전트 A가 성공해야 에이전트 B가 실행되고, 실패하면 에이전트 C를 호출하는 식으로요. 이걸 코드가 아니라 정책으로 관리하니, 복잡한 로직이 훨씬 깔끔해지고 변경도 정책만 수정하면 되니 유지보수성이 확 올라갑니다.

> Dogwood는 AWS가 오픈소스로 공개한 확장된 Cedar 프레임워크로, 에이전트 도구 호출의 연속적인 워크플로우를 관리하기 위한 정책 언어를 제공한다. 이를 통해 복잡한 백엔드 시스템 내에서 에이전트 도구의 호출 순서와 조건부 실행을 세밀하게 제어할 수 있다.[AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/)


## Dogwood 정책 언어, 기본 문법과 시퀀스 확장 기능은 꼭 익혀야 할 부분

Dogwood를 운영하려면 Cedar의 기본 문법은 물론, 시퀀스 제어를 위한 확장 기능을 이해하는 게 필수입니다. 처음에 저도 "그냥 정책 언어겠지" 싶었는데, 시퀀스 제어가 들어가면서 문법이 꽤 복잡해지더군요.

예를 들어, 아래는 Dogwood 정책의 간단한 예시입니다. 에이전트 도구 호출 순서를 정의하고, 실패 시 대체 경로를 지정하는 부분을 담고 있죠.

```cedar
policy AgentWorkflow {
  sequence {
    call AgentA
    onSuccess {
      call AgentB
    }
    onFailure {
      call AgentC
    }
  }
}
```

이 정책은 AgentA 호출 후 성공하면 AgentB를 호출하고, 실패하면 AgentC를 호출하는 간단한 시퀀스를 정의합니다. 실제 환경에서는 이보다 훨씬 복잡한 조건과 반복, 데이터 전달 로직이 필요하지만, Dogwood는 이런 패턴을 정책 레벨에서 깔끔하게 관리할 수 있게 해줍니다.

> Dogwood를 운영하기 위해서는 Cedar 정책 언어의 기본 문법과 시퀀스 제어 확장 기능을 이해하는 것이 필수적이다. 이를 통해 각 에이전트 도구 호출의 전후 관계, 실패 시 대체 경로, 반복 실행 등의 복잡한 패턴을 구현할 수 있다.[AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/)


## Spring 백엔드에 Dogwood를 적용했을 때 얻는 실질적 이점

우리 팀은 Spring 기반 마이크로서비스 아키텍처에서 에이전트 도구 호출이 많아지면서 호출 순서, 실패 처리, 상태 관리가 점점 골치 아파졌습니다. 그래서 Dogwood 도입을 시도했는데, 정책 중심으로 워크플로우를 분리하니 몇 가지 큰 이점이 있더군요.

- **마이크로서비스 의존성 분리**: 각 서비스가 호출 순서나 실패 처리 로직에 신경 쓸 필요 없이 정책만 따르니 서비스 코드가 훨씬 단순해졌습니다.
- **유지보수성 향상**: 정책 파일만 수정하면 워크플로우 전체가 바뀌니, 코드 배포 없이도 빠른 대응이 가능했습니다.
- **테스트 용이성**: 정책 시뮬레이션으로 다양한 시나리오를 쉽게 검증할 수 있었습니다.

물론 단점도 있죠. 정책 언어를 새로 배우고, Dogwood 런타임을 운영 환경에 통합하는 초기 진입 장벽이 있습니다. 하지만 장기적으로 보면 복잡한 에이전트 호출 관리에는 훨씬 효율적입니다.

> Dogwood의 도입은 Spring 기반 백엔드 시스템에서 에이전트 도구 호출을 체계적으로 관리하는 데 적합하며, 이를 통해 마이크로서비스 간의 복잡한 의존성과 상태 관리를 정책 중심으로 분리하여 유지보수성을 향상시킬 수 있다.[AWS Well-Architected Framework](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html)


## Dogwood 워크플로우 설계 시 꼭 고민해야 할 세 가지 결정 지점

Dogwood로 워크플로우를 설계할 때, 저희가 실제로 가장 많이 고민했던 지점이 세 가지 있습니다.

1. **호출 순서 명확화**: 어떤 에이전트가 먼저 실행되고, 어떤 조건에서 다음 호출로 넘어가는지 정책에 정확히 정의해야 합니다. 애매하면 예측 불가능한 동작이 나와서 디버깅 지옥으로 빠집니다.

2. **실패 처리 정책**: 실패 시 재시도, 대체 경로, 에러 로깅 등 행동을 명확히 정해야 해요. Dogwood는 `onFailure` 같은 구문으로 이를 지원하지만, 정책 설계가 복잡해질수록 꼼꼼한 테스트가 필수입니다.

3. **데이터 전달 방식**: 에이전트 간에 결과나 상태를 어떻게 넘길지 고민해야 합니다. Dogwood 정책 내에서 변수나 상태를 관리하는 방법을 잘 익혀야, 복잡한 워크플로우도 깔끔하게 유지할 수 있습니다.

이 세 가지를 명확히 설계하면, Dogwood 덕분에 백엔드 동작이 훨씬 예측 가능해지고, 장애 발생 시 원인 파악과 대응도 빨라집니다.

> Dogwood를 활용한 워크플로우 설계 시 주요 결정 지점은 호출 순서의 명확한 정의, 실패 처리 정책의 설정, 그리고 에이전트 도구 간 데이터 전달 방식이다. 이러한 패턴을 명확히 설계함으로써 예측 가능한 백엔드 동작을 보장할 수 있다.[AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/)

## 실제 Dogwood 정책 예시: 에이전트 호출과 실패 처리

아래는 저희가 실제로 사용한 Dogwood 정책 예시입니다. 3단계 에이전트 호출 중 두 번째가 실패하면 대체 경로를 타도록 설계했어요.

```cedar
policy ComplexAgentWorkflow {
  sequence {
    call Agent1
    onSuccess {
      call Agent2
      onFailure {
        call FallbackAgent
      }
    }
    onSuccess {
      call Agent3
    }
  }
}
```

이렇게 하면 Agent1 성공 → Agent2 호출 → Agent2 실패 시 FallbackAgent 호출 → Agent2 성공 시 Agent3 호출 순서로 진행됩니다. 정책만 수정하면 언제든지 흐름을 바꿀 수 있어, 운영 중에도 유연하게 대응 가능했습니다.

## 마무리하며: Dogwood 도입 전 꼭 해봐야 할 것들

- **Cedar 기본 문법과 Dogwood 시퀀스 확장 기능을 먼저 익히세요.** 정책 언어를 제대로 이해해야 실무에서 헷갈리지 않습니다.
- **작은 워크플로우부터 시작해 점진적으로 확장하세요.** 처음부터 복잡한 정책을 쓰면 관리가 어려워집니다.
- **테스트 자동화에 신경 쓰세요.** 정책 변경 시 시뮬레이션과 통합 테스트를 꼭 돌려야 합니다.
- **Spring 백엔드에 통합할 때는 정책과 서비스 간 인터페이스를 명확히 정의하세요.** 데이터 전달과 실패 처리 로직이 깔끔해야 운영이 편합니다.

Dogwood는 아직 신생 오픈소스라 커뮤니티도 작고 문서도 계속 업데이트 중입니다. 하지만 복잡한 에이전트 도구 호출 관리에 정책 중심 접근법을 고민 중이라면 꼭 한번 써볼 만한 툴입니다. 저도 직접 써보면서 "이런 게 진짜 생산성이다" 싶었거든요.
