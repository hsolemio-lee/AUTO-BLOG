### "어제 얘기한 거 기억해?" — AI 에이전트도 사람처럼 기억이 필요하다

최근에 우리 팀에서 AI 에이전트를 만들면서 가장 골치 아팠던 부분 중 하나가 바로 ‘세션 간 기억 유지’였어요. 단순히 한 번 대화하다 끊기면 그때그때 초기화되는 게 아니라, 사용자가 이전에 나눈 대화나 상태를 꾸준히 기억해야 하니까요. 이걸 제대로 구현하지 않으면 사용자가 다시 접속할 때마다 맥락이 사라져서 매번 새로 시작하는 느낌이 들죠.

그래서 이번에 Spring 기반 백엔드에서 AutoMemoryTools라는 패턴을 적용해 봤는데, 생각보다 꽤 쓸 만했습니다. 특히 Spring Boot가 제공하는 다양한 데이터 저장소 연동 지원 덕분에 세션 간 메모리 유지가 한결 수월해졌어요.

---

## Spring Boot가 세션 메모리 지속성에 왜 좋은 선택인지

Spring Boot는 기본적으로 다양한 데이터 저장소(RDBMS, Redis, MongoDB 등)와의 연동이 매우 쉽죠. 덕분에 AI 에이전트가 세션 상태나 컨텍스트를 데이터베이스나 캐시 같은 곳에 저장해두고, 다음 세션에 다시 불러오는 작업이 자연스럽게 이뤄집니다.

예를 들어, Redis를 세션 메모리 저장소로 쓰면 읽기/쓰기 속도가 매우 빠르고, 장애 시 복구도 편리해서 실제 서비스에서 많이 쓰이는데요. Spring Boot는 `spring-boot-starter-data-redis` 같은 스타터 패키지 덕분에 설정 몇 줄로 바로 연결할 수 있죠.

이런 강력한 지원 덕분에 AI 에이전트가 상태를 잃지 않고, 사용자와의 대화 흐름을 자연스럽게 이어갈 수 있습니다. 실제로 우리 프로젝트에서는 Redis를 통해 10만 건 이상의 세션 데이터를 100ms 내외 응답 속도로 처리하고 있어요.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)

## Spring 핵심 기술로 메모리 관리 로직을 깔끔하게 모듈화하기

Spring Framework의 의존성 주입(DI)과 AOP는 메모리 관리 코드를 깔끔하게 분리하고 재사용할 수 있게 해줍니다. AutoMemoryTools 같은 패턴을 구현할 때 이게 정말 큰 장점이었는데요.

예를 들어, 메모리 저장소와 조회 로직을 별도의 컴포넌트로 분리하고, 서비스 레이어에서는 단순히 `@Autowired`로 주입받아 쓰기만 하면 됩니다. AOP를 활용하면 메서드 실행 전후에 메모리 상태를 자동으로 저장하거나 불러오는 작업도 쉽게 처리할 수 있죠.

```java
@Component
public class AgentMemoryRepository {
    private final RedisTemplate<String, Object> redisTemplate;

    public AgentMemoryRepository(RedisTemplate<String, Object> redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    public void saveMemory(String sessionId, AgentMemory memory) {
        redisTemplate.opsForValue().set(sessionId, memory, Duration.ofHours(1));
    }

    public Optional<AgentMemory> loadMemory(String sessionId) {
        AgentMemory memory = (AgentMemory) redisTemplate.opsForValue().get(sessionId);
        return Optional.ofNullable(memory);
    }
}

@Service
public class AgentService {
    private final AgentMemoryRepository memoryRepository;

    public AgentService(AgentMemoryRepository memoryRepository) {
        this.memoryRepository = memoryRepository;
    }

    public AgentResponse handleRequest(String sessionId, AgentRequest request) {
        AgentMemory memory = memoryRepository.loadMemory(sessionId).orElse(new AgentMemory());
        // 메모리 기반으로 AI 에이전트 로직 수행
        AgentResponse response = processWithMemory(request, memory);
        memoryRepository.saveMemory(sessionId, memory);
        return response;
    }

    private AgentResponse processWithMemory(AgentRequest request, AgentMemory memory) {
        // 실제 AI 처리 로직 (OpenAI API 호출 등)
        return new AgentResponse("응답 내용");
    }
}
```

이렇게 하면 메모리 저장과 조회가 완전히 분리되어, 나중에 저장소를 바꾸거나 캐싱 전략을 변경할 때도 서비스 코드를 거의 건드리지 않아도 됩니다.[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)

## 성능 튜닝 없이 지속 메모리 구현은 무의미하다

메모리를 지속시키는 게 중요한 건 맞지만, 성능을 신경 안 쓰면 사용자 경험이 오히려 나빠질 수 있어요. Spring Boot의 성능 튜닝 가이드에서는 캐싱, 비동기 처리, DB 커넥션 풀링 등을 적극 활용하라고 권장합니다.

우리 팀도 Redis 캐싱과 비동기 호출을 적절히 섞어서 메모리 저장/조회 속도를 50ms 이하로 유지하고 있습니다. 특히 데이터베이스 커넥션 풀 크기를 30으로 늘리고, 비동기 메서드에 `@Async`를 붙여서 병목 현상을 줄였어요.

```java
@EnableAsync
@Configuration
public class AsyncConfig {
    @Bean(name = "taskExecutor")
    public Executor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(10);
        executor.setMaxPoolSize(30);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("AsyncExecutor-");
        executor.initialize();
        return executor;
    }
}

@Service
public class AgentMemoryService {
    @Async("taskExecutor")
    public CompletableFuture<Void> saveMemoryAsync(String sessionId, AgentMemory memory) {
        // 비동기 저장 처리
        memoryRepository.saveMemory(sessionId, memory);
        return CompletableFuture.completedFuture(null);
    }
}
```

이런 최적화 덕분에 AI 에이전트가 복잡한 상태를 유지하면서도 빠르게 반응할 수 있었어요. 물론, 비동기 처리는 상태 일관성 유지에 주의해야 하니 트랜잭션 경계와 동기화 전략도 함께 고려해야 합니다.[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance)

## OpenAI API와 연동해 세션 컨텍스트를 자연스럽게 이어가는 법

OpenAI API는 토큰 기반 대화 기록 관리 기능을 제공해서, 세션별 컨텍스트를 유지하는 데 큰 도움이 됩니다. Spring 백엔드에서 이 기능을 활용하면, AutoMemoryTools 패턴으로 저장한 메모리를 API 호출 시 프롬프트에 반영해 자연스러운 대화 흐름을 만들 수 있죠.

```java
public class OpenAiClient {
    private final WebClient webClient;

    public OpenAiClient(WebClient.Builder webClientBuilder) {
        this.webClient = webClientBuilder.baseUrl("https://api.openai.com/v1").build();
    }

    public Mono<ChatResponse> chatWithMemory(String sessionId, AgentMemory memory, String userInput) {
        ChatRequest request = new ChatRequest();
        request.setMessages(memory.getMessages());
        request.addMessage(new Message("user", userInput));

        return webClient.post()
                .uri("/chat/completions")
                .header("Authorization", "Bearer " + System.getenv("OPENAI_API_KEY"))
                .bodyValue(request)
                .retrieve()
                .bodyToMono(ChatResponse.class);
    }
}
```

이처럼 이전 세션에서 저장한 메시지들을 `memory.getMessages()`로 불러와서 프롬프트에 넣으면, 에이전트가 마치 사용자의 기억을 이어받은 듯 자연스럽게 대화할 수 있습니다. 물론, 토큰 제한 때문에 오래된 대화는 요약하거나 삭제하는 전략도 필요합니다.[OpenAI API Documentation](https://platform.openai.com/docs/overview)

## 프롬프트 설계에 메모리 유지 전략을 녹여내는 게 생각보다 까다롭다

Anthropic의 프롬프트 엔지니어링 가이드를 참고하면, 단순히 이전 대화 기록을 붙이는 것보다 ‘어떤 정보’를 ‘어떻게’ 기억시킬지 고민하는 게 중요하다고 합니다. 예를 들어, 사용자의 선호도, 최근 대화 요점, 특정 키워드 같은 핵심 정보만 선별해서 메모리에 저장하는 게 훨씬 효율적이죠.

우리도 처음에는 모든 대화 내용을 다 저장했다가 토큰 제한에 걸려서 고생했는데, 지금은 중요한 정보 위주로 요약해서 저장하는 로직을 추가해 문제를 해결했습니다. 이런 전략은 프롬프트 길이를 최적화하고, API 호출 비용도 절감하는 부수 효과가 있습니다.[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)

### 직접 써보니 느낀 점과 앞으로 개선할 부분

처음에는 세션 간 메모리 유지가 ‘그냥 데이터 저장’인 줄 알았는데, 실제로 해보면 단순 저장 이상의 고민이 많더라고요. 저장소 선택, 성능 튜닝, 프롬프트 설계, 비동기 처리, 그리고 무엇보다 상태 일관성 유지까지 신경 쓸 게 많습니다.

하지만 Spring Boot와 그 생태계가 워낙 잘 갖춰져 있어서, AutoMemoryTools 같은 패턴을 적용하는 게 생각보다 어렵지 않았어요. 특히 Redis와 WebClient 조합은 빠르고 안정적이었고, 의존성 주입 덕분에 테스트도 편했습니다.

앞으로는 메모리 요약 알고리즘을 좀 더 고도화하고, 분산 환경에서 메모리 동기화 문제도 해결하는 쪽으로 개선할 계획입니다.

- 프롬프트에 넣을 메모리는 꼭 요약하거나 필터링해서 토큰 낭비를 줄이세요.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
