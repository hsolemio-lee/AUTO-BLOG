## "Fat-Tree 네트워크? 라우터가 너무 많아서 비용 폭탄이었죠"

최근 AWS가 데이터 센터 네트워크 구조를 완전히 뒤집었습니다. 기존에 우리가 흔히 알고 있던 Fat-Tree 토폴로지를 버리고 무작위 그래프(random graph) 이론을 적용한 새로운 네트워크를 구축했는데요. 덕분에 라우터 수를 무려 69%나 줄이는 데 성공했다고 합니다. 이게 단순한 네트워크 토폴로지 변경을 넘어서 백엔드 아키텍처 설계에도 시사하는 바가 크더라고요.

처음엔 “네트워크 구조가 백엔드랑 무슨 상관이야?” 싶을 수 있지만, 이게 생각보다 우리 서비스의 비용과 확장성, 복원력에 직접적인 영향을 줍니다.


## AWS가 왜 Fat-Tree를 포기했을까? 무작위 그래프가 뭐길래?

Fat-Tree 구조는 대규모 데이터 센터에서 흔히 쓰이는 계층적 네트워크 설계입니다. 스위치와 라우터를 여러 계층에 걸쳐 배치해서 모든 서버가 고르게 연결되도록 하는 방식이죠. 하지만 이 구조는 라우터 수가 급격히 늘어나고, 비용과 전력 소비가 커지는 단점이 있습니다.

AWS는 여기에 무작위 그래프 이론을 도입했습니다. 무작위 그래프는 노드들이 무작위로 연결된 형태를 뜻하는데, 여기서는 네트워크 장비들이 계층적이지 않고 좀 더 유연하게 연결됩니다. 이 덕분에 전체 라우터 수를 69%나 줄일 수 있었고, 비용 절감과 확장성 두 마리 토끼를 잡았죠.

이 접근법은 기존의 계층적 네트워크가 가진 병목과 비효율을 줄이고, 네트워크 복원력(resilience)도 높여줍니다. 즉, 장애가 발생해도 네트워크가 쉽게 끊기지 않고 빠르게 복구됩니다.


## 백엔드 엔지니어가 이걸 어떻게 활용할 수 있을까?

이걸 우리 백엔드 서비스 설계에 바로 적용할 수 있는 건 아니지만, 생각해볼 점은 많습니다. AWS도 이 혁신을 통해 비용 최적화와 확장성 확보라는 Well-Architected Framework의 핵심 원칙을 충족시켰는데요.

우리도 서비스 아키텍처를 설계할 때, 무조건 계층적이고 정형화된 구조에 얽매이지 말고 자원 배치와 네트워크 토폴로지를 재고해보자는 겁니다. 예를 들어, 마이크로서비스 간 통신 경로나 데이터 복제 경로를 단순한 계층 구조에만 맡기지 않고, 좀 더 무작위적이면서도 복원력 높은 연결 방식을 고민해볼 수 있죠.


## 실제로 무작위 그래프 컨셉을 적용해본 코드 예시

간단한 시뮬레이션으로, 서비스 인스턴스들이 무작위로 서로 연결된 네트워크를 구성하는 예를 들어볼게요. 이 코드는 각 노드가 일정 수의 랜덤한 이웃과 연결되어 있는 그래프를 생성합니다.

```python
import random

class ServiceNode:
    def __init__(self, id):
        self.id = id
        self.connections = set()

    def connect(self, other):
        self.connections.add(other)
        other.connections.add(self)


def create_random_graph(num_nodes, connections_per_node):
    nodes = [ServiceNode(i) for i in range(num_nodes)]
    for node in nodes:
        while len(node.connections) < connections_per_node:
            target = random.choice(nodes)
            if target != node and target not in node.connections:
                node.connect(target)
    return nodes

# 예: 10개의 서비스 인스턴스, 각 인스턴스는 3개의 랜덤 연결을 가짐
nodes = create_random_graph(10, 3)

for node in nodes:
    print(f"Service {node.id} connected to {[n.id for n in node.connections]}")
```

이런 무작위 연결 구조는 장애가 발생해도 다른 경로를 통해 통신이 가능하도록 해 복원력을 높입니다. 물론 모든 상황에 최적은 아니고, 관리 복잡도가 올라갈 수 있으니 적절한 모니터링과 장애 대응 전략이 필요합니다.


## 비용과 확장성, 복원력 모두 잡으려면 네트워크 토폴로지부터 다시 생각해야

AWS 사례를 보면서 느낀 건, 백엔드 아키텍처 설계에서 네트워크 토폴로지나 자원 배치 같은 기본적인 인프라 구조를 다시 고민하는 게 얼마나 중요한지입니다. 단순히 코드나 서비스 레벨에만 집중하면 놓치기 쉬운 부분이죠.

무작위 그래프 이론을 적용해 라우터 수를 69% 줄인 AWS의 혁신은, 우리도 클라우드 비용 절감과 서비스 확장성, 장애 대응 능력을 동시에 개선할 수 있다는 자신감을 줍니다.

물론 새로운 구조 도입은 초기 투자와 학습 비용이 따르고, 관리 복잡도가 증가할 수 있습니다. 하지만 장기적으로 보면 비용과 성능, 안정성에서 얻는 이득이 훨씬 크죠.


## 마치며: 백엔드 아키텍처 설계에 무작위 그래프 이론을 어떻게 녹일까?

- 기존에 당연하게 여겼던 계층적 구조를 무작위적이고 유연한 연결로 바꿔보자
- 네트워크 복원력을 높이기 위해 다중 경로와 비정형 토폴로지를 고민하자
- 비용 최적화와 확장성을 위해 자원 배치와 네트워크 설계를 함께 고려하자
- 작은 규모 시뮬레이션이나 프로토타입부터 시작해 점진적으로 적용해보자

이런 시도는 단순히 네트워크 장비만의 문제가 아니라, 백엔드 시스템 전체의 아키텍처 혁신으로 이어질 수 있습니다. AWS가 보여준 사례가 우리에게 좋은 출발점이 되길 바랍니다.
