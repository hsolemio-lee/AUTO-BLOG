## AWS 멀티 리전 API, 왜 네트워크 왕복이 숨어 있을까?

얼마 전 우리 팀에서 멀티 리전 AWS API를 운영하면서 이상한 지연 현상을 발견했어요. 사용자 요청이 특정 리전에서 처리되는데도 불구하고 응답 시간이 너무 길었던 거죠. 로그를 보니 API 호출은 한 번인데 내부적으로는 여러 리전을 왔다 갔다 하는 네트워크 왕복이 숨어 있더라고요. 이걸 찾아내고 없애는 과정에서 배운 점을 공유하려고 합니다.

멀티 리전 아키텍처는 지연 시간과 가용성을 줄이기 위해 필수적이지만, 잘못 설계하면 리전 간 호출이 불필요하게 많아져서 오히려 성능과 비용에 악영향을 줍니다. 특히 AWS 리전 간 데이터 전송 비용은 꽤 비싸서, 숨겨진 왕복을 제거하는 게 비용 최적화에도 직접 연결됩니다.


## 분산 추적으로 API 호출 경로를 낱낱이 파헤치기

숨겨진 네트워크 왕복을 찾으려면, 단순 로그 분석만으로는 부족해요. API 호출이 내부적으로 어떤 서비스들을 거치고, 어떤 리전을 오가는지 정확히 파악해야 하거든요. 그래서 분산 추적(distributed tracing) 도구를 도입했습니다. AWS X-Ray 같은 도구를 활용하면, API 요청이 각 서비스와 리전에서 얼마나 지연되는지 시각적으로 볼 수 있어요.

실제로 우리 서비스는 API Gateway → 리전 A의 인증 서비스 → 리전 B의 데이터 서비스 순으로 호출이 이어졌는데, 리전 A와 B 사이 왕복이 150ms 이상 지연을 유발하는 걸 발견했습니다. 이왕복은 클라이언트 요청 하나당 매번 발생해서, 전체 응답 시간이 300ms 넘게 늘어나더라고요.

```java
// AWS X-Ray SDK를 활용한 간단한 분산 추적 예시
import com.amazonaws.xray.AWSXRay;
import com.amazonaws.xray.entities.Subsegment;

public class DataServiceClient {
    public String fetchData(String id) {
        Subsegment subsegment = AWSXRay.beginSubsegment("fetchDataFromRegionB");
        try {
            // 리전 B API 호출
            String response = callRegionBApi(id);
            return response;
        } finally {
            AWSXRay.endSubsegment();
        }
    }
}
```

이처럼 각 서비스 호출마다 세분화된 추적을 걸어두면, 어디서 병목이 발생하는지 명확해집니다.


## API 게이트웨이와 백엔드 간 직접 경로를 만드는 게 핵심

왕복을 줄이려면, API Gateway가 백엔드 서비스와 직접 소통하도록 경로를 최적화해야 합니다. 우리 사례에서는 API Gateway가 리전 A에만 배포되어 있었는데, 데이터 서비스가 리전 B에 있어서 리전 A → 리전 B로 매번 왕복이 생겼어요.

그래서 리전별로 API Gateway를 배포하고, 클라이언트 요청이 해당 리전의 API Gateway를 거치게 했습니다. 그리고 인증 정보는 각 리전에서 로컬로 검증하도록 캐시 전략을 도입했죠. 이렇게 하니 리전 간 호출이 70% 이상 줄었고, 응답 시간도 평균 120ms 단축됐습니다.

AWS Well-Architected Framework에서도 멀티 리전 아키텍처에서 데이터 접근 지연을 줄이려면 이런 직접 통신 경로 최적화를 권장합니다[https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html).


## 리전 간 데이터 복제를 활용해 지연과 비용을 동시에 잡기

리전 간 호출을 완전히 없앨 수는 없으니, 데이터 복제 전략도 함께 고민해야 해요. 우리 팀은 DynamoDB 글로벌 테이블을 도입해서 각 리전별로 데이터가 로컬에 복제되도록 했습니다. 덕분에 읽기 요청은 항상 로컬 리전에서 처리되고, 쓰기 지연도 크게 줄었죠.

하지만 데이터 복제에도 단점이 있습니다. 쓰기 충돌 가능성과 복제 지연으로 인한 일관성 문제를 감수해야 해요. 그래서 우리 팀은 쓰기 작업을 특정 리전으로 집중시키고, 읽기는 어디서든 가능하도록 CQRS 패턴을 일부 적용했습니다. 이게 처음엔 복잡해 보였지만, 실제 운영해보니 성능과 비용 모두 크게 개선됐어요.


## GitHub 엔지니어링 팀의 비동기 호출과 캐시 전략도 참고할 만해

GitHub 엔지니어링 팀도 멀티 리전 API에서 네트워크 지연 문제를 해결하기 위해 서비스 간 호출을 비동기화하고, 캐시를 적극 활용했다고 해요. 이 방식은 리전 간 호출을 줄이면서도 데이터 신선도를 어느 정도 유지할 수 있는 현실적인 타협점입니다[https://github.blog/category/engineering/](https://github.blog/category/engineering/).

우리도 비슷하게, 사용자 프로필 정보 같은 자주 변하지 않는 데이터는 리전별 캐시에 저장하고, 변경 시 비동기 이벤트로 동기화하는 방식을 도입했습니다. 덕분에 불필요한 리전 간 호출이 40% 감소했죠.


## 서비스 경계와 데이터 소유권을 명확히 하면 근본 해결책이 된다

마틴 파울러의 아키텍처 가이드에서도 멀티 리전 API의 네트워크 왕복 문제는 서비스 경계와 데이터 소유권을 명확히 정의하는 게 근본적인 해결책이라고 합니다[https://martinfowler.com/architecture/](https://martinfowler.com/architecture/). 즉, 각 리전이 독립적으로 데이터를 처리하고 소유하도록 설계하면, 리전 간 호출이 자연스럽게 줄어듭니다.

우리 팀도 이번 기회에 서비스별 데이터 소유권을 다시 정리하고, 리전별 독립성을 강화하는 방향으로 아키텍처를 리팩토링 중입니다. 물론 이 과정에서 데이터 중복과 복잡성 관리가 어려워지지만, 장기적으로는 성능과 확장성에 큰 도움이 될 거라 기대하고 있어요.


## 마치며: 숨겨진 왕복, 그냥 지나치지 말자

멀티 리전 AWS API에서 숨겨진 네트워크 왕복은 처음엔 눈에 잘 안 띄지만, 실제로 겪어보면 사용자 경험과 비용에 큰 영향을 줍니다. 분산 추적으로 호출 경로를 낱낱이 파악하고, API Gateway와 백엔드 간 직접 경로를 최적화하며, 데이터 복제와 캐시 전략을 적절히 조합하는 게 핵심입니다.

우리 팀 경험을 정리하면 다음과 같습니다:

- AWS X-Ray 같은 분산 추적 도구로 리전 간 호출과 지연을 시각화하자
- 리전별 API Gateway 배포와 로컬 인증 캐시로 불필요한 왕복 줄이기
- DynamoDB 글로벌 테이블 같은 데이터 복제로 읽기 지연 최소화
- 비동기 호출과 캐시 전략으로 리전 간 호출 횟수 줄이기
- 서비스 경계와 데이터 소유권을 명확히 하여 아키텍처 근본 개선

이 방법들은 단순히 성능 개선뿐 아니라 AWS 데이터 전송 비용 절감에도 직결됩니다. 멀티 리전 API를 운영 중이라면 꼭 한 번 점검해보세요.
