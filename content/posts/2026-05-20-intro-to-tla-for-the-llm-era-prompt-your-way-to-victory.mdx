## "이번 AI 에이전트가 또 엉뚱한 행동을?"  
최근 우리 팀에서 LLM 기반 에이전트 워크플로우를 운영하면서 가장 골치 아팠던 건, 예기치 않은 상태 전이와 오류 처리 누락이었다. “왜 이 상태에서 저런 응답이 나오지?” 하면서 디버깅에만 며칠을 쓴 적도 한두 번이 아니다.  
이런 문제를 근본적으로 줄일 수 있는 방법은 없을까? 바로 TLA+라는 형식 명세 도구를 알게 된 뒤부터 생각이 바뀌었다. 복잡한 분산 시스템 명세에 쓰이는 TLA+가 AI 에이전트 워크플로우 설계에도 딱 맞는다는 걸 직접 경험했기 때문이다.

## TLA+가 AI 에이전트 워크플로우 설계에 딱 맞는 이유

TLA+는 상태 머신(state machine) 기반으로 시스템을 수학적으로 엄밀하게 명세하고, 가능한 모든 상태 전이를 검증할 수 있는 도구다. 복잡한 분산 시스템에서 발생할 수 있는 교착 상태, 경쟁 조건, 예외 상황을 미리 찾아내는 데 탁월하다.  
Martin Fowler의 소프트웨어 아키텍처 가이드에서도 TLA+가 복잡한 분산 시스템과 AI 워크플로우 명세에 적합하다고 강조한다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

AI 에이전트 워크플로우 역시 여러 상태와 조건을 가진 복잡한 분산 시스템과 다를 바 없다. 예를 들어, 에이전트가 여러 API를 호출하고, 실패 시 재시도하거나 다른 경로로 우회하는 로직이 복잡할 때, TLA+로 명확하게 상태와 전이 조건을 정의하면 예상치 못한 버그를 크게 줄일 수 있다.

## LLM 시대에 Prompt 엔지니어링과 TLA+가 만나면 생기는 시너지

LLM(대형 언어 모델)을 활용한 AI 시스템은 입력 프롬프트가 곧 동작 명세라고 할 수 있다. 그런데 프롬프트가 애매하면 모델이 엉뚱한 답변을 내놓거나, 워크플로우가 꼬이는 일이 빈번하다. Anthropic의 프롬프트 엔지니어링 가이드에서도 명확한 입력 명세와 검증이 AI 시스템 신뢰성을 높이는 핵심이라고 말한다[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

여기서 TLA+가 빛을 발한다. 프롬프트로 유도하려는 워크플로우를 TLA+로 먼저 명세하고, 상태 전이와 오류 처리 로직을 수학적으로 검증한 뒤, 그 명세를 바탕으로 프롬프트를 설계하면 훨씬 예측 가능한 동작을 얻을 수 있다.

예를 들어, OpenAI API 문서에서도 에이전트 기반 AI 워크플로우 설계 시 명확한 상태 전이와 오류 처리 로직 사전 정의의 중요성을 강조하는데, TLA+의 상태 머신 모델링과 딱 맞아떨어진다[OpenAI API Documentation](https://platform.openai.com/docs/overview).

## 실제로 TLA+로 AI 워크플로우를 모델링해보니

간단한 예로, LLM 에이전트가 사용자 요청을 받아 처리하고, 실패 시 재시도하거나 대체 경로로 넘어가는 워크플로우를 TLA+로 명세해보자.

```tla
---- MODULE AgentWorkflow ----
EXTENDS Naturals, Sequences

VARIABLES state

(* 상태 정의 *)
States == {"Idle", "Processing", "Success", "Retry", "Failed"}

(* 초기 상태 *)
Init == state = "Idle"

(* 상태 전이 *)
Next == \/ (state = "Idle" /\ state' = "Processing")
        \/ (state = "Processing" /\ state' = "Success")
        \/ (state = "Processing" /\ state' = "Retry")
        \/ (state = "Retry" /\ state' = "Processing")
        \/ (state = "Retry" /\ state' = "Failed")

(* 사전 조건: 상태는 항상 States 집합에 속해야 함 *)
TypeInvariant == state \in States

Spec == Init /\ [][Next]_state /\ []TypeInvariant

====
```

이 간단한 명세에서 보듯, 상태와 가능한 전이 경로를 명확히 정의하고, "Retry" 상태에서 재처리하거나 실패로 넘어가는 경로도 빠뜨리지 않고 체크할 수 있다. 이걸 TLA+ 모델 검사기로 돌리면, 교착 상태나 도달 불가능한 상태가 없는지, 무한 재시도 루프는 없는지 검증할 수 있다.

이걸 실제 프롬프트 설계에 반영하면, 예를 들어 "재시도는 최대 3회까지만 허용한다" 같은 정책을 명확히 하고, 그에 맞는 프롬프트 문구와 후처리 로직을 만들 수 있다.

## TLA+ 도입 시 겪은 현실적인 어려움과 극복법

처음 TLA+를 접하면 수학적 표기법과 모델링 개념이 낯설어 진입 장벽이 꽤 높다. 팀에 형식 명세 경험자가 없으면 더 어렵다.  
하지만 GitHub 엔지니어링 블로그에서도 말하듯, 복잡한 백엔드 시스템에서 형식 명세와 자동 검증 도구를 도입하면 버그가 눈에 띄게 줄고 신뢰성이 올라간다[GitHub Engineering Blog](https://github.blog/category/engineering/).

우리 팀도 처음에는 간단한 워크플로우부터 TLA+로 명세하고, 점차 복잡한 시나리오로 확장했다.  
그리고 Cloudflare의 대규모 분산 시스템 설계 사례처럼 명확한 명세와 검증 프로세스가 안정성에 얼마나 큰 도움이 되는지 몸소 느꼈다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

한 가지 팁은, 너무 복잡한 세부 구현까지 한꺼번에 명세하려 하지 말고, 핵심 상태와 전이, 오류 처리 로직 위주로 단계별로 모델을 확장하는 것이다.  
이렇게 하면 팀원들도 조금씩 익숙해지고, 점진적으로 신뢰성을 높일 수 있다.

## 백엔드 엔지니어가 TLA+와 함께 AI 에이전트 신뢰성을 높이는 법

- **핵심 상태와 전이부터 명확히 정의하기:** AI 에이전트가 어떤 상태를 거치고, 어떤 이벤트에 따라 상태가 바뀌는지 TLA+로 먼저 모델링하세요.

- **오류 처리와 재시도 정책을 빼먹지 말기:** 실패 시 어떻게 대처하는지 명확히 하여 무한 루프나 교착 상태를 방지해야 합니다.

- **프롬프트 설계에 명세 결과 반영하기:** TLA+ 모델을 기반으로 프롬프트 문구를 작성하고, 예상 가능한 모든 시나리오를 커버하세요.

- **점진적 도입과 팀 내 공유:** 처음부터 완벽한 명세를 기대하지 말고, 작은 워크플로우부터 시작해 팀과 함께 학습하세요.

- **자동 검증 도구 활용:** TLA+ 모델 검사기를 적극 활용해 가능한 모든 상태 전이를 자동으로 체크하세요.

## 마치며

처음엔 TLA+가 너무 수학적이고 복잡해 보여서 "우리 AI 워크플로우에 정말 필요할까?" 싶었는데, 직접 써보니 확실히 버그를 줄이고 신뢰성을 높이는 데 큰 도움이 됐다.  
특히 LLM 기반 에이전트가 점점 더 복잡해지는 지금, 명확한 상태 전이와 오류 처리 로직을 사전에 검증하는 건 선택이 아니라 필수라고 느낀다.

백엔드 엔지니어라면 AI 에이전트 워크플로우 설계에 TLA+를 꼭 한 번 써보길 권한다. 프롬프트 엔지니어링과 결합하면 예측 불가능한 AI 동작을 줄이고, 안정적인 시스템 운영에 큰 힘이 될 것이다.
