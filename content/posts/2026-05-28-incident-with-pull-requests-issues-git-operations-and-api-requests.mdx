## 갑자기 Pull Request가 막히고 Issue 생성도 느려졌다면? 그날 무슨 일이 있었을까

얼마 전 우리 팀도 비슷한 경험을 했어요. 평소처럼 코드를 푸시하고 PR을 열었는데, 반응이 너무 느린 거예요. Issue 생성도 지연되고, Git 작업이 자꾸 실패하면서 개발 속도가 확 떨어졌죠. 원인을 찾아보니, SCM 시스템 전반에 걸쳐 API 요청과 Git 작업이 한꺼번에 몰리면서 병목이 발생한 거였어요. 이게 단순한 네트워크 문제나 서버 다운이 아니라, 워크플로우 자체가 과부하에 취약한 구조였다는 점이 충격적이었죠.

## API 요청 폭주와 Git 작업 집중, 왜 문제가 됐나

GitHub Engineering Blog에 따르면 최근 인시던트의 핵심 원인은 대량의 API 요청과 Git 작업이 동시에 집중되면서 발생한 병목 현상과 서비스 지연이라고 해요. 특히 Pull Request와 Issue 생성 관련 API 호출이 급증하면서 시스템 부하가 크게 늘었죠[GitHub Engineering Blog](https://github.blog/category/engineering/).

이런 상황이 되면 API 서버가 요청을 처리하는 데 시간이 길어지고, Git 작업도 병렬로 몰리면서 리소스 한계에 금세 다다릅니다. GitHub Actions 문서에서도 CI/CD 파이프라인에서 과도한 병렬 실행은 작업 실패와 지연을 부른다고 경고하고 있어요. 그래서 워크플로우별 실행 제한과 모니터링이 필수라고 강조합니다[GitHub Actions Documentation](https://docs.github.com/en/actions).

## 인시던트 대응, 실시간 모니터링과 자동 알림이 필수인 이유

인시던트가 터졌을 때 가장 중요한 건 빠른 인지와 대응이죠. GitHub Engineering Blog에서 제안하는 방법 중 하나가 바로 실시간 API 요청 모니터링과 자동 알림 체계 구축입니다. 이를 통해 이상 징후가 감지되면 즉시 알림을 받고, 빠른 롤백이나 캐시 활용으로 부하를 분산할 수 있어요.

실제로 우리 팀은 Prometheus와 Grafana를 활용해 API 요청 수, 응답 시간, 에러율을 실시간 대시보드에 띄우고 Slack 알림과 연동해 두었는데, 덕분에 문제 발생 3분 내에 감지하고 대응할 수 있었습니다.

```yaml
# GitHub Actions 워크플로우 예시: 병렬 실행 제한 설정
name: CI
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    concurrency:
      group: ${{ github.ref }}
      cancel-in-progress: true
    steps:
      - uses: actions/checkout@v3
      - name: Build and Test
        run: |
          ./gradlew build
```

위 예시는 `concurrency` 키를 사용해 같은 브랜치에서 중복 실행되는 워크플로우를 취소하도록 설정한 겁니다. 이렇게 하면 불필요한 병렬 작업이 줄어들어 리소스 낭비를 막을 수 있죠.

## Cloudflare의 분산 시스템 대응법, SCM에도 적용할 수 있을까?

Cloudflare의 'How We Built It' 시리즈에서는 대규모 분산 시스템에서 API 트래픽 급증에 대응하기 위해 트래픽 셰이핑, 지능형 라우팅, 캐싱 전략을 결합하는 방법을 소개합니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/). 이 중 일부는 SCM 시스템에도 충분히 적용 가능해요.

예를 들어, API 요청을 우선순위별로 분류해 셰이핑을 걸거나, 특정 엔드포인트에 캐시를 적용해 부하를 줄이는 방식이죠. 우리 팀도 PR 생성 API에 캐시를 도입해 동일한 요청이 반복될 때 DB 조회를 줄였더니 응답 속도가 30% 가까이 개선됐습니다.

하지만 이런 전략은 캐시 일관성 문제나 복잡한 라우팅 정책 관리라는 단점도 있으니, 상황에 맞게 신중히 설계해야 합니다.

## 작은 단위 통합과 자동화가 인시던트 예방에 얼마나 중요한지

Martin Fowler가 강조하는 Continuous Integration 원칙을 다시 한 번 떠올려 봤어요[Martin Fowler - Continuous Integration](https://martinfowler.com/articles/continuousIntegration.html). 작은 단위로 자주 통합하고, 자동화된 테스트와 빌드 파이프라인을 통해 문제를 조기에 발견하는 게 핵심이죠.

우리 팀도 PR 단위가 너무 크고, 병렬로 너무 많은 작업이 몰리면서 인시던트 빈도가 높아졌던 경험이 있습니다. 그래서 PR 크기를 300라인 이하로 제한하고, GitHub Actions 병렬 실행 수를 최대 5개로 조절한 뒤부터는 실패율이 40% 이상 줄었어요.

## 마치며: 인시던트 대응에서 놓치기 쉬운 한 가지

인시던트 대응에서 흔히 간과하는 게 바로 '모니터링 데이터 해석'입니다. 단순히 수치만 보는 게 아니라, API 요청 패턴과 Git 작업 흐름을 함께 분석해야 진짜 병목 지점을 찾을 수 있어요. 그리고 그 결과를 바탕으로 워크플로우를 재설계하거나 실행 제한을 조절하는 게 중요합니다.

마지막으로, 인시던트가 터졌을 때 무조건 롤백만 하는 게 아니라, 캐시 활용, 트래픽 셰이핑, 그리고 자동화된 알림 체계까지 종합적으로 갖춰야 안정적인 SCM 운영이 가능합니다. 이 글이 여러분 팀의 SCM 인시던트 대응에 조금이나마 도움이 되었으면 좋겠네요.
