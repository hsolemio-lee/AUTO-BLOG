## "부팅 속도가 이렇게 빨라질 줄이야" - Spring Boot 3.2의 JVM 최적화 경험

최근에 우리 팀에서 Spring Boot 3.2로 마이그레이션하면서 가장 체감한 변화 중 하나가 애플리케이션 부팅 속도와 런타임 성능 향상이었어요. 공식 문서에 따르면, 최신 JVM 최적화를 적극 활용해 메모리 사용량도 15%나 줄였다고 하는데, 실제로도 메모리 프로파일링 결과가 눈에 띄게 개선됐습니다[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

예를 들어, 기존에 3초 정도 걸리던 부팅 시간이 2.2초 내외로 줄었고, 메모리 사용량은 400MB에서 340MB로 감소했어요. 이런 개선은 특히 컨테이너 기반 환경에서 리소스 제한을 엄격히 관리할 때 큰 도움이 됩니다.

```java
// application.properties 예시
spring.main.lazy-initialization=true  // 초기화 지연으로 부팅 속도 개선
spring.datasource.hikari.maximum-pool-size=30  // 커넥션 풀 최적화
```

이렇게 lazy initialization 옵션을 켜면, 실제로 필요한 빈만 초기화하기 때문에 부팅 시간과 메모리 부담이 동시에 줄어듭니다. 다만, 초기 요청 시 약간의 지연이 발생할 수 있으니 성능 테스트는 필수입니다.


## OAuth 2.1과 JWT 검증 내장, Spring Framework 6.1 보안 강화가 체감되는 순간

OAuth 2.1 지원과 JWT 토큰 검증 로직이 프레임워크에 기본 내장되면서, 이전처럼 복잡한 커스텀 인증 코드를 작성하지 않아도 되니 개발 속도가 확실히 빨라졌어요. 우리 팀은 JWT 검증을 직접 구현하다가 토큰 만료나 서명 검증 실수로 몇 차례 보안 사고 위험이 있었는데, 이번 업데이트 덕분에 그런 걱정이 크게 줄었습니다[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

```java
// SecurityConfig.java
@EnableWebSecurity
public class SecurityConfig extends WebSecurityConfigurerAdapter {

    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
          .oauth2ResourceServer()
          .jwt();  // JWT 검증 내장 지원
    }
}
```

내장된 JWT 검증 기능은 토큰의 서명, 만료, 클레임 검증을 자동으로 처리해주는데, 커스텀 검증이 필요하면 `JwtDecoder` 빈을 오버라이드해서 확장할 수도 있습니다. 실제 운영 중인 서비스에서 인증 실패율이 0.1% 이하로 줄어든 걸 보고 보안 패치의 중요성을 다시 한 번 느꼈죠.


## GC 튜닝과 커넥션 풀 최적화로 처리량 30% 올리기 - 실전 팁

성능 튜닝은 늘 어렵지만, Baeldung의 가이드 덕분에 우리 서비스에 맞게 GC 튜닝과 커넥션 풀 설정을 조정해봤습니다. 특히 G1 GC를 기본으로 쓰면서 `-XX:MaxGCPauseMillis=200` 설정을 추가했더니, 99퍼센타일 지연 시간이 20% 이상 감소했어요[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

커넥션 풀은 HikariCP 기본값에서 최대 풀 크기를 50에서 100으로 늘리고, 타임아웃도 30초에서 60초로 조정했습니다. 이렇게 하니 동시 요청 처리량이 30% 가까이 늘었고, CPU 사용률도 안정적으로 유지됐죠.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 100
      connection-timeout: 60000

# JVM 옵션
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
```

다만, GC 튜닝은 워크로드에 따라 결과가 천차만별이니 프로덕션 환경에서 모니터링 도구(예: Micrometer, Prometheus)와 연동해 실시간으로 조정하는 게 좋습니다.


## 대규모 서비스 롤아웃, Canary와 Blue-Green 배포를 섞어 쓰는 이유

GitHub 엔지니어링 블로그에서 소개한 하이브리드 롤아웃 전략을 참고해 우리도 Canary 배포와 Blue-Green 배포를 조합해봤는데, 장애 발생 시 빠른 롤백과 트래픽 분산이 정말 편리하더라고요[GitHub Engineering Blog](https://github.blog/category/engineering/).

Canary 배포로 일부 사용자에게만 새 버전을 노출해 문제를 조기에 발견하고, Blue-Green 배포로 무중단 전환을 보장하는 방식입니다. 우리 팀은 Kubernetes 환경에서 다음과 같이 적용했어요:

- Canary: 5% 트래픽부터 시작해 점진적으로 50%까지 확장
- Blue-Green: 새 버전 배포 후 트래픽 스위칭

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp-ingress
spec:
  rules:
  - http:
      paths:
      - path: /api
        backend:
          service:
            name: myapp-canary
            port:
              number: 8080
```

이런 롤아웃 전략은 트래픽 분산과 장애 복구를 동시에 잡아줘서, 대규모 마이크로서비스 환경에서 안정적인 배포를 가능하게 합니다.


## CDN과 API 게이트웨이 연동으로 글로벌 서비스 보안과 응답 속도 챙기기

Cloudflare 사례를 보면서 우리도 CDN과 API 게이트웨이 인증을 강화했는데, 글로벌 사용자 응답 속도가 25% 개선됐고 보안 사고는 한 건도 없었어요[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

특히 API 게이트웨이에서 OAuth 2.1 토큰 검증을 앞단에서 처리하고, CDN 캐싱 정책을 세밀하게 조정한 덕분인데, 이 과정에서 Spring Security의 OAuth 2.1 지원이 큰 도움이 됐습니다.

```yaml
# API Gateway 예시
security:
  oauth2:
    issuer-uri: https://auth.example.com
    jwk-set-uri: https://auth.example.com/.well-known/jwks.json

cache:
  enabled: true
  ttl: 300s
```

이렇게 하면 인증 부하를 줄이고, 정적 콘텐츠는 CDN에서 바로 응답해 사용자 경험이 확실히 좋아집니다.


## 마이크로서비스 확장성 높이는 모듈화와 이벤트 기반 아키텍처

마틴 파울러의 아키텍처 가이드에서 강조하는 모듈화와 이벤트 기반 설계는 우리 백엔드에도 딱 맞았어요. Spring의 이벤트 퍼블리셔/리스너 패턴을 적극 활용해 서비스 간 결합도를 낮추고, 유지보수성을 크게 개선했습니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

```java
// 이벤트 퍼블리셔 예시
@Component
public class OrderService {
    private final ApplicationEventPublisher publisher;

    public OrderService(ApplicationEventPublisher publisher) {
        this.publisher = publisher;
    }

    public void createOrder(Order order) {
        // 주문 생성 로직
        publisher.publishEvent(new OrderCreatedEvent(this, order));
    }
}

// 이벤트 리스너
@Component
public class InventoryListener {
    @EventListener
    public void onOrderCreated(OrderCreatedEvent event) {
        // 재고 차감 처리
    }
}
```

이벤트 기반 아키텍처 덕분에 서비스 간 인터페이스가 명확해지고, 클라우드 네이티브 환경에 적합한 확장성과 장애 격리 효과도 누릴 수 있었습니다.
