## 프로덕션에서 Spring MVC가 느려 보일 때, 어디서부터 손대야 할까?

"왜 우리 서비스가 갑자기 느려졌지?" 이 질문은 한 번쯤 겪어본 개발자라면 누구나 공감할 겁니다. 특히 Spring MVC 기반의 백엔드는 구조가 복잡하고 설정 포인트가 많아 어디를 최적화해야 할지 막막할 때가 많죠. 저는 최근 프로젝트에서 프로덕션 환경에서 실제로 겪은 문제들을 바탕으로, 어떻게 성능을 개선하고 보안을 강화했는지 공유하려고 합니다.

### 애플리케이션 프로파일과 캐싱으로 반복 작업 줄이기

Spring Boot에서는 프로파일을 활용해 개발, 테스트, 운영 환경에서 각각 다른 설정을 적용할 수 있는데요. 프로덕션에서는 특히 캐싱 설정이 중요합니다. 예를 들어 데이터베이스에서 반복적으로 조회하는 API가 있다면 `@Cacheable` 어노테이션을 적극 활용하는 게 효과적입니다.

```java
@Service
public class ProductService {

    @Cacheable(value = "products", key = "#category")
    public List<Product> getProductsByCategory(String category) {
        // DB 호출 비용이 큰 로직
        return productRepository.findByCategory(category);
    }
}
```

이렇게 하면 동일 카테고리 조회 시 DB를 매번 호출하지 않고 캐시된 결과를 반환해 응답 속도가 눈에 띄게 빨라집니다. 저희 팀에서는 Redis를 캐시 저장소로 사용했는데, TTL(Time To Live)을 10분 정도로 설정해 데이터 신선도와 성능 사이에서 균형을 맞췄습니다. 

물론 캐시 무효화 전략이 중요해서, 데이터 변경 시점에 맞춰 캐시를 지우거나 갱신하는 로직을 반드시 넣어야 합니다. 이 부분을 소홀히 하면 오히려 데이터 불일치 문제로 더 큰 장애가 발생할 수 있거든요.

### Spring Security로 CSRF부터 세션 관리까지 탄탄하게

보안은 서비스 신뢰도를 결정짓는 핵심 요소입니다. Spring Security 모듈을 도입하면 CSRF 공격 방어, 세션 고정 공격 방지, 권한별 접근 제어 필터링 등을 비교적 쉽게 구현할 수 있습니다.

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig extends WebSecurityConfigurerAdapter {

    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
            .csrf().csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
            .and()
            .sessionManagement()
                .sessionFixation().migrateSession()
            .and()
            .authorizeRequests()
                .antMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated();
    }
}
```

위 설정에서 CSRF 토큰을 쿠키에 저장해 클라이언트가 쉽게 사용할 수 있게 했고, 세션 고정 공격을 막기 위해 로그인 시 세션을 새로 발급하도록 했습니다. 실제로 이런 기본 보안 조치를 적용하고 나서, 보안 취약점 스캐닝에서 경고가 크게 줄었고, 운영 중 의심스러운 세션 탈취 시도도 효과적으로 차단됐습니다.

### 블루-그린과 카나리 배포로 서비스 다운타임 없이 안정적인 롤아웃

배포할 때마다 서비스가 잠시 멈추는 건 이제 옛말이죠. 저희는 Spring Boot 애플리케이션을 여러 프로파일과 외부 설정 파일로 관리하면서, 인프라 레벨에서 블루-그린 배포를 적용했습니다. 

블루-그린 배포는 두 개의 거의 동일한 환경(블루와 그린)을 운영하면서 한쪽에서 새 버전을 배포하고 테스트한 뒤, 트래픽을 전환하는 방식입니다. 이 과정에서 다운타임이 전혀 없죠. 

카나리 배포는 트래픽의 일부만 새 버전으로 보내 점진적으로 전환하는 전략입니다. 이 방식은 새 버전의 안정성을 실시간으로 검증할 수 있어, 문제가 발견되면 즉시 롤백이 가능합니다.

Spring Boot는 `application-{profile}.properties` 같은 외부 설정 파일을 통해 환경별 설정을 분리할 수 있어서, 이런 배포 전략과도 궁합이 좋습니다. 예를 들어, `application-prod.properties`에는 프로덕션 DB 연결 정보와 캐시 정책을, `application-staging.properties`에는 테스트용 설정을 넣어 관리합니다.

### DI와 AOP를 활용해 코드 유지보수성과 성능 모두 잡기

Spring의 핵심인 DI(Dependency Injection)와 AOP(Aspect-Oriented Programming)는 단순히 코드를 깔끔하게 만드는 데 그치지 않고, 성능 최적화에도 큰 도움을 줍니다. 

예를 들어, AOP를 이용해 공통 로깅이나 트랜잭션 관리를 모듈화하면, 중복 코드가 줄어들고 성능 병목도 쉽게 파악할 수 있습니다. 다음은 간단한 실행 시간 로깅 AOP 예시입니다.

```java
@Aspect
@Component
public class PerformanceAspect {

    @Around("execution(* com.example.service..*(..))")
    public Object logExecutionTime(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.currentTimeMillis();
        Object proceed = joinPoint.proceed();
        long executionTime = System.currentTimeMillis() - start;

        System.out.println(joinPoint.getSignature() + " executed in " + executionTime + "ms");
        return proceed;
    }
}
```

이렇게 하면 서비스 메서드 실행 시간을 쉽게 모니터링할 수 있어, 느린 쿼리나 로직을 빨리 찾아낼 수 있죠. 물론 AOP를 남용하면 코드 흐름이 복잡해질 수 있으니, 적절한 범위 내에서 사용하는 게 중요합니다.

### 비동기 처리와 WebFlux 도입은 언제 고려해야 할까?

Spring MVC는 기본적으로 동기 처리 모델이지만, 최근에는 비동기 요청 처리와 WebFlux 같은 리액티브 프로그래밍 모델을 도입하는 사례가 늘고 있습니다. 특히 I/O 바운드 작업이 많거나, 높은 처리량과 낮은 응답 지연이 요구되는 서비스에서 효과적입니다.

예를 들어, 외부 API 호출이나 파일 입출력 같은 작업을 비동기로 처리하면, 스레드가 블로킹되지 않아 더 많은 요청을 동시에 처리할 수 있습니다.

```java
@GetMapping("/async-data")
public CompletableFuture<ResponseEntity<String>> getAsyncData() {
    return CompletableFuture.supplyAsync(() -> {
        // 무거운 작업 시뮬레이션
        try { Thread.sleep(2000); } catch (InterruptedException e) {}
        return ResponseEntity.ok("Async result");
    });
}
```

하지만 비동기 처리와 WebFlux는 학습 곡선이 있고, 기존 동기 코드와 혼용 시 복잡도가 증가할 수 있으니, 팀 역량과 서비스 특성을 고려해 단계적으로 도입하는 걸 추천합니다.

### 실제로 적용해보니 느낀 점

처음에는 설정 몇 개 바꾸고 캐시 좀 넣는 게 큰 차이가 있을까 싶었는데, 프로덕션에서 직접 체감하는 성능 개선 폭은 꽤 컸습니다. 특히 캐시 전략과 Spring Security 기본 설정만 잘 해도 운영 안정성이 크게 올라갔고, 배포 전략을 바꾸면서 서비스 다운타임 걱정이 사라진 건 큰 수확이었죠.

코드 구조를 DI와 AOP로 정리하면 유지보수도 편해지고, 성능 문제를 찾는 데 드는 시간도 줄어듭니다. 물론 모든 게 완벽한 해결책은 아니고, 캐시 무효화나 비동기 처리 도입 시 예상치 못한 부작용도 있으니 항상 모니터링과 테스트는 필수입니다.

---

### 정리하며

- 프로덕션 환경에 맞는 프로파일과 캐시 전략을 꼭 세우자
- Spring Security로 기본 보안 설정부터 탄탄히 다지자
- 다운타임 없는 배포를 위해 블루-그린, 카나리 배포 전략을 도입하자
- DI와 AOP로 코드 구조를 개선하고 성능 모니터링을 쉽게 만들자
- 비동기 처리와 WebFlux는 필요에 따라 단계적으로 도입하자

이런 최적화는 한 번에 끝나는 작업이 아니라, 서비스가 성장하면서 계속 손봐야 하는 부분입니다. 하지만 한번 제대로 세팅해두면, 팀도, 서비스도 한결 안정적이고 빠르게 돌아가는 걸 느낄 수 있을 겁니다.
