## 네이티브 바텀 탭, 진짜 성능 차이를 체감하다

최근에 React Navigation 8.0 알파 버전을 써볼 기회가 있었는데, 가장 먼저 눈에 띈 건 네이티브 바텀 탭 지원이었어요. 기존에 JS 기반으로 처리하던 바텀 탭이 네이티브 컴포넌트로 바뀌면서, 특히 애니메이션 부드러움과 터치 응답성이 확실히 좋아졌더라고요. 예를 들어, 이전 버전에서는 탭 전환 시 간헐적인 프레임 드랍이나 딜레이가 느껴졌는데, 이젠 거의 네이티브 앱 수준으로 매끄럽게 동작합니다. 

이걸 실제로 체감하려면, React Navigation 8.0 alpha에서 `createBottomTabNavigator`를 `native-stack`과 결합해서 써보면 돼요. 아래는 간단한 예시입니다.

```tsx
import { createNativeStackNavigator } from '@react-navigation/native-stack';
import { createBottomTabNavigator } from '@react-navigation/bottom-tabs';

const Stack = createNativeStackNavigator();
const Tab = createBottomTabNavigator();

function HomeTabs() {
  return (
    <Tab.Navigator
      screenOptions={{
        headerShown: false,
        tabBarActiveTintColor: '#42a5f5',
        tabBarStyle: { backgroundColor: '#fff' },
      }}
      // 네이티브 바텀 탭 활성화 옵션
      native={true}
    >
      <Tab.Screen name="Feed" component={FeedScreen} />
      <Tab.Screen name="Profile" component={ProfileScreen} />
    </Tab.Navigator>
  );
}

export default function App() {
  return (
    <NavigationContainer>
      <Stack.Navigator>
        <Stack.Screen name="Home" component={HomeTabs} />
        <Stack.Screen name="Details" component={DetailsScreen} />
      </Stack.Navigator>
    </NavigationContainer>
  );
}
```

`native={true}` 옵션이 핵심인데, 이걸 넣으면 내부적으로 네이티브 바텀 탭 컴포넌트를 사용합니다. 실제 프로젝트에서 이 설정만으로도 사용자 경험이 크게 달라졌어요.

## TypeScript 추론, 왜 이렇게 좋아졌을까?

TypeScript를 쓰는 입장에서 React Navigation 8.0의 타입스크립트 지원이 크게 좋아진 점도 빼놓을 수 없죠. 이전 버전에서는 네비게이션 파라미터 타입을 명확히 지정해도, 컴포넌트 내에서 `route.params`를 사용할 때 타입 추론이 매끄럽지 않아서, 자주 `as` 캐스팅을 해야 했어요. 이게 쌓이면 개발 생산성이 떨어지고, 타입 안정성도 흔들리죠.

8.0부터는 내부 타입 추론 로직을 완전히 재구성해서, 파라미터 타입을 선언하면 컴포넌트 내에서 자동으로 정확한 타입이 추론됩니다. 예를 들어 아래처럼요.

```tsx
type RootStackParamList = {
  Home: undefined;
  Details: { itemId: number; otherParam?: string };
};

const Stack = createNativeStackNavigator<RootStackParamList>();

function DetailsScreen({ route }: { route: RouteProp<RootStackParamList, 'Details'> }) {
  // itemId가 number 타입으로 딱 잡힌다
  const { itemId, otherParam } = route.params;
  return <Text>Item ID: {itemId}</Text>;
}
```

이전에는 `route.params`가 `any`거나 `unknown`으로 잡혀서, `itemId`를 쓸 때마다 타입 단언을 해야 했는데, 이제는 선언만 잘 해주면 타입스크립트가 알아서 추론해줍니다. 이 변화는 TypeScript 5.x의 타입 시스템 개선 덕분이기도 한데, [TypeScript 5.x Release Notes](https://devblogs.microsoft.com/typescript/announcing-typescript-5-4/)에서 자세히 설명하듯, 조건부 타입과 매핑 타입의 성능과 정확도가 많이 올라갔거든요.

이걸 현업에서 써보면, 타입 안정성이 높아져서 코드 리팩터링이 훨씬 부담 없고, 자동완성도 잘 되니까 개발 속도가 눈에 띄게 빨라집니다.

## 히스토리 관리가 네이티브와 웹을 자연스럽게 잇는다

React Navigation 8.0에서 또 하나 주목할 점은 히스토리 관리가 재설계됐다는 사실입니다. 모바일 앱에서 네비게이션 히스토리를 다루는 건 항상 까다로운 문제였는데, 이번 버전은 네이티브 네비게이션과 웹 라우팅을 아우르는 일관된 경험을 제공해요.

예를 들어, React Navigation을 웹과 모바일 양쪽에서 공통으로 쓰는 프로젝트가 있을 때, 히스토리 스택이 다르게 동작하면 사용자가 뒤로가기 버튼을 눌렀을 때 혼란이 생기죠. 8.0은 히스토리 API를 개선해서, 네이티브 스택과 웹 브라우저 히스토리를 더 자연스럽게 동기화합니다. 

이 덕분에 SPA처럼 웹에서 뒤로가기, 앞으로가기 버튼이 직관적으로 작동하고, 모바일에서는 스와이프 제스처로 뒤로가기 할 때도 일관된 동작을 보장해요. 실제로 앱 테스트 중에 뒤로가기 동작이 이전보다 훨씬 부드럽고 예측 가능해졌다는 피드백을 많이 받았습니다.

## 알파 버전 사용 시 주의할 점과 팁

물론 아직 알파 버전이라 완벽하진 않아요. 네이티브 바텀 탭을 쓰면 플랫폼별로 약간씩 동작 차이가 있을 수 있고, 특히 iOS와 Android에서 탭 전환 애니메이션이 미묘하게 다르더라고요. 

또, TypeScript 추론이 좋아졌다고 해도, 복잡한 네비게이션 구조에서는 타입 선언이 꽤 길어질 수 있으니, 타입 정의를 한 곳에 모아서 관리하는 게 좋아요. 

그리고 히스토리 관련 API는 아직 문서가 완전히 정리되지 않은 부분이 있어서, 직접 코드를 살펴보며 테스트하는 게 필요합니다. 

마지막으로, `native={true}` 옵션을 쓰려면 `react-native-screens` 같은 네이티브 모듈 버전 호환도 꼭 확인하세요. 버전 불일치로 빌드 오류가 날 수 있으니까요.

React Navigation 8.0 알파는 네이티브 바텀 탭과 TypeScript 추론 개선, 히스토리 재설계 덕분에 모바일 프론트엔드 개발 경험을 한 단계 업그레이드할 수 있는 좋은 기회입니다. 물론 알파라서 조심스럽게 접근해야 하지만, 미리 써보며 장단점을 파악해두면 정식 릴리즈 시점에 큰 경쟁력을 갖출 수 있어요.

혹시 바텀 탭 성능 문제나 타입스크립트 네비게이션 타입 때문에 고민 중이라면, 이번 알파 버전으로 직접 테스트해보길 권합니다. 실제로 써보면 "이게 왜 이제야 나왔지?" 싶은 부분이 많을 겁니다.

### 참고 코드

```tsx
import { NavigationContainer } from '@react-navigation/native';
import { createNativeStackNavigator } from '@react-navigation/native-stack';
import { createBottomTabNavigator } from '@react-navigation/bottom-tabs';
import { RouteProp } from '@react-navigation/native';
import React from 'react';
import { Text } from 'react-native';

// 타입스크립트 네비게이션 파라미터 선언
type RootStackParamList = {
  Home: undefined;
  Details: { itemId: number; otherParam?: string };
};

const Stack = createNativeStackNavigator<RootStackParamList>();
const Tab = createBottomTabNavigator();

function FeedScreen() {
  return <Text>Feed Screen</Text>;
}

function ProfileScreen() {
  return <Text>Profile Screen</Text>;
}

function DetailsScreen({ route }: { route: RouteProp<RootStackParamList, 'Details'> }) {
  const { itemId, otherParam } = route.params;
  return (
    <Text>
      Details Screen{`\n`}Item ID: {itemId}{otherParam ? `\nOther: ${otherParam}` : ''}
    </Text>
  );
}

function HomeTabs() {
  return (
    <Tab.Navigator native={true} screenOptions={{ headerShown: false }}>
      <Tab.Screen name="Feed" component={FeedScreen} />
      <Tab.Screen name="Profile" component={ProfileScreen} />
    </Tab.Navigator>
  );
}

export default function App() {
  return (
    <NavigationContainer>
      <Stack.Navigator>
        <Stack.Screen name="Home" component={HomeTabs} />
        <Stack.Screen name="Details" component={DetailsScreen} />
      </Stack.Navigator>
    </NavigationContainer>
  );
}
```

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
