## AI 기능 통합, 생각보다 쉽지 않은 이유

"우리 AI 기능 넣으면 끝이야"라고 생각했던 적 있나요? 저도 그랬습니다. 하지만 실제로 Spring 백엔드에 AI를 붙여보니, 단순히 API 호출만으로는 부족하더라고요. 성능 문제, 보안, 그리고 점진적 롤아웃까지 신경 써야 할 게 한두 가지가 아니었죠.

이번 글에서는 Spring Office Hours Podcast S5E20에서 Danny Thompson이 이야기한 내용을 바탕으로, 우리 팀이 실제로 겪은 경험과 함께 Spring 백엔드에서 AI 기능을 프로덕션 수준으로 구현하는 데 필요한 핵심 팁들을 풀어보려 합니다.


## Spring Boot에서 AI 기능을 위한 성능 튜닝, 이렇게 했다

AI 모델 호출은 보통 네트워크 I/O가 많이 발생하고, 응답 지연(latency)이 문제 될 수 있어요. 그래서 Spring Boot에서 기본 설정만으로는 한계가 있더라고요. Baeldung의 가이드에 따르면, 메모리 관리, 스레드 풀 설정, 캐싱 전략을 꼼꼼히 조절하는 게 필수입니다[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

예를 들어, 우리 팀은 AI API 호출에 별도의 스레드 풀을 할당했어요. 기본 톰캣 스레드 풀과 섞이면 지연시간이 튀는 현상이 있었거든요. 아래는 ThreadPoolTaskExecutor를 설정한 간단한 코드입니다:

```java
@Configuration
public class AsyncConfig {

    @Bean(name = "aiApiExecutor")
    public TaskExecutor aiApiExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(10);  // 최소 10개 스레드
        executor.setMaxPoolSize(50);   // 최대 50개 스레드
        executor.setQueueCapacity(100); // 큐 용량 100
        executor.setThreadNamePrefix("AI-API-");
        executor.initialize();
        return executor;
    }
}
```

이렇게 하면 AI 호출이 몰려도 다른 요청과 충돌 없이 안정적으로 처리할 수 있었어요. 또, AI 응답 결과는 자주 변하지 않는 경우가 많아서 Redis 캐싱을 적극 활용했죠. 캐시 TTL을 5분 정도로 잡아두니, 불필요한 API 호출을 줄여 비용과 응답 속도 모두 개선됐습니다.


## Spring Framework 핵심 기술로 AI 기능 모듈화하기

Spring의 의존성 주입(DI)과 AOP는 AI 기능을 깔끔하게 분리하는 데 정말 유용합니다. AI 관련 로직을 서비스 레이어에 몰아넣고, 보안이나 로깅 같은 공통 관심사는 AOP로 처리하니까 유지보수가 훨씬 쉬워졌어요[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

예를 들어, AI 호출 시 토큰 만료나 API 제한 초과 같은 예외를 잡아내는 로직을 AOP로 감쌌습니다. 이렇게 하면 각 서비스 메서드마다 중복 코드를 쓰지 않아도 되고, 정책 변경 시 한 곳만 수정하면 되니까요.

```java
@Aspect
@Component
public class AiApiExceptionAspect {

    @Around("execution(* com.example.ai.service.AiService.*(..))")
    public Object handleAiApiExceptions(ProceedingJoinPoint pjp) throws Throwable {
        try {
            return pjp.proceed();
        } catch (HttpClientErrorException.TooManyRequests e) {
            // API 호출 제한 초과 처리
            // 예: 재시도 로직 또는 사용자에게 알림
            throw new CustomAiRateLimitException("AI API 호출 제한 초과", e);
        } catch (Exception e) {
            // 기타 예외 처리
            throw e;
        }
    }
}
```

이런 구조 덕분에 보안 정책도 AOP로 한꺼번에 관리할 수 있었고, AI 기능 롤아웃 시에도 특정 기능만 분리해서 켜고 끄는 게 훨씬 편했어요.


## OpenAI API 통합 시 꼭 챙겨야 할 프로덕션 팁

OpenAI API는 RESTful 인터페이스라 Spring RestTemplate이나 WebClient로 쉽게 호출할 수 있습니다. 하지만 토큰 제한, 에러 핸들링, 요청 크기 제한 등 프로덕션 환경에서 고려할 게 많아요[OpenAI API Documentation](https://platform.openai.com/docs/overview).

우리 팀은 WebClient를 썼는데, 호출 시마다 헤더에 API 키를 넣고, 응답 지연이 2초 이상이면 타임아웃 처리하도록 설정했습니다. 아래는 WebClient 설정 예시입니다:

```java
@Bean
public WebClient openAiWebClient() {
    return WebClient.builder()
            .baseUrl("https://api.openai.com/v1")
            .defaultHeader(HttpHeaders.AUTHORIZATION, "Bearer " + openAiApiKey)
            .clientConnector(new ReactorClientHttpConnector(
                    HttpClient.create()
                            .responseTimeout(Duration.ofSeconds(2))))
            .build();
}
```

그리고 API 호출 시 토큰 제한에 걸리지 않도록 요청 길이를 적절히 자르고, 에러가 발생하면 재시도 로직을 넣었어요. 이런 세세한 조정이 없으면 실제 서비스 중에 갑자기 AI 기능이 멈추거나 비용 폭탄 맞기 쉽습니다.


## 프롬프트 엔지니어링으로 AI 응답 품질과 보안을 동시에 잡기

Anthropic의 프롬프트 엔지니어링 가이드를 참고해보면, 단순히 질문을 던지는 것보다 AI가 더 정확하고 안전하게 답변하도록 입력을 설계하는 게 중요하다고 합니다[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

우리 팀은 사용자 입력을 그대로 보내지 않고, 내부 검증 및 필터링을 거쳐 프롬프트에 컨텍스트를 추가하는 방식을 썼어요. 예를 들어, "이 사용자는 어떤 권한을 가지고 있고, 어떤 데이터를 요청하는지"를 명시적으로 넣어 AI가 불필요한 데이터 노출을 막도록 유도했습니다.

이 과정에서 AI 응답에 민감한 정보가 섞이지 않도록 AOP 레벨에서 로그 필터링도 병행했는데, 실제로 운영 중에 민감 정보가 로그에 남는 사고를 예방할 수 있었어요.


## 마이크로서비스 아키텍처와 클라우드 연동으로 AI 기능 확장성 확보하기

Spring Boot 공식 문서에 따르면, AI 기능은 독립적인 마이크로서비스로 분리하는 게 좋다고 합니다. 이렇게 하면 AI 모델 버전별 롤아웃, 트래픽 분산, 장애 격리가 훨씬 수월해지거든요[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

우리 팀도 AI 기능을 별도 서비스로 띄우고, 쿠버네티스 환경에서 Horizontal Pod Autoscaler(HPA)를 적용해 트래픽 급증에도 대응했어요. CPU 사용률 60%를 넘으면 자동으로 파드를 3개에서 최대 10개까지 늘리도록 설정했죠.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: ai-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: ai-service
  minReplicas: 3
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60
```

이런 구조 덕분에 AI 기능이 갑자기 느려지거나 다운되는 상황을 최소화할 수 있었고, 롤아웃 시에도 Canary 배포 전략으로 점진적 전환이 가능했습니다.


## 마치며: AI 통합, 한 번에 끝내려 하지 말고 단계별로 다져가자

처음 AI 기능을 백엔드에 붙일 때는 "그냥 API 호출만 하면 되겠지" 싶지만, 실제 운영 환경에서는 성능, 보안, 확장성 모두 챙겨야 할 게 많습니다. 

- 스레드 풀과 캐시를 적절히 조절해 AI 호출 부하를 분산시키고
- 의존성 주입과 AOP로 모듈화해 유지보수성을 높이며
- OpenAI API의 제한과 에러를 꼼꼼히 다루고
- 프롬프트 엔지니어링으로 응답 품질과 보안을 동시에 챙기고
- 마이크로서비스 아키텍처와 클라우드 오토스케일링으로 확장성을 확보하는 것

이 모든 게 모여서 진짜 프로덕션용 AI 백엔드가 완성됩니다. 

이건 실제로 겪어보면 "아, 이래서 이렇게 하는구나" 하는 부분이 많으니, 처음부터 다 하려고 부담 갖지 말고 한 단계씩 차근차근 적용해보시길 권합니다.
