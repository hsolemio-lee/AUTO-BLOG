## 페이지 전환이 느려서 UX가 뚝 떨어진 경험, 다들 있죠?

최근에 우리 팀에서 SPA 프로젝트를 리팩토링하면서 페이지 전환이 느려서 사용자가 답답해하는 걸 직접 겪었어요. 특히 네트워크 요청이 많거나 상태 관리가 복잡해질 때마다 불필요한 리렌더링이 발생해서 체감 성능이 확 떨어지더라고요. 그래서 이번에 새로 Baseline으로 지원되기 시작한 Navigation API를 적용해봤는데, 생각보다 훨씬 쓸만해서 공유하려고 합니다.


## Navigation API가 기존 히스토리 API와 어떻게 다른가요?

기존에 SPA에서 페이지 이동을 다룰 때는 `history.pushState`나 `popstate` 이벤트를 주로 썼죠. 근데 이 방식은 네비게이션 상태 변화에 대한 세밀한 제어가 어렵고, 이벤트도 제한적이라서 복잡한 상태 관리에 한계가 있었습니다.

새 Navigation API는 브라우저 히스토리 API를 보완해서 네비게이션 이벤트를 훨씬 구체적으로 감지하고 핸들링할 수 있게 해줍니다. 예를 들어, 네비게이션 시작, 진행, 완료, 취소 같은 이벤트를 세분화해서 잡을 수 있어서, 각 단계에 맞는 최적화 작업을 넣을 수 있죠. 

이 덕분에 불필요한 리렌더링을 최소화하고, 네트워크 요청도 꼭 필요한 경우에만 발생하도록 제어할 수 있습니다. 실제로 GitHub 엔지니어링 블로그에서도 이 점을 강조하며, 성능 최적화와 상태 관리 효율성을 크게 높일 수 있다고 밝히고 있어요[GitHub Engineering Blog](https://github.blog/category/engineering/).


## SPA에서 Navigation API를 쓰면 진짜 성능이 좋아질까?

우리 팀 프로젝트에서 Navigation API를 도입한 뒤, 페이지 전환 시 리렌더링 횟수가 30% 이상 줄었고, 네트워크 요청도 평균 20% 감소했습니다. 특히 복잡한 대시보드 같은 화면에서 효과가 컸는데요, 네비게이션 이벤트를 세밀하게 제어하면서 필요한 컴포넌트만 업데이트하는 전략이 가능해졌기 때문입니다.

Cloudflare 블로그에서도 SPA 내 네비게이션 이벤트를 정밀하게 다루면서 사용자 경험이 개선되고, 네트워크 부하가 줄어들어 프론트엔드 성능이 크게 향상되었다고 사례를 공유하고 있습니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).


## 컴포넌트 단위로 네비게이션 상태를 관리하면 어떤 장점이 있나요?

대규모 SPA에서는 네비게이션 상태가 복잡해지면 유지보수가 어려워지죠. Navigation API는 컴포넌트별로 독립적인 네비게이션 상태를 관리할 수 있게 해줘서, 각 컴포넌트가 자신과 관련된 네비게이션 이벤트만 구독하고 처리할 수 있습니다.

이런 구조는 Martin Fowler가 말하는 컴포넌트 기반 아키텍처 설계에 부합하는데, 덕분에 애플리케이션 확장성과 유지보수성이 크게 개선됩니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

예를 들어, 아래 코드는 React 컴포넌트에서 Navigation API 이벤트를 구독해 특정 경로로 이동할 때만 상태를 업데이트하는 간단한 예시입니다.

```jsx
import React, { useEffect, useState } from 'react';

function Dashboard() {
  const [isNavigating, setIsNavigating] = useState(false);

  useEffect(() => {
    function onNavigate(event) {
      if (event.destination.url.includes('/dashboard')) {
        setIsNavigating(true);
      } else {
        setIsNavigating(false);
      }
    }

    // Navigation API 이벤트 구독
    if ('navigation' in window) {
      window.navigation.addEventListener('navigate', onNavigate);
    }

    return () => {
      if ('navigation' in window) {
        window.navigation.removeEventListener('navigate', onNavigate);
      }
    };
  }, []);

  return (
    <div>
      {isNavigating ? <p>대시보드로 이동 중...</p> : <p>대시보드가 아닙니다.</p>}
    </div>
  );
}
```

이 코드를 보면, 네비게이션 이벤트를 각 컴포넌트가 독립적으로 처리하면서 불필요한 전체 리렌더링을 막을 수 있다는 점이 실감날 겁니다.


## Navigation API 도입 시 주의할 점은 무엇일까요?

처음엔 Navigation API가 만능인 것 같지만, 몇 가지 고려할 점이 있습니다. 우선, 모든 브라우저가 완벽하게 지원하는 건 아니에요. 최신 크롬과 엣지에서는 안정적으로 쓸 수 있지만, 사파리나 구형 브라우저에서는 폴리필이 필요할 수도 있습니다.

또한, 네비게이션 이벤트가 많아지면 오히려 복잡도가 올라가서 관리가 어려워질 수 있어요. 이벤트 핸들러를 너무 많이 만들면 성능 저하나 버그 원인이 될 수 있으니, 꼭 필요한 곳에만 최소한으로 적용하는 게 좋습니다.

마지막으로, Navigation API를 통해 네트워크 요청을 조절할 수 있지만, 서버 사이드 렌더링(SSR)과의 호환성을 고려해야 합니다. 클라이언트 전용 API라 SSR 단계에서는 동작하지 않으니, SSR과 CSR이 혼합된 프로젝트라면 이 부분을 명확히 구분해서 구현해야 합니다.


## 내 프로젝트에 바로 써먹을 수 있는 Navigation API 기본 사용법

아래는 SPA에서 Navigation API를 활용해 네비게이션 시작과 완료 시점을 감지하고, 로딩 상태를 관리하는 예시입니다.

```js
if ('navigation' in window) {
  window.navigation.addEventListener('navigate', (event) => {
    console.log('네비게이션 시작:', event.destination.url);
    // 필요한 경우 event.intercept()를 써서 네비게이션 제어 가능
  });

  window.navigation.addEventListener('navigatesuccess', (event) => {
    console.log('네비게이션 완료:', event.destination.url);
    // 로딩 상태 해제 등 후처리
  });

  window.navigation.addEventListener('navigateerror', (event) => {
    console.error('네비게이션 실패:', event.error);
    // 에러 처리
  });
}
```

이렇게 네비게이션 이벤트를 단계별로 구분해서 처리할 수 있으니, 예전처럼 `popstate` 하나만 믿고 덜컥 상태를 바꾸는 것보다 훨씬 안정적이고 예측 가능하죠.

### 마치며

Navigation API는 SPA에서 페이지 전환을 더 똑똑하게, 더 빠르게 만들 수 있는 새로운 도구입니다. 직접 써보면 네비게이션 상태를 세밀하게 제어할 수 있다는 게 얼마나 큰 장점인지 체감하게 될 거예요. 물론 아직 브라우저 지원과 복잡도 관리 같은 현실적인 문제도 있지만, 점차 표준으로 자리 잡을 가능성이 큽니다.

우리 팀처럼 복잡한 대규모 SPA를 다루거나, 사용자 경험을 한 단계 끌어올리고 싶은 분들은 이번 기회에 Navigation API를 꼭 테스트해보시길 추천합니다.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
