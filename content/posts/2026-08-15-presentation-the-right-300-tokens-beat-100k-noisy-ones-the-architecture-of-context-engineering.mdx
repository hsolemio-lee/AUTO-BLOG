## AI 모델 호출할 때 토큰 10만 개? 그거 진짜 필요한가요?

"우리 AI 서비스가 너무 느려요, 비용도 너무 많이 나와요." 이런 얘기, 요즘 AI 연동 백엔드 담당자라면 한 번쯤은 들어봤을 겁니다. 특히 GPT 같은 대형 언어 모델을 쓸 때, 요청에 포함되는 컨텍스트 토큰 수가 10만 단위로 불어나면 비용과 응답 속도 모두 치명적이죠.

그런데 진짜 필요한 정보만 300 토큰 정도로 딱 추려서 보내면, 성능은 훨씬 좋아지고 비용도 확 줄어듭니다. 이게 가능한 이유와, 백엔드 아키텍처에서 어떻게 이걸 구현할 수 있는지 제가 최근에 직접 설계하고 적용해본 경험을 공유하려고 합니다.


## 마이크로서비스로 토큰 사용량을 독립적으로 관리하는 이유

마이크로서비스 아키텍처를 도입하면 각 서비스가 자신에게 필요한 컨텍스트만 책임지고 관리할 수 있습니다. 예를 들어, 사용자 프로필 서비스는 사용자 기본 정보만, 주문 서비스는 주문 내역만 다루고, 이들 각각이 AI 호출에 필요한 핵심 토큰만 추려서 전달하는 식이죠.

Martin Fowler가 설명한 마이크로서비스의 독립성 덕분에 각 서비스는 토큰 최적화 전략을 따로 적용할 수 있습니다. 이게 중요한 이유는, 한꺼번에 모든 데이터를 몰아서 AI에 보내면 불필요한 노이즈가 많아지고, 그만큼 토큰 비용과 지연 시간이 늘어나기 때문입니다[Martin Fowler - Microservices](https://martinfowler.com/articles/microservices.html).

실제로 저희 팀도 사용자 행동 로그, 추천 데이터, 결제 정보가 섞인 큰 덩어리를 한 번에 보내던 걸, 서비스별로 쪼개고 핵심 필드만 뽑아내도록 바꿨더니 토큰 사용량이 평균 70% 이상 줄었고, 응답 속도도 2배 가까이 빨라졌습니다.


## 캐싱과 데이터 퍼시스턴스 패턴으로 중복 토큰 요청 줄이기

AI 모델 호출 시 매번 같은 컨텍스트를 새로 보내면 비용이 폭발합니다. 그래서 클라우드 디자인 패턴 중 캐싱 패턴과 데이터 퍼시스턴스 패턴을 적극 활용했습니다.

예를 들어, 사용자 프로필 정보는 자주 바뀌지 않으니 캐시에 저장해 두고, AI 호출 시 캐시된 내용을 재활용합니다. 또, 이벤트 발생 시점에만 최신 데이터를 퍼시스턴스 레이어에 저장하고, AI 호출 시에는 이 저장된 데이터를 불러와서 필요한 토큰만 전달하는 방식이죠.

이렇게 하면 매번 전체 데이터를 새로 요청하거나 생성하지 않아도 되니, 토큰 요청량이 크게 줄어듭니다. Microsoft에서 소개하는 클라우드 디자인 패턴 사례도 비슷한 맥락에서 AI 통합에 적용할 수 있습니다[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/).


## 이벤트 기반 스트림 처리로 실시간 핵심 데이터만 골라내기

Cloudflare 백엔드 팀이 공개한 사례를 보면, 이벤트 기반 설계와 스트림 처리 방식을 통해 실시간으로 필요한 데이터만 추출해 AI 모델에 넘기는 구조를 갖췄습니다. 이 방식은 대량의 로그나 이벤트 중 핵심 컨텍스트만 걸러내는 데 강력합니다.

예를 들어, 사용자 행동 이벤트가 초당 수천 건씩 쏟아져도, 스트림 처리 파이프라인에서 AI에 필요한 핵심 속성(예: 최근 5분간의 구매 이력, 특정 상품 카테고리 관심도)만 필터링해서 300 토큰 내외로 압축할 수 있습니다.

이런 실시간 필터링 덕분에 AI 호출 시점에 불필요한 데이터가 섞이지 않고, 토큰 낭비가 줄어듭니다. Cloudflare 사례는 백엔드가 어떻게 AI 통합 컨텍스트를 경량화할 수 있는지 좋은 참고가 됩니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).


## 데이터 경계와 중복 제거가 토큰 최적화의 핵심

마지막으로, Martin Fowler와 InfoQ에서 강조하는 것처럼, 데이터 흐름과 경계를 명확히 정의하는 게 매우 중요합니다. 즉, 어떤 서비스가 어떤 데이터를 책임지고, 어디까지가 AI 컨텍스트에 포함될지 딱 정해야 한다는 뜻입니다.

이걸 안 하면 같은 데이터가 여러 서비스에서 중복해서 AI에 전달되면서 토큰이 낭비됩니다. 또, 메시지 크기를 경량화하면 네트워크 비용과 처리 속도도 개선됩니다.

저희는 예를 들어 주문 상태 변경 이벤트를 처리할 때, 주문 ID, 상태, 변경 시각 정도만 AI 호출에 넘기고, 상세 결제 정보나 배송 내역은 별도 서비스에서 관리하도록 분리했습니다. 이렇게 경계를 명확히 하니 토큰 사용량이 자연스럽게 줄고, 유지보수도 편해졌습니다.


## 실제로 적용해본 토큰 최적화 코드 예시

아래는 Node.js 환경에서 Redis 캐시를 활용해, AI 호출 시 컨텍스트 토큰을 300개 내외로 유지하는 간단한 예시입니다. 캐시에 컨텍스트가 없으면 DB에서 가져와서 캐싱하고, AI 호출에 필요한 최소한의 필드만 추려서 전달합니다.

```javascript
const redis = require('redis');
const client = redis.createClient();
const { getUserContextFromDB } = require('./db');
const { callAIModel } = require('./aiClient');

async function getContext(userId) {
  const cacheKey = `user_context:${userId}`;
  let context = await client.get(cacheKey);
  if (context) {
    return JSON.parse(context);
  }

  // DB에서 사용자 컨텍스트를 가져옴
  const fullContext = await getUserContextFromDB(userId);

  // 핵심 필드만 추출 (300 토큰 내외로 가정)
  const minimalContext = {
    userId: fullContext.userId,
    recentPurchases: fullContext.recentPurchases.slice(-5),
    preferences: fullContext.preferences,
    lastLogin: fullContext.lastLogin
  };

  // 캐시에 10분간 저장
  await client.setEx(cacheKey, 600, JSON.stringify(minimalContext));

  return minimalContext;
}

async function handleAIRequest(userId, query) {
  const context = await getContext(userId);
  const prompt = `User info: ${JSON.stringify(context)}\nQuestion: ${query}`;
  const response = await callAIModel(prompt);
  return response;
}
```

이 코드는 캐시 미스 시 DB에서 전체 데이터를 가져오지만, AI에 넘기는 부분은 꼭 필요한 필드만 포함하도록 설계했습니다. 이렇게 하면 토큰 사용량이 불필요하게 늘어나지 않고, 캐시 덕분에 반복 호출 시 비용도 절감됩니다.


## 토큰 최적화, 이렇게 시작해보세요

- **서비스별로 컨텍스트 책임 분리**: 마이크로서비스 경계에 맞춰 AI에 넘길 컨텍스트를 분리하세요.
- **캐시와 영속화 적극 활용**: 변하지 않는 데이터는 캐싱하고, 변경 시점에만 갱신하세요.
- **이벤트 스트림에서 핵심 데이터 필터링**: 실시간 데이터 흐름에서 AI 호출에 꼭 필요한 정보만 걸러내세요.
- **데이터 중복과 경계 명확히 하기**: 중복된 데이터가 여러 서비스에서 AI 호출에 포함되지 않도록 설계하세요.
- **실제 토큰 수 측정과 모니터링**: AI 호출 전후 토큰 수를 꼭 측정해서 최적화 효과를 확인하세요.

처음엔 이게 별거 아닌 것 같지만, 실제로 해보면 비용 절감과 성능 개선 효과가 눈에 띄게 나타납니다. AI 연동 백엔드 설계할 때, 100k 토큰 덩어리 대신 딱 맞는 300 토큰을 목표로 한 번 아키텍처를 재점검해 보세요.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
