## Spring HATEOAS 3.1 GA, 업그레이드가 고민될 때

“이번에 Spring HATEOAS 3.1 GA가 나왔는데, 우리 서비스에 바로 적용해도 될까?” 이런 질문을 받으면 사실 고민이 많아집니다. 하이퍼미디어 지원을 강화했다고 하는데, 실제 프로덕션에선 어떤 점이 달라지고, 어떤 준비가 필요한지 체감하기 쉽지 않으니까요. 

저도 이번에 2.5.3에서 3.1 GA로 업그레이드하면서 겪은 시행착오와 팁들을 공유하려고 합니다. 특히 보안 패치, 성능 최적화, 그리고 점진적 롤아웃 전략에 초점을 맞췄으니, 비슷한 상황이라면 참고가 될 거예요.

---

## 3.1 GA가 가져온 변화, 실제로 뭐가 달라졌을까?

Spring Boot 공식 문서에 따르면, 3.1 GA 버전은 REST API 하이퍼미디어 지원을 한층 강화하면서 이전 3.0.7과 2.5.3 대비 성능과 보안 측면에서 개선이 이루어졌다고 합니다.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)

간단히 정리하면:

- **하이퍼미디어 표현 개선**: LinkBuilder API가 더 직관적이고 유연해졌고, HAL 뿐 아니라 Collection+JSON 같은 다른 미디어 타입도 더 잘 지원합니다.
- **보안 패치**: 이전 버전에서 발견된 몇 가지 XSS 취약점과 링크 생성 시 인젝션 가능성 문제를 해결했습니다.
- **성능 최적화**: 내부적으로 캐싱 전략이 개선되어, 반복되는 링크 생성 비용이 줄었고, 메시지 컨버터 처리 속도가 빨라졌습니다.

처음엔 "그냥 마이너 버전 업그레이드인데 뭐 크게 다르겠어?" 생각했는데, 실제로는 링크 생성과 하이퍼미디어 표현이 많은 API에서는 응답 속도가 10~15% 정도 개선되는 걸 체감했어요.

## 프로덕션에 바로 올리기 전에 꼭 점검해야 할 호환성 이슈

Spring Framework 문서에서는 3.x 버전 업그레이드 시 반드시 점진적 롤아웃과 호환성 테스트를 권장합니다.[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)

우리 팀이 겪은 사례를 예로 들어볼게요.

- **API 응답 구조 변화**: 일부 커스텀 ResourceAssembler에서 내부 링크 생성 방식이 바뀌면서, 기존 클라이언트가 예상하던 링크 경로가 달라졌습니다. 
- **의존성 충돌**: Spring HATEOAS 3.1은 Spring Boot 3.0 이상과 맞물려 있는데, 내부적으로 사용하는 Jackson 버전도 올라가면서 메시지 컨버터 설정을 다시 맞춰야 했어요.

그래서 실제 배포 전, 다음과 같은 절차를 거쳤습니다.

1. **로컬 및 스테이징 환경에서 3.1 GA 버전으로 교체 후 전체 API 통합 테스트 실행**
2. **특히 하이퍼미디어 링크 관련 커스텀 코드 집중 점검**
3. **롤아웃은 Canary 배포로 시작해, 트래픽 5% → 20% → 100% 순으로 점진 적용**

이 과정에서 발견한 문제들은 대부분 링크 생성 커스텀 로직과 관련 있었는데, 사전에 충분히 테스트하지 않으면 클라이언트가 링크를 잘못 해석하는 큰 사고로 이어질 수 있습니다.

## 성능 튜닝: 캐싱과 비동기 처리로 응답 속도 더 끌어올리기

Baeldung 가이드에 따르면, Spring Boot 애플리케이션에서 Spring HATEOAS 성능을 끌어올리려면 캐싱, 비동기 처리, 그리고 커스텀 메시지 컨버터 설정이 핵심이라고 합니다.[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance)

저는 다음과 같은 방법을 실제로 적용해봤는데, 꽤 효과적이었어요.

### 1) 링크 생성 결과 캐싱

하이퍼미디어 API는 동일 리소스에 대해 반복적으로 링크를 생성하는 경우가 많습니다. 매번 새로 만드는 대신, `@Cacheable`을 활용해 링크 생성 결과를 캐싱하면 CPU 사용량과 응답 시간이 줄어듭니다.

```java
@Component
public class UserResourceAssembler implements RepresentationModelAssembler<User, EntityModel<User>> {

    @Cacheable("userLinks")
    public EntityModel<User> toModel(User user) {
        return EntityModel.of(user,
            linkTo(methodOn(UserController.class).getUser(user.getId())).withSelfRel(),
            linkTo(methodOn(UserController.class).getAllUsers()).withRel("users")
        );
    }
}
```

이렇게 캐싱을 걸면, 동일한 유저에 대한 링크 생성은 첫 호출 이후 캐시에서 바로 반환되어 속도가 빨라집니다. 단, 캐시 만료 정책은 도메인 특성에 맞게 조절해야 합니다.

### 2) 비동기 응답 처리

Spring WebFlux나 `@Async`를 활용해 링크 생성과 데이터 조회를 비동기로 처리하면, I/O 병목을 줄이고 전체 API 응답 시간을 단축할 수 있습니다.

### 3) 커스텀 메시지 컨버터 최적화

Spring HATEOAS가 사용하는 메시지 컨버터는 기본적으로 Jackson 기반인데, 필요 없는 필드를 제외하거나, `@JsonView`를 활용해 직렬화 비용을 줄이면 응답 크기와 처리 속도 모두 개선됩니다.

## 보안 패치, 놓치면 안 되는 이유

이번 3.1 GA 버전에서 보안 관련 패치가 포함되었는데, 특히 링크 생성 시 외부 입력을 제대로 검증하지 않으면 XSS 공격에 노출될 수 있습니다.

실제로 우리 팀에서는 한 클라이언트가 URL 파라미터에 악의적인 스크립트를 삽입하려는 시도를 발견했고, 3.1 버전의 보안 패치가 없었다면 피해가 컸을 뻔했습니다.

따라서 업그레이드 후에는 다음 점검 사항을 꼭 확인하세요.

- 링크 생성에 쓰이는 파라미터를 항상 검증하고 인코딩 처리하기
- Spring Security와 연계해 API 접근 권한을 엄격히 제한하기
- 최신 버전의 보안 패치를 빠르게 적용하기

## 실제로 3.1 GA로 업그레이드할 때 참고한 코드 스니펫

아래는 2.5.3에서 3.1 GA로 넘어가면서 바뀐 부분을 반영한 간단한 ResourceAssembler 예시입니다.

```java
@Component
public class ProductResourceAssembler implements RepresentationModelAssembler<Product, EntityModel<Product>> {

    @Override
    public EntityModel<Product> toModel(Product product) {
        return EntityModel.of(product,
            WebMvcLinkBuilder.linkTo(WebMvcLinkBuilder.methodOn(ProductController.class).getProduct(product.getId())).withSelfRel(),
            WebMvcLinkBuilder.linkTo(WebMvcLinkBuilder.methodOn(ProductController.class).getAllProducts()).withRel("products")
        );
    }
}
```

3.1 GA부터는 `WebMvcLinkBuilder` 사용을 권장하며, 더 명확한 API로 변경됐습니다. 이전 버전에서 `ControllerLinkBuilder`를 썼다면 꼭 교체하세요.

## 마무리하며: 업그레이드는 전략적으로, 튜닝은 꼼꼼하게

처음엔 "버전 하나 올리는 게 뭐 그리 복잡해?" 싶지만, Spring HATEOAS처럼 API 하이퍼미디어를 다루는 핵심 라이브러리는 작은 변화도 서비스 전체에 큰 영향을 줄 수 있습니다.

- **3.1 GA는 성능과 보안 모두 잡은 버전**이니, 가능하면 빨리 적용하는 게 좋습니다.
- **롤아웃은 점진적으로, Canary 배포를 적극 활용**해서 문제 발생 시 빠르게 롤백할 수 있게 하세요.
- **성능 튜닝은 캐싱, 비동기 처리, 메시지 컨버터 최적화**를 중심으로 접근하면 효과적입니다.
- **보안 패치는 절대 간과하지 말고, 입력 검증과 권한 관리를 철저히** 하세요.

이 글이 Spring HATEOAS 업그레이드를 앞둔 동료 개발자들에게 조금이나마 도움이 되었으면 합니다. 실제 적용하면서 겪은 경험과 참고 자료를 바탕으로 쓴 만큼, 현업에서 바로 써먹을 수 있을 거예요.
