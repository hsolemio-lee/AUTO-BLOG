### 키보드 백라이트를 백엔드에서 제어한다고? 이게 가능할까?

얼마 전, 우리 팀에서 사내 개발 환경을 좀 더 쾌적하게 만들려고 키보드 백라이트를 원격으로 제어하는 프로젝트를 맡았어요. 처음엔 “키보드 백라이트 정도를 백엔드에서 왜 제어하지?” 싶었는데, 막상 하드웨어 API를 Python 백엔드에 연동해보니 생각보다 재밌고 까다로운 부분이 많더라고요. 특히 하드웨어와 소프트웨어가 만나는 지점에서 어떻게 코드를 구조화하고, 실시간 상태 반영을 어떻게 할지 고민이 컸죠.

이번 글에서는 제가 직접 구현하면서 느낀 점과 실무에서 적용한 패턴, 그리고 운영하면서 주의할 점들을 공유해볼게요.

## 하드웨어 API를 Python 백엔드에 통합할 때 가장 먼저 신경 써야 할 건 ‘추상화’

하드웨어 API를 직접 호출하는 코드는 보통 OS나 드라이버, 심지어 키보드 모델별로 조금씩 다릅니다. 그래서 처음부터 하드웨어에 종속적인 코드를 백엔드 로직에 직접 박아넣으면 유지보수가 지옥이 되죠. 

제가 쓴 방식은 ‘추상화 계층’을 명확히 나누는 거였어요. 예를 들어, `KeyboardController`라는 인터페이스를 만들고, 구체적인 하드웨어 호출은 이 인터페이스를 구현하는 별도의 모듈에 맡깁니다. 이렇게 하면 하드웨어가 바뀌거나 테스트할 때도 백엔드 로직은 거의 손대지 않아도 돼서 편합니다.

```python
from abc import ABC, abstractmethod

class KeyboardController(ABC):
    @abstractmethod
    def set_backlight_color(self, color: str) -> None:
        pass

    @abstractmethod
    def get_backlight_status(self) -> dict:
        pass

# 실제 하드웨어 호출을 담당하는 클래스
class UsbKeyboardController(KeyboardController):
    def __init__(self, device_id: str):
        self.device_id = device_id

    def set_backlight_color(self, color: str) -> None:
        # USB 프로토콜로 하드웨어에 명령 전송
        print(f"Setting backlight color to {color} on device {self.device_id}")
        # 실제 구현은 하드웨어 SDK 호출 등

    def get_backlight_status(self) -> dict:
        # 상태 조회
        return {"color": "blue", "brightness": 80}

# 백엔드 서비스에서 사용
keyboard = UsbKeyboardController(device_id="1234")
keyboard.set_backlight_color("red")
```

이런 추상화 덕에 나중에 Bluetooth 키보드가 추가돼도 `BluetoothKeyboardController`만 새로 만들면 되니까 백엔드 코드는 전혀 바뀌지 않아요. Martin Fowler의 아키텍처 가이드에서도 하드웨어-소프트웨어 경계에서 추상화 계층을 두는 걸 강력히 권장합니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).


## 하드웨어 상태 변화를 실시간으로 반영하려면 비동기와 이벤트 기반 구조가 필수

키보드 백라이트 상태가 바뀌는 걸 백엔드가 실시간으로 알아야 할 때가 있죠. 예를 들어, 사용자가 키보드의 물리적 버튼으로 백라이트 밝기를 조절하면, 백엔드도 그 상태를 즉시 반영해서 다른 서비스에 알리고 싶을 수 있어요.

이때 동기적으로 하드웨어 상태를 폴링(polling)하면 CPU 자원 낭비도 심하고 반응 속도도 느립니다. 그래서 저는 Python의 `asyncio`를 활용해 비동기 이벤트 루프를 돌리면서 하드웨어 이벤트를 감지하는 방식을 썼어요.

```python
import asyncio

class AsyncKeyboardController(UsbKeyboardController):
    async def watch_backlight_changes(self, callback):
        # 실제론 하드웨어 이벤트 리스너를 등록하거나 폴링
        while True:
            status = self.get_backlight_status()
            await callback(status)
            await asyncio.sleep(0.5)  # 0.5초마다 상태 체크

async def on_status_change(status):
    print(f"백라이트 상태 변경 감지: {status}")

async def main():
    keyboard = AsyncKeyboardController(device_id="1234")
    await keyboard.watch_backlight_changes(on_status_change)

# asyncio.run(main())
```

이렇게 하면 하드웨어 상태가 바뀌는 즉시 백엔드가 반응해서 다른 서비스에 이벤트를 전파하거나, 사용자에게 실시간 알림을 줄 수 있어요. InfoQ에서도 하드웨어 API 운영 시 비동기와 이벤트 기반 아키텍처를 추천하는 이유가 바로 이런 효율성 때문이라고 하네요[InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/).


## 마이크로서비스로 분리하면 하드웨어 API 확장과 안정성 관리가 훨씬 수월해진다

우리 팀은 키보드 백라이트 제어 기능을 별도의 마이크로서비스로 분리했어요. 이유는 하드웨어 API가 자주 바뀌고, 장애가 날 경우 전체 백엔드 서비스에 영향이 가는 걸 막기 위해서였죠.

마이크로서비스로 분리하면 다음과 같은 장점이 있어요:

- 하드웨어별, 기능별 독립적 배포 가능
- 장애가 나도 전체 서비스 영향 최소화
- 각 서비스에 맞는 스케일링 전략 적용 가능

GitHub 엔지니어링 블로그에서도 하드웨어 API를 백엔드에 통합할 때 마이크로서비스 아키텍처를 적용해 안정성과 확장성을 확보한 사례가 있습니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

우리 서비스는 다음과 같은 구조로 운영 중입니다:

- `keyboard-backlight-service`: 키보드 백라이트 제어 전용
- `user-notification-service`: 상태 변화를 받아 사용자에게 알림
- `device-management-service`: 키보드 디바이스 등록 및 관리

이렇게 역할을 분리하니 각 서비스가 독립적으로 발전하고, 장애 대응도 훨씬 수월해졌어요.


## 하드웨어 API 호출 시 보안은 절대 간과하면 안 된다

키보드 백라이트 제어가 단순해 보여도, 하드웨어와 백엔드 간 통신에서 보안 위협은 생각보다 큽니다. 특히 원격으로 제어하는 경우, 악의적인 공격자가 백라이트를 조작하거나 더 나아가 하드웨어 취약점을 노릴 수도 있거든요.

우리는 다음과 같은 보안 조치를 반드시 적용했어요:

- TLS 암호화로 통신 내용 보호
- 인증 토큰 기반 접근 제어로 권한 검증
- 요청당 권한 범위 최소화 (예: 읽기 전용 토큰과 쓰기 토큰 분리)

Cloudflare 블로그에서도 하드웨어와 백엔드 API 간 통신에서 TLS와 인증 토큰 기반 접근 제어를 적용해 보안을 강화한 경험을 공유했습니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

```python
import requests

API_URL = "https://keyboard-service.internal/api/backlight"
TOKEN = "eyJhbGciOiJI..."

headers = {
    "Authorization": f"Bearer {TOKEN}",
    "Content-Type": "application/json"
}

payload = {"color": "green"}

response = requests.post(API_URL, json=payload, headers=headers, verify=True)  # verify=True로 TLS 인증서 검증
if response.status_code == 200:
    print("백라이트 색상 변경 성공")
else:
    print(f"오류 발생: {response.status_code} - {response.text}")
```

이렇게 하면 외부 공격자가 API를 쉽게 호출하지 못하고, 내부에서도 권한 없는 사용자가 함부로 하드웨어를 조작하는 걸 막을 수 있습니다.


## 직접 써보니 알게 된 ‘작은’ 문제들

처음에 하드웨어 API를 단순히 함수 호출로만 생각했는데, 실제로는 다음과 같은 문제들이 있더라고요:

- **드라이버 버전별 미묘한 차이**: 같은 키보드라도 드라이버 버전에 따라 명령어가 달라서, 여러 버전을 지원하려면 꽤 신경 써야 함
- **하드웨어 연결 불안정**: USB 연결이 자주 끊기거나 재연결되면 API 호출이 실패하는 경우가 많음. 이걸 감지하고 재시도 로직을 넣는 게 필수
- **실시간 이벤트 누락 가능성**: 이벤트 기반 구조라도 하드웨어가 상태 변화를 놓치는 경우가 있어서, 주기적 폴링과 병행하는 하이브리드 방식 권장

이런 문제들은 문서화가 잘 안 된 경우가 많아 직접 테스트하면서 경험을 쌓는 수밖에 없었어요.


## 마무리하며: 하드웨어 API 통합, 백엔드에서도 충분히 매력적이다

키보드 백라이트 API를 Python 백엔드에 통합하는 과정은 단순히 하드웨어 제어를 넘어서, 소프트웨어 아키텍처 설계, 비동기 프로그래밍, 보안, 운영 안정성 등 백엔드 엔지니어링의 다양한 면을 경험할 수 있는 좋은 기회였어요.

하드웨어와 소프트웨어 사이에 명확한 추상화 계층을 두고, 비동기 이벤트 기반 아키텍처를 활용하며, 마이크로서비스로 분리해 확장성과 안정성을 확보하는 패턴은 꼭 기억할 만합니다. 그리고 보안은 언제나 기본 중의 기본이라는 점도요.

혹시 비슷한 프로젝트를 고민 중이라면, 처음부터 하드웨어와 소프트웨어 경계에 신경 쓰고, 실시간 상태 반영과 보안 체계를 함께 설계하는 걸 추천합니다. 이건 실제로 해보면 생각보다 까다롭고, 미리 대비하지 않으면 나중에 고생할 가능성이 큽니다.
