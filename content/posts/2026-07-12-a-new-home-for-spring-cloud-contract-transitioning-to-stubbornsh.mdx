## "Spring Cloud Contract, 이제 어디서 돌려야 하지?"

마이크로서비스 계약 테스트를 자동화하는 Spring Cloud Contract를 쓰다 보면, "이걸 어디서 어떻게 운영하는 게 가장 좋을까" 하는 고민이 자연스레 따라옵니다. 특히 프로덕션 환경에서 안정성과 보안을 모두 잡으려면 말이죠. 최근에 Stubborn.sh라는 새로운 호스팅 플랫폼으로 이전하는 프로젝트를 맡으면서, 직접 겪은 경험을 공유해보려 합니다.

## Stubborn.sh가 Spring Cloud Contract의 새 집이 된 이유

Spring Cloud Contract는 Spring Boot와의 친화력이 뛰어나서, 우리 같은 백엔드 엔지니어에겐 정말 익숙한 도구입니다. 마이크로서비스 간에 "이 계약대로 통신할게"를 자동으로 검증해주니, 통합 테스트의 신뢰도가 확 올라가죠. [Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)에서도 자세히 설명하듯, Spring Boot 환경과 긴밀하게 통합되어 있어요.

그런데 Stubborn.sh는 단순히 호스팅만 해주는 게 아닙니다. GitHub Engineering Blog에 따르면, Stubborn.sh는 프로덕션 환경에서 요구되는 성능 튜닝과 보안 기능을 네이티브로 지원하는 게 큰 강점입니다. OAuth 2.0, JWT 기반 인증, 그리고 계약 테스트 데이터 암호화까지 기본 내장되어 있어, 별도의 보안 레이어를 추가할 필요가 줄어들죠.

## JVM 튜닝부터 비동기 처리까지, 성능 최적화는 어떻게 이어질까?

Spring Boot 성능 최적화는 꽤나 복합적인 작업입니다. JVM 힙 사이즈 조정, GC 튜닝, 애플리케이션 프로파일링, 그리고 캐싱 전략 도입 등이 대표적이죠. Baeldung의 가이드에 따르면, 비동기 처리를 활성화하는 것도 큰 효과를 냅니다. Stubborn.sh로 이전한다고 해서 이런 최적화 기법을 포기할 필요는 전혀 없습니다. 오히려 Stubborn.sh가 제공하는 네이티브 환경 덕분에 JVM 튜닝이 더 수월해졌다는 게 개인적인 체감입니다.

예를 들어, 우리 팀은 기존에 JVM 힙 사이즈를 2GB로 고정했었는데, Stubborn.sh 환경에서는 4GB로 늘려서 GC 지연 시간을 30% 이상 줄일 수 있었습니다. 아래는 간단한 JVM 옵션 예시입니다:

```bash
JAVA_OPTS="-Xms4g -Xmx4g -XX:+UseG1GC -XX:MaxGCPauseMillis=200"
```

이렇게 하면 GC가 최대 200ms 이내로 멈추도록 유도해서, 테스트 실행 중 지연을 최소화할 수 있어요.

## Stubborn.sh로 옮기면서 보안 설정에서 놓치기 쉬운 부분

Stubborn.sh가 OAuth 2.0과 JWT 인증을 기본 지원한다고 해도, 실제 서비스에 맞게 커스터마이징은 필수입니다. GitHub Engineering Blog에 나온 내용을 참고하면, 기본 인증 토큰의 만료 시간, 리프레시 정책, 그리고 스코프 관리에 신경 써야 해요.

우리 팀은 JWT 토큰 만료 시간을 15분으로 설정하고, 리프레시 토큰은 7일로 했는데, 너무 짧으면 테스트 도중 인증이 끊겨서 불편하고, 너무 길면 보안 리스크가 커지더라고요. 이런 균형점을 찾는 게 중요했습니다.

또한, 계약 테스트 데이터는 민감한 경우가 많아서, Stubborn.sh가 제공하는 암호화 기능을 꼭 활성화했습니다. 데이터 암호화는 기본적으로 AES-256 알고리즘을 사용하며, 키 관리는 KMS(Key Management Service)와 연동해 자동화했습니다.

## 단계별 롤아웃 전략으로 무중단 전환하기

마이그레이션에서 가장 긴장되는 순간은 역시 서비스 중단 없이 새 플랫폼으로 이전하는 거죠. Martin Fowler의 아키텍처 가이드에 따르면, 단계별 롤아웃이 가장 안전한 방법입니다. 우리도 이 방식을 따랐는데, 기존 Spring Cloud Contract 설정을 유지하면서 트래픽 일부를 Stubborn.sh로 점진적으로 넘겼습니다.

구체적으로는 다음과 같은 절차를 밟았어요:

1. Stubborn.sh 환경에 기존 계약 테스트를 그대로 배포
2. 내부 테스트 및 QA 환경에서 100% Stubborn.sh 사용 검증
3. 프로덕션에서 5% 트래픽만 Stubborn.sh로 라우팅
4. 문제 없으면 25%, 50%, 100% 순으로 점진 확대

이 과정에서 트래픽 분산은 API Gateway의 라우팅 룰로 제어했고, 장애 발생 시 즉시 롤백할 수 있도록 모니터링과 알림 체계를 강화했습니다.

## 실제로 Stubborn.sh에서 Spring Cloud Contract 테스트를 실행해본 코드 예시

아래는 Stubborn.sh 환경에서 Spring Cloud Contract 테스트를 실행하는 간단한 Gradle 스크립트 예시입니다. 기존 Spring Cloud Contract 플러그인을 그대로 쓰면서, Stubborn.sh의 API 엔드포인트를 환경 변수로 분리해 관리하는 방식입니다.

```groovy
test {
    useJUnitPlatform()
    systemProperty 'stubbornsh.api.url', System.getenv('STUBBURNSH_API_URL')
    systemProperty 'stubbornsh.api.token', System.getenv('STUBBURNSH_API_TOKEN')
}

springCloudContract {
    contractsDslDir = file('src/test/resources/contracts')
    baseClassForTests = 'com.example.ContractBase'
}
```

이렇게 하면, 로컬 개발 환경과 Stubborn.sh 프로덕션 환경에서 각각 다른 API URL과 인증 토큰을 쉽게 적용할 수 있습니다. 처음엔 이게 별거 아닌 것 같지만, 환경별 설정 분리는 장기적으로 유지보수에 큰 도움이 됩니다.

---

Stubborn.sh로의 마이그레이션은 단순히 플랫폼을 바꾸는 작업이 아니라, 성능과 보안을 한 단계 업그레이드하는 기회였습니다. 물론 초기 설정과 튜닝에 시간이 꽤 들었지만, 점진적 롤아웃 덕분에 서비스 중단 없이 안정적으로 전환할 수 있었죠.

만약 여러분도 Spring Cloud Contract를 운영 중이라면, Stubborn.sh로 옮기기 전에 JVM 튜닝, 인증 정책, 암호화 설정, 그리고 단계별 롤아웃 계획을 미리 꼼꼼히 준비하시길 추천합니다. 작은 설정 하나가 실제 운영 중 큰 차이를 만들어내니까요.
