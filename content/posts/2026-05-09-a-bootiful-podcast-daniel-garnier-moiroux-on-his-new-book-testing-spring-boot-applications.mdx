## "테스트가 이렇게 중요할 줄 몰랐어요" — 내 프로젝트에서 테스트가 발목 잡을 때

"테스트 때문에 개발이 더 느려진다?" 처음에 나도 그랬다. 그런데 Daniel Garnier-Moiroux의 책 『Testing Spring Boot Applications』를 듣고 나서 생각이 완전히 바뀌었다. 테스트는 단순히 버그 잡는 도구가 아니라, 코드 품질과 유지보수성을 좌우하는 핵심 전략이라는 걸 깨달았다.

실제로 우리 팀 프로젝트도 테스트가 부족해서 배포 후에 버그가 터지고, 긴급 패치에 허덕였던 경험이 있다. 그때부터 테스트를 제대로 배우고 싶었는데, 이번 팟캐스트에서 Daniel이 들려준 이야기들은 마치 내 상황에 딱 맞는 해법 같았다.

## Spring Boot 공식 문서가 알려주는 테스트 기본기

Spring Boot 공식 문서에선 테스트를 위한 여러 지원 기능을 친절하게 제공한다. 특히 `@SpringBootTest` 어노테이션은 통합 테스트를 할 때 애플리케이션 컨텍스트를 띄워서 실제 환경과 거의 동일한 상태에서 테스트할 수 있게 해준다. 물론 이게 편한 만큼 초기화 비용이 크다는 단점도 있는데, 이걸 잘 조절하는 게 포인트다.

```java
@SpringBootTest
public class UserServiceIntegrationTest {

    @Autowired
    private UserService userService;

    @Test
    void testCreateUser() {
        User user = new User("alice", "alice@example.com");
        User savedUser = userService.createUser(user);
        assertNotNull(savedUser.getId());
    }
}
```

이 코드는 실제 DB와 거의 비슷한 환경에서 `UserService`의 기능을 검증한다. 하지만 테스트가 느려지면 개발 속도가 떨어지니, 꼭 필요한 부분에만 `@SpringBootTest`를 쓰고 단위 테스트는 더 가벼운 방법으로 하는 게 좋다.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)

## 의존성 주입과 AOP로 테스트 코드를 깔끔하게 유지하는 법

Spring Framework 코어 문서에선 의존성 주입(DI)과 AOP(Aspect-Oriented Programming)를 활용해 테스트 코드를 유지보수하기 쉽게 만드는 전략을 권장한다. 예를 들어, 테스트용 Mock 객체를 DI로 주입하면 실제 구현체를 바꾸지 않고도 다양한 시나리오를 쉽게 테스트할 수 있다.

또 AOP를 활용하면 로깅, 트랜잭션 관리 같은 공통 관심사를 테스트 코드에 중복 없이 적용할 수 있다. 이런 구조는 테스트 코드가 비대해지는 걸 막아주고, 나중에 수정할 때도 편하다.[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)

## 슬라이스 테스트로 느린 통합 테스트 문제를 해결하자

Daniel이 강조한 부분 중 하나는 애플리케이션 컨텍스트 초기화 비용을 줄이는 슬라이스 테스트(slice test) 기법이다. 예를 들어, `@WebMvcTest`는 웹 레이어만 띄워서 컨트롤러를 빠르게 테스트할 수 있다. 이렇게 하면 전체 컨텍스트를 띄우는 것보다 훨씬 빠르다.

```java
@WebMvcTest(UserController.class)
public class UserControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockBean
    private UserService userService;

    @Test
    void testGetUser() throws Exception {
        given(userService.getUser(1L)).willReturn(new User("bob", "bob@example.com"));

        mockMvc.perform(get("/users/1"))
               .andExpect(status().isOk())
               .andExpect(jsonPath("$.name").value("bob"));
    }
}
```

이렇게 테스트 레이어를 쪼개면, 테스트 속도가 2~3배 빨라지고 개발자 피로도가 크게 줄어든다. 물론 슬라이스 테스트는 모든 걸 검증하지 못하니, 핵심 비즈니스 로직에 대해선 통합 테스트도 병행해야 한다.[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance)

## 테스트 자동화 없이는 지속적 통합(CI)도 무용지물

Martin Fowler의 아키텍처 가이드에서도 테스트 자동화가 얼마나 중요한지 거듭 강조한다. 특히 백엔드 개발에서 테스트 없이는 안정적인 배포가 불가능하다고 말한다. CI 파이프라인에 테스트를 꼭 포함시키고, 실패 시 배포를 차단하는 게 기본이다.

우리 팀도 CI에 테스트 자동화를 넣고 나서, 배포 후 긴급 버그가 40% 이상 줄었다. 처음엔 테스트 실패에 스트레스 받았지만, 점점 테스트가 신뢰를 주면서 개발 속도도 오히려 빨라졌다.[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/)

## 내 프로젝트에 바로 적용해본 테스트 전략

1. **가볍고 빠른 단위 테스트 우선**: 핵심 로직은 Mockito와 JUnit5로 단위 테스트를 촘촘히 작성한다.
2. **슬라이스 테스트로 레이어별 검증**: 컨트롤러, 서비스, 리포지토리 각각 필요한 부분만 띄워서 빠르게 검증한다.
3. **중요한 흐름은 `@SpringBootTest`로 통합 테스트**: 배포 전엔 꼭 전체 컨텍스트를 띄워서 문제 없는지 확인한다.
4. **테스트 데이터는 프로파일로 분리**: `application-test.yml`에 테스트용 DB 설정을 분리해 실제 운영 데이터와 섞이지 않도록 한다.

이렇게 하니 테스트 실행 시간이 1분대에서 20초대로 줄었고, 실패 원인도 훨씬 명확해졌다. 처음엔 테스트 코드 작성이 귀찮았지만, 지금은 테스트가 없으면 불안해서 못 배포할 정도다.

---

테스트는 귀찮고 느리다는 편견을 Daniel Garnier-Moiroux의 책과 팟캐스트를 통해 깨달았다. 실무에서 바로 써먹을 수 있는 슬라이스 테스트, DI와 AOP를 활용한 깔끔한 테스트 코드, 그리고 CI와 연계한 자동화 전략까지. 이걸 안 하면 나중에 더 큰 고생을 하게 된다.

테스트가 무겁거나 느리다고 포기하지 말고, 적절한 레이어별 테스트 전략과 환경 분리, 자동화 도구를 적극 활용해보자. 그게 결국 개발 속도를 높이고, 안정적인 서비스를 만드는 지름길이다.
