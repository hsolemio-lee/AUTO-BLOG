## React Router v8, 왜 갑자기 ESM 전용 빌드로 바뀌었을까?

최근 React Router가 v8로 올라가면서 꽤 조용한 릴리즈가 있었어요. 사실 "조용하다"는 게 여기선 칭찬입니다. 큰 API 변화 없이 내부 구조를 현대화하는 데 집중했거든요. 그중 가장 눈에 띄는 건 바로 ESM(ECMAScript Module) 전용 빌드 도입입니다.

처음엔 "ESM 전용 빌드? 그냥 빌드 방식이 바뀐 건가?" 싶었는데, 직접 써보니 꽤 의미가 컸습니다. 기존의 CommonJS와 UMD 빌드가 섞여 있으면 트리 쉐이킹(tree shaking)이 제대로 안 돼서 번들 크기가 불필요하게 커지는 문제가 있었거든요. ESM-only 빌드는 모던 번들러(예: Vite, Webpack 5+)와 찰떡궁합이라 실제로 번들 크기를 10~15% 정도 줄여주더라고요.

실제로 Next.js App Router 문서에서도 ESM 기반 라우팅 시스템이 코드 분할과 SSR(서버 사이드 렌더링) 최적화에 유리하다고 명시하고 있습니다. React Router v8가 이런 트렌드에 맞춰 간 것은 자연스러운 수순이었죠[Next.js App Router Docs](https://nextjs.org/docs/app/building-your-application/routing).


## 기본 미들웨어가 생겼다는 건 무슨 뜻일까?

v8에서 또 한 가지 주목할 점은 "기본 미들웨어(default middleware)"가 도입됐다는 거예요. 이걸 처음 들었을 때, "미들웨어? 그거 Express나 Koa에서 쓰는 거 아니야?"라는 생각이 들었죠. 그런데 React Router 내부 라우팅 과정에 미들웨어 개념을 적용해 공통 작업을 중앙에서 처리할 수 있게 된 겁니다.

예를 들어, 인증 체크, 로깅, 에러 처리 같은 반복되는 작업을 각 라우트 컴포넌트마다 넣는 대신, 기본 미들웨어로 한 번에 처리할 수 있어요. 덕분에 각 컴포넌트는 UI 렌더링에만 집중할 수 있고, 코드가 훨씬 깔끔해집니다.

우리 팀도 이걸 적용하면서 인증 로직이 훨씬 단순해졌어요. 이전에는 각 페이지마다 `useEffect`로 토큰 유효성 검사하고 리다이렉트 처리하느라 중복 코드가 많았는데, 미들웨어 한 줄로 끝나니까 유지보수성이 확 올라갔죠[React - Thinking in React](https://react.dev/learn/thinking-in-react).


## 실제로 React Router v8에서 기본 미들웨어를 어떻게 쓰는지 예시

아래는 간단한 인증 미들웨어를 기본 미들웨어로 등록하는 예시입니다. 

```jsx
import { createRouter, RouterProvider } from 'react-router-dom';

// 인증 미들웨어
function authMiddleware({ next, location }) {
  const isLoggedIn = Boolean(localStorage.getItem('token'));
  if (!isLoggedIn && location.pathname !== '/login') {
    return next.redirect('/login');
  }
  return next();
}

// 라우터 생성 시 기본 미들웨어 등록
const router = createRouter({
  routes: [
    { path: '/', element: <Home /> },
    { path: '/login', element: <Login /> },
    { path: '/dashboard', element: <Dashboard /> },
  ],
  middleware: [authMiddleware],
});

export default function App() {
  return <RouterProvider router={router} />;
}
```

이렇게 하면 `/dashboard` 같은 보호된 경로에 접근할 때 자동으로 로그인 여부를 체크해주고, 로그인하지 않은 상태면 `/login`으로 리다이렉트합니다. 기존에는 각 컴포넌트마다 이런 검사를 넣어야 했던 걸 생각하면 엄청 편하죠.

이 방식의 단점은 미들웨어가 많아지면 실행 순서 관리가 필요하다는 점과, 미들웨어 내부에서 비동기 작업 시 약간 복잡해질 수 있다는 점입니다. 하지만 기본 미들웨어로 공통 작업을 한 곳에 모으는 게 장기적으로 유지보수에 훨씬 이득이라 저는 강력 추천합니다.


## ESM 전용 빌드로 전환할 때 주의할 점

ESM-only 빌드가 좋다고 무조건 바로 바꾸면 안 되는 경우도 있어요. 특히 기존 프로젝트가 CommonJS 기반이거나, Node.js 환경에서 SSR을 하면서 아직 완전한 ESM 지원이 안 되는 경우에는 호환성 문제가 발생할 수 있습니다.

예를 들어, Next.js 13 이전 버전이나 Webpack 4 이하를 쓰는 프로젝트는 ESM 전용 라이브러리를 제대로 처리하지 못할 수 있어요. 이런 경우엔 React Router v8로 업그레이드하기 전에 빌드 시스템을 최신화하는 작업이 선행돼야 합니다.

그리고 ESM 전용 빌드는 트리 쉐이킹이 잘 되지만, 번들러 설정에 따라 의도치 않게 일부 코드가 포함되지 않을 수도 있으니 꼭 프로덕션 빌드 결과물을 꼼꼼히 확인해야 합니다.


## 우리 팀에서 React Router v8로 갈아타며 느낀 점

솔직히 말하면, v8 업그레이드는 "대단한 혁신"보다는 "꾸준한 진화"에 가깝습니다. API가 크게 바뀌지 않아 마이그레이션이 크게 어렵지 않았고, ESM 전용 빌드 덕분에 번들 크기가 눈에 띄게 줄었어요. 기본 미들웨어 도입은 코드 중복을 줄이고, 라우팅 관련 공통 로직을 한 곳에서 관리할 수 있게 해줘서 유지보수성이 크게 향상됐죠.

처음엔 "기본 미들웨어? 별거 아닌 것 같은데?" 했는데, 실제로 써보니 페이지마다 인증, 로깅, 에러 처리를 반복하는 것보다 훨씬 깔끔하고 안전하다는 걸 깨달았습니다. 특히 대규모 프로젝트일수록 이런 일관된 구조가 얼마나 중요한지 실감했어요.

- React Router v8의 ESM-only 빌드는 모던 프론트엔드 환경에서 번들 최적화에 큰 도움을 줍니다.
- 기본 미들웨어를 활용하면 라우팅 과정에서 공통 작업을 중앙 집중식으로 관리할 수 있어 코드 중복과 유지보수 비용이 확 줄어듭니다.

- 미들웨어가 많아지면 실행 순서와 비동기 처리에 신경 써야 하니 설계 단계에서 고민을 충분히 하는 게 좋습니다.
