## MongoDB로 스프링 배치 작업을 돌려본 적 있나요?

최근에 우리 팀에서 Spring Boot 4.1 버전으로 업그레이드하면서 MongoDB를 백엔드로 사용하는 배치 작업을 도입했어요. 기존에 RDBMS를 쓰던 배치 작업과는 다르게, MongoDB 특성을 살려야 해서 고민이 많았죠. 특히 대용량 데이터 처리에 맞게 청크 크기나 병렬 처리, 커넥션 풀 튜닝을 어떻게 해야 할지 감이 안 잡혔거든요.

처음엔 "MongoDB가 NoSQL이라 배치에 적합할까?"라는 의문도 있었는데, Spring Boot 4.1 공식 문서에 MongoDB-backed Spring Batch 작업 지원이 명확히 나와 있더라고요. 덕분에 실제 구현과 최적화, 보안 적용까지 경험한 내용을 공유하려고 합니다.


## Spring Boot 4.1에서 MongoDB-backed Spring Batch 작업이 가능한 이유

Spring Boot 4.1부터는 Spring Batch가 MongoDB를 데이터 저장소로 공식 지원합니다. 기존에는 RDBMS 기반의 JobRepository, StepExecution, ExecutionContext 등을 사용했는데, 이제는 MongoDB에 이 정보들을 저장할 수 있죠. 덕분에 배치 상태 추적과 재시작 기능을 NoSQL 환경에서도 자연스럽게 쓸 수 있습니다.

실제로 `spring-boot-starter-batch` 의존성을 추가하고, `spring.batch.job.repository-type=mongodb` 설정만 해주면 MongoDB-backed 배치가 동작합니다. 내부적으로는 Spring Data MongoDB 모듈이 연동되어 트랜잭션 관리와 쿼리 실행을 처리해 주죠.

```yaml
spring:
  data:
    mongodb:
      uri: mongodb://user:password@localhost:27017/batchdb
  batch:
    job:
      repository-type: mongodb
```

이 부분이 핵심인데, MongoDB URI를 정확히 지정하고, 배치 저장소 타입을 mongodb로 바꾸는 것만으로도 기본적인 배치 실행 환경이 갖춰집니다. 물론 여기서 끝내면 성능이나 보안에서 아쉬움이 남죠.


## 배치 처리 성능을 좌우하는 MongoDB 커넥션 풀과 청크 사이즈 설정

이건 실제로 겪어보면 "커넥션 풀 크기를 너무 작게 잡으면 병목이 심하다"는 걸 금방 느끼게 돼요. MongoDB는 기본적으로 커넥션 풀 크기가 100인데, 배치 작업에서 동시성 높게 돌릴 때는 이보다 더 크게 조절하는 게 좋습니다.

application.yml에서 다음과 같이 설정해봤어요:

```yaml
spring:
  data:
    mongodb:
      uri: mongodb://user:password@localhost:27017/batchdb
      connection-pool:
        max-size: 200
        min-size: 50
```

이렇게 하면 동시 실행되는 Step이나 Tasklet들이 커넥션 부족으로 대기하는 일이 줄어들더라고요. 물론 너무 큰 풀은 메모리 부담이 있으니 서버 리소스에 맞게 조절해야 합니다.

그리고 청크 크기(chunk size)도 성능에 직결됩니다. 처음엔 10~20 정도로 시작했는데, 50~100 사이에서 가장 안정적인 처리량과 메모리 사용량 밸런스를 찾았어요.

```java
@Bean
public Step exampleStep() {
    return stepBuilderFactory.get("exampleStep")
        .<InputType, OutputType>chunk(50) // 청크 크기 50으로 설정
        .reader(mongoItemReader())
        .processor(itemProcessor())
        .writer(mongoItemWriter())
        .build();
}
```

이렇게 청크 크기를 키우면 DB와 네트워크 왕복 횟수가 줄어들어 처리 속도가 빨라지지만, 너무 크면 메모리 사용량이 급증해 GC가 자주 발생할 수 있으니 주의해야 합니다.

병렬 처리도 빼놓을 수 없는데, `TaskExecutor`를 활용해 Step을 병렬로 돌리거나 Partitioning을 적용해 MongoDB 컬렉션을 샤딩하듯 분할 처리하는 전략을 썼습니다. 이 부분은 배치 규모와 데이터 특성에 따라 튜닝이 필요합니다.


## MongoDB 인덱스 설정, 배치 성능에 얼마나 영향을 줄까?

MongoDB는 스키마가 유연한 만큼 인덱스가 없으면 쿼리 성능이 급격히 떨어집니다. 배치 작업에서 특정 필드로 데이터를 조회하거나 업데이트할 때는 꼭 적절한 인덱스를 만들어야 해요.

예를 들어, 배치 작업이 특정 상태(`status`) 필드로 레코드를 조회한다면 이렇게 인덱스를 생성합니다:

```shell
> db.batchCollection.createIndex({ status: 1 })
```

이 간단한 인덱스 하나가 없으면, 전체 컬렉션을 스캔하는 일이 발생해서 배치 처리 시간이 수십 배 늘어날 수 있습니다.

또한, 복합 인덱스(composite index)를 잘 활용하면 여러 조건으로 필터링할 때도 쾌적한 성능을 유지할 수 있죠. 인덱스 설계는 배치 쿼리 패턴을 분석한 후에 결정하는 게 가장 좋습니다.


## 보안은 배치 작업에서도 절대 빼놓으면 안 되는 요소

배치 작업이라고 해서 보안이 느슨해지면 안 됩니다. 특히 MongoDB-backed Spring Batch는 데이터 접근 권한을 엄격히 관리해야 해요.

Spring Security를 배치 작업에 적용해서 인증과 권한 부여를 처리하는 게 기본입니다. 예를 들어, 배치 작업용 서비스 계정만 MongoDB에 접근하도록 하고, 그 외 사용자 접근을 제한하는 방식이죠.

```java
@Configuration
@EnableBatchSecurity
public class BatchSecurityConfig extends WebSecurityConfigurerAdapter {

    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
          .authorizeRequests()
          .antMatchers("/batch/**").hasRole("BATCH_USER")
          .and()
          .httpBasic();
    }
}
```

그리고 MongoDB 자체 인증도 SCRAM-SHA-256 같은 강력한 인증 메커니즘을 쓰고, 역할 기반 접근 제어(RBAC)를 적용해 배치 데이터베이스 권한을 최소한으로 제한하는 게 좋습니다.

이렇게 하면 배치 작업 중 데이터 유출 위험을 크게 줄일 수 있습니다.


## 프로덕션에서 MongoDB-backed 배치 작업을 안정적으로 운영하려면?

실제 운영 환경에서는 배치 작업이 실패하거나 지연될 때 바로 알 수 있어야 하죠. 그래서 모니터링과 로깅 설정을 강화하는 게 필수입니다.

Spring Boot Actuator를 통해 배치 작업 상태를 REST API로 노출하고, Prometheus나 Grafana 같은 모니터링 도구와 연동해 실시간 대시보드를 만들었어요. 이렇게 하면 배치 지연이나 오류 발생 시 즉시 대응할 수 있습니다.

또한, MongoDB 쿼리 로그와 배치 로그를 분리해서 저장하고, 로그 레벨을 환경별로 조절해 장애 원인 분석에 도움을 주도록 했습니다.

### 마무리하며

처음엔 MongoDB-backed Spring Batch 작업이 낯설었지만, Spring Boot 4.1 덕분에 훨씬 쉽게 도입할 수 있었고, 성능과 보안도 충분히 챙길 수 있었습니다. 특히 커넥션 풀 크기와 청크 사이즈 튜닝, 인덱스 설계가 성능에 미치는 영향은 직접 경험해보니 확실히 체감됐어요.

보안 측면도 배치 작업이라고 소홀히 하면 안 되고, Spring Security와 MongoDB 인증을 적절히 조합하는 게 중요하다는 걸 다시 한번 느꼈습니다.

다음 프로젝트에서 MongoDB-backed 배치 작업을 고민한다면, 이 글에서 다룬 설정과 팁을 꼭 참고해보세요. 작은 설정 하나가 전체 배치 처리 속도와 안정성을 확 바꿔놓을 수 있습니다.
