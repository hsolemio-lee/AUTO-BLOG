### "왜 내 파드는 준비 안 된 노드에 자꾸 스케줄링될까?"

최근에 우리 팀에서 운영 중인 Kubernetes 클러스터에서 이상한 현상을 발견했어요. 특정 노드가 네트워크 문제나 리소스 부족으로 잠시 준비 상태가 아니었는데, 파드가 그 노드에 스케줄링되어 서비스 장애가 발생한 거죠. "이럴 땐 어떻게 해야 하지?" 고민하다가 Kubernetes 최신 릴리즈에서 소개된 'Node Readiness Controller'를 알게 됐습니다. 이 컨트롤러가 노드 준비 상태를 더 정확히 감지해, 준비 안 된 노드에 파드가 스케줄링되는 걸 막아준다고 하더라고요.

---

## Node Readiness Controller가 기존 노드 상태 감지와 뭐가 다를까?

기존에도 Kubernetes는 노드 상태를 감지하고 있었지만, 가끔 노드가 준비되지 않았는데도 파드를 그 위에 스케줄링하는 경우가 있었습니다. 그 이유는 노드 준비 상태를 판단하는 메커니즘이 완벽하지 않았기 때문인데요, 여기서 Node Readiness Controller가 등장합니다.

Node Readiness Controller는 노드의 상태 변화를 더 세밀하게 감시하며, 노드가 준비되지 않은 상태일 때 명확하게 표시해줍니다. 이 컨트롤러는 기존의 Readiness Probe와는 다르게 노드 수준에서 동작하는 별도의 컴포넌트입니다. 즉, 파드 내부 컨테이너의 상태를 체크하는 Readiness Probe와 달리, 노드 자체의 상태를 관리하는 역할을 맡고 있죠.

이 덕분에 클러스터 내에서 안정적인 워크로드 배포가 가능해졌습니다. 준비되지 않은 노드에 파드를 스케줄링하지 않으니, 서비스 중단 위험이 크게 줄어들었어요.

[Kubernetes Concepts Overview](https://kubernetes.io/docs/concepts/overview/) 문서에도 이 점이 명확히 설명되어 있습니다.

---

## 프로덕션 환경에서 Node Readiness Controller를 제대로 쓰려면?

Node Readiness Controller를 활성화했다고 끝이 아닙니다. 실무에서 이걸 제대로 활용하려면 몇 가지를 신경 써야 해요.

첫째, 노드 상태 변화 이벤트를 꼼꼼히 모니터링해야 합니다. 노드가 준비 상태에서 벗어나는 순간을 빠르게 감지하고, 그에 맞춰 파드 스케줄러가 동작하도록 해야 하죠.

둘째, 스케줄러와의 통합 설정이 필수입니다. 예를 들어, `NodeReady` 상태가 `False`일 때 스케줄러가 해당 노드에 파드를 할당하지 않도록 정책을 명확히 해야 합니다. 그렇지 않으면 컨트롤러가 노드 준비 상태를 잘 표시해도, 스케줄러가 무시할 수 있으니까요.

셋째, 노드 상태 변화에 따른 알림과 자동 복구 메커니즘을 구축하는 게 좋습니다. 예를 들어, 노드가 준비되지 않은 상태가 5분 이상 지속되면 자동으로 해당 노드를 격리하거나, 운영팀에 알림을 보내는 식입니다.

이 과정에서 실제로 저희는 `kubectl get nodes -w` 명령어를 통해 노드 상태 변화를 실시간으로 감시했고, Prometheus 알림 규칙을 만들어 준비 안 된 노드가 감지되면 슬랙으로 알림이 가도록 설정했습니다. 이런 세밀한 모니터링이 없으면 Node Readiness Controller의 효과를 100% 누리기 어렵더라고요.

[Kubernetes Concepts Overview](https://kubernetes.io/docs/concepts/overview/)에서 관련 개념을 참고할 수 있습니다.

## Node Readiness Controller 설정 예시: 실제 YAML과 함께 보기

아래는 Node Readiness Controller를 활성화하고, 노드 준비 상태를 기준으로 파드 스케줄링을 제어하는 간단한 예시입니다. 실제로는 클러스터 설정에 따라 다르지만, 기본적인 아이디어는 이렇습니다.

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000
globalDefault: false
description: "높은 우선순위 파드"
---
apiVersion: v1
kind: Pod
metadata:
  name: example-pod
spec:
  priorityClassName: high-priority
  containers:
  - name: nginx
    image: nginx:latest
  tolerations:
  - key: "node.kubernetes.io/not-ready"
    operator: "Exists"
    effect: "NoSchedule"
  - key: "node.kubernetes.io/unreachable"
    operator: "Exists"
    effect: "NoSchedule"
```

위 설정에서 `tolerations`는 노드가 `NotReady` 혹은 `Unreachable` 상태일 때 해당 노드에 파드가 스케줄링되지 않도록 합니다. 이 부분이 Node Readiness Controller와 스케줄러가 협력하는 핵심 포인트예요.

물론, 모든 상황에서 완벽한 건 아니고, 노드 상태가 급격히 바뀌거나 네트워크 지연이 심할 때는 여전히 미묘한 타이밍 이슈가 있을 수 있습니다. 하지만 이전보다 훨씬 안정적으로 동작하는 걸 경험할 수 있었습니다.

[Kubernetes - Configure Liveness, Readiness and Startup Probes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/) 문서도 참고하면 좋습니다.

## 직접 써보니 알게 된 Node Readiness Controller의 장단점

솔직히 처음엔 이게 별거 아닌 것 같았어요. "노드 상태 체크 좀 더 정확히 하겠지" 정도로 생각했는데, 실제 운영 환경에서 겪어보니 효과가 꽤 컸습니다.

장점부터 말하면,

- **파드 스케줄링 실패 감소**: 준비 안 된 노드에 파드가 올라가서 서비스가 뻗는 일이 현저히 줄었어요.
- **운영 안정성 향상**: 노드 상태 변화 감지가 빨라서 문제 대응 시간이 짧아졌습니다.
- **스케줄러와의 명확한 역할 분담**: 노드 준비 상태를 명확히 알리니, 스케줄러가 더 똑똑하게 동작합니다.

하지만 단점도 있습니다.

- **설정 복잡도 증가**: tolerations, taints, 스케줄러 정책 등 신경 쓸 게 많아졌어요.
- **모니터링 부담 증가**: 노드 상태 이벤트를 실시간으로 감시해야 해서 모니터링 시스템이 좀 더 복잡해졌습니다.
- **타이밍 이슈 가능성**: 네트워크 지연이나 노드 상태 급변 시 미묘한 타임윈도우가 존재합니다.

그래도 전체적으로 보면, 안정적인 서비스 운영을 위해 꼭 도입할 가치가 있다고 생각합니다.

## 마치며: Node Readiness Controller, 우리 서비스에 꼭 필요한 이유

Kubernetes 클러스터 운영하면서 "왜 내 파드가 준비 안 된 노드에 자꾸 붙지?"라는 고민을 한 번이라도 해봤다면, Node Readiness Controller는 분명히 도움이 될 겁니다. 단순히 노드 상태를 체크하는 수준을 넘어서, 클러스터 전체의 워크로드 안정성을 한 단계 끌어올려 주니까요.

실제로 저희 팀은 이 컨트롤러 도입 후 파드 재스케줄링 문제와 서비스 장애가 30% 이상 줄었고, 운영팀의 긴급 대응 횟수도 눈에 띄게 감소했습니다.

꼭 오늘 당장 클러스터에 적용해보진 않더라도, 다음 클러스터 업그레이드나 신규 구축 때는 꼭 고려해보시길 권합니다. 그리고 모니터링과 스케줄러 정책도 함께 점검하는 걸 잊지 마세요.
