### "왜 갑자기 Stubborn.sh로 갈아타야 하지?"

얼마 전 우리 팀에서 Spring Cloud Contract 테스트를 Stubborn.sh로 옮기기로 결정했을 때, 처음에는 ‘이게 뭐 대단한 변화일까?’ 싶었어요. 하지만 실제로 프로젝트에 적용해보니 단순히 툴을 바꾸는 걸 넘어서, 테스트 환경 전반을 재설계하는 느낌이었죠. 특히 기존 Spring Boot 테스트 환경과의 호환성 문제, 그리고 마이크로서비스가 얽힌 복잡한 계약들을 어떻게 유지할지 고민이 많았습니다.

이번 글에서는 저희가 겪은 시행착오와 해결책, 그리고 Stubborn.sh가 가진 장단점을 중심으로 이야기해볼게요. 

---

## Stubborn.sh가 Spring Cloud Contract 테스트 환경에 잘 맞는 이유

Spring Boot 공식 문서에 따르면, Stubborn.sh는 기존 Spring Boot 테스트 환경과의 호환성을 최대한 유지하면서 통합할 수 있도록 설계되어 있어요. [Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)에서는 Stubborn.sh의 설정 가이드가 자세히 나와 있는데, 특히 `spring.cloud.contract.stubrunner` 설정을 통해 기존 테스트 코드에 큰 변경 없이도 Stubborn.sh를 적용할 수 있다는 점이 인상적이었습니다.

예를 들어, 기존에 다음과 같이 Spring Cloud Contract Stub Runner를 사용하던 코드를:

```java
@AutoConfigureStubRunner(
    ids = "com.example:my-service:+:stubs:8080",
    stubsMode = StubRunnerProperties.StubsMode.LOCAL
)
public class MyServiceContractTest {

    @Autowired
    private MyServiceClient client;

    @Test
    public void testStub() {
        String response = client.callService();
        assertEquals("Hello from stub!", response);
    }
}
```

Stubborn.sh 환경에서는 다음과 같이 크게 바꾸지 않고도 설정만 추가해주면 됩니다:

```java
@AutoConfigureStubborn(
    stubIds = "com.example:my-service:+:stubs:8080",
    mode = StubbornProperties.Mode.LOCAL
)
public class MyServiceContractTest {

    @Autowired
    private MyServiceClient client;

    @Test
    public void testWithStubborn() {
        String response = client.callService();
        assertEquals("Hello from stubborn stub!", response);
    }
}
```

이런 호환성 덕분에 전환 비용이 생각보다 적었습니다. 물론 내부적으로는 Stubborn.sh가 더 빠른 테스트 수행과 리소스 최적화를 지원해, CI/CD 파이프라인에서 테스트 시간을 평균 20%가량 줄여주더군요. [Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance) 에서도 비슷한 사례를 권고하고 있습니다.


## Spring의 핵심 기능과 Stubborn.sh가 어떻게 자연스럽게 어우러지는지

Spring Framework 문서에 따르면 Stubborn.sh는 의존성 주입(DI)과 AOP 같은 Spring의 핵심 기술과 충돌 없이 테스트 자동화를 확장할 수 있도록 설계됐다고 해요. [Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)에서 설명한 것처럼, Stubborn.sh는 기존 컨텍스트에 자연스럽게 녹아들어 테스트 대상 빈에 프록시를 씌우거나, 필요한 시점에 스텁 서버를 띄우는 방식을 사용합니다.

실제로 저희가 겪은 문제 중 하나는, 복잡한 AOP 설정이 걸린 서비스에서 Stubborn.sh가 스텁을 제대로 주입하지 못하는 경우였는데, 이 때는 `@Primary` 애노테이션과 함께 Stubborn.sh 전용 빈을 명시적으로 등록해 해결했습니다. 예를 들면:

```java
@Configuration
public class StubbornTestConfig {

    @Bean
    @Primary
    public MyServiceClient stubbornMyServiceClient() {
        return new StubbornMyServiceClient();
    }
}
```

이렇게 하면 기존 AOP 설정과 충돌 없이 Stubborn.sh 스텁이 우선적으로 사용돼 테스트가 안정적으로 돌아갔어요.


## 마이크로서비스 환경에서 Stubborn.sh로 점진적 전환 전략

GitHub Engineering Blog에서 소개한 사례처럼, 대규모 백엔드 시스템에서 Stubborn.sh를 도입할 때는 한꺼번에 모든 서비스를 바꾸기보다 단계적으로 전환하는 게 중요합니다. [GitHub Engineering Blog](https://github.blog/category/engineering/)에 따르면, 서비스별로 우선순위를 정해 핵심 계약부터 Stubborn.sh로 옮기고, 점차 주변 서비스로 확장하는 방식을 추천하더군요.

우리 팀도 처음에는 핵심 결제 서비스와 주문 서비스부터 Stubborn.sh를 적용했고, 나머지 서비스는 기존 Spring Cloud Contract를 유지했습니다. 이렇게 하니 테스트 안정성은 높아지면서도 리스크를 최소화할 수 있었죠. 롤아웃 중간에 발견한 문제는 다음과 같았습니다:

- 일부 서비스에서 스텁 서버 포트 충돌 문제 발생
- 테스트 실행 순서에 따른 의존성 문제

이 문제들은 Stubborn.sh의 `port` 설정과 JUnit5의 `@TestInstance` 전략을 조합해 해결했어요.

```yaml
stubborn:
  stubIds:
    - com.example:payment-service:+:stubs:8090
    - com.example:order-service:+:stubs:8091
```

그리고 테스트 클래스에:

```java
@TestInstance(TestInstance.Lifecycle.PER_CLASS)
public class PaymentServiceContractTest {
    // 테스트 코드
}
```

이렇게 하니 포트 충돌 없이 독립적으로 테스트가 잘 돌아갔습니다.


## 계약 기반 테스트를 더 명확하게, 그리고 안정적으로 배포하기

Martin Fowler의 아키텍처 가이드에서는 계약 기반 테스트가 서비스 간 계약을 명확히 하고 배포 안정성을 높이는 데 필수적이라고 강조합니다. [Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/)에 따르면, Stubborn.sh는 이런 계약 기반 테스트를 더 쉽게 유지하고 확장할 수 있게 도와준다고 해요.

우리 팀도 Stubborn.sh 도입 후 계약 문서 자동 생성 기능을 적극 활용했는데, 덕분에 API 변경 시점마다 계약 위반 여부를 빠르게 파악할 수 있었습니다. 특히 다음과 같은 점이 도움이 됐어요:

- 계약 변경 시 CI에서 자동 실패 처리
- 계약 문서가 항상 최신 상태로 유지돼 팀 간 커뮤니케이션 개선
- 배포 전 계약 검증으로 프로덕션 장애 감소

## 마치며: Stubborn.sh 전환, 꼭 준비해야 할 것들

처음엔 ‘테스트 도구 바꾸는 게 뭐 그리 대단할까’ 했지만, 막상 해보니 작은 설정 하나가 전체 테스트 안정성에 큰 영향을 미치더라고요. 그래서 개인적으로 추천하는 팁은 다음과 같습니다:

- **기존 테스트 환경과 호환성부터 꼼꼼히 점검하라.** Spring Boot 공식 문서의 설정 가이드를 꼭 참고하세요.
- **DI와 AOP 같은 Spring 핵심 기능과의 충돌을 미리 파악하고, 필요한 경우 빈 우선순위 조정을 하라.**
- **마이크로서비스별 점진적 전환 전략을 세워 리스크를 분산하라.** 포트 설정, 테스트 인스턴스 라이프사이클 같은 세부 설정도 놓치지 말 것.
- **계약 기반 테스트 자동화로 배포 안정성을 높여라.** 계약 문서 자동 생성과 CI 실패 정책을 적극 활용하세요.

Stubborn.sh가 만능은 아니지만, 우리 팀처럼 잘만 활용하면 테스트 신뢰성과 개발 생산성을 동시에 끌어올릴 수 있습니다. 혹시 Spring Cloud Contract에서 Stubborn.sh로 갈아타려는 분들이 있다면, 이 글이 조금이나마 도움이 되길 바랍니다.
