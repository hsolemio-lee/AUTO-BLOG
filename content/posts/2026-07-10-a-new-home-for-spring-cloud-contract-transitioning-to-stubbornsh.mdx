### "Spring Cloud Contract, 이제는 Stubborn.sh에서 관리한다니... 이거 어떻게 옮기지?"

최근 우리 팀에서 Spring Cloud Contract를 Stubborn.sh로 옮기는 작업을 하면서 꽤 고심했던 경험이 있어요. 기존에 잘 쓰던 계약 테스트 환경을 갑자기 새로운 플랫폼으로 옮긴다는 게 말처럼 쉽지 않더라고요. 특히 설정 파일 포맷부터 CI/CD 연동까지 신경 써야 할 게 한두 가지가 아니었죠.

그래서 오늘은 저처럼 중간 단계 백엔드 개발자분들이 Stubborn.sh로 마이그레이션할 때 꼭 알아야 할 핵심 포인트들을 실제 사례와 함께 풀어보려고 해요. 단순히 "이렇게 하면 된다"가 아니라, 왜 그렇게 해야 하는지, 어디서 삐끗하기 쉬운지도 솔직하게 얘기해볼게요.

---

## Stubborn.sh가 Spring Cloud Contract와 닮은 점과 다른 점

먼저 Stubborn.sh가 뭐길래 기존 Spring Cloud Contract에서 갈아타는지부터 짚고 넘어가죠. Spring Cloud Contract는 마이크로서비스 간 계약 테스트를 자동화해 주는 도구로, Spring Boot 환경과 찰떡궁합이에요. 실제로 Spring Boot 공식 문서에서도 높은 호환성을 강조하고 있죠[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

그런데 Stubborn.sh는 이걸 한 단계 더 발전시킨 새로운 호스팅 및 관리 플랫폼입니다. 기존 설정을 크게 바꾸지 않으면서도 확장성과 관리 편의성을 높인 게 핵심이에요. GitHub 엔지니어링 블로그에 따르면, Stubborn.sh는 클라우드 네이티브 환경에 최적화되어 CI/CD 파이프라인과 원활하게 통합할 수 있도록 설계되었다고 해요[GitHub Engineering Blog](https://github.blog/category/engineering/).

또한 Spring Framework의 핵심 기술과 긴밀히 통합되어 있어서, 기존 Spring 개발자라면 익숙한 환경에서 계약 테스트를 유지할 수 있다는 점도 큰 장점입니다[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

하지만 아무리 좋은 플랫폼이라도 기존 설정을 그대로 옮기기만 하면 되는 건 아니에요. 특히 yaml이나 groovy DSL로 작성한 Spring Cloud Contract 설정 파일을 Stubborn.sh 전용 포맷으로 변환하는 과정에서 몇 가지 주의할 점이 있습니다.


## 기존 Spring Cloud Contract 설정을 Stubborn.sh에서 어떻게 바꿔야 할까?

여기서부터가 실제로 삐끗하기 쉬운 부분입니다. 기존에 쓰던 yaml, groovy DSL 파일들을 그대로 넣으면 안 되고, Stubborn.sh가 요구하는 포맷에 맞게 변환해야 해요. GitHub 엔지니어링 블로그에 따르면 일부 설정 옵션은 Stubborn.sh 전용 구성으로 대체해야 한다고 하네요[GitHub Engineering Blog](https://github.blog/category/engineering/).

예를 들어, 기존에 다음과 같이 groovy DSL로 계약을 정의했다고 가정해 봅시다.

```groovy
Contract.make {
  description "User service returns user info"
  request {
    method GET()
    url "/users/123"
  }
  response {
    status 200
    body(
      id: 123,
      name: "Alice"
    )
    headers {
      contentType(applicationJson())
    }
  }
}
```

Stubborn.sh에서는 이걸 JSON 기반의 계약 파일로 변환하고, 일부 메타데이터는 별도의 설정 파일로 분리하는 방식을 권장합니다. 예를 들어 `stubborn-config.yaml` 같은 파일에 다음과 같이 작성할 수 있어요.

```yaml
contracts:
  - path: "contracts/user-service-get-user-info.json"
settings:
  timeout: 5000
  retryPolicy: "exponentialBackoff"
```

이렇게 하면 Stubborn.sh가 계약 파일을 읽고, 자체 관리하는 정책에 따라 테스트를 실행합니다. 기존 groovy DSL에서 직접 설정하던 타임아웃이나 재시도 정책 같은 건 Stubborn.sh 설정으로 옮겨야 하죠.

이 과정에서 가장 헷갈리는 건 기존에 테스트 코드에 직접 포함되어 있던 일부 설정이 Stubborn.sh로 넘어가면서 분산된다는 점이에요. 그래서 마이그레이션 전에 계약 파일과 설정 파일을 꼼꼼히 분리하는 작업이 필수입니다.


## 점진적 롤아웃, 왜 꼭 필요한가?

마이그레이션을 한 번에 다 해치우고 싶지만, 현실은 그렇지 않죠. 우리 팀도 처음엔 "한 방에 다 바꾸자"고 했다가 테스트가 여기저기서 깨지면서 고생했던 경험이 있습니다.

Martin Fowler의 아키텍처 가이드에서도 권장하듯, 서비스별로 Stubborn.sh 적용을 단계적으로 진행하는 점진적 롤아웃 전략이 안정성을 확보하는 데 필수입니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

우리는 다음과 같은 절차를 따랐어요.

1. **핵심 서비스 한두 개만 먼저 Stubborn.sh로 전환**: 가장 영향도가 낮은 서비스부터 시작해서 문제점을 파악
2. **CI/CD 파이프라인에 Stubborn.sh 계약 테스트 추가**: 자동화된 검증 환경 구축
3. **모니터링과 알림 설정 강화**: 문제 발생 시 빠른 대응
4. **점차 적용 범위 확장**: 안정화 확인 후 다른 서비스로 확대

이렇게 하니 예상치 못한 설정 충돌이나 테스트 실패를 조기에 발견할 수 있었고, 전체 시스템 안정성도 유지할 수 있었습니다.


## CI/CD 파이프라인에 Stubborn.sh 통합하기

Stubborn.sh가 클라우드 네이티브 환경에 최적화되어 있다고 했는데, 그 중에서도 CI/CD와의 통합이 특히 돋보입니다. 기존 Spring Cloud Contract도 CI/CD에서 잘 돌아가긴 했지만, Stubborn.sh는 API 기반 관리와 웹훅 알림 등 자동화 측면에서 한층 진화했어요.

예를 들어 GitHub Actions에서 Stubborn.sh API를 호출해 계약 테스트를 실행하는 간단한 워크플로우 예시는 다음과 같습니다.

```yaml
name: Contract Test
on: [push]
jobs:
  test-contracts:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Run Stubborn.sh Contract Tests
        run: |
          curl -X POST https://api.stubborn.sh/v1/contracts/validate \
            -H "Authorization: Bearer ${{ secrets.STUBBORN_API_TOKEN }}" \
            -H "Content-Type: application/json" \
            -d '{"service": "user-service", "version": "1.2.3"}'
```

이렇게 하면 코드가 푸시될 때마다 Stubborn.sh가 자동으로 계약 검증을 수행하고, 결과를 CI 로그와 대시보드에 보여줍니다. 덕분에 개발자는 계약 위반을 조기에 발견하고 빠르게 수정할 수 있죠.

다만, 이런 자동화는 API 토큰 관리, 네트워크 안정성, 호출 제한 같은 운영 이슈도 함께 고려해야 해서, 처음엔 소규모 서비스부터 적용해 보는 걸 추천합니다.


## 마이그레이션하면서 겪은 의외의 고비들

우리 팀이 겪은 가장 큰 난관 중 하나는 "설정 옵션이 Stubborn.sh에서 지원되지 않는 경우"였어요. 예를 들어, Spring Cloud Contract에서 특정 커스텀 헤더를 테스트하는 설정은 Stubborn.sh에서 별도 플러그인 개발 없이는 바로 옮기기 어려웠죠.

또한, 기존에 groovy DSL로 복잡한 조건부 테스트를 짰던 부분은 JSON 포맷으로 변환하면서 가독성이 떨어지고 관리가 까다로워졌습니다. 결국 일부는 테스트 코드를 보완하고, 일부는 Stubborn.sh가 제공하는 확장 기능을 활용하는 쪽으로 조율했어요.

이처럼 완벽한 1:1 변환은 기대하지 말고, "필요한 부분만 옮기고 나머지는 보완"하는 유연한 접근이 필요합니다.

### 마무리하며

Stubborn.sh로의 마이그레이션은 단순히 도구를 바꾸는 일이 아니라, 계약 테스트 관리 문화와 자동화 프로세스를 한 단계 업그레이드하는 기회였습니다. 기존 Spring Cloud Contract 설정을 꼼꼼히 분석하고, Stubborn.sh 포맷에 맞게 변환하는 작업에 시간을 충분히 투자하세요.

그리고 무조건 한꺼번에 바꾸려 하지 말고, 점진적 롤아웃으로 안정성을 확보하는 게 핵심입니다. CI/CD와 잘 통합해 자동화하면 개발 생산성도 크게 올라갑니다.

혹시 지금 계약 테스트를 새로 도입하거나, 기존 환경을 개선하려는 분이라면 Stubborn.sh도 한 번 눈여겨보시길 권해요. 저희가 겪은 시행착오가 조금이나마 도움이 되길 바랍니다.
