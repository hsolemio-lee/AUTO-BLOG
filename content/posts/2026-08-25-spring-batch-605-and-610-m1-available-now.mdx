## 갑자기 Spring Batch를 업그레이드해야 한다면, 어디서부터 시작할까?

최근 우리 팀에서 Spring Batch 5.x에서 6.x로 마이그레이션을 고민하다가 실제로 6.0.5와 6.1.0-M1 버전을 직접 써보게 됐어요. 처음엔 "자바 17 이상이 필수라니, 우리 환경에 맞을까?" 하는 걱정도 있었죠. 그런데 막상 써보니 멀티스레딩 처리와 트랜잭션 관리가 훨씬 유연해져서, 대용량 데이터 처리에서 체감 성능이 꽤 올라갔습니다.

이번 글에서는 Spring Batch 6 버전의 핵심 변화와, 실제 프로덕션 환경에 적용할 때 꼭 챙겨야 할 튜닝 포인트, 보안 강화 사항, 그리고 안정적인 롤아웃 전략을 동료 개발자 눈높이에 맞춰 풀어보려고 해요.

## Spring Batch 6.0.5와 6.1.0-M1, 자바 17 이상에서 누릴 수 있는 성능과 보안

Spring Batch 6는 Spring Boot 3.x 및 Spring Framework 6.x와 완벽 호환되도록 설계됐습니다. 즉, 자바 17 이상이 필수인데요. 이 덕분에 레코드 처리 속도가 눈에 띄게 개선됐고, JDK 최신 기능을 활용하는 만큼 안정성도 좋아졌어요.

특히 6.0.5 버전은 안정화에 초점이 맞춰진 반면, 6.1.0-M1은 마일스톤 버전으로 새 기능 테스트 및 피드백 수집용입니다. 6.1.0-M1은 프로덕션 적용 전 충분한 검증이 필요하니, 실무에서는 6.0.5를 우선 고려하는 게 안전합니다.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)

### 자바 17 이상 필수, 왜 중요한가?

자바 17부터는 레코드, 패턴 매칭, 텍스트 블록 등 생산성 향상 기능들이 추가됐고, JVM 자체 최적화도 많이 이뤄졌죠. 덕분에 Spring Batch 내부에서도 더 깔끔한 코드와 빠른 실행이 가능해졌습니다.

예를 들어, 멀티스레딩 Chunk 처리 시 ForkJoinPool을 활용하는 부분에서 쓰레드 관리가 훨씬 효율적입니다. 이 부분은 아래에서 다시 설명할게요.

## 멀티스레딩과 트랜잭션 최적화로 대용량 배치 처리 속도 올리기

실제 운영 배치에서 가장 큰 고민은 "어떻게 하면 처리 속도를 높이면서도 데이터 정합성을 지킬 수 있을까"입니다. Spring Batch 6에서는 이 부분을 Chunk 기반 처리 개선과 트랜잭션 관리 최적화로 풀었어요.

### Chunk Size 조절과 멀티스레드 Step

기본적으로 Spring Batch는 Chunk 단위로 데이터를 읽고 처리한 뒤 커밋합니다. 그런데 6.x 버전부터는 멀티스레드 Step 구성이 더 쉬워졌고, Chunk 처리 성능도 개선됐죠.

아래 코드는 멀티스레드 Step 예시입니다. ThreadPoolTaskExecutor를 쓰고, chunkSize를 100으로 설정해 100건씩 읽고 쓰면서 동시에 4개의 쓰레드가 병렬 처리합니다.

```java
@Bean
public Step multiThreadStep() {
    return stepBuilderFactory.get("multiThreadStep")
        .<InputType, OutputType>chunk(100)
        .reader(itemReader())
        .processor(itemProcessor())
        .writer(itemWriter())
        .taskExecutor(taskExecutor())
        .throttleLimit(4) // 최대 4개의 쓰레드 동시 실행
        .build();
}

@Bean
public TaskExecutor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(4);
    executor.setMaxPoolSize(8);
    executor.setQueueCapacity(20);
    executor.setThreadNamePrefix("batch-thread-");
    executor.initialize();
    return executor;
}
```

이렇게 하면 CPU 코어를 최대한 활용하면서도, 트랜잭션 단위가 너무 커서 롤백 비용이 커지는 문제를 피할 수 있어요. Chunk 사이즈는 데이터 특성에 따라 50~200 사이에서 튜닝하는 걸 권장합니다.

### 트랜잭션 관리에서 주의할 점

멀티스레드 환경에서는 트랜잭션 격리 수준과 커밋 타이밍이 매우 중요합니다. Spring Batch 6는 트랜잭션 매니저와의 통합이 더 견고해졌지만, 데이터베이스 락 경합이나 교착 상태 가능성은 여전히 존재합니다.

따라서 트랜잭션 격리 수준은 기본 `READ_COMMITTED`를 유지하되, 필요한 경우 `REPEATABLE_READ`로 올려서 데이터 정합성을 확보하세요. 단, 이 경우 성능 저하가 있을 수 있으니 프로파일별로 설정 분리하는 게 좋습니다.

## 보안 강화, Spring Security 6와의 통합으로 배치 작업 권한 관리 더 단단하게

배치 작업 중 민감 데이터 처리 시 권한 관리와 인증은 절대 소홀히 할 수 없죠. Spring Batch 6는 Spring Security 6와의 통합을 강화해, 배치 잡 실행 권한을 세밀하게 제어할 수 있도록 했습니다.

### 배치 잡별 권한 설정 예시

예를 들어, 특정 잡은 관리자만 실행 가능하도록 하려면 Spring Security의 메서드 시큐리티를 활용할 수 있습니다.

```java
@EnableMethodSecurity
@Configuration
public class BatchSecurityConfig {

    @PreAuthorize("hasRole('ADMIN')")
    public void runSensitiveBatchJob() {
        // 배치 잡 실행 로직
    }
}
```

이렇게 하면 인증된 사용자 중 관리자 권한이 없는 경우 실행 자체가 차단돼, 보안 사고 위험이 줄어듭니다.

### 민감 데이터 암호화와 접근 제어

또한, Spring Batch 6에서는 민감 정보 암호화 처리도 권장합니다. 예를 들어, DB에 저장되는 배치 메타데이터나 로그에 개인정보가 포함될 경우, Jasypt 같은 라이브러리와 연동해 암호화하는 방식을 많이 씁니다.

참고로, Spring Security 6의 최신 암호화 알고리즘과 키 관리 정책을 함께 적용하면 더욱 안전해집니다.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)

## 운영 환경에선 프로파일 분리, 모니터링, 장애 복구 전략이 필수

실제 프로덕션에 Spring Batch 6를 도입할 때는 단순히 코드만 바꾸는 게 아니라, 환경 설정과 운영 전략도 꼼꼼히 준비해야 합니다.

### 프로파일별 설정 분리로 환경별 최적화

예를 들어, 개발, 테스트, 운영 환경마다 데이터베이스 연결, 트랜잭션 격리 수준, 로그 레벨 등이 다릅니다. Spring Boot 프로파일을 적극 활용해 `application-prod.yml`, `application-dev.yml`로 설정을 분리하세요.

```yaml
# application-prod.yml
spring:
  batch:
    initialize-schema: always
  datasource:
    url: jdbc:mysql://prod-db:3306/batch
    username: prod_user
    password: secret
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 50
logging:
  level:
    org.springframework.batch: INFO
```

이런 분리는 운영 중에 설정을 바꾸거나 문제를 빠르게 진단하는 데 큰 도움이 됩니다.

### Spring Boot Actuator와 연동한 모니터링

Spring Boot Actuator를 통해 배치 잡 상태, 메트릭, 헬스 체크를 실시간으로 모니터링할 수 있습니다. 배치 잡 실패나 지연이 감지되면 알림을 보내도록 설정하면 장애 대응 속도가 빨라지죠.

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,batch
  endpoint:
    batch:
      enabled: true
```

이렇게 하면 `/actuator/batch` 엔드포인트에서 잡 실행 현황을 확인할 수 있습니다.

### 장애 복구 전략은 어떻게 세울까?

배치 작업 중 장애가 발생하면, 재시도 정책과 실패 시 롤백 범위를 명확히 해야 합니다. Spring Batch 6에서는 실패한 청크만 재처리하는 기능이 더 안정적이어서, 전체 잡을 다시 돌리는 부담을 줄일 수 있어요.

운영 환경에서는 실패 시 자동 재시도 횟수, 백오프 정책, 그리고 실패 알림 체계를 반드시 마련하세요. 예를 들어, `RetryTemplate`을 활용해 3회 재시도 후 실패 처리하는 코드는 다음과 같습니다.

```java
@Bean
public RetryTemplate retryTemplate() {
    RetryTemplate retryTemplate = new RetryTemplate();
    FixedBackOffPolicy backOffPolicy = new FixedBackOffPolicy();
    backOffPolicy.setBackOffPeriod(2000); // 2초 대기
    retryTemplate.setBackOffPolicy(backOffPolicy);

    SimpleRetryPolicy retryPolicy = new SimpleRetryPolicy();
    retryPolicy.setMaxAttempts(3);
    retryTemplate.setRetryPolicy(retryPolicy);

    return retryTemplate;
}
```

이걸 배치 잡에 적용하면, 네트워크 일시 장애나 DB 락 문제 같은 흔한 오류에 유연하게 대응할 수 있습니다.[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance)

## 마치며: 6.1.0-M1은 아직 실험 단계, 6.0.5 안정 버전으로 시작하자

Spring Batch 6 시리즈는 자바 17 이상 환경에서 대용량 배치 처리 성능과 보안을 한 단계 끌어올렸습니다. 하지만 6.1.0-M1은 마일스톤 버전이라 아직 실험적 요소가 많으니, 안정적인 프로덕션 환경에서는 6.0.5 버전을 권장해요.

실제로 우리 팀도 6.0.5로 마이그레이션 후 멀티스레딩 Chunk 처리 덕분에 처리 시간이 30% 이상 단축됐고, Spring Security 6 연동으로 권한 관리도 훨씬 견고해졌습니다.

그리고 운영 환경에서는 프로파일별 설정 분리, Actuator 기반 모니터링, 장애 복구 전략 수립을 반드시 병행해야 한다는 점, 잊지 마세요. 이건 실제로 겪어보면 "아, 이걸 왜 이제야 했지?" 싶은 부분입니다.

여러분도 새 버전 도입 시 이런 점들을 참고해서, 안전하고 빠른 배치 시스템을 만들어 보시길 바랍니다!

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
