### 갑자기 서버가 느려졌다면, 어디부터 봐야 할까?

"어? 왜 갑자기 API 응답이 3초씩 걸리지?" 이런 경험, 한 번쯤은 다들 있을 거예요. 특히 Spring MVC로 만든 서비스라면, 기본 설정만으로는 트래픽이 조금만 몰려도 병목이 생기기 쉽죠. 그래서 이번에는 제가 직접 겪고 적용했던 Spring MVC 최적화 방법들을 공유해 보려고 합니다. 단순히 이론이 아니라, 실제 운영 환경에서 바로 써먹을 수 있는 팁 위주로요.

## Spring MVC에서 비동기 요청 처리가 왜 답일까?

전통적으로 Spring MVC는 요청이 들어오면 스레드 하나를 할당해서 처리하는 동기 방식이에요. 그런데 요청이 많아지면 스레드가 모자라서 큐가 길어지고, 응답 지연이 심해지죠. 이럴 때 비동기 요청 처리를 도입하면 스레드 블로킹을 줄일 수 있습니다.

예를 들어, DB 조회나 외부 API 호출처럼 시간이 걸리는 작업을 비동기로 처리하면, 스레드는 작업이 끝날 때까지 기다리지 않고 다른 요청을 처리할 수 있어요. 실제로 Spring Framework 공식 문서에서도 Async Request Processing을 권장하고 있습니다.[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)

```java
@RestController
public class AsyncController {

    @GetMapping("/async-data")
    public Callable<String> getAsyncData() {
        return () -> {
            // 시간이 오래 걸리는 작업 시뮬레이션
            Thread.sleep(2000);
            return "비동기 처리 완료";
        };
    }
}
```

이 코드는 요청이 들어오면 바로 Callable을 반환하고, 실제 작업은 별도 스레드에서 처리됩니다. 서버 스레드는 즉시 반환되어 다른 요청을 처리하죠. 물론, 비동기 처리 도입 시에는 스레드 풀 크기, 타임아웃 설정 등을 꼼꼼히 조절해야 합니다. 너무 크게 잡으면 메모리 압박, 너무 작으면 병목이 생기니까요.

## JVM 튜닝과 Actuator 모니터링으로 병목 잡기

프로덕션에서 JVM 튜닝 없이 그냥 돌리면 GC가 잦아지거나 메모리 부족으로 성능 저하가 발생하기 쉽습니다. Spring Boot에서는 Actuator를 활용해 애플리케이션 상태를 실시간으로 모니터링할 수 있는데요, 이걸 잘 활용하면 병목 구간을 빠르게 찾아낼 수 있어요.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)

예를 들어, JVM 힙 메모리 사용량, GC 통계, 스레드 덤프 등을 Actuator 엔드포인트로 노출시키고 Prometheus, Grafana 같은 툴과 연동하면 실시간 대시보드를 만들 수 있습니다.

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,metrics,threaddump,jvm
```

이렇게 설정한 뒤 `/actuator/metrics/jvm.memory.used` 같은 엔드포인트를 확인하면 메모리 상태를 바로 알 수 있죠. 실제로 우리 팀에서는 GC가 자주 발생하는 시점을 Actuator 모니터링으로 잡아서, 힙 사이즈를 2GB에서 4GB로 늘리고, G1 GC 튜닝을 적용해 응답 속도가 30% 이상 개선된 경험이 있습니다.

## 캐싱 전략으로 DB 호출과 네트워크 부담 줄이기

캐싱은 백엔드 최적화에서 빼놓을 수 없죠. Spring MVC에서는 `@Cacheable` 애노테이션으로 간단히 메서드 결과를 캐시할 수 있는데, 이걸 적절히 활용하면 DB 호출 횟수를 획기적으로 줄일 수 있습니다.[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance)

```java
@Service
public class UserService {

    @Cacheable(value = "userCache", key = "#userId")
    public User getUserById(Long userId) {
        // DB 호출
        return userRepository.findById(userId).orElse(null);
    }
}
```

위처럼 캐시를 쓰면 동일한 userId 요청이 들어올 때 DB를 다시 조회하지 않고 캐시에서 바로 응답하죠. 캐시 저장소로는 Redis를 많이 쓰는데, TTL(Time To Live)을 적절히 설정해 데이터 신선도를 유지하는 게 중요합니다.

또한 HTTP 캐시 헤더를 활용해 클라이언트가 불필요하게 서버에 재요청하지 않도록 하는 것도 성능 개선에 큰 도움이 됩니다. 예를 들어 `Cache-Control: max-age=3600` 헤더를 붙이면 1시간 동안 클라이언트가 캐시를 재사용하게 돼서 네트워크 트래픽이 줄어요.

## Spring Security 설정, 보안과 성능의 균형 맞추기

보안은 아무리 강조해도 지나치지 않지만, 과도한 보안 설정은 성능 저하를 부를 수 있어요. Spring Security를 쓸 때는 권한 검증과 CSRF 보호를 기본으로 하면서도, 불필요한 필터 체인을 줄이고 캐시 가능한 부분은 캐시하는 등 균형을 맞춰야 합니다.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)

예를 들어, REST API 서버라면 CSRF 보호를 비활성화하는 경우가 많은데, 이때는 JWT 같은 토큰 기반 인증으로 보안을 유지해야 합니다. 반대로 세션 기반 웹 애플리케이션이라면 CSRF 보호를 반드시 켜야 하죠.

```java
@Override
protected void configure(HttpSecurity http) throws Exception {
    http
        .csrf().disable() // REST API 특성상 비활성화
        .authorizeRequests()
        .antMatchers("/public/**").permitAll()
        .anyRequest().authenticated();
}
```

또한, 권한 검증 로직이 복잡해지면 필터 체인도 길어지는데, 이럴 때는 권한 체크를 서비스 레이어로 옮기고 필터는 최소화하는 게 성능에 유리합니다.

## 대규모 트래픽에서 커넥션 풀과 비동기 이벤트 처리 패턴이 중요한 이유

GitHub 엔지니어링 블로그에서는 대규모 트래픽을 처리할 때 Spring 기반 백엔드에서 커넥션 풀 최적화와 비동기 이벤트 처리 패턴을 적용해 높은 처리량과 낮은 지연 시간을 달성했다고 합니다.[GitHub Engineering Blog](https://github.blog/category/engineering/)

우리도 비슷한 상황이라면, 커넥션 풀 크기를 기본값(10~20)에서 트래픽에 맞춰 50~100까지 늘리고, 이벤트 처리에는 Spring의 `@Async` 혹은 메시지 큐를 적극 활용하는 게 좋습니다. 단, 커넥션 풀을 너무 크게 하면 DB가 감당 못 할 수 있으니 꼭 모니터링과 함께 조절해야 해요.

### 정리하며

- **비동기 요청 처리**로 스레드 블로킹 줄이기
- **Actuator + JVM 튜닝**으로 실시간 병목 파악과 GC 최적화
- **캐싱과 HTTP 캐시 헤더**로 DB 호출과 네트워크 부담 줄이기
- **Spring Security 설정**은 보안과 성능 균형 맞추기
- **대규모 트래픽 대응**에선 커넥션 풀과 비동기 이벤트 패턴 필수

이 중 한두 가지라도 적용해 보면 "왜 이제야 알았지?" 하는 경험을 하실 겁니다. 처음엔 설정 조절이 까다롭지만, 실제 운영 환경에서 성능과 보안을 동시에 잡으려면 이런 실전 팁들이 꼭 필요하니까요.
