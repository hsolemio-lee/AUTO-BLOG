## PyPI에서 AI 모델 라이브러리까지, 공급망 공격은 왜 이렇게 무서운가

얼마 전 PyPI에서 배포되는 LiteLLM 패키지가 공급망 공격에 노출됐다는 소식 들었나요? AI 모델을 백엔드에서 직접 호출하는 서비스라면, 단순히 라이브러리 버전 하나 바꾸는 일이 얼마나 큰 리스크가 될 수 있는지 체감했을 겁니다. 이번 공격은 악성코드가 포함된 패키지가 배포되어 민감한 정보가 외부로 유출되는 문제를 일으켰는데요, 단순한 의존성 업데이트가 아니라 서비스 전체 보안에 직결되는 사건이었죠.

실제로 AI 모델을 호출하는 백엔드 시스템은 API 응답 스키마, 지연시간, 비용 같은 계약 조건이 꽤 엄격하게 관리되는데, 이런 부분이 제대로 점검되지 않으면 예상치 못한 장애나 데이터 노출로 이어질 수 있습니다. [OpenAI API Documentation](https://platform.openai.com/docs/overview)에서도 모델 릴리즈 변경사항과 백엔드 계약을 함께 점검해야 안정적인 반영이 가능하다고 강조하고 있죠.

## LiteLLM 공급망 공격, 백엔드 관점에서 놓치기 쉬운 부분

이번 공격은 단순히 악성 패키지가 배포된 것 이상의 의미가 있습니다. AI 모델을 호출하는 백엔드 시스템은 보통 여러 외부 라이브러리에 의존하는데, 이 중 하나라도 악성코드가 포함되면 서비스 전체가 위험해집니다. 특히 LiteLLM 같은 AI 모델 라이브러리는 모델 추론 결과뿐 아니라, 내부 상태나 메모리까지 접근할 수 있어 민감한 데이터가 유출될 가능성이 큽니다.

처음엔 "내가 직접 코드를 작성하는 건 아니니까 괜찮겠지"라고 생각하기 쉽지만, 실제로는 의존성 패키지 내부에 숨겨진 악성 스크립트가 백엔드 환경에서 실행되어 중요한 API 키나 사용자 데이터가 외부로 전송될 수 있습니다.

이런 위험을 줄이려면, 단순히 패키지 버전 관리만이 아니라 공급망 공격에 대비한 추가적인 보안 계층이 필요합니다. 예를 들어, 모델 게이트웨이 계층에서 fallback 모델과 타임아웃 정책을 분리하면 장애 전파를 줄일 수 있다는 점도 참고할 만합니다. [Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)에서 설명하는 이 방법은 모델 호출 실패 시 백엔드가 무한 대기하거나 전체 서비스가 느려지는 걸 막아주죠.

## 백엔드에서 AI 모델 의존성을 안전하게 관리하는 현실적인 방법

1. **패키지 출처 검증과 해시 확인**

   PyPI에서 패키지를 설치할 때는 꼭 공식 출처인지 확인하고, 해시값을 검증하는 습관을 들여야 합니다. 예를 들어 `pip install` 시 `--require-hashes` 옵션을 사용하면, 사전에 등록된 해시값과 다운로드한 패키지의 해시를 비교해 변조 여부를 검사할 수 있습니다.

   ```bash
   pip install --require-hashes -r requirements.txt
   ```

   이 방법은 번거롭지만, 공급망 공격 위험을 크게 줄여줍니다.

2. **모델 호출 시 타임아웃과 폴백 분리**

   AI 모델 게이트웨이 레이어에서 타임아웃 정책과 폴백 모델을 분리해두면, 악성 코드나 장애가 발생해도 전체 서비스가 마비되는 걸 막을 수 있습니다. 예를 들어 아래처럼 Python `asyncio`를 활용해 타임아웃을 걸고, 실패 시 폴백 모델을 호출하는 구조를 만들 수 있죠.

   ```python
   import asyncio

   async def call_primary_model(input_data):
       # 실제 모델 호출 로직
       await asyncio.sleep(1)  # 예시
       return "primary result"

   async def call_fallback_model(input_data):
       # 폴백 모델 호출
       await asyncio.sleep(0.5)
       return "fallback result"

   async def get_model_result(input_data, timeout=2):
       try:
           return await asyncio.wait_for(call_primary_model(input_data), timeout)
       except asyncio.TimeoutError:
           return await call_fallback_model(input_data)

   # 사용 예
   result = asyncio.run(get_model_result("some input"))
   print(result)
   ```

   이렇게 하면 메인 모델 호출이 지연돼도 백엔드 전체가 멈추지 않고, 민감한 데이터 유출 가능성을 줄이면서 안정성을 높일 수 있습니다.

3. **의존성 업데이트 시 API 계약 점검 자동화**

   AI 모델 라이브러리 업데이트가 API 응답 스키마, 지연시간, 비용에 영향을 줄 수 있으니, CI/CD 파이프라인에 자동화된 계약 검증 테스트를 넣는 게 좋습니다. 예를 들어 OpenAI API처럼 명확한 스펙 문서가 있다면, 변경된 모델 버전이 기존 호출과 호환되는지, 응답 지연시간이 임계치를 넘지 않는지 자동으로 검증하는 스크립트를 돌릴 수 있죠.

   ```python
   import requests
   import time

   def test_model_response(api_url, payload, expected_schema):
       start = time.time()
       resp = requests.post(api_url, json=payload)
       duration = time.time() - start
       if duration > 1.0:  # 1초 이상 지연 시 경고
           print(f"경고: 응답 지연 시간 {duration:.2f}s")
       data = resp.json()
       # 간단한 스키마 체크
       for key in expected_schema:
           if key not in data:
               raise ValueError(f"응답에 {key} 누락")
       print("응답 스키마 정상")

   # 실제 테스트
   test_model_response("https://api.example.com/v2/model", {"input": "test"}, expected_schema=["result", "usage"])
   ```

   이런 자동화는 작은 변경에도 빠르게 대응할 수 있게 해줍니다.

## 공급망 공격 완전 차단은 어렵지만, 이렇게 하면 위험을 크게 줄일 수 있다

솔직히 말하면, 오픈 소스 생태계에서 공급망 공격을 100% 막기는 어렵습니다. 하지만 이번 LiteLLM 사건처럼 민감한 AI 모델 의존성을 백엔드에서 다룰 때는 다음 원칙들을 꼭 기억하세요.

- **출처 검증과 해시 체크는 기본 중 기본**
- **모델 게이트웨이에서 장애 전파 방지 설계**
- **API 계약과 지연시간을 CI/CD에 포함해 자동 점검**
- **의심스러운 패키지나 업데이트는 반드시 코드 리뷰와 테스트 거치기**

이건 실제로 겪어보면, "아 이게 별거 아닌 것 같지만 안 하면 사고 난다"는 걸 절감하게 됩니다. 특히 AI 모델 호출은 비용도 만만치 않으니, 장애나 악성 공격으로 인한 과금 폭탄도 조심해야 합니다.

---

이번 사건을 계기로 우리 팀도 PyPI 의존성 관리 정책을 강화하고, AI 모델 호출 로직에 타임아웃과 폴백 분리 전략을 적용해봤는데요. 덕분에 실제 장애 시에도 서비스가 안정적으로 유지되는 걸 확인했습니다. 여러분도 꼭 한번 점검해보시길 권합니다.
