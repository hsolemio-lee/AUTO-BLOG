# Spring Security로 프로덕션 보안을 제대로 세팅하려면?

최근에 "A Bootiful Podcast"에서 Spring Security 리드 개발자인 Rob Winch가 직접 보안 관련 질문에 답하는 내용을 들었는데, 평소 우리가 고민하는 보안 설정과 운영에 대한 실전 팁이 가득해서 공유하지 않을 수 없더라고요. 

내가 겪었던 보안 설정 문제, 성능 이슈, 유지보수 어려움 같은 고민들에 대해 Rob Winch는 어떻게 접근하는지, 그리고 실제 프로덕션 환경에서 어떤 패턴과 튜닝을 권장하는지 함께 살펴봅시다.

---

## "최소 권한 원칙"을 안 지키면 보안이 무너진다

내가 예전에 한 프로젝트에서 권한 관리를 너무 느슨하게 했다가, 한 번 내부 직원 계정이 과도한 권한을 갖고 있어서 큰 사고가 났던 적이 있어요. Rob Winch가 강조하는 첫 번째 보안 패턴도 바로 이 최소 권한 원칙(Least Privilege Principle)입니다. 

Spring Security 설정 시 사용자나 서비스가 꼭 필요한 권한만 갖도록 권한 범위를 좁히는 게 핵심인데, 이게 생각보다 쉽지 않죠. 특히 인증(Authentication)과 인가(Authorization)를 명확히 분리해서 관리해야 유지보수도 편해집니다. 

예를 들어, 인증은 `UserDetailsService`에서 처리하고 인가는 `@PreAuthorize` 같은 어노테이션이나 `AccessDecisionManager`를 통해 권한별로 세밀하게 나누는 식이죠.

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig extends WebSecurityConfigurerAdapter {

    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
            .authorizeRequests()
                .antMatchers("/admin/**").hasRole("ADMIN")
                .antMatchers("/user/**").hasAnyRole("USER", "ADMIN")
                .anyRequest().authenticated()
            .and()
            .formLogin();
    }

    @Bean
    public UserDetailsService userDetailsService() {
        UserDetails user = User.withDefaultPasswordEncoder()
            .username("user")
            .password("password")
            .roles("USER")
            .build();
        return new InMemoryUserDetailsManager(user);
    }
}
```

이렇게 하면 인증과 인가가 분리되고, 각 권한별 접근 범위를 명확히 관리할 수 있습니다. Rob Winch는 이 원칙이 보안의 기본 중 기본이라고 단언합니다[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

## 필터 체인, 꼭 필요한 것만 남겨야 성능 저하가 없다

Spring Security가 제공하는 필터 체인(Filter Chain)은 강력하지만, 무조건 다 켜놓으면 오히려 성능 저하가 심해질 수 있어요. Rob Winch는 프로덕션 환경에서 커스텀 필터 체인을 구성할 때 불필요한 필터를 과감히 제거하고, 필요한 필터만 명확히 등록하는 방식을 추천합니다.

내가 직접 겪어보니, 기본 필터를 다 켜놓으면 인증이나 권한 검사 시 불필요한 연산이 많아지고, 특히 대량 트래픽이 몰릴 때 병목이 생기더라고요. 

아래는 필터 체인을 커스터마이징하는 간단한 예시입니다.

```java
@Override
protected void configure(HttpSecurity http) throws Exception {
    http
        .addFilterBefore(customAuthenticationFilter(), UsernamePasswordAuthenticationFilter.class)
        .authorizeRequests()
            .anyRequest().authenticated();
}

@Bean
public CustomAuthenticationFilter customAuthenticationFilter() {
    return new CustomAuthenticationFilter();
}
```

필터 순서도 중요해서, 인증 필터는 `UsernamePasswordAuthenticationFilter` 전에 두고, 불필요한 필터는 아예 등록하지 않는 게 좋습니다. 이런 세밀한 튜닝이 없으면 오히려 보안은 물론 성능도 같이 떨어지니 조심해야 합니다[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

## 세션 관리, 세션 고갈 공격 대비는 필수

내가 운영하는 서비스에서 갑자기 세션이 다 소진돼서 신규 로그인이나 요청이 모두 실패했던 적이 있었는데, 알고 보니 세션 고갈 공격(Session Exhaustion Attack)이었어요. 

Rob Winch는 프로덕션 환경에서 세션 관리 설정을 꼭 조정하라고 권합니다. 세션 타임아웃을 짧게 설정하고, 동시 세션 수 제한을 두는 게 기본인데요, 이렇게 하면 공격자가 무한히 세션을 생성해 서버 자원을 고갈시키는 걸 방지할 수 있습니다.

```java
@Override
protected void configure(HttpSecurity http) throws Exception {
    http
        .sessionManagement()
            .maximumSessions(1)
            .maxSessionsPreventsLogin(true)
            .expiredUrl("/login?expired=true")
        .and()
        .sessionFixation().migrateSession()
        .invalidSessionUrl("/login?invalid-session=true");
}

// application.properties
server.servlet.session.timeout=15m
```

세션 타임아웃을 15분 정도로 짧게 잡는 게 보통 추천되는데, 너무 짧으면 사용자 경험이 나빠질 수 있으니 서비스 특성에 맞게 조절해야 합니다. 

이 세션 관리 설정만 잘해도 세션 고갈 공격은 물론이고, 세션 탈취 위험도 어느 정도 줄일 수 있습니다[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

## OAuth2와 JWT, 토큰 만료와 재발급 전략이 보안의 핵심

요즘은 JWT 토큰 기반 인증이 대세인데, Rob Winch는 토큰 유효 기간을 너무 길게 잡지 말라고 조언합니다. 토큰이 길게 유효하면 탈취 시 피해가 크기 때문이죠.

그래서 보통 액세스 토큰은 5~15분 정도로 짧게 설정하고, 리프레시 토큰(refresh token)을 통해 토큰을 재발급하는 패턴을 권장합니다. 

아래는 JWT 액세스 토큰과 리프레시 토큰을 함께 사용하는 간단한 예시입니다.

```java
// 액세스 토큰 생성
String accessToken = Jwts.builder()
    .setSubject(user.getUsername())
    .setExpiration(Date.from(Instant.now().plus(10, ChronoUnit.MINUTES)))
    .signWith(secretKey)
    .compact();

// 리프레시 토큰 생성
String refreshToken = Jwts.builder()
    .setSubject(user.getUsername())
    .setExpiration(Date.from(Instant.now().plus(7, ChronoUnit.DAYS)))
    .signWith(secretKey)
    .compact();
```

이렇게 하면 액세스 토큰이 만료돼도 리프레시 토큰으로 새 토큰을 받아 계속 인증할 수 있고, 리프레시 토큰도 탈취 위험이 있으니 저장 위치와 만료 시간을 신중히 관리해야 합니다. 

Rob Winch는 이런 토큰 전략이 OAuth2 인증 보안의 기본이라고 강조합니다[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

## CORS 정책은 보안과 사용자 경험 사이의 균형

크로스 사이트 요청 위조(CSRF) 공격을 막으려면 CORS 설정이 필수인데, Rob Winch는 불필요한 외부 도메인 접근을 차단하는 명확한 CORS 정책을 세우라고 합니다.

내가 직접 CORS 설정을 느슨하게 했다가, 예상치 못한 외부 도메인에서 API를 호출하는 사례가 있어서 곤란했던 적이 있거든요. 

```java
@Bean
public WebMvcConfigurer corsConfigurer() {
    return new WebMvcConfigurer() {
        @Override
        public void addCorsMappings(CorsRegistry registry) {
            registry.addMapping("/api/**")
                .allowedOrigins("https://mytrusteddomain.com")
                .allowedMethods("GET", "POST")
                .allowCredentials(true);
        }
    };
}
```

이렇게 특정 도메인만 허용하고, 허용 메서드도 제한하면 CSRF 공격 위험을 크게 줄일 수 있습니다. 물론, 너무 엄격하면 정당한 요청이 막힐 수 있으니 테스트를 충분히 해야 합니다[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

## 로그 레벨 조절, 보안 모니터링과 성능 사이에서 균형 잡기

마지막으로 Rob Winch가 강조하는 건 로그 관리입니다. 보안 이벤트를 꼼꼼히 모니터링하려면 로그 레벨을 DEBUG나 TRACE로 올리고 싶지만, 이러면 로그가 너무 많아져서 성능 저하가 발생할 수 있거든요.

그래서 프로덕션에선 INFO나 WARN 수준으로 기본 로그를 유지하면서, 문제 발생 시에만 DEBUG 모드로 전환하는 방식을 추천합니다.

```properties
logging.level.org.springframework.security=INFO
logging.level.com.myapp.security=DEBUG
```

이렇게 하면 보안 관련 핵심 로그는 남기면서도, 필요할 때 디버깅 정보를 빠르게 켤 수 있어요. 

내 경험상 로그 과다로 CPU와 디스크 I/O가 병목이 되는 경우가 꽤 많았는데, 이 조절 하나로 문제를 해결한 적이 여러 번 있습니다[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

내가 가장 크게 느낀 점은 다음과 같습니다:

- 최소 권한 원칙과 인증/인가 분리는 보안의 기본이자 유지보수의 핵심
- 필터 체인은 꼭 필요한 것만 남겨서 성능 저하를 막아야 한다
- 세션 관리를 통해 세션 고갈 공격을 방어하고, 타임아웃을 짧게 유지하자
- JWT와 OAuth2는 토큰 만료와 재발급 전략으로 보안을 강화하자
- CORS 정책은 외부 접근을 엄격하게 제한해 CSRF 공격을 예방한다
- 로그 레벨은 보안 모니터링과 성능 사이에서 적절히 조절해야 한다

이 팁들을 내 프로젝트에 적용하면서 보안 사고도 줄고, 운영 부담도 확실히 줄었어요. 여러분도 꼭 한 번 점검해 보시길 추천합니다!
