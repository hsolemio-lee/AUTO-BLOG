## "우리 데이터가 AI를 제대로 뒷받침할 수 있을까?"

얼마 전 우리 팀에서 agentic AI 프로젝트를 시작하면서 가장 먼저 부딪힌 질문이었어요. "기존 데이터 파이프라인과 저장소가 AI의 자율적 의사결정을 지원하기에 충분한가?" 처음엔 단순히 AI 모델만 잘 돌리면 된다고 생각했는데, 막상 실무에 들어가니 데이터 준비가 훨씬 더 중요하다는 걸 깨달았죠.

이번 글에서는 agentic AI 워크로드를 지원하기 위해 데이터 아키텍처를 어떻게 재설계하고, 어떤 점을 주의해야 하는지, 그리고 기존 시스템에서 어떻게 단계적으로 전환할 수 있는지 경험을 담아 얘기해보려 합니다.

---

## 실시간 데이터 처리 없이는 agentic AI가 힘들다

agentic AI는 단순히 명령을 받아 처리하는 게 아니라, 스스로 상황을 판단하고 여러 단계를 거쳐 의사결정을 내리는 특성이 있어요. 따라서 데이터 파이프라인도 실시간으로 데이터를 수집하고 처리할 수 있어야 하죠. 기존 배치(batch) 처리 중심의 시스템으로는 AI가 최신 상황을 반영하기 어렵습니다.

우리 팀은 이 부분을 해결하기 위해 이벤트 기반 아키텍처와 스트림 처리 시스템을 도입했습니다. 예를 들어 Kafka 같은 메시지 큐를 활용해 실시간 이벤트를 수집하고, Apache Flink로 스트림 데이터를 처리하는 구조로 바꿨죠. 이 덕분에 AI가 즉각적으로 최신 데이터를 참고해 의사결정을 내릴 수 있게 됐습니다.

```java
// Spring Boot에서 Kafka 컨슈머 설정 예시
@Configuration
public class KafkaConsumerConfig {

    @Bean
    public ConsumerFactory<String, String> consumerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ConsumerConfig.GROUP_ID_CONFIG, "agentic-ai-group");
        props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
        props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
        return new DefaultKafkaConsumerFactory<>(props);
    }

    @Bean
    public ConcurrentKafkaListenerContainerFactory<String, String> kafkaListenerContainerFactory() {
        ConcurrentKafkaListenerContainerFactory<String, String> factory = new ConcurrentKafkaListenerContainerFactory<>();
        factory.setConsumerFactory(consumerFactory());
        return factory;
    }
}

// 실시간 이벤트 수신
@KafkaListener(topics = "agentic-events", groupId = "agentic-ai-group")
public void listen(String message) {
    // 메시지 처리 로직
    System.out.println("Received event: " + message);
}
```

이렇게 실시간 데이터가 빠르게 AI로 흘러들어가야 agentic AI가 제대로 힘을 발휘할 수 있습니다.[OpenAI API Documentation](https://platform.openai.com/docs/overview)

## 비정형 데이터와 메타데이터, 어떻게 저장할까?

agentic AI는 텍스트, 이미지, 로그 등 다양한 비정형 데이터를 다루고, 각 데이터에 대한 메타데이터도 중요하게 활용합니다. 따라서 단순한 RDBMS로는 한계가 있고, 분산형 데이터베이스와 벡터 검색 인덱스를 적극 활용하는 게 필수입니다.

우리 팀은 MongoDB 같은 분산형 NoSQL 데이터베이스를 기본 저장소로 쓰면서, 벡터 검색을 위해 Pinecone이나 Weaviate 같은 벡터 DB를 도입했어요. 이렇게 하면 AI가 의미 기반 검색을 빠르게 수행할 수 있죠.

특히 벡터 검색 인덱스는 대규모 비정형 데이터에서 유사도를 계산해 필요한 정보를 빠르게 찾아내는 데 필수적입니다. 단순 키-밸류 조회와 달리, 문맥을 이해하는 AI에겐 없어선 안 될 기능이죠.

```json
{
  "id": "doc123",
  "content": "Agentic AI를 위한 데이터 준비 가이드",
  "embedding": [0.12, 0.98, ...],
  "metadata": {
    "source": "internal-docs",
    "created_at": "2024-05-01T10:00:00Z"
  }
}
```

이런 식으로 문서와 함께 임베딩 벡터, 메타데이터를 저장해두고, AI가 필요할 때 유사 문서를 빠르게 찾아서 참고할 수 있게 합니다.[Cursor Documentation](https://docs.cursor.com/)

## 프롬프트 엔지니어링과 데이터 준비는 동전의 양면

프롬프트 엔지니어링은 AI가 더 정확하고 유용한 응답을 내도록 하는 기술인데, 이게 데이터 준비와 얼마나 밀접한지 아는 사람은 많지 않아요. 구조화된 데이터와 적절한 컨텍스트가 없으면 아무리 좋은 프롬프트도 소용없거든요.

우리 팀에서는 AI에게 넘기는 데이터에 메타데이터, 타임스탬프, 관련 문서 링크 등을 함께 포함시켜 프롬프트를 구성했습니다. 예를 들어, 고객 문의에 AI가 답변할 때 단순 질문뿐 아니라, 고객의 최근 구매 내역, 이전 대화 기록 등을 함께 넣어주죠.

```python
prompt = f"""
고객 이름: {customer_name}
최근 구매: {recent_purchase}
문의 내용: {customer_question}

위 정보를 참고해서 친절하고 정확하게 답변해줘.
"""
response = ai_model.generate(prompt)
```

이렇게 하면 AI가 상황을 더 잘 이해해서 응답 품질이 확실히 올라갑니다. 프롬프트 설계는 데이터 준비와 함께 가야 하는 작업이라는 점, 꼭 기억하세요.[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)

## 기존 Spring 백엔드에 agentic AI 통합, 어떻게 접근할까?

많은 팀이 기존에 Spring 기반 백엔드를 운영 중일 텐데, 여기에 agentic AI를 붙이려면 어떻게 해야 할까요? 우리 경험으로는 API 중심의 모듈화된 아키텍처가 답입니다.

AI 서비스와 기존 비즈니스 로직을 명확히 분리하고, AI 호출은 별도의 서비스 레이어에서 담당하게 했어요. 이렇게 하면 AI 모델 교체나 확장도 훨씬 수월해지고, 장애 발생 시 영향 범위도 줄일 수 있습니다.

또한 데이터 파이프라인 각 단계별로 로깅과 모니터링을 강화해, AI 입력 데이터의 품질과 처리 상태를 실시간으로 점검할 수 있게 했습니다. 이게 없으면 AI가 엉뚱한 결과를 내도 원인을 찾기 힘들어요.

```java
@RestController
@RequestMapping("/api/agentic-ai")
public class AgenticAIController {

    private final AIService aiService;

    public AgenticAIController(AIService aiService) {
        this.aiService = aiService;
    }

    @PostMapping("/process")
    public ResponseEntity<String> processRequest(@RequestBody AIRequest request) {
        // 요청 로깅
        log.info("Received AI request: {}", request);

        String result = aiService.handleRequest(request);

        // 응답 로깅
        log.info("AI response: {}", result);

        return ResponseEntity.ok(result);
    }
}
```

이처럼 단계별 로깅과 모듈화를 통해 AI 통합의 안정성과 확장성을 확보할 수 있습니다.[GitHub Copilot Documentation](https://docs.github.com/en/copilot)

## 클라우드 AI SDK 활용으로 배포와 스케일링 복잡도 줄이기

우리 팀은 Vercel AI SDK 같은 클라우드 AI SDK를 적극 활용했는데, 덕분에 AI 모델과 데이터 파이프라인 통합이 훨씬 간단해졌어요. SDK가 기본적인 인증, 요청/응답 처리, 에러 핸들링을 다 해주니까 개발자가 AI 로직에 집중할 수 있죠.

또한 클라우드 환경에서 자동 스케일링과 로드 밸런싱도 지원해, 트래픽 급증 시에도 안정적인 서비스를 유지할 수 있었습니다.

```javascript
import { VercelAI } from '@vercel/ai';

const ai = new VercelAI({ apiKey: process.env.VERCEL_AI_API_KEY });

async function getAgenticResponse(prompt) {
  const response = await ai.chat.completions.create({
    model: 'gpt-4o-mini',
    messages: [{ role: 'user', content: prompt }],
  });
  return response.choices[0].message.content;
}
```

이런 SDK 활용은 초기 구축 부담을 줄이고, 빠른 프로토타입과 안정적 운영을 가능하게 합니다.[Vercel AI SDK Documentation](https://sdk.vercel.ai/docs/introduction)

## 기존 배치 처리에서 실시간 피드백 루프로, 단계적 마이그레이션 전략

한꺼번에 모든 시스템을 바꾸는 건 현실적으로 어렵죠. 우리 팀은 기존 배치 처리 시스템에서 스트림 처리와 실시간 피드백 루프로 점진적으로 전환하는 전략을 썼습니다.

1. 기존 ETL 파이프라인에 스트림 처리 모듈을 추가해 실시간 데이터 일부를 먼저 처리
2. AI가 실시간 데이터를 참고하도록 API를 확장
3. 점차 배치 처리 비중을 줄이고, 실시간 처리 비중을 늘림

이 과정에서 데이터 신선도를 높이면서도 시스템 안정성을 유지할 수 있었어요. 물론 초기에는 데이터 일관성 문제, 모니터링 복잡도 증가 같은 어려움이 있었지만, 단계별 검증과 모니터링 강화로 극복했습니다.[Cursor Documentation](https://docs.cursor.com/)

## 마치며: 데이터 준비가 agentic AI 성공의 열쇠

처음엔 agentic AI 하면 모델만 잘 다루면 된다고 생각했는데, 데이터 파이프라인과 저장소 준비가 훨씬 더 중요하다는 걸 직접 경험했습니다. 실시간 데이터 수집, 분산 저장, 벡터 검색, 프롬프트와 데이터의 긴밀한 연계, 그리고 기존 시스템과의 모듈화된 통합까지. 이 모든 게 맞물려야 AI가 제대로 작동하더라고요.

실제 업무에 적용할 때는 단계별 마이그레이션과 모니터링 체계 구축을 꼭 병행하시길 추천합니다. 그래야 안정성과 신뢰성을 확보할 수 있으니까요.

여러분도 agentic AI 프로젝트를 준비 중이라면, 데이터 아키텍처부터 차근차근 준비해보세요. AI가 더 똑똑해지는 만큼, 우리의 데이터도 더 똑똑해져야 하니까요.
