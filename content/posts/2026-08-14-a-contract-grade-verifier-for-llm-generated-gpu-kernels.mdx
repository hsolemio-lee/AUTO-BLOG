### "이 커널, 진짜 제대로 동작할까?"

최근 AI 백엔드에서 LLM을 활용해 GPU 커널 코드를 자동 생성하는 사례가 늘고 있습니다. 그런데 자동 생성된 코드가 실제 환경에서 오류 없이 신뢰할 수 있을까요? GPU 커널은 성능과 정확성이 생명인데, 작은 버그 하나가 전체 AI 파이프라인을 망칠 수 있죠. 그래서 저는 LLM이 생성한 GPU 커널을 계약 기반(contract-grade)으로 검증하는 방법을 직접 구현해봤습니다. 이 경험을 공유하며, 왜 계약 기반 검증이 필수인지, 어떻게 설계하고 적용했는지 이야기해보려 합니다.

---

## LLM 코드 생성과 계약 기반 검증, 왜 같이 가야 할까?

LLM이 GPU 커널 코드를 생성할 때 가장 큰 문제는 "출력 코드가 내가 원하는 명확한 규격을 따르는가?"입니다. OpenAI API 문서에서도 API 입력과 출력에 대한 명확한 계약(contract)을 정의하는 게 신뢰성을 높이는 핵심이라고 강조하죠[OpenAI API Documentation](https://platform.openai.com/docs/overview). 

GPU 커널은 병렬 처리 특성상 디버깅이 어렵고, 작은 논리 오류가 치명적입니다. Anthropic의 프롬프트 엔지니어링 가이드에서도 LLM에게 명확한 계약 조건을 프롬프트에 포함시켜 예상 동작을 엄격하게 제한하는 방법을 소개합니다. 이게 바로 계약 기반 검증의 출발점입니다[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

즉, 우리가 할 일은 "LLM에게 계약을 명확히 알려주고, 생성된 커널이 계약을 만족하는지 검증하는 것"입니다. 이걸 안 하면, GPU 커널이 잘못 생성되어도 모른 채 배포하는 위험이 큽니다.

## 계약 기반 설계 원칙을 GPU 커널 검증에 녹여내기

Martin Fowler의 아키텍처 가이드에 따르면 계약 기반 설계는 복잡한 컴포넌트 간 신뢰성을 확보하는 데 필수입니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/). GPU 커널도 마찬가지로, LLM이 생성한 커널이 기대하는 입력, 출력, 부작용을 계약으로 명확히 정의해야 합니다.

예를 들어, 다음과 같은 계약 조건을 생각할 수 있습니다:

- 입력 배열 크기는 1024 이상이어야 한다.
- 출력 배열은 입력 배열과 동일한 크기를 가진다.
- 커널 실행 후 출력 배열 값은 입력 배열 값의 제곱이다.
- 실행 시간은 10ms를 넘지 않는다.

이런 조건을 코드로 검증할 수 있다면, "이 커널은 계약을 충족한다"는 신뢰를 가질 수 있습니다.

## 실전: LLM 생성 CUDA 커널에 계약 기반 검증 적용해보기

제가 직접 구현한 예시 코드를 공유할게요. 간단한 벡터 제곱 GPU 커널을 LLM에게 생성 요청하고, 계약을 검증하는 테스트 코드를 작성했습니다.

```cpp
// LLM이 생성한 GPU 커널 예시 (CUDA)
__global__ void vector_square(const float* input, float* output, int n) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < n) {
        output[idx] = input[idx] * input[idx];
    }
}

// 계약 검증 함수
bool verify_contract(const float* input, const float* output, int n) {
    for (int i = 0; i < n; i++) {
        float expected = input[i] * input[i];
        if (fabs(output[i] - expected) > 1e-5) {
            printf("계약 위반: output[%d] = %f, expected = %f\n", i, output[i], expected);
            return false;
        }
    }
    return true;
}

// 테스트 실행 코드
void test_kernel() {
    const int N = 1024;
    float *d_input, *d_output;
    float h_input[N], h_output[N];

    // 입력 초기화
    for (int i = 0; i < N; i++) h_input[i] = float(i);

    cudaMalloc(&d_input, N * sizeof(float));
    cudaMalloc(&d_output, N * sizeof(float));
    cudaMemcpy(d_input, h_input, N * sizeof(float), cudaMemcpyHostToDevice);

    vector_square<<<(N + 255) / 256, 256>>>(d_input, d_output, N);
    cudaMemcpy(h_output, d_output, N * sizeof(float), cudaMemcpyDeviceToHost);

    if (verify_contract(h_input, h_output, N)) {
        printf("계약 검증 성공: GPU 커널 정상 동작 확인\n");
    } else {
        printf("계약 검증 실패: GPU 커널 오류 발견\n");
    }

    cudaFree(d_input);
    cudaFree(d_output);
}
```

이 코드는 LLM이 생성한 커널을 실제로 실행한 후, 출력이 계약 조건(입력값 제곱)과 일치하는지 하나하나 확인합니다. 처음엔 "이게 별거 아닌 것 같은데?" 싶지만, 실무에서 보면 GPU 커널 오류 찾기가 얼마나 까다로운지 알기에 이런 자동화된 계약 검증이 얼마나 중요한지 체감하게 됩니다.

## LLM 프롬프트에 계약 조건을 명확히 넣는 게 시작점

코드를 검증하는 것도 중요하지만, 계약은 LLM에게 처음부터 명확히 알려줘야 합니다. Anthropic 가이드에 따르면, 프롬프트에 "입력 배열 크기는 1024 이상이고, 출력 배열은 입력 배열의 각 원소 제곱이어야 한다" 같은 조건을 명시하는 게 신뢰성 향상에 큰 도움이 됩니다[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

예를 들어, 프롬프트를 이렇게 짜봤습니다:

```
"CUDA 커널 코드를 작성해 주세요. 이 커널은 float 배열을 입력받아 각 원소를 제곱하여 같은 크기의 출력 배열에 저장해야 합니다. 배열 크기는 1024 이상이며, 경계 조건을 반드시 처리해야 합니다."
```

이렇게 계약을 명확히 하면, LLM이 더 정확한 코드를 생성할 확률이 높아지고, 검증 코드도 훨씬 단순해집니다.

## 자동화 도구와 정적 분석도 계약 검증의 동반자

GitHub Engineering Blog에서도 대규모 코드 베이스에서 계약 기반 테스트와 정적 분석 도구를 함께 쓰는 사례가 많습니다[GitHub Engineering Blog](https://github.blog/category/engineering/). GPU 커널도 마찬가지로, 런타임 검증뿐 아니라 정적 분석으로 메모리 접근 오류, 경계 조건 위반 등을 사전에 잡아내면 안정성이 크게 올라갑니다.

예를 들어, CUDA 정적 분석 도구인 `cuda-memcheck`를 CI 파이프라인에 넣어 자동으로 메모리 오류를 검출하고, 계약 검증 테스트를 통과해야만 배포하도록 하는 식입니다. 이렇게 하면 LLM이 만든 코드라도 인간이 작성한 코드 수준의 신뢰성을 확보할 수 있습니다.

## 계약 기반 검증, 완벽하진 않지만 AI 백엔드에서 필수인 이유

물론 계약 기반 검증도 만능은 아닙니다. 계약 조건을 잘못 정의하면 오히려 잘못된 코드가 통과할 수 있고, 복잡한 GPU 커널은 모든 경계 케이스를 계약에 넣기 어렵습니다. 하지만 LLM이 생성한 코드의 불확실성을 줄이기 위해선 필수적인 안전망입니다.

처음 도입할 때는 계약 조건을 하나씩 늘려가며 검증 범위를 넓히고, LLM 프롬프트도 계속 다듬어야 합니다. 이 과정에서 GPU 커널의 특성, AI 백엔드 워크플로우의 요구사항을 깊이 이해하게 되는 부수 효과도 있죠.

### 마무리하며

LLM이 GPU 커널 코드를 생성하는 시대, "그냥 돌려보자"는 접근은 너무 위험합니다. OpenAI와 Anthropic이 강조하는 명확한 계약 정의와 검증 원칙을 실무에 적용해보세요. 단순한 출력 검증부터 시작해, 점차 정적 분석과 CI 통합까지 확장하면 AI 백엔드의 신뢰성을 한층 끌어올릴 수 있습니다.

계약 기반 검증은 처음엔 귀찮고 복잡하지만, GPU 커널 같은 민감한 코드에선 절대 빼놓을 수 없는 안전 장치입니다. 제가 직접 경험한 시행착오와 팁들이 여러분 팀에도 도움이 되길 바랍니다.
