## "왜 우리 AI 서비스는 가끔 갑자기 느려질까?"

최근에 LLM 기반 AI 서비스를 운영하면서 가장 골치 아팠던 문제가 바로 ‘tail latency’였어요. 평균 응답 속도는 괜찮은데, 가끔씩 95백분위수(p95)나 99백분위수(p99) 지연 시간이 훅 뛰는 거죠. 이게 특히 사용자 경험에 악영향을 주더라고요. 한두 번은 괜찮지만, 반복되면 신뢰도가 확 떨어지고요.

이 문제를 겪으면서 백엔드 쪽에서 어떻게 하면 tail latency를 줄일 수 있을지 여러 방법을 시도해봤는데, 오늘은 그중에서도 실제로 효과를 본 간단한 해결책을 공유해보려 합니다.


## LLM tail latency가 왜 이렇게 심각한 문제인지

LLM은 워낙 무거운 모델이고, API 호출 시에도 내부적으로 큐잉과 속도 제한(rate limiting)이 걸려 있어요. 예를 들어 OpenAI API는 초당 요청 수 제한과 큐잉 메커니즘을 통해 서버 부하를 관리하는데, 이 과정에서 요청이 밀리면 tail latency가 급격히 늘어납니다. 

평균 응답 시간이 500ms라 해도 p99가 3초 이상 튀면, 사용자 입장에서는 서비스가 불안정하다고 느낄 수밖에 없죠. 이런 현상은 특히 동시 요청이 몰릴 때 심해집니다.

그래서 단순히 평균 지연 시간만 줄이는 게 아니라, tail latency를 관리하는 게 더 중요해요. GitHub 엔지니어링 블로그에서도 LLM tail latency 완화를 위해 요청 큐잉과 비동기 처리, 우선순위 조정이 핵심이라고 강조합니다[GitHub Engineering Blog](https://github.blog/category/engineering/).


## 백엔드에서 요청 큐잉과 비동기 처리로 latency를 잡는 법

우리 팀에서는 다음과 같은 구조를 도입했어요.

1. **요청 큐잉**: 들어오는 LLM 요청을 바로 API로 보내지 않고, 내부 큐에 넣어 순차적으로 처리합니다.
2. **비동기 처리**: 요청을 비동기로 처리해서, 사용자에게는 빠른 응답(예: 작업 접수 완료)을 먼저 주고, 실제 LLM 응답은 나중에 받아서 전달합니다.
3. **우선순위 조정**: 긴급한 요청과 그렇지 않은 요청을 구분해, 중요한 요청을 먼저 처리합니다.

이렇게 하면 갑자기 요청이 몰려도 큐가 버퍼 역할을 하면서 서버 과부하를 막고, tail latency가 급격히 튀는 걸 완화할 수 있어요.

아래는 간단한 Node.js 예시 코드입니다. `bull` 라이브러리로 Redis 기반 큐를 만들고, 우선순위에 따라 작업을 처리하는 구조입니다.

```javascript
const Queue = require('bull');

// LLM 요청 큐 생성, 우선순위 지원
const llmQueue = new Queue('llm-requests', {
  redis: { host: '127.0.0.1', port: 6379 },
  defaultJobOptions: { removeOnComplete: true, removeOnFail: true }
});

// 요청을 큐에 넣는 함수
async function enqueueLLMRequest(requestPayload, priority = 5) {
  // priority: 1(가장 높음) ~ 10(가장 낮음)
  await llmQueue.add(requestPayload, { priority });
  return { status: 'queued' };
}

// 큐 작업 처리
llmQueue.process(async (job) => {
  // 여기에 OpenAI API 호출 로직 넣기
  // 예: const response = await callOpenAI(job.data);
  // 반환값을 DB나 캐시 등에 저장
  console.log(`Processing job ${job.id} with priority ${job.opts.priority}`);
  // ...
});

module.exports = { enqueueLLMRequest };
```

이런 식으로 큐잉과 비동기 처리를 결합하면, API 호출 속도 제한이나 서버 부하에 따른 지연을 내부적으로 흡수할 수 있습니다.


## 엣지 컴퓨팅과 캐싱으로 네트워크 지연도 잡아보자

LLM 자체 처리 시간이 길어지는 것도 문제지만, 네트워크 지연도 무시 못 합니다. Cloudflare는 AI 서비스에 엣지 컴퓨팅과 캐싱을 적극 도입해서 네트워크 왕복 시간을 줄이고 서버 부하를 낮췄다고 해요[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

예를 들어, 자주 묻는 질문이나 반복되는 쿼리에 대해선 엣지에서 미리 캐싱해두고, LLM 호출 없이도 빠르게 응답하는 전략입니다. 물론 캐싱이 불가능한 동적 쿼리는 큐잉과 비동기 처리로 커버하는 식이죠.

우리도 일부 정형화된 쿼리에 대해선 Redis 캐시를 적극 활용하고, 엣지 CDN을 통해 응답 속도를 개선했습니다. 덕분에 네트워크 지연으로 인한 tail latency가 눈에 띄게 줄었어요.


## 아키텍처 관점에서 tail latency를 줄이는 설계법

마틴 파울러는 비동기 이벤트 드리븐 아키텍처와 마이크로서비스 분리를 통해 LLM 서비스의 tail latency를 효과적으로 관리할 수 있다고 제안합니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

실제로 우리도 LLM 요청 처리 로직을 별도의 서비스로 분리하고, 내부 이벤트 버스를 통해 비동기 통신하도록 바꿨습니다. 이렇게 하면 한 서비스가 느려져도 전체 시스템 지연으로 이어지는 걸 막을 수 있죠.

또한, Anthropic의 프롬프트 엔지니어링 가이드에서는 모델 호출을 최적화하고 요청을 분할해 백엔드 부담을 줄이는 방법도 소개합니다[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview). 예를 들어, 복잡한 요청을 여러 작은 요청으로 나누거나, 불필요한 토큰 생성을 줄여서 API 호출 비용과 응답 시간을 절감하는 거죠.


## 직접 써보니 알게 된 현실적인 한계와 주의점

- **큐가 너무 길어지면 오히려 지연 증가**: 큐잉은 지연 완화에 도움되지만, 큐가 과도하게 길어지면 사용자 대기 시간이 늘어납니다. 적절한 큐 길이 모니터링과 알림 설정이 필수입니다.

- **우선순위 남용 주의**: 우선순위가 너무 많거나 복잡하면 관리가 어려워지고, 낮은 우선순위 요청은 무한 대기할 수 있습니다. 적절한 선에서 제한해야 합니다.

- **캐싱은 항상 최신성 트레이드오프가 있다**: 캐시된 데이터가 오래되면 사용자 경험이 떨어질 수 있어, TTL 설정과 캐시 무효화 전략이 중요합니다.

- **비동기 처리 후 결과 전달 방식 고민 필요**: 사용자에게 비동기 처리 상태를 어떻게 알려줄지, 실패 시 재시도와 알림 정책도 설계해야 합니다.


## 마무리하며: "내 서비스에 맞는 tail latency 개선법 찾기"

LLM tail latency는 단순히 모델 성능 문제만이 아니라, 백엔드 아키텍처와 운영 전략이 크게 좌우합니다. 요청 큐잉과 비동기 처리, 우선순위 조정, 엣지 캐싱, 그리고 아키텍처 분리를 적절히 조합하면 체감 성능을 크게 개선할 수 있어요.

처음엔 큐잉이나 비동기 처리가 별거 아닌 것 같아도, 실제로 현업에서 겪어보면 큰 차이를 느낍니다. 다만, 무작정 적용하기보단 우리 서비스 특성과 트래픽 패턴에 맞춰 튜닝하는 게 중요합니다.

오늘 공유한 내용이 LLM 기반 AI 서비스의 tail latency 때문에 고민하는 분들께 실질적인 도움이 되길 바랍니다.
