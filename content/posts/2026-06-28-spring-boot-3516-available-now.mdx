## 갑자기 서비스가 느려졌다면? Spring Boot 3.5.16 성능 튜닝부터 시작해보자

지난주에 우리 서비스가 갑자기 시작 시간이 길어지고 메모리 사용량도 늘어난 걸 발견했어요. 원인을 찾아보니 Spring Boot 버전을 3.5.16으로 올리면서 기본 설정이 바뀐 부분이 있더라고요. 이 버전은 프로덕션 환경에서 안정성을 높이기 위해 시작 시간 최적화와 메모리 사용 최소화에 꽤 신경 쓴 업데이트가 포함되어 있거든요.

예를 들어, `spring.main.lazy-initialization=true` 옵션을 적용하면 애플리케이션 컨텍스트 초기화 시점에 빈을 지연 생성해 시작 시간을 20~30% 줄일 수 있습니다. 물론 빈 생성이 늦어지면서 첫 요청 지연이 발생할 수 있으니 트래픽 패턴에 맞게 조절해야 해요.

```yaml
spring:
  main:
    lazy-initialization: true
  jpa:
    properties:
      hibernate:
        generate_statistics: false
```

이외에도 JVM 튜닝이 핵심인데, Baeldung에서 추천하는 `-XX:+UseG1GC -Xms512m -Xmx2g` 같은 설정을 3.5.16 환경에 맞게 적용하면 GC로 인한 지연을 줄일 수 있어요. 캐시 활용과 비동기 처리도 빼놓을 수 없죠. 예를 들어, `@Async`를 적절히 써서 DB 호출을 병렬화하면 응답 속도가 눈에 띄게 개선됩니다.

## OAuth 2.0과 JWT 처리, 보안이 한층 더 단단해졌다

보안 이슈는 늘 민감하죠. Spring Boot 3.5.16은 최신 보안 패치 적용뿐 아니라 OAuth 2.0과 JWT 토큰 처리 기능을 강화해서 인증·인가 체계를 더 안전하게 만들 수 있어요. 특히 JWT 토큰 서명 검증 로직이 개선되어 토큰 위변조 공격에 대한 내성이 높아졌습니다.

실제 코드로 보면, `NimbusJwtDecoder`를 커스터마이징해서 토큰 검증 과정을 세밀하게 제어할 수 있는데요:

```java
@Bean
public JwtDecoder jwtDecoder() {
    NimbusJwtDecoder jwtDecoder = NimbusJwtDecoder.withJwkSetUri(jwkSetUri).build();
    jwtDecoder.setJwtValidator(JwtValidators.createDefaultWithIssuer(issuerUri));
    return jwtDecoder;
}
```

이렇게 하면 발급자 검증과 토큰 구조 검증을 모두 거치면서 보안 수준을 올릴 수 있죠. 그리고 OAuth 2.0 클라이언트 설정도 더 유연해져서 다양한 인증 서버와 쉽게 연동할 수 있습니다.

## 무중단 배포? Spring Boot 3.5.16에서 어떻게 달라졌나

서비스를 운영하다 보면 다운타임 없이 새 버전을 배포하는 게 얼마나 중요한지 절실히 느끼죠. Spring Boot 3.5.16은 점진적 배포와 무중단 배포를 지원하는 기능을 강화했어요. 기본적으로 Actuator와 Health 체크를 활용해 롤백 조건을 자동으로 감지할 수 있고, Kubernetes 같은 환경에서 Readiness Probe와 Liveness Probe 설정을 최적화하기 쉬워졌습니다.

예를 들어, `management.endpoint.health.probes.enabled=true` 옵션을 켜면 배포 스크립트가 상태를 더 세밀하게 체크해서 트래픽 전환 시점을 정확히 판단할 수 있어요.

```yaml
management:
  endpoint:
    health:
      probes:
        enabled: true
```

이걸 CI/CD 파이프라인에 연동하면, 배포 중 문제가 생겨도 자동으로 이전 버전으로 롤백하는 전략을 쉽게 구현할 수 있습니다. 물론 이런 무중단 배포가 완벽한 건 아니고, 상태 저장 세션이나 DB 마이그레이션 같은 부분은 별도로 신경 써야 한다는 점은 잊지 마세요.

## Spring Framework 6.x 기반의 변화, 리액티브 프로그래밍과 모듈화

Spring Boot 3.5.16은 Spring Framework 6.x를 기반으로 만들어졌는데, 이게 생각보다 큰 변화를 가져왔어요. 코어 기술 측면에서 모듈화가 더 잘 되어 있고 의존성 주입도 개선돼서 복잡한 애플리케이션 구조를 깔끔하게 관리하기 좋아졌습니다.

또 하나 눈에 띄는 건 리액티브 프로그래밍 지원 강화인데요. WebFlux를 비롯한 리액티브 스택이 더 안정적이고 성능도 좋아졌어요. 만약 고성능 비동기 API 서버를 만들 계획이라면 3.5.16 버전에서 리액티브 스택을 적극 활용해보는 걸 추천합니다.

```java
@GetMapping("/events")
public Flux<Event> streamEvents() {
    return eventService.getEventStream();
}
```

이렇게 `Flux`를 반환하면 서버가 클라이언트에 실시간으로 데이터를 흘려보낼 수 있죠. 물론 리액티브 프로그래밍은 학습 곡선이 있으니 팀 상황에 맞게 도입 여부를 결정하는 게 좋습니다.

### 마무리하며

Spring Boot 3.5.16은 단순히 버전 업에 그치지 않고, 프로덕션 환경에서 실제 도움이 되는 성능 튜닝 옵션, 보안 강화, 그리고 무중단 배포 지원을 꽉 채워서 나왔다는 점이 인상적입니다. JVM 튜닝과 캐시 활용, OAuth 2.0과 JWT 처리, 그리고 최신 Spring Framework 6.x 기반 기술까지 살펴보면, 이 버전으로의 전환은 충분히 가치가 있죠.

다만, 모든 최적화가 그렇듯 환경에 맞게 세밀하게 조정하는 게 중요합니다. 시작 시간 단축을 위해 무작정 `lazy-initialization`을 켰다가 첫 요청 지연 문제에 부딪힐 수 있고, 무중단 배포도 DB 스키마 변경이 있으면 별도 전략이 필요하니까요.

저라면 이번 주말에 사내 테스트 환경에서 3.5.16으로 올리고 JVM 옵션과 보안 설정을 하나씩 점검해보는 걸 추천합니다. 그리고 실제 트래픽 환경에서 모니터링하면서 점진적으로 배포하는 게 가장 안전한 방법이겠죠.

혹시 여러분도 3.5.16으로 마이그레이션하면서 겪은 에피소드나 팁 있으면 댓글로 공유해 주세요. 같이 고민하고 배우면 더 빠르게 성장할 수 있으니까요!
