## "Ingress가 너무 복잡한데, Gateway API로 바꾸면 정말 나아질까?"

요즘 클라우드 네이티브 환경에서 서비스 인그레스 설정이 점점 복잡해지면서, 기존 Kubernetes Ingress 리소스가 한계에 부딪힌 팀들이 많아요. 저도 최근에 Gateway API를 도입하면서 느낀 건데, 단순히 새로운 API를 쓴다는 것 이상의 변화가 있더라고요. 

기존 Ingress는 단일 리소스로 라우팅과 TLS 설정, 인증 등을 한꺼번에 처리하다 보니, 복잡한 정책이나 멀티 테넌시 요구사항을 반영하기 어렵고 확장성도 제한적이었죠. 반면 Gateway API는 Gateway, Route, Listener 같은 리소스를 분리해서 각자의 역할에 집중할 수 있게 설계됐어요. 덕분에 훨씬 세밀한 트래픽 제어와 보안 정책 적용이 가능해졌습니다.


## Gateway, Route, Listener가 뭔지 헷갈릴 때 이렇게 이해하세요

처음 Gateway API 문서를 보면 "Gateway", "Route", "Listener"라는 용어가 나오는데, 이게 뭔지 헷갈릴 수 있어요. 간단히 말하면:

- **Gateway**: 네트워크 경계, 즉 외부 트래픽이 들어오는 접점이에요. 예를 들어, 클러스터의 로드밸런서 역할을 하죠.
- **Listener**: Gateway 안에서 특정 포트와 프로토콜을 듣는 구성 요소예요. 예를 들어, 443번 포트에서 HTTPS 트래픽을 받는 역할입니다.
- **Route**: 들어온 트래픽을 실제 서비스로 연결하는 규칙이에요. HTTPRoute, TCPRoute 등 다양한 타입이 있어요.

이 구조 덕분에 한 Gateway에 여러 Listener를 붙이고, Listener별로 다양한 Route를 연결해 복잡한 트래픽 흐름을 유연하게 관리할 수 있죠. 예를 들어, 같은 Gateway에서 HTTP 80 포트는 내부 서비스로, HTTPS 443 포트는 외부 인증이 필요한 서비스로 분리하는 게 가능해집니다.


## 실무에서 Gateway API 운영하며 꼭 챙겨야 할 프로브 설정

실제로 Gateway API를 운영하면서 가장 중요한 부분 중 하나가 컨트롤러의 안정성 확보였어요. Gateway API는 컨트롤러가 Pod로 동작하는데, 이 컨트롤러가 제대로 동작하지 않으면 서비스 인그레스가 중단되니까요. 

그래서 **Liveness, Readiness, Startup 프로브** 설정을 꼼꼼히 해야 합니다. 예를 들어, Liveness 프로브는 10초마다 HTTP GET 요청을 보내서 컨트롤러가 살아있는지 확인하고, 실패 시 재시작하게 설정했어요. Readiness 프로브는 트래픽 수신 준비가 됐는지 판단하는데, 초기에는 5초 간격으로 체크하다가 안정화되면 30초 간격으로 조정했습니다.

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 15
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10
  failureThreshold: 3
startupProbe:
  httpGet:
    path: /startup
    port: 8080
  failureThreshold: 30
  periodSeconds: 10
```

이런 프로브 설정 덕분에 컨트롤러가 다운되거나 초기화 지연 시 빠르게 감지하고 복구할 수 있었어요. 특히 대규모 트래픽이 몰리는 시간대에 안정적인 인그레스 운영에 큰 도움이 됐습니다.


## Gateway API로 TLS와 인증서 관리를 어떻게 하면 좋을까?

Cloudflare 사례를 보면 Gateway API를 통해 TLS 암호화와 인증서 관리를 체계적으로 하는 게 클라우드 환경에서 얼마나 중요한지 알 수 있어요. TLS Termination을 Gateway 레벨에서 처리하면서 인증서를 자동 갱신하도록 설정하면, 서비스별로 개별 인증서 관리 부담이 크게 줄어듭니다.

예를 들어, 아래처럼 Gateway 리소스에 TLS 설정을 붙여서 443 포트 Listener에서 TLS를 처리하도록 할 수 있어요.

```yaml
apiVersion: gateway.networking.k8s.io/v1beta1
kind: Gateway
metadata:
  name: example-gateway
spec:
  gatewayClassName: my-gateway-class
  listeners:
  - name: https
    protocol: HTTPS
    port: 443
    tls:
      certificateRefs:
      - name: example-cert
    routes:
      kind: HTTPRoute
      selector:
        matchLabels:
          app: my-app
```

이렇게 하면 Gateway 컨트롤러가 인증서를 참조해서 TLS 연결을 처리하고, 내부 서비스에는 암호화된 트래픽이 전달되죠. 인증서 자동 갱신은 cert-manager 같은 툴과 연동해 운영하는 게 일반적입니다.


## 마이크로서비스 아키텍처에서 Gateway API가 주는 확장성과 유지보수성

Martin Fowler의 아키텍처 가이드에서도 언급하듯, Kubernetes Gateway API는 마이크로서비스 간 통신을 명확히 분리하고 정책 기반 트래픽 제어를 가능하게 해서 유지보수성을 크게 향상시킵니다. 

예를 들어, 서비스 A와 B가 같은 클러스터에 있어도 각기 다른 Gateway와 Route 정책을 적용해 트래픽을 분리할 수 있어요. 덕분에 특정 서비스에 대한 보안 정책이나 트래픽 제한을 독립적으로 관리할 수 있죠. 

이건 실제로 겪어보면, 대규모 팀에서 여러 서비스가 동시에 배포되고 운영될 때 정책 충돌 없이 안정적으로 운영할 수 있는 큰 장점입니다.


## Gateway API 도입 후 겪은 현실적인 문제와 해결법

처음 Gateway API를 도입할 때, 문서가 아직 완벽하지 않고 컨트롤러별 지원 기능이 달라서 고민이 많았어요. 예를 들어, 어떤 컨트롤러는 HTTPRoute만 지원하고 TCPRoute는 미지원이었죠. 그래서 우리 환경에 맞는 컨트롤러 선택이 중요했습니다.

또한, 복잡한 Route 정책을 잘못 설정하면 트래픽이 엉뚱한 서비스로 흘러가거나 TLS 인증서 오류가 발생하기도 했어요. 이때는 작은 단위로 리소스를 나누고, 단계별로 적용하면서 문제를 찾는 게 효과적이었죠.

마지막으로, 기존 Ingress와 병행 운영할 때는 리소스 충돌과 네임스페이스 접근 권한 문제도 신경 써야 했습니다. 권한은 RBAC 정책으로 세밀하게 관리했고, 네임스페이스별로 Gateway 리소스를 분리해 충돌을 최소화했어요.


## 정리하며: Gateway API를 시작할 때 꼭 기억할 점

- Gateway, Listener, Route 개념을 명확히 이해하고 설계부터 꼼꼼히 하자.
- 컨트롤러 프로브 설정은 필수, 특히 Liveness와 Readiness는 서비스 안정성의 기본이다.
- TLS와 인증서 관리는 Gateway 레벨에서 집중 관리하고 자동화 도구와 연동하자.
- 마이크로서비스별로 정책을 분리해 확장성과 유지보수성을 높일 수 있다.
- 컨트롤러별 지원 기능 차이를 미리 파악하고, 작은 단위로 점진 적용하자.

Gateway API는 아직 완전히 대중화된 건 아니지만, 클라우드 네이티브 환경에서 서비스 인그레스를 더 유연하고 안전하게 운영하려는 팀에게는 분명한 해답이 될 수 있습니다. 저도 이걸 도입하고 나서 트래픽 관리가 훨씬 명확해지고, 보안 이슈 대응도 빨라져서 만족도가 높아요.
