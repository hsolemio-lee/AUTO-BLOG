## VS Code 확장 프로그램 업데이트에 2시간 지연이 왜 생겼을까?

얼마 전 VS Code 1.123이 릴리즈되면서 확장 프로그램 업데이트에 2시간 딜레이를 걸기 시작했어요. 처음엔 "왜 갑자기 업데이트가 느려지지?" 싶었는데, 알고 보니 공급망 공격(Supply Chain Attack)을 막기 위한 조치더라고요. 

이게 무슨 말이냐면, 확장 프로그램이 배포되면 바로 내 개발 환경에 적용되는 게 아니라, 최소 2시간 동안 검증 시간을 거쳐서 악성 코드가 포함됐는지 탐지하는 시간을 둔다는 거죠. 

실제로 요즘 공급망 공격이 너무 많아서, 작은 라이브러리나 확장 프로그램 하나가 전체 개발 환경을 위험에 빠뜨릴 수 있다는 걸 다들 체감하고 있을 거예요. 이런 공격은 백엔드뿐 아니라 프론트엔드, 데브옵스까지 광범위하게 영향을 미치니까요.

## 공급망 공격 위험, 왜 2시간이 의미가 있을까?

공급망 공격은 흔히 공격자가 정상 소프트웨어 업데이트 경로를 타고 악성 코드를 심는 방식이에요. 예를 들어, 누군가가 확장 프로그램 배포 서버에 침투해서 악성 코드를 심으면, 그걸 받는 모든 개발자가 감염될 수 있죠. 

VS Code 팀이 2시간 딜레이를 둔 건, 이 사이에 자동화된 스캔과 모니터링 시스템이 새 확장 프로그램을 분석해서 이상 징후가 있으면 배포를 차단할 수 있도록 하려는 목적이에요. 

사실 2시간이라는 시간은 너무 길지도 짧지도 않은 타협점인데, 너무 짧으면 자동화 검증이 부족하고, 너무 길면 개발자들이 불편하니까요. 

이 지연 덕분에 공급망 공격으로 인한 피해를 상당 부분 줄일 수 있다고 하니, 백엔드 보안 담당자로서도 주목할 만한 변화죠.

## CI/CD 파이프라인에서 이 지연을 어떻게 감안해야 할까?

여기서 고민이 생겨요. 우리 팀은 VS Code 확장 프로그램을 활용한 개발 환경을 CI/CD 파이프라인에 맞춰 자동화해 왔는데, 이제는 확장 프로그램 업데이트가 최대 2시간 늦어질 수 있다는 거죠. 

가령, 빌드 서버가 최신 확장 프로그램을 자동으로 설치해서 테스트하는 시나리오라면, 이 지연 때문에 빌드가 실패하거나 오래 걸릴 수 있어요. 그래서 몇 가지 대응책을 생각해봤습니다.

### 1. 확장 프로그램 버전 고정하기

가장 간단한 방법은 `extensions.json` 같은 설정 파일에서 확장 프로그램 버전을 명시적으로 고정하는 거예요. 이렇게 하면 불필요한 자동 업데이트를 막고, 검증된 버전만 쓰게 할 수 있죠.

```json
{
  "recommendations": [
    "ms-python.python@2023.4.1",
    "esbenp.prettier-vscode@9.10.0"
  ]
}
```

이렇게 하면 CI/CD 파이프라인에서 특정 버전 확장 프로그램을 바로 설치할 수 있어서, 업데이트 지연과 무관하게 안정적인 빌드를 유지할 수 있어요.

### 2. 확장 프로그램 업데이트 주기 조정하기

자동 업데이트를 완전히 끄기보단, 배포 주기를 좀 더 넉넉하게 잡는 것도 방법입니다. 예를 들어, 하루에 한 번만 업데이트 체크를 하도록 스케줄링해서, 2시간 지연이 전체 워크플로우에 큰 영향을 주지 않도록 하는 거죠.

### 3. 실패 유형을 초기에 계측해서 장애 대응 속도 높이기

확장 프로그램 업데이트 실패나 호환성 문제는 CI/CD 파이프라인에서 꽤 흔한 이슈인데요, 이걸 초기에 잘 계측해두면 문제 원인을 빠르게 파악할 수 있어요. 

예를 들어, 업데이트 실패 시점, 실패 사유, 영향을 받은 테스트 케이스 등을 로깅해서 모니터링하면, 장애 대응 속도가 훨씬 빨라집니다. 이런 계측 전략은 Anthropic의 프롬프트 엔지니어링 가이드에서 실패 유형 조기 계측이 유지보수성과 장애 대응 속도를 개선한다고 강조하는 부분과도 맞닿아 있죠[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

## 실제로 우리 팀은 이렇게 적용했다

우리 팀은 VS Code 확장 프로그램 업데이트 지연이 도입되자마자, CI 파이프라인에 다음과 같은 스크립트를 추가했어요. 

```bash
# extensions-list.txt에 확장 프로그램과 버전 명시
while read extension; do
  code --install-extension "$extension" --force
done < extensions-list.txt
```

`extensions-list.txt`에는 `ms-python.python@2023.4.1` 같은 식으로 버전을 고정해서 적어두고, 빌드 때마다 이 파일을 참고해서 확장 프로그램을 설치해요. 

이렇게 하니, 업데이트 지연 때문에 빌드가 불필요하게 실패하는 일이 사라졌고, 확장 프로그램 버전 관리도 훨씬 명확해졌습니다.

물론, 이 방법은 확장 프로그램의 최신 기능을 바로바로 쓸 수 없다는 단점이 있지만, 안정성과 보안이 더 중요하니까요. 

## 점진적 배포 전략과 공급망 보안, 왜 같이 봐야 할까?

이 부분은 OpenAI API 문서에서 강조하는 점진적 배포 전략과도 연결돼요. 새로운 백엔드 기능을 한꺼번에 다 배포하는 게 아니라, 작은 범위로 점진적으로 배포하면 운영 리스크가 훨씬 낮아진다고 하죠[OpenAI API Documentation](https://platform.openai.com/docs/overview).

VS Code 확장 프로그램 업데이트 지연도 비슷한 맥락이에요. 확장 프로그램이 한 번에 모든 사용자에게 바로 배포되는 걸 막고, 일정 시간 동안 검증하는 과정을 두면서, 공급망 공격 위험을 줄이는 거니까요. 

이걸 CI/CD에 적용하면, 확장 프로그램뿐 아니라 내부 서비스 배포에도 점진적 배포와 실패 계측을 적극 활용해서 장애 가능성을 줄일 수 있습니다.

## 마무리하며

처음엔 VS Code 확장 프로그램 업데이트가 2시간씩 지연된다는 게 개발자 입장에서 꽤 불편하게 느껴졌어요. 하지만 이게 공급망 공격을 막는 중요한 보안 조치라는 걸 알고 나니, 오히려 안심이 되더라고요. 

우리 백엔드 개발자들이 할 일은 이런 보안 정책 변화에 맞춰 CI/CD 파이프라인을 조정하고, 실패를 초기에 잘 계측해서 장애 대응 속도를 높이는 거라고 생각해요. 

그리고 확장 프로그램 버전을 명확히 고정하는 습관을 들이면, 예상치 못한 업데이트로 인한 빌드 실패도 줄일 수 있습니다. 

이건 실제로 겪어보면, 작은 설정 하나가 개발 생산성과 보안에 큰 차이를 만든다는 걸 체감할 수 있을 거예요.
