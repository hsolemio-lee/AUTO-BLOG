## "왜 내 서비스는 아직도 느릴까?" 비동기 로깅과 커넥션 풀 개선으로 답을 찾다

최근에 우리 팀에서 Spring Boot 3.2로 마이그레이션하면서 가장 먼저 체감한 변화는 바로 비동기 로깅과 커넥션 풀 관리 개선 덕분에 지연 시간이 눈에 띄게 줄었다는 점입니다. 사실 프로덕션에서 로그가 많으면 동기 로깅 때문에 I/O 병목이 발생하는 경우가 많잖아요. Spring Boot 3.2부터는 `Logback` 기반 비동기 로깅이 기본 지원되어, 설정 한 줄로 CPU와 I/O 리소스 부담을 크게 줄일 수 있습니다.

```yaml
logging:
  logback:
    async:
      enabled: true
      queue-size: 512
      discarding-threshold: 0
```

이 설정으로 로그 이벤트를 비동기 큐에 넣고 별도 스레드에서 처리해, 메인 요청 처리 스레드가 로그 쓰기에 묶이지 않게 됩니다. 큐 사이즈는 512 정도가 적당한데, 너무 작으면 로그 손실이 발생할 수 있고, 너무 크면 메모리 부담이 커져요.

커넥션 풀도 HikariCP 기본 설정이 한층 개선되어, 최대 풀 크기(`maximumPoolSize`)와 커넥션 타임아웃(`connectionTimeout`)을 프로덕션 환경에 맞게 조정하면 DB 연결 지연을 줄일 수 있습니다. 예를 들어, 최대 풀 크기를 30, 타임아웃을 10000ms로 설정하면 대부분의 중간 규모 트래픽에서 안정적인 성능을 보장합니다.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 30
      connection-timeout: 10000
```

이 두 가지 설정만으로도 평균 응답 시간이 10~15% 개선된 사례를 우리 팀에서 경험했어요. 물론 애플리케이션 구조나 DB 부하에 따라 다르니, 모니터링과 조합해 조절하는 게 중요합니다.

## Spring Framework 6.1, OAuth 2.1과 CSRF 기본 활성화로 보안 걱정 덜어내기

보안은 늘 신경 쓰지만, 기본 설정만으로도 꽤 큰 효과를 볼 수 있다는 점을 이번에 새삼 느꼈습니다. Spring Framework 6.1부터는 OAuth 2.1 지원이 강화되고, CSRF(Cross-Site Request Forgery) 방어 메커니즘이 기본 활성화되어 있어요.

OAuth 2.1은 이전 버전 대비 권고사항이 명확해지고, 토큰 관리가 더 엄격해져서 기본 설정만으로도 인증과 권한 부여 과정에서 실수를 줄일 수 있습니다. 예를 들어, `spring-security-oauth2-client` 의존성을 추가하고 간단히 설정하면 바로 활용 가능하죠.

```java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            .anyRequest().authenticated()
        )
        .oauth2Login(Customizer.withDefaults())
        .csrf(csrf -> csrf
            .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
        );
    return http.build();
}
```

CSRF 토큰을 쿠키에 안전하게 저장하면서, 기본적으로 CSRF 공격을 막아주니 별도 커스텀 없이도 꽤 든든합니다. 물론 REST API를 운영한다면 CSRF 적용 범위를 조절해야 하는데, 그건 케이스 바이 케이스로 대응하면 됩니다.

이 기본 보안 기능 덕분에 별도의 복잡한 설정 없이도 보안 취약점을 줄일 수 있었고, 우리 팀 신규 프로젝트에서는 이 부분을 적극 활용 중입니다.

## JVM 튜닝과 Spring Actuator로 실시간 성능 모니터링하기

Baeldung 가이드에 따르면 JVM 힙 메모리와 GC 튜닝은 프로덕션 성능 문제를 조기 발견하고 대응하는 데 핵심이라고 합니다. 우리도 최근에 힙 크기를 2GB에서 4GB로 늘리고, G1 GC 옵션을 조정해서 GC로 인한 지연이 눈에 띄게 줄었어요.

```bash
-Xms4g -Xmx4g -XX:+UseG1GC -XX:MaxGCPauseMillis=200
```

특히 `MaxGCPauseMillis`를 200ms로 설정해 GC가 너무 오래 멈추지 않도록 조율했습니다. 물론 GC 튜닝은 애플리케이션 특성에 따라 달라서, 꼭 프로파일링하면서 조절해야 하죠.

그리고 Spring Actuator를 활용하면 힙 메모리 사용량, GC 활동, HTTP 요청 메트릭 같은 실시간 데이터를 편하게 볼 수 있습니다. 예를 들어, `application.yml`에 다음을 추가하면 `/actuator/metrics` 엔드포인트가 활성화됩니다.

```yaml
management:
  endpoints:
    web:
      exposure:
        include: "health,info,metrics"
```

이걸 Grafana 같은 대시보드와 연동하면 운영 중인 서비스의 상태를 한눈에 파악할 수 있어, 문제 발생 시 빠른 대응이 가능해집니다. 우리 팀도 이 덕분에 장애 원인 분석 시간이 절반 이상 줄었어요.

## 대규모 서비스도 걱정 없는 카나리 릴리즈와 자동 롤백 전략

GitHub Engineering Blog에서 소개한 점진적 배포 전략은 우리 팀에도 큰 영감을 줬습니다. Spring 기반 백엔드에서도 카나리 릴리즈를 적용해 신규 버전을 소수 사용자에게 먼저 노출하고, 문제가 발견되면 자동으로 롤백하는 방식을 도입했죠.

예를 들어, Kubernetes 환경에서 `Deployment` 리소스에 `maxSurge`와 `maxUnavailable`을 적절히 설정하고, 헬스체크를 꼼꼼히 구성하면 안전한 배포가 가능합니다.

```yaml
strategy:
  rollingUpdate:
    maxSurge: 25%
    maxUnavailable: 0
```

이렇게 하면 새 버전이 25%씩 점진적으로 올라가고, 장애가 발생하면 즉시 이전 버전으로 복귀할 수 있어요. 물론 모니터링 시스템과 자동화 스크립트가 필수입니다. 우리 팀은 Prometheus와 Alertmanager를 연동해 이상 징후 감지 시 자동 롤백 트리거를 걸었는데, 실제로 몇 차례 덕분에 장애를 미연에 방지했습니다.

이 전략을 적용하면서 배포 리스크가 크게 줄고, 개발자들도 마음 편히 기능을 릴리즈할 수 있게 됐습니다.

## 클라우드 API 게이트웨이와 보안 토큰 관리 자동화는 어떻게 할까?

Cloudflare Blog 사례를 참고해보면, Spring 백엔드와 클라우드 플랫폼을 연동할 때 API 게이트웨이를 통해 인증과 보안 토큰 관리를 자동화하는 게 핵심입니다. 우리도 AWS API Gateway와 Lambda@Edge를 활용해 토큰 검증과 권한 부여를 분리했는데, 배포 프로세스가 훨씬 간결해지고 보안 사고 위험도 줄었어요.

예를 들어, JWT 토큰을 API Gateway에서 미리 검증하고, Spring 서비스는 신뢰된 요청만 처리하도록 하면 내부 로직이 단순해집니다. 아래는 Spring Security에서 JWT 토큰을 검증하는 필터 예시입니다.

```java
public class JwtAuthenticationFilter extends OncePerRequestFilter {
    private final JwtTokenProvider tokenProvider;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {
        String token = resolveToken(request);
        if (token != null && tokenProvider.validateToken(token)) {
            Authentication auth = tokenProvider.getAuthentication(token);
            SecurityContextHolder.getContext().setAuthentication(auth);
        }
        filterChain.doFilter(request, response);
    }

    private String resolveToken(HttpServletRequest request) {
        String bearerToken = request.getHeader("Authorization");
        if (bearerToken != null && bearerToken.startsWith("Bearer ")) {
            return bearerToken.substring(7);
        }
        return null;
    }
}
```

이 필터는 API Gateway에서 전달된 JWT를 검증하고, 유효하면 Spring Security 컨텍스트에 인증 정보를 넣어줍니다. 이렇게 하면 Spring 백엔드는 토큰 검증 부담에서 어느 정도 자유로워지고, 보안 정책 변경 시 API Gateway만 수정하면 돼서 운영 편의성이 높아집니다.
