## "왜 이걸 선택했지?"라는 질문에 답할 수 있는 기록이 필요하다

우리 팀이 마이크로서비스 아키텍처를 도입한 지 벌써 2년째다. 처음에는 서비스 경계 설정, 데이터 관리 방식, 통신 프로토콜 선택 같은 중요한 결정들을 구두로만 공유하거나 슬랙 메시지에 흩뿌려 두는 식이었다. 그런데 어느 순간, "왜 이걸 선택했지?"라는 질문이 자주 나왔다. 특히 신규 합류한 동료들이 과거 의사결정 배경을 이해하지 못해 혼란이 컸다. 

이때부터 우리는 아키텍처 결정 기록(Architecture Decision Record, ADR)을 도입했다. ADR은 단순한 문서가 아니라, 우리가 왜 특정 설계를 선택했는지, 어떤 트레이드오프가 있었는지, 그리고 향후 마이그레이션 경로는 어떻게 되는지 명확하게 남기는 수단이다. 이게 없으면 6개월 뒤, 1년 뒤에 똑같은 논쟁을 반복하게 된다.

## 마이크로서비스 경계 설정에 ADR이 어떻게 도움을 주는가

마틴 파울러가 말한 것처럼, 마이크로서비스 아키텍처에서 서비스 경계는 시스템 확장성과 유지보수성의 핵심이다. 우리 팀도 서비스 하나를 쪼갤지, 아니면 통합할지 결정할 때 ADR을 썼다. 

예를 들어, 결제 서비스와 주문 서비스 경계를 나눌 때, 단순히 "결제는 따로 관리하는 게 좋겠다"라고 결론 내는 대신, 다음과 같은 내용을 ADR에 기록했다.

- **결제와 주문을 분리하는 이유**: 결제 시스템은 PCI DSS 준수가 필요해 보안 요구사항이 높음.
- **트레이드오프**: 서비스 간 통신 비용 증가, 데이터 일관성 문제 발생 가능성.
- **마이그레이션 계획**: 기존 모놀리식 주문 시스템에서 결제 모듈을 분리하는 단계별 절차.

이렇게 기록해두니, 신규 팀원이 "왜 분리했나요?"라고 물어볼 때 바로 근거를 보여줄 수 있었다. 또, 나중에 통신 프로토콜을 REST에서 gRPC로 바꾸는 결정도 ADR에 남겨, 변경 이유와 예상 영향도를 공유했다.

## 클라우드 환경에서 ADR이 다루는 실제 운영 제약과 트레이드오프

클라우드 환경에선 확장성, 장애 복구, 데이터 일관성 같은 운영 제약이 훨씬 복잡해진다. Microsoft의 클라우드 디자인 패턴 문서도 이런 트레이드오프를 체계적으로 다루는데, 우리도 ADR을 통해 비슷한 내용을 정리했다.

예를 들어, 데이터 일관성을 위해 강력한 트랜잭션을 포기하고 이벤트 소싱(event sourcing)을 선택했을 때, 다음과 같은 내용을 기록했다.

- **선택한 패턴**: 이벤트 소싱 및 CQRS.
- **장점**: 확장성 향상, 읽기/쓰기 분리로 성능 최적화.
- **단점 및 제약**: 최종 일관성 모델, 복잡한 이벤트 재처리 로직 필요.
- **운영 고려사항**: 이벤트 저장소 장애 시 복구 절차, 이벤트 버전 관리.

이런 기록 덕분에 운영팀과 개발팀이 장애 대응 시나리오를 미리 공유할 수 있었고, 실제 장애 발생 시 빠르게 원인을 파악하고 대응할 수 있었다.

## 마이그레이션 경로를 ADR에 상세히 남겨야 하는 이유

아키텍처 변경은 서비스 중단과 데이터 무결성 위험을 동반한다. GitHub 엔지니어링 블로그에서도 강조하듯, 마이그레이션 경로를 명확히 계획하고 기록하는 게 필수다. 우리 팀도 ADR에 다음과 같은 마이그레이션 계획을 상세히 적었다.

```markdown
# ADR 012: 주문 서비스 DB 분리

## 배경
기존 모놀리식 DB에서 주문 서비스 DB를 분리하여 독립적 확장성 확보 필요.

## 마이그레이션 단계
1. 읽기 전용 복제본 생성 및 주문 서비스에 연결.
2. 주문 서비스 쓰기 작업 점진적 이전.
3. 모놀리식 DB에서 주문 관련 테이블 제거.

## 위험 및 대응
- 데이터 동기화 지연 문제: CDC(Change Data Capture) 도입.
- 서비스 중단 최소화: 블루-그린 배포 전략 적용.

## 참고
- CDC 구현 관련 문서 링크
- 블루-그린 배포 가이드
```

이렇게 기록해두니, 마이그레이션을 담당하는 팀원들이 혼란 없이 절차를 따라갈 수 있었고, 예상치 못한 문제 발생 시 빠르게 대처할 수 있었다.

## ADR을 CI/CD 파이프라인과 연동하는 실제 사례

처음엔 ADR이 단순 문서 관리라고 생각했는데, 마틴 파울러가 말한 지속적 통합(Continuous Integration)과 연계하면 훨씬 효과적이라는 걸 알게 됐다. 우리 팀은 GitHub Actions를 활용해 ADR 변경사항이 빌드 및 배포에 미치는 영향을 자동으로 검증하는 프로세스를 만들었다.

예를 들어, ADR에서 서비스 간 통신 프로토콜을 변경하는 결정이 기록되면, 관련 코드 변경과 함께 다음 작업이 자동으로 실행된다.

- 프로토콜 변경에 따른 API 호환성 테스트.
- 관련 마이크로서비스 배포 스크립트 자동 업데이트.
- 변경 영향도 분석 리포트 생성.

간단한 GitHub Actions 워크플로우 예시는 다음과 같다.

```yaml
name: ADR Change Impact Check
on:
  push:
    paths:
      - 'docs/adr/**'
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Validate ADR format
        run: |
          # ADR Markdown 문법 검사 스크립트 실행
          ./scripts/validate_adr.sh
      - name: Run impact analysis
        run: |
          # 변경된 ADR 내용 기반 영향도 분석
          ./scripts/impact_analysis.sh
```

이렇게 하니 아키텍처 변경이 코드 빌드와 배포에 미치는 영향을 사전에 파악할 수 있어, 운영 위험을 크게 줄였다.

---

### 내 경험에서 얻은 핵심 팁

1. **ADR은 단순히 문서가 아니라 커뮤니케이션 도구다.** 팀원 모두가 쉽게 접근하고 이해할 수 있어야 한다.
2. **트레이드오프를 숨기지 말자.** 좋은 결정은 항상 장단점이 있으니 솔직하게 기록하는 게 신뢰를 만든다.
3. **마이그레이션 계획은 구체적으로.** 단계별 절차와 위험 대응까지 적으면 실제 운영에서 큰 도움이 된다.
4. **CI/CD와 연동해 자동화하라.** ADR 변경이 배포 파이프라인에 미치는 영향을 미리 검증하면 안정성이 높아진다.

ADR을 도입하면서 우리 팀은 과거보다 훨씬 빠르고 안정적으로 아키텍처 변경을 진행할 수 있었다. 처음엔 귀찮게 느껴질 수 있지만, 이건 실제로 겪어보면 장기적으로 엄청난 시간과 비용 절감으로 돌아온다.
