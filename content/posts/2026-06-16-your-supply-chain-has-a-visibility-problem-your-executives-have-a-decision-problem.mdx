### 공급망 데이터가 사라진다면, 경영진은 어떻게 결정할까?

얼마 전 우리 팀에서 SCM(공급망 관리) 시스템을 AWS 서버리스 환경으로 전환하는 프로젝트를 맡았는데, 재미있는 일이 벌어졌어요. 데이터는 있는데, 실시간으로 안 보이니 경영진이 결정을 못 내리는 상황이었죠. 공급망 가시성 문제는 단순히 데이터가 부족한 게 아니라, ‘데이터가 언제, 어떻게, 얼마나 정확하게 보이는가’가 핵심이었어요.

이걸 해결하려면 결국 백엔드에서 실시간 데이터 처리와 모니터링, 그리고 빠른 의사결정을 지원하는 인프라가 필요했죠. 그래서 AWS Lambda 기반 서버리스 Java 애플리케이션 최적화와 클라우드 SCM 솔루션 통합을 중심으로 얘기해보려고 합니다.

## AWS Lambda에서 Java 서버리스 성능 최적화, 메모리와 패키지 크기의 진실

Java로 Lambda 함수를 짤 때 가장 먼저 직면하는 문제는 콜드 스타트 지연이에요. 특히 메모리 할당이 적으면 CPU도 같이 제한되기 때문에 처리 속도가 뚝 떨어집니다. 우리 팀은 512MB 메모리 할당으로 시작했는데, 평균 응답 시간이 1.2초였어요. 메모리를 1024MB로 늘리니 응답 시간이 0.6초로 반으로 줄더군요.

메모리와 CPU는 비례하기 때문에, 메모리 늘리면 CPU도 같이 늘어나서 처리 속도가 개선됩니다. 하지만 무작정 크게 잡으면 비용이 올라가니까, 실제 호출 패턴과 지연 시간을 모니터링하면서 조절해야 해요.

그리고 패키지 크기도 콜드 스타트에 영향을 줍니다. Java 애플리케이션은 라이브러리 의존성이 많아 패키지가 커질 수밖에 없는데, 이를 최소화하려고 Spring Boot에서 `spring-boot-starter` 대신 꼭 필요한 모듈만 골라 쓰고, `AWS SDK`도 필요한 서비스만 포함시켰어요. 덕분에 배포 패키지 크기를 30MB에서 12MB로 줄였고, 콜드 스타트가 평균 700ms에서 300ms로 개선됐습니다.

```java
// AWS Lambda Handler 예시
public class Handler implements RequestHandler<Map<String, Object>, String> {
    @Override
    public String handleRequest(Map<String, Object> input, Context context) {
        // 간단한 비즈니스 로직
        String orderId = (String) input.get("orderId");
        // 주문 상태 조회 및 처리
        return "Order " + orderId + " processed successfully.";
    }
}
```

이런 식으로 불필요한 복잡성을 줄이고, 함수 하나에 집중하는 게 중요합니다.

## CloudWatch와 X-Ray로 서버리스 함수 상태를 실시간 감시하는 법

실무에서 성능 최적화는 한 번 하고 끝나는 게 아니에요. 호출량이 늘거나, 특정 API가 느려질 때 바로 알아차려야 하죠. AWS CloudWatch Metrics와 X-Ray를 적극 활용하면, Lambda 함수의 지연 시간, 오류율, 메모리 사용량을 실시간으로 모니터링할 수 있어요.

예를 들어, CloudWatch에서 `Duration`, `Errors`, `Throttles` 지표를 대시보드에 띄워놓고, 임계치를 넘으면 알람을 받도록 설정했습니다. X-Ray는 호출 트레이스(trace)를 시각화해 병목 구간을 정확히 파악하는 데 유용했어요. 특히 복잡한 공급망 이벤트 흐름을 추적할 때 빛을 발하더군요.

이렇게 모니터링을 체계화하니, 성능 저하가 발생해도 평균 5분 내에 원인을 찾아 대응할 수 있었습니다.

## GitHub Actions로 서버리스 Java 애플리케이션 배포 자동화하기

우리 팀은 GitHub Actions를 써서 CI/CD 파이프라인을 구축했어요. 매 커밋마다 테스트, 빌드, 배포가 자동으로 이뤄지니까 운영 효율이 크게 올라갔죠. 특히 서버리스 환경에서는 함수 코드가 자주 바뀌기 때문에 자동화가 필수입니다.

다음은 간단한 워크플로우 예시입니다:

```yaml
name: Deploy Lambda Function

on:
  push:
    branches:
      - main

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v3
      - name: Set up JDK 17
        uses: actions/setup-java@v3
        with:
          java-version: '17'
      - name: Build with Maven
        run: mvn clean package
      - name: Deploy to AWS Lambda
        uses: aws-actions/aws-lambda-deploy@v1
        with:
          function-name: my-java-lambda
          zip-file: target/my-lambda.jar
          region: ap-northeast-2
```

이 워크플로우 덕분에 배포 오류가 줄고, 코드 변경 사항이 실시간으로 반영되어 빠르게 피드백 받을 수 있었습니다.

## 공급망 가시성 문제, 클라우드 SCM 솔루션과 이벤트 기반 아키텍처로 풀다

공급망 가시성 문제는 단순히 데이터 저장소를 바꾸는 걸로 해결되지 않아요. 실시간 데이터 통합과 분석이 핵심입니다. 우리 프로젝트에서는 Microsoft Dynamics 365 Supply Chain Management API와 Oracle SCM 클라우드 솔루션을 연동해, 서버리스 백엔드에서 이벤트 기반으로 데이터를 처리했어요.

예를 들어, 주문이 들어오면 Lambda가 이벤트를 받아 재고 상태를 조회하고, 부족하면 자동으로 알림을 보내는 식이죠. 이렇게 하면 경영진은 실시간 재고 현황과 주문 처리 상황을 대시보드에서 바로 볼 수 있습니다.

SAP SCM 시스템도 AI 기반 예측 분석 기능을 제공하는데, 이를 통해 수요 예측과 재고 최적화를 지원해 경영진의 의사결정 속도를 높일 수 있더군요.

이런 클라우드 SCM 솔루션들은 서버리스 및 마이크로서비스 아키텍처와도 잘 맞아서, 확장성과 유지보수성도 좋아집니다.

### 마치며: 실무에서 꼭 챙겨야 할 팁

- **메모리와 CPU 할당은 함께 조절하라**: 메모리 늘리면 CPU도 같이 올라가 성능 개선 효과가 크다.
- **패키지 크기는 콜드 스타트의 적**: 꼭 필요한 라이브러리만 포함해 배포 패키지 크기를 최소화하자.
- **모니터링은 실시간으로**: CloudWatch와 X-Ray를 활용해 지표와 트레이스를 꾸준히 감시해야 문제를 조기에 발견할 수 있다.
- **배포 자동화로 운영 부담 줄이기**: GitHub Actions 같은 CI/CD 도구로 테스트와 배포를 자동화하자.
- **SCM 가시성은 이벤트 기반 아키텍처가 답**: 클라우드 SCM 솔루션 API와 Lambda 이벤트를 연동해 실시간 데이터 흐름을 확보하자.

이건 실제로 겪어보면, 데이터가 제때 안 보이는 게 얼마나 큰 장애인지 알게 됩니다. 서버리스 Java 애플리케이션 최적화와 SCM 솔루션 통합을 통해 공급망 가시성과 경영진 의사결정 문제를 동시에 해결할 수 있길 바랍니다.
