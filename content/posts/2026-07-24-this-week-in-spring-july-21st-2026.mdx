### "왜 내 Spring 애플리케이션이 갑자기 느려졌을까?"

최근에 우리 팀에서 운영 중인 Spring Boot 서비스가 갑자기 응답 속도가 느려지는 현상을 겪었어요. 로그를 뒤져보니 DB 커넥션 풀이 포화 상태였고, GC도 자주 발생하더라고요. 이런 문제를 만나면 누구나 당황하기 마련인데, 이번에 Spring Boot 최신 버전과 관련된 프로덕션 튜닝 팁을 정리하면서 꽤 많은 도움이 됐습니다.

---

## Spring Boot 3.x에서 달라진 캐싱과 커넥션 풀 기본 설정

Spring Boot 최신 버전(3.1.x 기준)은 프로덕션 환경에서 성능 최적화를 위해 기본 내장 캐싱 메커니즘과 커넥션 풀 설정을 꽤 손봤어요. 예를 들어, HikariCP 커넥션 풀의 기본 최대 커넥션 수가 10에서 20으로 늘어났고, 커넥션 타임아웃과 유휴 커넥션 검사 주기도 더 적극적으로 조정됩니다.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      connection-timeout: 30000 # 30초
      idle-timeout: 600000      # 10분
      max-lifetime: 1800000     # 30분
```

이 설정 덕분에 갑작스러운 트래픽 급증에도 커넥션 풀이 빨리 소진되는 문제를 완화할 수 있었어요. 물론 무작정 최대 커넥션 수만 늘리면 DB 부하가 커질 수 있으니, DB 서버 상태와 트래픽 패턴을 꼭 모니터링하면서 조절해야 합니다.

캐싱도 기본적으로 `@Cacheable`에 내장된 ConcurrentMapCache 외에 Caffeine 캐시가 더 선호되는데, Spring Boot 3.x는 Caffeine을 기본 지원해 캐시 적중률과 응답 속도를 향상시켰습니다. 캐시 TTL(Time To Live)을 5분 정도로 설정해두면 데이터 신선도와 성능 간 균형을 잡기 좋아요.

## 멀티스레딩과 비동기 처리, 이젠 기본기

Spring Framework 코어가 멀티스레딩과 비동기 처리를 더 탄탄하게 지원하면서, 백엔드 서버 처리량이 눈에 띄게 좋아졌어요. 특히 `@Async`와 `CompletableFuture`를 활용해 I/O 작업을 비동기로 처리하면, 스레드 블로킹을 줄여서 처리량을 30% 이상 개선한 사례도 있습니다.

```java
@Service
public class EmailService {

    @Async
    public CompletableFuture<Boolean> sendEmailAsync(String to, String subject, String body) {
        // 이메일 전송 로직
        return CompletableFuture.completedFuture(true);
    }
}
```

위처럼 간단히 `@Async`를 붙이기만 해도 스레드 풀에서 별도 스레드를 할당해 비동기 실행이 가능해요. 다만, 스레드 풀 크기 설정을 안 하면 기본값이 작아서 오히려 병목이 될 수 있으니 `TaskExecutor` 빈을 직접 설정해주는 게 좋습니다.

```java
@Configuration
@EnableAsync
public class AsyncConfig {

    @Bean(name = "taskExecutor")
    public Executor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(10);
        executor.setMaxPoolSize(50);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("AsyncExecutor-");
        executor.initialize();
        return executor;
    }
}
```

이렇게 하면 비동기 작업이 몰려도 스레드 부족으로 인한 지연을 줄일 수 있어요.

## OAuth 2.0 + JWT 조합으로 보안 강화하기

보안 쪽도 요즘은 OAuth 2.0과 JWT 토큰 기반 인증을 결합한 다중 인증 체계가 대세입니다. 우리 서비스도 Cloudflare 사례를 참고해 OAuth 2.0으로 인증을 처리하고, JWT 토큰에 권한 정보를 담아 API 호출 시 검증하는 방식을 도입했는데, 권한 위·변조 위험을 크게 줄일 수 있었어요.

```java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
      .oauth2ResourceServer(oauth2 -> oauth2.jwt())
      .authorizeHttpRequests(authz -> authz
          .requestMatchers("/api/admin/**").hasRole("ADMIN")
          .anyRequest().authenticated()
      );
    return http.build();
}
```

`spring-boot-starter-oauth2-resource-server` 의존성을 추가하고, JWT 토큰 검증을 위한 공개키 설정만 해주면 간단히 구현할 수 있습니다. 다만, JWT 토큰 만료 시간과 리프레시 전략을 꼼꼼히 설계하지 않으면 보안 구멍이 될 수 있으니 주의하세요.

## 대규모 서비스는 점진적 롤아웃이 답이다

새로운 기능을 한꺼번에 전체 서비스에 배포하면 리스크가 너무 크죠. GitHub 엔지니어링 블로그에서 소개한 점진적 롤아웃 전략을 우리 팀에도 적용했는데, 실제로 장애 발생률이 40% 이상 줄었어요.

기본 아이디어는 기능 플래그(Feature Flag)를 활용해 일부 사용자에게만 새 기능을 노출시키고, 모니터링을 통해 문제 없으면 점차 범위를 넓히는 겁니다. Spring Cloud Feature Flags 같은 라이브러리를 쓰면 쉽게 구현할 수 있어요.

```yaml
feature:
  flags:
    newCheckoutFlow: true
```

```java
if (featureFlagService.isEnabled("newCheckoutFlow", userId)) {
    // 새 결제 흐름 실행
} else {
    // 기존 흐름
}
```

이 방식은 롤백도 간편하고, 모니터링과 피드백 루프를 통해 안정성을 높여줍니다. 물론 관리해야 할 플래그가 많아지면 복잡해지니, 플래그 수명 주기 관리도 신경 써야 해요.

## 마이크로서비스 환경에서 Spring의 DDD와 이벤트 기반 통신 활용법

마지막으로, Martin Fowler가 강조한 것처럼 Spring 백엔드에서 도메인 주도 설계(DDD)를 경량화해 적용하고, 이벤트 기반 통신으로 서비스 간 결합도를 낮추는 방법도 소개할게요.

예를 들어, 주문 서비스에서 주문 생성 이벤트를 발행하고, 결제 서비스가 이를 구독하는 구조입니다. Spring Cloud Stream과 Kafka를 조합해 구현하면 확장성과 유지보수성이 크게 개선됩니다.

```java
// 주문 서비스에서 이벤트 발행
OrderCreatedEvent event = new OrderCreatedEvent(orderId, userId);
kafkaTemplate.send("order-events", event);

// 결제 서비스에서 이벤트 수신
@KafkaListener(topics = "order-events")
public void handleOrderCreated(OrderCreatedEvent event) {
    // 결제 처리
}
```

이벤트 기반 아키텍처는 비동기 처리와 장애 격리에 유리하지만, 이벤트 순서 보장과 중복 처리 문제를 반드시 고려해야 합니다.
