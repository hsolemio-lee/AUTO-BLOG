## SPA에서 네비게이션이 왜 이렇게 복잡해졌을까?

"페이지 전환이 느려서 사용자 경험이 떨어져요." 이런 얘기, 다들 한 번쯤 들어봤을 겁니다. 특히 SPA(단일 페이지 애플리케이션)를 만들다 보면, 화면 전환이 부드럽지 않고 네트워크 요청이 너무 많아지는 문제가 자주 발생하죠. 기존에는 히스토리 API와 라우터 라이브러리로 버텼지만, 복잡한 상태 관리와 불필요한 리렌더링을 막기엔 한계가 있었습니다.

그런데 최근에 Navigation API가 "Baseline"으로 정식 지원되면서, 이 문제를 좀 더 깔끔하게 해결할 수 있는 길이 열렸습니다. 실제로 GitHub 같은 대형 서비스도 이 API를 도입해 성능과 UX를 크게 개선했다는 사례가 나오고 있죠[GitHub Engineering Blog](https://github.blog/category/engineering/).

## Navigation API가 기존 네비게이션과 어떻게 다른가?

간단히 말해, Navigation API는 네비게이션 이벤트를 브라우저 레벨에서 더 세밀하게 제어할 수 있게 해줍니다. 기존에 SPA에서 페이지 전환을 구현할 때는 히스토리 API(pushState, replaceState)와 라우팅 라이브러리 조합으로 "내가 원하는 타이밍에" 화면을 바꾸고 데이터를 가져오는 방식을 썼죠.

하지만 이 방식은 다음과 같은 한계가 있었습니다:

- 네비게이션 이벤트마다 전체 컴포넌트가 리렌더링되는 경우가 많아 성능 저하
- 네트워크 요청이 중복되거나 불필요하게 발생
- 상태 관리와 라우팅 로직이 뒤섞여 유지보수가 어려움

Navigation API는 이런 문제를 해결하기 위해 네비게이션 이벤트를 세밀하게 훅(hook)할 수 있는 이벤트와 상태를 제공합니다. 예를 들어, `navigation.navigate` 메서드로 이동을 제어하고, `navigation.transition` 이벤트를 통해 네비게이션 진행 상태(대기, 진행, 완료 등)를 감지할 수 있죠. 이를 통해 불필요한 리렌더링을 줄이고, 필요한 데이터만 선별적으로 페칭하는 최적화가 가능해집니다.

Cloudflare에서도 이 API를 도입해 네트워크 요청 최적화와 렌더링 성능 향상에 성공했다는 사례가 있습니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

## 실제로 Navigation API를 활용해보면 어떤 모습일까?

제가 최근 프로젝트에서 적용한 간단한 예제를 보여드릴게요. React 환경에서 Navigation API를 사용해 페이지 전환 시 데이터 페칭과 상태 관리를 분리한 코드입니다.

```jsx
import React, { useEffect, useState } from 'react';

function useNavigationData(url) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(false);
  
  useEffect(() => {
    let isMounted = true;
    setLoading(true);
    fetch(url)
      .then(res => res.json())
      .then(json => {
        if (isMounted) {
          setData(json);
          setLoading(false);
        }
      })
      .catch(() => {
        if (isMounted) setLoading(false);
      });
    
    return () => { isMounted = false; };
  }, [url]);

  return { data, loading };
}

export default function Page({ navigation }) {
  const [currentUrl, setCurrentUrl] = useState('/api/home');
  const { data, loading } = useNavigationData(currentUrl);

  useEffect(() => {
    function onNavigate(event) {
      event.intercept({
        async handler() {
          setCurrentUrl(event.destination.url);
        }
      });
    }

    navigation.addEventListener('navigate', onNavigate);
    return () => navigation.removeEventListener('navigate', onNavigate);
  }, [navigation]);

  if (loading) return <div>로딩 중...</div>;
  return <div>{JSON.stringify(data)}</div>;
}
```

이 예제의 핵심은 `navigate` 이벤트를 가로채서 상태를 바꾸고, 그에 따라 필요한 데이터만 다시 불러오는 구조입니다. 덕분에 전체 페이지가 리렌더링되지 않고, 네트워크 요청도 꼭 필요한 부분만 발생합니다.

이렇게 상태 관리와 네비게이션 로직을 분리하면, 코드 유지보수도 훨씬 수월해집니다. 대규모 프로젝트에서 컴포넌트 재사용성과 테스트 편의성도 크게 올라가죠.

## 백엔드와 클라우드 플랫폼과의 연계도 생각해보자

Navigation API는 프론트엔드에서만 좋은 게 아닙니다. 사실 이 API를 잘 활용하면 백엔드와 클라우드 플랫폼 차원에서도 효율적인 상태 전환과 데이터 페칭 전략을 세울 수 있어요.

예를 들어, Spring 백엔드와 연동할 때는 API 요청 시점에 따라 캐싱 전략이나 세션 상태를 다르게 관리할 수 있습니다. InfoQ에서 소개한 사례처럼, 네비게이션 상태를 기반으로 서버 사이드에서 필요한 데이터만 선별적으로 보내는 게 가능해지죠[InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/).

이 부분은 팀 내 아키텍처 설계 시 꼭 함께 논의해야 할 주제입니다. 프론트엔드가 무작정 데이터를 요청하는 게 아니라, 네비게이션의 상태 변화에 맞춰 백엔드가 최적화된 응답을 줄 수 있도록 API 설계와 클라우드 인프라 구성을 맞추는 게 핵심입니다.

## Navigation API 도입 시 주의할 점들

처음에 이 API를 접하면 꽤 매력적이지만, 몇 가지 현실적인 고민도 필요합니다.

- **브라우저 지원**: 아직 모든 브라우저에서 완벽히 지원하지는 않으니, 폴리필이나 대체 로직을 준비해야 합니다.
- **학습 곡선**: 기존 라우팅 라이브러리와 패턴에서 벗어나야 하므로 팀원 교육이 필수입니다.
- **복잡한 상태 관리**: 네비게이션 상태를 세밀히 다루는 만큼, 상태 관리가 더 복잡해질 수 있습니다. 따라서 상태 관리 라이브러리와 잘 조합하는 전략이 필요합니다.

하지만 이런 단점들을 감수할 만큼 얻는 이점이 크다는 게 제 경험입니다. 특히 성능과 UX가 중요한 대형 SPA에서는 충분히 고려해볼 만합니다.

## 정리하며: Navigation API, 언제 써야 할까?

- SPA에서 페이지 전환이 잦고, 리렌더링 최적화가 필요할 때
- 네트워크 요청을 줄이고, 데이터 페칭을 네비게이션 상태에 맞게 제어하고 싶을 때
- 유지보수성과 재사용성을 높이기 위해 상태 관리와 라우팅 로직을 분리하고 싶을 때
- 백엔드(Spring 등)와 클라우드 인프라 연동을 고려해 전체 시스템 최적화를 도모할 때

처음엔 "이게 별거 아닌 것 같아 보이는데..." 하다가 직접 써보면 확실히 다릅니다. 특히 복잡한 사용자 흐름과 대규모 데이터를 다루는 앱에서 Navigation API는 게임 체인저가 될 수 있어요.

앞으로 프론트엔드 네비게이션을 고민하는 분들께 Navigation API 도입을 적극 추천합니다. 물론, 기존 라우팅 라이브러리와 함께 점진적으로 도입하는 것도 좋은 방법입니다.
