### "우리 서비스, 갑자기 느려졌는데 어디서부터 손대야 할까?"

이 질문, 아마 Spring MVC 백엔드 운영하는 분들이라면 한 번쯤은 고민해봤을 겁니다. 특히 트래픽이 급증하거나 기능이 복잡해질수록 성능 병목과 보안 취약점이 눈에 띄게 드러나죠. 저도 비슷한 경험을 했는데, 단순히 서버 스펙 올리는 것만으로는 답이 안 나오더라고요. 그래서 이번 글에서는 제가 직접 겪고 적용한 Spring MVC 성능 최적화와 보안 강화 팁, 그리고 안정적인 롤아웃 전략까지 공유하려고 합니다.

## Spring Boot Actuator로 병목 구간 빠르게 찾는 법

처음에 성능 문제가 생기면 어디가 문제인지부터 파악하는 게 급선무입니다. Spring Boot가 기본 제공하는 Actuator가 이 부분에서 큰 힘이 되더라고요. 메트릭 수집과 프로파일링 기능이 내장되어 있어서, 런타임 중에 CPU 사용량, 힙 메모리 상태, HTTP 요청 처리 시간 같은 지표를 바로 확인할 수 있습니다.

예를 들어, `/actuator/metrics/http.server.requests` 엔드포인트를 통해 각 API별 응답 시간 분포를 확인하면, 어느 요청이 병목인지 한눈에 파악 가능하죠. 실제로 제가 운영하는 서비스에서는 특정 API의 p95 응답 시간이 갑자기 1초를 넘는 걸 Actuator 덕분에 빨리 발견해서, 해당 컨트롤러 비동기 처리 전환 작업으로 문제를 해결한 경험이 있습니다.

```java
@RestController
public class AsyncController {

    @GetMapping("/async-data")
    public Callable<String> getAsyncData() {
        return () -> {
            // 시간이 오래 걸리는 작업
            Thread.sleep(2000);
            return "완료";
        };
    }
}
```

이렇게 `Callable`을 반환하면 Spring MVC가 별도의 스레드에서 처리해 메인 요청 처리 스레드가 블로킹되지 않습니다. 덕분에 고부하 상황에서 처리량과 응답 속도가 확실히 개선됐어요. 물론, 스레드 풀 크기 조절과 타임아웃 설정은 필수입니다. 너무 크게 잡으면 오히려 리소스 낭비가 심해지고, 너무 작으면 큐가 밀려서 지연이 발생하니까요.

[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html) 문서에 자세한 설정법이 있으니 참고하세요.

## JVM 힙과 GC 튜닝, G1 GC가 답일 때

성능 튜닝에서 JVM 설정 빼놓을 수 없죠. 특히 Spring Boot 기반 서비스라면 JVM 힙 메모리 크기와 GC 튜닝이 직접적인 체감 성능에 큰 영향을 줍니다. 제가 운영하는 대용량 트래픽 서비스에서는 G1 GC를 기본으로 쓰는데, 이게 생각보다 효과가 좋더라고요.

G1 GC는 힙을 여러 영역으로 나누고, 짧은 시간에 부분적으로 가비지 컬렉션을 수행해서 긴 멈춤 시간을 줄여줍니다. 실제로 힙 크기를 8GB로 설정하고 G1 GC 옵션을 적용한 후, p99 지연 시간이 평균 300ms에서 150ms로 줄어든 걸 확인했습니다.

```bash
java -Xms8g -Xmx8g -XX:+UseG1GC -XX:MaxGCPauseMillis=200 -jar app.jar
```

- `-Xms`와 `-Xmx`를 동일하게 맞추면 힙 확장 비용을 줄일 수 있고,
- `-XX:MaxGCPauseMillis=200`은 최대 GC 멈춤 시간을 200ms로 제한하는 설정입니다.

물론, G1 GC도 완벽한 건 아니고, 메모리 사용량이 급격히 늘거나 너무 많은 객체가 생성되는 패턴에서는 GC가 자주 발생해 성능 저하가 있을 수 있습니다. 그래서 JVM 모니터링 툴(JVisualVM, Mission Control 등)과 Actuator 메트릭을 같이 보면서 튜닝하는 걸 추천합니다.

더 자세한 JVM 튜닝 팁은 [Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance)에서 확인할 수 있습니다.

## Spring Security로 세션과 CSRF, HTTP 헤더까지 꽉 잡기

성능 못지않게 보안도 무시할 수 없죠. Spring MVC 애플리케이션에서 가장 기본적이면서 중요한 건 세션 관리 강화와 CSRF 보호입니다. 특히 로그인 세션이 많아질 때 세션 탈취 위험과 세션 고갈 문제가 심각해지는데, Spring Security가 제공하는 세션 정책 설정으로 어느 정도 방어할 수 있습니다.

```java
@EnableWebSecurity
public class SecurityConfig extends WebSecurityConfigurerAdapter {
    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
            .csrf().csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
            .and()
            .sessionManagement()
                .maximumSessions(1)
                .maxSessionsPreventsLogin(true);

        http.headers()
            .contentSecurityPolicy("default-src 'self'")
            .and()
            .frameOptions().deny();
    }
}
```

- `maximumSessions(1)`은 한 계정당 하나의 세션만 허용해서 중복 로그인이나 세션 탈취를 방지합니다.
- CSRF 토큰을 쿠키에 저장해 SPA나 AJAX 요청 시 쉽게 토큰을 주고받게 설정했고,
- Content Security Policy(CSP)와 Frame Options로 클릭재킹과 XSS 공격 위험을 낮췄습니다.

이렇게 HTTP 헤더 보안 설정을 꼼꼼히 해두면, 외부 공격 벡터를 크게 줄일 수 있더라고요. 물론, 너무 엄격하게 설정하면 정당한 요청도 막힐 수 있으니 테스트 환경에서 충분히 검증하는 게 중요합니다.

관련 내용은 [Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)의 Security 섹션에서 자세히 다루고 있습니다.

## 무중단 배포를 위한 Canary와 블루-그린 전략 직접 써보니

성능과 보안을 개선한 뒤에는 안정적인 롤아웃 전략도 필요합니다. 저희 팀은 Canary 배포와 블루-그린 배포 방식을 조합해서 운영 중인데, 이게 생각보다 효과가 큽니다.

Canary 배포는 새 버전을 소수의 사용자에게만 먼저 노출해서 문제를 조기에 발견하는 방식이고, 블루-그린 배포는 완전히 분리된 두 환경을 두고 트래픽을 전환하는 방식입니다. 둘 다 무중단 배포를 보장하면서 점진적으로 모니터링할 수 있어서 대규모 서비스에 적합하죠.

실제로 신규 기능 배포 시 5% 트래픽만 Canary 환경으로 보내고, Actuator와 Prometheus로 모니터링하며 에러율과 응답 시간을 체크합니다. 이상 징후가 없으면 1시간 단위로 점차 비중을 늘려서 전체 트래픽으로 전환합니다. 만약 문제가 생기면 즉시 블루 환경으로 롤백할 수 있어 다운타임 없이 안정적으로 운영할 수 있었습니다.

이 전략은 [Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/)에서도 소개하는 검증된 방법입니다.

### 정리하며

- **Actuator로 병목 API 빠르게 찾기**: `/actuator/metrics` 활용해 p95, p99 응답 시간 집중 모니터링
- **비동기 요청 처리로 스레드 블로킹 줄이기**: `Callable`이나 `DeferredResult` 적극 활용
- **JVM G1 GC 튜닝으로 지연 시간 낮추기**: 힙 크기 고정, `-XX:+UseG1GC`, `MaxGCPauseMillis` 조절
- **Spring Security로 세션, CSRF, HTTP 헤더 보안 강화**: 중복 로그인 제한, CSP 설정 필수
- **Canary + 블루-그린 배포로 무중단 안정 롤아웃**: 점진적 트래픽 전환과 실시간 모니터링 병행

처음엔 이게 별거 아닌 것 같지만, 실제로 적용해보면 서비스 안정성과 사용자 경험이 확실히 달라집니다. 특히 성능 문제는 한두 가지 튜닝으로 해결되지 않는 경우가 많으니, 여러 방면에서 조금씩 개선하는 게 중요해요. 그리고 보안은 한 번 뚫리면 복구가 어려우니, 기본부터 꼼꼼하게 챙기는 습관을 들이시길 바랍니다.

여러분 서비스에도 꼭 도움이 되길 바라며, 궁금한 점 있으면 언제든지 댓글로 질문 주세요!
