## "왜 우리 백엔드에 Bliki 같은 인터로가토리 LLM이 필요하지?"

최근 우리 팀에서 Bliki라는 인터로가토리 LLM 도입을 검토하면서, "기존 REST API로도 충분한데 왜 자연어 질의응답 시스템을 백엔드에 붙여야 할까?"라는 질문이 많이 나왔어요. 실제로 이걸 도입하면 아키텍처가 복잡해지고, 응답 지연 시간도 걱정되고, 무엇보다 데이터 프라이버시 문제도 신경 써야 하죠. 그래서 이번 글에서는 Bliki가 어떤 식으로 설계되고, 기존 시스템과 어떻게 점진적으로 통합할 수 있는지, 그리고 운영하면서 어떤 제약과 절충점이 있는지 경험을 공유해보려 합니다.

---

## Bliki 아키텍처, 확장성과 응답 속도, 프라이버시 사이에서 균형 잡기

Bliki는 인터로가토리 LLM으로서, 사용자의 자연어 질의에 대해 백엔드 데이터와 지식을 조합해 답변을 생성해줍니다. 여기서 중요한 건 세 가지 트레이드오프가 있다는 점이에요.

1. **확장성**: LLM 모델은 무겁고 자원 소모가 크기 때문에, 수천 건 이상의 동시 질의를 처리하려면 멀티 노드 분산 아키텍처가 필요합니다. 하지만 분산 구조가 복잡해질수록 데이터 일관성 유지와 네트워크 비용이 늘어나죠.

2. **응답 지연 시간**: 자연어 처리 모델은 보통 수백 밀리초에서 수 초 단위의 추론 시간이 필요한데, 백엔드 API처럼 즉각적인 응답을 기대하는 서비스에선 이게 문제입니다. 그래서 캐싱 계층을 두거나, 비동기 처리로 사용자 경험을 보완합니다.

3. **데이터 프라이버시**: LLM이 외부 클라우드 API를 호출할 경우, 민감한 데이터가 노출될 위험이 있습니다. 그래서 사내 전용 모델 운영 혹은 프라이버시 강화 기법 적용이 필수적입니다.

이런 균형점을 찾는 건 마틴 파울러가 말한 소프트웨어 아키텍처 설계의 핵심과도 맞닿아 있어요[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

## 기존 REST API에서 Bliki로, 점진적 마이그레이션 전략

기존에 REST API 기반으로 운영 중인 시스템에 Bliki 같은 LLM을 도입할 때, 한꺼번에 교체하는 건 현실적으로 무리입니다. 우리 팀도 처음에는 "모두 LLM으로 전환하자"고 했다가, 너무 큰 리스크와 비용 때문에 방향을 바꿨죠.

대신 추천하는 건 하이브리드 모델이에요. 예를 들어, 기존 API가 제공하는 정형화된 데이터는 그대로 두고, LLM은 자연어 질의 처리와 비정형 데이터 분석에 집중시키는 거죠. 이 과정에서 아래와 같은 단계를 거칩니다:

- **1단계: LLM 프록시 레이어 추가** — 기존 API 앞단에 LLM 질의 처리 레이어를 둬서, 자연어 요청을 API 호출로 변환하거나 API 응답을 보완
- **2단계: 데이터 파이프라인 호환성 유지** — LLM이 참조하는 데이터 소스를 기존 DB, 캐시, 로그 등과 연동하여 일관성 확보
- **3단계: 점진적 기능 전환** — 특정 도메인이나 기능부터 LLM 기반 인터로가토리 서비스로 옮겨가며 안정성 검증

이런 접근법은 InfoQ에서 소개하는 소프트웨어 아키텍처 설계 원칙과도 일맥상통합니다[InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/).

## 실제 운영에서 만나는 비용, 지연, 그리고 모델 업데이트 문제

LLM을 운영하면서 가장 골치 아픈 부분 중 하나가 바로 추론 비용과 실시간 처리 요구 사이의 균형이에요. 예를 들어, OpenAI API 같은 클라우드 기반 LLM은 호출당 비용이 발생하는데, 초당 수백 건 요청이 들어오면 비용이 급증합니다.

그래서 우리 팀은 다음과 같은 전략을 썼어요:

- **캐싱 전략**: 자주 묻는 질문이나 동일한 쿼리에 대한 응답은 Redis 캐시(5분 TTL)로 저장해 재사용
- **비동기 처리**: 즉시 응답이 필요 없는 경우, 백그라운드에서 LLM 추론을 수행하고 결과를 나중에 전달
- **점진적 롤아웃**: 모델 버전 업데이트 시, 전체 트래픽의 10%부터 적용해 문제 발생 시 빠르게 롤백 가능

이런 운영 전략은 OpenAI 공식 문서에서도 권장하는 방법입니다[OpenAI API Documentation](https://platform.openai.com/docs/overview).

## Bliki 프롬프트 설계, 정확도와 품질을 좌우하는 숨은 열쇠

Bliki 같은 인터로가토리 LLM은 프롬프트 엔지니어링이 성능의 절반 이상을 좌우한다고 해도 과언이 아니에요. 처음에 우리 팀도 단순히 "질문만 넣으면 답 나오겠지" 했는데, 결과가 너무 들쭉날쭉해서 고생했죠.

Anthropic의 프롬프트 설계 가이드를 참고해보니, 다음 요소가 중요하더라고요[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview):

- **명확한 컨텍스트 제공**: 질문 배경, 관련 데이터 범위, 기대하는 답변 형태를 구체적으로 명시
- **의도 파악**: 단순 질의가 아니라, 사용자가 실제로 원하는 정보를 유추해 반영
- **단계적 질의 구성**: 복잡한 질문은 여러 단계로 나누어 LLM이 논리적으로 접근하도록 유도

예를 들어, 다음은 우리 팀에서 실제 쓴 프롬프트 예시입니다:

```python
prompt_template = '''
당신은 백엔드 시스템 전문가입니다.
아래는 사용자 질의입니다:
"""
{user_query}
"""
관련 데이터는 {data_source}에 있습니다.
이 정보를 바탕으로, 가능한 한 구체적이고 정확한 답변을 3문장 이내로 작성하세요.

답변:
'''

# 실제 호출 예
user_query = "최근 1시간 동안 API 오류율이 5%를 넘은 원인이 무엇인가요?"
data_source = "로그 DB와 모니터링 지표"
prompt = prompt_template.format(user_query=user_query, data_source=data_source)

# 이 프롬프트를 LLM에 넘겨서 응답 받음
```

이렇게 하면 LLM이 불필요한 추측을 줄이고, 핵심 데이터에 집중해서 답변을 만들어줘요.

## 대규모 분산 환경에서 Bliki 운영, 캐싱과 비동기 처리의 현실적인 효과

Cloudflare와 GitHub 엔지니어링 사례를 보면, 인터로가토리 LLM을 대규모 분산 시스템에 붙일 때 네트워크 지연과 데이터 일관성 문제가 가장 큰 장애물이라고 해요[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/), [GitHub Engineering Blog](https://github.blog/category/engineering/).

그래서 이들은 다음과 같은 방식을 도입했습니다:

- **멀티 레이어 캐싱**: 글로벌 CDN 캐시 + 지역별 엣지 캐시 + 애플리케이션 레벨 캐시로 다중 계층 캐싱 구현
- **비동기 처리 메커니즘**: API 게이트웨이에서 요청을 큐에 넣고, 별도 서비스가 LLM 추론 후 결과를 비동기 반환
- **마이크로서비스 아키텍처 전환**: 기존 모놀리식에서 각 기능별 독립 서비스로 분리해 장애 격리 및 독립 확장 가능

우리 팀도 비슷하게, API 게이트웨이에서 LLM 호출을 비동기 큐에 연결해 응답 지연을 줄였고, 캐시 TTL을 1분~5분 사이로 조절하며 비용과 성능을 맞췄습니다.

## 마무리하며: Bliki 도입 전 꼭 챙겨야 할 3가지

1. **아키텍처 설계에 시간 투자하기**
   - 확장성, 응답 지연, 프라이버시 요구사항을 명확히 정의하고, 트레이드오프를 문서화하세요.

2. **점진적 마이그레이션 계획 세우기**
   - 기존 API와 LLM 하이브리드 모델로 시작해, 안정성 검증 후 점차 전환하는 게 리스크를 줄입니다.

3. **프롬프트 엔지니어링에 집중하기**
   - LLM 정확도는 프롬프트 품질에 달려 있으니, 명확한 컨텍스트와 의도 파악을 위한 템플릿을 꼭 만드세요.

처음엔 Bliki 같은 인터로가토리 LLM이 복잡하고 까다로워 보이지만, 실제로는 이런 세밀한 설계와 운영 전략 덕분에 안정적인 서비스가 가능해집니다. 우리 팀도 시행착오를 거치며 배운 점이 많으니, 비슷한 고민을 하는 동료 엔지니어분들께 조금이나마 도움이 되길 바랍니다.
