## 갑자기 트래픽 폭주? OpenSearch 서버리스로 어떻게 대응할까

"갑자기 검색 쿼리가 3배로 늘었는데, 클러스터가 멈춰버렸어!" 이런 경험, 혹시 있나요? 우리 팀도 최근에 비슷한 상황을 겪었는데, 그때 AWS가 발표한 차세대 Amazon OpenSearch Serverless가 큰 도움이 됐습니다. 서버 관리 부담을 줄이고, 비용도 훨씬 유연하게 조절할 수 있었거든요. 이 글에서는 제가 직접 겪은 실제 사례와 함께, 어떻게 OpenSearch Serverless를 활용해 백엔드 확장성과 비용 효율성을 잡았는지 이야기해보려 합니다.


## Amazon OpenSearch Serverless, 뭐가 달라졌길래?

기존 OpenSearch 클러스터는 노드 스펙과 수를 직접 관리해야 했죠. 그래서 트래픽 급증 시점에 대비해 항상 여유 용량을 두거나, 반대로 과도한 비용이 발생하는 문제가 있었습니다. 그런데 이번에 AWS가 내놓은 차세대 OpenSearch Serverless는 완전 관리형으로, 인프라 프로비저닝 없이 자동으로 확장과 축소가 가능해졌어요. 

실제로 우리 팀은 다음과 같은 점에서 큰 변화를 느꼈습니다:

- **자동 확장**: 트래픽이 갑자기 3배로 늘었는데도 별도의 조치 없이 지연 시간 95백분위(p95)가 200ms 이하로 안정적으로 유지됐습니다.
- **비용 최적화**: 사용한 만큼만 과금되니, 비수기에는 비용이 40% 이상 줄었어요.
- **운영 부담 감소**: 클러스터 상태 모니터링과 노드 관리에 쏟던 시간을 다른 핵심 개발에 투자할 수 있었습니다.


## 점진적 배포 전략으로 신규 기능 도입 시 리스크 줄이기

OpenSearch Serverless 도입 초기에 가장 신경 쓴 부분은 '점진적 배포'였습니다. 아무리 좋은 기술도 한 번에 전체 서비스에 적용하면 예상치 못한 장애가 발생할 수 있거든요. 그래서 신규 백엔드 기능을 작은 범위부터 점진적으로 배포했는데, 이 전략이 정말 효과적이었어요.

예를 들어, 검색 API 중 일부 엔드포인트만 먼저 OpenSearch Serverless로 전환하고, 트래픽의 10%만 라우팅했습니다. 그 결과, 문제 발생 시 빠르게 원복 가능했고, 실제 장애 없이 점차 범위를 넓힐 수 있었죠. 

이 방식은 React 공식 문서에서 강조하는 "작은 범위의 점진적 배포 전략은 신규 백엔드 기능의 운영 리스크를 낮춘다"는 주장과도 일맥상통합니다[React - Thinking in React](https://react.dev/learn/thinking-in-react).


## 실패 유형을 조기 계측해 장애 대응 속도 높이기

운영 중 가장 힘든 건 장애가 났을 때 원인을 신속히 파악하는 일이죠. OpenSearch Serverless를 도입하면서 우리 팀은 장애 유형을 조기에 계측하는 방식을 적극 도입했습니다. 

구체적으로는 OpenSearch 쿼리 실패, 타임아웃, 권한 오류 등 다양한 실패 케이스를 CloudWatch 지표와 연동해 실시간 모니터링 대시보드를 만들었어요. 덕분에 장애 발생 5분 내에 원인 분석과 대응책 수립이 가능해졌습니다. 

이런 접근법은 Next.js 공식 문서에서 말하는 "실패 유형을 초기부터 계측하면 유지보수성과 장애 대응 속도가 개선된다"는 점과도 잘 맞아떨어집니다[Next.js App Router Docs](https://nextjs.org/docs/app/building-your-application/routing).


## OpenSearch Serverless 쿼리 최적화: 비용과 성능 두 마리 토끼 잡기

서버리스 환경에서는 쿼리 효율성이 비용과 직결됩니다. 저희는 다음과 같은 팁을 실무에 적용했습니다:

- **필요한 필드만 조회하기**: `_source` 필드에서 필요한 데이터만 명시해 불필요한 데이터 전송 최소화
- **쿼리 캐싱 활용**: 자주 조회되는 쿼리는 애플리케이션 레벨에서 캐싱 처리
- **비용이 큰 집계 쿼리 제한**: 집계 쿼리는 서버리스 리소스를 많이 쓰므로, 쿼리 빈도와 범위를 제한

아래는 간단한 예시 코드입니다. 특정 사용자 ID로 로그 데이터를 조회할 때, 필요한 필드만 뽑아오는 쿼리입니다.

```json
{
  "query": {
    "term": { "userId": "12345" }
  },
  "_source": ["timestamp", "action", "resource"]
}
```

이렇게 하면 불필요한 필드 조회를 줄여 네트워크 비용과 처리 시간을 절약할 수 있습니다.


## 운영 중 마주친 한계와 앞으로의 고민거리

물론 OpenSearch Serverless가 만능은 아닙니다. 저희가 겪은 한계도 공유할게요.

- **쿼리 복잡도 제한**: 너무 복잡한 집계나 스크립트 쿼리는 서버리스 환경에서 성능 저하가 발생할 수 있습니다.
- **초기 학습 곡선**: 서버리스 특성에 맞는 모니터링과 비용 관리 방법을 익히는 데 시간이 필요했습니다.
- **데이터 보존 정책**: 서버리스는 인프라 관리가 없다는 장점이 있지만, 장기 데이터 보존과 백업 정책은 별도 설계가 필요합니다.

이런 점들은 AWS Well-Architected Framework에서 권장하는 운영 우수 사례와도 맞물려 앞으로도 계속 개선해 나가야 할 부분입니다[AWS Well-Architected Framework](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html).


## 마치며: OpenSearch Serverless 도입, 이렇게 시작해보세요

- **작은 기능부터 점진적 배포**로 운영 리스크 낮추기
- **실패 유형을 조기 계측**해 장애 대응 속도 높이기
- **쿼리 최적화**로 비용과 성능 균형 맞추기
- **모니터링과 비용 대시보드**를 꼭 구축해 실시간 상태 파악하기

처음엔 서버리스라는 개념이 낯설고, 비용 모델도 감이 잘 안 잡힐 수 있지만, 실제로 써보면 운영 부담이 크게 줄고 확장성이 월등히 좋아집니다. 우리 팀 경험이 여러분 백엔드 운영에 조금이라도 도움이 되길 바랍니다.
