## 로컬 LLM으로 긴 작업을 하려니 왜 이렇게 힘들까?

요즘 로컬에서 작은 LLM을 돌려보는 재미에 빠져 있는데, 문제는 한계가 명확하다는 거예요. 컨텍스트 길이가 짧아서 긴 작업을 한 번에 맡기기 어렵고, 중간 상태를 기억시키기도 쉽지 않죠. 저도 한 프로젝트에서 이런 벽을 맞닥뜨렸는데, 그냥 "더 큰 모델을 쓰자"가 답이 아니더라고요. 그래서 외부 상태를 저장하고, 필요한 도구를 붙이고, 역할을 나누고, 작업을 루프로 돌리는 식으로 실험해봤습니다.

이게 생각보다 꽤 쓸만해서 오늘은 그 경험을 공유하려고 해요.

---

## Gemento: 외부 상태 저장이 왜 필요할까?

작은 LLM은 한 번에 처리할 수 있는 텍스트 길이가 제한적입니다. 예를 들어 GPT-3.5-turbo 기준으로도 4,000 토큰 정도인데, 로컬에서 돌리는 모델은 이보다 훨씬 적죠. 그래서 긴 작업을 하다 보면 ‘앞에서 무슨 얘기했더라?’ 하면서 맥락을 잃기 쉽습니다.

이럴 때 외부 상태 저장소를 두면, 모델이 직접 기억하지 못하는 정보를 따로 관리할 수 있어요. 예를 들어 JSON 파일, 간단한 DB, 혹은 Redis 같은 인메모리 저장소를 활용해서 중간 결과나 진행 상황을 기록합니다.

```python
# 간단한 외부 상태 저장 예시 (파이썬)
import json

state_file = 'gemento_state.json'

# 상태 불러오기
def load_state():
    try:
        with open(state_file, 'r') as f:
            return json.load(f)
    except FileNotFoundError:
        return {}

# 상태 저장하기
def save_state(state):
    with open(state_file, 'w') as f:
        json.dump(state, f)

# 작업 중간에 상태 업데이트
state = load_state()
state['step'] = 'tokenize_done'
save_state(state)
```

이렇게 하면 LLM이 매번 모든 정보를 다시 받아야 하는 부담을 덜고, 중간중간 상태를 참고하며 작업을 이어갈 수 있죠. 실제로 OpenAI API 문서에서도 외부 상태를 활용해 컨텍스트 한계를 극복하는 방법을 권장합니다[OpenAI API Documentation](https://platform.openai.com/docs/overview).

## 역할과 루프: LLM에게 일을 나눠주고 반복시키기

LLM에게 한꺼번에 복잡한 작업을 시키면, 답이 엉키거나 놓치는 부분이 생기기 쉽습니다. 그래서 역할(role)을 부여하고, 루프(loop)를 돌려서 점진적으로 문제를 해결하는 방식을 써봤어요.

예를 들어, 문서 요약 작업을 할 때 ‘요약자’, ‘검토자’, ‘교정자’ 같은 역할을 시뮬레이션해서 각 역할이 맡은 부분을 처리하도록 프롬프트를 설계합니다. 그리고 루프를 돌면서 요약을 점점 다듬어요.

Anthropic의 프롬프트 엔지니어링 가이드에서도 역할과 루프를 활용해 LLM의 반복적 작업 수행을 극대화하는 방법을 자세히 설명합니다[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

```python
# 역할과 루프를 활용한 간단한 프롬프트 예시
roles = ['요약자', '검토자', '교정자']

for role in roles:
    prompt = f"당신은 {role}입니다. 다음 텍스트를 처리하세요:\n{input_text}"
    response = call_local_llm(prompt)  # 로컬 LLM 호출 함수
    input_text = response  # 다음 역할이 처리할 입력으로 사용

print(f"최종 결과:\n{input_text}")
```

이런 방식을 쓰면 LLM이 한 번에 모든 걸 하려다 실패하는 걸 방지하고, 역할별로 집중하게 만들어서 결과 품질이 올라갑니다.

## 도구 통합으로 LLM의 약점을 보완하기

로컬 LLM은 외부 도구와 연동하면 훨씬 강력해집니다. 예를 들어 계산기, 데이터베이스 쿼리, 웹 스크래핑 같은 작업은 LLM이 직접 하기엔 비효율적이거나 불가능하죠. 그래서 도구를 API 형태로 붙여서 필요할 때 호출하도록 합니다.

이때 중요한 건 LLM이 도구 호출 결과를 다시 받아서 다음 작업에 반영할 수 있게 하는 거예요. 도구 호출 결과를 외부 상태에 저장하고, 프롬프트에 반영하는 구조를 만들면 됩니다.

Cloudflare 블로그에서도 클라우드 플랫폼 환경에서 LLM과 외부 도구 연동이 작업 자동화에 큰 도움이 된다고 언급합니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

```python
# 도구 호출 예시
import requests

def call_tool(query):
    # 예: 간단한 계산기 API 호출
    response = requests.post('http://localhost:5000/calc', json={'expr': query})
    return response.json()['result']

# LLM 프롬프트에서 도구 호출 포함
query = "12 + 34 * 2"
result = call_tool(query)
prompt = f"계산 결과는 {result}입니다. 다음 작업을 이어가세요."
response = call_local_llm(prompt)
```

도구 통합은 LLM의 한계를 보완하면서도, 시스템 아키텍처 측면에서 모듈화와 확장성을 높여 유지보수성을 개선하는 효과도 있습니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

## 실제 프로젝트에서 Gemento 방식을 써보고 느낀 점

저희 팀에서 Gemento 방식을 도입해보니, 처음엔 상태 관리와 역할 분담 설계가 생각보다 복잡했어요. 특히 상태 동기화 문제와 루프 중 무한 반복 방지 로직을 꼼꼼히 챙겨야 했죠. 하지만 한 번 안정화되니, 긴 작업을 여러 단계로 나누고 도구를 적절히 활용하는 게 훨씬 효율적이라는 걸 체감했습니다.

예를 들어, 코드 리뷰 자동화 파이프라인을 만들 때 작은 LLM이 각 리뷰어 역할을 맡아 코드를 분석하고, 테스트 도구를 호출해 결과를 반영하는 식으로 구성했는데, 작업 실패율이 30% 이상 줄었어요.

그리고 프론트엔드와 백엔드 모두에서 이런 외부 상태와 도구 연동 전략이 UX와 시스템 응답성 개선에 도움이 된다는 점도 인상적이었습니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

## Gemento를 직접 써보고 싶다면 이렇게 시작해보세요

1. **외부 상태 관리부터 시작**
   - JSON, SQLite, Redis 등 간단한 저장소를 정하고 중간 결과를 기록하세요.
2. **역할과 루프 설계**
   - 작업을 단계별 역할로 나누고, 각 역할이 맡은 일을 순차적으로 수행하도록 프롬프트를 짜보세요.
3. **도구 통합 준비**
   - 계산기, API 호출, DB 쿼리 같은 자주 쓰는 도구를 래핑해서 LLM이 호출할 수 있게 만드세요.
4. **무한 루프 방지 로직 추가**
   - 루프가 일정 횟수 이상 돌면 종료하거나, 상태 변화를 체크해서 중복 실행을 막으세요.

처음엔 복잡해 보여도, 실제로 해보면 작은 로컬 LLM으로도 꽤 긴 작업을 안정적으로 처리할 수 있다는 걸 알게 될 겁니다.
