## 비디오 생성 API, 왜 백엔드 설계가 이렇게 복잡할까?

최근에 Prism이라는 YC X25 스타트업이 공개한 비디오 생성·편집 API를 보면서, "이걸 백엔드에서 어떻게 설계하고 운영해야 할까?"라는 생각이 들었어요. 단순히 영상 파일을 업로드하고 변환하는 걸 넘어서, 실시간 편집, 다양한 효과 적용, 그리고 안정적인 확장성까지 고려해야 하니까요. 

특히 영상 처리 작업은 CPU와 메모리를 엄청나게 쓰는 계산 집약적 작업이라, 그냥 서버 하나에 다 몰아넣을 수도 없고, 사용자 요청이 몰릴 때마다 튕기면 안 되니까요.

그래서 오늘은 Prism 같은 서비스가 실제로 어떤 백엔드 아키텍처와 운영 전략으로 비디오 생성·편집 API를 구현하고 확장하는지, 제가 공부한 내용을 공유해보려 합니다.

---

## 마이크로서비스로 나누면 비디오 처리도 관리가 쉬워진다

비디오 생성과 편집 기능을 한 덩어리로 묶으면, 서비스가 점점 커질수록 유지보수도 힘들고 확장도 어렵습니다. 그래서 Martin Fowler가 말하는 마이크로서비스 아키텍처를 적용하는 게 유리해요. [Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/)

예를 들어, 비디오 업로드, 편집 명령 처리, 렌더링, 썸네일 생성, 인코딩 등 기능별로 독립적인 서비스로 나누고, 각 서비스가 독자적으로 배포되고 확장될 수 있도록 설계합니다.

이렇게 하면 특정 기능에 부하가 집중될 때 그 부분만 스케일 아웃할 수 있고, 장애가 나도 전체 서비스가 멈추지 않아요. 실제로 Prism도 이런 식으로 기능별로 마이크로서비스를 운영한다고 하네요.

## 클라우드 서버리스와 컨테이너 오케스트레이션으로 비용과 성능 균형 맞추기

비디오 처리 작업은 CPU, GPU 등 리소스 소모가 크고, 사용량이 들쭉날쭉하기 때문에 고정된 서버를 계속 돌리는 건 비용 낭비가 심합니다.

Cloudflare 블로그에서 소개한 사례처럼 [Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/) 서버리스 컴퓨팅과 쿠버네티스 같은 컨테이너 오케스트레이션을 활용하면, 수요에 따라 자동으로 리소스를 늘리고 줄일 수 있어요.

예를 들어, AWS Lambda 같은 서버리스 함수로 간단한 영상 변환 작업을 처리하고, 복잡한 렌더링은 GPU가 달린 컨테이너 클러스터에서 처리하는 식입니다. 

이때 컨테이너는 쿠버네티스의 HPA(Horizontal Pod Autoscaler)를 써서 CPU 사용률이 70% 이상이면 자동으로 파드를 늘리도록 설정하는 게 일반적입니다. 

이런 조합은 비용 효율적이면서도 부하가 갑자기 몰려도 안정적인 처리가 가능하다는 장점이 있어요.

## 이벤트 기반 아키텍처로 비디오 처리 파이프라인 안정성 높이기

비디오 편집 API는 여러 단계의 작업이 순차적 또는 병렬로 진행됩니다. 예를 들어, 편집 명령을 받고, 렌더링 작업 큐에 넣고, 완료되면 후처리하는 식이죠.

GitHub 엔지니어링 블로그에서도 강조하는 것처럼 [GitHub Engineering Blog](https://github.blog/category/engineering/) 이런 복잡한 파이프라인은 이벤트 기반 아키텍처로 설계하는 게 좋아요.

즉, 각 작업 단계가 독립적인 서비스로 이벤트를 발행하고 구독하며 비동기적으로 처리하는 겁니다. 작업 큐(RabbitMQ, Kafka 등)를 두고, 렌더링 작업을 메시지로 보내면 워커가 받아서 처리하는 식이죠.

이 방식은 작업 병목을 줄이고, 장애 발생 시 해당 단계만 재처리하거나 재시도할 수 있어 안정성이 크게 올라갑니다.


```python
# Python 예시: RabbitMQ를 이용해 비디오 렌더링 작업 큐에 작업 보내기
import pika
import json

connection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
channel = connection.channel()
channel.queue_declare(queue='video_render_queue', durable=True)

job = {
    'video_id': 'abc123',
    'edit_instructions': {
        'trim': [10, 50],
        'filters': ['grayscale']
    }
}

channel.basic_publish(
    exchange='',
    routing_key='video_render_queue',
    body=json.dumps(job),
    properties=pika.BasicProperties(delivery_mode=2)  # 메시지 내구성 설정
)

print("[x] Sent video rendering job")
connection.close()
```

이 코드는 비디오 렌더링 작업을 메시지 큐에 넣는 간단한 예시입니다. 실제로는 작업 상태 추적, 재시도 로직, 우선순위 큐 관리 등이 추가되어야 하죠.

## API 게이트웨이와 인증·권한 관리를 분리하는 게 왜 중요할까?

대규모 비디오 편집 API는 보안도 무시할 수 없습니다. 특히 유료 서비스라면 사용자별 권한 관리가 필수고, API 호출 빈도 제한도 필요합니다.

InfoQ에서 권장하는 패턴을 보면 [InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/) API 게이트웨이에서 인증과 권한 관리를 분리하는 게 확장성과 보안 측면에서 유리하다고 합니다.

즉, API 게이트웨이는 요청 라우팅과 기본적인 인증 토큰 검증만 담당하고, 실제 권한 체크는 별도의 권한 관리 서비스에서 처리하는 거죠.

이렇게 하면 권한 정책 변경이 있을 때 API 게이트웨이를 건드리지 않고 권한 서비스만 업데이트하면 되고, 권한 서비스도 독립적으로 확장할 수 있어요.

또한, API 게이트웨이에서 요청 속도 제한(rate limiting)을 걸어 과부하를 막고, 인증 실패 시 빠르게 차단할 수 있습니다.

## 내가 Prism 같은 비디오 API 백엔드를 설계한다면 이렇게 할 것 같다

1. **마이크로서비스로 기능 분리**: 업로드, 편집 명령 처리, 렌더링, 인코딩, 썸네일 생성 등으로 나누고 독립 배포
2. **이벤트 기반 작업 큐 도입**: RabbitMQ나 Kafka로 비디오 처리 작업을 비동기 큐에 넣고 워커가 처리
3. **클라우드 인프라 활용**: 서버리스 함수와 쿠버네티스 오토스케일링 조합으로 비용과 성능 최적화
4. **API 게이트웨이 + 권한 서비스 분리**: 인증은 게이트웨이에서, 권한 관리는 별도 서비스에서 처리

이 중 하나라도 놓치면 확장성이나 안정성, 비용 효율성에서 큰 차이가 납니다. 실제로 Prism의 사례를 보면서 이런 패턴들이 현업에서 얼마나 중요한지 다시 느꼈어요.

---

비디오 생성·편집 API는 단순한 CRUD API와는 완전히 다른 난이도와 설계 고려사항이 많습니다. 계산 집약적인 작업, 복잡한 파이프라인, 보안, 확장성까지 신경 써야 하죠.

하지만 마이크로서비스, 이벤트 기반 아키텍처, 클라우드 오토스케일링, 그리고 분리된 인증·권한 관리 같은 패턴들을 적절히 조합하면, Prism처럼 안정적이고 확장 가능한 서비스를 만들 수 있습니다.

실제로 저도 이런 패턴들을 적용하며 겪은 시행착오가 많은데, 다음에 기회가 되면 구체적인 운영 모니터링과 장애 대응 경험도 공유할게요.
