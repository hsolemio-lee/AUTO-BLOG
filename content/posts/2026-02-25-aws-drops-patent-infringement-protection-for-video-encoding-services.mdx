## 갑작스러운 특허 보호 중단, 우리 서비스는 괜찮을까?

얼마 전 AWS가 비디오 인코딩 서비스에 대해 제공하던 특허 침해 보호 정책을 갑자기 중단했다는 소식을 들었을 때, 우리 팀도 적잖이 당황했어요. ‘그럼 이제 AWS에서 제공하는 인코딩 서비스 쓰는 것만으로도 특허 침해 위험에 노출되는 건가?’라는 질문이 자연스레 나왔죠. 특히 영상 스트리밍이나 VOD 서비스를 운영하는 백엔드 엔지니어라면 이 변화가 단순한 정책 변경 그 이상이라는 걸 직감할 겁니다.

이 글에서는 AWS의 정책 변화가 백엔드 아키텍처에 어떤 의미인지, 그리고 특허 침해 리스크를 줄이기 위해 우리가 실무에서 어떤 설계 전략과 운영 방식을 고민해야 하는지 이야기해보려 합니다.

## AWS 특허 보호 중단, 왜 이렇게 큰 파장이 생겼을까?

AWS는 그동안 비디오 인코딩 서비스에 대해 특허 침해 소송으로부터 고객을 보호하는 정책을 제공해왔습니다. 쉽게 말해, AWS 인코딩 서비스를 쓰면 해당 특허 문제는 AWS가 책임진다는 의미였죠. 그런데 최근 이 보호 정책을 공식적으로 중단하면서, 고객사들이 직접 특허 침해 위험을 관리해야 하는 상황이 됐습니다.

AWS 공식 블로그에 따르면 이런 변화는 특허 관련 법적 책임을 명확히 하고, 고객이 직접 컴플라이언스와 위험 관리를 강화하도록 유도하기 위한 조치라고 합니다([AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/)).

이게 왜 문제냐면, 비디오 인코딩은 MPEG, H.264, HEVC 등 복잡한 특허 풀에 걸려 있어요. AWS가 책임져주던 부분이 사라지면, 우리 서비스에 사용된 인코딩 기술이 혹시라도 특허권을 침해할 경우 직접 소송 위험에 노출될 수 있다는 뜻입니다.

## 특허 위험을 줄이려면 아키텍처에서부터 다르게 접근해야 한다

이제 특허 침해 보호가 없으니, 백엔드 아키텍처를 설계할 때부터 법적 리스크를 고려하는 게 필수가 됐습니다. AWS Well-Architected Framework에서도 보안과 컴플라이언스가 클라우드 설계의 핵심 축임을 강조하고 있죠([AWS Well-Architected Framework](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html)).

### 마이크로서비스로 인코딩 책임 분리하기

예를 들어, 비디오 인코딩 기능을 마이크로서비스로 분리해보세요. 인코딩 관련 로직과 API, 저장소를 독립된 서비스 단위로 떼어내는 겁니다. 이렇게 하면 특허 위험이 있는 부분을 명확히 구분하고, 문제가 생겼을 때 해당 서비스만 빠르게 교체하거나 수정할 수 있어요.

실제로 마틴 파울러도 아키텍처 설계 가이드에서 복잡한 도메인을 분리하고 위험 요소를 국소화하는 패턴을 권장합니다([Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/)).

### 특허 회피 설계 패턴 적용하기

또 한 가지는 특허 회피(design-around) 전략입니다. 예를 들어, 인코딩 알고리즘 중 특허가 걸려있는 부분을 오픈 소스 코덱으로 대체하거나, 자체 개발한 알고리즘으로 바꾸는 방법이죠.

이 과정에서 오픈 소스 코덱을 활용하면 비용도 절감되고, 특허 침해 소송 위험도 줄일 수 있습니다만, 성능이나 품질 면에서 트레이드오프가 있을 수 있다는 점은 감안해야 합니다.

## 실제로 우리 서비스에 적용한 특허 리스크 관리 전략

우리 팀은 AWS 정책 변경 이후, 다음과 같은 단계를 거쳐 아키텍처를 재설계했습니다.

1. **인코딩 서비스 분리 및 컨테이너화**: 기존 모놀리식 서비스에서 인코딩 부분만 별도의 컨테이너화된 마이크로서비스로 분리했습니다. 이를 통해 인코딩 로직 변경 시 전체 서비스 영향도를 최소화했어요.

2. **오픈 소스 코덱 도입 테스트**: x264, x265 같은 오픈 소스 코덱을 실제 영상에 적용해보고 성능과 화질, 인코딩 속도를 비교했습니다. 일부 콘텐츠는 자체 코덱으로도 충분히 커버 가능하다는 결론을 얻었죠.

3. **라이선스 및 특허 모니터링 체계 구축**: 인코딩 라이브러리와 관련된 라이선스 상태를 주기적으로 점검하는 자동화 스크립트를 만들었습니다. 예를 들어, GitHub Actions를 활용해 의존성 라이선스 변경사항을 감지하는 식입니다.

### 라이선스 모니터링 예시 코드

```bash
# SPDX 라이선스 정보를 정기적으로 확인하는 간단한 스크립트 예시
# 매주 실행하여 라이선스 변경 감지

npm install -g license-checker

license-checker --json > licenses.json

diff licenses.json licenses_last_week.json > license_diff.txt || echo "No changes"

mv licenses.json licenses_last_week.json
```

이 스크립트는 `license-checker`라는 npm 패키지를 이용해 현재 프로젝트 의존성의 라이선스 정보를 JSON 형태로 추출하고, 이전 주차와 비교해 변경된 부분을 알려줍니다. 이렇게 하면 인코딩 관련 라이브러리가 갑자기 라이선스가 바뀌거나 특허 문제가 될 수 있는 코드가 포함됐는지 빠르게 파악할 수 있습니다.

## 공급망 관리 관점에서 특허 정책 변화가 주는 숙제

특히 클라우드 플랫폼에서 라이브러리나 서비스 공급망이 복잡해지면서, 특허 정책 변경은 단순히 우리 코드만의 문제가 아닙니다. 인코딩에 쓰이는 외부 라이브러리, 서드파티 API, 심지어 컨테이너 이미지까지도 라이선스와 특허 상태를 꼼꼼히 관리해야 하죠.

InfoQ에서 다룬 아키텍처 및 설계 관련 글에서도 공급망 관리가 점점 중요해지고, 법적 리스크 관리가 아키텍처 설계의 한 축으로 자리 잡아야 한다고 지적합니다([InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/)).

우리 팀은 다음과 같은 프로세스를 도입했습니다.

- **서드파티 라이브러리 승인 프로세스 강화**: 신규 라이브러리 도입 시 법무팀과 협업해 특허 및 라이선스 검토를 의무화
- **컨테이너 이미지 스캔 자동화**: 이미지 빌드 파이프라인에 보안 및 라이선스 스캔 도구 통합
- **정기적인 아키텍처 리뷰 세션**: 특허 정책 변화에 따른 아키텍처 영향 평가 및 대응책 논의

## 마지막으로, 특허 위험에 대응하는 우리만의 팁

- **특허 보호가 사라졌다고 해서 당장 모든 걸 바꿀 필요는 없다**: 우선 현재 서비스가 어떤 특허에 노출될 가능성이 있는지 기술적, 법적 검토를 해보세요.

- **마이크로서비스로 위험 분산은 필수**: 인코딩뿐 아니라 특허 관련 기능을 분리해두면, 문제가 생겨도 빠르게 격리하고 대응할 수 있습니다.

- **오픈 소스 코덱과 자체 알고리즘을 병행해보자**: 완전히 특허 회피가 어려우면, 리스크를 분산하는 차원에서 여러 옵션을 동시에 운영하는 것도 방법입니다.

- **라이선스 모니터링 자동화는 투자 대비 효과가 크다**: 매주 혹은 매월 의존성 라이선스 변화를 체크하는 스크립트를 꼭 도입하세요.

- **법무팀과 긴밀한 협업 없이는 위험 관리가 어렵다**: 기술팀 혼자 판단하기 힘든 부분이 많으니, 정기적으로 소통하는 채널을 마련하세요.

이번 AWS 정책 변화는 단순히 클라우드 서비스 하나의 정책 변경이 아니라, 비디오 인코딩 서비스 아키텍처 전반에 걸친 법적, 기술적 리스크 관리 패러다임을 바꾸는 신호탄입니다. 실제로 겪어보면, 특허 문제는 기술적 문제만큼이나 복잡하고 까다롭다는 걸 절감하게 될 거예요. 하지만 미리 준비하고, 아키텍처 설계 단계부터 법적 컴플라이언스를 염두에 둔다면 충분히 안전하게 서비스를 운영할 수 있습니다.

우리 모두 이번 기회에 특허와 라이선스 문제를 단순한 법무 이슈가 아니라, 백엔드 아키텍처 설계의 중요한 요소로 인식하는 계기로 삼았으면 합니다.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
