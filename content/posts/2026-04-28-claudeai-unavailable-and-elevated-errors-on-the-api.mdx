## 갑자기 Claude.ai API가 안 될 때, 우리 서비스는 어떻게 버텨야 할까?

얼마 전, 우리 서비스에서 Claude.ai API 호출이 갑자기 실패하는 일이 잦아졌어요. 대규모 트래픽이 몰린 것도 아닌데, 내부 장애인지 응답이 지연되거나 503 에러가 뜨는 상황이 반복됐죠. 이걸 겪으면서 ‘AI API가 불안정할 때 백엔드가 어떻게 대응해야 할까?’ 고민이 깊어졌습니다.

Claude.ai API는 대규모 트래픽과 모델 운영 복잡성 때문에 일시적으로 사용 불가 상태가 되거나 오류 발생률이 올라가는 게 자연스러운 현상이라고 하더군요. Anthropic 공식 문서에서도 이런 부하 변동과 장애 가능성을 명확히 언급하고 있어요[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

그럼 이런 상황에서 백엔드는 어떻게 설계해야 할까요? 제가 직접 적용해보고 느낀 점과 함께 실제 코드 예시도 공유해봅니다.

## 장애 상황에서 무작정 재시도만 하면 안 되는 이유

처음엔 API 호출 실패가 발생하면 단순히 재시도 로직만 넣었어요. 그런데 문제는, 재시도를 너무 빠르고 무한정 하다 보니 오히려 API 서버에 부하를 더 주고, 장애가 더 심해지는 악순환이 발생했습니다.

그래서 도입한 게 바로 **지수적 백오프(exponential backoff)** 입니다. 실패할 때마다 재시도 간격을 점점 늘려서 서버가 회복할 시간을 주는 거죠. 여기에 **회로 차단기(circuit breaker)** 패턴을 더해 일정 횟수 이상 실패하면 일정 시간 동안 아예 호출을 중단해서 무의미한 요청을 막았습니다.

Martin Fowler의 아키텍처 가이드에서도 이 패턴을 강력 추천하고 있죠[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

```java
// Spring에서 RestTemplate과 Resilience4j 회로 차단기 + 재시도 적용 예시
@Bean
public RestTemplate restTemplate() {
    return new RestTemplate();
}

// Resilience4j 설정
CircuitBreaker circuitBreaker = CircuitBreaker.of("claudeApiCircuitBreaker",
    CircuitBreakerConfig.custom()
        .failureRateThreshold(50) // 실패율 50% 넘으면 열림
        .waitDurationInOpenState(Duration.ofSeconds(30)) // 30초 후 half-open
        .slidingWindowSize(10)
        .build());

Retry retry = Retry.of("claudeApiRetry",
    RetryConfig.custom()
        .maxAttempts(5)
        .waitDuration(Duration.ofMillis(500))
        .intervalFunction(IntervalFunction.ofExponentialBackoff(500, 2))
        .build());

public String callClaudeApiWithResilience() {
    Supplier<String> decoratedSupplier = CircuitBreaker.decorateSupplier(circuitBreaker, () -> {
        // 실제 Claude.ai API 호출
        return restTemplate().getForObject("https://api.claude.ai/v1/query", String.class);
    });

    decoratedSupplier = Retry.decorateSupplier(retry, decoratedSupplier);

    try {
        return Try.ofSupplier(decoratedSupplier).get();
    } catch (Exception e) {
        // fallback 처리
        return "서비스 일시 중단 상태입니다.";
    }
}
```

이렇게 하면 장애가 심할 때는 재시도 시도를 줄이고, 회로 차단기가 열려서 빠르게 실패를 감지해 사용자에게 빠른 피드백을 줄 수 있습니다.

## 핵심 기능만 살리고 나머지는 잠시 쉬게 하는 'graceful degradation'

Claude.ai API가 불안정해지면 우리 서비스 전체가 멈추는 게 아니라, 핵심 기능은 유지하고 부가 기능만 잠시 중단하는 게 중요해요. 이걸 **graceful degradation**이라고 합니다.

Cloudflare 블로그에서도 대규모 서비스 장애 시 핵심 기능 유지에 집중하는 전략을 자세히 설명하는데[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/), 실제로 우리도 다음과 같은 방식을 적용했습니다:

- AI 기반 추천 기능은 최소한의 캐시된 결과로 대체
- 비핵심 통계 집계, 로그 전송 등은 비동기 큐에 쌓아두고 장애 복구 후 처리
- 사용자에게는 "일부 기능이 제한될 수 있습니다"라는 안내 메시지 제공

이렇게 하면 API가 잠시 안 되더라도 사용자 경험이 완전히 무너지지 않고, 서비스 전체가 멈추는 걸 막을 수 있죠.

## Spring 백엔드에서 비동기 큐를 활용해 장애 시 요청 누락 줄이기

Claude.ai API 호출이 실패하면, 단순히 실패 응답을 돌려주는 것보다 **비동기 큐잉 시스템**에 요청을 저장해두고 나중에 재처리하는 게 훨씬 안정적입니다. 특히 Spring 기반 백엔드에서는 RabbitMQ, Kafka 같은 메시지 큐를 쉽게 연동할 수 있죠.

예를 들어, AI 요청을 큐에 넣는 간단한 코드:

```java
@Autowired
private RabbitTemplate rabbitTemplate;

public void enqueueClaudeRequest(String requestPayload) {
    rabbitTemplate.convertAndSend("claudeRequestQueue", requestPayload);
}

// 큐에서 꺼내 처리하는 리스너
@RabbitListener(queues = "claudeRequestQueue")
public void processClaudeRequest(String requestPayload) {
    try {
        // Claude.ai API 호출
        String response = callClaudeApi(requestPayload);
        // 결과 처리
    } catch (Exception e) {
        // 실패 시 재큐잉 또는 별도 에러 처리
    }
}
```

이렇게 하면 API가 일시적으로 불안정해도 요청이 사라지지 않고, 백그라운드에서 천천히 처리할 수 있어요. InfoQ에서도 이런 비동기 설계가 장애 대응에 효과적이라고 소개합니다[InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/).

## 프론트엔드와 협업: API 오류 시 사용자 경험을 어떻게 지킬까?

백엔드에서 아무리 잘 처리해도, 결국 프론트엔드에서 사용자에게 에러가 보이면 경험이 나빠집니다. GitHub 엔지니어링 블로그에서는 API 오류 발생 시 명확한 오류 메시지 전달과 자동 재시도, 대체 UI 제공 전략을 권장합니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

예를 들어, 프론트엔드에서 Claude.ai API 호출 실패 시:

- "잠시 AI 기능이 불안정합니다. 잠시 후 다시 시도해주세요."라는 친절한 메시지 표시
- 자동으로 3회 재시도 시도
- 핵심 기능은 유지하되, AI 결과가 없어도 최소한의 기본 UI 제공

이런 조합이 사용자 불만을 크게 줄여줍니다.

## 마치며: Claude.ai API 장애 대응, 결국은 '조금씩 천천히'가 답

Claude.ai 같은 AI 서비스는 내부 모델 복잡성과 트래픽 변동으로 인해 완벽한 안정성을 보장하기 어렵습니다. 그래서 백엔드에서 무조건 빠르게 재시도하거나 모든 기능을 다 살리려 하기보다는:

- 실패 시 지수적 백오프와 회로 차단기로 무리한 호출을 막고
- 핵심 기능 중심으로 graceful degradation을 적용하며
- 비동기 큐잉으로 부하를 분산시키고
- 프론트엔드와 협력해 사용자 경험 저하를 최소화하는 게 현실적인 해법입니다.

직접 적용해보니, 이런 패턴을 도입한 뒤 장애 시 복구 속도가 눈에 띄게 빨라졌고, 사용자 불만도 줄었어요. 혹시 Claude.ai API를 백엔드에서 다루는 분들이라면 꼭 한번 고민해보시길 바랍니다.
