## 프로덕션에서 성능 튜닝, Spring Boot 3.2가 달라진 점

최근에 우리 팀에서 Spring Boot 3.2로 업그레이드하면서 가장 먼저 체감한 건 바로 내장된 메트릭 수집 기능이었어요. 예전에는 Micrometer 설정을 직접 꼼꼼히 다듬어야 했는데, 이번 버전부터는 애플리케이션의 CPU, 메모리 사용량과 응답 시간 같은 주요 지표를 실시간으로 모니터링할 수 있는 기본 기능이 훨씬 강화됐더라고요.

특히 `management.metrics.enable` 설정이 기본 활성화되어 있고, Prometheus나 Grafana 같은 도구와 연동도 훨씬 수월해졌습니다. 우리 환경에서는 JVM GC 시간과 HTTP 요청 지연 시간을 1분 단위로 집계해서 대시보드에 띄우는데, 덕분에 문제 발생 시점 파악이 훨씬 빨라졌어요.

```yaml
management:
  metrics:
    enable:
      all: true
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
```

이 설정만으로도 프로덕션에서 성능 병목 구간을 빠르게 찾아내고, 리소스 낭비를 줄이는 데 큰 도움이 됩니다. 물론, 모니터링 데이터가 많아지면 네트워크나 저장소 부담이 커질 수 있으니, 필요한 메트릭만 선별해서 수집하는 게 좋습니다.

## OAuth 2.1 지원, Spring Framework 6.1에서 보안이 더 쉬워졌다

보안 쪽에서는 Spring Framework 6.1이 큰 변화를 가져왔죠. OAuth 2.1 표준이 기본 내장되어서, 예전처럼 별도의 라이브러리나 복잡한 설정 없이도 최신 인증 방식을 바로 적용할 수 있게 됐어요. 

우리 프로젝트도 최근에 소셜 로그인과 API 권한 관리를 OAuth 2.1 기반으로 전환했는데, `spring-security-oauth2-client` 모듈만 추가하면 기본적인 인증 흐름이 바로 작동했습니다. 예를 들어, 구글 OAuth 인증을 설정할 때는 이렇게 간단합니다:

```java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            .anyRequest().authenticated()
        )
        .oauth2Login();
    return http.build();
}

@Bean
public ClientRegistrationRepository clientRegistrationRepository() {
    return new InMemoryClientRegistrationRepository(
        CommonOAuth2Provider.GOOGLE.getBuilder("google")
            .clientId("your-client-id")
            .clientSecret("your-client-secret")
            .build()
    );
}
```

이게 실제로 해보면 생각보다 훨씬 간단하고, Spring Security의 보안 패치도 자동으로 반영되니 안심할 수 있더라고요. 다만 OAuth 2.1은 이전 버전과 호환되지 않는 부분도 있으니, 기존 OAuth 2.0 기반 코드는 꼼꼼히 테스트해야 합니다.

## GC 튜닝과 HikariCP 설정, 프로덕션 성능에 미치는 영향

Baeldung 가이드에 따르면, JVM GC 튜닝과 커넥션 풀 최적화가 Spring Boot 애플리케이션 성능에 직결된다고 하더군요. 우리도 이번에 GC 로그를 분석해서 `-XX:+UseG1GC` 옵션과 함께 `-XX:MaxGCPauseMillis=200`으로 설정했는데, 평균 응답 시간이 15% 정도 줄었어요.

커넥션 풀은 기본값인 HikariCP를 그대로 쓰면서도, `maximumPoolSize`를 실제 트래픽에 맞춰 50에서 100으로 늘렸습니다. 이 설정은 데이터베이스 커넥션 부족으로 인한 대기 시간을 줄이는 데 효과적이었죠.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 100
      minimum-idle: 20
      idle-timeout: 30000
      max-lifetime: 1800000
```

처음엔 이게 별거 아닌 것 같지만, 실제 서비스 트래픽이 몰릴 때 커넥션 풀 크기가 너무 작으면 요청이 대기 상태로 쌓이면서 전체 응답 속도가 뚝 떨어집니다. GC 튜닝도 마찬가지로, 너무 잦은 Full GC가 발생하면 서버가 멈춘 것처럼 느껴질 수 있으니 로그를 주기적으로 모니터링하는 게 중요해요.

## 마이크로서비스 배포, 카나리 전략으로 무중단 배포 경험하기

GitHub 엔지니어링 블로그에서 소개한 카나리 배포 전략은 우리 팀이 마이크로서비스를 운영하면서 적용해본 결과 정말 효과적이었어요. 신규 버전을 전체에 한꺼번에 배포하는 대신, 트래픽의 5%만 새 버전으로 보내고 모니터링하다가 문제 없으면 점차 늘리는 방식입니다.

이렇게 하면 배포 실패 시 빠르게 롤백할 수 있고, 사용자 영향도 최소화할 수 있죠. 실제로 우리는 Istio와 같은 서비스 메쉬를 활용해 트래픽 분배를 제어했고, 배포 자동화 파이프라인에 Slack 알림과 모니터링 대시보드를 연동해 실시간으로 상태를 확인했습니다.

단, 카나리 배포는 모니터링과 롤백 체계가 잘 갖춰져 있어야 의미가 있으니, 로그와 메트릭 수집에 신경 써야 합니다.

## TLS 세션 재사용과 캐시 전략으로 보안과 성능 두 마리 토끼 잡기

Cloudflare 블로그에서 본 사례처럼, 대규모 분산 시스템에서는 TLS 세션 재사용이 성능 최적화에 큰 도움이 됩니다. Spring 기반 백엔드에서도 `server.ssl.session-cache-size`와 `server.ssl.session-timeout` 설정을 조정해서 세션 캐시를 적절히 유지할 수 있어요.

```yaml
server:
  ssl:
    enabled: true
    key-store: classpath:keystore.p12
    key-store-password: changeit
    key-store-type: PKCS12
    session-cache-size: 10000
    session-timeout: 300
```

이렇게 하면 TLS 핸드셰이크 비용이 줄어들어 HTTPS 요청 처리 속도가 개선되고, 동시에 보안 수준도 유지할 수 있습니다. 물론, 세션 캐시 크기를 너무 크게 잡으면 메모리 부담이 커질 수 있으니 적절한 균형이 필요합니다.

- JVM GC 튜닝과 HikariCP 커넥션 풀 설정은 프로덕션 성능 최적화의 기본 중 기본.
