## SSH 대신 REST API, Slack EMR 파이프라인에서 무슨 일이?

"왜 아직도 SSH로 작업을 실행하고 있지?" 어느 날 우리 팀에서 이런 질문이 나왔을 때, 사실 나도 처음엔 그게 별거 아닌 것처럼 들렸어. 그런데 Slack이 700개가 넘는 EMR(Elastic MapReduce) 작업을 SSH 기반에서 REST API 기반으로 완전히 갈아엎었다는 걸 알게 되면서 생각이 달라졌지. 이게 단순히 프로토콜 바꾼 게 아니라, 백엔드 신뢰성과 확장성에 얼마나 큰 변화를 가져오는지 직접 눈으로 확인한 사례였거든.

## SSH에서 REST API로 옮기면서 얻은 가장 큰 변화

기존에 SSH 기반으로 EMR 작업을 실행하면, 네트워크 연결 문제나 인증 실패가 곧바로 전체 파이프라인 장애로 이어지는 경우가 많았어. SSH는 기본적으로 세션 연결이 필요한데, 이 연결이 끊기면 작업 상태 추적도 어려워지고 장애 격리도 힘들었거든. 반면 REST API는 HTTP 기반이라 상태 관리와 재시도가 훨씬 수월하고, 장애가 발생해도 서비스 간 독립성이 보장돼서 한쪽 문제가 전체를 무너뜨리지 않아.

Slack은 이걸 실제로 적용하면서 700개 이상의 EMR 작업을 REST API 호출로 바꿨는데, 네트워크 관리도 간소화되고 인증 토큰 기반으로 바뀌면서 보안도 강화됐어. 이 과정에서 API Gateway와 Circuit Breaker 같은 클라우드 디자인 패턴을 적극 활용했는데, 이게 서비스 간 통신 안정성을 크게 끌어올리는 데 핵심 역할을 했지.[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/)

## API Gateway와 Circuit Breaker, 이게 왜 중요할까?

Slack 사례에서 특히 인상 깊었던 점은 API Gateway를 통해 모든 EMR 작업 요청을 중앙에서 관리했다는 거야. 이렇게 하면 인증, 로깅, 트래픽 제어 같은 공통 기능을 한 곳에서 처리할 수 있어서 각 서비스가 가벼워지고 배포도 독립적으로 할 수 있지.

그리고 Circuit Breaker 패턴을 적용해, 만약 어떤 EMR 작업 API가 장애를 일으키면 즉시 호출을 차단하고 빠르게 실패를 반환해 전체 시스템이 느려지는 걸 막았어. 이 덕분에 장애 격리가 명확해지고, 복구도 빨라졌지. 실제로 Slack은 이 패턴 덕분에 파이프라인 장애 시 평균 복구 시간이 30% 이상 단축됐다고 해.

## CI/CD와 REST API 전환, 개발 속도도 빨라졌다

Slack의 REST API 전환은 단순히 통신 방식을 바꾼 게 아니라, 지속적 통합(CI)과 지속적 배포(CD) 파이프라인과도 긴밀히 연동됐어. REST API는 HTTP 요청만으로 쉽게 테스트할 수 있어서, GitHub Actions 같은 CI/CD 도구와 궁합이 정말 잘 맞더라고.[GitHub Actions Documentation](https://docs.github.com/en/actions)

예를 들어, 새로운 EMR 작업을 추가하거나 API를 수정할 때마다 자동으로 통합 테스트가 돌고, 문제 없으면 바로 배포까지 이어지는 구조를 만들었어. 덕분에 개발자들이 변경 사항을 빠르게 검증하고 배포할 수 있게 되어 전체 파이프라인의 민첩성과 신뢰성이 크게 올라갔지.

## 실무에 바로 써먹는 REST API 호출 패턴 예제

아래는 EMR 작업을 REST API로 호출할 때 자주 사용하는 재시도 로직을 포함한 간단한 파이썬 코드야. 실제 Slack 사례처럼 네트워크 불안정이나 일시적 오류에 대비해 재시도와 오류 처리를 넣는 게 핵심 포인트야.

```python
import requests
import time

class EMRJobClient:
    def __init__(self, base_url, token):
        self.base_url = base_url
        self.headers = {'Authorization': f'Bearer {token}'}

    def submit_job(self, job_id, payload):
        url = f'{self.base_url}/jobs/{job_id}/run'
        retries = 3
        backoff = 2

        for attempt in range(1, retries + 1):
            try:
                response = requests.post(url, json=payload, headers=self.headers, timeout=10)
                response.raise_for_status()
                return response.json()
            except requests.RequestException as e:
                print(f'Attempt {attempt} failed: {e}')
                if attempt == retries:
                    raise
                time.sleep(backoff ** attempt)

# 사용 예
client = EMRJobClient('https://api.slack-emr.com', 'your_api_token_here')
payload = {'input': 's3://bucket/data.csv', 'config': {'mapper': 'map.py', 'reducer': 'reduce.py'}}

try:
    result = client.submit_job('job123', payload)
    print('Job submitted successfully:', result)
except Exception as e:
    print('Failed to submit job:', e)
```

이 코드는 실패 시 지수 백오프로 재시도하고, 마지막에 실패하면 예외를 던져 호출자에게 알려줘. 이런 패턴이 REST API 기반 EMR 작업 실행에서 신뢰성을 높이는 데 필수적이야.

## REST API 전환의 숨은 단점도 알아두자

물론 REST API 전환이 만능은 아니야. SSH처럼 직접 서버에 접속하는 게 아니니, 실시간 로그 확인이나 디버깅이 좀 더 까다로워질 수 있어. 또, API 설계가 잘못되면 오히려 복잡도가 올라가고 유지보수가 어려워질 수도 있지.

Slack도 이 부분을 해결하기 위해 API 문서화와 모니터링, 그리고 로깅 시스템에 상당한 투자를 했어. 특히 API Gateway에서 요청과 응답을 모두 로깅하고, 장애 발생 시 빠르게 원인을 파악할 수 있도록 했던 점이 인상적이었지.

## 마무리하며

Slack의 EMR 파이프라인 SSH 제거와 REST API 마이그레이션 사례는 단순한 기술 교체가 아니라, 백엔드 신뢰성과 확장성을 획기적으로 개선한 좋은 본보기야. 특히 API Gateway와 Circuit Breaker 같은 클라우드 디자인 패턴을 적극 활용하고, CI/CD 파이프라인과 연동해 개발 민첩성까지 잡은 점은 우리 실무에도 큰 시사점을 준다고 생각해.

이 글을 읽고 나면, SSH로 무거운 작업 관리하는 게 얼마나 리스크인지, 그리고 REST API 기반 아키텍처가 왜 대세인지 조금은 감이 올 거야. 나도 Slack 사례를 참고해 우리 파이프라인에 재시도 로직과 API Gateway 패턴을 적용해봤는데, 실제로 장애 복구 속도가 눈에 띄게 빨라졌거든.

작은 변화 같아도, 이런 인프라 개선이 결국 개발자 경험과 서비스 안정성에 큰 차이를 만들더라고. 여러분도 한 번 시도해보길 추천할게.
