## "내장 톰캣 덕분에 개발 속도가 이렇게 빨라질 줄은 몰랐어요"

처음 Spring Boot를 만났을 때 가장 놀랐던 부분이 바로 내장 톰캣 서버와 자동 구성 기능이었어요. 복잡한 XML 설정이나 수동 빈 등록 없이도 바로 애플리케이션을 띄울 수 있다는 게 실무에서 얼마나 큰 시간 절약인지 경험해보면 압니다. 필 웹브가 직접 말하길, "Spring Boot는 신속한 개발과 배포를 위해 설계됐다"고 하죠. 실제로 기본 설정만으로도 톰캣 서버가 내장되어 있고, `@SpringBootApplication` 하나면 자동으로 필요한 빈들이 등록됩니다[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

예를 들어, 아래처럼 간단한 REST API를 만들 때도 별도의 서버 설정은 필요 없어요.

```java
@SpringBootApplication
@RestController
public class DemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }

    @GetMapping("/hello")
    public String hello() {
        return "Hello, Spring Boot!";
    }
}
```

이 코드를 실행하면 내장 톰캣 서버가 8080 포트에서 바로 뜨고, `/hello` 요청에 응답합니다. 처음엔 이게 별거 아닌 것 같지만, 복잡한 프로젝트에서 이 자동화가 주는 개발 속도는 정말 체감됩니다.

## JVM 튜닝부터 커넥션 풀까지, 프로덕션 성능 최적화는 이렇게

필 웹브가 강조하는 부분 중 하나는 "프로덕션 환경에서의 성능 튜닝"입니다. Spring Boot는 단순히 빨리 개발하는 데 그치지 않고, 실제 서비스에서 안정적이고 빠른 응답성을 유지하도록 다양한 옵션을 제공합니다. JVM 튜닝, 커넥션 풀 관리, 캐싱 전략이 대표적이죠.

예를 들어, HikariCP 커넥션 풀을 기본으로 제공하는데, 기본 설정이 꽤 괜찮지만 서비스 특성에 맞게 조정하는 게 중요합니다. 다음은 `application.yml`에서 커넥션 풀을 조정하는 예시입니다.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 30  # 기본 10에서 늘려서 동시 DB 연결을 확장
      minimum-idle: 10
      idle-timeout: 600000  # 10분
      max-lifetime: 1800000  # 30분
      connection-timeout: 30000  # 30초
```

이렇게 설정하면 동시 접속자가 많을 때 DB 커넥션 부족으로 인한 대기 현상을 줄일 수 있어요. 물론 너무 크게 잡으면 DB 부하가 커질 수 있으니, 실제 트래픽과 DB 성능을 고려해 조절해야 합니다.

또 JVM 힙 사이즈와 가비지 컬렉션 튜닝도 병행해야 하는데, 필 웹브가 말하길 "GC 튜닝은 서비스 특성에 따라 달라지므로, 프로파일링 도구를 적극 활용하라"고 하더군요. `-Xms4g -Xmx4g -XX:+UseG1GC` 같은 옵션으로 시작해, 실제 메모리 사용 패턴을 보고 조정하는 게 좋습니다.

캐싱도 빼놓을 수 없는데, Spring Boot는 `@Cacheable` 애노테이션으로 간단히 메서드 결과를 캐싱할 수 있습니다. 예를 들어,

```java
@Cacheable("users")
public User getUserById(Long id) {
    // DB 조회 로직
}
```

이렇게 하면 동일한 ID 조회 시 DB를 매번 호출하지 않고 캐시에서 바로 꺼내와 응답 속도를 크게 단축시킬 수 있죠.

## Spring Security와 프로파일로 나누는 유연한 보안 관리

보안은 백엔드에서 절대 소홀히 할 수 없는 부분입니다. Spring Boot는 Spring Security와 완벽하게 통합되어 있어, 인증과 권한 부여를 기본적으로 지원합니다.

필 웹브가 강조하는 팁 중 하나는 "보안 설정을 프로파일별로 분리해 관리하라"는 점입니다. 예를 들어 개발 환경과 운영 환경에서 다른 인증 방식을 쓰거나, 특정 API 접근 정책을 다르게 적용할 때 유용하죠.

아래는 `SecurityConfig`를 프로파일별로 분리한 예시입니다.

```java
@Configuration
@Profile("prod")
public class ProdSecurityConfig extends WebSecurityConfigurerAdapter {
    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
            .authorizeRequests()
                .antMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            .and()
            .httpBasic();
    }
}

@Configuration
@Profile("dev")
public class DevSecurityConfig extends WebSecurityConfigurerAdapter {
    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http.csrf().disable()
            .authorizeRequests().anyRequest().permitAll();
    }
}
```

이렇게 하면 `-Dspring.profiles.active=prod`로 운영 환경에서 실행할 때는 엄격한 보안 정책이 적용되고, 개발 환경에서는 인증 없이 편리하게 테스트할 수 있습니다.

## 점진적 배포와 피처 토글로 대규모 서비스 안정적으로 운영하기

대규모 서비스 운영 경험이 있는 분이라면 한 번쯤은 "배포 후 장애로 인한 서비스 중단"의 공포를 겪어봤을 겁니다. 필 웹브도 이 부분을 매우 중요하게 생각하는데, 그래서 Spring Boot 생태계에서는 점진적 배포(gradual rollout)와 피처 토글(feature toggle)을 적극 권장합니다.

점진적 배포는 전체 사용자 중 일부에게만 새 버전을 먼저 노출해 문제 발생 시 빠르게 롤백하거나 수정할 수 있도록 하는 전략입니다. 예를 들어 쿠버네티스 환경에서 `Deployment`의 `maxSurge`와 `maxUnavailable` 설정을 이용해 트래픽 일부만 새 버전으로 전환하는 식이죠.

피처 토글은 코드 내에서 특정 기능을 켜고 끌 수 있게 만들어, 운영 중에도 위험한 기능을 비활성화하거나 점진적으로 활성화할 수 있습니다. Spring Boot에서는 `spring-cloud-feature-toggle` 같은 라이브러리를 활용할 수 있는데, 간단한 예시는 다음과 같습니다.

```java
@Component
public class FeatureService {

    @Value("${feature.newCheckout:false}")
    private boolean newCheckoutEnabled;

    public void processCheckout() {
        if (newCheckoutEnabled) {
            // 새로운 결제 로직
        } else {
            // 기존 결제 로직
        }
    }
}
```

운영 중에 `application-prod.yml`에서 `feature.newCheckout` 값을 변경하면, 재배포 없이도 기능 활성화 여부를 조절할 수 있어 운영 유연성이 크게 향상됩니다.

## 의존성 주입과 AOP로 유지보수 쉬운 대규모 백엔드 만들기

Spring Framework의 핵심 기술인 의존성 주입(DI)과 AOP는 Spring Boot에서도 그대로 활용됩니다. 필 웹브가 말하길, "이 두 가지는 모듈화된 코드 작성과 유지보수를 쉽게 하는 비장의 무기"라고 하더군요.

DI 덕분에 컴포넌트 간 결합도가 낮아지고, 테스트도 훨씬 편해집니다. 예를 들어, 서비스 클래스에 DAO를 주입하는 코드는 이렇게 간단하죠.

```java
@Service
public class UserService {

    private final UserRepository userRepository;

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public User findUser(Long id) {
        return userRepository.findById(id).orElse(null);
    }
}
```

AOP는 공통 관심사를 분리해 로깅, 트랜잭션 관리, 보안 검사 등을 코드 중복 없이 처리할 수 있게 해줍니다. 예를 들어, 메서드 실행 시간을 측정하는 간단한 AOP는 다음과 같습니다.

```java
@Aspect
@Component
public class PerformanceAspect {

    @Around("execution(* com.example.service.*.*(..))")
    public Object logExecutionTime(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.currentTimeMillis();
        Object proceed = joinPoint.proceed();
        long duration = System.currentTimeMillis() - start;
        System.out.println(joinPoint.getSignature() + " executed in " + duration + "ms");
        return proceed;
    }
}
```

이런 패턴을 잘 활용하면, 대규모 백엔드도 체계적으로 관리할 수 있습니다[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

---

필 웹브가 직접 들려준 이야기들을 정리해보면, Spring Boot는 단순히 빠른 개발 도구가 아니라, 프로덕션 환경에서 안정적이고 효율적인 백엔드 운영을 위한 다양한 기능과 패턴을 내장하고 있다는 점이 인상적입니다. 내장 톰캣과 자동 구성 덕분에 개발 초기 진입 장벽이 낮고, JVM과 커넥션 풀 튜닝으로 성능을 최적화하며, Spring Security와 프로파일 분리로 보안을 체계적으로 관리할 수 있죠. 여기에 점진적 배포와 피처 토글로 대규모 서비스도 무리 없이 운영할 수 있습니다.

이걸 직접 경험해보면, "아 이래서 Spring Boot가 이렇게 사랑받는구나" 하는 생각이 절로 듭니다.
