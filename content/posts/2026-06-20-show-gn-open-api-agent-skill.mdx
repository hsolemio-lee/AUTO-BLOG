## 토스증권 Open API와 대화형 Agent Skill, 왜 도전해볼 만한가

"API 연동하는 건 다 거기서 거기 아니야?"라고 생각했는데, 토스증권 Open API를 활용해 실시간 금융 데이터를 다루는 Agent Skill을 만들면서 생각이 좀 바뀌었어요. 단순히 API 호출만 하면 되는 게 아니라, 사용자 질문 의도를 정확히 파악하고, 안정적인 인증 관리, 그리고 빠른 응답을 위한 캐싱과 비동기 처리까지 신경 써야 하더라고요.

특히 금융 서비스 특성상 보안과 오류 처리에 민감한데, 이 부분을 놓치면 서비스 신뢰도가 바로 떨어집니다. 그래서 이번 글에서는 제가 직접 구현하며 깨달은 실무 팁과 아키텍처 고민을 공유하려고 합니다.


## 토큰 관리와 요청 최적화, OpenAI API 문서에서 배운 핵심

Agent Skill을 만들 때 가장 먼저 부딪힌 벽은 인증과 토큰 관리였어요. 토스증권 Open API는 OAuth 2.0 기반 인증을 사용하는데, 액세스 토큰 만료 시 재발급 로직이 필수입니다. OpenAI API 문서에서 권장하는 토큰 관리 방식을 참고했는데, 이게 정말 도움이 됐어요. 

- 액세스 토큰 만료 5분 전에 미리 갱신
- 토큰 갱신 실패 시 재시도 로직과 사용자 알림
- 요청 시 토큰 헤더 자동 삽입

이런 기본기를 탄탄히 하니까 인증 오류로 인한 서비스 중단이 거의 없었어요. 그리고 요청 최적화를 위해 API 호출을 묶거나, 자주 변하지 않는 정보는 캐싱하는 전략도 필수입니다. 예를 들어, 사용자의 계좌 정보는 10분 단위로 캐시해서 API 호출 횟수를 30% 이상 줄였어요.

```java
// Spring Boot 예시: 토큰 만료 5분 전 자동 갱신
@Scheduled(fixedDelay = 300000) // 5분마다 실행
public void refreshTokenIfNeeded() {
    if (tokenExpiryTime.minusMinutes(5).isBefore(Instant.now())) {
        try {
            String newToken = authService.refreshAccessToken(refreshToken);
            accessToken = newToken;
            tokenExpiryTime = Instant.now().plusSeconds(3600); // 1시간 유효
        } catch (Exception e) {
            log.error("토큰 갱신 실패", e);
            // 알림 처리
        }
    }
}
```

이 코드는 실제로 서비스에서 돌리면서 토큰 만료로 인한 장애를 거의 없앴습니다. 물론, 토큰 갱신 실패 시 사용자에게 재로그인 안내를 하는 UX도 꼭 챙겨야 해요.


## 프롬프트 설계는 Anthropic 가이드처럼, 단계별로 명확하게

Agent Skill의 핵심은 결국 사용자 질문을 정확히 이해하고, 적절한 API 호출로 연결하는 거잖아요. 이 부분에서 Anthropic의 프롬프트 엔지니어링 가이드가 큰 도움이 됐습니다. 단순히 질문을 그대로 API에 넘기는 게 아니라, 의도를 분명하게 하고, 필요한 정보를 단계별로 묻는 방식을 적용했죠.

예를 들어, "내 계좌 잔액 알려줘"라는 질문에 바로 API 호출하기보다, 먼저 어떤 계좌인지 확인하는 추가 질문을 넣습니다. 이렇게 하면 오탐율이 확 줄어요.

```plaintext
User: 내 증권 계좌 잔액 알려줘
Agent: 어떤 증권 계좌를 말씀하시는지 알려주세요. 예: 주식계좌, CMA계좌
User: 주식계좌
Agent: 확인 중입니다...
```

이런 단계적 프롬프트 설계 덕분에 대화가 자연스러워지고, API 호출도 정확해졌습니다. Anthropic 가이드에서는 명확한 의도 설정과 예시 기반 프롬프트 작성법을 자세히 다루니 참고해보세요[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).


## 마이크로서비스와 이벤트 기반 아키텍처로 확장성 챙기기

토스증권 Open API용 Agent Skill 백엔드는 단일 서비스로 시작했지만, 금방 확장과 유지보수 문제에 부딪혔어요. 그래서 GitHub 엔지니어링 블로그에서 소개한 마이크로서비스와 이벤트 기반 비동기 처리 방식을 참고해 아키텍처를 개편했습니다.

- 인증, 프롬프트 처리, API 연동, 응답 캐싱을 각각 독립된 서비스로 분리
- Kafka를 이용해 이벤트 발행/구독 구조 구현
- 비동기 메시지 큐로 API 호출 부하 분산

이렇게 하니까 장애가 나도 전체 서비스가 멈추지 않고, 특정 모듈만 재배포해도 되니 운영이 훨씬 편해졌어요. 물론, 분산 시스템 특성상 메시지 순서 보장이나 장애 복구 로직이 복잡해졌지만, 장기적으로 보면 투자 가치가 충분했습니다.


## API 게이트웨이와 캐싱 전략으로 응답 속도 40% 개선

금융 서비스에서 응답 속도는 고객 만족도와 직결되죠. Cloudflare의 'How We Built It' 시리즈를 참고해 API 게이트웨이를 도입하고, 캐싱 전략을 강화했습니다. 

- API 게이트웨이에서 인증 토큰 검증과 요청 라우팅 처리
- 자주 조회하는 금융 데이터는 Redis 캐시 적용
- 캐시 만료 시간은 데이터 특성에 맞게 30초~5분 사이로 조절

이 덕분에 트래픽이 몰릴 때도 서버 부하가 줄고, 응답 속도가 평균 300ms에서 180ms로 40% 이상 빨라졌어요. 물론 캐시 일관성 문제는 항상 고민거리인데, 금융 데이터 특성상 실시간성도 중요해서 캐시 만료 시간을 너무 길게 잡으면 안 됩니다.


## 도메인 주도 설계(DDD)로 복잡한 금융 로직 깔끔하게 관리하기

마틴 파울러의 아키텍처 가이드에서 강조하는 클린 아키텍처와 DDD 원칙은 토스증권 Open API 통합 시 정말 큰 도움이 됐어요[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/). 금융 도메인 특유의 복잡한 비즈니스 로직을 서비스, 도메인, 인프라 계층으로 명확히 나누니 유지보수가 쉬워지고, 신규 기능 추가도 부담이 줄었죠.

예를 들어, 계좌별 거래 내역 조회 로직은 도메인 계층에 모아두고, API 호출과 캐싱은 인프라 계층에서 담당하게 했습니다. 이렇게 하면 API가 바뀌어도 도메인 로직은 거의 손대지 않아도 되니 안정성이 높아집니다.


## 정리하며: 실무에서 꼭 챙겨야 할 포인트

- **토큰 관리**는 미리 만료 5분 전 갱신, 실패 시 사용자 알림까지 챙기자.
- **프롬프트 설계**는 단계별 질문으로 의도를 명확히, Anthropic 가이드가 큰 도움.
- **아키텍처**는 마이크로서비스 + 이벤트 기반으로 확장성과 장애 대응력 확보.
- **응답 속도**는 API 게이트웨이와 캐싱 전략으로 40% 이상 개선 가능.
- **도메인 주도 설계**로 금융 비즈니스 로직을 깔끔하게 분리해 유지보수 편하게.

이건 제가 직접 겪으면서 느낀 건데, 처음엔 다 귀찮고 복잡해 보여도 하나씩 적용해보면 서비스 안정성과 개발 생산성이 확실히 올라가요. 특히 금융 API처럼 민감한 데이터를 다룰 땐 이런 세심한 준비가 필수입니다.
