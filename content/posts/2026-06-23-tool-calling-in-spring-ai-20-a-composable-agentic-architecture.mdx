## AI 도구 호출, 왜 에이전트 아키텍처가 필요한가?

최근 AI를 백엔드 서비스에 통합하는 프로젝트를 하면서 가장 고민했던 부분 중 하나가 ‘도구 호출’이었다. 단순히 OpenAI API를 호출하는 걸 넘어서, 여러 AI 도구를 조합하고 상황에 맞게 선택해서 호출하는 구조가 필요했는데, 이걸 어떻게 깔끔하게 설계할지 막막했다. 

Spring AI 2.0이 등장하면서 이 문제에 대한 해답을 조금 찾을 수 있었다. 이 버전은 모듈화된 컴포저블 아키텍처를 통해 여러 AI 도구를 에이전트 방식으로 호출할 수 있게 해준다. 즉, AI 호출 로직을 마치 여러 에이전트가 상황에 맞게 도구를 골라 쓰듯 유연하게 구성할 수 있다는 뜻이다. 

이 글에서는 내가 직접 경험하며 배운 Spring AI 2.0 기반 도구 호출 아키텍처 설계와, 성능 튜닝 팁을 공유하려 한다.


## Spring Framework 핵심 기술로 에이전트 아키텍처를 유연하게 만들기

Spring AI 2.0은 Spring Framework의 DI(Dependency Injection)와 AOP(Aspect-Oriented Programming)를 적극 활용한다. 이 두 가지가 에이전트 기반 도구 호출 아키텍처를 구성하는 데 얼마나 중요한지 직접 써보니 확실히 알겠더라.

예를 들어, 여러 AI 도구 호출 클래스를 빈으로 등록하고, 호출 시점에 어떤 도구를 쓸지 DI로 주입받아 바꿔 끼울 수 있다. AOP를 이용하면 호출 전후에 공통 로직(예: 로깅, 트랜잭션 관리, 캐싱 등)을 쉽게 적용할 수 있어 코드 중복도 줄고 유지보수도 편하다.

이런 구조 덕분에 새로운 AI 도구가 생겨도 기존 코드를 크게 건드리지 않고 확장 가능하다. 실제로 내가 진행한 프로젝트에서는 OpenAI, Anthropic, 자체 개발한 AI 도구를 모두 같은 인터페이스로 호출하도록 설계했고, 상황에 따라 동적으로 도구를 선택하는 에이전트 역할을 쉽게 구현할 수 있었다.


## 대규모 AI 도구 호출, 성능 튜닝에서 꼭 챙겨야 할 것들

AI API 호출은 네트워크 I/O가 많아 응답 시간이 길고, 호출량이 많아지면 백엔드 시스템에 부담이 커진다. Baeldung의 Spring Boot 성능 튜닝 가이드에 따르면, 이런 상황에서 비동기 처리, 캐싱, 커넥션 풀링 같은 기법을 적용하면 확장성과 응답성을 크게 개선할 수 있다.

내 경험을 예로 들면, OpenAI API를 호출하는 부분을 `@Async` 어노테이션으로 비동기화하고, 자주 쓰는 결과는 Redis 캐시에 5분간 저장했다. 또한 HTTP 커넥션 풀 크기를 50으로 설정해 동시 호출 처리량을 높였다. 이렇게 하니 호출 지연이 평균 300ms에서 120ms로 줄었고, 서버 부하도 눈에 띄게 낮아졌다.

```java
@Service
public class OpenAiService {

    private final WebClient webClient;
    private final CacheManager cacheManager;

    public OpenAiService(WebClient.Builder webClientBuilder, CacheManager cacheManager) {
        this.webClient = webClientBuilder.baseUrl("https://api.openai.com/v1").build();
        this.cacheManager = cacheManager;
    }

    @Async
    @Cacheable(value = "openAiCache", key = "#prompt", unless = "#result == null")
    public CompletableFuture<String> callOpenAi(String prompt) {
        return webClient.post()
                .uri("/chat/completions")
                .header("Authorization", "Bearer " + System.getenv("OPENAI_API_KEY"))
                .bodyValue(Map.of(
                    "model", "gpt-4",
                    "messages", List.of(Map.of("role", "user", "content", prompt))
                ))
                .retrieve()
                .bodyToMono(String.class)
                .toFuture();
    }
}
```

이 코드는 Spring WebClient를 쓰면서 비동기 호출과 캐싱을 동시에 구현한 예다. 중요한 건, 캐시 키를 프롬프트로 설정해 같은 질문에 대한 호출을 줄였고, `@Async` 덕분에 호출이 블로킹되지 않아 서버 처리량이 올라갔다.


## OpenAI API와 Spring AI 2.0 연동 시 프롬프트 설계가 왜 중요한가

OpenAI API는 RESTful 인터페이스라 Spring AI 2.0과 연동이 쉽다. 하지만 API 호출 성능과 정확도는 프롬프트 설계에 크게 좌우된다. Anthropic의 프롬프트 엔지니어링 가이드에서도 강조하는 것처럼, 에이전트가 명확한 지시와 충분한 컨텍스트를 받으면 결과가 훨씬 좋아진다.

예를 들어, 단순히 "요약해줘"라고 요청하는 대신, "아래 텍스트를 3문장으로 요약해줘. 핵심 키워드도 포함해줘."라고 구체적으로 지시하면 AI가 더 정확한 답을 준다. 이런 프롬프트 작성법을 Spring AI 2.0의 에이전트 아키텍처에 반영하면, 도구 호출 시점에서 프롬프트를 동적으로 조합해 최적화할 수 있다.

내가 만든 에이전트는 각 도구별로 프롬프트 템플릿을 관리하고, 상황에 따라 템플릿을 조합해 호출한다. 덕분에 같은 입력이라도 도구별 특성에 맞게 최적화된 프롬프트를 보낼 수 있었다.


## 실제 프로젝트에서 Spring AI 2.0 도구 호출 아키텍처를 이렇게 썼다

내가 참여한 금융권 AI 챗봇 프로젝트에서, 고객 문의에 따라 OpenAI, Anthropic, 그리고 사내 규정 기반 룰 엔진을 조합해 답변을 생성하는 시스템을 구축했다. 

각 도구는 `Tool` 인터페이스를 구현했고, Spring DI로 에이전트가 상황에 맞게 호출 도구를 선택했다. 호출 결과는 비동기로 받고, 중요 답변은 캐시에 저장해 재호출 비용을 줄였다. 

```java
public interface Tool {
    CompletableFuture<String> call(String input);
}

@Service
public class AgentService {

    private final Map<String, Tool> tools;

    public AgentService(List<Tool> toolList) {
        tools = toolList.stream()
            .collect(Collectors.toMap(tool -> tool.getClass().getSimpleName(), Function.identity()));
    }

    public CompletableFuture<String> handleRequest(String toolName, String input) {
        Tool tool = tools.get(toolName);
        if (tool == null) {
            return CompletableFuture.completedFuture("도구를 찾을 수 없습니다.");
        }
        return tool.call(input);
    }
}
```

이 구조 덕분에 새로운 AI 도구를 추가할 때마다 `Tool` 인터페이스만 구현하면 되고, 호출 로직은 바꿀 필요가 없었다. 또한, 각 도구 호출 전후에 AOP로 로깅과 메트릭 수집을 넣어 운영 모니터링도 수월했다.


## 여기서 주의할 점: 에이전트 아키텍처도 무조건 좋은 건 아니다

처음엔 이런 에이전트 방식이 만능인 줄 알았는데, 실제로는 복잡도가 꽤 올라간다. 도구 간 호출 순서나 실패 처리, 상태 관리가 까다로워지고, 에이전트가 많아질수록 테스트 케이스도 폭발적으로 늘어난다. 

또한, 비동기 호출과 캐시를 남발하면 디버깅이 어려워질 수 있다. 그래서 적절한 로깅과 모니터링, 그리고 호출 실패 시 재시도 정책을 반드시 설계해야 한다. 

내 경험상, 처음부터 너무 많은 도구를 한꺼번에 붙이기보다는, 핵심 도구부터 차근차근 에이전트 아키텍처로 전환하는 게 현명하다.


## 정리하며: Spring AI 2.0 도구 호출 아키텍처 활용법

- Spring Framework의 DI와 AOP를 적극 활용해 도구 호출 컴포넌트를 모듈화하고, 에이전트가 동적으로 도구를 선택하도록 설계하자.
- 비동기 처리(`@Async`), 캐싱(`@Cacheable`), 커넥션 풀링 설정으로 API 호출 성능과 확장성을 높여야 한다.
- OpenAI API 같은 RESTful AI 도구는 프롬프트 설계가 핵심이니, 에이전트 아키텍처 내에서 프롬프트 템플릿을 관리하고 상황에 맞게 조합하자.
- 운영 시 로깅과 모니터링, 실패 처리 정책을 꼼꼼히 설계해 복잡한 에이전트 아키텍처의 단점을 보완하자.

이런 경험을 바탕으로 Spring AI 2.0을 도입하면, 단순 API 호출을 넘어 복잡한 AI 도구 조합과 확장성 높은 백엔드 AI 통합이 가능해진다. 실제로 써보면, 이게 얼마나 유연하고 강력한지 체감할 수 있을 거다.
