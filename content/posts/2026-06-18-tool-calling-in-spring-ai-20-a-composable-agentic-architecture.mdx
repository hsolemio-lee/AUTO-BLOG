# 도구 호출, AI 에이전트 설계에 왜 이렇게 골치 아플까?

최근 우리 팀에서는 Spring AI 2.0을 도입해 AI 기반 에이전트 아키텍처를 설계하는 작업을 진행했어요. 그런데 막상 도구 호출(tool calling)을 유연하게 연결하고, 프로덕션 환경에서 안정적으로 운영하려니 생각보다 할 게 많더라고요. 

"도대체 Spring AI 2.0이 뭔데 이렇게 편하다면서?"라고 반문할 수도 있지만, 사실 핵심은 Spring Boot 3.x가 제공하는 모듈화된 컴포저블 구조 덕분에 가능한 일입니다. 이걸 잘 이해하고 적용하면, 여러 도구를 마치 블록 쌓듯 조합하는 에이전트를 만들 수 있어요. 

이번 글에서는 실제로 저희가 겪은 시행착오와 함께, JVM 튜닝부터 비동기 API 호출, 그리고 프롬프트 설계까지 프로덕션급으로 다루는 팁을 나눠보겠습니다.

---

## Spring AI 2.0이 말하는 ‘컴포저블 에이전트’란 뭘까?

일단 ‘컴포저블(composable)’이라는 말부터 풀어볼게요. 쉽게 말해, 에이전트가 여러 도구를 호출할 때 각 도구를 독립적인 컴포넌트로 분리하고, 이 컴포넌트들을 조합해서 하나의 큰 기능을 만든다는 뜻이에요. 

Spring Boot 3.x는 이걸 지원하기 위해 모듈화된 구조를 제공하는데, 덕분에 새로운 도구를 추가하거나 기존 도구를 교체할 때 전체 코드를 크게 고치지 않아도 됩니다. 

예를 들어, OpenAI API 호출과 내부 DB 조회, 외부 REST API 호출을 각각 별도의 컴포넌트로 만들고, 이들을 하나의 에이전트가 필요에 따라 호출하는 식이죠. 

```java
@Component
public class OpenAiTool implements Tool {
    private final OpenAiClient client;

    public OpenAiTool(OpenAiClient client) {
        this.client = client;
    }

    @Override
    public CompletableFuture<String> call(String prompt) {
        // 비동기 호출로 응답 지연 최소화
        return client.chatCompletion(prompt)
                     .thenApply(response -> response.getChoices().get(0).getMessage().getContent());
    }
}

@Component
public class Agent {
    private final List<Tool> tools;

    public Agent(List<Tool> tools) {
        this.tools = tools;
    }

    public CompletableFuture<String> execute(String input) {
        // 여러 도구를 순차 또는 병렬로 호출하는 로직
        return tools.stream()
                    .map(tool -> tool.call(input))
                    .reduce((f1, f2) -> f1.thenCombine(f2, (r1, r2) -> r1 + "\n" + r2))
                    .orElse(CompletableFuture.completedFuture("No tools available"));
    }
}
```

위 예시는 아주 단순화한 형태지만, Spring의 의존성 주입(DI) 덕분에 도구 컴포넌트를 쉽게 교체하거나 확장할 수 있습니다. 이게 바로 Spring Framework가 지향하는 느슨한 결합(loose coupling)의 힘이죠[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

## 프로덕션에서 JVM 튜닝과 쓰레드 풀 최적화가 왜 중요한가

이런 구조가 멋지긴 한데, 실무에서 가장 골치 아픈 부분은 성능과 안정성입니다. AI API 호출은 네트워크 지연이 있고, 도구 호출이 많아질수록 지연 시간이 누적되거든요.

저희는 JVM 튜닝과 쓰레드 풀 설정을 통해 이 문제를 꽤 효과적으로 완화했습니다. 

- JVM 힙 메모리를 서비스 규모에 맞게 4GB~8GB로 조절
- 쓰레드 풀(core pool size 20, max pool size 50, queue capacity 100) 설정으로 동시 호출 처리
- 캐시(예: Caffeine)로 자주 쓰는 결과 저장해 API 호출 최소화

특히 쓰레드 풀 설정은 `@Async`나 `CompletableFuture`를 사용할 때 중요한데, 너무 작으면 요청이 밀리고, 너무 크면 오히려 GC 부담이 커집니다. 

```java
@Configuration
@EnableAsync
public class AsyncConfig {
    @Bean(name = "taskExecutor")
    public ThreadPoolTaskExecutor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(20);
        executor.setMaxPoolSize(50);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("AiAgent-");
        executor.initialize();
        return executor;
    }
}
```

이런 세팅은 Baeldung의 Spring Boot 성능 튜닝 가이드에서 권장하는 방법과도 일치합니다[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

## OpenAI API와 비동기 호출, 그리고 오류 처리 전략

Spring AI 2.0에서 OpenAI API를 호출할 때는 자연어 프롬프트를 넘기고, 응답을 받아서 다시 에이전트 로직에 반영하는 흐름이 기본입니다. 하지만 네트워크 장애나 API 제한이 걸리면 에러가 발생할 수 있죠.

그래서 저희는 API 호출을 비동기(`CompletableFuture`)로 처리하고, 타임아웃과 재시도 로직을 꼭 넣었습니다. 예를 들어, 3초 이상 지연되면 타임아웃 처리하고, 최대 3회 재시도하는 식입니다.

```java
public CompletableFuture<String> callOpenAiWithRetry(String prompt) {
    return CompletableFuture.supplyAsync(() -> {
        int attempts = 0;
        while (attempts < 3) {
            try {
                return openAiClient.chatCompletion(prompt).get(3, TimeUnit.SECONDS)
                    .getChoices().get(0).getMessage().getContent();
            } catch (TimeoutException | InterruptedException | ExecutionException e) {
                attempts++;
                if (attempts == 3) {
                    throw new RuntimeException("OpenAI API 호출 실패", e);
                }
            }
        }
        return "";
    });
}
```

이렇게 하면 호출 실패 시에도 에이전트가 무한 대기하거나 멈추지 않고, 적절히 에러를 처리하면서 다음 작업으로 넘어갈 수 있습니다. 

OpenAI 공식 문서에서도 비동기 호출과 오류 핸들링을 권장하고 있으니 참고하세요[OpenAI API Documentation](https://platform.openai.com/docs/overview).

## 프롬프트 설계, 왜 구체적이어야 하는가

도구 호출에서 프롬프트는 단순한 입력이 아니라, 에이전트가 어떤 행동을 할지 결정하는 ‘명령서’나 다름없습니다. Anthropic의 프롬프트 엔지니어링 가이드에 따르면, 명확하고 구체적인 프롬프트가 AI 응답의 정확도와 품질을 크게 좌우한다고 해요[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

예를 들어, 단순히 "날씨 알려줘" 대신 "서울의 오늘 오후 3시 기준 날씨와 미세먼지 수치를 알려줘"라고 하면 훨씬 정확한 답변을 받을 수 있죠.

Spring AI 2.0에서는 프롬프트 템플릿을 별도로 관리하는 기능이 있어서, 이런 구체적인 프롬프트를 재사용하기 편리합니다. 

```java
@Component
public class WeatherPromptTemplate {
    public String createPrompt(String city, LocalDateTime dateTime) {
        return String.format("%s의 %s 기준 날씨와 미세먼지 수치를 알려줘",
                             city, dateTime.format(DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm")));
    }
}
```

템플릿을 활용하면 프롬프트 관리가 체계적이고, 수정도 한 곳에서 끝나서 유지보수가 훨씬 수월해집니다.

## Cursor와 함께하는 AI 도구 자동화 경험

마지막으로, 저희 팀은 Cursor라는 개발 환경도 함께 도입했는데요, AI 기반 코드 생성과 도구 호출 자동화에 꽤 도움이 되더라고요. 

Cursor는 AI 에이전트가 외부 도구와 상호작용할 때 필요한 API와 툴킷을 제공해서, Spring AI 2.0과 연동하면 생산성이 크게 올라갑니다[Cursor Documentation](https://docs.cursor.com/).

예를 들어, 코드 내에서 특정 API 호출 코드를 자동 완성하거나, 도구 호출 결과를 바로 테스트하는 워크플로우를 만들 수 있어서 개발 속도가 체감상 30% 이상 빨라졌어요.

# 직접 써보면서 느낀 점

처음엔 Spring AI 2.0의 컴포저블 아키텍처가 그저 ‘모듈화’ 정도로만 생각했는데, 실제로 적용해보니 의존성 주입과 AOP 덕분에 에이전트 상태 관리와 도구 호출 흐름을 훨씬 유연하게 제어할 수 있다는 게 신기했습니다. 

그리고 JVM 튜닝이나 쓰레드 풀 크기 조절 같은 기본적인 성능 최적화가 얼마나 중요한지도 몸소 체감했죠. AI API 호출이 느린데, 그냥 막 돌리면 전체 서비스가 느려질 수밖에 없으니까요.

프롬프트 설계도 처음엔 별거 아닌 것 같지만, 구체적인 템플릿을 만들고 관리하는 게 장기적으로 응답 품질 관리에 큰 도움이 됩니다.

마지막으로, Cursor 같은 도구와 함께 쓰면 개발 생산성이 확실히 올라가니, AI 에이전트 개발에 관심 있다면 한 번 써보길 추천합니다.

# 이번 글에서 바로 적용해볼 수 있는 팁

- Spring Boot 3.x의 컴포저블 구조를 활용해 도구별 컴포넌트를 분리하고, DI로 관리하세요.
- JVM 힙 사이즈와 쓰레드 풀 설정을 서비스 규모에 맞게 조절해 API 호출 지연을 최소화하세요.
- OpenAI API 호출은 비동기 처리하고, 타임아웃과 재시도 로직을 반드시 넣으세요.
- 프롬프트는 구체적이고 명확하게 설계해 템플릿으로 관리하면 유지보수가 편합니다.
- Cursor 같은 AI 개발 툴킷을 도입해 코드 생성과 도구 호출 자동화를 경험해보세요.

이렇게 하면 Spring AI 2.0 기반의 도구 호출 에이전트를 좀 더 안정적이고 확장성 있게 운영할 수 있을 겁니다.
