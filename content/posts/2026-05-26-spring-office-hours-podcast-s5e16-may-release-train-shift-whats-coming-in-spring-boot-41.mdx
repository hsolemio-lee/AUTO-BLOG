### "배포 후 갑자기 응답 지연?" 내 경험에서 찾은 Spring Boot 4.1의 답

회사에서 운영 중인 서비스가 갑자기 응답 속도가 느려졌던 적이 있어요. 원인을 찾다 보니, 프로덕션 환경에서 JVM 튜닝과 커넥션 풀 설정이 제대로 안 되어 있었더군요. 이번에 공개된 Spring Boot 4.1을 보면서, "아 이걸 미리 적용했으면 좋았겠다"는 생각이 들었어요. 이번 글에서는 저처럼 현장에서 직접 겪은 문제를 해결할 수 있는 Spring Boot 4.1의 핵심 기능들을 정리해봤습니다.

## Spring Boot 4.1, 프로덕션 환경에서 달라진 점은?

Spring Boot 4.1은 특히 프로덕션 환경에서 애플리케이션 성능과 안정성을 높이기 위한 튜닝 기능을 대폭 강화했어요. JVM 옵션, 커넥션 풀, 캐시 설정 등 기본적으로 손봐야 할 부분이 많았는데, 이번 버전에서는 좀 더 직관적이고 세밀한 설정이 가능해졌죠.

예를 들어, `application.yml`에서 커넥션 풀 최대 크기를 환경별로 다르게 설정할 수 있는데, 이렇게 하면 개발 환경과 프로덕션 환경을 한꺼번에 관리할 때 훨씬 편합니다.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: ${DB_POOL_SIZE:20} # 기본 20, 환경변수로 조절 가능
```

이런 설정 덕분에 프로덕션에서는 50 이상으로 늘리고, 로컬 개발에선 5 정도로 낮출 수 있죠.

Baeldung에서 소개한 JVM 튜닝 팁도 여전히 유효한데, Spring Boot 4.1에서는 `spring-boot-starter-actuator`가 더 많은 JVM 메트릭을 기본 제공해서 모니터링이 훨씬 수월해졌습니다. [Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance)

## 보안, "기본 설정만으로도 충분한가?" Spring Boot 4.1의 변화

보안은 항상 민감한 영역이죠. Spring Boot 4.1에서는 기본 보안 설정이 강화되면서 OAuth2와 JWT 지원이 크게 개선됐어요. OAuth2 클라이언트 설정이 더 간단해졌고, JWT 토큰 검증 로직도 커스터마이징하기 편해졌습니다.

예를 들어, JWT 토큰에서 사용자 권한을 추출하는 커스텀 `JwtAuthenticationConverter`를 등록하는 코드가 훨씬 직관적이 됐는데요:

```java
@Bean
public JwtAuthenticationConverter jwtAuthenticationConverter() {
    JwtAuthenticationConverter converter = new JwtAuthenticationConverter();
    converter.setJwtGrantedAuthoritiesConverter(jwt -> {
        List<String> roles = (List<String>) jwt.getClaims().getOrDefault("roles", Collections.emptyList());
        return roles.stream()
            .map(SimpleGrantedAuthority::new)
            .collect(Collectors.toList());
    });
    return converter;
}
```

이렇게 하면 JWT 내부의 `roles` 클레임을 스프링 시큐리티 권한으로 바로 매핑할 수 있어요. 이전 버전보다 훨씬 깔끔하죠.

그리고 기본적으로 CSRF 보호가 더 엄격해졌고, 보안 헤더 설정도 자동으로 강화돼서 "보안 설정을 깜빡했다" 싶은 상황이 줄어들었습니다.

[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)에 따르면, 이런 보안 기본값 강화는 특히 마이크로서비스 아키텍처에서 각 서비스별 보안 일관성을 유지하는 데 큰 도움이 된다고 하네요.

## 점진적 배포와 Canary Release, Spring Boot 4.1이 도와주는 부분

대규모 서비스에서 새 버전을 한번에 던지는 건 위험하죠. 그래서 점진적 배포와 Canary Release가 필수인데, Spring Boot 4.1은 이를 지원하는 설정 옵션을 많이 추가했어요.

예를 들어, `management.endpoint.health.probes.enabled=true` 옵션을 켜면 쿠버네티스 같은 오케스트레이션 도구가 더 정밀하게 헬스 체크를 할 수 있습니다. 이 덕분에 트래픽을 점진적으로 새 버전으로 옮길 때 실패율을 빠르게 감지할 수 있죠.

또, `spring.profiles.group` 기능을 활용하면 여러 프로파일을 묶어서 환경별 롤아웃 전략을 손쉽게 관리할 수 있어요.

```yaml
spring:
  profiles:
    group:
      canary:
        - canary-feature
        - monitoring
```

이렇게 하면 `canary` 프로파일을 활성화할 때 관련된 여러 기능을 한 번에 켤 수 있어서, Canary Release 환경 구성에 드는 수고가 줄어듭니다.

롤아웃 전략을 고민할 때는 항상 "문제가 생기면 빠르게 롤백할 수 있나"가 관건인데, Spring Boot 4.1은 헬스 체크와 프로파일 관리 덕분에 이 부분에서 훨씬 유연해졌어요.

## Spring Framework 6과 함께 쓰는 Spring Boot 4.1, 모듈화와 DI 개선

Spring Boot 4.1은 Spring Framework 6 기반이라 DI(Dependency Injection)와 모듈화 측면에서 진일보했습니다. 예전에는 복잡한 의존성 주입 설정 때문에 유지보수가 어려웠다면, 이제는 컴포넌트 스캔과 빈 정의가 더 깔끔해졌어요.

특히 `@Configuration` 클래스에서 `@Import`를 활용해 모듈별로 설정을 분리하는 패턴이 권장됩니다. 이렇게 하면 기능별로 설정을 나누고, 필요에 따라 조합할 수 있어 확장성이 좋아지죠.

```java
@Configuration
@Import({SecurityConfig.class, DataSourceConfig.class})
public class AppConfig {
    // 공통 설정
}
```

이런 구조 덕분에 팀 내에서 역할 분담도 명확해지고, 테스트도 더 효율적으로 할 수 있었습니다.

[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html) 문서에서도 이런 모듈화 전략과 DI 개선사항을 자세히 다루고 있으니 참고해보세요.

## 실제 현장에서 써본 Spring Boot 4.1 설정 예시

마지막으로 제가 최근 프로젝트에 적용한 `application.yml` 예시를 공유할게요. 프로덕션 환경에서 JVM 튜닝, 커넥션 풀, 보안, 헬스 체크까지 고려한 설정입니다.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 50
      minimum-idle: 10
      idle-timeout: 300000
      max-lifetime: 1800000
  security:
    oauth2:
      client:
        registration:
          my-client:
            client-id: your-client-id
            client-secret: your-secret
            scope: openid,profile,email
  profiles:
    active: prod
  main:
    allow-bean-definition-overriding: false
management:
  endpoint:
    health:
      probes:
        enabled: true
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
```

이 설정만으로도 JVM과 커넥션 풀이 안정적으로 동작하고, OAuth2 인증도 문제없이 처리되며, 쿠버네티스 헬스 체크와 모니터링이 원활하게 작동했습니다.

## 마무리하며: Spring Boot 4.1, "기술이 아니라 경험의 문제"

Spring Boot 4.1은 분명 기능적으로 많은 발전이 있었지만, 결국 중요한 건 "우리 팀과 서비스에 맞게 잘 적용하는 것"입니다. 자동화된 보안 강화나 프로덕션 튜닝 기능도, 제대로 이해하지 않고 무작정 적용하면 오히려 문제를 키울 수 있거든요.

그래서 저는 이번 버전을 도입할 때 이렇게 권합니다.

- **기본 설정부터 차근차근 확인하기**: 새 기능이 많아도 한꺼번에 다 바꾸지 말고, 하나씩 적용하며 모니터링하세요.
- **모니터링과 로깅 강화**: Actuator와 Prometheus, Grafana 같은 툴을 적극 활용해 JVM과 애플리케이션 상태를 실시간으로 파악하세요.
- **보안 정책은 팀 내 공유 필수**: OAuth2, JWT 설정은 문서화하고, 권한 관리 정책도 명확히 합시다.
- **롤아웃 전략은 항상 준비**: Canary Release나 점진적 배포를 기본으로, 문제가 생기면 빠르게 롤백할 수 있는 절차를 마련하세요.

이 글이 여러분이 Spring Boot 4.1을 현업에서 안정적으로 활용하는 데 작은 도움이 되었으면 합니다. 궁금한 점이나 경험 공유는 언제든 환영입니다!
