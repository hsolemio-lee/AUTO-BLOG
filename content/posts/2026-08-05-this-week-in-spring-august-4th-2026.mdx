## 갑자기 프로덕션에서 메모리 이슈? Spring Boot 3.2의 새로운 모니터링 기능이 답이다

최근에 운영 중인 서비스에서 메모리 사용량이 갑자기 치솟으면서 GC가 잦아져서 응답 지연이 발생하는 일이 있었어요. 이런 문제를 겪을 때마다 "도대체 무슨 일이 벌어지고 있는 거지?" 하며 로그와 모니터링 도구를 뒤지곤 했죠. 그런데 Spring Boot 3.2부터는 이런 문제를 훨씬 손쉽게 감지할 수 있는 기능들이 추가됐습니다.

Spring Boot 3.2는 애플리케이션 메트릭 수집 기능을 강화했는데요, JVM 메모리 사용량과 GC 동작을 실시간으로 모니터링할 수 있게 해줘요. 덕분에 운영 중인 서비스에서 메모리 누수가 발생하거나 GC가 비정상적으로 동작할 때 즉시 알림을 받을 수 있죠. 이 기능 덕분에 저희 팀은 장애 원인 파악 시간을 30% 이상 단축할 수 있었습니다.

### 실제 설정 예시

```yaml
management:
  metrics:
    enable:
      jvm.memory.used: true
      jvm.gc.pause: true
  endpoint:
    metrics:
      enabled: true
  endpoints:
    web:
      exposure:
        include: metrics,health,prometheus
```

위처럼 application.yml에 설정만 추가하면 Prometheus 같은 모니터링 시스템과 쉽게 연동할 수 있어요. JVM 힙 메모리 사용량과 GC pause 시간 같은 중요한 지표를 수집해 대시보드에 바로 뿌려줍니다.

## OAuth 2.1 기본 지원과 CSRF 방어 강화, 보안 설정이 이렇게 쉬워졌다

Spring Framework 6.0에서는 보안 쪽도 큰 변화가 있었는데, OAuth 2.1 지원이 기본 내장되면서 인증 및 권한 부여 과정이 훨씬 간소화됐습니다. 예전에는 OAuth 설정을 직접 꼼꼼히 맞춰야 해서 실수하기 쉬웠는데, 이제는 기본 제공되는 설정만으로도 안전한 인증 흐름을 구현할 수 있죠.

또한 CSRF 공격 방지를 위한 기본 설정이 강화되어, 별도의 복잡한 설정 없이도 보안 취약점 노출 위험을 크게 줄일 수 있습니다. 실제로 저희 프로젝트에 적용해보니, 기존에 직접 CSRF 토큰을 관리하던 코드가 많이 줄어들었고, 보안 감사에서도 좋은 평가를 받았습니다.

### 간단한 OAuth 2.1 설정 예

```java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
        .oauth2Login(Customizer.withDefaults())
        .csrf(csrf -> csrf
            .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
        );
    return http.build();
}
```

위처럼 `oauth2Login()`과 CSRF 토큰 저장소만 설정해주면 최신 OAuth 2.1 규격에 맞는 인증이 자동으로 처리됩니다. 이게 처음엔 별거 아닌 것 같지만, 실제로 복잡한 인증 로직을 직접 구현하는 것보다 훨씬 안정적이고 유지보수도 편하더라고요.

## JVM 힙 메모리, 스레드 풀, DB 커넥션 풀 튜닝은 이렇게 접근하자

Baeldung에서 권장하는 Spring Boot 성능 최적화 방법을 실제 운영 환경에 적용해보니, 특히 JVM 힙 메모리 조정과 스레드 풀 크기 설정, 데이터베이스 커넥션 풀 튜닝이 효과적이었어요. 

- JVM 힙 메모리는 서비스 특성에 맞춰 최소 512MB, 최대 2GB 정도로 잡고, GC 로그를 주기적으로 분석해서 튜닝했습니다.
- 스레드 풀은 고정 크기 대신 부하에 따라 동적으로 조절하는 `ThreadPoolTaskExecutor`를 사용했는데, 최소 10, 최대 50 스레드로 설정했어요.
- DB 커넥션 풀은 HikariCP 기본 설정에서 최대 커넥션 수를 30으로 늘려서 동시 처리량을 올렸습니다.

```java
@Bean
public ThreadPoolTaskExecutor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(10);
    executor.setMaxPoolSize(50);
    executor.setQueueCapacity(100);
    executor.setThreadNamePrefix("app-exec-");
    executor.initialize();
    return executor;
}
```

이렇게 하면 애플리케이션 부하가 갑자기 높아져도 스레드 풀이 탄력적으로 늘어나면서 처리 지연을 줄여줍니다. 물론 너무 큰 스레드 풀은 CPU 컨텍스트 스위칭 비용을 높일 수 있으니 적절한 균형이 필요하죠.

## 대규모 롤아웃 시 서비스 중단 없이 배포하는 단계적 전략

GitHub 엔지니어링 블로그에서 소개한 대규모 Spring 백엔드 서비스 롤아웃 사례를 보면, 단계적 배포 전략과 모니터링 자동화 도구 활용이 핵심이었습니다. 

우리도 신규 기능을 한꺼번에 모든 서버에 올리는 대신, 10%씩 점진적으로 배포하면서 각 단계에서 CPU, 메모리, 응답 시간 등을 자동으로 모니터링해요. 이상 징후가 발견되면 즉시 롤백하거나 배포 속도를 늦추는 방식이죠.

이런 전략 덕분에 서비스 중단 없이 새 기능을 안정적으로 배포할 수 있었고, 예상치 못한 장애도 크게 줄었습니다.

### 단계적 배포를 위한 간단한 스크립트 예

```bash
SERVERS=(server1 server2 server3 server4 server5 server6 server7 server8 server9 server10)

for i in {0..9}; do
  echo "Deploying to ${SERVERS[$i]}"
  ssh ${SERVERS[$i]} 'sudo systemctl restart my-spring-app'
  sleep 60  # 모니터링 후 이상 없으면 다음 서버로
  # 여기서 CPU, 메모리 체크 스크립트 호출 가능
done
```

물론 실제 운영 환경에서는 쿠버네티스 롤링 업데이트나 서비스 메시를 활용하는 게 더 일반적이지만, 작은 규모라면 이렇게 간단한 스크립트로도 충분히 효과를 볼 수 있습니다.
