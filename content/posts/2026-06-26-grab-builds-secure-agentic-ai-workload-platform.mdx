### 에이전틱 AI, 실제로 운영하려면 뭘 신경 써야 할까?

최근 Grab에서 에이전틱(Agentic) AI 워크로드를 위한 플랫폼을 구축하면서 느낀 점이 많았어요. 단순히 AI 모델을 쓰는 걸 넘어서, 실제 서비스 환경에서 안전성과 확장성을 보장하는 게 얼마나 까다로운지 직접 경험했거든요. 특히 API 기반으로 설계한다는 건 말처럼 쉽지 않았습니다.

이 글에서는 Grab이 어떻게 에이전틱 AI를 위한 백엔드 아키텍처를 설계하고, 운영하며, 보안을 챙겼는지 현실적인 관점에서 얘기해보려고 해요. 실제로 적용한 구체적인 설정값이나 패턴, 그리고 코드 예시도 하나 넣어볼게요.

---

## API 중심 아키텍처가 왜 필수였을까?

에이전틱 AI 시스템은 여러 에이전트가 독립적으로 행동하고, 서로 상호작용하며, 외부 시스템과도 연결돼야 하죠. 이때 Grab은 API 기반 아키텍처를 택했는데, 이유가 명확했습니다. API는 인증, 요청 제한, 데이터 암호화 같은 보안 패턴을 체계적으로 적용하기 쉽고, 확장성도 확보하기 좋거든요.

OpenAI API 문서에서도 인증 토큰 관리, 요청당 최대 토큰 수 제한, TLS 암호화 적용 등을 기본 보안 수칙으로 강조하고 있어요. 예를 들어, 인증은 OAuth 2.0이나 API 키 방식으로 엄격히 관리하고, 요청 제한을 통해 과도한 트래픽으로부터 시스템을 보호합니다. 이런 기본기가 없으면 에이전틱 AI가 오히려 공격 벡터가 될 수 있거든요[OpenAI API Documentation](https://platform.openai.com/docs/overview).

Grab에서도 내부 API 게이트웨이 레벨에서 JWT 기반 인증과 IP 화이트리스트를 적용했고, 요청당 최대 60초 타임아웃과 초당 1000건 요청 제한을 두어 무분별한 호출을 막았습니다. 이 설정값은 실제 트래픽 패턴 분석을 통해 정한 건데, 처음엔 500 TPS로 시작했다가 점진적으로 늘려가며 안정성을 확인했어요.

## 프롬프트 설계와 운영 전략, 이게 왜 중요한가

에이전틱 AI는 단순한 챗봇이 아니에요. 명령을 수행하는 ‘에이전트’라서, 의도한 행동을 정확히 유도하는 프롬프트 설계가 핵심입니다. Anthropic이 제시하는 프롬프트 엔지니어링 가이드를 참고하면, 프롬프트 내에서 역할과 제한사항을 명확히 하여 AI가 예상치 못한 행동을 하지 않도록 유도하는 게 중요하다고 하죠[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

Grab에서는 각 에이전트별로 역할 정의와 행동 가이드라인을 JSON 템플릿으로 관리해요. 예를 들어, 결제 에이전트는 "사용자 결제 정보를 절대 외부에 노출하지 말라"는 규칙을 프롬프트에 명시하는 식이죠. 이렇게 하면 AI가 민감 정보를 다룰 때 실수를 줄일 수 있습니다.

운영 측면에선 프롬프트 버전 관리도 필수입니다. 실시간으로 프롬프트를 수정하면 예측 불가능한 동작이 발생할 수 있기 때문에, 모든 변경은 코드 리뷰와 테스트를 거쳐 배포합니다. 그리고 로그를 통해 프롬프트별 응답 패턴을 분석해 이상 징후를 조기에 감지하는 시스템도 구축했어요.

## 대규모 AI 워크로드, 백엔드에서 어떻게 감당할까?

Cursor 문서에서 제안하는 AI 기반 코드 생성과 자동화 워크플로우 백엔드 통합 패턴을 보면, 대규모 작업 부하를 처리하려면 비동기 처리와 큐잉 시스템이 필수라고 합니다. Grab도 마찬가지로, AI 작업 요청이 폭주할 때를 대비해 RabbitMQ 기반 큐 시스템을 도입했어요[Cursor Documentation](https://docs.cursor.com/).

큐에 작업을 쌓고, 여러 워커 인스턴스가 병렬로 처리하는 구조입니다. 워커는 컨테이너 오토스케일링 정책에 따라 최소 3개에서 최대 20개까지 자동으로 늘어나죠. 이렇게 하면 갑작스러운 요청 증가에도 지연 시간을 500ms 이하로 유지할 수 있었습니다.

보안 측면에선 큐 메시지 자체를 암호화하고, 워커와 큐 간 통신은 mTLS로 보호합니다. 다만 이 구조는 복잡도가 올라가고, 디버깅이 어려워지는 단점이 있어요. 그래서 로그와 모니터링 시스템에 각 단계별 트레이싱을 꼼꼼히 넣어두었습니다.

## 코드 생성과 실행 환경 격리, 어떻게 관리했나?

Anthropic의 Claude Code 개요를 보면, 에이전틱 AI에서 생성된 코드를 안전하게 실행하려면 권한 관리와 실행 환경 격리가 필수라고 하죠[Anthropic - Claude Code Overview](https://docs.anthropic.com/en/docs/claude-code/overview). Grab도 마찬가지로, AI가 생성한 코드를 바로 프로덕션 환경에 투입하지 않고, 샌드박스 환경에서 먼저 실행 검증을 합니다.

예를 들어, AI가 SQL 쿼리를 생성하면, 먼저 테스트 DB 인스턴스에서 실행해보고 결과를 확인하는 프로세스를 둡니다. 이 과정에서 쿼리 실행 시간이 2초를 초과하면 자동으로 롤백하고, 관리자에게 알림을 보내죠.

아래는 간단한 샌드박스 실행 예시 코드입니다. Python Flask API로 AI가 생성한 코드를 받아 임시 컨테이너에서 실행하는 구조예요.

```python
from flask import Flask, request, jsonify
import subprocess
import uuid
import os

app = Flask(__name__)

@app.route('/execute', methods=['POST'])
def execute_code():
    code = request.json.get('code')
    sandbox_id = str(uuid.uuid4())
    sandbox_dir = f'/tmp/sandbox_{sandbox_id}'
    os.makedirs(sandbox_dir)

    code_file = os.path.join(sandbox_dir, 'script.py')
    with open(code_file, 'w') as f:
        f.write(code)

    try:
        # 2초 타임아웃 설정
        result = subprocess.run(
            ['python3', code_file],
            stdout=subprocess.PIPE,
            stderr=subprocess.PIPE,
            timeout=2
        )
        output = result.stdout.decode() + result.stderr.decode()
    except subprocess.TimeoutExpired:
        output = 'Execution timed out and was terminated.'

    # 샌드박스 정리
    subprocess.run(['rm', '-rf', sandbox_dir])

    return jsonify({'output': output})

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)
```

이 방식의 단점은 리소스가 많이 든다는 점이에요. 컨테이너 생성과 삭제가 빈번하면 비용이 올라가고, 지연 시간도 길어질 수 있죠. 그래서 Grab은 빈번한 작업은 미리 준비된 워커 풀에서 처리하도록 최적화했습니다.

## 실시간 코드 제안과 생산성 향상을 위한 백엔드 설계

GitHub Copilot 문서에 따르면, 실시간 코드 제안 기능은 낮은 지연 시간과 높은 보안 요구사항 때문에 백엔드 설계가 까다롭습니다[GitHub Copilot Documentation](https://docs.github.com/en/copilot). Grab도 비슷한 요구사항을 갖고 있어서, WebSocket 기반 통신과 API 인증을 결합해 사용자의 세션을 엄격히 관리합니다.

또한, AI 모델 호출은 캐싱 레이어를 두어 반복 요청에 대해 응답 속도를 개선했고, 민감 데이터는 호출 전후에 별도로 암호화 처리합니다. 이런 설계 덕분에 개발자들이 AI 제안을 실시간으로 받으면서도 보안 위협은 최소화할 수 있었죠.

Grab에서 에이전틱 AI 워크로드 플랫폼을 구축하며 느낀 건, ‘안전’과 ‘확장성’은 절대 타협할 수 없는 가치라는 점입니다. API 기반 아키텍처, 프롬프트 설계의 엄격한 관리, 큐잉과 오토스케일링, 샌드박스 실행 환경까지 모두가 맞물려야 비로소 안정적인 서비스가 가능해지더라고요.

처음엔 이게 너무 복잡하고 비용도 많이 드는 것 같았는데, 실제로 운영하면서 장애가 줄고 개발 생산성이 올라가는 걸 보니 투자할 가치가 충분했습니다. 여러분도 에이전틱 AI 시스템을 고민 중이라면, 이런 구체적인 운영 전략과 아키텍처 패턴을 꼭 참고해보시길 권해요.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
