### "왜 내 테스트는 매번 달라질까?"

최근에 우리 팀에서 테스트가 가끔씩 실패하는 문제를 겪었어요. 로컬에서는 잘 되는데 CI에서는 실패하고, 또 다른 동료 환경에선 아예 실행이 안 되고… 이런 경험, 다들 한 번쯤 있죠? 이게 다 외부 의존 서비스(예: 데이터베이스, 캐시, 메시지 브로커)를 제대로 격리하지 않고 테스트하기 때문입니다.

그래서 저는 Spring 백엔드 프로젝트에 Docker, Docker Compose, 그리고 Testcontainers를 도입해봤는데, 이 조합이 얼마나 강력한지 직접 경험하면서 느낀 점들을 공유하려 합니다.

---

## Dockerfile 최적화, 컨테이너 이미지 크기와 빌드 속도에 이렇게 영향을 준다

처음에는 Dockerfile을 그냥 공식 OpenJDK 이미지 위에 Spring Boot fat jar 올려서 뚝딱 만들었는데, 이미지가 1GB가 넘더라고요. 배포할 때마다 네트워크 부담도 크고, 빌드 시간도 길고…

그래서 Docker 공식 문서에서 권장하는 베스트 프랙티스를 적용했죠. 예를 들어,

- `alpine` 기반 경량 이미지 사용
- 멀티스테이지 빌드로 빌드 환경과 런타임 환경 분리
- 불필요한 캐시, 임시 파일 제거
- 레이어 수 최소화

아래는 제가 실제로 쓰는 Dockerfile 예시입니다:

```dockerfile
# 빌드 단계
FROM maven:3.8.7-openjdk-17-slim AS build
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

# 런타임 단계
FROM openjdk:17-jdk-slim
WORKDIR /app
COPY --from=build /app/target/myapp.jar ./myapp.jar

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "myapp.jar"]
```

멀티스테이지 빌드를 쓰니까 빌드 도구(maven)와 소스코드는 최종 이미지에 포함되지 않아 300MB 이하로 줄었어요. 이건 실제로 겪어보면 배포 파이프라인 속도와 비용 절감에 큰 도움이 됩니다.[Docker - Best practices for writing Dockerfiles](https://docs.docker.com/develop/develop-images/dockerfile_best-practices/)

## Docker Compose로 여러 컨테이너 한방에 띄우기, 개발 환경 세팅이 이렇게 쉬울 줄이야

우리 프로젝트는 MySQL, Redis, Kafka 같은 의존 서비스가 많아요. 매번 각 서비스 설치하고 설정하는 것도 번거롭고, 버전 차이로 인한 문제도 잦았죠.

Docker Compose를 도입하고 나서는 `docker-compose.yml` 파일 하나로 모든 의존 서비스를 정의하고, `docker-compose up` 만으로 통째로 띄울 수 있게 됐어요. 예를 들어 이렇게요:

```yaml
docker-compose.yml
version: '3.8'
services:
  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: rootpass
      MYSQL_DATABASE: mydb
    ports:
      - "3306:3306"
  redis:
    image: redis:6.2
    ports:
      - "6379:6379"
```

이렇게 하니까 신규 개발자도 환경 세팅에 10분이면 충분하고, CI/CD 파이프라인에도 쉽게 통합할 수 있었습니다. Docker Compose가 여러 컨테이너를 관리하는 데 얼마나 편리한지 새삼 깨달았죠.[Docker Compose Overview](https://docs.docker.com/compose/)

## Testcontainers로 테스트 환경도 컨테이너화, 테스트 실패율이 확 줄었다

테스트 자동화에서 진짜 혁신은 Testcontainers 덕분에 왔어요. 예전에는 테스트용 DB를 따로 띄우거나, Mock 객체로 대체했는데, 환경 차이 때문에 테스트가 불안정했죠.

Testcontainers는 테스트 코드 내에서 실제 Docker 컨테이너를 띄우고, 테스트가 끝나면 자동으로 정리해줍니다. Spring Boot와도 자연스럽게 통합되어서, 예를 들어 JUnit5와 함께 이렇게 쓰면 됩니다:

```java
@SpringBootTest
@Testcontainers
public class UserRepositoryTest {

    @Container
    public static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.0")
            .withDatabaseName("testdb")
            .withUsername("test")
            .withPassword("test");

    @Autowired
    private UserRepository userRepository;

    @DynamicPropertySource
    static void mysqlProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", mysql::getJdbcUrl);
        registry.add("spring.datasource.username", mysql::getUsername);
        registry.add("spring.datasource.password", mysql::getPassword);
    }

    @Test
    void testUserSave() {
        User user = new User("alice");
        userRepository.save(user);
        assertThat(userRepository.findByName("alice")).isPresent();
    }
}
```

이렇게 하면 테스트가 실행될 때마다 MySQL 컨테이너가 자동으로 올라가고, 테스트가 끝나면 컨테이너가 내려갑니다. 덕분에 테스트 환경이 항상 깨끗하고 재현 가능해졌어요. 물론 컨테이너 띄우는 데 시간이 좀 걸리긴 하지만, 신뢰성 확보가 훨씬 중요하니까요.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)

## Spring Framework DI와 Testcontainers의 궁합, 통합 테스트가 더 편해진 이유

Testcontainers를 쓸 때 Spring의 의존성 주입(DI) 덕분에 컨테이너 라이프사이클 관리가 훨씬 수월해졌습니다. 컨테이너를 정적 필드로 선언하고 `@Container` 어노테이션을 붙이면, Spring이 테스트 실행 전에 컨테이너를 띄우고 종료 시점도 알아서 관리해주거든요.

또 `@DynamicPropertySource`를 이용해 컨테이너에서 생성된 DB URL, 포트 등을 Spring 환경 변수로 주입할 수 있어서, 별도의 설정 변경 없이 테스트 코드를 깔끔하게 유지할 수 있었습니다. 이런 점은 Spring Framework의 코어 기술 덕분이죠.[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)

## JVM 튜닝과 이미지 경량화, 배포 성능 최적화 팁

마지막으로, Docker 컨테이너로 Spring Boot 앱을 배포할 때 JVM 튜닝도 빼놓을 수 없습니다. 기본 JVM 옵션으로는 GC가 잦거나 메모리 사용이 비효율적일 수 있거든요.

저는 아래 옵션들을 주로 씁니다:

- `-Xms512m -Xmx512m` : 컨테이너 메모리 제한과 맞춰 고정 메모리 할당
- `-XX:+UseG1GC` : 최신 GC 알고리즘 사용
- `-XX:MaxRAMPercentage=75.0` : 컨테이너 메모리 대비 최대 RAM 사용 비율 지정

그리고 앞서 말한 이미지 경량화와 불필요한 서비스 제거를 병행하면, 배포 파이프라인이 훨씬 빠르고 안정적으로 돌아갑니다. 실제로 우리 팀은 이 조합 덕분에 배포 실패율이 30% 이상 줄었어요.[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance)

## 마치며: 이 조합이 가져다준 변화

- Dockerfile 최적화로 이미지 크기 3배 이상 줄이고 빌드 속도 개선
- Docker Compose로 개발 환경 세팅 10분 내외로 단축
- Testcontainers로 테스트 신뢰성 대폭 향상
- Spring DI로 컨테이너 라이프사이클 관리 편리
- JVM 튜닝과 이미지 경량화로 배포 안정성 확보

이건 처음엔 별거 아닌 것 같지만, 실제로 프로젝트에 적용해보면 개발 생산성과 운영 안정성이 눈에 띄게 좋아집니다. 특히 테스트 실패로 골머리 앓던 분들께 Testcontainers는 꼭 추천하고 싶어요.
