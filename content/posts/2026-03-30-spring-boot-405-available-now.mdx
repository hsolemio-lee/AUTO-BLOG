### "업데이트만 하면 다 해결될 줄 알았는데…"

최근 우리 팀이 Spring Boot 4.0.5로 업그레이드하면서 겪은 일화부터 시작해볼게요. 처음엔 그냥 버전만 올리면 끝날 줄 알았는데, 막상 돌려보니 보안 설정이 바뀌고 의존성 주입 방식도 조금씩 달라져서 애플리케이션 컨텍스트가 꼬이더라고요. 게다가 프로덕션 환경에서 성능 튜닝도 다시 해야 했고요. 이 글은 그런 경험을 바탕으로, Spring Boot 4.0.5 업그레이드 후에 꼭 챙겨야 할 보안과 성능 최적화 포인트를 현실적으로 정리한 겁니다.

## Spring Boot 4.0.5에서 보안 설정이 왜 더 까다로워졌나?

Spring Boot 4.0.5는 기본 보안 설정이 한층 강화됐어요. 예를 들어, HTTPS 강제 적용이 기본 권장사항으로 자리 잡았고, 보안 헤더 설정도 자동화되어 있죠. 하지만 이게 자동으로 다 해결되는 건 아니에요. 실제 프로덕션 환경에서는 다음과 같은 점을 직접 설정해야 합니다.

- **HTTPS 강제 적용**: `application.properties`에 `server.ssl.enabled=true`와 함께 인증서 경로를 정확히 지정해야 하고,
- **보안 헤더 추가**: `Content-Security-Policy`, `X-Content-Type-Options` 같은 헤더를 직접 설정하거나 Spring Security 설정에서 추가해야 하며,
- **OAuth2 및 JWT 인증**: 최신 OAuth2 표준과 JWT 토큰 기반 인증 방식을 적용해 사용자 인증을 강화하는 게 권장됩니다.

예를 들어, `SecurityConfig` 클래스에서 HTTPS 리다이렉트를 강제하고 보안 헤더를 추가하는 코드는 다음과 같습니다.

```java
@EnableWebSecurity
public class SecurityConfig extends WebSecurityConfigurerAdapter {

    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
            .requiresChannel()
                .anyRequest()
                .requiresSecure()
            .and()
            .headers()
                .contentSecurityPolicy("default-src 'self'")
                .and()
                .xssProtection()
                .and()
                .frameOptions().deny();
        // OAuth2, JWT 설정은 별도 config에서 처리
    }
}
```

처음엔 이게 별거 아닌 것 같지만, 실제로 HTTPS가 안 걸려 있으면 프로덕션에서 치명적인 보안 사고로 이어질 수 있어요. 그리고 Spring Boot 4.0.5부터는 이런 보안 설정이 기본값에 더 가까워졌기 때문에, 업그레이드 후에는 반드시 보안 설정을 꼼꼼히 점검해야 합니다[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

## Spring Framework 최신 코어 변경점, 의존성 주입과 애플리케이션 컨텍스트 주의

Spring Boot 4.0.5는 Spring Framework 최신 버전과 호환되도록 설계되었는데, 이 과정에서 의존성 주입 방식과 애플리케이션 컨텍스트 설정에 미묘한 변화가 있었습니다. 구체적으로는 다음과 같은 점을 주의해야 합니다.

- **`@Autowired` 필드 주입보다 생성자 주입 권장**: 최신 Spring Framework에서는 생성자 주입이 더 안정적이며 테스트하기 쉽다고 강조합니다.
- **`ApplicationContext` 초기화 시점 변경**: 일부 빈이 예상보다 늦게 초기화되거나, 프록시 객체 생성 방식이 바뀌어 순환 참조 문제가 발생할 수 있습니다.

예를 들어, 이전에는 필드 주입으로 잘 작동하던 코드가 4.0.5 업그레이드 후에 `NullPointerException`을 뱉는다면 생성자 주입으로 바꿔보는 게 빠른 해결책입니다.

```java
@Component
public class MyService {
    private final MyRepository repository;

    // 생성자 주입으로 변경
    public MyService(MyRepository repository) {
        this.repository = repository;
    }

    // 필드 주입(@Autowired) 대신 생성자 주입 권장
}
```

이 외에도 `@Configuration` 클래스 내에서 `@Bean` 메서드 호출 시 프록시 동작 방식이 바뀌어, 예상치 못한 빈 재생성 문제가 발생할 수 있으니 주의해야 합니다. 이런 변경점은 공식 문서의 코어 기술 섹션에서 자세히 설명하고 있으니 참고하세요[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

## JVM 튜닝과 캐시 활용으로 체감 성능 올리기

Spring Boot 4.0.5 업그레이드 후 성능이 느려졌다는 얘기를 종종 듣는데, 대부분 JVM 튜닝과 캐시 설정을 안 했기 때문입니다. Baeldung에서 권장하는 몇 가지 핵심 팁을 공유할게요.

- **JVM 힙 메모리 설정**: `-Xms2g -Xmx2g` 같이 최소/최대 힙 크기를 동일하게 맞춰 GC 오버헤드를 줄이세요.
- **G1 GC 사용**: `-XX:+UseG1GC` 옵션을 기본으로 사용하면 짧고 예측 가능한 GC가 가능합니다.
- **Spring Cache 활용**: `@Cacheable` 애노테이션으로 DB 쿼리 결과를 캐싱해 불필요한 호출을 줄이세요.
- **비동기 처리**: `@Async` 애노테이션과 `TaskExecutor`를 적절히 설정해 I/O 블로킹을 최소화합니다.
- **커넥션 풀 최적화**: HikariCP 설정에서 `maximumPoolSize`를 실제 트래픽에 맞게 조절하는 게 중요합니다.

예를 들어, 캐시 적용 간단 예시는 아래와 같습니다.

```java
@Service
public class UserService {

    @Cacheable(value = "users", key = "#userId")
    public User getUserById(Long userId) {
        // DB 조회 로직
    }
}
```

그리고 `application.properties`에서 캐시와 HikariCP 설정을 이렇게 해볼 수 있죠.

```properties
spring.cache.type=simple
spring.datasource.hikari.maximum-pool-size=20
```

이런 설정을 적용하면 실제로 요청당 응답 시간이 20~30%까지 개선되는 걸 경험할 수 있었습니다. JVM 튜닝과 캐시 활용은 꼭 병행해서 해야 효과가 극대화됩니다[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

## 로그와 모니터링, 업그레이드 후에 반드시 재점검해야 하는 이유

마지막으로, 업그레이드 후 로깅과 모니터링 설정을 다시 점검하는 게 생각보다 중요합니다. Spring Boot 4.0.5는 내부 로깅 라이브러리 버전도 업데이트되어 로그 포맷이나 로그 레벨 동작이 미묘하게 달라졌어요.

- **로그 포맷 통일**: JSON 포맷 로그를 쓰는 경우, 업그레이드 후 로그 필드가 달라져서 로그 분석 도구가 제대로 파싱 못 하는 경우가 있습니다.
- **로그 레벨 기본값 변경**: 디버그 레벨이 기본적으로 꺼져 있거나, 특정 패키지 로그가 너무 많아져서 로그가 노이즈가 될 수 있습니다.
- **모니터링 지표 변화**: Actuator 엔드포인트가 추가/변경되면서 기존 모니터링 대시보드가 깨질 수 있습니다.

예를 들어, `application.properties`에서 로그 레벨을 명시적으로 설정해주는 게 좋습니다.

```properties
logging.level.org.springframework=INFO
logging.level.com.mycompany=DEBUG
logging.pattern.console=%d{yyyy-MM-dd HH:mm:ss} - %msg%n
```

그리고 Actuator 설정도 확인해서 필요한 메트릭과 헬스체크를 활성화하세요.

```java
management.endpoints.web.exposure.include=health,info,metrics,httptrace
```

이런 점검을 안 하면, 문제 발생 시 원인 파악이 늦어지고 대응이 어려워집니다. 특히 프로덕션에서 장애가 터졌을 때 로그와 모니터링이 잘 안 되어 있으면 복구 시간이 길어지는 게 현실이죠[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).
