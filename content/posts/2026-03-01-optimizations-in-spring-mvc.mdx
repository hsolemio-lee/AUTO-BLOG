### 트래픽 폭주에 서버가 버벅일 때, 가장 먼저 손대야 할 부분은?

"요즘 우리 서비스가 갑자기 느려졌는데, 뭘 먼저 봐야 할까요?" 이런 질문, 백엔드 하다 보면 꼭 한번은 듣게 되죠. 저도 최근에 비슷한 문제를 겪으면서 Spring MVC 기반 애플리케이션을 어떻게 튜닝해야 할지 다시 정리해봤어요. 단순히 코드 최적화만이 답이 아니더라고요. 서버 설정부터 비동기 처리, 캐싱, 그리고 보안까지 챙겨야 진짜 체감 성능과 안정성이 올라갑니다.

## 내장 톰캣 설정 조정만으로도 체감 성능이 달라진다

Spring Boot 쓰면 내장 톰캣이 기본으로 딸려오는데, 기본 설정 그대로 쓰는 경우가 많아요. 그런데 톰캣 커넥터 설정을 조금만 손대도 성능 차이가 꽤 납니다. 예를 들어, `server.tomcat.max-threads` 기본값은 200인데, 요청량이 많으면 이걸 500 이상으로 올려서 동시 처리량을 늘릴 수 있어요. 물론 너무 높이면 메모리 부담이 커지니 서버 사양에 맞게 조절해야 합니다.

또 HTTP/2를 활성화하면 멀티플렉싱 덕분에 요청-응답 지연이 줄어듭니다. Spring Boot에서는 `server.http2.enabled=true`만 추가하면 되는데, HTTPS 환경에서만 동작하니 SSL 설정도 필수죠. 커넥션 타임아웃(`server.connection-timeout`)도 기본 30초에서 10초 정도로 줄이면, 느린 클라이언트가 연결을 오래 잡고 있는 걸 방지해 서버 자원 낭비를 막을 수 있어요.

```yaml
server:
  tomcat:
    max-threads: 500
  http2:
    enabled: true
  connection-timeout: 10000 # 10초
```

이 설정만 바꿔도 트래픽 몰릴 때 서버가 좀 더 버텨주는 걸 체감할 수 있습니다[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

## 비동기 요청 처리로 스레드 블로킹 문제 해결하기

Spring MVC는 기본적으로 요청 하나당 스레드 하나가 할당돼요. 그런데 DB 호출이나 외부 API 요청처럼 시간이 오래 걸리는 작업이 있으면 그 스레드가 블로킹돼서 전체 처리량이 떨어집니다. 이럴 때 `@Async`나 `Callable`, `DeferredResult` 같은 비동기 요청 처리 기능을 활용하면 스레드가 블로킹되지 않고 다른 요청을 처리할 수 있어요.

예를 들어, 아래처럼 컨트롤러 메서드를 `Callable`로 감싸면 Spring이 별도의 스레드풀에서 작업을 처리하고, 메인 스레드는 즉시 반환돼서 다른 요청을 받습니다.

```java
@GetMapping("/async-data")
public Callable<String> getAsyncData() {
    return () -> {
        // 오래 걸리는 작업 시뮬레이션
        Thread.sleep(3000);
        return "완료";
    };
}
```

이렇게 하면 3초 동안 스레드가 블로킹되지 않고, 서버는 더 많은 요청을 동시에 처리할 수 있죠. 단, 비동기 처리 시 스레드풀 크기, 타임아웃 설정을 잘 조절하지 않으면 오히려 리소스 낭비가 될 수 있으니 주의해야 합니다[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

## 캐시 전략 없이는 데이터베이스가 병목된다

우리 팀에서 한창 DB 부하 때문에 고생할 때, Spring Cache를 도입한 게 큰 전환점이었어요. 특히 자주 조회하지만 자주 변경되지 않는 데이터는 캐시에 올려두면 DB 호출 횟수를 확 줄일 수 있습니다. Spring Boot에서는 `@EnableCaching`과 `@Cacheable` 애노테이션만 붙이면 Redis, Ehcache 같은 다양한 캐시 솔루션과 쉽게 연동돼서 금방 적용할 수 있어요.

```java
@EnableCaching
@SpringBootApplication
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}

@Service
public class ProductService {
    @Cacheable(value = "products", key = "#id")
    public Product getProductById(Long id) {
        // DB 호출
        return productRepository.findById(id).orElse(null);
    }
}
```

이렇게 캐시를 쓰면 데이터베이스 부하가 눈에 띄게 줄고, 응답 속도도 30~50% 이상 개선된 경우도 많았습니다. 다만 캐시 무효화 정책을 꼼꼼히 설계하지 않으면 오래된 데이터가 응답될 수 있으니 주의해야 합니다[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

## Spring Security로 기본 보안부터 탄탄히 다지기

성능만큼 중요한 게 보안이죠. Spring Security는 CSRF 보호, 세션 관리 강화, 권한 기반 접근 제어 같은 기능을 기본 제공해서 백엔드 안정성에 필수적입니다. 특히 CSRF 토큰을 활성화하면 POST, PUT, DELETE 같은 상태 변경 요청에 대해 악의적 요청을 막을 수 있어요.

```java
@EnableWebSecurity
public class SecurityConfig extends WebSecurityConfigurerAdapter {
    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
            .csrf().csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
            .and()
            .authorizeRequests()
                .antMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            .and()
            .sessionManagement()
                .maximumSessions(1)
                .maxSessionsPreventsLogin(true);
    }
}
```

이 설정은 관리자 페이지 접근을 관리자 권한으로 제한하고, 한 계정으로 동시 로그인 세션을 1개로 제한해 세션 하이재킹 위험을 줄여줍니다. 보안 설정을 너무 느슨하게 하면 나중에 큰 사고로 이어지니, 초기부터 꼼꼼히 챙기는 게 좋아요[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

## 실제 운영 환경에서 이 최적화들이 어떻게 작동했나

우리 팀은 최근 대규모 트래픽을 처리하는 서비스에서 위 방법들을 조합해 적용했는데, 특히 비동기 처리와 캐시 도입 이후 평균 응답 시간이 400ms에서 250ms로 40% 이상 줄었어요. 톰캣 스레드 수를 200에서 400으로 늘리고 HTTP/2를 켠 것도 체감 성능 향상에 큰 몫을 했습니다.

GitHub 엔지니어링 블로그에서도 대규모 트래픽 백엔드에서 지연 시간 줄이기 위해 서비스 간 호출 최적화, 캐시 전략, 비동기 처리 등을 적극 활용한다고 하니, 우리 사례가 크게 벗어나지 않는다는 걸 알 수 있었습니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

## 마무리하며

처음엔 톰캣 설정 바꾸고 비동기 처리 적용하는 게 별거 아닌 것 같지만, 실제로 해보면 서버가 훨씬 안정적으로 버티고 응답 속도도 눈에 띄게 좋아집니다. 그리고 캐시와 보안은 한 번 잘 설계해두면 장기적으로 유지보수와 운영 부담을 크게 줄여주죠.

이 글에서 다룬 최적화는 모두 실무에서 검증된 방법들이니, 내 서비스 상황에 맞게 하나씩 적용해보길 추천합니다. 특히 비동기 처리와 캐시 도입은 꼭 성능 병목 구간을 먼저 프로파일링해서 적용하는 게 실패 확률을 줄이는 팁입니다.
