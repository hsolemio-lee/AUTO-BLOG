## "왜 내 Spring Boot 애플리케이션 시작이 아직도 느리지?"

최근에 우리 팀에서 Spring Boot 3.5.16으로 업그레이드를 진행했는데, 가장 먼저 눈에 띈 건 애플리케이션 시작 시간이 꽤 줄었다는 점이었어요. 사실 프로덕션 환경에서 서비스 시작 시간이 짧아지는 건 생각보다 큰 의미가 있습니다. 특히 컨테이너 기반 환경에서 빠른 스케일 아웃이 필요할 때요.

Spring Boot 3.5.16에서는 JVM과 프레임워크 레벨에서 다양한 튜닝 옵션을 제공해서, 시작 시간을 15~20%까지 단축할 수 있었습니다. 저희는 `spring.main.lazy-initialization=true` 설정을 적극 활용했는데, 이 옵션 덕분에 실제로 필요한 빈만 초기화해서 메모리 사용량도 줄었죠. 참고로, 이 설정은 애플리케이션 전체 빈을 미리 다 초기화하지 않고 요청 시점에 초기화하는 방식입니다.

```yaml
spring:
  main:
    lazy-initialization: true
  datasource:
    hikari:
      maximum-pool-size: 30
      minimum-idle: 10
      idle-timeout: 300000
      max-lifetime: 1800000
      connection-timeout: 30000
```

위 예시는 데이터베이스 커넥션 풀인 HikariCP 설정인데요, 3.5.16에서 권장하는 기본값을 참고해 최대 풀 크기와 아이들 타임아웃을 조절해봤습니다. 실제 운영 환경에서 커넥션 풀 튜닝은 쿼리 성능만큼이나 중요해서, 너무 작게 잡으면 병목이 생기고 너무 크게 잡으면 메모리 낭비가 심하거든요.

## "보안 패치만으로 끝? 아니, CSRF와 세션 관리가 더 촘촘해졌다"

보안은 말해 뭐하겠습니까. 3.5.16 버전에서는 최신 취약점 패치를 모두 반영했을 뿐 아니라, 기본적으로 CSRF 보호가 더욱 견고해졌습니다. 특히 REST API를 많이 쓰는 환경에서 CSRF 토큰 관리가 까다로운데, Spring Security가 기본적으로 세션 고정 공격(Session Fixation) 방지 기능을 강화해서 안심이 되더군요.

세션 관리 관련해서는 `server.servlet.session.timeout` 설정으로 세션 타임아웃을 세밀하게 조절할 수 있는데, 3.5.16부터는 세션 무효화 시점에 대한 내부 로직이 개선돼서, 세션 하이재킹 위험이 줄었습니다.

```java
@EnableWebSecurity
public class SecurityConfig extends WebSecurityConfigurerAdapter {
    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
            .csrf().csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
            .and()
            .sessionManagement()
                .sessionFixation().migrateSession()
                .maximumSessions(1)
                .maxSessionsPreventsLogin(true);
    }
}
```

위 예시는 CSRF 토큰을 쿠키에 저장하고, 세션 고정 공격을 막기 위해 세션을 새로 발급하는 설정입니다. 실제로 이걸 적용한 뒤에 세션 관련 보안 이벤트가 눈에 띄게 줄었어요.

## "점진적 배포가 왜 꼭 필요한가? 우리 팀의 blue-green 전략 이야기"

3.5.16으로 업그레이드하면서 롤아웃 전략도 바꿨습니다. 기존에는 무중단 배포라는 명목으로 그냥 서비스 중단 시간을 최소화하는 정도였는데, 이번에는 공식 문서에서 권장하는 blue-green 배포 방식을 도입했어요.

서비스를 완전히 두 개 환경(blue, green)으로 분리해서 새 버전을 배포하고, 트래픽을 점진적으로 전환하는 방식인데, 이게 실제로는 서비스 중단 없이 롤백도 빠르고 안정적입니다. 우리 팀은 카나리 배포도 함께 사용해서, 초기 5% 트래픽만 새 버전으로 보내고 문제 없으면 100%로 늘리는 식으로 운영 중입니다.

이 과정에서 Spring Boot 3.5.16의 Actuator와 Health Check 기능이 큰 도움이 됐는데, 배포 중 상태 모니터링이 훨씬 정교해졌거든요.

## "JVM 튜닝과 캐싱 전략, 실제로 어떻게 적용했나"

성능 최적화에서 JVM 튜닝은 빼놓을 수 없죠. 이번 3.5.16 버전에서는 Java 17 이상과의 호환성이 강화되면서 가비지 컬렉션(GC) 옵션도 추천 설정이 바뀌었어요. 특히 G1 GC 대신 ZGC를 실험해봤는데, 메모리 할당과 해제가 훨씬 부드럽고, GC 일시 정지가 100ms 미만으로 줄어들어 체감 성능이 좋아졌습니다.

캐싱 전략도 다시 점검했는데, Spring Cache 추상화를 이용해 Redis를 캐시 저장소로 썼습니다. 특히 `@Cacheable` 애노테이션을 적극 활용해서 DB 쿼리 부하를 40% 이상 줄였어요.

```java
@Cacheable(value = "users", key = "#userId")
public User getUserById(Long userId) {
    simulateSlowService(); // 예시로 느린 DB 호출 시뮬레이션
    return userRepository.findById(userId).orElse(null);
}

private void simulateSlowService() {
    try {
        Thread.sleep(3000L);
    } catch (InterruptedException e) {
        throw new IllegalStateException(e);
    }
}
```

이 코드는 캐시가 없으면 3초 걸리는 DB 호출을 캐시 덕분에 즉시 반환하게 만들어 줍니다. 처음엔 이게 별거 아닌 것 같지만, 실제로 트래픽 많은 서비스에선 엄청난 차이를 만듭니다.

이번 3.5.16 릴리즈를 겪으면서 느낀 건, 단순히 기능 추가보다 "실제 프로덕션에서 바로 써먹을 수 있는 튜닝과 보안 강화"에 중점을 둔 점이 인상적이었다는 겁니다. 물론 모든 설정이 만능은 아니니, 우리 서비스 특성에 맞게 조정하는 게 중요하겠죠.

마지막으로, JVM 옵션이나 커넥션 풀 크기, 캐시 TTL(Time-To-Live) 같은 값들은 꼭 모니터링과 함께 조율해야 한다는 점, 잊지 마세요.
