### "어? 갑자기 배치가 안 돌아가네?"

최근에 우리 팀에서 Spring Batch 5.x에서 6.x로 업그레이드를 진행했는데, 처음에 이 메시지가 자주 떠서 꽤 당황했어요. 6.x 버전이 나오면서 Spring Boot 3.x, Spring Framework 6와 맞물려 대대적인 리팩토링과 API 변경이 있었거든요. 기존 코드를 고치지 않으면 빌드조차 안 되더라고요. 그래서 이번 글에서는 저희가 겪은 업그레이드 과정과 함께, 성능 튜닝, 보안 강화, 그리고 프로덕션 환경에서 무리 없이 롤아웃하는 방법까지 공유하려고 합니다.

---

## Spring Batch 6.x, 왜 이렇게 큰 변화가 있었을까?

Spring Batch 6.x는 Java 17 이상을 요구하면서 최신 JVM 기능을 적극 활용할 수 있도록 설계됐어요. 동시에 Spring Boot 3.x와 Spring Framework 6의 변화에 맞춰 내부 구조가 꽤 많이 바뀌었죠. 예를 들어, `JobLauncher`나 `StepBuilder` 같은 핵심 API가 일부 deprecated 되고, 새로운 방식으로 바뀌었어요.

이건 단순히 버전 업그레이드가 아니라, 앞으로의 유지보수와 확장성을 위한 큰 밑그림이라고 볼 수 있는데요. 덕분에 성능도 좀 더 좋아지고, 보안도 강화됐죠. 다만, 기존 코드를 그대로 쓰면 컴파일 에러가 나거나 런타임에 이상 동작이 발생할 수 있어서 반드시 코드 수정이 필요합니다.

> 참고로 Spring Boot 공식 문서에는 "Spring Batch 6.x는 Spring Boot 3.x 및 Spring Framework 6와의 호환성을 위해 주요 리팩토링과 API 변경이 포함되어 있어, 업그레이드 시 기존 코드의 수정이 필요하다"고 명시되어 있어요.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)


## Java 17 이상 필수, 성능 최적화는 어떻게 달라졌나?

Java 17 이상을 요구한다는 건, 곧 최신 JVM 기능을 쓸 수 있다는 뜻인데요. 저희는 실제로 업그레이드하면서 JVM 튜닝과 GC 최적화에 좀 더 집중하게 됐어요. 특히 배치 작업은 메모리 사용 패턴이 독특해서, GC가 자주 발생하면 전체 작업 지연으로 직결되거든요.

예를 들어, 저희는 다음과 같은 JVM 옵션을 적용했습니다:

```bash
-XX:+UseG1GC \
-XX:MaxGCPauseMillis=200 \
-XX:+ParallelRefProcEnabled \
-XX:InitiatingHeapOccupancyPercent=45
```

G1 GC를 기본으로 쓰면서 최대 GC 일시 정지 시간을 200ms로 제한했고, 병렬 참조 처리도 켰어요. 이 설정 덕분에 배치 잡이 중간에 멈추거나 지연되는 일이 눈에 띄게 줄었죠.

또한, Spring Batch 6.x는 내부적으로 커넥션 풀과 트랜잭션 관리도 개선돼서, 데이터베이스 I/O 병목 현상이 완화됐습니다. 물론, 데이터베이스 커넥션 풀 설정도 꼼꼼히 조정해야 하는데, HikariCP 같은 풀을 쓴다면 최소 20~50 사이즈로 시작해 부하에 맞게 튜닝하는 걸 추천해요.

> "Spring Batch 6.0.5 및 6.1.0-M1 버전은 성능 최적화를 위한 내부 개선과 함께, Java 17 이상을 요구하여 최신 JVM 기능을 활용할 수 있다"는 점도 공식 문서에 명확히 나와 있습니다.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)


## 보안도 놓칠 수 없다, Spring Security 6과의 통합

배치 작업은 보통 백엔드에서 조용히 돌아가지만, 보안은 항상 신경 써야 할 부분이죠. 이번 6.x 버전부터는 Spring Security 6과 기본 통합되어 배치 실행 시 인증과 권한 부여를 더 세밀하게 제어할 수 있어요.

예를 들어, 특정 배치 잡은 오직 관리자 권한을 가진 사용자만 실행하도록 설정할 수 있습니다. 실제로 저희는 `JobLauncher`를 호출하는 REST API에 아래와 같이 권한 체크를 걸었죠:

```java
@EnableWebSecurity
public class BatchSecurityConfig {
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/batch/run").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .httpBasic();
        return http.build();
    }
}
```

이렇게 하면 `/batch/run` 엔드포인트는 관리자만 접근 가능하게 되고, 배치 작업 실행을 무단으로 막을 수 있죠. 물론, 배치 내에서 JobParameters에 민감한 정보가 있다면 암호화도 고려해야 합니다.

> Spring Batch 6.x는 보안 강화 측면에서 기본적으로 Spring Security 6과 통합되어, 배치 작업 실행 시 인증 및 권한 부여를 세밀하게 제어할 수 있습니다.[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)


## 프로덕션 배포, 무작정 바꾸면 큰일 난다

업그레이드 후 가장 조심해야 할 부분이 바로 프로덕션 롤아웃이에요. 배치 작업은 업무에 직접적인 영향을 주기 때문에, 갑자기 새 버전으로 바꾸면 장애 위험이 큽니다.

그래서 저희는 점진적 배포 전략을 썼어요. 구체적으로는 블루-그린 배포와 카나리 배포를 병행했는데요. 예를 들어, 새 배치 서버를 별도로 띄워서 일부 작업만 돌려보고, 문제 없으면 점차 트래픽을 옮기는 식입니다.

이 과정에서 중요한 건 배치 메타데이터 테이블(`BATCH_JOB_EXECUTION` 등)의 호환성인데, 6.x에서 스키마가 바뀌었을 수도 있으니 반드시 백업과 테스트를 거쳐야 해요.

> "Spring Batch 6.x로 업그레이드 시, 프로덕션 환경에서의 롤아웃 전략으로 점진적 배포(블루-그린, 카나리 배포)를 권장하며, 이는 배치 작업의 중단 없는 서비스 제공에 효과적이다"는 점도 참고하세요.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)

### 실제로 업그레이드하면서 쓴 코드 예시

기존 5.x에서 6.x로 넘어가면서 `JobBuilderFactory`와 `StepBuilderFactory` 사용법이 조금 바뀌었는데요, 아래는 6.x 스타일로 배치 잡을 정의하는 간단한 예입니다:

```java
@Bean
public Job exampleJob(JobRepository jobRepository, PlatformTransactionManager transactionManager) {
    Step step = new StepBuilder("step1", jobRepository)
        .tasklet((contribution, chunkContext) -> {
            System.out.println("Hello, Spring Batch 6.x!");
            return RepeatStatus.FINISHED;
        }, transactionManager)
        .build();

    return new JobBuilder("exampleJob", jobRepository)
        .start(step)
        .build();
}
```

기존에 `JobBuilderFactory`를 쓰던 것과 달리, 생성자에 `JobRepository`를 직접 넣어주는 방식으로 바뀌었어요. 처음엔 이게 좀 번거롭지만, 내부 구현이 더 명확해져서 유지보수성은 좋아졌다고 느꼈습니다.

### 정리하며

- Spring Batch 6.x는 Spring Boot 3.x, Spring Framework 6에 맞춰 대대적인 리팩토링과 API 변경이 있어 기존 코드 수정이 필수입니다.
- Java 17 이상을 요구하며, JVM 튜닝과 GC 최적화가 중요해졌고, 데이터베이스 커넥션 풀 설정도 꼼꼼히 해야 합니다.
- 보안이 강화되어 Spring Security 6과 통합, 배치 작업 실행 권한을 세밀하게 제어할 수 있습니다.
- 프로덕션 롤아웃은 블루-그린, 카나리 배포 같은 점진적 배포 전략을 써서 중단 없는 서비스를 유지해야 합니다.

처음엔 버전 업그레이드가 번거롭고 귀찮지만, 장기적으로 보면 최신 기술 스택과 보안, 성능 측면에서 훨씬 이득이 큽니다. 저희 팀도 이번 업그레이드 덕분에 배치 안정성이 눈에 띄게 좋아졌고, 운영 중인 서비스 장애도 크게 줄었어요. 여러분도 꼭 한번 도전해보시길 추천합니다!
