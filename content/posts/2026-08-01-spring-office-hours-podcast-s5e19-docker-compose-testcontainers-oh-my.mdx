## "내 로컬에서 왜 안 돌아가?" 문제를 Docker로 어떻게 줄였을까

"아니, 내 컴퓨터에선 잘 되는데 왜 CI에선 안 되지?" 이 질문, 한 번쯤은 다들 해봤을 겁니다. 저도 그랬고요. 특히 Spring 백엔드 개발하면서 데이터베이스 버전이나 환경 설정이 조금만 달라도 테스트가 깨지는 순간, 진짜 멘탈이 나가죠. 그래서 시작한 게 Docker 도입이었어요. 

Dockerfile을 제대로 써서 이미지 빌드 속도를 올리고, Compose로 여러 컨테이너를 묶어 로컬에서 똑같은 환경을 띄우는 거죠. 그리고 Testcontainers로 테스트할 때마다 진짜 컨테이너를 띄워서 외부 의존성을 격리하는 방법까지. 이 조합이 저희 팀 개발 생산성을 얼마나 올렸는지 체감이 확 옵니다.


## Dockerfile, 이렇게 쓰면 빌드 속도와 안정성 두 마리 토끼 잡는다

처음 Dockerfile 짤 때는 그냥 `FROM openjdk:11-jdk` 딱 하나만 쓰고, 소스 복사하고 빌드하는 식이었어요. 근데 이러면 빌드 속도가 너무 느리고, 이미지 크기도 커서 배포할 때 부담이 컸죠.

그래서 Docker 공식 문서에서 권장하는 베스트 프랙티스를 적용해봤습니다. 

- **레이어 캐싱을 최대한 활용하기**: 자주 바뀌지 않는 부분(예: 의존성 설치)은 먼저 복사하고, 소스 코드는 나중에 복사해서 변경 시 전체 빌드가 다시 안 되도록.
- **최소 베이스 이미지 사용**: `openjdk:11-jdk` 대신 `openjdk:11-jdk-slim` 같은 경량 이미지로 사이즈 줄이기.

아래는 제가 실제로 쓰는 Dockerfile 예시입니다:

```Dockerfile
# 베이스 이미지로 슬림 버전 사용
FROM openjdk:11-jdk-slim

# 작업 디렉토리 설정
WORKDIR /app

# 의존성 캐싱을 위해 먼저 빌드 스크립트와 의존성 파일만 복사
COPY build.gradle settings.gradle ./

# 의존성 다운로드
RUN ./gradlew dependencies --no-daemon

# 소스 코드 복사
COPY src ./src

# 애플리케이션 빌드
RUN ./gradlew bootJar --no-daemon

# 실행 명령
CMD ["java", "-jar", "build/libs/myapp.jar"]
```

이렇게 하니까 이미지 빌드 시간이 이전 대비 40% 이상 단축됐고, 이미지 크기도 300MB에서 150MB로 거의 반토막 났어요. 안정성도 덩달아 좋아졌고요. 이건 실제로 겪어보면 체감 확실합니다.[Docker - Best practices for writing Dockerfiles](https://docs.docker.com/develop/develop-images/dockerfile_best-practices/)


## Docker Compose로 로컬 개발 환경, 이렇게 간단해도 되나 싶을 정도

Spring 백엔드가 점점 마이크로서비스화되면서 DB, Redis, Kafka 같은 여러 서비스가 필요해졌어요. 매번 하나하나 띄우고 설정하는 게 너무 귀찮아서 Docker Compose를 도입했죠.

Compose 덕분에 `docker-compose.yml` 하나만 있으면 로컬에서 서비스 전체를 통째로 띄울 수 있어요. 의존성 설정도 한번에 해결되고, 환경 변수 관리도 편해집니다. 

예를 들어, 저희는 이렇게 씁니다:

```yaml
dversion: '3.8'
services:
  app:
    build: .
    ports:
      - "8080:8080"
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/mydb
    depends_on:
      - db

  db:
    image: postgres:13
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
      POSTGRES_DB: mydb
    ports:
      - "5432:5432"
```

Compose로 띄우면 개발자 누구나 동일한 환경에서 개발할 수 있고, 통합 테스트도 쉽게 할 수 있어요. 의존성 문제로 인한 "내 로컬에선 되는데" 문제를 확실히 줄여줍니다.[Docker Compose Overview](https://docs.docker.com/compose/)


## Testcontainers로 테스트 신뢰성 높이기: 진짜 컨테이너를 테스트에 쓴다니!

테스트 환경에서 DB나 메시지 큐 같은 외부 리소스를 어떻게 할지 고민 많으시죠? Mock 쓰면 편하지만 실제 환경과 다르니 버그가 숨어있고, 로컬에 직접 설치하면 환경 차이로 깨질 위험이 큽니다.

그래서 Testcontainers를 도입했는데, 이건 진짜 Docker 컨테이너를 테스트 시점에 띄워서 격리된 환경을 만들어줍니다. Spring Boot는 공식적으로 이걸 지원해서 설정도 간단해요.

예를 들어, PostgreSQL 컨테이너를 띄워서 통합 테스트하는 코드:

```java
@SpringBootTest
@Testcontainers
public class UserRepositoryTest {

    @Container
    public static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:13")
            .withDatabaseName("testdb")
            .withUsername("user")
            .withPassword("pass");

    @Autowired
    private UserRepository userRepository;

    @DynamicPropertySource
    static void properties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Test
    void testSaveAndFind() {
        User user = new User(null, "testuser");
        userRepository.save(user);
        assertThat(userRepository.findById(user.getId())).isPresent();
    }
}
```

이렇게 하면 테스트할 때마다 진짜 DB 컨테이너가 뜨니까, 테스트 신뢰도와 재현성이 확 올라갑니다. 물론 컨테이너 띄우는 데 시간이 좀 걸려서 테스트 속도는 약간 느려질 수 있지만, 안정성을 위해선 충분히 감수할 만한 트레이드오프죠.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)


## Spring Framework가 Docker 환경에서 더 빛나는 이유

Spring의 코어 기술들, 특히 의존성 주입(DI)과 애플리케이션 컨텍스트 관리가 Docker 컨테이너 환경에서 참 잘 맞아요. 컨테이너 환경은 애플리케이션을 여러 인스턴스로 나누고 격리해서 실행하는데, Spring은 이런 구조에서 필요한 빈 관리와 라이프사이클 제어를 유연하게 지원합니다.

덕분에 Docker로 배포할 때도, 컨테이너가 재시작되거나 스케일링돼도 애플리케이션 상태 관리가 깔끔하죠. 그리고 Testcontainers 같은 도구와도 자연스럽게 통합됩니다.[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)


## Docker, Compose, Testcontainers를 묶으면 개발 생산성과 신뢰성이 이렇게 달라진다

제가 직접 경험한 바로는 이 세 가지 도구를 함께 쓰면 개발 속도가 눈에 띄게 빨라지고, 테스트 신뢰성도 확 올라갑니다. 

- **환경 차이 문제 감소**: 로컬, CI, 프로덕션 환경이 거의 동일해져서 "내 컴퓨터에선 되는데" 문제를 줄임
- **테스트 격리 보장**: Testcontainers로 외부 리소스 격리해서 테스트 간섭 최소화
- **배포 안정성 향상**: Docker 이미지 빌드 최적화로 배포 시간 단축 및 이미지 크기 감소

물론 초기 세팅과 학습 비용이 있긴 한데, 장기적으로 보면 유지보수 비용 절감과 개발자 만족도 상승으로 충분히 보상받습니다. 

이 조합을 아직 안 써봤다면, 꼭 한 번 시도해보세요. 특히 Spring Boot 프로젝트라면 공식 문서와 커뮤니티 자료가 잘 되어 있어서 진입 장벽도 낮습니다.
