## "왜 이 아키텍처 결정은 나중에 문제를 만든 걸까?"

팀에서 새로운 백엔드 시스템을 설계할 때, 한 번 내린 아키텍처 결정이 시간이 지나면서 발목을 잡는 경우를 많이 봤을 거예요. 그때마다 ‘왜 이걸 이렇게 했지?’ 하면서 뒤늦게 후회하고, 결정 과정이 제대로 기록되어 있지 않아 혼란이 커지는 경우도 허다하죠. 저도 비슷한 경험이 많았는데, 그래서 Bliki를 활용한 아키텍처 결정 기록(ADR) 방식을 도입해봤습니다.


## Bliki가 ADR 문서화에 딱인 이유

Bliki는 위키(Wiki)와 블로그(Blog)의 장점을 합친 도구인데, 아키텍처 결정 기록을 남기기에 정말 적합해요. 기본적으로 각 ADR 문서는 독립된 페이지처럼 다룰 수 있어서, 결정 배경, 선택한 옵션, 대안, 그리고 무엇보다 트레이드오프를 명확히 정리할 수 있죠. 

실제 백엔드 시스템에서는 단순히 ‘이걸 선택했다’는 기록만으로는 부족해요. 왜 선택했는지, 어떤 대안이 있었는지, 그리고 선택에 따른 단점과 마이그레이션 경로까지 꼼꼼히 남겨야 나중에 문제가 생겼을 때 빠르게 대응할 수 있습니다. Martin Fowler가 마이크로서비스 아키텍처를 설명하면서도 이런 ADR 기록의 중요성을 강조한 것도 같은 맥락이에요[Martin Fowler - Microservices](https://martinfowler.com/articles/microservices.html).


## 실제 사례: 우리 팀이 Bliki로 ADR을 관리하는 방법

우리 팀은 GitHub 저장소 내에 Bliki를 구축하고, 아키텍처 결정마다 다음과 같은 형식으로 문서화하고 있어요.

```markdown
# ADR-001: 데이터베이스 샤딩 도입 결정

## 배경
- 트래픽 증가로 단일 DB가 병목 현상 발생

## 선택한 옵션
- MongoDB 샤딩 기능 활용

## 대안
- 수평 확장 가능한 NewSQL 도입 검토

## 트레이드오프
- 샤딩으로 읽기 성능 향상, 쓰기 복잡도 증가

## 마이그레이션 경로
1. 신규 샤드 클러스터 구축
2. 점진적 데이터 분산 및 테스트
3. 기존 DB에서 트래픽 점진 이전

## 참고
- [MongoDB 샤딩 공식 문서](https://docs.mongodb.com/manual/sharding/)
```

이렇게 각 ADR에 마이그레이션 경로를 명확히 적어두니, 실제 전환 시나리오를 팀원 모두가 이해할 수 있고, 위험 요소도 사전에 대비할 수 있더라고요. 단순히 결정만 기록하는 것과는 차원이 달라요.


## Bliki ADR에 CI/CD 자동화 붙이면 좋은 점

문서가 많아지면 관리가 어렵죠. 그래서 우리는 GitHub Actions를 활용해 ADR 문서의 포맷 검증과 최신 상태 유지 작업을 자동화했습니다. 예를 들어, 새 ADR이 PR로 올라오면 다음 작업을 수행해요:

- Markdown 문법 및 필수 필드(배경, 대안, 트레이드오프, 마이그레이션 경로) 검증
- 중복된 ADR 제목이나 번호 체크
- 변경 사항을 팀 슬랙 채널에 알림 전송

간단한 GitHub Actions 워크플로우 예시는 다음과 같습니다.

```yaml
name: Validate ADR

on:
  pull_request:
    paths:
      - 'adr/**/*.md'

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Validate Markdown
        run: |
          for file in adr/*.md; do
            if ! grep -q '## 배경' "$file"; then
              echo "배경 섹션 누락: $file"
              exit 1
            fi
            # 추가 검증 로직 삽입 가능
          done

      - name: Notify Slack
        if: success()
        uses: slackapi/slack-github-action@v1.23.0
        with:
          channel-id: 'C12345678'
          slack-message: '새로운 ADR PR이 승인 대기 중입니다.'
        env:
          SLACK_BOT_TOKEN: ${{ secrets.SLACK_BOT_TOKEN }}
```

이렇게 하니 ADR 문서가 항상 최신 상태로 유지되고, 팀 내 공유도 자연스럽게 이루어집니다. Microsoft 클라우드 디자인 패턴 문서에서도 이런 기록과 공유 방식을 권장하고 있죠[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/).


## Bliki ADR, 팀 커뮤니케이션과 의사결정 투명성에 미친 영향

GitHub 엔지니어링 블로그 사례를 보면, 대규모 시스템에서 Bliki를 활용한 ADR 관리가 팀 간 커뮤니케이션과 의사결정 투명성을 크게 높였다고 합니다. 우리 팀도 비슷한 경험을 했는데요, 예전에는 결정이 구두로만 전달되거나 산발적으로 기록되어 혼선이 많았지만, 이제는 모든 결정 근거가 문서화되어 새로 합류한 엔지니어도 빠르게 맥락을 이해할 수 있어요[GitHub Engineering Blog](https://github.blog/category/engineering/).


## 처음 시작할 때 꼭 기억해야 할 Bliki ADR 작성 팁

- **결정을 내릴 때마다 즉시 기록하자**: 시간이 지나면 잊기 쉽습니다.
- **트레이드오프를 솔직하게 적자**: 완벽한 결정은 없습니다. 단점도 공유해야 팀이 더 나은 선택을 할 수 있어요.
- **마이그레이션 경로를 구체적으로 작성하자**: 점진적 전환 계획이 있으면 실제 적용 시 리스크가 줄어듭니다.
- **자동화 도구와 연동해 문서 품질을 유지하자**: CI/CD와 연동하면 문서가 방치되는 걸 막을 수 있습니다.


## 마치며

Bliki로 ADR을 관리하는 건 처음에 약간의 귀찮음이 있지만, 실제로 해보면 팀의 의사결정 투명성이 크게 올라가고, 나중에 문제 발생 시 빠른 대응이 가능해집니다. 특히 백엔드 시스템처럼 복잡하고 변화가 잦은 환경에서는 ‘왜 이걸 이렇게 했지?’라는 질문에 명확한 답을 줄 수 있다는 점이 큰 장점이에요. 

한 가지 단점이라면, 문서가 많아지면 관리가 번거로울 수 있는데, 이 부분은 앞서 소개한 CI/CD 자동화로 충분히 극복 가능합니다. 

다음에 아키텍처 결정할 때는 꼭 Bliki ADR을 써보세요. 나중에 분명히 고마워할 겁니다.
