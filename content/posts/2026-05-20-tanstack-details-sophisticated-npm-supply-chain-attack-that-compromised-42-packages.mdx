## "내가 쓴 패키지가 갑자기 이상한 코드를 심었다고?"  
최근 TanStack이 공개한 npm 공급망 공격 사례를 접하면서, 나도 모르게 쓰던 패키지들이 해킹에 연루됐다는 사실에 등골이 오싹했다. 이번 공격은 단순한 악성코드 삽입이 아니라 42개의 패키지를 동시에 타깃으로 한 정교한 전략이었다. 우리 백엔드 개발자 입장에서 이런 공격을 어떻게 감지하고, 막고, 나아가 예방할 수 있을지 진지하게 고민해볼 필요가 있다.

---

## TanStack 공격, 왜 이렇게 까다로웠을까?  
이번 공격의 핵심은 ‘공급망’ 자체를 노렸다는 점이다. npm 생태계에서 한 번 침투하면 수많은 프로젝트에 악영향을 줄 수 있다. TanStack이 밝힌 바로는, 공격자는 42개의 패키지에 악성 코드를 몰래 심었고, 이를 통해 사용자 환경에서 원격 명령 실행과 같은 치명적인 권한 탈취가 가능했다.

특히 이 공격이 까다로운 이유는 다음과 같다:

- **다수 패키지 동시 감염:** 단일 패키지가 아니라 연관된 여러 패키지를 한꺼번에 타깃으로 삼아 탐지 난이도를 높임
- **점진적 배포:** 한꺼번에 대량 배포하지 않고, 점진적으로 악성 버전을 퍼뜨려 의심을 피함
- **정상 코드와 혼합:** 악성 코드가 정상 기능 코드와 섞여 있어 코드 리뷰만으로는 발견이 어려움

이런 점들이 백엔드 서비스에서 npm 의존성을 관리할 때 큰 위험 요소가 될 수 있음을 알게 되었다.

---

## npm 패키지에서 이상 징후를 어떻게 찾아낼까?  
실제로 이런 공격을 막으려면, 단순히 버전 업데이트만 체크하는 걸 넘어서야 한다. 내가 최근에 적용해본 방법 중 효과적이었던 걸 공유한다.

### 1. 패키지 무결성 검사 (Integrity Check)
npm은 기본적으로 `package-lock.json`에 해시값을 저장하는데, 이걸 활용해서 의존성 트리 전체의 무결성을 주기적으로 검증한다. 예를 들어 `npm ci` 명령어는 `package-lock.json`과 일치하지 않는 패키지는 설치하지 않도록 돕는다.

```bash
npm ci --prefer-offline
```

이렇게 하면, lock 파일과 실제 설치된 패키지 간 불일치를 어느 정도 방지할 수 있다. 하지만 이것만으로는 공격자의 악성 코드 삽입을 완벽히 막기 어렵다.

### 2. 패키지 변경 이력 모니터링
TanStack 공격 사례처럼 악성 코드가 점진적으로 퍼지는 경우, 패키지의 변경 이력을 주기적으로 모니터링하는 게 중요하다. 예를 들어, GitHub Actions를 활용해 주요 패키지의 새 릴리즈가 나오면 자동으로 Diff를 분석하거나, 이상한 코드 패턴(예: eval, exec, 네트워크 호출 등)을 탐지하는 스크립트를 돌릴 수 있다.

### 3. 신뢰할 수 있는 소스만 사용하기
물론 가장 기본은 공식 레지스트리와 검증된 패키지만 사용하는 것이다. 하지만 이번 공격처럼 인기 있는 패키지조차 위험에 노출될 수 있어서, 2차 검증 체계를 갖추는 게 필요하다.

## 실전에서 적용해본 공급망 공격 대응 코드 예시

아래는 Node.js 환경에서 특정 패키지의 설치 시점에 악성 코드 삽입을 감지하기 위한 간단한 후킹 예시다. `postinstall` 스크립트에 주목해서, 의심스러운 네트워크 호출을 탐지하는 로직을 넣었다.

```js
const { execSync } = require('child_process');
const fs = require('fs');

// postinstall 스크립트 실행 전후에 네트워크 호출 로그 확인
function detectSuspiciousNetworkCalls() {
  const log = execSync('lsof -i -n -P').toString();
  if (log.includes('suspicious-domain.com')) {
    console.warn('경고: 의심스러운 네트워크 호출 감지됨!');
    process.exit(1); // 설치 중단
  }
}

// 설치 전 검사
detectSuspiciousNetworkCalls();

// 실제 설치 명령어 실행
execSync('npm install', { stdio: 'inherit' });

// 설치 후 검사
detectSuspiciousNetworkCalls();
```

이 코드는 완벽하지 않지만, 의심스러운 네트워크 활동을 조기에 포착하는 데 도움을 준다. 실제 운영 환경에서는 더 정교한 로깅과 알림 체계를 구축해야 한다.

## 공급망 공격 대응, 결국은 ‘작은 범위 점진적 배포’가 답이다

OpenAI 문서에서도 언급했듯이, 신규 백엔드 기능이나 의존성 업데이트를 한꺼번에 대규모로 배포하는 것보다, 작은 범위에서 점진적으로 배포하는 전략이 운영 리스크를 크게 줄인다[OpenAI API Documentation](https://platform.openai.com/docs/overview). 이번 TanStack 공격처럼 악성 코드가 잠복해 있다가 대량 확산되는 걸 막으려면, 다음과 같은 점진적 배포 원칙을 지키는 게 좋다.

- **Canary Release:** 전체 서비스 중 일부 서버에만 먼저 적용해 이상 징후를 관찰
- **Feature Flag 활용:** 위험도가 높은 기능이나 의존성은 플래그로 제어해 빠르게 롤백 가능하게
- **자동화된 모니터링:** 실패 유형을 초기에 계측해 유지보수성과 장애 대응 속도를 높이는 것도 필수[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)

## 마치며: npm 패키지 관리, 이제는 보안이 기본이다

이번 TanStack 공급망 공격 사례를 보면서, 패키지 관리가 단순히 편리함을 위한 도구가 아니라 보안의 최전선이라는 걸 다시 깨달았다. 우리 백엔드 개발자들은 다음을 명심해야 한다.

- 신뢰할 수 있는 패키지만 쓴다고 끝이 아니다. 패키지 무결성, 변경 이력, 네트워크 호출 등 다층 방어가 필요하다.
- 자동화 도구와 점진적 배포 전략은 운영 리스크를 줄이는 데 큰 역할을 한다.
- 항상 의심하고, 의심스러우면 바로 차단하는 습관을 들여야 한다.

처음엔 이게 별거 아닌 것 같지만, 실제로 겪어보면 공급망 공격은 서비스 전체를 마비시킬 수 있는 심각한 위협이다. 오늘부터라도 우리 프로젝트의 패키지 관리 정책을 다시 점검해보자.
