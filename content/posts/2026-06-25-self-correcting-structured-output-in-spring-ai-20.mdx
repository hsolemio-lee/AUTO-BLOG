한번 AI 모델이 뱉은 결과가 엉망이라서 백엔드에서 골치 아픈 경험, 다들 있죠? 특히 구조화된 데이터를 기대하는데, AI가 한두 개 필드를 빼먹거나 포맷이 깨지면 downstream 서비스가 줄줄이 꼬입니다. 이걸 어떻게 하면 자동으로 잡아내고, 다시 고쳐서 넘길 수 있을까요? 

최근에 Spring AI 2.0을 써보면서 self-correcting, 즉 스스로 오류를 감지하고 수정하는 구조화 출력 방식을 실무에 적용해봤는데, 생각보다 훨씬 체계적이고 효과적이더라고요. 오늘은 그 과정을 공유하면서, "우리 AI 출력이 왜 자꾸 틀릴까?" 고민하는 분들께 작은 힌트가 되길 바랍니다.

## Spring AI 2.0, 왜 최신 Spring Boot와 Framework 버전이 중요한가

Spring AI 2.0은 Spring Boot 3.x와 Spring Framework 6.x의 최신 기능을 적극 활용합니다. 이 최신 스택 덕분에 AI 모델의 출력 데이터를 POJO(Plain Old Java Object)로 깔끔하게 매핑하고, 검증 로직을 빈(Bean) 단위로 통합할 수 있죠. 

예를 들어, AI가 JSON 형태로 반환하는 복잡한 구조를 단일 DTO 클래스로 받고, `@Validated` 애노테이션과 커스텀 검증기를 붙여서 출력 값의 일관성을 보장할 수 있습니다. 

```java
@Data
@Validated
public class AiStructuredOutput {
    @NotNull(message = "id는 필수입니다.")
    private String id;

    @Size(min = 1, message = "결과 리스트는 비어있을 수 없습니다.")
    private List<ResultItem> results;

    // 커스텀 검증기 등록 가능
}
```

이런 구조가 가능한 건 Spring Framework의 핵심 기술 덕분인데, 객체지향적 설계와 강력한 검증 체계를 통해 AI 출력의 신뢰도를 높일 수 있습니다[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

처음엔 이게 별거 아닌 것 같지만, AI 모델이 조금만 엉뚱한 데이터를 보내도 바로 잡아내는 게 얼마나 중요한지 직접 겪어보면 압니다.

## OpenAI API와 Anthropic 가이드에서 배우는 self-correcting 전략

AI 출력의 self-correction은 단순히 백엔드에서 검증만 하는 게 아닙니다. OpenAI API 문서에서는 프롬프트 설계 단계에서부터 명확한 출력 포맷을 지정하고, 오류가 감지되면 재요청(retry)하는 방식을 권장합니다. 예를 들어, JSON 스키마를 명확히 정의하고, AI가 이를 벗어나면 다시 요청하는 거죠[OpenAI API Documentation](https://platform.openai.com/docs/overview).

Anthropic의 프롬프트 엔지니어링 가이드도 비슷한데, 다단계 검증과 피드백 루프를 통해 AI 출력 오류를 줄이는 구조를 소개합니다. 즉, AI가 출력한 결과를 다시 AI에게 검증받거나, 백엔드에서 추가 검증 후 문제가 있으면 재요청하는 과정을 포함합니다[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

이런 아이디어를 Spring AI 2.0 백엔드에 녹여내면, 다음과 같은 흐름이 가능합니다.

1. AI에게 명확한 JSON 스키마를 프롬프트로 전달
2. AI 출력 수신 후 DTO 매핑 및 검증
3. 검증 실패 시 재요청 로직 실행
4. 최종 검증된 결과를 서비스에 전달

## Spring Boot에서 비동기 처리와 캐싱으로 self-correcting 출력 지연 최소화하기

self-correcting 구조는 검증과 재요청으로 인해 지연이 발생할 수밖에 없습니다. 특히 AI 모델 호출이 네트워크 I/O를 포함하니, 동기 처리하면 응답 지연이 체감될 수 있죠. 

그래서 저는 Spring Boot에서 `@Async`와 `CompletableFuture`를 적극 활용해 비동기 호출을 기본으로 설계했습니다. 이렇게 하면 AI 호출과 검증, 재요청이 병렬로 돌아가면서 전체 응답 시간을 줄일 수 있더군요.

```java
@Service
public class AiService {

    @Async
    public CompletableFuture<AiStructuredOutput> fetchAndValidateOutput(String prompt) {
        return CompletableFuture.supplyAsync(() -> {
            AiStructuredOutput output = callAiModel(prompt);
            if (!validateOutput(output)) {
                output = retryCall(prompt);
            }
            return output;
        });
    }

    private AiStructuredOutput callAiModel(String prompt) {
        // OpenAI API 호출 코드
    }

    private boolean validateOutput(AiStructuredOutput output) {
        // DTO 검증 로직
    }

    private AiStructuredOutput retryCall(String prompt) {
        // 재요청 처리
    }
}
```

또한, 자주 쓰는 결과는 Redis 같은 캐시를 활용해 불필요한 AI 호출을 줄였습니다. 캐싱 TTL은 5분 정도로 짧게 설정해 최신성을 유지하면서도 비용과 응답 속도를 최적화했죠[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

이런 튜닝은 처음에 귀찮지만, 실제 서비스에서 AI 호출 비용과 사용자 경험을 동시에 잡으려면 꼭 필요합니다.

## 실무에서 겪은 self-correcting 구조화 출력의 장단점과 주의할 점

이걸 실제 프로젝트에 적용하면서 느낀 점은, self-correcting 메커니즘이 완벽한 정답을 보장하지는 않는다는 겁니다. AI 모델 특성상 예기치 못한 출력이 나올 수 있고, 재요청을 무한히 돌리면 비용과 지연이 급증하니까요.

그래서 저는 재요청 횟수를 2회로 제한하고, 그 이후에는 로그를 남기고 fallback 처리하는 방식을 썼습니다. 예를 들어, 기본값을 채우거나 사용자에게 재시도 안내 메시지를 띄우는 거죠.

또한, 검증 로직을 너무 빡세게 하면 정상적인 변형도 걸러질 수 있어서, 적절한 유연성을 주는 게 중요합니다. 예를 들어, 날짜 포맷 하나가 달라도 무조건 에러 내기보다, 허용 가능한 포맷 목록을 만들어두고 검증하는 식입니다.

마지막으로, AI 출력 포맷이 바뀌면 DTO도 그만큼 빠르게 수정해야 하는데, 이 부분에 대한 자동화 테스트를 꼭 구축하세요. CI 파이프라인에 AI 출력 검증 테스트를 넣는 것도 좋은 방법입니다.

오늘은 Spring AI 2.0 환경에서 self-correcting 구조화 출력 메커니즘을 어떻게 설계하고 튜닝했는지, 그리고 실무에서 겪은 현실적인 이야기를 나눠봤습니다. 

- 최신 Spring Boot와 Framework의 검증 기능을 적극 활용해 DTO 매핑과 검증을 체계화
- OpenAI와 Anthropic 가이드에서 영감을 받아 프롬프트 설계부터 재요청까지 다단계 검증 루프 구현
- 비동기 처리와 캐싱으로 AI 호출 지연 최소화하며 비용과 성능 균형 맞추기
- 재요청 횟수 제한과 유연한 검증 로직으로 실제 서비스 안정성 확보

이제 AI 백엔드 통합할 때, 단순히 "AI가 잘하겠지" 믿기보다 이런 구조를 만들어서 직접 오류를 잡고 고치는 경험을 해보세요. 처음엔 복잡해 보여도, 나중에 서비스 안정성과 유지보수성이 훨씬 좋아지는 걸 느낄 겁니다.
