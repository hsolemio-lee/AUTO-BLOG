### 아키텍처 결정, 왜 매번 입 밖에 내지 않고 기록해야 할까?

우리 팀도 한때는 "아, 이건 그냥 다들 알아서 할 거야" 하면서 아키텍처 결정들을 구두로만 처리했었어요. 그런데 어느 순간부터 신규 멤버가 들어오면 "왜 이렇게 했나요?"라는 질문이 쏟아지고, 누군가가 갑자기 "그 부분 바꿔야 하지 않나요?"라고 하면 다들 머뭇거리기 일쑤였죠. 이게 바로 아키텍처 결정에 대한 기록이 없어서 벌어진 혼란입니다.

이럴 때 Architecture Decision Record, 줄여서 ADR이 빛을 발합니다. ADR은 단순히 "이렇게 했다"를 넘어서, 왜 그렇게 했는지, 어떤 대안들이 있었고 그 트레이드오프는 무엇인지, 그리고 나중에 바꿀 때 어떻게 해야 하는지까지 문서화하는 도구입니다. 

### ADR이 팀에 가져다주는 변화

저도 처음엔 "문서 쓰는 거 귀찮은데..." 했는데, ADR을 도입한 뒤 팀 내 커뮤니케이션이 확실히 달라졌어요. 특히 중간 수준 개발자들이 아키텍처 결정의 배경을 명확히 이해하고, 신규 입사자도 빠르게 적응할 수 있게 된 게 가장 큰 변화였죠.

마틴 파울러도 마이크로서비스 아키텍처에서 ADR의 중요성을 강조하는데, 각 서비스의 설계 결정과 변경 사항을 체계적으로 기록하면 복잡한 시스템 내에서도 의사소통이 명확해지고, 향후 아키텍처 변경 시 참고할 수 있는 이력이 된다고 합니다[Martin Fowler - Microservices](https://martinfowler.com/articles/microservices.html).

또 클라우드 디자인 패턴 문서에서도 아키텍처 결정 시 다양한 패턴과 트레이드오프를 고려하고 명확히 문서화하는 것이 시스템 확장성과 유지보수에 필수적이라고 하니, ADR은 이 작업에 최적의 방법론인 셈이죠[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/).

### ADR 작성, 이렇게 시작해보세요

실제로 ADR을 쓸 때는 다음과 같은 구조를 추천합니다. 꼭 이대로 할 필요는 없지만, 제가 현업에서 써보고 효과 본 포맷입니다.

```markdown
# 1. 제목(Title)
# 2. 상태(Status): 제안(Proposed), 승인(Approved), 폐기(Superseded) 등
# 3. 맥락(Context): 왜 이 결정을 해야 했는지 배경 설명
# 4. 결정(Decision): 구체적으로 어떤 결정을 내렸는지
# 5. 대안(Alternatives): 고려했던 다른 옵션과 장단점
# 6. 결과 및 트레이드오프(Consequences): 선택한 결정의 영향과 부작용
# 7. 마이그레이션 경로(Migration): 기존 시스템에서 새 결정으로 넘어가는 방법
```

예를 들어, 우리 팀에서 서비스 간 통신을 REST API에서 gRPC로 전환할 때 작성한 ADR 일부를 공유합니다.

```markdown
# 제목: 서비스 간 통신 프로토콜을 REST에서 gRPC로 변경

## 상태
승인

## 맥락
기존 REST API는 JSON 직렬화 비용과 네트워크 대역폭 문제로 지연시간이 200ms 이상 발생. 대규모 트래픽 환경에서 성능 저하 우려.

## 결정
서비스 간 통신을 gRPC로 변경하여 바이너리 직렬화를 사용하고, HTTP/2 기반 멀티플렉싱으로 성능 개선.

## 대안
- REST 유지: 개발 생산성 우수하지만 성능 한계 있음
- 메시지 큐 도입: 비동기 처리 가능하나 복잡도 증가

## 결과 및 트레이드오프
- gRPC 도입으로 평균 지연시간 120ms로 감소
- 신규 학습 비용 발생 및 디버깅 난이도 증가

## 마이그레이션 경로
- 2개월간 REST와 gRPC 병행 운영
- 점진적으로 클라이언트 전환 후 REST 폐기
```

### ADR을 지속적으로 관리하는 방법

ADR은 한 번 쓰고 끝나는 문서가 아닙니다. 아키텍처가 바뀔 때마다 업데이트하거나 새 ADR을 추가해야 하죠. 우리 팀은 Git 저장소 내 docs/adr 폴더에 모든 ADR을 모아두고, PR을 통해 리뷰와 승인을 거칩니다. 이렇게 하면 변경 이력이 명확해지고, CI 파이프라인에서 ADR 문서가 누락됐는지 체크하는 자동화도 가능해집니다.

예를 들어, GitHub Actions를 활용해 PR에 ADR 문서가 포함됐는지 검사하는 간단한 워크플로우는 다음과 같습니다.

```yaml
name: Check ADR
on: [pull_request]
jobs:
  check_adr:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Check ADR files
        run: |
          if ! git diff --name-only origin/main...HEAD | grep '^docs/adr/'; then
            echo 'ADR 문서가 포함되어 있지 않습니다. 아키텍처 변경 시 반드시 ADR을 작성하세요.'
            exit 1
          fi
```

이렇게 하면 아키텍처 변경 사항을 놓치지 않고 기록할 수 있어, 시스템 안정성 유지에 큰 도움이 됩니다[Martin Fowler - Continuous Integration](https://martinfowler.com/articles/continuousIntegration.html).

### ADR, 무조건 좋은 것만은 아니다

솔직히 ADR 작성이 번거롭고, 문서가 너무 많아지면 오히려 찾기 어려워지는 단점도 있습니다. 또 너무 사소한 결정까지 기록하다 보면 문서 관리 부담이 커지죠. 그래서 우리 팀은 기준을 세워 "시스템에 큰 영향을 주는 결정"만 ADR로 남기고 있습니다.

그리고 ADR 작성 시 너무 기술적인 내용에만 집중하면, 나중에 읽는 사람이 왜 이 결정을 했는지 이해하기 어려울 수 있어요. 그래서 배경과 트레이드오프를 꼭 명확히 적는 걸 습관화했습니다.

### ADR을 통해 얻는 가장 큰 가치

결국 ADR은 단순 문서가 아니라, 팀 내 지식 공유와 협업의 촉진제입니다. 중간 개발자가 아키텍처 결정에 주도적으로 참여하고, 그 과정을 기록으로 남기면서 팀 전체가 성장하는 경험을 하게 되죠. 신규 멤버도 "왜 이렇게 했지?"를 줄이고 빠르게 적응할 수 있으니, 장기적으로 보면 개발 생산성과 시스템 안정성 모두에 긍정적인 영향을 줍니다.

아키텍처 결정이 흔들릴 때마다 ADR을 펼쳐보는 경험, 직접 해보면 생각보다 중독성 있습니다.
