## "하나의 서버에서 여러 가상 머신을 돌릴 수 있다고?"

최근 AWS가 EC2 인스턴스에서 네스티드 가상화(Nested Virtualization)를 지원하기 시작했다는 소식을 들었을 때, 저도 처음엔 ‘그게 왜 필요하지?’ 싶었어요. 그런데 실제로 써보니 단순히 가상 머신을 겹쳐 돌리는 걸 넘어, 백엔드 아키텍처 설계에 꽤 큰 변화를 줄 수 있겠더라고요.

### 네스티드 가상화가 뭔데, 왜 갑자기 주목받나?

간단히 말하면, 네스티드 가상화는 물리 서버 위에 띄운 가상 머신(VM) 안에서 다시 가상 머신을 실행하는 기술이에요. AWS EC2 인스턴스에서 이게 가능해졌다는 건, 기존에는 한 계층 VM만 돌릴 수 있었던 환경에서 이제는 VM 안에 또 다른 VM을 띄울 수 있다는 뜻이죠.

이게 왜 대단하냐면, 개발이나 테스트 환경을 물리적으로 분리하지 않고도 완벽하게 격리된 다양한 환경을 한 서버에서 운영할 수 있다는 점 때문이에요. 예를 들어, 서로 다른 커널 버전이나 운영체제를 동시에 돌려야 하는 복잡한 백엔드 시스템 요구사항을 훨씬 쉽게 충족할 수 있죠. 

실제로 AWS 공식 아키텍처 블로그에서도 네스티드 가상화가 백엔드 아키텍처 유연성을 크게 높여준다고 강조하고 있어요[1].

### 네스티드 가상화를 활용한 실무 배포 사례

저희 팀에서 한 번 적용해 본 사례를 공유할게요. 우리 서비스는 멀티테넌시 환경을 지원해야 했는데, 각 테넌트마다 완전히 독립적인 OS 환경과 설정이 필요했어요. 기존에는 테넌트별로 EC2 인스턴스를 따로 띄우는 방식이었는데, 비용과 관리 복잡도가 너무 컸죠.

네스티드 가상화를 도입하면서, 하나의 고성능 EC2 인스턴스(AWS에서 권장하는 인스턴스 타입은 `m6i.metal`이나 `c6i.metal` 같은 베어메탈 인스턴스입니다)를 물리 호스트로 쓰고, 그 위에 각 테넌트별 VM을 띄우는 방식을 시도했어요. 

이렇게 하니 물리 인프라 자원을 훨씬 효율적으로 쓸 수 있었고, 테넌트별 VM을 재시작하거나 스냅샷을 뜨는 것도 훨씬 간편해졌습니다. 물론, VM끼리 완전 격리돼 있어 보안 측면에서도 만족스러웠고요.

또 다른 활용법으로는 CI/CD 파이프라인 내에서 테스트 환경을 자동으로 생성하는 데 썼어요. 예를 들어, PR 하나당 격리된 VM을 네스티드 가상화 환경에서 띄워서 테스트를 돌리고, 끝나면 바로 삭제하는 식이죠. 이 덕분에 테스트 환경 충돌 없이 안정적인 빌드가 가능해졌습니다.

### 네스티드 가상화 도입 시 꼭 챙겨야 할 조건들

그렇다고 무작정 네스티드 가상화만 쓰면 다 해결되는 건 아니에요. AWS Well-Architected Framework에서도 강조하듯, 하드웨어 지원과 호스트 OS 커널 버전 호환성에 신경 써야 합니다[2].

예를 들어, 네스티드 가상화를 지원하는 인스턴스 타입은 제한적이고, 베어메탈 인스턴스가 아니면 성능 저하가 심할 수 있어요. 호스트 OS가 최신 커널을 써야 Nested VT-x 같은 가상화 확장 기능을 제대로 활용할 수 있죠. 

그리고 네스티드 가상화 환경은 관리가 복잡할 수 있어서, 모니터링과 로깅 체계를 잘 갖추는 게 필수입니다. VM이 여러 겹이라 장애 추적이 어려워질 수 있거든요.

### 실제로 네스티드 가상화 환경에서 VM 띄우는 간단한 예시

아래는 AWS EC2 베어메탈 인스턴스에서 KVM 기반으로 네스티드 가상화를 활성화하는 기본 설정 예시입니다.

```bash
# 호스트 OS에서 nested virtualization 활성화 확인
cat /sys/module/kvm_intel/parameters/nested
# 출력이 'Y'여야 활성화된 상태

# 만약 비활성화 상태면 modprobe 옵션으로 활성화
sudo modprobe -r kvm_intel
sudo modprobe kvm_intel nested=1

# VM 생성 예시 (virt-install 사용)
sudo virt-install \
  --name nested-vm1 \
  --memory 2048 \
  --vcpus 2 \
  --disk size=20 \
  --cdrom /path/to/iso \
  --os-type linux \
  --os-variant ubuntu20.04 \
  --graphics none \
  --console pty,target_type=serial
```

위처럼 설정하면 베어메탈 EC2 인스턴스에서 KVM 기반 VM을 띄우고, 그 VM 안에서도 다시 가상 머신을 구동할 수 있습니다. 물론, nested VM 내부에서 또 KVM을 쓰려면 추가 설정이 필요하긴 하지만, 기본 골격은 이렇습니다.

### 네스티드 가상화, 비용과 운영 효율성 측면에서 어떤 장점이 있나?

AWS Well-Architected Framework는 네스티드 가상화를 비용 최적화 측면에서 매우 긍정적으로 평가합니다[2].

기존에는 각 개발/테스트 환경이나 멀티테넌트 환경을 위해 물리 인스턴스를 여러 개 띄워야 했는데, 네스티드 가상화를 쓰면 하나의 물리 인스턴스 자원을 최대한 활용할 수 있거든요. 즉, 인스턴스당 비용 대비 처리량이 올라가고, 운영 관리도 단순해지는 효과가 있죠.

하지만 단점도 있습니다. 네스티드 가상화는 호스트 리소스에 더 많은 부하를 주기 때문에, CPU와 메모리 오버헤드가 발생할 수 있어요. 그래서 인스턴스 타입을 잘 골라야 하고, 성능 모니터링을 꼼꼼히 해야 합니다.

또한, 네스티드 VM에서 발생하는 네트워크 지연이나 I/O 병목 현상도 주의해야 합니다. 이런 부분은 실제 서비스 특성에 맞게 튜닝이 필요해요.

### 마무리하며

처음엔 네스티드 가상화가 그저 ‘가상 머신 안에 가상 머신 띄우는 것’ 정도로만 생각했는데, 직접 써보니 백엔드 아키텍처 설계에 꽤 강력한 도구가 되더라고요. 특히 멀티테넌시 환경 구축이나 테스트 자동화 파이프라인에서 비용과 운영 효율을 크게 개선할 수 있었습니다.

다만, 하드웨어 지원과 커널 버전, 인스턴스 타입 같은 기본 조건을 꼼꼼히 챙기고, 성능 모니터링과 장애 대응 체계를 잘 갖추는 게 필수라는 점도 꼭 기억하세요.

여러분도 AWS EC2 네스티드 가상화로 기존 인프라 고민을 한 번 새롭게 해보시면 좋겠습니다.
