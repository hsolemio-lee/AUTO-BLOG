# P&G가 Supply Chain 3.0을 대규모 롤아웃할 때 백엔드 엔지니어가 마주한 현실

"이거 한 번에 다 바꾸는 거 맞죠?"

최근 P&G가 Supply Chain 3.0과 연관된 여러 플랫폼을 대규모로 전환한다는 소식을 들었을 때, 우리 팀 내에서 이런 질문이 나왔습니다. 대기업의 공급망 시스템 전환은 단순히 기능 하나 바꾸는 게 아니라, 계획부터 조달, 재고, 주문 이행까지 전방위적으로 영향을 미치죠. 특히 백엔드 시스템 입장에선 설계와 배포, 장애 대응까지 복잡도가 확 올라갑니다.

이 글에서는 P&G의 사례를 바탕으로, 대규모 공급망 시스템 롤아웃이 백엔드 엔지니어링에 어떤 영향을 주는지, 그리고 실제로 어떻게 접근해야 하는지 이야기해보려 합니다.

## 점진적 배포가 왜 대규모 SCM 시스템에서 생명줄이 되는가

대규모 공급망 시스템은 수많은 서비스와 데이터 파이프라인이 얽혀있습니다. P&G가 Supply Chain 3.0을 전사적으로 적용하면서도 "작은 범위의 점진적 배포 전략"을 고수한 이유가 바로 여기 있습니다. 

처음부터 전사적 대규모 배포를 시도하면, 장애 발생 시 복구가 어렵고 영향 범위가 너무 큽니다. 반면, 몇 개의 물류 센터나 특정 지역부터 점진적으로 배포하면 문제 발생 시 빠른 롤백과 원인 파악이 가능하죠. 

실제로 TypeScript 팀도 신규 백엔드 기능을 도입할 때 점진적 배포를 통해 운영 리스크를 크게 낮췄다고 합니다. 우리도 이 전략을 SCM 시스템에 그대로 적용할 수 있습니다[TypeScript Handbook](https://www.typescriptlang.org/docs/handbook/intro.html).

예를 들어, P&G는 한 번에 전 세계 물류 센터를 바꾸는 대신, 북미 일부 센터에서만 Supply Chain 3.0을 먼저 적용해 운영 안정성을 검증했습니다. 이 과정에서 얻은 피드백을 반영해 다음 단계 배포 시 문제를 줄였죠.


## 장애 유형 초기 계측이 장애 대응 속도를 어떻게 바꾸는가

공급망 시스템은 장애가 곧 매출과 직결됩니다. 그래서 장애 대응 속도가 곧 경쟁력입니다. P&G는 Supply Chain 3.0 도입 초기에 실패 유형을 체계적으로 계측하는 데 집중했습니다. 

이게 왜 중요하냐면, 장애가 나도 "어디서 뭘 잘못했는지"를 빠르게 파악할 수 있어야 복구가 빠르기 때문입니다. 단순 로그 수집을 넘어서, 장애 유형별 메트릭과 알람을 세분화해 운영팀과 개발팀 모두가 문제를 빠르게 인지하고 대응할 수 있도록 했죠.

이 방식은 TypeScript 5.x 릴리즈 노트에서도 강조하는 부분입니다. 장애 유형을 초기부터 계측하면 유지보수성과 장애 대응 속도가 눈에 띄게 개선된다고 하네요[TypeScript 5.x Release Notes](https://devblogs.microsoft.com/typescript/announcing-typescript-5-4/).

실제로 P&G의 SCM 시스템에서는 주문 처리 지연, 재고 불일치, 공급처 응답 실패 등 장애 유형을 세분화해 각기 다른 대응 프로세스를 마련했습니다. 덕분에 장애 발생 시 평균 복구 시간이 30% 이상 단축됐다고 하더군요.


## 계획·조달·재고·이행 시스템 간 데이터 동기화, 어떻게 안정적으로 할까?

P&G Supply Chain 3.0의 핵심은 여러 시스템 간 데이터 일관성을 유지하는 데 있습니다. 계획 시스템에서 수요 예측이 나오면, 조달 시스템이 자동으로 공급 계획을 세우고, 재고 시스템은 실시간으로 상태를 반영하며, 이행 시스템은 주문 처리에 반영해야 하죠.

이 과정에서 데이터 동기화 문제는 가장 큰 골칫거리입니다. 분산 시스템 특성상 데이터 지연, 중복, 불일치가 발생할 수밖에 없거든요.

P&G는 이벤트 소싱과 CQRS 패턴을 적극 활용했습니다. 예를 들어, 재고 변경 이벤트를 중앙 이벤트 버스에 기록하고, 각 시스템이 이를 구독해 자신의 상태를 업데이트하는 방식입니다. 이러면 결국 모든 시스템이 동일한 이벤트 스트림을 기반으로 동기화되기 때문에 상태 불일치 가능성이 줄어듭니다.

아래는 이벤트 소싱을 간단히 구현한 예시입니다. 실제 SCM 시스템에서는 훨씬 복잡하지만, 핵심은 이벤트를 중심으로 상태를 관리한다는 점입니다.

```typescript
interface InventoryEvent {
  type: 'ADD' | 'REMOVE';
  productId: string;
  quantity: number;
  timestamp: number;
}

class Inventory {
  private events: InventoryEvent[] = [];
  private stockMap: Map<string, number> = new Map();

  applyEvent(event: InventoryEvent) {
    this.events.push(event);
    const currentStock = this.stockMap.get(event.productId) ?? 0;
    if (event.type === 'ADD') {
      this.stockMap.set(event.productId, currentStock + event.quantity);
    } else {
      this.stockMap.set(event.productId, currentStock - event.quantity);
    }
  }

  getStock(productId: string) {
    return this.stockMap.get(productId) ?? 0;
  }
}
```

이런 구조는 장애 발생 시 이벤트 로그를 재생해 상태를 복구할 수 있다는 장점도 있습니다. 다만 이벤트 소싱은 이벤트 설계와 관리가 까다롭고, 초기 학습 비용이 크다는 단점이 있으니 신중히 도입해야 합니다.


## P&G가 대규모 SCM 시스템에 적용한 배포 자동화와 모니터링 전략

대규모 공급망 시스템은 배포 빈도가 높고, 실패 시 영향이 크기 때문에 배포 자동화와 모니터링이 필수입니다.

P&G는 CI/CD 파이프라인에 Canary 배포, Blue-Green 배포 전략을 도입했습니다. Canary 배포는 신규 버전을 일부 서버에만 적용해 문제를 사전에 발견하는 방법이고, Blue-Green 배포는 두 환경을 번갈아가며 운영해 다운타임 없이 배포하는 전략입니다.

또한, 장애 유형별 계측을 통해 서비스별 SLA를 정의하고, 실시간 대시보드로 운영팀이 즉시 인지할 수 있게 했습니다. 예를 들어 주문 처리 지연이 5분 이상 지속되면 자동 알람이 울리고, 관련 팀에 슬랙 메시지가 발송되죠.

이 과정에서 TypeScript 프로젝트에서 배운 점진적 배포와 장애 계측 원칙이 큰 도움이 됐다고 합니다.

# 마치며: P&G SCM 3.0 롤아웃에서 배운 점

- **작은 단위부터 점진적 배포하라**: 대규모 공급망 시스템은 한 번에 다 바꾸려 하지 말고, 영향 범위를 최소화하면서 점진적으로 배포하는 게 운영 리스크를 줄이는 지름길입니다.

- **장애 유형을 초기에 세분화하고 계측하라**: 장애 원인을 빠르게 파악하고 대응 속도를 높이려면, 장애 유형별 메트릭과 알람 설계가 필수입니다.

- **이벤트 소싱으로 데이터 동기화 문제를 해결할 수 있다**: 여러 시스템 간 상태 불일치를 줄이려면 이벤트 중심 설계가 효과적입니다. 다만 설계 난이도와 운영 복잡성도 고려해야 합니다.

- **배포 자동화와 실시간 모니터링은 선택이 아닌 필수**: Canary, Blue-Green 배포와 SLA 기반 모니터링을 통해 장애를 사전에 감지하고 대응하는 체계를 갖춰야 합니다.

이 글이 여러분이 대규모 SCM 시스템을 설계하거나 운영할 때 조금이나마 도움이 되었으면 합니다. 실제로 겪어보면, 이런 전략들이 단순한 이론이 아니라 생명줄이라는 걸 몸소 느끼실 거예요.
