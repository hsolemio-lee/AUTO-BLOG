### "업그레이드하다가 서비스가 멈췄다" — 이 상황, 다들 한 번쯤 겪었죠?

최근에 Spring Office Hours 팟캐스트 S5E15 에피소드를 들으면서, 우리 팀이 겪었던 Spring 업그레이드 작업이 떠올랐어요. 버전만 바꾸면 끝날 줄 알았는데, 실제론 JVM 튜닝부터 보안 패치, 단계적 배포까지 챙길 게 한두 가지가 아니더라고요. 그래서 이번 글에서는 실제 프로덕션 환경에서 Spring과 OSS 보안을 강화하면서 업그레이드하는 현실적인 팁들을 공유해 보려고 합니다.

---

## JVM 튜닝과 커넥션 풀 설정, 이걸 안 하면 성능이 답 안 나와요

Spring Boot 업그레이드를 하면서 가장 먼저 마주친 건 성능 이슈였어요. 최신 버전이니까 무조건 빨라지겠지 했는데, JVM 설정이 그대로라 GC가 더 자주 일어나고, 커넥션 풀이 병목이 되더라고요.

Baeldung에서 권장하는 JVM 튜닝 포인트는 크게 다음과 같아요:

- `-Xms`와 `-Xmx`를 프로덕션 메모리 상황에 맞춰 균형 있게 조절
- G1 GC 옵션(`-XX:+UseG1GC`) 기본 활성화 여부 확인
- `-XX:MaxGCPauseMillis=200` 등으로 GC 일시중지 시간 제한 설정

그리고 데이터베이스 커넥션 풀도 꼭 점검하세요. HikariCP 기본 설정이 좋아졌다고 해도, 트래픽 패턴에 맞춰 `maximumPoolSize`를 조정하지 않으면 오히려 대기 시간이 늘어납니다. 우리 팀은 TPS가 5000 이상인 서비스라서 `maximumPoolSize`를 50으로 올렸더니 응답 지연이 눈에 띄게 줄었어요.

캐시도 적극적으로 활용하는 게 좋습니다. Redis나 Caffeine 캐시를 도입해 DB 부하를 줄이고, Spring Cache 추상화를 통해 코드 변경 최소화하는 전략이 효과적이었어요.

이 모든 내용은 Baeldung의 [Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance) 문서에 잘 정리되어 있으니 참고해 보세요.

## Spring Framework 코어 업데이트, 의존성 주입 개선이 보안에도 도움된다

Spring Framework의 핵심 업데이트는 모듈화와 의존성 주입(DI) 개선에 집중되어 있는데, 이게 단순히 코드 깔끔함을 넘어서 보안 취약점 완화에도 직결됩니다.

예전에는 복잡한 빈 설정과 의존성 꼬임 때문에 보안 취약점이 숨어있기 쉬웠는데, 최신 Spring Framework는 컴포넌트 스캔과 프로파일별 빈 등록을 더 정교하게 지원해 불필요한 빈이 로딩되는 것을 막아줍니다. 이 덕분에 공격자가 악성 빈을 주입하거나, 의도치 않은 빈이 노출되는 리스크가 줄어들었죠.

또한, `@Configuration` 클래스의 프록시 모드 개선으로 런타임에 빈 생성 순서가 안정화되어, 초기화 시점에 발생할 수 있는 보안 취약점도 예방할 수 있습니다.

직접 코드를 보면 이런 식으로 바뀌었어요:

```java
@Configuration(proxyBeanMethods = false) // 이전에는 true가 기본
public class AppConfig {

    @Bean
    public ServiceA serviceA() {
        return new ServiceA(serviceB());
    }

    @Bean
    public ServiceB serviceB() {
        return new ServiceB();
    }
}
```

`proxyBeanMethods=false`로 설정하면 불필요한 프록시 생성이 줄고, 빈 초기화가 더 명확해집니다. 이게 보안에 직접적인 영향을 준다고는 할 수 없지만, 복잡한 의존성 문제로 인한 예기치 않은 동작 가능성을 줄여주는 효과가 있어요.

더 자세한 내용은 Spring 공식 문서의 [Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)에서 확인할 수 있습니다.

## 최신 Spring Boot는 보안 기본 설정이 강화되어 있다, 그래도 우리만의 검증 절차는 필수

Spring Boot 최신 버전은 기본적으로 보안 관련 의존성 버전을 엄격히 관리하고, 취약점이 발견된 라이브러리는 빠르게 교체하는 정책을 적용하고 있어요. 그래서 업그레이드만 잘 해도 상당 부분 OSS 보안 리스크를 줄일 수 있습니다.

예를 들어, Spring Security 모듈은 OAuth2, JWT 지원이 강화되고, 기본 CSRF 설정도 더 견고해졌습니다. 또한, 의존성 관리를 통해 Log4j 같은 유명 취약점 라이브러리 버전을 자동으로 최신으로 유지하려고 노력 중입니다.

하지만 여기서 끝내면 안 돼요. 우리 팀은 다음과 같은 절차를 꼭 추가했습니다:

- CI/CD 빌드 파이프라인에서 의존성 스캔 도구(예: OWASP Dependency-Check) 실행
- 서명 검증 및 해시 체크를 통한 공급망 공격 방지
- 정기적인 라이브러리 업데이트 알림과 사내 보안 리뷰

GitHub Engineering Blog에서 강조하는 것처럼, 단순히 라이브러리 버전을 올리는 것만으로는 공급망 공격을 완전히 막을 수 없기 때문에 빌드 파이프라인 검증이 필수입니다([GitHub Engineering Blog](https://github.blog/category/engineering/)).

## 대규모 시스템 업그레이드, 단계적 배포와 모니터링 없으면 바로 골치

우리가 겪은 가장 큰 난관은 바로 롤아웃 과정이었어요. 한 번에 전체 트래픽을 새 버전으로 돌리면, 예상치 못한 버그나 성능 저하가 서비스 전체를 마비시킬 위험이 큽니다.

Martin Fowler가 말한 것처럼 단계적 배포(카나리, 블루그린)와 모니터링을 병행해야 해요([Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/)).

우리 팀은 다음과 같은 절차를 적용했습니다:

1. **카나리 배포**: 전체 트래픽의 5%만 새 버전으로 라우팅
2. **실시간 모니터링**: CPU, 메모리, 응답 시간, 에러율을 1분 단위로 체크
3. **자동 롤백 조건 설정**: 에러율 1% 이상, 응답 시간 200ms 초과 시 자동 롤백
4. **점진적 트래픽 확장**: 안정성 확인 후 25%, 50%, 100% 순으로 확대

이 과정에서 Prometheus와 Grafana를 활용해 대시보드를 만들었는데, 이상 징후가 보이면 바로 슬랙 알림이 오도록 설정해 둔 게 큰 도움이 됐습니다.

## 실제로 써먹는 코드 예시: HikariCP 커넥션 풀 튜닝

```java
@Configuration
public class DataSourceConfig {

    @Bean
    public DataSource dataSource() {
        HikariConfig config = new HikariConfig();
        config.setJdbcUrl("jdbc:postgresql://db-host:5432/mydb");
        config.setUsername("dbuser");
        config.setPassword("secret");

        config.setMaximumPoolSize(50); // TPS 5000 이상인 서비스에 맞춤
        config.setConnectionTimeout(30000); // 30초
        config.setIdleTimeout(600000); // 10분
        config.setMaxLifetime(1800000); // 30분

        config.setPoolName("MyHikariCP");

        return new HikariDataSource(config);
    }
}
```

이 설정은 고트래픽 환경에서 커넥션 풀이 병목이 되지 않도록 최대 풀 사이즈를 넉넉하게 잡은 예입니다. 물론 너무 크게 잡으면 DB에 부하가 커질 수 있으니, 실제 트래픽과 DB 성능을 고려해 조정해야 해요.

### 마무리하며

Spring 업그레이드는 단순히 버전만 올리는 작업이 아니라, JVM 튜닝, 의존성 보안, 단계적 배포 등 여러 요소가 맞물려야 성공합니다. 처음엔 이게 별거 아닌 것 같지만, 실제로 겪어보면 작은 설정 하나가 서비스 전체 안정성에 큰 영향을 준다는 걸 알게 돼요.

특히 OSS 보안은 라이브러리 업데이트뿐 아니라 빌드 파이프라인 검증과 서명 확인 절차까지 챙겨야 진짜 안전합니다. 그리고 대규모 롤아웃 시에는 모니터링과 자동 롤백 전략을 반드시 준비하세요.

이 글이 여러분 팀의 Spring 업그레이드와 보안 강화에 조금이나마 도움이 되길 바랍니다.
