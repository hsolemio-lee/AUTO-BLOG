## "테스트는 귀찮지만, 안 하면 더 귀찮다" — 실제로 겪어본 이야기

내가 처음 Spring Boot로 프로젝트를 시작했을 때, 테스트는 그냥 ‘해야 하는 것’ 정도로만 생각했어요. 그런데 어느 순간, 배포 후에 갑자기 터지는 버그 때문에 야근이 잦아지고, 그때부터 테스트 코드를 제대로 쓸 수밖에 없었죠. Daniel Garnier-Moiroux가 최근에 출간한 『Testing Spring Boot Applications』를 들으면서, ‘아 이 부분은 내가 진짜 놓치고 있던 거구나’ 싶었던 부분들을 정리해봤습니다.


## 통합 테스트와 단위 테스트, 어떻게 조합해야 할까?

Spring Boot 공식 문서에 따르면, 단위 테스트와 통합 테스트를 적절히 섞는 게 핵심입니다. 단위 테스트는 빠르고 격리된 환경에서 비즈니스 로직을 검증하는 데 집중하고, 통합 테스트는 실제 프로덕션 환경과 최대한 비슷한 조건을 만들어서 전체 애플리케이션 흐름을 점검하죠. 

여기서 중요한 건 ‘프로덕션 환경과 유사한 조건’입니다. 예를 들어, 데이터베이스 연결, 메시지 큐, 외부 API 호출 같은 부분을 실제 환경과 최대한 맞춰서 테스트해야 신뢰도가 올라갑니다. 그냥 Mock만 잔뜩 써서 테스트를 돌리면, 배포 후에 예상치 못한 문제가 터질 확률이 높아져요.

이걸 실제로 적용하려면, @SpringBootTest 어노테이션을 적극 활용하는 게 좋아요. 이 어노테이션은 스프링 컨텍스트 전체를 로드해서 진짜 서비스 환경과 유사한 상태를 만들어줍니다. 물론, 컨텍스트 로딩 시간이 길어질 수 있으니 모든 테스트에 무분별하게 쓰면 안 되고, 필요한 곳에만 써야 합니다.


## 테스트 환경을 분리해서 관리하는 게 왜 중요한가

프로파일(profile)을 분리해서 테스트 환경을 구성하는 것도 Daniel의 책에서 강조하는 부분입니다. 예를 들어, `application-test.properties` 같은 별도 설정 파일을 만들어서 테스트용 DB 연결 정보, 캐시 설정 등을 따로 관리하는 거죠. 

이렇게 하면 테스트 실행 시 프로덕션 설정과 충돌하지 않고, 테스트 환경을 깔끔하게 유지할 수 있습니다. 실제로 우리 팀에서도 테스트 프로파일을 분리한 이후로, 테스트 실패 원인을 찾는 시간이 현저히 줄었어요.


## 불필요한 컨텍스트 로드를 줄이는 방법과 Mock 활용법

통합 테스트가 좋다고 해서 모든 테스트에서 @SpringBootTest를 쓰면, 테스트가 느려지고 비효율적입니다. Baeldung의 성능 튜닝 가이드에서도 ‘불필요한 컨텍스트 로드를 최소화하라’고 조언합니다. 

내가 추천하는 방법은 다음과 같아요:

- 서비스 레이어 단위 테스트는 @WebMvcTest, @DataJpaTest 같은 슬라이스 테스트(slice test)를 활용해서 필요한 빈만 로드하기
- 외부 API 호출이나 메시지 큐 같은 의존성은 Mockito 같은 Mock 라이브러리로 격리하기

예를 들어, 아래는 서비스 레이어 단위 테스트 시 Mockito를 활용해 외부 의존성을 Mock 처리하는 코드입니다:

```java
@SpringBootTest
class UserServiceTest {

    @MockBean
    private ExternalApiClient externalApiClient; // 외부 API 클라이언트 Mock

    @Autowired
    private UserService userService;

    @Test
    void testUserCreation() {
        // 외부 API 호출 시 Mock 응답 정의
        Mockito.when(externalApiClient.callExternalService(Mockito.anyString()))
               .thenReturn("mocked response");

        User user = userService.createUser("testuser");
        Assertions.assertNotNull(user);
        Assertions.assertEquals("testuser", user.getUsername());
    }
}
```

이렇게 하면 외부 시스템에 영향을 받지 않고, 빠르고 안정적인 단위 테스트가 가능합니다.


## 의존성 주입(DI)이 테스트 코드를 얼마나 편하게 만드는지

Spring Framework의 핵심 중 하나인 의존성 주입(DI)은 테스트 코드 작성에 정말 큰 도움을 줍니다. Mock 객체를 주입하기가 훨씬 편해지니까요. 

예전에는 직접 new 해서 객체를 만들고, 의존성을 일일이 세팅하느라 코드가 지저분해지곤 했는데, Spring 덕분에 훨씬 깔끔해졌습니다. 유지보수성도 좋아지고, 테스트 코드 가독성도 확 올라가죠.


## 단순한 커버리지 숫자보다 ‘실제 운영 시나리오’ 시뮬레이션에 집중해야 하는 이유

테스트 커버리지를 100% 맞추는 게 목표가 아니라는 얘기, 다들 들어봤을 겁니다. Daniel의 책과 Spring Boot 공식 문서 모두 ‘프로덕션 등급 테스트 전략’은 실제 서비스 운영 중 발생할 수 있는 다양한 시나리오를 시뮬레이션하는 데 집중해야 한다고 말합니다.

예를 들어, 네트워크 지연, DB 장애, 동시성 문제 같은 ‘현실적인 장애 상황’을 테스트에 반영하는 거죠. 단순히 코드 라인만 많이 실행하는 게 아니라, 실제 문제가 터질 가능성이 높은 부분을 집중적으로 점검하는 게 훨씬 효과적입니다.


## 마무리하며: 내일부터 바로 써먹을 수 있는 팁

- **테스트 프로파일 분리**: `application-test.properties` 만들어서 테스트 환경 전용 설정 관리
- **@SpringBootTest는 꼭 필요한 곳에만**: 무분별한 사용은 테스트 속도 저하의 지름길
- **Mock 활용으로 외부 의존성 격리**: Mockito와 @MockBean 적극 활용하기
- **실제 운영 시나리오 중심 테스트 설계**: 장애 상황, 네트워크 문제 등 현실적인 케이스 반영
- **의존성 주입 덕분에 테스트 코드가 깔끔해진다**는 점 기억하기

테스트는 귀찮지만, 제대로 하면 배포 후 야근 횟수를 확 줄일 수 있습니다. Daniel Garnier-Moiroux의 책과 Spring 공식 문서를 참고해서, 여러분 프로젝트에 맞는 ‘프로덕션 등급 테스트 전략’을 꼭 세워보시길 추천합니다.
