## 425TB MySQL 데이터, 1000개 샤드… 이걸 어떻게 관리하지?

Etsy에서 일하다 보면 데이터가 폭발적으로 늘어나면서 MySQL 샤딩 아키텍처가 점점 복잡해지는 걸 체감할 수밖에 없었어요. 425TB에 달하는 데이터가 1000개가 넘는 샤드에 흩어져 있었는데, 이걸 관리하는 게 얼마나 힘든지 상상 가시나요? 단순히 쿼리를 날리는 것뿐 아니라 운영, 백업, 장애 대응까지 감당해야 하니까요.

처음엔 샤딩만 잘 나누면 다 해결될 줄 알았는데, 실제로는 샤드가 많아질수록 오히려 운영 복잡도가 기하급수적으로 증가하더라고요. 그래서 Etsy는 Vitess라는 분산 데이터베이스 솔루션으로 전환을 결정했습니다. 이번 글에서는 그 과정에서 겪은 현실적인 문제들과 Vitess가 어떻게 해결책이 되었는지 이야기해볼게요.

---

## Vitess 도입 전후, 아키텍처에서 가장 크게 달라진 점

Vitess를 도입하기 전 Etsy의 MySQL 샤딩은 수동으로 샤드 관리, 쿼리 라우팅, 리밸런싱 작업을 처리했어요. 이 때문에 다음과 같은 문제가 있었습니다:

- **샤드 수 증가에 따른 관리 비용 폭증**: 1000개 샤드를 하나하나 모니터링하고 튜닝하는 데 인력과 시간이 너무 많이 들었죠.
- **복잡한 쿼리 라우팅**: 애플리케이션 레벨에서 샤드 키 기반 라우팅 로직이 복잡했고, 잘못된 라우팅으로 인한 장애도 종종 발생했습니다.
- **스케일 아웃 한계**: 새로운 샤드를 추가하거나 리밸런싱할 때 데이터 이동이 너무 무거워서 다운타임 없이 확장하기 어려웠죠.

Vitess는 이 부분을 다음과 같이 개선했습니다:

- **자동 샤딩과 중앙 집중식 메타데이터 관리**: Vitess가 샤드 분할과 라우팅을 자동으로 처리해서 운영 부담이 크게 줄었어요.
- **투명한 쿼리 라우팅**: 애플리케이션은 Vitess 클러스터를 하나의 MySQL 서버처럼 바라볼 수 있어서 코드 변경 없이도 마이그레이션이 가능했습니다.
- **온라인 리샤딩 지원**: 데이터 이동 시에도 서비스 중단 없이 샤드 리밸런싱이 가능해졌죠.

이걸 실제로 적용하면서 느낀 점은, Vitess가 단순히 기술 스택을 바꾸는 게 아니라 운영 패러다임 자체를 바꾸는 경험이라는 겁니다.

## Vitess 마이그레이션에서 가장 까다로웠던 운영 이슈들

마이그레이션 과정에서 가장 골치 아팠던 건 역시 "점진적 배포 전략"이었어요. 1000개 샤드를 한꺼번에 옮길 수 없으니 작은 범위 단위로 나눠서 옮기고, 새 시스템에서 잘 작동하는지 검증하는 과정을 반복했죠. 이 부분은 [TypeScript Handbook](https://www.typescriptlang.org/docs/handbook/intro.html)에서 말하는 "작은 범위의 점진적 배포 전략은 신규 백엔드 기능의 운영 리스크를 낮춘다"는 주장과 딱 맞아떨어졌어요.

또한, 마이그레이션 초기에 실패 유형을 세밀하게 계측하는 작업을 병행했는데, 이 덕분에 장애 대응 속도가 훨씬 빨라졌습니다. [TypeScript 5.x Release Notes](https://devblogs.microsoft.com/typescript/announcing-typescript-5-4/)에서 강조하는 "실패 유형을 초기부터 계측하면 유지보수성과 장애 대응 속도가 개선된다"는 부분을 실무에서 체감한 셈이죠.

예를 들어, Vitess에서 쿼리 타임아웃이 발생하면 어떤 샤드에서 병목이 생겼는지 로그와 메트릭으로 바로 파악할 수 있었고, 문제 샤드만 신속하게 격리하거나 리밸런싱할 수 있었습니다.

## 실제 Vitess 쿼리 라우팅 설정 예시와 활용법

Vitess를 도입하면 애플리케이션 입장에서는 기존 MySQL과 거의 똑같이 쓸 수 있지만, 내부적으로는 Vitess가 샤드 키를 기준으로 쿼리를 자동 라우팅해 줍니다. 간단한 예로, 아래처럼 `vtgate`를 통해 쿼리를 날릴 수 있어요:

```sql
-- vtgate에 접속한 상태에서 user_id를 기준으로 샤딩된 테이블에 쿼리
SELECT * FROM user_profiles WHERE user_id = 12345;
```

이때 `user_id`가 샤드 키로 설정되어 있으면, Vitess가 자동으로 해당 샤드에 쿼리를 전달합니다. 애플리케이션은 별도 샤드 라우팅 로직을 신경 쓸 필요가 없죠.

만약 복합 샤드 키를 쓰거나, 범위 쿼리가 필요하다면 아래처럼 쓸 수도 있습니다:

```sql
SELECT * FROM orders WHERE order_date BETWEEN '2024-01-01' AND '2024-01-31';
```

Vitess가 내부적으로 여러 샤드에 쿼리를 분산해서 실행하고 결과를 합쳐서 반환해 줍니다. 다만 이런 범위 쿼리는 샤드 수가 많아질수록 성능 부담이 커지므로, 쿼리 설계 시 주의가 필요해요.

## Vitess 도입 후 확장성과 운영 효율성은 얼마나 달라졌나?

Etsy는 Vitess 도입 후 다음과 같은 효과를 경험했습니다:

- **샤드 관리 비용 30% 이상 감소**: 자동화된 샤딩과 메타데이터 관리 덕분에 인력 부담이 크게 줄었어요.
- **쿼리 실패율 15% 감소**: 안정적인 라우팅과 장애 격리 기능 덕분에 장애 영향 범위가 줄었습니다.
- **리샤딩 시 다운타임 0에 가까움**: 온라인 리샤딩 기능으로 서비스 중단 없이 데이터 이동이 가능해졌죠.

물론 Vitess도 만능은 아닙니다. 초기 셋업이 복잡하고, 클러스터 규모가 커질수록 Vitess 자체의 운영 난이도도 올라가요. 따라서 충분한 사전 테스트와 모니터링 체계 구축이 필수입니다.

## 마이그레이션을 준비하는 팀에게 해주고 싶은 조언

1. **작은 단위로 점진적 배포를 하라**: 한꺼번에 다 옮기려 하지 말고, 샤드 단위로 단계별로 검증하세요.
2. **실패 유형을 꼼꼼히 계측하라**: 장애가 나면 원인 분석이 빠를수록 복구도 빠릅니다.
3. **Vitess 내부 메커니즘을 충분히 이해하라**: 자동 샤딩, 리샤딩, 쿼리 라우팅 동작 원리를 정확히 알아야 운영이 편해집니다.
4. **모니터링과 알림 체계를 갖춰라**: Vitess 클러스터 상태를 실시간으로 감시할 수 있어야 문제를 조기에 발견할 수 있습니다.

---

Etsy의 사례는 단순히 기술 스택을 바꾸는 걸 넘어, 대규모 데이터베이스 운영 패러다임을 바꾸는 여정이었어요. Vitess가 제공하는 자동화와 확장성은 분명 매력적이지만, 그만큼 준비와 운영 노하우가 필요하다는 점도 꼭 기억하세요.
