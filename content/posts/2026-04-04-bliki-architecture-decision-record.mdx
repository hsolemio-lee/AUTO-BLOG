### "왜 이 아키텍처 선택이 이렇게 된 건지 나중에 이해가 안 될까?"

우리 팀에서 한 번쯤은 이런 상황 겪어봤을 겁니다. 프로젝트가 커지면서 아키텍처 결정이 여기저기 흩어지고, 누군가가 왜 이걸 이렇게 했는지 물어보면 명확한 답변이 안 나오는 경우요. 특히 신규 팀원이 들어오면 더 심하죠. 이럴 때 아키텍처 결정 기록(ADR)은 단순 문서 그 이상입니다. 팀 내 공통 이해를 돕고, 유지보수를 훨씬 수월하게 만들어주는 일종의 ‘팀 기억 장치’ 역할을 합니다.

---

### 아키텍처 결정 기록(ADR)이 왜 꼭 필요한가?

Martin Fowler가 말했듯이, 마이크로서비스 같은 복잡한 시스템에서는 아키텍처 선택과 트레이드오프를 명확히 기록하는 것이 필수입니다. 단순히 "이렇게 했다"가 아니라 "왜 이렇게 했는지", "다른 대안은 뭐가 있었는지", "어떤 리스크가 있는지"까지 담아야 하죠[Martin Fowler - Microservices](https://martinfowler.com/articles/microservices.html).

저도 경험해보니, ADR 없이는 같은 논쟁이 반복되고, 결정 근거가 사라져서 결국엔 비효율적인 재작업이 많아집니다. 특히 대규모 팀이나 분산된 조직에서는 이런 기록이 없으면 의사소통 비용이 폭발적으로 늘어나요.

---

### 효과적인 ADR 문서에 꼭 들어가야 할 내용들

Microsoft의 클라우드 디자인 패턴 문서에서는 좋은 ADR이 다음 요소들을 포함해야 한다고 강조합니다[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/):

- **결정된 아키텍처 선택**: 예를 들어, "메시지 큐를 RabbitMQ로 선택했다" 같은 구체적인 내용
- **대안과 그 장단점**: Kafka, AWS SQS 등 다른 옵션과 비교해 왜 RabbitMQ를 택했는지
- **마이그레이션 경로**: 기존 시스템에서 새 아키텍처로 어떻게 전환할지 단계별 계획
- **운영 환경 제약 조건**: 예를 들어, 네트워크 대역폭 제한, SLA 요구사항, 기존 인프라와의 호환성 등

이 중 운영 환경 제약 조건을 포함하는 게 특히 중요합니다. 현실적인 제약을 무시하면 설계는 이상적일지 몰라도 실제 적용 시 큰 문제에 봉착합니다.

---

### 실제 운영 환경 제약을 ADR에 담는 게 왜 중요한지

처음엔 "그냥 기술적으로 좋은 걸 선택하면 되지"라고 생각할 수 있어요. 하지만 운영 환경에서의 제약을 무시하면 다음과 같은 문제가 생깁니다:

- **예상치 못한 장애 증가**: 예를 들어, 네트워크 지연이나 제한된 리소스 때문에 설계대로 동작하지 않음
- **마이그레이션 실패 위험**: 기존 시스템과 충돌하거나 데이터 손실 우려
- **팀 내 혼란과 불신**: "왜 이걸 이렇게 했지?"라는 질문이 계속 나옴

저희 팀도 한 번은 클라우드 서비스의 특정 리전에서만 지원하는 기능을 무시하고 설계했다가, 실제 배포 때 큰 수정이 필요했습니다. 그때부터 ADR에 "운영 환경 제약" 섹션을 반드시 넣고, 매 배포 전 리뷰하도록 프로세스를 바꿨죠.

---

### GitHub 같은 대규모 조직에서 ADR이 어떻게 쓰이는지

GitHub 엔지니어링 블로그를 보면, 그들은 복잡한 시스템 아키텍처 변경 시 ADR을 적극 활용해 팀 간 조율을 원활하게 하고, CI/CD 파이프라인과 연계해 운영 효율성을 극대화합니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

예를 들어, 새로운 API 게이트웨이를 도입할 때 ADR을 통해 다음 내용을 공유합니다:

- 왜 기존 게이트웨이가 한계에 부딪혔는지
- 새로운 솔루션 후보들 (예: Kong, Envoy) 비교
- 선택한 솔루션의 단점과 이를 보완할 방법
- 점진적 전환 계획과 롤백 전략

이렇게 하면 팀원 모두가 같은 그림을 보고 움직일 수 있고, CI/CD 자동화 단계에서 체크리스트로 활용해 실수도 줄입니다.

---

### ADR 문서 작성 예시: 메시지 브로커 선택

```markdown
# ADR 001: 메시지 브로커 선택

## 결정
RabbitMQ를 메시지 브로커로 사용하기로 결정함.

## 배경
- 시스템 간 비동기 통신 필요
- 기존에 Kafka 도입 시도했으나 운영 복잡성 문제 발생

## 대안
- Kafka: 높은 처리량, 복잡한 운영
- AWS SQS: 관리형 서비스, 비용 문제

## 장단점
- RabbitMQ 장점: 설정 및 운영이 비교적 간단, 다양한 클라이언트 지원
- 단점: Kafka 대비 처리량 낮음

## 운영 제약
- 현재 인프라에서 RabbitMQ 클러스터 운영 가능
- 네트워크 대역폭 제한으로 대용량 메시지 처리에 제약

## 마이그레이션 경로
1. 신규 서비스에 RabbitMQ 적용 테스트
2. 기존 Kafka 기반 서비스 점진적 전환
3. Kafka 클러스터 단계적 축소 및 종료

## 참고
- [RabbitMQ 공식 문서](https://www.rabbitmq.com/)
```

이런 식으로 작성하면, 나중에 누가 봐도 "왜 RabbitMQ를 썼는지" 명확히 알 수 있고, 마이그레이션 계획도 한눈에 들어옵니다.

### ADR을 꾸준히 관리하는 게 생각보다 어렵다

처음엔 ADR 작성이 번거롭게 느껴질 수 있습니다. "결정만 빠르게 하고 넘어가자"는 생각도 들죠. 하지만 꾸준히 기록하고 리뷰하는 습관이 쌓이면, 오히려 팀 내 논쟁 시간을 줄이고 신규 팀원 온보딩 속도를 높여줍니다.

저희 팀은 Git 저장소 내 docs/adr 폴더에 ADR을 모아두고, PR 리뷰 때 관련 ADR이 최신인지 확인하는 프로세스를 만들었어요. 이렇게 하니 변경 이력이 자연스럽게 관리되고, 문서가 살아있는 자료가 됐습니다.

---

### 마무리하며: ADR은 단순 문서가 아니라 팀의 기억

아키텍처 결정 기록은 단순히 "문서화"가 아니라, 팀이 같은 방향을 보고 움직이도록 돕는 중요한 도구입니다. 특히 트레이드오프, 마이그레이션 경로, 운영 환경 제약을 함께 담아내면, 실제 현장에서 겪는 문제를 미리 예방할 수 있습니다.

처음엔 귀찮아도, 한두 개만 제대로 써보면 "이걸 왜 이제야 시작했지?" 하는 생각이 듭니다. 우리 팀도 ADR로 더 나은 협업과 유지보수를 경험해보시길 바랍니다.

## 운영에서 바로 점검할 항목 1

- **아키텍처 결정 기록(Architecture Decision Record, ADR)은 팀 내에서 중요한 아키텍처 선택과 그에 따른 트레이드오프를 명확히 문서화하여 팀원 간 이해와 협업을 증진시키고 유지보수성을 높이는 데 필수적이다.** ([Martin Fowler - Microservices](https://martinfowler.com/articles/microservices.html))
  실제 적용에서는 트래픽 패턴, 장애 허용 범위, 팀의 온콜 역량을 같이 봐야 합니다. 초기에는 전체 전환보다 일부 기능에 먼저 도입하고, 지표가 안정화되는지 확인한 다음 확장하는 방식이 안전합니다. 특히 롤백 기준을 사전에 숫자로 정의해 두면 운영 중 의사결정 속도가 크게 좋아집니다.
