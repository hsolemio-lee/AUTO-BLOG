### "왜 AI 연동만 하면 지연시간이 늘어날까?"

최근 우리 서비스에 AI 기능을 붙이면서 가장 크게 부딪힌 문제는 바로 응답 지연이었다. AI 모델 호출이 외부 API를 쓰는 경우가 많아 네트워크 딜레이와 처리 시간 때문에 사용자 체감 성능이 뚝 떨어졌던 거다. 그런데 Spring Boot 3.x부터 공식 통합된 Spring AI 모듈을 써보니, 이 문제를 꽤 효과적으로 해결할 수 있었다. 특히 1.0.9과 1.1.8 버전에서 비동기 호출과 캐싱 기능이 크게 강화되면서, 실제 서비스에서 안정성과 성능을 모두 잡을 수 있었다.

이번 글에서는 내가 직접 겪고 적용한 Spring AI 최신 버전 통합 과정과, JVM과 스레드 풀 튜닝, 그리고 OpenAI API와의 연동 팁까지 아낌없이 풀어보려 한다.

---

## Spring AI, 왜 이제야 제대로 된 공식 지원이 나왔을까?

Spring Boot 3.x부터 Spring AI 모듈이 공식적으로 통합되면서, AI 모델 호출과 관리가 훨씬 쉬워졌다. 이전에는 AI API 호출을 직접 래핑하거나, 별도의 라이브러리를 붙여야 했는데, 이제는 스프링 컨텍스트 내에서 자연스럽게 의존성 주입(DI) 방식으로 AI 서비스 컴포넌트를 관리할 수 있다. 

덕분에 테스트 코드 작성도 간편해지고, 유지보수도 쉬워졌다. Spring Framework 코어 문서에서도 DI 패턴을 활용해 AI 관련 컴포넌트를 모듈화하는 걸 적극 권장하고 있다[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

내 경험상, 이게 실제로 큰 차이를 만든다. AI 호출 로직이 서비스 레이어에 분산되어 있으면 테스트가 복잡해지고, 버그 찾기도 어렵다. 반면에 AI 호출을 별도의 빈(bean)으로 분리하면, 모킹(mocking)도 쉽고, AI 모델 버전 업그레이드나 교체 시에도 영향 범위를 최소화할 수 있다.

## Spring AI 1.0.9과 1.1.8, 비동기 호출과 캐싱 기능이 이렇게 달라졌다

내가 가장 반가웠던 건 1.0.9과 1.1.8 버전에서 비동기 호출과 캐싱 기능이 대폭 강화됐다는 점이다. AI 모델 호출은 보통 네트워크 요청이 포함돼서 지연시간이 길어질 수밖에 없는데, 이걸 비동기 방식으로 처리하면 메인 스레드가 블로킹되지 않아 전체 서비스 처리량이 늘어난다.

예를 들어, 아래 코드는 Spring AI 1.1.8 버전에서 OpenAI GPT 모델을 비동기로 호출하는 간단한 예시다.

```java
@Service
public class AiService {

    private final OpenAIClient openAIClient;

    public AiService(OpenAIClient openAIClient) {
        this.openAIClient = openAIClient;
    }

    public CompletableFuture<String> generateTextAsync(String prompt) {
        return openAIClient.chatCompletion(
                ChatCompletionRequest.builder()
                        .model("gpt-4")
                        .messages(List.of(new ChatMessage("user", prompt)))
                        .build()
        ).thenApply(response -> response.getChoices().get(0).getMessage().getContent());
    }
}
```

이렇게 하면 AI 응답을 기다리는 동안 다른 작업을 병렬로 처리할 수 있어, 특히 다중 사용자 환경에서 큰 효과를 본다. 

또한 캐싱 기능도 강화돼서, 동일한 프롬프트에 대해 반복 호출 시 API 호출 횟수를 줄이고 응답 속도를 높일 수 있다. Spring Boot 공식 문서에 따르면 캐싱 전략을 적절히 조합하면 AI 호출 비용 절감과 서비스 안정성 향상에 큰 도움이 된다[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

## JVM 힙과 스레드 풀, 커넥션 풀 튜닝은 필수다

Spring AI를 통합한 후에 성능 문제로 골머리 앓는 팀이 많다. 내 경험을 토대로 JVM과 스레드 풀, 커넥션 풀 튜닝 팁을 공유한다.

1. **JVM 힙 메모리**: AI 호출이 많아지면 내부에서 생성되는 객체가 많아 GC 부하가 커진다. 기본 512MB 힙은 무조건 부족하고, 최소 2GB 이상으로 시작하는 걸 추천한다. 특히 AI 요청이 몰릴 때는 메모리 부족으로 OOM(OutOfMemory) 에러가 날 수 있으니, `-Xms2g -Xmx4g` 정도로 여유 있게 잡고 GC 로그를 모니터링하자.

2. **스레드 풀**: 비동기 AI 호출을 처리하는 스레드 풀 크기는 CPU 코어 수와 AI 호출 지연시간을 고려해 조절해야 한다. 예를 들어, 8코어 서버에서 AI 호출 평균 지연이 500ms라면, 스레드 풀 크기를 50~100 사이로 설정해도 괜찮다. 너무 작으면 병목, 너무 크면 컨텍스트 스위칭 비용이 커진다.

3. **커넥션 풀**: OpenAI API 등 외부 AI 서비스와의 HTTP 커넥션 풀 크기도 중요하다. 기본값인 5~10개로는 동시 요청이 몰릴 때 큐잉이 발생한다. `spring.rest.template.connection-pool.max-total=50` 정도로 늘려주면 안정적인 처리량 확보에 도움이 된다.

이 외에도 타임아웃 설정을 짧게 잡아, 응답 지연 시 빠르게 실패 처리하고 재시도 로직을 돌리는 게 중요하다. Baeldung의 Spring Boot 성능 튜닝 가이드에 자세한 내용이 있으니 참고하자[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

## OpenAI API와 토큰 관리, 오류 재시도 로직은 이렇게 짜봤다

Spring AI 1.1.8은 OpenAI API와의 통합이 크게 개선됐다. 특히 토큰 관리와 오류 재시도 로직이 내장돼서, 직접 구현 부담이 줄었다. 하지만 실제 서비스에서는 상황별 커스텀 로직이 필요하다.

내가 쓴 재시도 로직 예시는 다음과 같다.

```java
@Service
public class OpenAiRetryService {

    private final OpenAIClient client;
    private final int maxRetries = 3;

    public OpenAiRetryService(OpenAIClient client) {
        this.client = client;
    }

    public String callWithRetry(String prompt) {
        int attempt = 0;
        while (attempt < maxRetries) {
            try {
                var response = client.chatCompletion(
                    ChatCompletionRequest.builder()
                        .model("gpt-4")
                        .messages(List.of(new ChatMessage("user", prompt)))
                        .build()
                );
                return response.getChoices().get(0).getMessage().getContent();
            } catch (ApiException e) {
                if (e.getStatusCode() == 429) { // 토큰 초과 등 rate limit
                    try {
                        Thread.sleep(1000 * (attempt + 1));
                    } catch (InterruptedException ignored) {}
                } else {
                    throw e;
                }
            }
            attempt++;
        }
        throw new RuntimeException("OpenAI API 호출 실패: 최대 재시도 초과");
    }
}
```

이렇게 하면 토큰 제한이나 일시적 네트워크 오류 발생 시 자동으로 재시도해서 안정성을 높일 수 있다. OpenAI 공식 문서에서도 이런 패턴을 권장한다[OpenAI API Documentation](https://platform.openai.com/docs/overview).

## 프롬프트 엔지니어링과 파라미터 튜닝, AI 정확도와 효율성에 미치는 영향

AI 모델 호출에서 프롬프트 설계는 성능만큼이나 중요하다. Anthropic의 프롬프트 엔지니어링 가이드에 따르면, 적절한 프롬프트 구조와 파라미터 조합은 응답의 정확도와 효율성을 크게 좌우한다. 

내 프로젝트에서는 다음과 같은 점을 신경 썼다.

- **프롬프트 길이 최적화**: 너무 길거나 불필요한 정보가 많으면 토큰 소모가 커지고 응답 지연이 늘어난다.
- **temperature 조절**: 생성되는 텍스트의 다양성과 창의성을 조절하는데, 서비스 목적에 맞게 0.7~0.9 사이에서 튜닝했다.
- **max_tokens 제한**: 응답 길이를 제한해 API 비용과 처리 시간을 관리했다.

이런 세밀한 튜닝은 AI 호출 빈도가 높을수록 비용과 성능에 직결되니, 꼭 실험을 통해 최적값을 찾아야 한다.

- OpenAI API 호출 시 토큰 제한과 오류 재시도 로직 구현으로 안정성 강화
- 프롬프트 엔지니어링과 파라미터 튜닝으로 AI 응답 품질 최적화

Spring AI 최신 버전을 실제 서비스에 붙여보면, 단순히 라이브러리 하나 추가하는 것 이상의 변화가 느껴진다. 개발 생산성은 물론, 서비스 안정성과 성능까지 한 단계 업그레이드할 수 있다. 물론 모든 게 완벽한 건 아니다. 비동기 처리 시 예외 처리 복잡도 증가, 캐시 무효화 정책 고민 등 고려할 점도 많다. 하지만 이 글에서 다룬 팁들을 차근차근 적용해보면, AI 백엔드 통합의 큰 산을 훨씬 수월하게 넘을 수 있을 거라 자신한다.
