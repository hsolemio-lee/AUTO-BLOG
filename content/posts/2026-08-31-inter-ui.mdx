### "왜 또 Inter 말고 다른 글꼴을 고민해야 하지?"

이 질문, 프론트엔드 하다 보면 한 번쯤은 꼭 마주해요. Inter는 가독성 좋고, 오픈소스라서 많이 쓰이지만, 프로젝트마다 다 똑같은 글꼴 쓰면 개성도 없고, 때론 퍼포먼스 문제도 느껴질 때가 있죠. 그래서 저도 최근에 Inter 대신 다른 UI 글꼴을 골라야 할 일이 생겼는데요, 그 과정에서 "이 두 가지 기준만 제대로 보면 글꼴 선택이 훨씬 수월하다"는 걸 깨달았어요. 오늘은 그 경험을 공유해볼게요.

---

## 1. UI 글꼴은 ‘가독성’과 ‘렌더링 성능’ 두 가지가 생명선

글꼴 고를 때 보통 디자인 예쁘고, 라이선스 확인하고, 지원하는 문자 범위 보는 정도로 끝내는데요, 진짜 중요한 건 사용자 화면에서 얼마나 빠르고 선명하게 보이냐예요. 특히 UI 글꼴은 텍스트가 작고, 버튼이나 메뉴처럼 자주 노출되는 부분에 쓰이니까요.

- **가독성**: 글자 하나하나가 뭉개지지 않고, 작은 크기에서도 쉽게 읽혀야 해요. Inter가 이 부분에서 워낙 뛰어나서 기본 선택지가 되었지만, 다른 글꼴도 특정 크기대에서 더 잘 보일 수 있어요.

- **렌더링 성능**: 웹에서 글꼴은 다운로드 크기와 렌더링 속도에 직접 영향을 줍니다. 예를 들어, Inter는 18~20KB 정도로 비교적 가볍지만, 일부 글꼴은 60KB 이상으로 무거워서 초기 페이지 로딩에 부담이 되죠. 게다가 렌더링 방식에 따라 GPU 가속이 잘 되느냐, 텍스트가 깜빡임 없이 부드럽게 나타나느냐도 달라져요.

제가 직접 경험한 사례로, 한 쇼핑몰 UI에서 Inter 대신 ‘Noto Sans’ 계열 글꼴을 썼는데, 14px 이하 작은 텍스트에서 가독성이 떨어져서 고객 문의가 늘었어요. 결국 16px 이상은 Noto Sans, 14px 이하는 Inter를 섞어 쓰는 타협을 했죠.

## 2. 프로젝트 특성과 사용자 환경에 맞춰 글꼴 무게와 스타일을 조절하라

UI 글꼴은 단순히 한 가지 스타일로 쓰는 게 아니라, 굵기(weight)와 스타일(italic 등)을 상황에 맞게 조절해야 해요. 특히 모바일과 데스크톱, 고해상도 화면에서 글꼴이 어떻게 보이는지 차이가 크거든요.

- **글꼴 무게 선택**: 너무 가벼운(weight 100~200) 글꼴은 작은 크기에서 흐릿해지고, 너무 무거운(weight 700 이상)은 텍스트가 뭉쳐 보여요. 보통 UI는 400~500 사이가 적당한데, 프로젝트 특성에 따라 조정이 필요합니다.

- **스타일 다양성**: 버튼, 강조 텍스트, 링크 등 UI 요소별로 다른 스타일을 써야 할 때가 많아요. 이때 글꼴이 다양한 스타일을 지원하지 않으면, 대체 글꼴이 섞여서 디자인이 깨집니다.

저희 팀은 한 번, 가벼운 글꼴만 지원하는 폰트를 썼다가, 버튼에 이탤릭 스타일을 넣으려니 대체 글꼴이 적용되어 UI가 엉망이 된 적이 있어요. 그래서 글꼴 선택 시 "이 프로젝트에서 필요한 스타일이 모두 있나"를 꼭 체크합니다.

## Inter 대신 쓸 만한 글꼴을 고를 때 실제 쓴 코드 예시

```css
/* 구글 폰트에서 Roboto와 Inter를 비교하며 쓰는 예시 */
@import url('https://fonts.googleapis.com/css2?family=Roboto:wght@400;500&display=swap');
@import url('https://fonts.googleapis.com/css2?family=Inter:wght@400;500&display=swap');

body {
  /* 기본 텍스트에는 Roboto 적용 */
  font-family: 'Roboto', sans-serif;
  font-weight: 400;
  font-size: 16px;
  line-height: 1.5;
}

button {
  /* 버튼 텍스트에는 Inter 적용, 가독성 및 스타일 차별화 */
  font-family: 'Inter', sans-serif;
  font-weight: 500;
  font-size: 14px;
  text-transform: uppercase;
}
```

이렇게 두 글꼴을 섞어 쓰면, UI 요소별로 가독성 최적화와 디자인 통일성을 어느 정도 맞출 수 있습니다. 물론 폰트 파일이 두 개라 번들 크기가 늘어나긴 하지만, 요즘 CDN과 HTTP/2 덕분에 크게 문제되지 않더라고요.

## UI 글꼴 선택에서 놓치기 쉬운 ‘실패 유형’을 미리 계측하는 방법

실패 유형, 즉 "이 글꼴이 특정 환경에서 깨지거나 렌더링이 이상해지는 경우"를 미리 파악하는 게 중요해요. Cloudflare처럼 장애 대응을 빠르게 하려면 초기부터 이런 실패 유형을 계측해야 한다는 점을 참고할 만합니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

예를 들어, 특정 OS나 브라우저에서 폰트가 안 깔리거나, 렌더링이 너무 느려지는지, 혹은 접근성(Accessibility) 문제는 없는지 테스트 케이스를 만들어서 자동화해두는 거죠. 이걸 안 하면, 배포 후에 "폰트가 안 보여요" "글자가 깨져요" 하는 이슈가 터져서 대응이 늦어집니다.

저희 팀은 다음과 같은 체크리스트를 자동화 테스트에 넣었어요.

- 주요 브라우저(Chrome, Firefox, Safari, Edge)에서 글꼴 렌더링 확인
- 모바일(iOS, Android)에서 텍스트 가독성 테스트
- 네트워크 느린 환경에서 폰트 로딩 속도 측정
- 접근성 도구를 통한 색 대비 및 크기 검증

이런 테스트를 통해 실패 유형을 초기에 잡으면 유지보수 비용이 크게 줄고, 장애 대응 속도도 빨라집니다.

## 글꼴 선택, 디자인과 퍼포먼스 사이에서 균형 잡는 법

마지막으로, 글꼴 선택은 디자인과 퍼포먼스 사이에서 균형을 잡는 작업이에요. 예쁜 글꼴이 꼭 빠른 건 아니고, 가벼운 글꼴이 꼭 예쁜 것도 아니니까요.

- **디자인 우선**: 브랜드 아이덴티티가 강한 서비스라면, 글꼴이 디자인을 얼마나 잘 살리느냐가 중요합니다. 이 경우 폰트 용량이 좀 커도 감수해야 할 때가 많죠.

- **퍼포먼스 우선**: 반대로, 로딩 속도가 중요한 뉴스 사이트나 대규모 서비스는 글꼴 용량과 렌더링 효율에 더 신경 써야 합니다.

저희는 보통 이런 기준을 정해서, 글꼴을 1~2개로 최소화하고, 필요한 스타일만 골라서 서브셋(subset)으로 배포합니다. 예를 들어, 영어와 숫자만 쓰는 UI라면 한글 글리프를 빼서 용량을 30~40% 줄이기도 해요.

## 글꼴 선택에 대해 제가 얻은 가장 큰 깨달음

처음엔 글꼴 고르는 게 별거 아닌 줄 알았는데, 실제로 프로젝트에 적용해보니 UI 가독성과 퍼포먼스에 큰 영향을 준다는 걸 체감했어요. 특히 작은 크기 텍스트에서 가독성 차이는 사용성에 바로 연결되고, 렌더링 속도는 사용자 경험 전체에 영향을 미칩니다.

그리고 실패 유형을 초기에 계측하는 게 얼마나 중요한지도 새삼 느꼈고요. 이 부분은 Cloudflare 사례처럼 장애 대응을 빠르게 하는 데도 꼭 필요한 과정입니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

UI 글꼴, 그냥 예쁘고 유명한 걸 쓰는 게 아니라, 우리 서비스 환경에 딱 맞는 걸 골라야 한다는 점, 꼭 기억하세요.
