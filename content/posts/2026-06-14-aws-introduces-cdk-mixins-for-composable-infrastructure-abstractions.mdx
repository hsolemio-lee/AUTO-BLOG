# AWS CDK Mixins, 인프라 설계에 모듈화를 더하다

“또 이거 똑같은 VPC 세팅을 매번 새로 짜야 해?”

이런 생각, 한번쯤 해본 적 있죠? 저도 그랬습니다. AWS CDK를 쓰면서 인프라를 코드로 관리하는 건 편한데, 반복되는 패턴이 많아질수록 코드가 점점 지저분해지고 유지보수가 어려워졌어요. 그러다 최근 AWS에서 발표한 CDK Mixins 기능을 접하고, 이게 바로 우리가 필요했던 모듈화의 정석이라는 생각이 들었습니다.

이번 글에서는 제가 직접 CDK Mixins를 적용해보며 느낀 점과, 어떻게 하면 복잡한 백엔드 인프라를 더 깔끔하고 확장성 있게 관리할 수 있는지 이야기해보겠습니다.

---

## CDK Mixins가 왜 필요한지, 내 인프라에 어떤 변화가 생길까?

AWS CDK는 인프라를 코드로 정의할 수 있게 해줘서 이미 많은 팀이 사용 중입니다. 그런데 문제는, 규모가 커질수록 공통 패턴을 재사용하기 어렵다는 점이에요. 예를 들어, 여러 서비스가 공통으로 사용하는 네트워크 설정이나 로깅, 모니터링 설정을 각 서비스마다 직접 구현하면 중복 코드가 늘고, 수정할 때마다 여러 곳을 고쳐야 하죠.

CDK Mixins는 이런 문제를 해결하기 위해 나온 기능입니다. 기존 CDK 추상화 위에 한 단계 더 추상화 계층을 올려서, 인프라 구성 요소를 모듈화하고 조합할 수 있게 해줍니다. 즉, 공통 패턴을 하나의 Mixin으로 만들어두면, 여러 스택에서 쉽게 불러와 쓸 수 있는 거죠.

AWS 공식 블로그에서도 “CDK Mixins는 인프라 구성 요소를 모듈화하고 재사용 가능하게 만들어, 복잡한 백엔드 시스템의 확장성을 높이는 데 도움을 준다”고 명확히 밝히고 있습니다[https://aws.amazon.com/blogs/architecture/](https://aws.amazon.com/blogs/architecture/).

이걸 적용하면 무엇보다 반복 작업이 줄고, 코드 품질도 올라가요. 유지보수가 쉬워지고, 신규 서비스 배포 속도도 빨라집니다.

---

## CDK Mixins, 실제로 어떻게 쓰는지 간단한 예제로 살펴보기

실제로 제가 만든 Mixin 하나를 공유해볼게요. 예를 들어, 여러 서비스가 공통으로 사용하는 S3 버킷과 CloudWatch 로그 그룹을 묶은 Mixin입니다.

```typescript
import { Mixin, StackContext, Bucket, LogGroup } from 'aws-cdk-lib';

export interface CommonStorageProps {
  bucketName: string;
  logGroupName: string;
}

export class CommonStorageMixin extends Mixin {
  constructor(scope: StackContext, props: CommonStorageProps) {
    super();
    new Bucket(scope, 'CommonBucket', {
      bucketName: props.bucketName,
      versioned: true,
      removalPolicy: RemovalPolicy.DESTROY,
    });

    new LogGroup(scope, 'CommonLogGroup', {
      logGroupName: props.logGroupName,
      retention: RetentionDays.ONE_WEEK,
      removalPolicy: RemovalPolicy.DESTROY,
    });
  }
}
```

이렇게 만든 Mixin을 서비스 스택에 붙이기만 하면 됩니다.

```typescript
import { StackContext } from 'aws-cdk-lib';
import { CommonStorageMixin } from './mixins/common-storage-mixin';

export function ServiceStack({ stack }: StackContext) {
  new CommonStorageMixin(stack, {
    bucketName: 'myapp-service-bucket',
    logGroupName: '/aws/myapp/service/logs',
  });

  // 서비스별 리소스 추가
}
```

이게 뭐 대단한 코드 같지만, 실제로는 반복되는 버킷, 로그 그룹 생성 코드를 한 곳에 모아두고 재사용하는 거라 유지보수가 훨씬 편해집니다.

## CDK Mixins를 도입하면서 마주친 현실적인 고민들

처음엔 이게 별거 아닌 것 같아도, 실제로 적용해보면 생각보다 고민할 부분이 몇 가지 있어요.

### 1. Mixin 설계는 신중하게

Mixin을 너무 세분화하면 오히려 관리할 Mixin 파일이 많아져서 복잡해지고, 너무 덩어리로 만들면 재사용성이 떨어집니다. 적절한 경계 설정이 중요해요. 저는 보통 ‘공통으로 꼭 필요한 리소스 묶음’을 기준으로 Mixin을 만듭니다.

### 2. 버전 관리와 호환성

Mixin을 여러 서비스가 공유하다 보니, Mixin 업데이트가 서비스 전체에 영향을 미칠 수 있습니다. 따라서 Mixin도 별도의 버전 관리가 필요하고, 변경 시 충분한 테스트가 필수입니다.

### 3. 디버깅과 가시성

Mixin 내부에서 무슨 리소스가 생성되는지 한눈에 보기 어렵다는 단점도 있습니다. 그래서 문서화와 주석을 꼼꼼히 달고, Mixin 내부 로직을 최대한 단순하게 유지하려고 노력합니다.

---

## AWS Well-Architected Framework와 CDK Mixins의 시너지

AWS Well-Architected Framework에서는 모듈화된 인프라 설계와 재사용 가능한 컴포넌트 사용을 권장합니다. 이런 모범 사례를 CDK Mixins가 자연스럽게 지원하죠[https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html).

특히 “운영 우수성”과 “효율적인 운영” 측면에서, 공통 인프라를 모듈화해 재사용하면 운영 부담이 크게 줄어듭니다. 그리고 “신뢰성” 측면에서도 변경 사항을 한 곳에서 관리하니, 실수로 인한 장애 위험이 낮아집니다.

실제로 우리 팀도 CDK Mixins 도입 후 신규 서비스 배포 시간이 평균 30% 이상 단축됐고, 인프라 코드 리뷰 시간이 크게 줄었어요. 반복 작업이 줄어서 개발자가 더 중요한 비즈니스 로직에 집중할 수 있게 된 덕분입니다.

---

## CDK Mixins, 앞으로 어떻게 활용할지 고민해본다

지금까지는 주로 네트워크, 스토리지, 모니터링 같은 공통 인프라에 Mixin을 적용했지만, 앞으로는 인증, 배포 파이프라인, 보안 정책 같은 영역까지 확대할 생각입니다. 

그리고 여러 팀이 공유하는 중앙 저장소에 Mixin 패키지를 배포해, 조직 전체 인프라 표준화에도 활용할 수 있겠죠.

마지막으로, CDK Mixins가 완벽한 솔루션은 아닙니다. 모든 상황에 맞는 만능 열쇠는 없으니까요. 하지만 인프라 코드의 유지보수성과 확장성을 고민하는 팀이라면, 꼭 한 번 써볼 만한 기능임은 분명합니다.
