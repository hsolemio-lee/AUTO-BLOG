## "또 LLM 라우터? 우리도 만들었는데 결국 폐기했어요"

요즘 LLM 라우터 만드는 게 대세긴 하죠. 우리 팀도 한창 열심히 만들었는데, 어느 순간 "이거 왜 이렇게 복잡하지?" 싶더라고요. 성능은 떨어지고, UX는 엉망이고, 유지보수는 더 힘들어지고. 결국 기존 라우터를 과감히 내려놓고 다시 설계하는 결정을 내렸습니다. 이 글은 그 과정에서 얻은 인사이트를 공유하려고 해요.

---

## 프론트엔드에서 LLM 라우터, 성능 최적화가 왜 이렇게 어려운가

LLM 라우터는 여러 LLM API를 상황에 맞게 호출해주는 역할인데, 프론트엔드에서 직접 구현할 때 가장 큰 문제는 지연시간과 API 호출 비용입니다. 예를 들어, 사용자 입력마다 여러 LLM에 요청을 보내면 응답이 느려지고, 비용도 눈덩이처럼 불어나죠. 

우리도 초반에는 단순히 요청을 분산시키는 정도로 끝냈는데, 실제 서비스에서 1초 이상 로딩이 느려지는 경우가 많았습니다. 사용자는 기다리다 지쳐서 이탈했고, 서버 비용도 급격히 증가했죠. 그래서 요청 분산과 캐싱 전략을 조합하는 패턴을 도입했습니다.


### 요청 분산과 캐싱을 조합한 실전 패턴

- **요청 분산**: 사용자의 쿼리를 여러 LLM API에 병렬로 보내되, 우선순위가 높은 API부터 응답을 기다립니다.
- **캐싱**: 이미 처리한 쿼리는 로컬 스토리지나 IndexedDB에 저장해, 동일한 요청 시 API 호출을 줄입니다.
- **비동기 처리와 로딩 상태 관리**: React의 Suspense나 상태 관리 라이브러리를 활용해 로딩 UI를 자연스럽게 보여줍니다.

이렇게 하니 평균 응답 시간이 30% 줄었고, UX 만족도도 눈에 띄게 좋아졌습니다. 특히 캐싱 덕분에 반복 질의에 대한 응답 속도가 5배 이상 빨라졌어요.

[GitHub Engineering Blog](https://github.blog/category/engineering/)에서도 비슷한 접근법을 강조하는데, 요청 분산과 캐싱을 적절히 조합하면 대규모 사용자 환경에서도 안정적인 성능을 유지할 수 있다고 하더군요.


## 컴포넌트 구조를 어떻게 설계해야 확장성과 유지보수가 쉬울까?

LLM 라우터는 단순히 API 호출만 하는 게 아니라, 다양한 LLM 모델과 프롬프트를 유연하게 연결해야 합니다. 우리 팀이 실패했던 이유 중 하나는 컴포넌트가 너무 뭉뚱그려져서 특정 LLM에 종속적이었다는 점이었어요.

Martin Fowler의 아키텍처 가이드에서 말하듯, 컴포넌트는 재사용성과 독립성이 핵심입니다. 이를 위해 다음과 같은 원칙을 적용했습니다.

- **LLM 호출을 담당하는 컴포넌트를 분리**: API 호출 로직을 별도의 훅(hook)이나 서비스로 분리해 테스트와 교체가 쉽도록 설계
- **프롬프트 템플릿 관리 컴포넌트 분리**: 프롬프트를 컴포넌트 상태나 별도 JSON으로 관리해 쉽게 수정 가능
- **UI와 비즈니스 로직 분리**: UI는 상태와 이벤트 처리에 집중하고, LLM 라우팅 로직은 독립된 레이어에서 처리

이 구조 덕분에 새로운 LLM API가 나와도 기존 코드를 거의 손대지 않고 확장할 수 있었습니다. 유지보수 시간도 40% 이상 단축됐죠.


## OpenAI API 최적화 팁을 프론트엔드에 적용하기

OpenAI API 문서에서는 토큰 사용량과 응답 지연을 줄이기 위해 프롬프트를 꼭 최적화하라고 권장합니다. 우리도 처음에는 무작정 긴 프롬프트를 보내느라 비용과 속도가 너무 나빠졌어요.

그래서 다음과 같은 전략을 썼습니다.

- **필요한 정보만 포함한 최소한의 프롬프트 구성**
- **프롬프트 템플릿 재사용 및 변수 바인딩 활용**
- **사용자 입력과 컨텍스트를 분리해 필요한 부분만 API 호출에 포함**

예를 들어, 아래 코드는 React에서 OpenAI API를 호출할 때 프롬프트를 최소화하는 간단한 예시입니다.

```jsx
import { useState } from 'react';

const OPENAI_API_KEY = process.env.REACT_APP_OPENAI_API_KEY;

async function fetchCompletion(prompt) {
  const response = await fetch('https://api.openai.com/v1/chat/completions', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${OPENAI_API_KEY}`,
    },
    body: JSON.stringify({
      model: 'gpt-4',
      messages: [{ role: 'user', content: prompt }],
      max_tokens: 150,
      temperature: 0.7,
    }),
  });
  const data = await response.json();
  return data.choices[0].message.content;
}

export default function Chat() {
  const [input, setInput] = useState('');
  const [output, setOutput] = useState('');
  const [loading, setLoading] = useState(false);

  const handleSubmit = async () => {
    setLoading(true);
    // 프롬프트를 간결하게 유지
    const prompt = `Answer concisely: ${input}`;
    const result = await fetchCompletion(prompt);
    setOutput(result);
    setLoading(false);
  };

  return (
    <div>
      <textarea
        value={input}
        onChange={(e) => setInput(e.target.value)}
        placeholder="질문을 입력하세요"
      />
      <button onClick={handleSubmit} disabled={loading || !input.trim()}>
        {loading ? '응답 중...' : '질문하기'}
      </button>
      <pre>{output}</pre>
    </div>
  );
}
```

이 예시처럼 프롬프트를 단순화하고, `max_tokens`를 제한하는 것만으로도 응답 속도와 비용을 크게 개선할 수 있습니다.

[OpenAI API Documentation](https://platform.openai.com/docs/overview)에서 자세한 최적화 가이드도 참고하면 좋습니다.


## Anthropic 프롬프트 엔지니어링에서 배운 UX 개선법

Anthropic의 프롬프트 엔지니어링 가이드를 보면, 프롬프트 설계와 LLM 호출 패턴이 UX에 얼마나 큰 영향을 주는지 알 수 있습니다. 불필요한 API 호출을 줄이고, 사용자 인터랙션 속도를 높이는 게 핵심이죠.

우리도 다음과 같은 방법을 도입했습니다.

- **사용자 입력을 실시간으로 검증해 불필요한 호출 방지**
- **중복 요청을 디바운스(debounce) 처리**
- **API 호출 결과를 부분적으로 보여주면서 다음 요청을 준비하는 선행 처리**

이런 개선 덕분에 사용자는 답변을 기다리는 동안도 앱이 멈춘 것 같지 않고, 자연스러운 대화 흐름을 경험할 수 있었습니다.


## Cloudflare의 대규모 분산 시스템 설계에서 힌트 얻기

Cloudflare 블로그의 "How We Built It" 시리즈를 보면, 대규모 분산 시스템에서 라우터를 단순화하는 게 얼마나 중요한지 알 수 있습니다. 프론트엔드와 백엔드 간 인터페이스를 명확히 나누고, 책임을 분산시키는 설계가 핵심이죠.

우리도 프론트엔드 LLM 라우터를 너무 복잡하게 만들지 않고, 가능한 백엔드에 일부 로직을 넘기는 쪽으로 방향을 틀었습니다. 예를 들어, 프롬프트 전처리나 API 키 관리 같은 민감한 부분은 백엔드에서 처리하고, 프론트엔드는 UI와 요청 분산, 캐싱에 집중하는 식입니다.

이렇게 하니 유지보수가 훨씬 쉬워졌고, 성능도 안정적으로 나왔습니다.

## 마치며: 직접 겪어보니 알게 된 현실적인 팁

- LLM 라우터는 만들기 쉽지만, 제대로 운영하려면 요청 분산과 캐싱을 꼭 조합해야 한다.
- 컴포넌트는 독립성과 재사용성을 최우선으로 설계해야 확장과 유지보수가 수월하다.
- 프롬프트 최적화는 비용과 속도에 직결되니, 항상 최소한의 정보만 보내도록 신경 써야 한다.
- UX를 위해 API 호출 타이밍과 로딩 상태 관리를 꼼꼼히 구현하는 게 생각보다 중요하다.
- 백엔드와 역할 분담을 명확히 하면 프론트엔드가 가벼워지고 전체 시스템 안정성이 올라간다.

처음엔 LLM 라우터가 단순히 API 호출 중개 정도로 생각했는데, 실제로는 프론트엔드 아키텍처와 UX 전반을 고민하게 만드는 꽤 까다로운 문제더군요. 우리 팀 경험이 비슷한 고민을 하는 분들께 조금이나마 도움이 되길 바랍니다.
