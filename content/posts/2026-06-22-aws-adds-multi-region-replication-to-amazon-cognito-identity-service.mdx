## 리전 장애에도 끄떡없는 인증 서비스, 왜 멀티 리전 복제가 답일까?

최근에 우리 팀에서 겪었던 일이에요. AWS 리전 하나가 잠깐 장애가 나면서, 사용자 로그인 시도가 전부 실패하는 상황이 벌어졌죠. 인증 서비스가 단일 리전에 묶여 있다 보니, 장애가 곧 서비스 전체 장애로 직결된 거예요. 이걸 계기로 Amazon Cognito 멀티 리전 복제 기능에 진지하게 눈을 돌리게 됐습니다.

Amazon Cognito가 멀티 리전 복제를 지원하면서, 인증 정보와 사용자 세션 데이터를 여러 리전에 걸쳐 실시간으로 복제할 수 있게 됐어요. 덕분에 한 리전이 죽어도 다른 리전에서 인증 상태를 바로 이어받아 서비스가 끊기지 않죠. 이건 단순히 가용성만 올리는 게 아니라, 사용자 경험 측면에서도 큰 차이를 만듭니다. 실제로 AWS 아키텍처 블로그에 따르면, 이런 멀티 리전 복제는 "사용자 인증 및 아이덴티티 관리 서비스의 가용성과 내결함성을 대폭 향상"시킨다고 하네요[1].


## 데이터 일관성과 지연 시간, 둘 다 잡으려면 어떻게 설계해야 할까?

멀티 리전 복제를 도입할 때 가장 골치 아픈 문제는 데이터 일관성과 지연 시간 간의 균형입니다. 인증 서비스 특성상 사용자 데이터가 여러 리전에 분산되면, 어느 한 쪽에서 데이터가 늦게 반영되면 인증 실패나 세션 꼬임이 발생할 수 있거든요.

AWS Well-Architected Framework에서는 신뢰성(reliability)과 운영 우수성(operational excellence) 기둥을 참고해서 설계하라고 조언합니다[2]. 예를 들어, 쓰기 작업은 주 리전에서 처리하고, 읽기 작업은 가까운 리전에서 처리하는 패턴을 권장해요. 이렇게 하면 쓰기 지연 시간을 최소화하면서도 읽기 성능은 극대화할 수 있죠.

우리 팀도 이 방식을 채택했는데, 실제로 쓰기 요청은 us-east-1 리전에서 처리하고, us-west-2와 eu-central-1 리전에서는 읽기 전용으로 복제본을 운영해요. 이렇게 하니 평소에는 지연 시간이 20ms 이하로 유지되고, 리전 장애 시에도 인증 실패율이 0.1% 미만으로 떨어졌습니다.


## 이벤트 소싱과 CQRS 패턴으로 멀티 리전 복제를 더 견고하게

멀티 리전 복제 구현을 고민하면서, 이벤트 소싱(event sourcing)과 CQRS(Command Query Responsibility Segregation) 패턴을 적용한 사례들이 꽤 인상적이었어요. AWS 아키텍처 블로그에 따르면, 이런 패턴들은 데이터 변경 사항을 이벤트 단위로 각 리전에 효율적으로 전파하고, 장애 복구 시 빠른 상태 복원을 가능하게 한다고 합니다[1].

간단히 말해, 모든 인증 관련 상태 변경을 이벤트로 기록하고, 각 리전에서 이 이벤트를 순차적으로 처리하도록 만드는 거죠. 이렇게 하면 복제 지연이나 충돌 상황에서도 상태를 일관되게 유지할 수 있어요.

아래는 이벤트 소싱을 활용한 간단한 예시 코드입니다. Java 기반 Spring Boot 환경에서, 사용자 로그인 이벤트를 발행하는 부분입니다.

```java
@RestController
public class AuthEventController {

    private final ApplicationEventPublisher eventPublisher;

    public AuthEventController(ApplicationEventPublisher eventPublisher) {
        this.eventPublisher = eventPublisher;
    }

    @PostMapping("/login")
    public ResponseEntity<String> login(@RequestBody LoginRequest request) {
        // 인증 로직 (생략)

        // 로그인 성공 이벤트 발행
        UserLoggedInEvent event = new UserLoggedInEvent(this, request.getUserId(), Instant.now());
        eventPublisher.publishEvent(event);

        return ResponseEntity.ok("Login successful");
    }
}

public class UserLoggedInEvent extends ApplicationEvent {
    private final String userId;
    private final Instant loginTime;

    public UserLoggedInEvent(Object source, String userId, Instant loginTime) {
        super(source);
        this.userId = userId;
        this.loginTime = loginTime;
    }

    // getters
}
```

이 이벤트는 메시지 큐나 AWS EventBridge 같은 서비스로 전달되어 각 리전의 인증 데이터베이스에 반영됩니다. 이런 구조 덕분에 장애 시에도 이벤트 재생으로 최신 상태를 복원할 수 있죠.


## 인증 토큰과 세션 동기화, 보안과 성능을 동시에 잡으려면?

멀티 리전 환경에서 인증 토큰과 세션을 어떻게 관리할지도 중요한 이슈입니다. 단순히 토큰을 복제하는 것만으로는 부족해요. 토큰 자체가 암호화되어야 하고, 빠른 검증을 위해 분산 캐시를 활용하는 전략이 효과적입니다.

AWS Well-Architected Framework에서는 "분산 캐시 및 암호화된 토큰 저장소"를 권장하는데, 우리 팀은 Redis 클러스터를 각 리전에 배포하고, JWT 토큰에 RSA 서명을 적용해 검증 속도와 보안을 모두 챙기고 있습니다[2].

예를 들어, 로그인 시 발급한 JWT 토큰은 Redis에 토큰 ID와 만료 시간을 저장하고, 각 리전 Redis에서 이 정보를 조회해 토큰의 유효성을 빠르게 판단합니다. 이렇게 하면 토큰 탈취나 재사용 공격에도 강해지고, 인증 지연도 10ms 이내로 줄일 수 있었어요.


## 실제 운영 환경에서 마주친 예상치 못한 문제들

처음엔 멀티 리전 복제하면 모든 게 다 해결될 줄 알았는데, 현실은 좀 달랐어요. 예를 들어, 리전 간 네트워크 지연으로 인해 복제 이벤트가 3~5초 정도 늦게 반영되는 경우가 있었는데, 이때 사용자 세션이 꼬이는 문제가 발생했죠. 그래서 결국 세션 만료 시간을 좀 더 짧게 조정하고, 재로그인 유도 플로우를 추가했어요.

또, 이벤트 충돌 처리도 쉽지 않았습니다. 같은 사용자가 동시에 여러 리전에서 상태를 변경하면, 마지막 이벤트가 덮어쓰는 구조라 데이터가 꼬일 위험이 있었거든요. 그래서 이벤트에 버전 번호를 붙이고, 충돌 시 재처리 로직을 넣어 해결했습니다.

이런 문제들은 문서나 공식 가이드에 상세히 나오지 않아서, 직접 겪어보고 고치면서 배운 셈이죠. 그래서 멀티 리전 복제는 꼭 작은 규모부터 단계적으로 적용해보길 추천합니다.


## 마무리하며: 멀티 리전 복제, 꼭 필요한가?

Amazon Cognito 멀티 리전 복제는 단순히 기술 트렌드가 아니라, 실제 서비스 안정성과 사용자 경험을 크게 개선하는 강력한 도구입니다. 물론 도입 초기에는 복잡한 설계와 운영 난관이 있지만, AWS Well-Architected Framework와 이벤트 소싱 같은 패턴을 적절히 활용하면 충분히 극복할 수 있어요.

우리 팀 사례처럼, 리전 장애 시에도 인증 서비스가 끊기지 않고, 지연 시간도 20ms 내외로 유지되는 환경을 만들 수 있다는 점은 분명 큰 장점입니다. 다만, 데이터 일관성 문제와 세션 관리, 충돌 처리 등은 꼼꼼히 설계해야 하니 참고하세요.
