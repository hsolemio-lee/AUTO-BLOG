## SSH 접속으로 EMR 작업 관리하다가 겪은 골치

한 번은 우리 팀에서 EMR(Elastic MapReduce) 작업을 관리하는데 SSH 접속을 통해 직접 서버에 들어가 명령어를 실행하는 방식을 쓰고 있었어요. 700개가 넘는 파이프라인 작업을 이렇게 관리한다는 게 말이 되냐고요? 저도 처음엔 "이게 최선인가?" 싶었죠. 실제로 SSH 기반 관리 방식은 작업 상태 확인이나 장애 대응에 너무 느리고, 자동화도 쉽지 않았어요. 

특히, SSH 접속은 보안 설정도 까다롭고, 작업을 수동으로 실행하다 보니 운영 중 실수가 잦았습니다. 게다가 여러 팀이 동시에 작업을 관리하려면 충돌도 잦았고, 배포도 번거로웠죠.

## Slack이 REST API 아키텍처로 갈아탄 이유

Slack은 이런 문제를 해결하기 위해 EMR 파이프라인 관리 방식을 완전히 바꿨습니다. SSH 접속 대신 REST API 기반 아키텍처로 전환한 거죠. 무려 700개 이상의 작업을 한꺼번에 마이그레이션했는데, 이 과정에서 마이크로서비스와 클라우드 디자인 패턴을 적극 활용했습니다.

이전에는 작업 하나하나에 SSH로 접속해서 명령을 내렸다면, 이제는 REST API 호출로 작업 상태를 조회하고, 실행 명령을 내립니다. 이게 왜 좋은지 체감이 확 되더라고요. API를 통해 작업 상태를 중앙에서 모니터링할 수 있으니 장애가 나도 빠르게 대응할 수 있고, 자동화 스크립트와 CI/CD 파이프라인에 자연스럽게 통합할 수 있습니다.

Microsoft의 클라우드 디자인 패턴 문서에서도 언급하듯, 느슨한 결합(loose coupling)과 독립적 배포가 가능한 구조는 운영 효율성을 극대화하는 데 필수입니다. Slack도 이걸 잘 적용했죠[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/).

## REST API 도입으로 바뀐 운영 모습

가장 크게 달라진 점은 작업 상태 모니터링과 제어가 완전히 중앙화됐다는 겁니다. 예전에는 SSH 접속 로그를 뒤져가며 상태를 확인했는데, 이제는 API 호출로 실시간 상태를 받아볼 수 있어요. 덕분에 장애 발생 시 빠른 롤백이나 재시작이 가능해졌고, 운영 자동화 수준도 크게 올라갔습니다.

또한, API 기반이라 CI/CD 도구와도 쉽게 연동됩니다. 예를 들어, GitHub Actions 같은 자동화 도구에서 API 호출로 EMR 작업을 실행하거나 상태를 확인하는 식이죠. 이 덕분에 배포 파이프라인에 EMR 작업 관리가 자연스럽게 녹아들어갔습니다[Martin Fowler - Continuous Integration](https://martinfowler.com/articles/continuousIntegration.html).

## 실제로 Slack에서 쓴 REST API 예시

아래는 Slack에서 EMR 작업을 시작하는 REST API 호출 예시입니다. 실제 코드가 공개된 건 아니지만, 이런 형태로 내부 API를 설계했다고 보면 됩니다.

```python
import requests

EMR_API_BASE = "https://emr-api.slack.com/v1"

# EMR 작업 실행 요청
job_id = "job-1234"
response = requests.post(f"{EMR_API_BASE}/jobs/{job_id}/start", headers={"Authorization": "Bearer token"})

if response.status_code == 200:
    print("작업이 성공적으로 시작되었습니다.")
else:
    print(f"작업 시작 실패: {response.text}")
```

이런 API 호출을 통해 작업을 실행하고, 상태 조회, 중단, 재시작 등 모든 관리 작업을 프로그래매틱하게 처리할 수 있습니다. SSH 접속 없이도 말이죠.

## 마이크로서비스와 클라우드 패턴이 왜 중요한가

Slack의 전환은 단순히 SSH를 REST로 바꾼 게 아니에요. 마이크로서비스 아키텍처를 도입해 각 파이프라인 작업을 독립적인 서비스 단위로 분리했고, 클라우드 디자인 패턴을 적용해 확장성과 장애 대응력을 높였습니다. 

이렇게 하면 한 작업에서 문제가 생겨도 전체 시스템에 영향이 적고, 개별 서비스만 독립적으로 배포할 수 있어 개발 속도도 빨라집니다. 물론, 서비스 간 통신이 많아져 네트워크 비용과 복잡도가 늘어나는 단점도 있지만, Slack은 이걸 API 게이트웨이와 서비스 메시 같은 최신 인프라로 잘 관리하고 있죠[Martin Fowler - Microservices](https://martinfowler.com/articles/microservices.html).

## 도입하면서 겪은 현실적인 어려움과 극복법

처음엔 기존 SSH 기반 작업을 API로 전환하는 게 생각보다 쉽지 않았습니다. 700개 넘는 작업마다 인터페이스가 조금씩 달라서 표준화가 필요했고, 기존 스크립트와 툴을 모두 수정해야 했거든요. 

또한, API 서버의 안정성 확보가 관건이었는데, 장애 시 전체 파이프라인이 멈추는 걸 막기 위해 장애 격리 패턴을 도입했습니다. 서비스별 타임아웃과 재시도 정책을 엄격히 적용했고, 모니터링과 알림 체계를 촘촘히 구축했죠.

이 과정에서 Slack 백엔드 팀은 클라우드 기반 자동화 도구도 적극 활용했습니다. 배포 파이프라인을 표준화하고, 운영과 개발팀 간 협업을 원활하게 만들어 전환 성공률을 높였어요[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/).

## 이걸 우리 팀에 적용하려면 어떻게 시작할까?

- **기존 SSH 스크립트 목록화**: 어떤 작업이 있는지, 어떤 명령을 실행하는지 정리하세요.
- **REST API 설계부터 시작**: 작업 실행, 상태 조회, 중단 등 필요한 기능을 API로 정의합니다.
- **점진적 마이그레이션**: 한두 개 작업부터 API 호출로 전환해 안정성을 확인하세요.
- **자동화 도구 연동**: CI/CD 파이프라인에 API 호출을 넣어 자동화 수준을 높입니다.
- **모니터링과 장애 대응 체계 구축**: API 서버와 작업 상태를 실시간으로 감시할 수 있도록 만드세요.

이 과정에서 마이크로서비스 패턴과 클라우드 디자인 패턴을 참고하면 구조 설계에 큰 도움이 될 겁니다.

---

Slack 사례를 통해 알 수 있듯, SSH 기반 관리에서 REST API 아키텍처로 전환하는 건 단순한 기술 교체가 아니라 운영 효율성과 확장성, 협업 방식을 근본적으로 바꾸는 일입니다. 처음엔 복잡하고 힘들지만, 제대로만 한다면 장기적으로 큰 이득을 가져다줍니다.
