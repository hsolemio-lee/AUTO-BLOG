### "AI 서비스가 갑자기 느려졌어요!" - Spring AI 2.0.0-M8 프로덕션 도입에서 마주친 현실 문제

얼마 전 우리 팀에서 Spring AI 2.0.0-M8 버전을 프로덕션에 올렸는데, 처음엔 성능이 괜찮아 보였지만 실제 트래픽이 몰리면서 지연시간이 확 늘고 메모리 사용량도 급증하는 걸 경험했어요. 이걸 겪고 나니, 단순히 최신 버전 쓴다고 끝나는 게 아니더라고요. 그래서 이번 글에서는 Spring AI 2.0.0-M8를 안정적으로 운영하기 위해 꼭 필요한 튜닝 팁과 보안 설정, 그리고 안전한 롤아웃 전략을 공유해보려 합니다.

## Spring Boot 3.x 기반이라 튜닝 가이드도 그대로 쓸 수 있다

Spring AI 2.0.0-M8는 Spring Boot 3.x 위에서 만들어졌어요. 즉, 기존에 Baeldung에서 정리한 [Spring Boot 성능 튜닝 가이드](https://www.baeldung.com/spring-boot-performance)가 그대로 적용 가능하다는 뜻이죠. 우리가 실제로 적용했던 설정 몇 가지를 예로 들면:

- **JVM 힙 메모리 제한**: `-Xms512m -Xmx2g`로 시작해서 실제 메모리 사용량을 모니터링하며 조절
- **스레드 풀 크기 조정**: AI 모델 호출이 I/O 바운드 작업이라, 기본 200에서 500으로 늘려서 처리량 증가
- **캐시 활용**: 반복되는 AI 프롬프트 결과는 Redis 캐시로 5분간 저장해 API 호출 수 줄임

이런 세팅을 통해 메모리 과다 사용과 스레드 경합 문제를 어느 정도 완화할 수 있었어요. 물론, 서비스 특성에 따라 조절은 필수입니다.

## Spring Framework 핵심 기능으로 AI 서비스 보안과 확장성 챙기기

Spring AI 2.0.0-M8는 Spring Framework의 의존성 주입(DI)과 AOP를 적극 활용해 보안과 확장성을 강화할 수 있어요. 예를 들어, OpenAI API 키를 관리할 때:

```java
@Component
public class OpenAIClient {

    @Value("${openai.api.key}")
    private String apiKey;

    public String callAIModel(String prompt) {
        // 실제 API 호출 로직
        // API 키는 외부 설정 파일이나 Vault에서 주입받아 노출 최소화
    }
}

@Aspect
@Component
public class ApiCallLoggingAspect {

    @Around("execution(* com.example.ai.OpenAIClient.callAIModel(..))")
    public Object logApiCall(ProceedingJoinPoint joinPoint) throws Throwable {
        // 호출 시간과 요청 내용 로깅
        long start = System.currentTimeMillis();
        Object result = joinPoint.proceed();
        long duration = System.currentTimeMillis() - start;
        System.out.println("AI API 호출 시간: " + duration + "ms");
        return result;
    }
}
```

이렇게 하면 API 키 노출 위험을 줄이고, 호출 로그를 통해 이상 징후 감지도 가능하죠. 또한, AOP를 활용해 인증·인가 로직을 공통으로 처리하면 서비스 확장 시 보안 유지가 훨씬 수월해집니다.[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)에서 자세한 내용을 참고할 수 있어요.

## OpenAI API 키 관리와 요청 제한 설정은 필수

AI 모델 호출 시 OpenAI API를 쓴다면, API 키 관리와 요청 제한 설정은 절대 빼먹으면 안 됩니다. 저희는 다음과 같은 방법을 썼어요:

- **API 키는 환경 변수 또는 Vault에 저장해 코드에 직접 하드코딩 금지**
- **Spring Boot의 `application.yml`에서 요청 제한과 타임아웃 설정**

```yaml
openai:
  api:
    key: ${OPENAI_API_KEY}
    timeout: 5000  # 5초 타임아웃
    max-requests-per-minute: 60
```

- **스프링 인터셉터로 분당 호출 횟수 제한 구현**

이런 조치 덕분에 과금 폭탄 맞을 위험도 줄이고, 갑작스러운 API 장애에도 서비스가 무너지지 않도록 대비할 수 있었죠.[OpenAI API Documentation](https://platform.openai.com/docs/overview)에서 권장하는 보안 모범 사례를 꼭 참고하세요.

## AI 프롬프트 튜닝은 비용과 응답 품질 양쪽을 잡는 핵심

AI 모델 호출 비용과 응답 품질은 프롬프트 설계에 크게 좌우됩니다. Anthropic의 [프롬프트 엔지니어링 가이드](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)를 참고해보면, 짧고 명확한 지시문이 비용 절감에 효과적이라는 점을 알 수 있어요.

우리 팀에서는 Spring AI 2.0.0-M8 내에서 프롬프트 템플릿 클래스를 만들어 재사용하고, 상황에 따라 변수를 동적으로 바꾸는 방식을 썼습니다:

```java
public class PromptTemplate {
    private String template = "Answer briefly: %s";

    public String formatPrompt(String question) {
        return String.format(template, question);
    }
}

// 사용 예
String prompt = new PromptTemplate().formatPrompt("Spring AI 2.0.0-M8의 장점은?");
String response = openAIClient.callAIModel(prompt);
```

이렇게 하면 프롬프트 길이가 불필요하게 길어지는 걸 막고, 응답 속도와 비용을 최적화할 수 있었어요.

## 점진적 배포와 Canary 전략으로 무중단 롤아웃 하기

Spring Boot Reference Documentation에 따르면, Spring AI 2.0.0-M8 프로덕션 도입 시 점진적 배포와 Canary 배포 방식을 권장합니다. 실제 우리 팀도 다음과 같은 전략을 썼어요:

1. **스테이징 환경에서 충분한 부하 테스트 진행**
2. **프로덕션 트래픽의 5%만 Canary 인스턴스로 라우팅**
3. **모니터링 지표(응답 시간, 에러율, 메모리 사용량)를 10분 단위로 체크**
4. **문제 없으면 트래픽 점진 확대, 문제 발생 시 즉시 롤백**

이 과정에서 GitHub Engineering Blog에서 소개한 [대규모 서비스 롤아웃과 모니터링 전략](https://github.blog/category/engineering/)을 참고해 장애 대응 프로세스를 만들었는데, 실제로 빠른 문제 감지와 대응에 큰 도움이 됐습니다.

## 실제 적용 후 느낀 점과 주의할 점

처음엔 Spring AI 2.0.0-M8가 최신 버전이라 무조건 좋을 줄 알았는데, 프로덕션 환경에서는 튜닝과 모니터링 없이는 금방 병목이 생긴다는 걸 뼈저리게 느꼈어요. 특히 AI 호출이 외부 API 의존도가 높으니, 네트워크 장애나 API 변경에도 유연하게 대응할 수 있는 설계가 필수입니다.

또, 보안 관련해서는 API 키를 안전하게 관리하는 게 정말 중요해요. 한 번 노출되면 과금 폭탄이나 데이터 유출 위험이 크니까요.

마지막으로, 프롬프트 튜닝은 단순히 비용 절감뿐 아니라 AI 응답의 품질과 직결되니, 여러 버전을 테스트하면서 최적점을 찾아가는 게 좋습니다.
