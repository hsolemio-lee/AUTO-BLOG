## 대규모 LLM 서빙, Netflix는 왜 직접 만들었을까?

최근 AI 모델들이 점점 커지고 복잡해지면서, 단순히 모델을 학습시키는 것만큼이나 실시간으로 안정적으로 서빙하는 게 더 큰 도전이 되고 있어요. 특히 Netflix처럼 수백만 명이 동시에 쓰는 서비스에서는 지연시간과 가용성이 생명인데, 상용 솔루션만으로는 한계가 분명하죠. 그래서 Netflix는 직접 Triton과 vLLM을 조합해 자체 LLM 서빙 플랫폼을 만들었는데, 여기에는 꽤 흥미로운 실무 고민과 트레이드오프가 숨어있습니다.


## Triton과 vLLM, 왜 같이 썼을까?

Triton은 NVIDIA에서 만든 고성능 추론 서버로, GPU 자원을 효율적으로 관리하면서 여러 모델을 동시에 돌릴 수 있어요. 반면 vLLM은 대규모 언어 모델을 배치 처리(batch inference)와 비동기 요청에 최적화한 라이브러리인데, 특히 여러 요청을 묶어서 처리하는 데 강점이 있죠. Netflix는 이 둘을 결합해 GPU 활용률을 극대화하면서도, 개별 요청에 대한 응답 지연을 최소화하는 방향을 택했어요.

처음엔 단일 Triton 서버에 모든 걸 맡겼는데, 실제 트래픽이 몰리면 GPU가 놀거나 병목이 생기더라고요. vLLM을 중간에 끼워 넣으니까, 여러 요청을 묶어서 한 번에 처리하면서도 각 요청의 대기시간을 100ms 이하로 유지할 수 있었어요. 이건 실제로 겪어보면 체감 성능 차이가 꽤 큽니다.


## 배포할 때 작은 범위부터 점진적으로, 이게 정말 답이더라

Netflix가 강조하는 부분 중 하나는 바로 점진적 배포 전략이에요. LLM 서빙 같은 복잡한 백엔드 기능은 한꺼번에 전체 트래픽에 적용하면 장애 리스크가 너무 크거든요. 그래서 신규 기능이나 모델 버전은 전체 트래픽의 1~5% 정도부터 시작해서, 안정성을 확인하며 점차 늘려가는 방식을 썼습니다.

이게 단순히 안정성 확보뿐 아니라, 실제 운영 중에 발생하는 미묘한 성능 저하나 오류 패턴을 빠르게 감지하는 데도 효과적이에요. 실패 유형을 초기에 계측하면 장애 대응 속도가 훨씬 빨라진다는 점은 다른 대규모 서비스 사례에서도 입증된 바 있죠[TypeScript 5.x Release Notes](https://devblogs.microsoft.com/typescript/announcing-typescript-5-4/).


## 실제 성능 튜닝에서 가장 신경 쓴 부분은?

Netflix는 GPU 메모리 관리와 요청 큐잉 전략에 특히 공을 들였어요. 예를 들어, vLLM에서는 여러 요청을 배치로 묶는 과정에서 최대 배치 크기(max_batch_size)를 64로 설정했는데, 이 수치를 너무 높이면 GPU 메모리 부족으로 OOM(Out Of Memory) 오류가 발생하고, 너무 낮으면 GPU 활용률이 떨어지거든요.

또한, 요청 큐잉 시 최대 대기 시간(max_wait_time_ms)을 20ms로 제한해, 너무 오래 기다리지 않도록 했어요. 이 설정 덕분에 평균 응답 시간은 150ms 안팎으로 유지하면서도, GPU는 85% 이상 꾸준히 활용할 수 있었습니다.

아래는 이런 설정을 반영한 간단한 vLLM 서버 초기화 예시입니다:

```python
from vllm import LLMEngine

engine = LLMEngine(
    model="facebook/opt-6.7b",
    max_batch_size=64,
    max_wait_time_ms=20,
    device="cuda:0"
)

# 요청을 비동기로 처리하는 예
async def handle_request(prompt: str):
    result = await engine.generate(prompt)
    return result.text
```

이 코드는 실제로 Netflix가 공개한 구조와 완전히 같진 않지만, 핵심 아이디어인 배치 크기와 대기 시간 조절, 그리고 GPU 디바이스 지정 방식을 보여줍니다.


## 운영 중 겪은 의외의 문제와 해결책

Netflix가 겪은 재미있는 문제 중 하나는, 특정 시점에 갑자기 요청 패턴이 몰리면서 GPU 스케줄링이 꼬여버린 거였어요. 원인은 vLLM 내부 큐에 요청이 너무 빠르게 쌓이면서, 배치 생성 타이밍과 GPU 커널 실행 간 타이밍이 엇박자가 난 거였죠.

이를 해결하기 위해, 내부적으로 큐 길이를 모니터링하고, 임계치 이상이면 신규 요청을 잠시 지연시키는 '백프레셔(backpressure)' 메커니즘을 도입했어요. 덕분에 GPU가 과부하 상태에 빠지지 않고, 전체 시스템 안정성이 크게 개선됐습니다.

이 경험은 작은 범위의 점진적 배포 전략과 맞물려서, 신규 기능 도입 시 운영 리스크를 확실히 낮추는 데 큰 도움이 됐죠[TypeScript Handbook](https://www.typescriptlang.org/docs/handbook/intro.html).


## Netflix LLM 서빙 플랫폼에서 배울 점

- **Triton과 vLLM 조합의 힘**: 단일 솔루션보다 두 기술의 장점을 살려 GPU 활용과 응답 속도를 동시에 잡는 게 핵심.
- **배치 크기와 대기 시간 조절**: 이 두 파라미터 튜닝이 성능 최적화의 승부처.
- **점진적 배포와 실시간 계측**: 장애 예방과 빠른 대응을 위해 필수.
- **백프레셔 도입으로 과부하 방지**: 운영 중 발생하는 예기치 못한 부하를 막는 안전장치.


LLM 서빙은 단순히 모델만 잘 돌리는 게 아니라, 인프라와 소프트웨어가 유기적으로 잘 맞아야 하는 복잡한 영역입니다. Netflix 사례를 보면서, 우리도 실제 운영 환경에서 작은 실험과 계측을 통해 점진적으로 개선하는 게 얼마나 중요한지 다시 한번 느꼈어요.
