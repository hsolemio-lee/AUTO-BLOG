## "왜 자동 구성만으로는 부족할까?"

최근에 팀에서 Spring Boot 기반 서비스의 성능 문제를 겪으면서, Phil Webb가 진행한 "A Bootiful Podcast" 에피소드를 다시 들었어요. 그중에서 "자동 구성(auto-configuration)과 스타터(starter) 의존성"이 얼마나 개발 생산성을 높여주는지, 그리고 프로덕션에서 실제로 어떻게 튜닝해야 하는지에 대한 이야기가 인상적이었죠.

처음 Spring Boot를 접할 때는 "자동으로 다 해주니까 편하다"가 전부였는데, 실제 운영 환경에서는 JVM 튜닝, 커넥션 풀 최적화, 캐싱 전략 같은 세밀한 조정이 필수라는 걸 깨달았습니다. 자동 구성은 기본 뼈대를 빠르게 세우는데 탁월하지만, 서비스가 커질수록 기본 세팅만으로는 한계가 분명하거든요.


## JVM, 커넥션 풀, 캐싱 — 어디서부터 손대야 할까?

Phil Webb가 강조한 부분 중 하나는 JVM 설정입니다. 예를 들어, 힙 메모리 크기를 서비스 특성에 맞게 조절하는 건 기본 중의 기본인데요. 우리가 운영하는 API 서버는 트래픽이 급증할 때 GC가 잦아져서 응답 지연이 발생했었어요. JVM 옵션을 `-Xms4g -Xmx4g -XX:+UseG1GC`로 고정하고, G1 GC 튜닝 파라미터를 조정하니 GC 시간이 30% 이상 줄었죠.

다음으로 데이터베이스 커넥션 풀 최적화도 중요합니다. Spring Boot 기본 HikariCP 설정은 꽤 합리적이지만, 최대 커넥션 수(`maximumPoolSize`)를 실제 DB 처리량과 맞추지 않으면 오히려 대기 시간이 길어질 수 있어요. 우리 팀은 최대 커넥션 수를 50에서 100으로 늘리고, 커넥션 타임아웃을 30000ms로 설정했더니 동시 요청 처리량이 눈에 띄게 개선됐습니다.

캐싱 전략도 빼놓을 수 없죠. Redis를 활용해 자주 조회되는 데이터를 캐싱하는데, TTL(Time To Live)을 10분으로 고정했다가 트래픽 패턴에 맞게 5분~30분 사이에서 조정하며 성능을 최적화했습니다. 캐시 미스율을 모니터링하면서 TTL을 조절하는 게 핵심입니다.


```java
// 간단한 Redis 캐싱 예제
@Service
public class UserService {

    private final UserRepository userRepository;
    private final CacheManager cacheManager;

    public UserService(UserRepository userRepository, CacheManager cacheManager) {
        this.userRepository = userRepository;
        this.cacheManager = cacheManager;
    }

    @Cacheable(value = "users", key = "#userId")
    public User getUserById(Long userId) {
        return userRepository.findById(userId).orElseThrow(() -> new RuntimeException("User not found"));
    }

    public void evictUserCache(Long userId) {
        cacheManager.getCache("users").evict(userId);
    }
}
```

위 코드는 Spring Boot에서 `@Cacheable`을 활용해 Redis 캐시를 쉽게 적용하는 예입니다. 실제 운영에서는 캐시 무효화 시점을 신중하게 관리해야 하는데, 이 부분에서 실수가 많으니 꼭 주의하세요.


## Spring Security와 OAuth2, JWT로 보안도 기본 이상은 챙기자

Phil Webb가 직접 만든 Spring Boot는 기본적으로 Spring Security와 통합이 잘 되어 있어요. OAuth2, JWT 같은 표준 인증 방식을 바로 적용할 수 있다는 점이 정말 편리하죠. 우리 팀도 최근에 OAuth2 기반 소셜 로그인과 JWT 토큰 인증을 도입했는데, 설정이 생각보다 간단해서 놀랐습니다.

다만, 기본 설정만 믿고 넘어가면 안 됩니다. 예를 들어, JWT 토큰 만료 시간을 너무 길게 잡으면 보안 리스크가 커지고, 너무 짧게 잡으면 사용자 경험이 나빠지거든요. 우리는 액세스 토큰 만료 시간을 15분, 리프레시 토큰은 7일로 설정해 적절한 균형을 맞췄습니다.

아래는 Spring Security에서 JWT 필터를 등록하는 간단한 예시입니다.

```java
@Configuration
public class SecurityConfig extends WebSecurityConfigurerAdapter {

    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
            .csrf().disable()
            .authorizeRequests()
                .antMatchers("/api/auth/**").permitAll()
                .anyRequest().authenticated()
            .and()
            .addFilterBefore(jwtAuthenticationFilter(), UsernamePasswordAuthenticationFilter.class);
    }

    @Bean
    public JwtAuthenticationFilter jwtAuthenticationFilter() {
        return new JwtAuthenticationFilter();
    }
}
```

이처럼 Spring Boot는 보안 설정을 모듈화해서 관리하기 쉽게 해줍니다. 하지만 보안은 한 번 설정으로 끝나는 게 아니라, 주기적인 점검과 개선이 필수라는 점도 잊지 마세요.


## 블루-그린과 카나리 배포, Spring Boot는 어떻게 돕나?

프로덕션 롤아웃 전략도 Phil Webb가 자주 언급하는 주제입니다. 블루-그린 배포와 카나리 배포가 대표적인데, Spring Boot 애플리케이션은 클라우드 네이티브 환경에 잘 맞춰져 있어서 이런 전략을 적용하기 편리합니다.

우리 팀은 AWS ECS와 함께 카나리 배포를 도입했는데, Spring Boot의 헬스체크 엔드포인트(`/actuator/health`) 덕분에 로드 밸런서가 새 버전 인스턴스 상태를 정확히 판단해 점진적 트래픽 전환이 가능했어요.

처음엔 배포 자동화 스크립트 작성이 복잡했지만, Gradle 빌드와 Docker 이미지 태깅을 체계화하고, 헬스체크 커스터마이징으로 실패 시 롤백 조건을 명확히 하니 안정성이 크게 올라갔습니다.


## Spring Framework의 핵심 기능들이 왜 여전히 중요한가

Phil Webb가 강조하는 또 하나는 Spring Framework 코어 기술들의 중요성입니다. 의존성 주입(DI)과 AOP는 Spring Boot의 기반이자, 안정적인 백엔드 아키텍처를 만드는 데 필수적이죠.

DI 덕분에 테스트하기 쉬운 코드 구조를 만들 수 있고, AOP로 로깅, 트랜잭션 관리 같은 횡단 관심사를 깔끔하게 분리할 수 있습니다. 이런 기본기가 튼튼해야만, 프로덕션 환경에서 발생하는 복잡한 문제도 빠르게 대응할 수 있다는 걸 여러 번 경험했습니다.

### 정리하며

Phil Webb의 경험과 조언을 듣고 나니, Spring Boot는 단순히 빠른 개발 도구가 아니라, 프로덕션 환경에서 안정성과 확장성을 확보할 수 있는 강력한 플랫폼이라는 생각이 듭니다. 하지만 그만큼 기본 설정에 안주하지 않고, JVM부터 보안, 배포 전략까지 꼼꼼히 챙기는 노력이 필요하죠.

- JVM GC 튜닝과 커넥션 풀 크기 조절은 필수
- 캐시 전략은 서비스 특성에 맞게 TTL과 무효화 정책을 관리
- Spring Security와 JWT로 인증 보안 강화, 토큰 만료 시간 조절 신경 쓰기
- 헬스체크를 활용한 블루-그린, 카나리 배포로 무중단 배포 실현
- Spring Framework 코어 기능을 이해하고 활용해 유지보수성 높이기

이런 부분들이 결국 서비스 안정성과 사용자 경험을 좌우합니다. 여러분도 다음 배포 전, 한 번쯤 Phil Webb의 조언을 떠올리며 설정을 점검해보세요.
