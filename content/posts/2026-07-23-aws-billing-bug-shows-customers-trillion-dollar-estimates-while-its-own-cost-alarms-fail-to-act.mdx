## AWS 청구서에 조 단위 숫자가 찍힌다면, 당신의 첫 반응은?

얼마 전 AWS 고객들이 청구서에서 수조 달러(trillion-dollar)가 찍힌 걸 보고 깜짝 놀랐다는 소식이 들려왔습니다. 이게 단순한 오타일까? 아니면 시스템 어딘가에 치명적인 버그가 있는 걸까? 문제는 이뿐만이 아니었어요. 심지어 AWS 자체의 비용 알람 시스템도 이 엄청난 오산을 감지하지 못했다는 점이 더 충격적이었죠.

이런 일이 벌어진다면, 우리 같은 백엔드 엔지니어는 어떤 교훈을 얻어야 할까요? 오늘은 이 사건을 출발점으로, 클라우드 비용 청구 시스템에서 어떻게 비용 오산을 막고, 알람 실패를 예방할 수 있는지 살펴보겠습니다.

---

## 비용 계산 오류가 왜 이렇게 심각한 문제인가?

비용 청구는 단순히 숫자 맞추기 이상의 의미를 가집니다. 고객 신뢰, 서비스 안정성, 그리고 회사의 재무 건전성까지 직결되죠. 특히 클라우드 환경은 자원 사용량이 실시간으로 변동하고, 복잡한 과금 정책이 적용되기 때문에 작은 계산 오류가 엄청난 오산으로 이어질 수 있습니다.

예를 들어, AWS 청구 버그에서는 다음과 같은 문제가 있었습니다:

- 비용 산출 로직에서 단위 변환 오류 혹은 데이터 누락 발생
- 비용 집계 과정에서 값이 비정상적으로 커지는 이상치 발생
- 이상치를 감지하는 알람 시스템이 오작동해 경고가 전혀 발생하지 않음

이런 문제는 고객에게 잘못된 청구서를 보내는 것뿐 아니라, 내부적으로도 비용 관리 시스템의 신뢰성을 무너뜨립니다.

## AWS Well-Architected Framework가 말하는 비용 관리 핵심은?

AWS Well-Architected Framework에서는 비용 관리와 모니터링에 대해 꽤 구체적인 가이드라인을 제공합니다. 핵심은 ‘다중 계층의 검증과 자동화된 알림 시스템 구축’입니다.[AWS Well-Architected Framework](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html)

- **다중 검증 레이어**: 비용 계산 결과를 여러 단계에서 검증해서 이상치를 조기에 발견
- **자동화된 알람**: 단순 임계치뿐 아니라 이상 탐지 알고리즘을 적용해 비정상 패턴을 감지
- **비용 계산 모듈 분리**: 비용 산출 로직을 독립적인 마이크로서비스로 분리해 테스트와 배포를 용이하게

처음에는 이게 별거 아닌 것 같지만, 실제로 대규모 환경에서 비용 계산 모듈을 하나로 뭉쳐두면 작은 버그가 전체 시스템에 치명타를 입힙니다. 분리된 서비스는 문제 발생 시 빠른 롤백과 부분 수정이 가능하죠.

## AWS 아키텍처 블로그가 제안하는 비용 산출 시스템 설계법

AWS Architecture Blog에서는 대규모 클라우드 환경에서 비용 계산 오류를 줄이기 위해 다음과 같은 아키텍처 패턴을 강조합니다.[AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/)

- **데이터 검증 및 이상 탐지**: 비용 데이터가 들어올 때마다 스키마 검증과 이상치 탐지 알고리즘 적용
- **분산 처리 아키텍처**: 비용 산출을 여러 서비스로 분산 처리해 단일 장애점 제거
- **장애 감지 및 자동 복구**: 알람 실패 시 자동으로 재시도하거나 관리자에게 즉시 통보하는 메커니즘 구축

예를 들어, 비용 데이터를 처리하는 파이프라인에서 Kafka 같은 메시징 큐를 활용해 데이터 흐름을 분리하고, 각 단계별로 유효성 검사를 넣는 식입니다. 만약 특정 단계에서 이상치가 감지되면 자동으로 해당 데이터를 격리하고, 운영자에게 즉시 알림을 보내는 거죠.

## 비용 계산 모듈을 마이크로서비스로 분리하면 어떤 점이 좋을까?

클라우드 비용 계산은 복잡한 로직과 다양한 외부 데이터 소스(API 호출, 로그 집계 등)를 필요로 합니다. 이걸 한 덩어리로 관리하다 보면 다음과 같은 문제가 생겨요:

- 작은 버그가 전체 비용 계산 결과를 망침
- 테스트가 어려워 배포 시 리스크 증가
- 장애 발생 시 전체 청구 시스템 마비

그래서 비용 계산 모듈을 독립적인 마이크로서비스로 분리하는 게 권장됩니다. 이렇게 하면:

- 각 서비스별로 단위 테스트, 통합 테스트가 쉬워짐
- 장애 시 영향을 받는 범위가 국한됨
- 새로운 비용 정책 도입이나 수정이 빠름

### 간단한 비용 계산 마이크로서비스 예시 (TypeScript)

```typescript
import express from 'express';

const app = express();
app.use(express.json());

// 비용 산출 함수
function calculateCost(usage: number, rate: number): number {
  if (usage < 0 || rate < 0) {
    throw new Error('Usage and rate must be non-negative');
  }
  return usage * rate;
}

app.post('/calculate', (req, res) => {
  try {
    const { usage, rate } = req.body;
    // 기본 유효성 검사
    if (typeof usage !== 'number' || typeof rate !== 'number') {
      return res.status(400).json({ error: 'Invalid input types' });
    }

    const cost = calculateCost(usage, rate);
    res.json({ cost });
  } catch (error) {
    res.status(500).json({ error: error.message });
  }
});

app.listen(3000, () => {
  console.log('Cost calculation service running on port 3000');
});
```

이런 식으로 비용 산출 로직을 API 형태로 분리하면, 다른 서비스들이 이 API를 호출해 비용을 계산할 수 있습니다. 그리고 이 서비스만 집중적으로 모니터링하고 테스트하면 되니 훨씬 안정적입니다.

## 비용 알람 시스템, 왜 실패했나? 그리고 어떻게 고칠까?

AWS 버그 사례에서 가장 놀라웠던 점은, 수조 달러라는 비정상적인 비용이 발생했는데도 자체 알람이 전혀 작동하지 않았다는 점입니다. 이걸 보면 단순 임계치 기반 알람만으로는 부족하다는 걸 알 수 있죠.

### 알람 실패 원인

- 임계치 설정이 너무 높거나 너무 낮아서 이상치를 감지 못함
- 알람 시스템 자체에 장애가 발생해 알림 전송 실패
- 비용 계산 결과가 비정상적일 때 이를 감지하는 로직 부재

### 개선 방안

- **이상 탐지 알고리즘 도입**: 단순 임계치 대신 통계 기반 이상치 탐지 기법(예: 이동 평균, 표준편차 기반 감지) 적용
- **중복 알람 경로 확보**: 이메일, SMS, 슬랙 등 다양한 채널로 알람 전송
- **알람 시스템 자체 모니터링**: 알람 전송 성공 여부를 별도로 모니터링해 실패 시 자동 재시도

예를 들어, 비용 알람을 AWS CloudWatch에서 설정할 때, 단순 임계치 외에 Lambda 함수로 커스텀 이상 탐지 로직을 넣을 수도 있습니다. 아래는 간단한 이상 탐지 예시 코드입니다.

```typescript
// 비용 데이터 배열에서 평균과 표준편차 계산
function mean(data: number[]): number {
  return data.reduce((a, b) => a + b, 0) / data.length;
}

function stddev(data: number[]): number {
  const m = mean(data);
  return Math.sqrt(data.reduce((a, b) => a + (b - m) ** 2, 0) / data.length);
}

function isAnomaly(latestCost: number, history: number[]): boolean {
  const m = mean(history);
  const sd = stddev(history);
  // 평균에서 3배 표준편차 이상 벗어나면 이상치로 판단
  return Math.abs(latestCost - m) > 3 * sd;
}

// 예시 사용
const pastCosts = [100, 105, 98, 102, 110];
const currentCost = 5000;

if (isAnomaly(currentCost, pastCosts)) {
  console.log('비용 이상치 감지!');
  // 알람 전송 로직 호출
}
```

이런 커스텀 로직을 CloudWatch 이벤트와 연동하면, 단순 임계치보다 훨씬 정교한 비용 이상 탐지가 가능합니다.

## 실제로 이런 아키텍처를 도입하면 어떤 점이 좋아질까?

- **비용 오산 방지**: 여러 검증 레이어 덕분에 수조 달러 급 오산은 거의 불가능
- **알람 신뢰도 상승**: 이상 탐지와 자동 복구 덕분에 알람 실패 확률 대폭 감소
- **운영 효율 개선**: 문제 발생 시 빠른 원인 파악과 대응 가능
- **서비스 확장성 확보**: 비용 정책 변경이나 신규 서비스 추가에 유연하게 대응

하지만 단점도 있습니다. 마이크로서비스 분리와 이상 탐지 로직 도입은 초기 개발 비용과 운영 복잡도를 늘립니다. 따라서 팀 규모와 서비스 규모에 맞춰 적절히 조절하는 게 중요하죠.
