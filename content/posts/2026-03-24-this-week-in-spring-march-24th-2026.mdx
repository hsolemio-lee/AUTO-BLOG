## "갑자기 프로덕션에서 메트릭이 더 촘촘해졌는데, 이걸 어떻게 활용하지?"

최근 우리 팀에서 Spring Boot 3.2로 업그레이드하면서 가장 먼저 맞닥뜨린 변화 중 하나가 바로 메트릭 수집과 모니터링 기능의 강화였습니다. 기본 제공되는 메트릭이 훨씬 정밀해져서, 애플리케이션 상태를 실시간으로 더 세밀하게 파악할 수 있게 된 거죠. 처음엔 "이게 별거 아니겠지" 했는데, 막상 운영 환경에서 체감하는 효과가 상당했습니다.

Spring Boot 3.2부터는 Micrometer 기반의 메트릭 기능이 기본 활성화되어, JVM 상태부터 HTTP 요청 지연시간, DB 커넥션 풀 상태까지 한눈에 모니터링할 수 있어요. 특히 p95, p99 같은 지연시간 퍼센타일을 기본으로 제공하기 때문에, 평균값에 가려졌던 병목 현상을 조기에 발견하는 데 큰 도움이 됩니다.

```java
// application.properties 예시
management.endpoints.web.exposure.include=health,metrics,prometheus
management.metrics.enable-all=true
management.endpoint.metrics.enabled=true

// JVM 힙 메모리와 쓰레드 풀 모니터링 활성화
management.metrics.distribution.percentiles-histogram.http.server.requests=true
```

이 설정만으로도 Prometheus나 Grafana 같은 툴과 연동해 대시보드를 만들 수 있는데, 우리 팀은 특히 GC 지연과 쓰레드 풀 대기 시간을 집중 모니터링하면서 이상 징후를 빠르게 잡아냈습니다. JVM 힙 메모리 설정과 쓰레드 풀 크기 조정이 성능 튜닝에서 얼마나 중요한지도 다시금 체감했죠.

## OAuth 2.1 지원과 JWT 검증 강화, 보안이 이렇게 달라졌다고?

Spring Framework 6.1에서는 보안 쪽에서도 꽤 큰 변화가 있었습니다. OAuth 2.1 프로토콜 지원이 추가되면서, 기존 OAuth 2.0 대비 더 안전한 인증 흐름을 구현할 수 있게 됐어요. 특히 JWT 토큰 검증 과정에서 발견된 취약점을 보완해, 토큰 변조나 재사용 공격에 대한 방어가 강화됐습니다.

우리 서비스는 외부 API와 연동하면서 OAuth를 쓰는데, 이번 업데이트 덕분에 토큰 검증 로직을 간단히 업그레이드할 수 있었어요. 예전에는 직접 토큰 서명 검증 코드에 신경 써야 했는데, 이제는 Spring Security가 기본적으로 최신 권고사항을 반영해 안전하게 처리해줍니다.

```java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
        .oauth2ResourceServer(oauth2 -> oauth2
            .jwt(jwt -> jwt
                .jwtAuthenticationConverter(new CustomJwtAuthenticationConverter())
            )
        );
    return http.build();
}
```

이 코드에서 중요한 건 `jwtAuthenticationConverter`를 커스터마이징해서, 토큰 내 권한 클레임을 우리 서비스에 맞게 해석하는 부분입니다. Spring Framework 6.1에서는 기본 JWT 검증 로직이 한층 견고해져서, 우리가 신경 써야 할 부분이 줄어들었어요.

## JVM 힙, 쓰레드 풀, DB 커넥션 풀… 이거 진짜 튜닝 안 하면 답 없다

Spring Boot 성능 튜닝에 관한 이야기는 늘 나오지만, 실제로 어디서부터 손대야 할지 막막한 경우가 많죠. 제가 최근 참고한 Baeldung 글에 따르면, JVM 힙 메모리 설정부터 시작해서 쓰레드 풀 크기, 그리고 데이터베이스 커넥션 풀 최적화가 핵심이라고 합니다.

우리 팀은 힙 메모리를 2GB에서 4GB로 늘리고, GC 방식을 G1GC로 변경한 뒤, 쓰레드 풀 크기를 CPU 코어 수의 2배로 맞췄습니다. 데이터베이스 커넥션 풀은 HikariCP 기본값에서 최대 50까지 올렸는데, 트래픽이 몰리는 시간대에 응답 지연이 눈에 띄게 줄었어요.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 50

# JVM 옵션 예시
-Xms4g -Xmx4g -XX:+UseG1GC
```

이 튜닝 과정에서 중요한 건, 무작정 수치를 키우기보다는 실제 부하 테스트를 통해 병목 구간을 찾아내고, 그에 맞게 조정하는 겁니다. Baeldung 글에서는 단계별로 어떤 지표를 봐야 하는지, JVM 힙 덤프 분석법까지 자세히 다루고 있으니 꼭 참고해보세요[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

## 대규모 서비스에서 안전하게 배포하려면? GitHub가 추천하는 점진적 롤아웃

대규모 백엔드 서비스를 운영하다 보면, 새 버전 배포가 항상 골칫거리입니다. 장애가 나면 바로 롤백해야 하는데, 이 과정에서 사용자 경험이 크게 흔들리죠. GitHub 엔지니어링 블로그에서는 이런 문제를 해결하기 위해 카나리아 배포와 블루-그린 배포 방식을 권장합니다.

우리도 이번에 이 방식을 도입했는데, 특히 자동화된 모니터링 시스템과 결합하니 장애 발생 시 빠른 롤백이 가능해졌어요. 예를 들어, 신규 버전의 에러율이 1%를 넘으면 자동으로 이전 버전으로 트래픽을 돌려보내는 식입니다.

```yaml
# 간단한 카나리아 배포 예시 (Kubernetes와 Istio 사용)
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: my-service
spec:
  hosts:
  - my-service.example.com
  http:
  - route:
    - destination:
        host: my-service
        subset: v1
      weight: 90
    - destination:
        host: my-service
        subset: v2
      weight: 10
```

이렇게 트래픽을 10%만 새 버전으로 보내면서 모니터링하고, 문제가 없으면 점차 비중을 늘리는 방식입니다. 물론 이 과정에서 모니터링 지표와 알림 체계를 잘 갖추는 게 필수입니다.

## 엣지 컴퓨팅과 API 게이트웨이로 네트워크 지연 줄이기, Cloudflare 사례

마지막으로, Cloudflare가 소개한 Spring 기반 백엔드 최적화 전략도 인상 깊었습니다. 분산 환경에서 엣지 컴퓨팅과 API 게이트웨이 통합을 통해 네트워크 지연을 줄이고, 공격 표면을 최소화했다는 사례인데요.

우리도 비슷한 구조를 고민 중인데, 엣지에서 인증과 간단한 요청 필터링을 처리하면 백엔드 부하가 크게 줄고, 응답 속도도 개선됩니다. 물론 엣지 컴퓨팅 도입은 복잡도가 올라가고, 디버깅이 어려워질 수 있으니 신중한 설계가 필요합니다.

## 마무리하며

이번 Spring 최신 버전 업데이트를 겪으면서 느낀 건, "기본 제공 기능을 잘 활용하는 것만으로도 프로덕션 안정성과 성능이 크게 개선된다"는 점입니다. 물론 튜닝과 보안 강화, 배포 전략 모두 한꺼번에 완벽하게 적용하기 쉽지 않지만, 차근차근 단계별로 개선해 나가면 분명 큰 도움이 됩니다.

특히 메트릭 수집과 모니터링을 강화해 실시간 상태를 파악하고, 최신 보안 프로토콜을 적용해 인증을 안전하게 만들고, JVM과 DB 커넥션 풀 튜닝으로 병목을 줄이고, 점진적 롤아웃으로 배포 위험을 낮추는 이 네 가지는 꼭 챙기시길 추천합니다.

이 글이 여러분의 다음 Spring 프로젝트에 작은 힌트가 되었으면 좋겠습니다.
