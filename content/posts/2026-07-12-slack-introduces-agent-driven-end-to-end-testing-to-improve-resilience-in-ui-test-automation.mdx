# UI 테스트가 갑자기 불안정해진다면, 에이전트 드리븐 테스트가 답일까?

"어제까지 잘 돌아가던 UI 테스트가 오늘은 왜 이렇게 자꾸 실패하지?" 이런 경험, 한 번쯤은 다들 해봤을 겁니다. 특히 슬랙(Slack) 같은 대규모 서비스에서 UI 테스트가 불안정해지는 건 치명적이죠. 슬랙은 이 문제를 해결하기 위해 에이전트 드리븐(Agent Driven) 엔드투엔드 테스트 방식을 도입했습니다. 이게 도대체 뭘까, 백엔드 시스템에선 어떻게 구현할 수 있을까? 저도 직접 살펴보고 실제 코드까지 짜보면서 느낀 점을 공유해볼게요.

---

## 에이전트 드리븐 테스트가 기존 UI 테스트와 어떻게 다른가?

우리가 흔히 하는 UI 테스트는 말 그대로 브라우저나 앱 UI를 직접 조작해서 시나리오를 검증합니다. 그런데 이 과정에서 네트워크 지연, 비동기 처리, 타이밍 문제 등으로 테스트가 불안정해지는 경우가 많아요. 슬랙이 도입한 에이전트 드리븐 테스트는 백엔드에 "테스트 에이전트"라는 중간 역할을 둡니다. 이 에이전트가 백엔드 API 호출과 UI 상호작용을 조율하면서 테스트를 실행해요.

즉, UI 테스트가 직접 프론트엔드 요소를 조작하는 대신, 에이전트가 백엔드 상태를 조작하고 UI 이벤트를 트리거해서 테스트를 진행합니다. 이 방식은 테스트가 외부 환경 변화에 덜 민감해져서 플레이키 테스트(불안정한 테스트)를 크게 줄여줍니다.[GitHub Engineering Blog](https://github.blog/category/engineering/)

저도 직접 써보니, 단순히 UI를 클릭하고 기다리는 것보다 에이전트가 API 상태를 관리해주는 게 훨씬 안정적이더라고요. 특히 백엔드에서 상태가 꼬일 때 UI 테스트가 엉키는 경우가 많은데, 이걸 에이전트가 미리 정리해줘서 실패 확률이 줄어듭니다.

## 재시도 패턴과 서킷 브레이커가 테스트 내구성에 미치는 영향

에이전트 드리븐 테스트를 구현할 때 꼭 함께 써야 하는 패턴이 두 가지 있어요. 바로 재시도(Retry) 패턴과 서킷 브레이커(Circuit Breaker) 패턴입니다.

### 재시도 패턴

네트워크 요청이 실패하거나 일시적인 장애가 발생했을 때, 무작정 실패 처리하지 않고 일정 횟수 재시도하는 전략입니다. 예를 들어, API 호출이 실패하면 3번까지 500ms 간격으로 재시도하도록 설정할 수 있죠. 이렇게 하면 순간적인 장애로 테스트가 깨지는 걸 막아줍니다.

```java
// 재시도 패턴 예시 (Java, Spring Retry)
@Retryable(
  value = {HttpServerErrorException.class, ResourceAccessException.class},
  maxAttempts = 3,
  backoff = @Backoff(delay = 500)
)
public ResponseEntity<String> callBackendApi() {
    return restTemplate.getForEntity("https://api.example.com/data", String.class);
}
```

실제로 마이크로소프트 아키텍처 가이드에 따르면, 재시도 패턴은 테스트뿐 아니라 실제 서비스 내 장애 복구에도 필수적이라고 합니다.[Microsoft - Retry pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/retry)

### 서킷 브레이커 패턴

반면 장애가 장기화될 때는 재시도만 하면 오히려 더 큰 부하가 될 수 있죠. 이럴 때 서킷 브레이커가 작동합니다. 실패율이 일정 기준 이상이면 즉시 실패를 반환하고, 일정 시간 후에 다시 시도하는 방식이에요. 테스트 파이프라인이 불필요하게 지연되지 않도록 해줍니다.

```java
// Resilience4j 서킷 브레이커 설정 예
CircuitBreaker circuitBreaker = CircuitBreaker.of("backendService",
    CircuitBreakerConfig.custom()
        .failureRateThreshold(50)
        .waitDurationInOpenState(Duration.ofSeconds(30))
        .slidingWindowSize(10)
        .build());

Supplier<String> decoratedSupplier = CircuitBreaker.decorateSupplier(circuitBreaker, () -> callBackendApi().getBody());

Try<String> result = Try.ofSupplier(decoratedSupplier)
    .recover(throwable -> "fallback response");
```

서킷 브레이커 덕분에 장애 상황에서도 테스트 에이전트가 빠르게 실패를 감지하고, 전체 테스트 파이프라인이 멈추지 않고 회복할 수 있었습니다.[Microsoft - Circuit Breaker pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker)

## 클라우드 API와 자동화 도구를 활용해 에이전트 관리하기

에이전트 드리븐 테스트는 에이전트가 백엔드와 프론트엔드 사이에서 복잡한 상호작용을 조율하기 때문에, 에이전트의 상태 관리와 환경 설정이 중요합니다. 슬랙도 클라우드 플랫폼에서 제공하는 API와 자동화 도구를 적극 활용했더군요.[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/)

예를 들어, AWS Lambda나 Google Cloud Functions 같은 서버리스 환경에 에이전트 로직을 배포해 필요할 때마다 빠르게 스케일링하고, 테스트 환경을 격리할 수 있죠. 또 Terraform이나 Pulumi 같은 IaC(Infrastructure as Code) 도구로 테스트 인프라를 코드로 관리하면, 환경 설정 실수도 줄어듭니다.

저는 최근에 클라우드 API를 활용해 테스트 에이전트를 관리하는 프로젝트를 맡았는데, 덕분에 테스트 실패 원인 파악과 재현이 훨씬 수월해졌어요. 특히 테스트 에이전트가 로그와 상태를 자체적으로 수집해서, 문제 발생 시 빠르게 대응할 수 있었습니다.

## 직접 써본 에이전트 드리븐 테스트 간단 예제

아래는 Spring Boot 기반 백엔드에서 간단히 에이전트 드리븐 테스트를 구현한 예시입니다. 핵심은 테스트 에이전트가 API 호출과 UI 시뮬레이션을 담당하고, 재시도와 서킷 브레이커를 적용한 부분이에요.

```java
@RestController
public class TestAgentController {

    private final RestTemplate restTemplate = new RestTemplate();
    private final CircuitBreaker circuitBreaker;

    public TestAgentController() {
        circuitBreaker = CircuitBreaker.of("backendService",
            CircuitBreakerConfig.custom()
                .failureRateThreshold(50)
                .waitDurationInOpenState(Duration.ofSeconds(20))
                .slidingWindowSize(5)
                .build());
    }

    @Retryable(value = {HttpServerErrorException.class}, maxAttempts = 3, backoff = @Backoff(delay = 300))
    public String callApiWithRetry() {
        return restTemplate.getForObject("http://backend-service/api/state", String.class);
    }

    @GetMapping("/agent/run-test")
    public ResponseEntity<String> runTest() {
        Supplier<String> decoratedSupplier = CircuitBreaker.decorateSupplier(circuitBreaker, this::callApiWithRetry);

        Try<String> result = Try.ofSupplier(decoratedSupplier)
            .recover(throwable -> "API 호출 실패로 테스트 중단");

        if (result.isSuccess()) {
            // 여기서 UI 이벤트 시뮬레이션 호출 가능
            return ResponseEntity.ok("테스트 성공: " + result.get());
        } else {
            return ResponseEntity.status(HttpStatus.SERVICE_UNAVAILABLE).body(result.getCause().getMessage());
        }
    }
}
```

이런 식으로, 테스트 에이전트가 백엔드 API 상태를 직접 확인하고, 실패 시 재시도와 서킷 브레이커를 통해 안정성을 확보합니다. UI 이벤트 시뮬레이션은 별도의 서비스나 프론트엔드 테스트 도구와 연동하면 됩니다.

### 마무리하며

에이전트 드리븐 엔드투엔드 테스트는 단순히 UI를 조작하는 기존 테스트 방식보다 훨씬 더 견고한 테스트 환경을 만들어줍니다. 물론 구현이 복잡해지고, 에이전트 상태 관리에 신경 써야 하는 단점도 있죠. 하지만 슬랙 사례처럼 대규모 서비스에서 플레이키 테스트 문제를 해결하려면 이런 접근이 필요합니다.

저는 이번에 직접 구현해보면서, 재시도와 서킷 브레이커 패턴을 꼭 결합해야 한다는 점이 가장 와닿았어요. 그리고 클라우드 API를 활용해 에이전트 환경을 자동화하는 것도 생각보다 훨씬 중요한 부분이었습니다.

만약 여러분 팀에서 UI 테스트가 자주 깨진다면, 에이전트 드리븐 테스트를 한 번 시도해보세요. 초기 투자 비용은 좀 들지만, 장기적으로는 테스트 안정성은 물론 개발 생산성도 크게 올라갈 겁니다.
