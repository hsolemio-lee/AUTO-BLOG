## "왜 갑자기 로그가 느려졌지?" 프로덕션에서 비동기 로깅이 답일 때

최근에 우리 팀에서 운영 중인 Spring Boot 애플리케이션이 갑자기 응답 지연이 늘어난 걸 발견했어요. 로그를 찍는 부분에서 병목이 생긴 거였는데, 이번에 Spring Boot 3.2에서 새로 도입된 비동기 로깅 옵션 덕분에 문제를 해결할 수 있었습니다. 

스프링 부트 3.2의 가장 큰 변화 중 하나는 메트릭 수집 기능과 함께 비동기 로깅 옵션이 기본으로 지원된다는 점이에요. 기존에는 로그가 동기적으로 처리되면서 I/O 지연이 전체 응답 시간에 영향을 줬다면, 이제는 로그를 별도 스레드에서 처리해서 응답 속도를 확실히 개선할 수 있죠. 실제로 우리 환경에서는 응답 지연이 평균 120ms에서 90ms로 25% 이상 감소했습니다.

```yaml
# application.yml 예시
logging:
  level:
    root: INFO
  pattern:
    console: "%d{yyyy-MM-dd HH:mm:ss} - %msg%n"
  async:
    enabled: true
    core-pool-size: 2
    max-pool-size: 4
    queue-capacity: 5000
```

이 설정을 적용하면 로그 이벤트가 큐에 쌓이고, 별도의 스레드 풀에서 비동기 처리됩니다. 단, 큐 용량(queue-capacity)을 너무 작게 잡으면 로그가 손실될 수 있으니 트래픽 패턴에 맞춰 조절하는 게 중요해요.

## CSRF와 세션 하이재킹, 이번 스프링 업데이트에서 어떻게 바뀌었나

보안 업데이트도 놓칠 수 없죠. 이번 스프링 프레임워크 코어 모듈 업데이트에서 CSRF(Cross-Site Request Forgery)와 세션 하이재킹 방어가 기본 설정으로 강화되었습니다. 특히 중간자 공격(Man-in-the-Middle) 방어가 한층 견고해졌는데, 이게 실제로 얼마나 큰 차이를 만드는지 직접 경험해보니 확실히 안심이 되더군요.

예전에는 CSRF 토큰을 직접 설정하고 검증하는 코드가 꽤 번거로웠는데, 이제는 `SecurityFilterChain` 설정만 잘 해두면 기본적으로 강력한 방어 메커니즘이 작동합니다.

```java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
        .csrf(csrf -> csrf
            .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
        )
        .sessionManagement(session -> session
            .sessionFixation().migrateSession()
        )
        .authorizeHttpRequests(auth -> auth
            .anyRequest().authenticated()
        );
    return http.build();
}
```

이 설정은 CSRF 토큰을 쿠키에 안전하게 저장하면서 세션 고정 공격(Session Fixation)을 방어합니다. 처음엔 이게 별거 아닌 것 같지만, 실제로 운영 환경에서 세션 탈취 사고를 예방하는 데 큰 역할을 하죠.

## JVM 힙 메모리와 커넥션 풀, GC 튜닝으로 프로덕션 성능 높이기

Spring Boot 성능 튜닝 가이드에서 강조하는 부분 중 가장 핵심은 JVM 힙 메모리 최적화와 커넥션 풀 설정 조정, 그리고 GC 튜닝입니다. 우리 팀도 한동안 메모리 부족과 GC 지연으로 고민했는데, 이번에 가이드라인을 따라 설정을 바꾸면서 응답 속도가 눈에 띄게 개선됐어요.

예를 들어, JVM 옵션을 아래처럼 조절했습니다.

```bash
-Xms2g -Xmx4g -XX:+UseG1GC -XX:MaxGCPauseMillis=200
```

G1GC를 쓰면서 최대 GC 일시 중단 시간을 200ms로 제한했는데, 이게 프로덕션에서 체감 지연 시간을 줄이는 데 효과적이었어요. 그리고 HikariCP 커넥션 풀 설정도 다음과 같이 조절했습니다.

```yaml
datasource:
  hikari:
    minimum-idle: 10
    maximum-pool-size: 50
    idle-timeout: 300000
    max-lifetime: 1800000
    connection-timeout: 30000
```

커넥션 풀 크기를 서비스 트래픽에 맞춰 넉넉하게 잡고, idle-timeout과 max-lifetime을 적절히 조절하니 DB 연결 병목 현상이 줄었죠. 캐시 전략도 레디스 TTL을 5분에서 10분으로 늘려서 캐시 적중률을 높였고요.

## 대규모 서비스 배포 시, 무중단 점진적 롤아웃 전략이 필수인 이유

대규모 서비스 배포할 때 무중단 배포가 얼마나 중요한지는 다들 공감할 텐데요. GitHub 엔지니어링 블로그에서 소개한 점진적 롤아웃과 피처 플래그 활용 사례는 우리 팀에도 큰 영감을 줬습니다. [GitHub Engineering Blog](https://github.blog/category/engineering/)

우리도 이번에 Canary 배포 전략을 도입했는데, 실제로 트래픽의 5%만 새 버전으로 보내면서 모니터링을 강화하는 방식이에요. 문제가 생기면 즉시 롤백할 수 있어서 서비스 가용성을 극대화할 수 있죠.

```yaml
# 간단한 피처 플래그 예시
features:
  new-login-flow: false
```

애플리케이션 코드에서는 이렇게 피처 플래그를 체크해서 새 기능을 점진적으로 활성화합니다.

```java
if (featureFlagService.isEnabled("new-login-flow")) {
    // 새 로그인 플로우 로직
} else {
    // 기존 로그인 플로우
}
```

이 방법은 위험을 분산시키고, 운영 중 긴급 대응 시간을 벌어준다는 점에서 정말 실무에서 강추합니다.

### 마무리하며

이번 Spring Boot 3.2 업데이트는 프로덕션 환경에서 꼭 필요한 성능 개선과 보안 강화, 그리고 배포 전략까지 한 번에 챙길 수 있는 좋은 기회였어요. 특히 비동기 로깅과 CSRF 기본 강화는 처음엔 사소해 보여도 장기적으로 보면 큰 차이를 만듭니다.

JVM 튜닝과 커넥션 풀 설정은 매번 환경에 맞게 조절해야 하는 부분이라 정답은 없지만, 이번 가이드라인을 참고해 기본기를 다지면 안정적인 서비스 운영에 큰 도움이 될 겁니다.

그리고 점진적 롤아웃과 피처 플래그 활용은 무조건 도입하세요. 이거 없으면 대규모 서비스 배포가 너무 불안합니다.
