### "왜 우리 시스템 아키텍처 결정은 늘 흐지부지 끝나지?"

한 번쯤은 이런 상황 겪어봤을 겁니다. 팀에서 새로운 기술이나 아키텍처 패턴을 도입할 때, 누군가는 "이게 맞는 방향인가?" 고민하지만, 정작 그 결정이 왜 내려졌는지, 어떤 대안이 있었는지, 미래에 어떻게 바꿀 수 있는지 기록이 없어서 나중에 혼란이 오죠. 저도 중간 개발자로 일하면서 이 문제를 여러 번 겪었는데, ADR(Architecture Decision Record)을 제대로 활용하면서 상황이 훨씬 나아졌습니다.

---

## ADR이 그냥 문서가 아닌 이유: 결정 뒤에 숨은 이야기까지 담기

아키텍처 결정 기록은 단순히 "이걸 썼다" 정도의 기록이 아닙니다. [Martin Fowler](https://martinfowler.com/articles/microservices.html)도 강조하듯, ADR은 시스템 아키텍처에서 중요한 선택과 그에 따른 트레이드오프, 그리고 미래 마이그레이션 경로를 명확히 문서화하는 작업입니다. 이게 왜 중요하냐면, 나중에 누군가가 "왜 이걸 선택했지?"를 다시 묻지 않아도 되고, 결정 배경을 이해하면 유지보수와 확장도 훨씬 수월해지거든요.

실제로 제가 참여했던 프로젝트에서는, 초기에는 "왜 이 메시지 큐를 썼는지"에 대한 기록이 없어서 새로 합류한 팀원이 혼란을 겪었는데, ADR을 도입한 뒤로는 신규 인력이 빠르게 맥락을 잡고 작업에 들어갈 수 있었습니다.

---

## 클라우드 시스템 설계에서 ADR이 특히 빛나는 이유

복잡한 클라우드 환경에서 아키텍처 결정은 단순한 선택이 아닙니다. Microsoft의 클라우드 디자인 패턴 문서에서도 알 수 있듯이, 각 결정에는 명확한 트레이드오프가 있고, 대안과 마이그레이션 경로까지 고려해야 합니다. 예를 들어, 서버리스 아키텍처를 선택할 때 비용, 성능, 운영 복잡성 등 다양한 요소를 저울질해야 하죠.

이럴 때 ADR을 쓰면, "왜 서버리스인가?" "대안으로 컨테이너 기반 오케스트레이션은 왜 배제했나?" "나중에 필요하면 어떻게 전환할 수 있나?" 이런 질문에 명확한 답을 남길 수 있습니다. 실제로 우리 팀은 Azure Functions 도입 결정 때 ADR을 써서, 비용 절감과 빠른 개발 속도를 얻은 대신, 디버깅과 로컬 테스트가 어려운 단점도 명시했고, 필요 시 Kubernetes로 이전하는 계획도 함께 적었습니다.

## 중간 개발자가 ADR을 작성할 때 꼭 챙겨야 할 포인트

중간 개발자 입장에서 ADR을 쓸 때, 단순히 "OO 기술 도입"만 기록하면 아쉽습니다. [Martin Fowler](https://martinfowler.com/articles/microservices.html)도 말했듯, 다음 내용을 꼭 포함하세요:

- **결정 배경**: 왜 이 문제를 해결해야 했는지, 어떤 요구사항이 있었는지
- **대안 분석**: 고려했던 다른 옵션은 무엇이고, 각각의 장단점은?
- **최종 선택 이유**: 왜 이 옵션이 가장 적합했는지
- **미래 변경 가능성**: 나중에 바꿔야 할 경우 어떤 경로와 영향이 예상되는지

예를 들어, 다음은 간단한 ADR 마크다운 템플릿입니다:

```markdown
# ADR 001: 메시지 큐 선택

## 배경
대규모 비동기 이벤트 처리를 위해 메시지 큐 도입이 필요함.

## 고려한 대안
- RabbitMQ: 성숙하고 기능 풍부하지만 관리가 복잡함.
- AWS SQS: 관리형 서비스로 운영 부담 적음, 지연시간이 다소 있음.

## 결정
AWS SQS를 선택함. 운영 부담 감소와 확장성 우선 고려.

## 트레이드오프
지연시간이 RabbitMQ 대비 높음. 실시간성이 중요한 경우 재검토 필요.

## 마이그레이션 경로
필요 시 RabbitMQ로 이전 가능하나, 운영 비용 증가 예상.
```

이런 식으로 적으면, 나중에 누가 봐도 "왜 이걸 썼는지" 한눈에 파악할 수 있습니다.

## CI/CD 환경에서 ADR을 어떻게 관리할까?

지속적 통합 환경에서는 코드 변경과 아키텍처 결정이 빠르게 바뀌는 경우가 많습니다. [Martin Fowler](https://martinfowler.com/articles/continuousIntegration.html)도 지적한 것처럼, ADR을 통해 변경 이력을 체계적으로 관리하고, 변경에 따른 영향과 마이그레이션 계획을 명확히 해야 합니다.

우리 팀은 ADR 문서를 Git 저장소 내에 `docs/adr/` 폴더에 두고, PR 템플릿에 "ADR 업데이트가 필요한가요?" 질문을 넣었습니다. 예를 들어, 메시지 큐를 바꾸거나 API 게이트웨이 전략을 변경할 때 반드시 ADR을 새로 작성하거나 수정하도록 했죠.

이렇게 하면, 코드 리뷰 과정에서 아키텍처 결정도 함께 검토할 수 있어, "왜 갑자기 이걸 바꾸냐"는 불필요한 논쟁을 줄일 수 있었습니다.

---

## 실제로 ADR을 도입하며 겪은 한 가지 딜레마

처음엔 ADR 작성이 귀찮고, "이 정도는 구두로 해결해도 되지" 싶었는데, 프로젝트가 커질수록 그 생각이 바뀌었습니다. 다만, 너무 자세하게 쓰면 문서 관리가 부담되고, 너무 간단하면 의미가 없으니 적절한 균형이 중요합니다.

예를 들어, 우리 팀은 500자 내외로 핵심만 간결하게 적되, 필요하면 링크나 참고 자료를 첨부하는 방식을 택했습니다. 그리고 ADR 작성자는 해당 결정에 가장 가까운 사람이 맡도록 했죠. 이렇게 하니 문서 작성 부담이 줄고, 실제로 읽히는 문서가 되었습니다.

---

## 마무리하며: ADR은 "기록"이 아니라 "소통"이다

중간 개발자 입장에서 ADR은 단순한 문서 작성이 아니라, 팀 내 아키텍처 이해를 돕고, 미래 변경에 대비하는 소통 도구입니다. 처음엔 귀찮아도, 꾸준히 쓰고 관리하면 복잡한 시스템도 더 견고하고 유지보수 쉬워집니다.

실제로 ADR을 생활화한 팀은 신규 개발자 온보딩 시간이 30% 이상 단축됐고, 아키텍처 변경 시 발생하는 버그도 눈에 띄게 줄었다고 합니다. 여러분도 오늘부터 작게라도 ADR을 시작해보세요. 나중에 분명히 고마워할 겁니다.

---

### 참고 코드 예시: GitHub Actions로 ADR 변경 감지하기

지속적 통합 환경에서 ADR 변경을 감지해 자동 알림을 보내는 간단한 GitHub Actions 워크플로우 예시입니다.

```yaml
name: ADR Change Check

on:
  pull_request:
    paths:
      - 'docs/adr/**'

jobs:
  check-adr:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: ADR 변경 감지
        run: |
          echo "ADR 문서가 변경되었습니다. 리뷰어는 아키텍처 결정 변경 사항을 꼭 확인하세요."
```

이런 작은 자동화도 ADR 관리에 큰 도움이 됩니다.

- **지속적 통합(Continuous Integration) 환경에서는 아키텍처 결정이 코드 변경과 맞물려 빠르게 변할 수 있으므로, ADR을 통해 변경 이력을 체계적으로 관리하고, 변경에 따른 영향과 마이그레이션 계획을 명확히 해야 한다.** ([Martin Fowler - Continuous Integration](https://martinfowler.com/articles/continuousIntegration.html))
  실제 적용에서는 트래픽 패턴, 장애 허용 범위, 팀의 온콜 역량을 같이 봐야 합니다. 초기에는 전체 전환보다 일부 기능에 먼저 도입하고, 지표가 안정화되는지 확인한 다음 확장하는 방식이 안전합니다. 특히 롤백 기준을 사전에 숫자로 정의해 두면 운영 중 의사결정 속도가 크게 좋아집니다.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
