## 갑자기 멈춘 AWS North Virginia, 그날 우리 서비스는 어떻게 버텼나

지난 AWS North Virginia 리전 장애 소식 들었나요? 꽤 큰 규모였고, 복구에 수 시간이 걸렸다는 점에서 우리 같은 백엔드 개발자들에게 다시 한번 클라우드 아키텍처의 복원력에 대해 고민하게 만들었죠. 실제로 우리 팀도 이 장애를 겪으면서 ‘다중 리전 배포가 얼마나 중요한지’, 그리고 ‘복구 자동화 없이는 몇 시간씩 다운타임을 감수해야 한다’는 걸 뼈저리게 느꼈습니다.

이 글에서는 단순히 장애가 났다는 뉴스만 전달하는 게 아니라, 왜 이런 장애가 발생했는지, 그리고 우리 같은 개발자가 어떻게 준비하고 대응해야 하는지 현실적인 관점에서 이야기를 해보려고 해요.

## AWS Well-Architected Framework가 말하는 다중 리전 배포의 진짜 이유

AWS 공식 문서인 [AWS Well-Architected Framework](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html)를 보면, 장애 복원력 강화를 위해 다중 리전 배포와 장애 격리 설계를 꼭 하라고 권장합니다. 여기서 중요한 포인트는 단순히 여러 리전에 똑같은 서비스를 띄우는 게 아니라, 장애가 난 리전과 다른 리전이 서로 영향을 주지 않도록 격리하는 아키텍처를 설계하는 겁니다.

이걸 안 하면 장애가 발생했을 때 복구 시간이 길어지고, 서비스 전체가 멈출 위험이 커지죠. 반대로 다중 리전 아키텍처를 잘 구축하면 장애 발생 시 빠르게 다른 리전으로 트래픽을 전환해 서비스 연속성을 확보할 수 있습니다.

근데 여기서 한 가지 현실적인 고민이 생깁니다. 다중 리전 배포는 비용이 꽤 많이 든다는 점이에요. AWS 리소스를 두 배로 쓰는 거니까 당연하죠. 그래서 우리 팀도 처음에는 비용 때문에 망설였는데, 이번 장애를 겪고 나니 '비용 대비 복원력'의 가치를 다시 보게 됐습니다.

## 장애 대응 비용과 복원력, 이 균형을 어떻게 맞출까?

AWS 아키텍처 블로그에서는 최근 North Virginia 리전 장애 사례를 통해 비용과 복원력 간 트레이드오프를 명확히 설명합니다([AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/)). 다중 리전 아키텍처와 자동화된 복구 전략은 비용이 증가하는 게 사실이지만, 장애 발생 시 서비스 다운타임을 최소화하는 데 필수적이라는 거죠.

우리 팀도 이 부분에서 고민이 많았습니다. 예를 들어, 다중 리전에서 데이터 동기화를 어떻게 할지, 혹은 장애 발생 시 자동으로 롤백하거나 트래픽을 전환하는 자동화 스크립트를 어떻게 만들지 등 기술적 난제들이 있었거든요.

하지만 비용 때문에 복원력을 희생하면, 장애가 발생했을 때 서비스 중단으로 인한 손실이 훨씬 커질 수 있습니다. 그래서 저는 비용과 복원력 사이에서 ‘적당한 선’을 찾는 게 가장 중요하다고 봅니다. 예를 들어, 모든 서비스에 다중 리전을 적용하는 대신, 핵심 서비스에만 집중하거나, 장애 시 수동 복구가 가능한 서비스는 비용 절감을 위해 단일 리전으로 운영하는 식이죠.

## GitHub와 Cloudflare가 보여준 복구 자동화의 힘

대규모 클라우드 장애에서 빠른 복구가 왜 중요한지, GitHub 엔지니어링 블로그에서 좋은 사례를 볼 수 있습니다([GitHub Engineering Blog](https://github.blog/category/engineering/)). 그들은 사전에 준비된 복구 플랜과 인프라 자동화 덕분에 장애 복구에 걸리는 시간을 크게 줄였다고 해요. 물론 복구에 몇 시간이 걸릴 수밖에 없지만, 자동화가 없었다면 훨씬 더 길어졌을 거라고 하네요.

Cloudflare 역시 다중 데이터센터와 트래픽 분산 전략으로 장애 복원력을 강화하는 사례를 공유합니다([Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/)). 이들은 복구까지 몇 시간이 걸렸지만, 장애 영향 범위를 최소화하고 빠른 트래픽 전환으로 서비스 연속성을 확보했습니다.

우리 팀에서도 이런 자동화 전략을 도입하기 시작했는데, 초기에는 복잡한 스크립트와 설정 때문에 시행착오가 많았어요. 하지만 한 번 제대로 세팅해두면 장애 상황에서도 긴장 덜 하고 대응할 수 있다는 점이 가장 큰 장점입니다.

## 실제로 다중 리전 장애 복구 자동화 스크립트 예시

아래는 AWS CLI를 이용해 장애 발생 시 자동으로 리전 간 트래픽을 전환하는 간단한 스크립트 예시입니다. 실제로는 더 복잡한 로직과 상태 체크가 필요하지만, 기본 아이디어는 이렇습니다.

```bash
#!/bin/bash

PRIMARY_REGION="us-east-1"
SECONDARY_REGION="us-west-2"

# 장애 감지 (예: 특정 서비스 헬스체크 실패)
SERVICE_HEALTH=$(aws --region $PRIMARY_REGION elb describe-instance-health --load-balancer-name my-loadbalancer | grep "OutOfService")

if [ -n "$SERVICE_HEALTH" ]; then
  echo "Primary region 장애 감지. Secondary region으로 트래픽 전환 시작..."
  # Route53에서 가중치 변경 예시
  aws route53 change-resource-record-sets --hosted-zone-id Z3P5QSUBK4POTI --change-batch '{
    "Changes": [{
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "myapp.example.com",
        "Type": "A",
        "SetIdentifier": "Secondary",
        "Weight": 100,
        "TTL": 60,
        "ResourceRecords": [{"Value": "52.23.45.67"}]
      }
    }]
  }'
  echo "트래픽 전환 완료"
else
  echo "Primary region 정상"
fi
```

이 스크립트는 간단한 헬스체크 결과를 바탕으로 AWS Route53의 가중치 기반 라우팅을 조정해 트래픽을 보조 리전으로 전환합니다. 물론 실제 운영 환경에서는 더 정교한 모니터링과 복구 플랜, 그리고 롤백 전략이 필요하죠.

## 마틴 파울러가 강조한 비용과 복원력 균형 잡기

마틴 파울러의 소프트웨어 아키텍처 가이드에서도 장애 대응 아키텍처 설계 시 비용 효율성과 복원력 간 균형을 맞추는 게 중요하다고 합니다([Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/)). 장애 복구에 장시간이 걸릴 수 있음을 감안해 설계해야 한다는 점, 그리고 무작정 복원력을 높이려다 비용 폭탄 맞지 말라는 조언이 현실적이죠.

우리 팀도 이 조언을 마음에 새기면서, 장애 대응 준비 수준을 단계별로 나누어 비용과 효과를 비교해봤습니다. 예를 들어, 1단계는 단일 리전에 자동화된 헬스체크만 적용, 2단계는 핵심 서비스에 다중 리전 배포, 3단계는 전체 서비스 다중 리전 및 완전 자동화 복구 체계 구축 같은 식으로요.

## 장애 복구 준비, 이제는 선택이 아니라 필수

이번 AWS North Virginia 리전 장애는 우리에게 클라우드 복원력의 중요성을 다시 한 번 일깨워줬습니다. 단순히 장애가 났다는 뉴스가 아니라, 실제로 복구까지 몇 시간이 걸렸고, 이 과정에서 다중 리전 배포와 자동화된 복구 전략이 얼마나 중요한지 체감했죠.

복원력을 높이려면 비용이 늘어나고 운영 복잡도도 올라가지만, 장애 시 서비스 중단으로 인한 손실을 생각하면 투자할 가치가 분명히 있습니다. 그리고 자동화 스크립트 하나만 잘 만들어놔도 장애 대응 속도가 확실히 달라집니다.

우리 팀 경험을 정리하면 다음과 같습니다:

- 핵심 서비스는 반드시 다중 리전 배포를 적용하자.
- 장애 감지 및 복구 자동화는 초기에 어렵지만, 장기적으로는 필수 투자다.
- 비용과 복원력 간 균형을 단계별로 점검하며 전략을 세우자.
- 장애 발생 시 수동 복구에 의존하면 복구 시간이 크게 늘어난다.

이 글을 읽는 동료 개발자 여러분도 이번 장애 사례를 참고해 자신의 서비스 복원력 점검과 개선에 꼭 시간을 투자하시길 바랍니다.
