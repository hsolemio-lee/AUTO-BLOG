## "왜 HTTP 대신 웹소켓인가?"

얼마 전 우리 팀에서 AI 에이전트를 활용한 공급망 관리 시스템을 구축하면서, API 호출 지연 때문에 실시간 반응이 어려웠던 적이 있었어요. 기존에는 OpenAI API를 HTTP 요청-응답 방식으로 호출했는데, 매번 연결을 새로 맺고 끊는 구조라서 200~300ms 정도의 지연이 쌓이더라고요. AI 에이전트가 여러 단계로 의사결정을 해야 하는데, 이 지연이 누적되면 사용자 경험이 크게 떨어졌죠.

그때 OpenAI에서 웹소켓(WebSocket) 기반 실행 모드를 발표한 걸 보고 바로 적용을 고민했습니다. 웹소켓은 한 번 연결을 맺으면 지속적으로 양방향 통신이 가능해서, 에이전트가 상태를 실시간으로 주고받으며 빠르게 반응할 수 있다는 점이 매력적이었거든요. 실제로 OpenAI 공식 문서에서도 웹소켓 모드가 기존 HTTP 대비 지연 시간을 크게 줄이고, 에이전트 워크플로우의 신뢰성과 실시간성을 높인다고 명시하고 있습니다[OpenAI API Documentation](https://platform.openai.com/docs/overview).


## Spring 백엔드에 웹소켓 클라이언트 구현하기

Spring 환경에서 OpenAI 웹소켓 API를 직접 호출하려면, 먼저 웹소켓 클라이언트를 만들어야 합니다. Spring 자체에는 클라이언트 전용 웹소켓 API가 없으니, `java-websocket` 라이브러리 같은 경량 클라이언트를 쓰는 게 편해요. 아래는 간단한 예제 코드입니다:

```java
import org.java_websocket.client.WebSocketClient;
import org.java_websocket.handshake.ServerHandshake;

import java.net.URI;

public class OpenAIWebSocketClient extends WebSocketClient {

    public OpenAIWebSocketClient(URI serverUri) {
        super(serverUri);
    }

    @Override
    public void onOpen(ServerHandshake handshakedata) {
        System.out.println("웹소켓 연결 성공");
        // OpenAI에 초기 메시지 보내기
        send("{\"type\": \"start\", \"payload\": {...}} ");
    }

    @Override
    public void onMessage(String message) {
        System.out.println("수신 메시지: " + message);
        // 여기서 AI 응답 처리 및 상태 업데이트
    }

    @Override
    public void onClose(int code, String reason, boolean remote) {
        System.out.println("웹소켓 연결 종료: " + reason);
    }

    @Override
    public void onError(Exception ex) {
        ex.printStackTrace();
    }
}

// 사용 예
URI uri = new URI("wss://api.openai.com/v1/agentic-websocket");
OpenAIWebSocketClient client = new OpenAIWebSocketClient(uri);
client.connect();
```

위 예제는 연결을 맺고 나서 OpenAI 웹소켓 API에 초기 메시지를 보내는 구조입니다. 실제로는 인증 토큰을 헤더에 넣거나, 메시지 포맷을 OpenAI 문서에 맞게 JSON으로 구성해야 하죠. 중요한 건 이 연결을 유지하면서 서버에서 오는 이벤트를 실시간으로 처리할 수 있다는 점입니다.


## 웹소켓 연결 유지와 이벤트 기반 메시지 처리의 장점

웹소켓 실행 모드는 단순히 지연 시간만 줄이는 게 아닙니다. 지속적인 연결 덕분에 AI 에이전트가 상태(state)를 실시간으로 관리할 수 있어요. 예를 들어, 여러 단계의 의사결정 플로우에서 각 단계 결과를 즉시 받아서 다음 행동을 결정하거나, 외부 이벤트에 따라 유연하게 대응할 수 있죠.

이벤트 기반 메시지 송수신이 가능하니, 백엔드 시스템도 AI 에이전트 상태 변화를 감지해서 적절한 후처리를 바로 할 수 있습니다. HTTP 폴링 방식과 비교하면 리소스 낭비도 크게 줄고, 확장성도 좋아집니다. 특히 Spring에서 `@Async`나 `CompletableFuture`를 활용해 비동기 이벤트 처리 로직을 구현하면, 웹소켓 메시지를 효율적으로 처리할 수 있어요.


## 클라우드 환경에서 웹소켓 실행 모드를 쓸 때 고려할 점

우리 팀은 AWS ECS와 같은 컨테이너 환경에서 웹소켓 클라이언트를 운영했는데, 몇 가지 주의할 점이 있었습니다. 첫째, 웹소켓 연결이 끊어질 경우 자동 재연결 로직을 반드시 넣어야 해요. 네트워크 불안정이나 서버 재시작 시 연결이 끊길 수 있으니까요.

둘째, 클라우드 로드밸런서(ALB, NLB) 설정에서 웹소켓 연결을 제대로 지원하는지 확인해야 합니다. 특히 ALB는 HTTP/2를 기본으로 쓰는데, 웹소켓은 HTTP/1.1 업그레이드를 필요로 하므로 설정이 맞지 않으면 연결이 실패할 수 있어요.

셋째, 리소스 사용량을 모니터링하며 필요에 따라 연결 수를 조절하는 게 중요합니다. 웹소켓 연결은 HTTP 요청보다 리소스를 더 오래 점유하므로, 너무 많은 동시 연결은 오히려 서버 부하를 높일 수 있습니다.

이런 점들을 잘 관리하면, 공급망 관리처럼 실시간 데이터 처리와 빠른 의사결정이 중요한 AI 에이전트 시스템에 웹소켓 기반 실행 모드가 큰 도움이 됩니다[OpenAI API Documentation](https://platform.openai.com/docs/overview).


## 실제 적용 후 체감 성능과 한계

우리 팀은 웹소켓 실행 모드를 적용한 뒤, 평균 응답 지연 시간이 300ms에서 80ms로 4배 가까이 줄었고, 에이전트가 실시간 이벤트에 즉각 반응하는 모습을 확인했습니다. 사용자 피드백도 훨씬 좋아졌고, 시스템 신뢰성도 눈에 띄게 향상됐죠.

하지만 단점도 있습니다. 첫째, 웹소켓 연결 관리는 HTTP보다 복잡해서 코드가 더 길어지고, 장애 대응 로직도 신경 써야 합니다. 둘째, 모든 환경에서 웹소켓을 지원하는 건 아니고, 일부 프록시나 방화벽에서 차단될 수 있어요.

또한, AI 모델의 응답 자체가 느릴 때는 웹소켓이라도 한계가 있으니, 모델 호출 최적화와 캐싱 전략도 함께 고민해야 합니다.

### 마무리하며

OpenAI의 웹소켓 기반 실행 모드는 AI 에이전트 워크플로우의 지연 시간을 줄이고, 실시간 상호작용을 가능하게 하는 강력한 도구입니다. Spring 백엔드에 적용할 때는 `java-websocket` 같은 클라이언트 라이브러리를 활용하고, 연결 유지, 비동기 이벤트 처리, 클라우드 환경 설정에 신경 쓰는 게 핵심이에요.

이걸 실제로 써보면, 단순히 빠른 응답뿐 아니라 에이전트 상태 관리와 확장성 측면에서 큰 장점을 느낄 수 있습니다. 물론 복잡도가 올라가니, 팀 상황에 맞게 점진적으로 도입하는 걸 추천합니다.
