## "폰트가 왜 백엔드랑 상관있어?" — 실제로 한 번 겪어보니

처음엔 폰트 페어링 레지스트리라길래 그냥 프론트엔드 디자이너들이나 관심 가질 만한 거라고 생각했어요. 그런데 우리 팀에서 shadcn/ui를 도입하면서 Fonttrio라는 오픈소스 폰트 페어링 레지스트리를 백엔드 API에 통합해보니, UI 일관성 유지뿐 아니라 개발 생산성에도 꽤 큰 도움이 되더군요. 특히 대규모 풀스택 프로젝트에서 프론트엔드와 백엔드가 분리되어 있을 때 말이죠.

오늘은 Fonttrio가 뭔지, 그리고 백엔드 입장에서 어떻게 활용할 수 있는지 실제 사례와 함께 풀어볼게요.

---

## Fonttrio가 뭔데, 왜 shadcn/ui랑 같이 쓰는 거야?

Fonttrio는 shadcn/ui라는 React 컴포넌트 라이브러리와 잘 맞게 설계된 오픈소스 폰트 페어링 레지스트리입니다. 쉽게 말해, UI에서 쓸 폰트 조합을 미리 정의해놓고, 팀 내에서 일관되게 쓸 수 있게 도와주는 저장소죠.

shadcn/ui가 Tailwind CSS와 함께 많이 쓰이는데, Tailwind는 폰트 스타일을 유연하게 바꿀 수 있지만, 폰트 선택이 너무 자유로우면 UI 일관성이 깨지기 쉽습니다. Fonttrio는 여기서 "이 폰트 조합이면 이 컴포넌트에 딱 맞는다"는 가이드라인 역할을 해주죠.

백엔드에서도 폰트 정보를 API로 제공하면, 프론트엔드가 폰트 설정을 하드코딩하지 않고도 최신 폰트 페어링을 바로 가져와 쓸 수 있어요. 이게 생각보다 유지보수성과 협업 생산성에 큰 영향을 줍니다.

---

## 백엔드에서 Fonttrio 레지스트리를 운영하는 게 왜 좋은가?

1. **UI 일관성 자동화**: 폰트 조합을 API로 관리하면, 프론트엔드 개발자가 개별 컴포넌트마다 폰트를 따로 지정할 필요가 없어집니다. 예를 들어, `GET /api/fonts`로 최신 페어링 리스트를 받아서 UI에 적용하면, 팀 전체가 같은 폰트 스타일을 쓰게 되죠.

2. **점진적 배포 전략과 잘 맞는다**: 신규 폰트 조합을 추가할 때, 작은 범위로 점진적 배포가 가능합니다. 예를 들어, 특정 페이지나 컴포넌트부터 새 폰트를 적용해보고 문제 없으면 점차 확대하는 식이죠. 이는 OpenAI API 문서에서 말하는 "작은 범위의 점진적 배포 전략"과도 맥락이 맞습니다[OpenAI API Documentation](https://platform.openai.com/docs/overview).

3. **장애 대응과 유지보수성 향상**: 폰트 관련 실패 유형(예: 폰트 로딩 실패, 폰트 호환성 문제)을 API 레벨에서 계측하면, 장애 대응 속도가 빨라집니다. Anthropic의 프롬프트 엔지니어링 가이드처럼 초기부터 실패 유형을 체계적으로 관리하는 게 유지보수에 큰 도움이 되거든요[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

## 실제로 우리 팀이 Fonttrio API를 백엔드에 붙여본 경험

우리 팀은 Next.js와 shadcn/ui를 쓰는 프론트엔드와 Node.js 기반 백엔드를 분리해서 운영 중입니다. Fonttrio 레지스트리를 직접 운영하는 대신, 오픈소스 레지스트리에서 폰트 페어링 데이터를 주기적으로 가져와서 자체 API로 제공합니다.

```js
// Node.js Express 예시
const express = require('express');
const axios = require('axios');
const app = express();

// Fonttrio 오픈소스 레지스트리 URL (가정)
const FONTTRIO_REGISTRY_URL = 'https://fonttrio.example.com/api/pairings';

// 서버 시작 시와 매 6시간마다 최신 폰트 페어링 캐싱
let cachedFontPairings = [];

async function updateFontPairings() {
  try {
    const res = await axios.get(FONTTRIO_REGISTRY_URL);
    cachedFontPairings = res.data;
    console.log('Fonttrio 페어링 데이터 업데이트 완료:', cachedFontPairings.length, '개');
  } catch (e) {
    console.error('Fonttrio API 호출 실패:', e.message);
  }
}

updateFontPairings();
setInterval(updateFontPairings, 6 * 60 * 60 * 1000); // 6시간마다 업데이트

app.get('/api/fonts', (req, res) => {
  res.json(cachedFontPairings);
});

app.listen(3000, () => {
  console.log('폰트 API 서버 3000번 포트에서 시작');
});
```

이렇게 하면 프론트엔드에서 `/api/fonts`만 호출하면 항상 최신 Fonttrio 페어링을 쓸 수 있죠. 실제로 폰트 변경이 잦은 프로젝트에서, 이 구조가 프론트엔드 코드 수정 없이 폰트 업데이트를 가능하게 해줘서 개발 속도가 빨라졌습니다.

## 백엔드에서 폰트 페어링 레지스트리를 운영할 때 꼭 기억해야 할 점

- **캐싱 전략은 필수**: Fonttrio 같은 외부 레지스트리를 매번 실시간 호출하면 네트워크 지연과 장애 위험이 커집니다. 위 예시처럼 6시간 단위 캐싱이나, 필요하면 Redis 같은 인메모리 캐시를 활용하세요.

- **버전 관리와 호환성 체크**: 폰트 페어링 데이터가 업데이트되면 UI가 깨질 수도 있습니다. 버전 정보를 API 응답에 포함시키고, 프론트엔드와 협의해 점진적 배포 전략을 쓰는 게 좋습니다.

- **모니터링과 실패 계측**: 폰트 로딩 실패, API 호출 실패 등 장애 유형을 초기에 계측해두면, 문제 발생 시 빠른 대응이 가능합니다. Anthropic 가이드에서 강조하는 것처럼 초기부터 장애 유형을 체계적으로 관리하는 게 유지보수의 핵심입니다[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

- **보안과 접근 제어**: 폰트 API가 공개되면 누구나 최신 폰트 정보를 가져갈 수 있지만, 내부 정책상 제한이 필요하면 인증 토큰을 붙이거나 IP 화이트리스트를 적용하세요.

## Fonttrio를 백엔드에서 활용하며 느낀 점과 앞으로의 가능성

폰트 페어링 같은 UI 요소를 백엔드 API로 관리하는 게 처음엔 좀 낯설었는데, 실제로 해보니 프론트엔드-백엔드 간 경계를 넘나드는 좋은 협업 방식이라는 생각이 들었어요. 특히 대규모 팀이나 다수의 프로젝트가 같은 디자인 시스템을 쓸 때, 이런 중앙 집중식 관리가 큰 도움이 됩니다.

그리고 Fonttrio 같은 오픈소스 레지스트리를 활용하면, 폰트 선택에 대한 디자인팀과 개발팀 간 커뮤니케이션 비용도 줄일 수 있죠. 앞으로는 폰트뿐 아니라 컬러 팔레트, 아이콘 세트 같은 UI 자산도 비슷한 방식으로 API화하는 추세가 될 것 같습니다.

---

## 마무리하며 — Fonttrio 백엔드 통합 시 꼭 기억할 것

- Fonttrio 같은 폰트 페어링 레지스트리를 백엔드 API로 제공하면 UI 일관성과 개발 생산성이 크게 높아진다.
- 점진적 배포 전략을 적용해 새 폰트 조합 도입 시 리스크를 줄여라.
- 장애 유형을 초기에 계측해 유지보수성과 장애 대응 속도를 개선하자.
- 캐싱과 버전 관리, 보안 정책도 반드시 챙겨야 한다.

폰트가 단순한 UI 꾸밈을 넘어서 개발 프로세스 전반에 영향을 줄 수 있다는 걸 이번에 몸소 느꼈습니다. 혹시 shadcn/ui 같은 라이브러리를 쓰면서 폰트 관리 때문에 고민이라면, Fonttrio 오픈소스 레지스트리 한번 살펴보세요. 그리고 백엔드 API로 한번 감싸보는 걸 추천합니다.
