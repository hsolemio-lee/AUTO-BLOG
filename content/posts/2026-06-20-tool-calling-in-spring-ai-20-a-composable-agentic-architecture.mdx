### AI 에이전트를 백엔드에 붙일 때 가장 먼저 마주하는 질문

"이걸 어떻게 확장 가능하게 만들지?" AI 모델과 통신하는 백엔드 시스템을 설계할 때, 단순히 API 호출만 하는 게 아니라 여러 도구(툴)를 조합해 복잡한 작업을 처리하는 에이전트 구조를 만들려면 고민이 많아집니다. 특히 Spring Boot 3.0 이상과 Spring AI 2.0이 나오면서, 기존과는 다른 컴포저블하고 에이전트 중심적인 아키텍처를 어떻게 구현할지가 핫한 주제죠.

내가 최근에 직접 Spring AI 2.0으로 이런 아키텍처를 설계해보면서 느낀 점과, 실제로 어떻게 구성하고 튜닝했는지 공유해보려고 합니다. 딱딱한 공식 문서보다 실무에서 겪은 경험 위주로요.

---

## Spring Boot 3.0과 Spring AI 2.0이 바꿔놓은 AI 백엔드

Spring Boot 3.0부터는 AI 모델 통합을 위한 자동 구성(auto-configuration)과 의존성 주입이 훨씬 편해졌습니다. 덕분에 AI 도구 호출을 담당하는 여러 컴포넌트를 컴포저블하게 조합할 수 있죠. 예를 들어, OpenAI API 호출, 프롬프트 관리, 결과 후처리 같은 역할을 각각 모듈화해서 필요할 때마다 조립하는 식입니다.

이런 구조 덕분에 서비스가 커져도 유지보수가 쉽고, 새로운 AI 도구가 추가되더라도 기존 코드를 크게 건드리지 않아도 됩니다. 실제로 Spring Boot Reference Documentation에도 IoC와 DI를 활용한 확장 가능한 아키텍처 설계법이 자세히 나와 있죠[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

내가 직접 해보니, 처음에는 컴포넌트 분리 작업이 좀 귀찮아도, 나중에 기능 추가하거나 문제 생겼을 때 훨씬 빠르게 대응할 수 있어서 진짜 시간 절약이 됩니다.

## IoC와 AOP가 AI 에이전트 행동 조정에 미치는 영향

Spring Framework의 IoC(제어의 역전)와 AOP(관점 지향 프로그래밍)는 단순히 코드 재사용성을 높이는 걸 넘어, AI 도구 호출 시 모듈 간 결합도를 낮추고 에이전트의 행동을 동적으로 바꾸는 데 큰 도움이 됩니다.

예를 들어, API 호출 전후에 로깅이나 트레이싱, 리트라이 정책을 AOP로 쉽게 적용할 수 있습니다. 이걸 직접 구현해보면, 기존 코드에 전혀 손대지 않고도 AI 호출 흐름에 관여하는 로직을 심을 수 있어서 유지보수가 훨씬 편해집니다.

또한, IoC 덕분에 각 AI 도구 호출 컴포넌트를 독립적으로 테스트할 수 있고, 필요에 따라 런타임 시 동적으로 교체하는 것도 가능해요. 이런 유연성은 AI 모델이 계속 업데이트되고, 호출 방식이 바뀌는 환경에서 진가를 발휘합니다.

자세한 내용은 Spring Framework 공식 문서에서 IoC와 AOP의 핵심 원리를 참고하세요[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

## 비동기 처리와 스레드 풀 튜닝 없인 AI 호출 병목 못 잡는다

AI API 호출은 대부분 네트워크 I/O가 병목이 되기 쉽습니다. 내가 운영하는 서비스도 초기엔 동기 호출로 구현했다가, AI 요청이 몰리면 응답 지연과 타임아웃 문제가 빈번히 발생했죠.

그래서 Spring Boot의 비동기 처리 기능을 적극 활용했습니다. `@Async` 어노테이션과 커스텀 스레드 풀 설정으로 AI 호출을 비동기로 처리하고, 스레드 풀 크기는 CPU 코어 수의 2~4배 정도로 잡아봤어요. 예를 들어, 8코어 서버면 16~32 스레드 정도가 적당했습니다. 너무 크면 컨텍스트 스위칭 비용이 늘어나고, 너무 작으면 동시 처리량이 부족하더라고요.

```java
@Configuration
@EnableAsync
public class AsyncConfig {

    @Bean(name = "aiTaskExecutor")
    public Executor aiTaskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(16); // CPU 코어 8개 기준
        executor.setMaxPoolSize(32);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("AI-Executor-");
        executor.initialize();
        return executor;
    }
}

@Service
public class AiCallService {

    @Async("aiTaskExecutor")
    public CompletableFuture<String> callOpenAiAsync(String prompt) {
        // OpenAI API 호출 로직
        return CompletableFuture.completedFuture("response");
    }
}
```

이렇게 하니 AI 호출 지연으로 인한 전체 서비스 지연이 크게 줄었고, 확장성도 눈에 띄게 좋아졌습니다. Baeldung의 Spring Boot 성능 튜닝 가이드에도 비동기 처리와 스레드 풀 설정이 핵심이라고 나와 있어요[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

## OpenAI API 호출 시 꼭 챙겨야 할 점들

OpenAI API는 RESTful 인터페이스를 제공하는데, Spring AI 2.0에서 이걸 호출할 때는 API 키 관리, 요청 제한(rate limiting), 그리고 응답 처리 전략이 정말 중요합니다.

내가 겪은 가장 큰 문제는 API 키 노출 위험과 갑작스러운 트래픽 폭증에 따른 429 Too Many Requests 에러였어요. 그래서 다음과 같은 전략을 썼습니다.

- **API 키는 Spring Cloud Config나 Vault 같은 안전한 비밀 관리 시스템에 보관**
- **요청 제한을 초과하지 않도록 RateLimiter 적용 (예: Resilience4j)**
- **에러 발생 시 지수 백오프(exponential backoff)와 재시도 로직 구현**

또한, OpenAI API 응답이 느릴 때를 대비해 타임아웃 설정도 꼼꼼히 했는데, Spring의 `RestTemplate` 혹은 `WebClient`에서 타임아웃을 3초 내외로 잡는 게 무난했습니다.

```java
@Bean
public WebClient openAiWebClient(WebClient.Builder builder) {
    return builder
            .baseUrl("https://api.openai.com/v1")
            .defaultHeader(HttpHeaders.AUTHORIZATION, "Bearer " + openAiApiKey)
            .clientConnector(new ReactorClientHttpConnector(
                HttpClient.create()
                    .responseTimeout(Duration.ofSeconds(3))))
            .build();
}
```

이런 설계 덕분에 AI 에이전트가 외부 도구와 안정적으로 통신할 수 있었고, 장애도 최소화할 수 있었습니다. OpenAI 공식 문서도 이런 부분을 강조하고 있으니 참고하세요[OpenAI API Documentation](https://platform.openai.com/docs/overview).

## 프롬프트 설계가 AI 에이전트 신뢰성에 미치는 영향

Anthropic의 프롬프트 엔지니어링 가이드에서 강조하는 것처럼, AI 에이전트가 여러 도구를 호출할 때 프롬프트를 명확하고 일관되게 설계하는 게 성능과 신뢰성에 엄청난 영향을 줍니다.

내가 직접 여러 프롬프트를 실험해보니, 복잡한 작업을 여러 도구에 나눠서 맡길 때는 각 도구가 이해하기 쉬운 형태로 정보를 주고받아야 에러가 줄더라고요. 예를 들어, 다음과 같이 역할과 기대 결과를 구체적으로 명시하는 게 좋습니다.

```text
당신은 문서 요약 도구입니다. 입력된 긴 텍스트를 3문장 이내로 간결하게 요약해 주세요.
```

이런 명확한 지침이 없으면 AI가 엉뚱한 답변을 하거나, 도구 간 인터페이스가 꼬여서 전체 프로세스가 실패하는 경우가 많았습니다.

Spring AI 2.0도 이런 프롬프트 템플릿을 컴포넌트화해서 재사용할 수 있게 해줘서, 프롬프트 관리가 훨씬 수월해졌어요. Anthropic 가이드도 참고하면 많은 도움이 됩니다[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

## 각 도구 호출을 별도 컴포넌트로 분리하는 이유

Cursor 문서에서 말하는 것처럼, AI 도구 호출을 각각 독립된 컴포넌트로 분리하고, 이들을 조합하는 아키텍처는 재사용성과 유지보수성 면에서 엄청난 장점이 있습니다.

내가 구현한 구조도 이와 비슷했는데, 예를 들어 `SummarizationTool`, `TranslationTool`, `SearchTool` 같은 컴포넌트가 각각 독립적으로 구현되어 있어요. 그리고 에이전트는 이들을 조합해 복합적인 작업을 수행합니다.

```java
@Component
public class SummarizationTool {
    public String summarize(String text) {
        // OpenAI API 호출 및 요약 로직
        return "요약된 텍스트";
    }
}

@Component
public class Agent {

    private final SummarizationTool summarizationTool;

    public Agent(SummarizationTool summarizationTool) {
        this.summarizationTool = summarizationTool;
    }

    public String handleRequest(String input) {
        // 복합 작업 예: 요약 후 번역 등
        String summary = summarizationTool.summarize(input);
        // 추가 도구 호출 가능
        return summary;
    }
}
```

이런 모듈화 덕분에, 새로운 도구가 추가되어도 기존 코드에 영향이 적고, 테스트도 독립적으로 할 수 있어 개발 속도가 확실히 빨라졌습니다. Cursor 문서에서 말하는 컴포저블 아키텍처와도 일맥상통합니다[Cursor Documentation](https://docs.cursor.com/).

### 마치며: 실제로 써보니 이런 점이 가장 중요했다

- **컴포넌트 분리와 IoC 활용**: 처음엔 귀찮아도 장기적으로 유지보수와 확장에 큰 도움이 된다.
- **비동기 호출과 스레드 풀 튜닝**: AI 호출 병목을 잡지 않으면 서비스 전체가 느려진다.
- **API 호출 안정성 확보**: 키 관리, 요청 제한, 재시도 로직은 필수다.
- **프롬프트 명확성**: AI가 기대한 대로 동작하게 하려면 프롬프트 설계에 공을 들여야 한다.
- **모듈화된 도구 호출 구조**: 재사용성과 테스트 편의성을 위해 각 도구를 독립 컴포넌트로 분리하자.

이 글이 Spring AI 2.0으로 AI 에이전트 아키텍처를 구성하는 데 조금이나마 도움이 되었으면 합니다. 실제로 써보면 문서에서 미처 다루지 않는 현장의 노하우가 꽤 많거든요.
