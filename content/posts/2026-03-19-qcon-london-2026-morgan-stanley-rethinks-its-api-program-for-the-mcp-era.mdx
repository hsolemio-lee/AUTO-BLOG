## MCP 시대, API가 다시 태어나야 했던 이유

"우리 API가 클라우드마다 다르게 동작하는데, 관리가 너무 어렵다"는 이야기를 들어본 적 있나요? Morgan Stanley가 QCon London 2026에서 공개한 사례는 바로 이런 현실적인 문제에서 시작됐습니다. MCP(Multi-Cloud Platform) 환경으로 전환하면서 기존 API 프로그램이 확장성, 운영 효율성에서 한계를 드러냈거든요. 

이걸 그냥 두면 서비스 장애도 잦고, 개발 생산성도 떨어질 수밖에 없죠. 그래서 그들은 마이크로서비스 아키텍처와 클라우드 네이티브 패턴을 적극 도입해 API 프로그램을 완전히 재설계했습니다. 이 과정에서 얻은 깨달음과 실전 노하우를 공유하려고 해요.


## 타입 안정성, TypeScript 5.x로 백엔드-프론트엔드 계약을 단단하게

Morgan Stanley가 특히 신경 쓴 부분 중 하나가 타입 안정성이었습니다. API 계약이 깨지면 고객 경험에 직격탄이니까요. 그래서 백엔드와 프론트엔드 간 계약 검증을 자동화하기 위해 TypeScript 5.x의 최신 기능을 도입했습니다. 

예를 들어, `const enum`과 `satisfies` 연산자를 적극 활용해 API 스펙을 선언적이고 엄격하게 관리했죠. 이렇게 하면 프론트엔드가 API 스펙을 벗어나는 호출을 시도할 때 컴파일 단계에서 바로 잡아낼 수 있습니다.

```typescript
// API 응답 타입 선언
interface UserProfile {
  id: string;
  name: string;
  email: string;
  createdAt: string;
}

// API 호출 함수에 타입 계약 적용
async function fetchUserProfile(userId: string): Promise<UserProfile> {
  const response = await fetch(`/api/users/${userId}`);
  const data = await response.json();
  
  // 타입 검증을 위한 satisfies 사용
  return data satisfies UserProfile;
}
```

이렇게 하면 런타임 오류 가능성을 크게 줄일 수 있고, 개발자가 API 변경 사항을 실시간으로 감지할 수 있어 생산성이 확실히 올라갑니다. 물론 타입스크립트 도입 초기에는 빌드 시간이 조금 늘고, 복잡한 제네릭 타입 때문에 러닝커브가 있었지만, 장기적으로 보면 투자 대비 효과는 확실했습니다[TypeScript 5.x Release Notes](https://devblogs.microsoft.com/typescript/announcing-typescript-5-4/).


## GitHub Actions로 빠르고 안정적인 API 배포 파이프라인 구축

클라우드 환경에서 API를 운영하다 보면 배포 주기가 짧아지고, 릴리즈 안정성은 더 중요해집니다. Morgan Stanley는 GitHub Actions를 적극 활용해 CI/CD 파이프라인을 만들었는데요, 이 덕분에 코드 푸시부터 프로덕션 배포까지 평균 15분 이내에 끝낼 수 있었답니다.

특히 다음과 같은 워크플로우를 구성했어요:

- **PR 생성 시 자동 타입 검사 및 유닛 테스트 실행**
- **메인 브랜치 머지 시 자동 빌드 및 컨테이너 이미지 생성**
- **스테이징 환경에 자동 배포 후 통합 테스트 수행**
- **테스트 통과 시 프로덕션 롤아웃**

```yaml
name: API CI/CD

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Setup Node.js
        uses: actions/setup-node@v3
        with:
          node-version: '20'
      - name: Install dependencies
        run: npm ci
      - name: Run type check
        run: npm run type-check
      - name: Run tests
        run: npm test
  deploy:
    needs: build-and-test
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v3
      - name: Build Docker image
        run: docker build -t morganstanley/api:${{ github.sha }} .
      - name: Push to registry
        run: docker push morganstanley/api:${{ github.sha }}
      - name: Deploy to Kubernetes
        run: kubectl apply -f k8s/deployment.yaml
```

이런 자동화 덕분에 오류가 줄고, 빠른 피드백 사이클로 개발 속도가 눈에 띄게 빨라졌습니다. 물론 초기 설정에 시간이 꽤 들고, 복잡한 워크플로우를 유지보수하는 데 신경 써야 하는 단점도 있지만, 대규모 팀에서 이득이 훨씬 크죠[GitHub Engineering Blog](https://github.blog/category/engineering/).


## 엣지 플랫폼으로 API 응답 속도와 보안 둘 다 잡기

MCP 환경에서는 API가 여러 클라우드에 분산되다 보니, 네트워크 지연과 보안 위협에 노출될 가능성이 커집니다. Morgan Stanley는 Cloudflare 같은 엣지 플랫폼을 적극 활용해 이 문제를 해결했는데요.

엣지에서 API 요청을 캐싱하고, DDoS 공격이나 봇 트래픽을 차단하는 동시에 TLS 종료를 엣지에서 처리해 응답 속도를 획기적으로 개선했습니다. 

이런 아키텍처는 특히 금융권처럼 보안과 성능 모두 놓칠 수 없는 서비스에 적합합니다. 물론 엣지 캐싱 정책을 잘못 설정하면 실시간성이 중요한 데이터에서 문제가 생길 수 있으니, 캐시 무효화 전략도 꼼꼼히 설계해야 하죠.


## MCP 시대, 분산 트랜잭션과 이벤트 기반 아키텍처가 답인 이유

InfoQ의 아키텍처 디자인 가이드에 따르면, MCP 환경에서는 API 설계 시 공급망 관리, 보안, 신뢰성 확보가 필수적입니다. Morgan Stanley는 이를 위해 분산 트랜잭션 처리와 이벤트 기반 아키텍처를 적극 도입했는데요.

예를 들어, 서비스 간 데이터 일관성을 위해 SAGA 패턴을 적용해 트랜잭션을 관리하고, 이벤트 버스(Kafka 등)를 통해 비동기 통신을 구현했습니다. 이렇게 하면 각 클라우드 환경에서 독립적으로 서비스가 운영되면서도 데이터 신뢰성을 유지할 수 있습니다.

이 과정에서 발생하는 복잡성은 분명 부담이지만, MCP의 장점을 살리면서도 일관된 사용자 경험을 제공하려면 필수적인 선택이었죠[InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/).


## 직접 경험해본 MCP API 재설계, 내게 남은 교훈

사실 처음엔 MCP 환경에 맞춰 API를 재설계하는 게 막막했습니다. 클라우드마다 네트워크 특성도 다르고, 보안 정책도 천차만별이라서요. 하지만 Morgan Stanley 사례를 보며 다음 세 가지를 꼭 기억하게 됐어요.

1. **타입 안정성은 개발 생산성의 핵심** — TypeScript 5.x 같은 최신 도구를 적극 활용해 계약 검증을 자동화하자.
2. **자동화된 CI/CD는 빠른 피드백과 안정적 릴리즈의 기초** — GitHub Actions 같은 플랫폼을 활용해 배포 파이프라인을 잘 구축하라.
3. **엣지 플랫폼과 분산 아키텍처는 필수** — 성능과 보안을 동시에 잡으려면 엣지 캐싱과 이벤트 기반 설계를 고민해야 한다.

이걸 적용하고 나니 서비스 장애도 줄고, 개발자 만족도도 올라갔습니다. 물론 MCP 전환은 단기간에 끝나는 프로젝트가 아니고, 지속적인 모니터링과 개선이 필요하다는 점도 잊지 말아야 합니다.
