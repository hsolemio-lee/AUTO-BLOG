### "기존 Spring Cloud Contract 테스트를 어떻게 Stubborn.sh에 맞게 옮기지?"

최근 우리 팀에서는 마이크로서비스 간 계약 테스트를 담당하던 Spring Cloud Contract를 Stubborn.sh라는 새로운 플랫폼으로 이전하는 작업을 진행했어요. 처음엔 ‘그냥 설정 몇 개 바꾸면 되겠지’ 했는데, 막상 해보니 생각보다 복잡한 부분이 많더라고요. 특히 프로덕션 환경에 맞춘 성능 튜닝과 보안 설정, 그리고 무중단 전환을 위한 롤아웃 전략까지 챙기려니 머리가 복잡했습니다.

이번 글에서는 저희가 직접 부딪히고 해결한 경험을 바탕으로, 중급 백엔드 엔지니어 입장에서 Spring Cloud Contract에서 Stubborn.sh로 이전할 때 꼭 알아야 할 핵심 포인트들을 공유하려고 해요.

---

## Spring Cloud Contract와 Stubborn.sh, 왜 옮기게 됐나?

Spring Boot 기반 마이크로서비스에서 계약 기반 테스트는 필수죠. Spring Cloud Contract는 이걸 자동화해줘서 꽤 오랫동안 애용해왔습니다. [Spring Boot 공식 문서](https://docs.spring.io/spring-boot/reference/)에서도 마이크로서비스 아키텍처에서 계약 테스트를 강조하고 있고요.

그런데 Stubborn.sh가 등장하면서, 더 직관적인 API와 클라우드 네이티브 환경에 맞는 확장성을 제공한다는 소식에 팀 차원에서 전환을 결정했습니다. 특히 Stubborn.sh는 OAuth 2.0과 JWT 인증을 기본 지원해 보안 강화에 유리했고, 클라우드 환경에서의 퍼포먼스 튜닝 옵션도 다양했거든요.

---

## 기존 계약 테스트 설정을 Stubborn.sh API에 맞게 어떻게 바꿨나?

Spring Cloud Contract는 Gradle/Maven 플러그인과 DSL 기반의 계약 정의가 핵심인데, Stubborn.sh는 REST API 호출과 JSON 기반 계약 관리에 초점이 맞춰져 있어요. 그래서 기존 DSL을 Stubborn.sh 포맷으로 변환하는 스크립트를 직접 만들어야 했습니다.

예를 들어, Spring Cloud Contract에서 이런 식으로 계약을 정의했다면:

```groovy
Contract.make {
    request {
        method 'GET'
        url '/api/v1/users/123'
    }
    response {
        status 200
        body([id: 123, name: 'Alice'])
        headers { contentType(applicationJson()) }
    }
}
```

Stubborn.sh에서는 JSON으로 다음과 같이 변환해서 API로 등록했어요:

```json
{
  "request": {
    "method": "GET",
    "path": "/api/v1/users/123"
  },
  "response": {
    "status": 200,
    "body": {"id": 123, "name": "Alice"},
    "headers": {"Content-Type": "application/json"}
  }
}
```

이 변환 작업은 Python 스크립트로 자동화했는데, 처음엔 계약이 복잡해질수록 변환 누락이나 오류가 많아서 꽤 고생했어요. 결국 계약별로 검증 테스트를 병행하며 점진적으로 안정화했습니다.

## 프로덕션 환경에서 성능 튜닝, JVM부터 비동기 처리까지 다시 점검하기

Spring Boot 애플리케이션에서 JVM 튜닝, 캐싱, 비동기 처리 등은 기본 중의 기본이지만, Stubborn.sh로 계약 테스트를 이전하면서 이 부분을 다시 한 번 꼼꼼히 살펴봤어요. [Baeldung의 성능 튜닝 가이드](https://www.baeldung.com/spring-boot-performance)를 참고해서 JVM 힙 메모리 설정(-Xms512m -Xmx2g), GC 옵션(UseG1GC), 그리고 스레드 풀 크기 조정 등을 적용했습니다.

특히 계약 테스트 호출이 많아질수록 I/O 대기 시간이 늘어나서, 비동기 WebClient 기반 호출로 전환한 게 효과적이었죠. 캐싱 전략도 재설계했는데, 계약 테스트 결과를 일정 시간 캐싱해 불필요한 호출을 줄이니 평균 응답 시간이 30% 이상 개선됐습니다.

```java
// WebClient를 이용한 비동기 계약 테스트 호출 예시
public Mono<ClientResponse> callContractTest(String url) {
    return webClient.get()
            .uri(url)
            .retrieve()
            .onStatus(HttpStatus::isError, clientResponse -> Mono.error(new RuntimeException("Test failed")))
            .toBodilessEntity();
}
```

이렇게 비동기 호출을 도입하면, 테스트 병렬 처리도 자연스럽게 가능해져서 전체 테스트 시간 단축에 큰 도움이 됐어요.

## Stubborn.sh의 보안 설정, OAuth 2.0과 JWT 적용 시 주의할 점

Stubborn.sh가 기본 제공하는 OAuth 2.0과 JWT 인증 체계를 도입하면서, 기존 Spring Cloud Contract에서 쓰던 인증 메커니즘과 호환성 문제를 겪었습니다. OAuth 2.0 토큰 발급 서버와 클라이언트 설정을 신중하게 맞춰야 했는데, 특히 JWT 서명 키 관리와 토큰 만료 정책이 중요했죠.

Spring Boot 공식 문서에 따르면, 인증 서버와 리소스 서버 간 키 공유 및 검증 로직을 명확히 해야 하며, 토큰 재발급 로직도 필수입니다. Stubborn.sh API 호출 시 Authorization 헤더에 Bearer 토큰을 반드시 포함시키는 것도 잊으면 안 되고요.

```yaml
security:
  oauth2:
    client:
      registration:
        stubbornsh:
          client-id: your-client-id
          client-secret: your-client-secret
          authorization-grant-type: client_credentials
          scope: read write
    resourceserver:
      jwt:
        jwk-set-uri: https://auth.yourdomain.com/.well-known/jwks.json
```

이렇게 설정 후, 테스트 자동화 파이프라인에 토큰 발급과 갱신 스크립트를 넣어야 해서 처음엔 번거로웠지만, 보안 사고 위험이 확 줄어들어 결과적으로는 만족스러웠습니다.

## 무중단 전환을 위한 점진적 롤아웃 전략은 어떻게 세웠나?

마이크로서비스 계약 테스트 환경을 한꺼번에 바꾸는 건 위험하다고 판단해, [Martin Fowler의 아키텍처 가이드](https://martinfowler.com/architecture/)와 [GitHub Engineering Blog](https://github.blog/category/engineering/)에서 강조하는 단계별 마이그레이션 방식을 채택했어요.

1. **일부 서비스에만 Stubborn.sh 적용**: 먼저 트래픽이 적은 서비스부터 Stubborn.sh 계약 테스트를 적용해 문제점을 조기에 발견했습니다.
2. **모니터링 강화**: 테스트 실패율, 응답 시간, 리소스 사용량을 실시간으로 모니터링하며 이상 징후를 빠르게 포착했죠.
3. **롤백 계획 수립**: 문제가 생기면 바로 Spring Cloud Contract로 되돌릴 수 있도록 배포 파이프라인에 롤백 스크립트를 준비했습니다.

덕분에 실제 프로덕션 전환 시 큰 장애 없이 안정적으로 이전할 수 있었고, 팀 내에서도 "이전보다 테스트 신뢰도가 더 높아졌다"는 평가를 받았습니다.

## 마무리하며

Stubborn.sh로의 이전은 단순히 도구 교체가 아니라, 계약 테스트 운영 전반을 다시 점검하고 개선하는 기회였습니다. 자동화 스크립트 작성, JVM과 비동기 처리 튜닝, 보안 설정 재구성, 그리고 점진적 롤아웃까지. 하나하나 직접 겪어보니, 이론과 실제는 다르다는 걸 다시 한 번 느꼈네요.

혹시 여러분도 비슷한 전환을 고민 중이라면, 저희가 겪은 시행착오와 팁들이 조금이나마 도움이 되길 바랍니다. 특히 계약 변환 자동화와 보안 토큰 관리, 그리고 무중단 롤아웃은 꼭 미리 준비하세요. 안 그러면 저처럼 새벽에 알람 울리며 고생할 수도 있습니다!
