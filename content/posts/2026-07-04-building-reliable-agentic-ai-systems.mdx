### "이번 배포에서 AI가 갑자기 이상한 답변을 내놓았어요" — 이 상황, 어떻게 막을 수 있을까?

우리 팀이 에이전틱 AI 시스템을 운영하면서 가장 자주 겪는 문제 중 하나가 바로 "AI가 예측 불가능한 행동을 할 때"다. 특히, 서비스가 커지고 요청이 폭증할 때 지연이나 오류가 발생하면 사용자 경험에 치명적이다. 그래서 확장 가능한 아키텍처와 안정적인 요청 제어, 그리고 AI가 의도한 대로 행동하게 하는 프롬프트 설계가 필수라는 걸 몸소 깨달았다.

이번 글에서는 내가 직접 경험한 에이전틱 AI 시스템 구축 과정에서 마주친 현실적인 고민과 그 해결책을 공유한다. OpenAI API와 Anthropic 프롬프트 가이드, 그리고 Claude Code 플랫폼까지 실제 사례와 설정값 중심으로 풀어보겠다.

## OpenAI API, 왜 확장성과 요청 제어가 신뢰성의 핵심인가

OpenAI API를 쓰다 보면 가장 먼저 마주치는 건 "요청이 몰릴 때 어떻게 안정적으로 처리할 것인가" 문제다. API는 기본적으로 확장 가능한 구조지만, 단순히 요청을 막 던지면 지연이 길어지고, 심하면 오류가 난다. 그래서 우리는 다음과 같은 전략을 썼다.

- **동시 요청 제한**: 한 서비스 인스턴스당 최대 10개의 동시 요청으로 제한
- **재시도 정책**: 429(Too Many Requests)나 503(Service Unavailable) 응답 시, 지수 백오프(exponential backoff)로 최대 5회 재시도
- **타임아웃 설정**: API 호출 타임아웃을 5초로 고정하여 지연이 길어질 경우 빠르게 실패 처리

이 조합 덕분에, 한 달간 99.9% 이상의 API 가용성을 유지할 수 있었다. 물론, 타임아웃을 너무 짧게 잡으면 네트워크 변동성에 취약하고, 너무 길게 하면 사용자 대기 시간이 늘어난다. 적절한 균형이 중요하다.

```python
import openai
import time

openai.api_key = "YOUR_API_KEY"

MAX_RETRIES = 5


def call_openai_api(prompt):
    for attempt in range(MAX_RETRIES):
        try:
            response = openai.ChatCompletion.create(
                model="gpt-4",
                messages=[{"role": "user", "content": prompt}],
                timeout=5
            )
            return response.choices[0].message.content
        except openai.error.RateLimitError:
            wait_time = 2 ** attempt
            print(f"Rate limit hit, retrying in {wait_time}s...")
            time.sleep(wait_time)
        except openai.error.Timeout:
            print("Request timed out, retrying...")
            time.sleep(1)
    raise Exception("API 호출 실패: 최대 재시도 초과")
```

이 코드는 지수 백오프와 타임아웃을 조합해 안정성을 높인 예시다. 실제 운영 환경에선 로그와 모니터링을 꼭 함께 둬야 한다.

[OpenAI API Documentation](https://platform.openai.com/docs/overview)에서 권장하는 패턴이기도 하니 참고하길 바란다.

## "프롬프트가 AI의 운명을 결정한다" — Anthropic의 프롬프트 설계법

내가 Anthropic의 프롬프트 엔지니어링 가이드를 접하고 가장 크게 느낀 점은, AI가 어떻게 행동할지 예측 가능하게 만드는 건 결국 프롬프트 설계라는 사실이었다. 단순히 질문을 던지는 게 아니라, 의도와 맥락을 명확히 구조화해야 한다는 거다.

예를 들어, 단순히 "이 문장을 번역해줘" 대신에 이렇게 쓴다.

```
You are a helpful assistant specialized in translating English to Korean. Please translate the following sentence accurately and politely.

Sentence: "Can you help me with my homework?"
```

이렇게 역할(role)과 기대 행동을 명확히 적으면 AI가 더 일관된 답변을 낸다. Anthropic 가이드에서는 이런 "의도된 행동 유도"가 에이전틱 AI의 안정성에 얼마나 중요한지 강조한다.

또한, 프롬프트 내에 금지어, 허용어, 예시 등을 넣어 AI가 잘못된 방향으로 가지 않게 하는 것도 좋은 방법이다. 이런 구조화 덕분에 우리는 서비스 내에서 AI가 이상한 답변을 내놓는 빈도를 30% 이상 줄일 수 있었다.

[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)에서 더 자세한 사례와 템플릿을 볼 수 있다.

## Claude Code 플랫폼과 상태 관리, 유지보수성을 어떻게 잡았나

AI가 코드를 생성하거나 수정하는 기능을 서비스에 넣을 때, 단순히 "코드 생성"만 하면 끝이 아니다. 상태 관리가 굉장히 중요하다. Claude Code 플랫폼은 이런 부분을 잘 설계해놨다.

우리도 Claude Code API를 도입하면서 다음을 신경 썼다.

- **명확한 API 계약**: 요청마다 어떤 상태(state)를 넘기고, AI가 반환하는 결과도 상태를 포함하게 설계
- **버전 관리**: 생성된 코드 조각마다 버전 태그를 붙여 변경 이력을 추적
- **에러 핸들링**: 코드 생성 실패 시 롤백 메커니즘과 재시도 로직 구현

이렇게 하니, AI가 생성한 코드가 의도와 다르게 변경되거나, 중간에 상태가 꼬이는 문제를 크게 줄일 수 있었다. 물론, 상태를 관리하다 보니 API 호출이 복잡해지고 응답 시간도 약간 늘어나는 단점은 있다. 하지만 유지보수성과 신뢰성을 위해선 필수적인 트레이드오프라고 생각한다.

[Anthropic - Claude Code Overview](https://docs.anthropic.com/en/docs/claude-code/overview) 문서에서 자세한 아키텍처 패턴을 참고할 수 있다.

## 실제 운영에서 AI SDK 선택은 어떻게 해야 할까?

우리 팀은 AI 기능을 빠르게 통합하기 위해 여러 SDK를 테스트했다. 그중 OpenAI API와 Anthropic Claude Code 외에도 Cursor, GitHub Copilot, Vercel AI SDK를 잠깐 써봤다.

- **Cursor**: 프론트엔드와 백엔드 모두에 맞는 SDK를 제공해 코드 자동 완성에 강점. 하지만 복잡한 상태 관리나 대규모 트랜잭션 처리에는 한계가 있었다.
- **GitHub Copilot**: 개발 생산성 향상에 탁월하지만, AI 시스템 아키텍처의 신뢰성을 직접 보장하지는 않는다. 반복 작업 감소에 도움.
- **Vercel AI SDK**: 프론트엔드 중심 빠른 배포에 최적화되어 있지만, 백엔드 복잡한 로직에는 적합하지 않았다.

결국, 신뢰성 높은 에이전틱 AI 시스템을 위해선 OpenAI API와 Anthropic 플랫폼의 조합이 가장 현실적이었다. 물론, 서비스 목적과 규모에 따라 선택지는 달라질 수 있다.

## 마무리하며 — "신뢰성은 설계에서부터 시작된다"

에이전틱 AI 시스템을 만들면서 깨달은 건, AI 모델 자체만 믿으면 안 된다는 점이다. API 호출 전략, 프롬프트 설계, 상태 관리, SDK 선택까지 모두 조화롭게 맞춰야 서비스가 흔들리지 않는다.

특히, 운영 환경에서 지연과 오류를 줄이려면 다음을 꼭 챙기자.

- API 요청 제한과 재시도 정책은 필수
- 프롬프트는 역할과 의도를 명확히, 구조화해서 설계
- 상태 관리는 코드 생성/수정 과정에서 필수적
- SDK는 서비스 특성에 맞게 신중히 선택

이건 실제로 겪어보면 "이게 왜 이렇게 중요한지" 바로 느껴진다. 나도 처음엔 프롬프트 설계 같은 게 별거 아닐 줄 알았는데, 막상 서비스에 적용하니 시스템 안정성에 미치는 영향이 엄청났다.

앞으로도 AI 시스템은 더 복잡해질 텐데, 이런 기본 원칙만 잘 지켜도 꽤 든든한 기반이 될 거라 믿는다.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
