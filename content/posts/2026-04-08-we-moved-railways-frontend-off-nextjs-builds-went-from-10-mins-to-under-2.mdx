## 빌드가 10분 넘게 걸릴 때, 이대로 괜찮을까?

"빌드가 10분 넘게 걸리는데, 이거 어떻게 해야 할까요?"

최근 우리 팀에서 가장 많이 들었던 질문 중 하나였습니다. Railway 프론트엔드가 Next.js 기반인데, 빌드 시간이 너무 길어 개발 속도가 현저히 느려지고 있었거든요. 특히 배포 전 빌드가 10분 이상 걸리니, 작은 수정에도 기다림이 길어져 개발 생산성이 크게 떨어졌죠.

처음엔 Next.js의 강력한 기능들, 예를 들어 서버 사이드 렌더링(SSR)이나 App Router가 주는 편리함 때문에 쉽게 포기하지 못했습니다. 그런데 실제로 빌드 시간을 자세히 들여다보니, Next.js가 내부적으로 복잡한 라우팅과 SSR을 처리하면서 빌드 시간이 비약적으로 늘어나고 있더군요.[Next.js App Router Docs](https://nextjs.org/docs/app/building-your-application/routing)

그래서 우리 팀은 과감히 Next.js를 벗어나 클라이언트 중심의 경량 빌드 시스템으로 마이그레이션을 결정했습니다. 이 과정에서 React의 컴포넌트 기반 아키텍처가 얼마나 큰 도움이 되었는지, 그리고 빌드 시간을 10분 이상에서 2분 이하로 줄인 실제 경험을 공유해보려 합니다.


## React 컴포넌트 단위로 쪼개니 리팩토링과 재사용이 훨씬 수월했다

Next.js를 포기하고 새 빌드 시스템으로 갈아타려면, 기존 코드를 어떻게 옮기고 유지보수할지 걱정이 컸습니다. 다행히 React의 컴포넌트 기반 아키텍처 덕분에 이 고민이 한결 가벼웠어요.

React는 UI를 독립적인 컴포넌트 단위로 쪼개서 생각하도록 설계되어 있습니다. 이 덕분에 전체 앱을 한꺼번에 옮길 필요 없이, 컴포넌트별로 점진적으로 리팩토링하고 재사용할 수 있었죠.[React - Thinking in React](https://react.dev/learn/thinking-in-react)

예를 들어, 기존에 Next.js 페이지 컴포넌트로 작성된 부분을 React 컴포넌트로 분리하고, 라우팅 로직만 새 시스템에 맞게 바꾸는 식이었습니다. 이렇게 하니 마이그레이션 중에도 서비스가 끊기지 않고 점진적으로 전환할 수 있었어요.

```jsx
// 기존 Next.js 페이지
export default function Dashboard() {
  return <div>대시보드 내용</div>;
}

// 새 빌드 시스템에서 React 컴포넌트로 재사용
function Dashboard() {
  return <div>대시보드 내용</div>;
}

export default Dashboard;
```

컴포넌트 단위로 쪼개진 구조는 빌드 시에도 유리했습니다. 불필요한 부분은 빌드에서 제외하거나, 코드 스플리팅을 통해 필요한 컴포넌트만 로드하도록 최적화할 수 있었거든요.


## Next.js App Router가 빌드 시간을 잡아먹는 주범이었다

Next.js의 App Router는 SSR, 동적 라우팅, 데이터 페칭 등 강력한 기능을 제공합니다. 하지만 이 모든 게 빌드 과정에서 복잡한 처리와 번들링을 요구하다 보니, 빌드 시간이 급격히 늘어나는 원인이 되었습니다.

Railway도 이 부분에서 고생했는데, App Router를 완전히 떼어내고 클라이언트 중심 라우팅으로 전환하니 빌드 시간이 확 줄었어요. 서버 사이드 렌더링 대신 정적 빌드와 클라이언트 라우팅을 병행하는 방식을 선택한 거죠.

이 과정에서 React Router 같은 경량 라우터를 도입해, 라우팅 로직을 훨씬 단순하게 유지할 수 있었습니다.

```jsx
import { BrowserRouter as Router, Routes, Route } from 'react-router-dom';

function App() {
  return (
    <Router>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/dashboard" element={<Dashboard />} />
      </Routes>
    </Router>
  );
}
```

이렇게 하니 빌드가 10분 이상 걸리던 게 2분 이내로 줄었고, 개발자 피드백도 즉각적으로 받을 수 있어 생산성이 크게 올라갔습니다.


## Cloudflare 사례에서 배운 빌드 최적화 전략

Cloudflare 엔지니어링 블로그에서 소개한 빌드 최적화 사례도 우리에게 큰 힌트를 줬습니다. 불필요한 SSR 제거, 코드 스플리팅, 캐싱 전략을 적극 활용해 빌드 시간을 줄인 점이 인상적이었죠.[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/)

우리도 비슷한 전략을 적용했습니다. 예를 들면:

- **SSR 제거**: Next.js의 SSR 기능을 없애고 클라이언트 렌더링 위주로 전환
- **코드 스플리팅**: React.lazy와 Suspense를 활용해 초기 번들 크기를 줄이고 필요한 컴포넌트만 로드
- **캐싱**: 빌드 캐시를 적극 활용해 변경되지 않은 모듈은 다시 빌드하지 않도록 설정

```jsx
import React, { Suspense, lazy } from 'react';

const HeavyComponent = lazy(() => import('./HeavyComponent'));

function App() {
  return (
    <Suspense fallback={<div>로딩 중...</div>}>
      <HeavyComponent />
    </Suspense>
  );
}
```

이렇게 하니 초기 로딩 속도도 빨라지고, 빌드 시간도 확실히 단축되었습니다. 물론 코드 스플리팅이 많아지면 관리가 복잡해질 수 있으니, 적절한 균형이 필요합니다.


## 마이그레이션하면서 겪은 예상치 못한 문제들

처음에는 빌드 속도만 생각했는데, 마이그레이션 과정에서 몇 가지 골치 아픈 문제도 마주쳤습니다.

- **라우팅 전환 시 SEO 영향**: Next.js의 SSR이 없어지면서 SEO 최적화에 신경 써야 했습니다. 정적 메타 태그 삽입과 prerendering 전략을 별도로 마련했죠.

- **상태 관리 복잡도 증가**: 클라이언트 중심 라우팅으로 바꾸니 상태 관리가 복잡해졌습니다. 그래서 Recoil이나 Zustand 같은 가벼운 상태 관리 라이브러리를 도입해 해결했습니다.

- **빌드 캐시 무효화 문제**: 캐시 전략을 잘못 설정하면 변경사항이 반영 안 되는 이슈가 있었는데, 캐시 키를 파일 해시 기반으로 바꾸면서 해결했습니다.

이런 문제들은 실제로 겪어보지 않으면 감이 잘 안 오는데, 우리 팀은 한 달 정도 시행착오를 거쳐 안정화할 수 있었습니다.


## 정리하며: 빌드 시간 줄이려면 Next.js 기능을 무조건 쓰는 게 답은 아니다

Railway가 Next.js에서 벗어나 빌드 시간을 10분 이상에서 2분 이하로 줄인 경험은, "무조건 최신 프레임워크 기능을 다 쓰는 게 좋은 건 아니다"라는 점을 다시 한 번 깨닫게 해줬습니다.

- React 컴포넌트 기반 설계 덕분에 점진적 마이그레이션과 재사용이 가능했고
- Next.js App Router와 SSR을 제거해 빌드 복잡도를 낮췄으며
- 코드 스플리팅과 캐싱 전략으로 빌드 효율을 극대화했습니다.

물론 이런 선택이 모든 프로젝트에 맞는 건 아니지만, 빌드 시간이 개발 생산성에 미치는 영향이 크다면 한 번쯤 고민해볼 만한 접근법입니다.

혹시 지금 빌드 시간이 너무 길어 고생 중이라면, 우리 사례가 조금이나마 도움이 되길 바랍니다.
