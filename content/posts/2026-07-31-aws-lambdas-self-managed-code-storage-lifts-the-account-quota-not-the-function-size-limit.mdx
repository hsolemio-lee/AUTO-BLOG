# AWS Lambda 코드 저장소가 바뀌었는데, 함수 크기 제한은 왜 안 바뀌는 걸까?

최근 AWS Lambda에서 "셀프 매니지드 코드 저장소(Self-Managed Code Storage)" 기능이 나왔다는 소식 들었나요? 이걸 들으면 보통 "오, 함수 크기 제한이 커지는구나!"라고 기대하기 쉽죠. 그런데 실제로는 함수당 최대 배포 가능한 코드 크기 제한(50MB 압축 기준)은 그대로고, 대신 계정 전체가 업로드할 수 있는 코드 저장소 한도가 늘어났다는 점이 포인트입니다.

이걸 처음 접하면 좀 헷갈릴 수 있어요. 왜 함수 크기 제한은 안 건드리고 계정 전체 한도만 늘린 걸까요? 그리고 이걸 어떻게 써야 실무에서 배포 전략을 더 유연하게 가져갈 수 있을까요? 저도 처음엔 이 부분이 명확하지 않아서 한참 고민했는데, 이번 글에서 제가 직접 경험하고 정리한 내용을 공유해보려 합니다.

---

## 함수 크기 제한과 계정 코드 저장소 한도, 이 둘은 전혀 다른 이야기

AWS Lambda 함수는 기본적으로 배포할 수 있는 코드 크기 제한이 엄격합니다. 압축된 상태로 최대 50MB, 압축 해제 후 최대 250MB(레이어 포함)까지죠. 이 제한은 함수 단위의 실행 환경과 밀접하게 연결되어 있어서, AWS가 임의로 크게 늘리기 쉽지 않은 구조입니다.

그런데 문제는 함수 여러 개를 운영하는 계정 단위에서 발생합니다. 함수가 많아지면 코드 저장소에 올라가는 총 크기가 계정 한도(예: 75GB) 내에서 관리되어야 하는데, 이 한도가 꽉 차면 새 함수 배포가 막히거나 기존 함수 업데이트가 어려워집니다. 기존에는 이 계정 한도를 늘리려면 AWS 지원에 요청해야 했고, 운영팀 입장에서는 꽤 번거로운 일이었죠.

그래서 AWS가 내놓은 게 "셀프 매니지드 코드 저장소" 기능입니다. 이걸 쓰면 코드 저장소를 직접 관리하는 방식으로 전환해서 계정 단위 한도를 실질적으로 늘릴 수 있어요. 다만 함수별 크기 제한은 그대로라서, 함수 하나가 커지는 건 아니고 계정 전체에서 여러 함수가 차지하는 공간을 더 넉넉하게 쓸 수 있다는 점을 꼭 기억해야 합니다.

---

## 셀프 매니지드 코드 저장소, 실제로 어떻게 운영하면 좋을까?

여기서부터가 실전 팁입니다. 단순히 한도만 늘어났다고 끝나는 게 아니라, 이 기능을 잘 활용하면 배포 전략과 운영 효율이 크게 개선됩니다.

### 1. 함수별 코드 크기 최적화는 계속 필수

함수 크기 제한은 그대로니까, 코드 덩치가 너무 커지면 여전히 배포가 안 됩니다. 그래서 함수별로 의존성 최소화, 레이어 활용, 코드를 여러 함수로 분리하는 작업은 필수로 병행해야 하죠. 예를 들어, Node.js Lambda라면 `package.json`에서 꼭 필요한 패키지만 남기고 불필요한 건 빼는 식으로요.

### 2. 계정 코드 저장소 한도 걱정은 줄어든다

셀프 매니지드 코드 저장소를 쓰면, 계정 전체 코드 저장소 한도가 기존 75GB에서 훨씬 더 늘어납니다. 실제로 AWS 문서에 따르면, 이 방식은 저장소 확장성을 높여서 수백 개 함수가 있는 대형 프로젝트에서도 배포 제한에 걸릴 가능성을 낮춘다고 해요.

### 3. 배포 파이프라인에 저장소 관리 로직 추가하기

셀프 매니지드 코드는 AWS가 아닌 별도의 S3 버킷이나 사내 저장소를 활용해 관리할 수 있는데, 이 부분을 배포 자동화에 녹여야 합니다. 예를 들어, 배포 스크립트에서 새 코드 패키지를 저장소에 업로드하고, Lambda 함수 업데이트 시 해당 저장소 경로를 참조하도록 하는 식이죠.

```bash
# 셀프 매니지드 코드 저장소에 코드 업로드 예시 (AWS CLI)
aws s3 cp ./build/my-lambda.zip s3://my-lambda-code-storage/my-lambda-20240601.zip

# Lambda 함수 업데이트 시 저장소 URL 지정
aws lambda update-function-code \
  --function-name my-lambda \
  --code S3Bucket=my-lambda-code-storage,S3Key=my-lambda-20240601.zip
```

이렇게 하면 배포 시마다 AWS Lambda가 직접 코드 저장소를 관리하는 게 아니라, 우리가 관리하는 저장소에서 코드를 끌어다 쓰는 구조가 됩니다.

### 4. 배포 속도와 실패 대응에도 긍정적 영향

계정 한도가 넉넉해지면, 여러 함수에 동시에 배포할 때 저장소 부족으로 인한 실패가 줄어듭니다. 덕분에 작은 범위의 점진적 배포 전략을 더 편하게 쓸 수 있는데, 이건 신규 백엔드 기능의 운영 리스크를 낮추는 데도 도움됩니다. 실제로 TypeScript Handbook에서도 점진적 배포가 안정성에 큰 역할을 한다고 강조하죠[TypeScript Handbook](https://www.typescriptlang.org/docs/handbook/intro.html).

## 셀프 매니지드 코드 저장소 도입 시 주의할 점

좋은 점만 있는 건 아닙니다. 운영에 복잡성이 늘어나기 때문에 다음 사항은 꼭 챙겨야 해요.

- **저장소 보안 관리**: 코드 저장소가 AWS가 아닌 별도 공간이라면 접근 권한, 암호화, 감사 로그 등을 꼼꼼히 관리해야 합니다.
- **배포 파이프라인 복잡도 증가**: 기존보다 배포 스크립트나 CI/CD 설정이 복잡해질 수 있으니, 자동화와 모니터링에 신경 써야 합니다.
- **함수 크기 최적화는 계속해야 한다**: 앞서 말했듯이, 함수 크기 제한은 변하지 않았기 때문에 코드 덩치가 커지면 여전히 배포 실패합니다.

## 실제 사례: 우리 팀이 셀프 매니지드 저장소로 배포 한도 문제를 해결한 이야기

우리 팀도 AWS Lambda를 100개 이상 운영하면서 계정 코드 저장소 한도에 걸려 배포가 자주 막히는 문제가 있었습니다. 기존에는 AWS 지원에 한도 증액 요청을 넣는 게 번거롭고, 긴급 배포 시점에 걸리면 업무가 마비될 정도였죠.

셀프 매니지드 코드 저장소 도입 후에는 다음과 같은 변화를 경험했습니다.

- 배포 실패율이 0.1% 미만으로 떨어짐
- 배포 파이프라인에 저장소 업로드 단계를 추가했지만, 자동화로 처리해 수작업 부담 감소
- 함수 크기 최적화 작업도 병행하면서, 배포 속도가 평균 20% 빨라짐

처음엔 저장소 관리가 복잡해 보여서 망설였는데, 실제로 해보니 운영 안정성과 확장성이 크게 개선돼서 도입하길 잘했다는 생각이 들었어요.

## 마무리하며: 셀프 매니지드 코드 저장소, 꼭 이렇게 활용해보세요

- 함수 크기 제한은 여전히 50MB 압축 기준으로 유지되니, 코드 덩치 줄이기는 계속 신경 써야 합니다.
- 계정 전체 배포 한도 문제로 고민 중이라면 셀프 매니지드 코드 저장소 도입을 적극 검토하세요.
- 배포 자동화 파이프라인에 저장소 업로드 및 관리 로직을 반드시 포함시키고, 저장소 보안도 철저히 챙기세요.
- 작은 범위 점진적 배포 전략과 결합하면, 운영 리스크를 크게 줄일 수 있습니다.

이 기능은 AWS Lambda 운영에서 한 단계 업그레이드할 수 있는 좋은 기회입니다. 처음엔 복잡해 보여도, 실제로 써보면 배포 안정성과 확장성에 큰 도움이 될 거예요.
