### "왜 재시도 로직이 또 실패하면 안 될까?"

최근에 우리 서비스에서 외부 API 호출 실패가 잦아지면서, 재시도 전략이 제대로 동작하지 않는다는 걸 발견했어요. 재시도 횟수를 무작정 늘리다 보니 오히려 부하가 커지고, 중복 요청으로 인한 문제도 발생했죠. 이걸 해결하려면 단순히 횟수만 조절하는 게 아니라, 재시도 정책 전반을 꼼꼼히 설계해야 한다는 걸 깨달았습니다. 

이번에 나온 Spring Retry 2.0.13 버전이 딱 그런 고민에 답을 줄 수 있을까 해서 직접 업그레이드하고, 세밀하게 튜닝해봤어요. 실제로 어떤 점이 달라졌고, 어떻게 적용해야 프로덕션에서 안정적인 재시도 메커니즘을 만들 수 있는지 이야기해볼게요.

---

## Spring Retry 2.0.13, 뭐가 달라졌길래 주목할까?

이번 2.0.13 버전은 마이너 업데이트 같지만, 예외 처리와 재시도 정책 구성에서 꽤 중요한 개선이 있었습니다. 공식 문서에 따르면, 예외 유형별로 재시도 여부를 더 정교하게 구분할 수 있고, 정책을 조합하는 방식도 유연해졌어요. 특히 프로덕션 환경에서 점진적 롤아웃과 모니터링을 함께 권장하는 점이 눈에 띄더군요[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

이전 버전에서는 재시도 정책을 단순히 횟수와 고정 딜레이 중심으로만 설정했는데, 2.0.13부터는 백오프 전략, 예외 필터링, 멱등성 보장 등 다양한 옵션을 조합해 실제 상황에 맞는 맞춤형 재시도 로직을 만들기 쉬워졌습니다.

## 내 서비스에 맞는 재시도 정책, 어떻게 설계해야 할까?

재시도 로직은 단순히 "몇 번 더 해보자"가 아니라, 실패 원인과 서비스 특성에 따라 달라져야 해요. 예를 들어, 네트워크 일시 장애라면 빠른 재시도가 효과적이지만, 인증 실패 같은 경우 재시도 자체가 무의미하니까요.

Spring Boot 공식 문서에서는 재시도 횟수, 지연 시간, 예외 유형별 재시도 설정 등 다양한 튜닝 옵션을 제공한다고 명시합니다. 이를 활용하면 백엔드 서비스 내구성을 크게 높일 수 있죠[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

### 재시도 정책 예시 코드

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.retry.backoff.ExponentialBackOffPolicy;
import org.springframework.retry.policy.SimpleRetryPolicy;
import org.springframework.retry.support.RetryTemplate;

import java.util.Collections;

@Configuration
public class RetryConfig {

    @Bean
    public RetryTemplate retryTemplate() {
        RetryTemplate retryTemplate = new RetryTemplate();

        // 최대 5회 재시도, IOException과 TimeoutException에만 재시도
        SimpleRetryPolicy retryPolicy = new SimpleRetryPolicy(5, 
            Collections.singletonMap(java.io.IOException.class, true));
        retryTemplate.setRetryPolicy(retryPolicy);

        // 지연 시간은 500ms에서 시작해 최대 5초까지 지수 백오프
        ExponentialBackOffPolicy backOffPolicy = new ExponentialBackOffPolicy();
        backOffPolicy.setInitialInterval(500);
        backOffPolicy.setMaxInterval(5000);
        retryTemplate.setBackOffPolicy(backOffPolicy);

        return retryTemplate;
    }
}
```

이 코드는 IOException에 대해서만 최대 5회 재시도하며, 재시도 간 간격을 0.5초에서 시작해 최대 5초까지 점점 늘리는 전략을 보여줍니다. 처음엔 이게 별거 아닌 것 같지만, 실제로는 불필요한 재시도를 줄이고 시스템 자원 낭비를 막는 데 엄청 효과적이에요[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

## 재시도 메커니즘에서 놓치기 쉬운 보안과 멱등성 문제

재시도 로직을 설계할 때 보안 이슈를 간과하면 큰 낭패를 봅니다. 민감한 데이터가 재시도 과정에서 노출될 수 있고, 중복 요청으로 인한 부작용도 무시 못 하죠.

Microsoft의 재시도 패턴 문서에서는 재시도 시 멱등성 보장과 적절한 예외 분류가 필수라고 강조합니다. 즉, 재시도 대상 요청이 중복되어도 서비스 상태가 꼬이지 않도록 설계해야 한다는 뜻이에요[Microsoft - Retry pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/retry).

예를 들어, 결제 API 호출 시 재시도하다가 중복 결제가 발생하면 큰 문제입니다. 그래서 재시도 정책에선 409 Conflict 같은 중복 요청 관련 예외는 재시도하지 않도록 설정하거나, 재시도 시 고유 트랜잭션 ID를 활용해 중복 처리를 막아야 합니다.

## 프로덕션에서 안전하게 Spring Retry 2.0.13 적용하려면?

새 버전 도입은 항상 긴장되죠. 갑자기 재시도 정책이 바뀌면 예상치 못한 부하나 장애가 생길 수 있으니까요. 그래서 Spring Framework 공식 문서에선 점진적 배포와 모니터링을 병행할 것을 권장합니다.

우리 팀은 다음과 같은 단계를 거쳤어요:

1. **스테이징 환경에서 충분한 테스트** - 다양한 실패 시나리오를 만들어 재시도 정책이 의도대로 동작하는지 검증
2. **카나리 배포로 5% 트래픽만 새 정책에 노출** - 초기 문제 발견 시 빠르게 롤백 가능
3. **재시도 관련 메트릭 수집 및 알람 설정** - 재시도 횟수, 실패율, 지연 시간 등을 모니터링
4. **점차 범위 확대 후 전체 롤아웃**

이 과정에서 Spring Retry 2.0.13의 유연한 정책 설정 덕분에, 특정 예외에만 재시도 적용하거나 백오프 전략을 상황별로 조절하는 게 훨씬 수월했습니다.

## 마무리하며: 재시도 로직, "적당함"이 답이다

재시도는 백엔드 내구성 강화에 필수지만, 무조건 많이 하는 게 능사는 아닙니다. 적절한 재시도 횟수와 백오프 전략, 예외 분류, 멱등성 보장, 그리고 안전한 롤아웃 절차가 모두 맞물려야 진짜 안정적인 시스템이 만들어져요.

Spring Retry 2.0.13은 이런 요구사항을 충족시키기 위한 여러 기능 개선을 담고 있어, 실무에서 꼭 한번 업그레이드해 볼 만합니다. 다만, 새 기능을 무작정 다 켜기보단 우리 서비스 특성에 맞게 튜닝하는 게 관건이죠.

오늘 소개한 정책 설계 팁과 코드 예시, 그리고 점진적 배포 전략이 여러분 백엔드 재시도 로직 개선에 도움이 되길 바랍니다.
