## 갑자기 프로덕션에서 튜닝이 필요해졌을 때, Spring 3.2가 준 선물

얼마 전 우리 팀에서 갑자기 프로덕션 서비스의 응답 시간이 불안정해지는 문제가 발생했어요. 원인을 찾으려던 찰나에 Spring Boot 3.2에서 새로 도입된 메트릭 수집 기능과 커스텀 모니터링 API가 큰 도움이 됐죠. 기존에는 APM 도구에만 의존했는데, 이제는 애플리케이션 내부에서 실시간으로 다양한 메트릭을 수집하고, 커스텀하게 모니터링할 수 있어서 문제 탐지가 훨씬 수월해졌습니다.

실제로 3.2 버전부터는 Micrometer 기반의 메트릭이 확장돼서 JVM 힙 메모리 사용량, GC 빈도뿐 아니라 스레드 풀 상태, HTTP 요청 처리 시간 등 세밀한 지표를 직접 노출할 수 있어요. 우리 서비스에서는 다음과 같이 간단한 커스텀 메트릭을 추가해서 특정 API의 처리 시간을 추적했습니다.

```java
@Bean
public MeterBinder customApiTimer() {
    return registry -> {
        Timer timer = Timer.builder("custom.api.timer")
            .description("Custom API 처리 시간")
            .register(registry);

        // 예를 들어 AOP로 감싸서 사용
    };
}
```

이걸 통해 문제 구간을 빠르게 좁힐 수 있었고, 실시간으로 모니터링 대시보드에 반영돼 운영팀과 개발팀 모두 빠르게 대응할 수 있었죠. 물론 이런 메트릭 수집은 약간의 오버헤드가 있으니, 프로덕션에서는 샘플링 비율을 적절히 조절하는 게 필수입니다.

[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)에서 자세한 설정법과 권장값을 확인할 수 있어요.

## OAuth 2.1과 CSRF 기본 활성화, 보안 설정이 이렇게 쉬워졌다니

Spring Framework 6.1로 업그레이드하면서 가장 반가웠던 점 중 하나는 보안 기능 강화였어요. 특히 OAuth 2.1 지원이 기본으로 들어오면서, 기존에 직접 커스텀하던 인증 흐름이 훨씬 깔끔해졌습니다. 그리고 CSRF 보호가 기본 활성화되어 있어서, "아차" 하는 순간 발생할 수 있는 보안 취약점을 미연에 방지할 수 있었죠.

예를 들어, 이전에는 POST 요청에 CSRF 토큰을 직접 넣고 검증하는 로직을 신경 써야 했는데, 6.1부터는 `SecurityFilterChain` 설정만 잘 해주면 기본적으로 CSRF가 활성화됩니다. 아래는 OAuth 2.1 로그인과 CSRF 보호를 함께 설정한 예시입니다.

```java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(authz -> authz
            .requestMatchers("/public/**").permitAll()
            .anyRequest().authenticated()
        )
        .oauth2Login(withDefaults())
        .csrf(csrf -> csrf
            .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
        );
    return http.build();
}
```

또한, 권한 부여 부분도 세밀하게 설정할 수 있어서, 특정 API별로 권한을 다르게 주거나, 조건부 권한 검사를 쉽게 할 수 있었습니다. 이건 실제로 써보면 얼마나 편한지 바로 체감될 겁니다.

보안 설정은 항상 까다로운데, 이번 6.1 버전은 기본값이 보안에 더 안전하게 맞춰져 있어서 초기 설정 부담이 확 줄었어요. 자세한 내용은 [Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)에서 확인하세요.

## JVM 힙 조정부터 캐시 전략까지, Baeldung이 추천하는 프로덕션 튜닝 팁

성능 문제는 언제나 골치 아픈데, Baeldung에서 정리한 Spring Boot 성능 튜닝 가이드가 큰 도움이 됐습니다. 특히 JVM 힙 메모리 설정, 스레드 풀 최적화, 그리고 캐시 활용 전략을 구체적으로 다뤄서 우리 팀도 바로 적용해봤어요.

가장 먼저 JVM 힙 메모리를 서비스 특성에 맞게 조정했는데, 기본 512MB에서 2GB로 늘리고, GC 옵션도 `-XX:+UseG1GC`로 바꾸니 메모리 부족으로 인한 GC 지연이 크게 줄었습니다. 그리고 스레드 풀은 기본 설정에서 최소 10, 최대 50으로 조절했는데, 이게 CPU 코어 수와 요청 패턴에 딱 맞더군요.

캐시는 Spring Cache 추상화를 활용해 Redis를 백엔드로 쓰면서 TTL(Time To Live)을 5분으로 설정했는데, 이걸로 DB 부하가 30% 이상 감소했습니다. 다음은 캐시 설정 예시입니다.

```java
@Configuration
@EnableCaching
public class CacheConfig {

    @Bean
    public CacheManager cacheManager(RedisConnectionFactory redisConnectionFactory) {
        RedisCacheConfiguration cacheConfig = RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(5))
            .disableCachingNullValues();

        return RedisCacheManager.builder(redisConnectionFactory)
            .cacheDefaults(cacheConfig)
            .build();
    }
}
```

하지만 튜닝은 항상 트레이드오프가 있죠. 힙을 너무 크게 하면 GC가 길어지고, 스레드 풀을 너무 크게 하면 컨텍스트 스위칭 비용이 늘어납니다. 그래서 프로덕션 롤아웃 전에 충분한 부하 테스트를 꼭 해야 합니다. Baeldung 가이드가 이 부분을 특히 강조하니 [Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance)에서 자세히 참고하세요.

## 다운타임 없이 배포하려면? GitHub에서 배운 점진적 롤아웃 전략

서비스를 운영하다 보면 배포가 가장 긴장되는 순간인데, GitHub 엔지니어링 블로그에서 소개한 Canary 배포와 블루-그린 배포 전략이 우리 팀에 딱 맞았습니다. 이 두 가지 방식을 적절히 섞어서 사용하면, 사용자에게 영향을 최소화하면서 새 버전을 안전하게 배포할 수 있더군요.

예를 들어, Canary 배포는 전체 트래픽 중 5%만 새 버전으로 보내고 모니터링하다가 문제가 없으면 점차 비율을 늘리는 방식입니다. 블루-그린 배포는 두 개의 동일한 환경(블루와 그린)을 두고, 트래픽을 한쪽에서 다른 쪽으로 스위칭하는 방법이죠.

우리 팀은 다음과 같은 스크립트를 통해 Kubernetes 환경에서 Canary 배포를 자동화했습니다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-canary
spec:
  replicas: 1 # 전체 10대 중 1대만 Canary
  template:
    metadata:
      labels:
        version: canary
    spec:
      containers:
      - name: myapp
        image: myapp:2.0-canary
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp-ingress
spec:
  rules:
  - http:
      paths:
      - path: /
        backend:
          service:
            name: myapp-service
            port:
              number: 80
        # 트래픽 비율 조절은 Ingress 컨트롤러 설정으로
```

이렇게 하면 Canary 인스턴스에만 일부 트래픽이 가고, 문제가 없으면 레플리카 수를 늘려 전체로 확장합니다. 물론 모니터링과 롤백 체계가 반드시 뒷받침되어야 하죠.

더 자세한 사례와 전략은 [GitHub Engineering Blog](https://github.blog/category/engineering/)에서 확인할 수 있습니다.

### 마무리하며

이번 주에 직접 써본 Spring Boot 3.2와 Spring Framework 6.1의 변화는 "실제 운영 환경에서 얼마나 편해질까" 하는 기대를 충족시켜줬어요. 메트릭 수집과 보안 강화는 기본 중의 기본인데, 이번 버전들은 그걸 훨씬 더 쉽게 만들어줬고, 성능 튜닝 가이드와 점진적 롤아웃 전략까지 더해지니 프로덕션 운영이 한결 안정적이 됐습니다.

다만, 모든 기능이 만능은 아니니 실제 서비스 특성에 맞춰 적절히 조합하고, 충분한 테스트와 모니터링을 병행하는 게 중요합니다. 여러분도 이번 기회에 최신 스프링 기능을 한 번 더 점검해보시고, 운영 환경에 맞게 꼭 맞는 세팅을 찾아보시길 권합니다.
