## 페이지가 통째로 리로딩되는 순간, 사용자 경험은 왜 망가질까?

웹 개발하면서 이런 경험 한 번쯤 있죠? 버튼 클릭했는데 페이지가 깜빡이며 통째로 다시 로딩되고, 그 사이에 뭔가 어색한 깜빡임이나 지연이 느껴지는 순간. 특히 대형 SPA에서도 라우팅이 복잡해지면 이런 현상이 잦아지곤 합니다. 이걸 해결하려고 React Router 같은 라이브러리를 쓰고, 상태 관리 라이브러리를 도입하는데도 한계가 있더라고요.

최근에 Navigation API가 Baseline으로 새롭게 지원되면서, 이 문제를 네이티브 브라우저 차원에서 해결할 수 있게 됐습니다. 이건 단순히 SPA 라우팅 라이브러리 업그레이드가 아니라, 브라우저가 직접 "필요한 부분만 바꿔치기"하는 내비게이션 방식을 제공하는 거라서 꽤 신선했어요.


## Navigation API, 왜 기존 SPA 라우팅과 다를까?

기존 SPA 라우팅은 자바스크립트가 URL 변화를 감지해서 적절한 컴포넌트를 렌더링하는 방식이었죠. 하지만 이 과정에서 상태 관리가 복잡해지고, 초기 로딩 때 필요한 리소스가 많아지거나, 페이지 간 전환 시 불필요한 재렌더링이 발생하는 문제가 있었습니다.

Navigation API는 브라우저 내장 API를 활용해 페이지 전환 시 전체 페이지를 다시 불러오지 않고, 필요한 리소스와 DOM만 갱신합니다. 즉, 네트워크 요청과 렌더링을 브라우저가 직접 최적화해 주는 거죠. GitHub Engineering Blog에서도 "Navigation API는 페이지 리로딩 없이 필요한 부분만 갱신하여 성능과 UX를 크게 개선한다"고 언급했는데, 실제로 써보니 체감이 확실했습니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

Cloudflare 사례를 보면, Navigation API 도입 후 네트워크 요청 최적화와 캐시 활용이 눈에 띄게 좋아져 사용자 반응 속도가 빨라지고 내비게이션이 훨씬 부드러워졌다고 해요. 이런 점에서 Navigation API는 단순한 기술 변화가 아니라 프론트엔드 성능 최적화의 새로운 기준이 될 가능성이 큽니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).


## 컴포넌트 기반 구조에서 Navigation API를 활용하는 실전 팁

대규모 애플리케이션에서는 상태 관리와 렌더링 분리가 필수인데요, Martin Fowler도 Navigation API를 활용하면 이 두 가지를 효과적으로 분리할 수 있어 유지보수성과 확장성이 높아진다고 강조합니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

예를 들어, 페이지 전환 시 상태는 별도의 전역 상태 관리 라이브러리(예: Redux, Zustand)에 맡기고, Navigation API로 페이지 전환 이벤트를 감지해 필요한 컴포넌트만 새로 렌더링하는 구조를 생각해볼 수 있습니다. 이렇게 하면 불필요한 전체 리렌더링을 막고, 상태도 꼼꼼히 관리할 수 있죠.

```js
// Navigation API를 활용한 간단한 페이지 전환 핸들러 예시
// SPA 라우터와 달리 브라우저 내비게이션 이벤트를 직접 다룹니다.

if ('navigation' in window) {
  window.navigation.addEventListener('navigate', event => {
    event.intercept({
      async handler() {
        // 새 URL에서 필요한 데이터만 fetch
        const response = await fetch(event.destination.url);
        const html = await response.text();

        // 필요한 부분만 DOM에 업데이트
        const parser = new DOMParser();
        const doc = parser.parseFromString(html, 'text/html');
        const newContent = doc.querySelector('#app-root');

        document.querySelector('#app-root').replaceWith(newContent);

        // 상태 업데이트 또는 컴포넌트 재렌더링 로직 추가 가능
      }
    });
  });
} else {
  console.warn('Navigation API가 지원되지 않는 브라우저입니다.');
}
```

이 코드는 `navigate` 이벤트를 가로채서 fetch로 새 페이지 HTML을 가져온 뒤, `#app-root` 부분만 교체하는 간단한 예입니다. SPA 라우터처럼 복잡한 상태 관리 없이도 자연스러운 페이지 전환 효과를 낼 수 있죠. 물론, 상태 관리가 필요한 부분은 별도로 연결해줘야 하고, SEO나 접근성도 신경 써야 합니다.


## 실제 도입 시 고려해야 할 점들

처음엔 이게 별거 아닌 것처럼 보여도, 실제로 적용해보면 몇 가지 트레이드오프가 있더라고요.

- **브라우저 지원 범위**: 아직 모든 브라우저가 Navigation API를 완벽히 지원하는 건 아닙니다. 따라서 폴리필이나 대체 로직을 준비해야 하죠.

- **상태 동기화 문제**: 페이지 일부만 교체하다 보면 상태가 꼬일 위험이 있습니다. 특히 폼 입력값, 스크롤 위치 같은 UI 상태는 별도 관리가 필요합니다.

- **SEO와 접근성**: SPA처럼 클라이언트 사이드 렌더링이 많아지면 SEO가 약해질 수 있는데, Navigation API는 서버에서 완전한 HTML을 받아오기 때문에 이 부분은 오히려 개선될 가능성도 있습니다. 다만, 서버가 반드시 완전한 페이지를 제공해야 하니 백엔드와의 협업이 필수입니다.

- **기존 라우팅 라이브러리와의 충돌**: React Router나 Vue Router 같은 기존 라우팅 라이브러리와 함께 쓸 때는 이벤트 중복 처리나 상태 관리 충돌을 주의해야 합니다.


## Navigation API, 앞으로 어떻게 활용할까?

이 기술은 단순히 "빠른 페이지 전환"을 넘어서, 프론트엔드 아키텍처 전반에 영향을 줄 수 있는 잠재력을 가지고 있어요. 예를 들어, 컴포넌트 단위로 필요한 리소스만 부분적으로 업데이트하는 전략과 결합하면, 대규모 애플리케이션도 훨씬 가볍고 반응성 좋게 만들 수 있겠죠.

또한, 네이티브 브라우저 API를 활용하기 때문에 라이브러리 의존도를 줄이고, 코드 복잡도를 낮출 수 있다는 점도 매력적입니다. 물론 아직은 초기 단계라 문서나 사례가 많지 않지만, GitHub과 Cloudflare 같은 대형 서비스가 이미 도입해 효과를 보고 있으니 곧 더 많은 프로젝트에서 채택될 것 같아요.
