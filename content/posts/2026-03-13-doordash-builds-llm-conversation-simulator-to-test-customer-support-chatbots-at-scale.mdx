## 고객 지원 챗봇, 진짜 고객과 대화해보지 않고 어떻게 테스트할까?

"우리 챗봇, 고객 문의에 잘 대응할까?" 이 질문, 실제 운영에 들어가기 전엔 참 막막하죠. DoorDash가 겪은 고민도 비슷했습니다. 고객 지원 챗봇이 수많은 고객 문의 유형을 제대로 처리하는지, 예기치 않은 대화 흐름에서도 튕기지 않고 잘 작동하는지 검증하려면 실제 대화 데이터를 대량으로 확보해야 하는데, 현실적으로 쉽지 않거든요.

그래서 DoorDash는 대규모 언어 모델(LLM)을 활용해 ‘대화 시뮬레이터’를 직접 만들었습니다. 이 시뮬레이터는 사람과 비슷한 고객 역할을 자동으로 생성해 챗봇과 수천, 수만 건의 대화를 시뮬레이션하죠. 덕분에 챗봇의 문제점을 조기에 발견하고, 개선 주기를 빠르게 돌릴 수 있었습니다.

오늘은 이 DoorDash 대화 시뮬레이터를 벤치마크 삼아, 어떻게 LLM 기반 시뮬레이터를 백엔드에서 설계하고 확장할 수 있는지, 그리고 실제 적용 시 고려할 점들을 이야기해보겠습니다.

---

## LLM으로 대화 시뮬레이터를 만드는 핵심은 ‘프롬프트 설계’

LLM을 쓰는 건 이제 흔한 일이 됐지만, 좋은 대화 시뮬레이터를 만들려면 단순히 모델 호출만으로는 부족합니다. Anthropic의 프롬프트 엔지니어링 가이드가 강조하는 것처럼, ‘대화의 자연스러움’과 ‘맥락 유지’, 그리고 ‘다양한 고객 문의 유형 반영’이 관건입니다.[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)

예를 들어, 고객이 주문 지연, 환불 요청, 메뉴 변경 등 여러 상황을 다양하게 제시할 수 있어야 하죠. 프롬프트에 이런 시나리오를 구체적으로 명시하고, 모델이 이전 대화 내용을 기억하며 자연스럽게 응답하도록 유도하는 설계가 필요합니다.

아래는 간단한 프롬프트 예시입니다:

```typescript
const prompt = `
You are a customer who just placed a food delivery order.
Simulate a conversation with a support chatbot where you ask about a delayed order.
Respond naturally and include possible follow-up questions.

Chatbot: Hello! How can I assist you today?
Customer:`;

// OpenAI API 호출 예시
const response = await openai.chat.completions.create({
  model: "gpt-4o-mini",
  messages: [{ role: "system", content: prompt }],
  max_tokens: 150,
  temperature: 0.7,
});

console.log(response.choices[0].message.content);
```

이런 프롬프트를 다양하게 조합해 시뮬레이터가 여러 고객 유형과 상황을 흉내 내도록 합니다. OpenAI API 문서에서도 LLM을 활용해 대화 시나리오 생성과 시뮬레이션하는 방법을 자세히 다루고 있으니 참고하면 좋습니다.[OpenAI API Documentation](https://platform.openai.com/docs/overview)


## 백엔드에서 LLM 시뮬레이터를 대량으로 돌릴 때 고려해야 할 인프라 이야기

DoorDash처럼 수천, 수만 건의 대화를 동시에 시뮬레이션하려면 단순 API 호출 이상의 인프라 설계가 필요합니다. Cloudflare가 자사 블로그 ‘How We Built It’ 시리즈에서 설명한 것처럼, 클라우드 인프라 구성과 성능 최적화가 핵심입니다.[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/)

예를 들어, 다음과 같은 점들을 신경 써야 하죠:

- **병렬 처리와 큐잉**: LLM API 호출은 비용과 지연시간이 크기 때문에, 호출을 병렬화하되 API rate limit을 넘지 않도록 큐잉 시스템을 둡니다.
- **캐싱과 재사용**: 동일 시나리오에 대해 반복 호출을 줄이기 위해 응답을 캐싱하거나, 시뮬레이션 결과를 저장해 재사용합니다.
- **오토스케일링**: 부하에 따라 시뮬레이터 인스턴스를 자동으로 늘리고 줄여 비용 효율성을 확보합니다.
- **모니터링과 로깅**: 실패한 시뮬레이션이나 이상 응답을 빠르게 감지해 대응할 수 있게 로그와 메트릭을 꼼꼼히 수집합니다.

이런 인프라 설계는 DoorDash뿐 아니라 우리도 고객 지원 챗봇 테스트를 대규모로 하려면 꼭 참고할 만합니다.


## TypeScript 5.x로 유지보수성과 확장성 챙기기

대화 시뮬레이터 백엔드 코드는 복잡해지기 쉽고, 여러 API 호출과 비동기 처리가 얽혀 있습니다. 여기서 TypeScript 5.x의 최신 기능들이 큰 도움이 됩니다.[TypeScript 5.x Release Notes](https://devblogs.microsoft.com/typescript/announcing-typescript-5-4/)

- **`satisfies` 연산자**: 타입 안전성을 높이면서도 유연한 타입 선언이 가능해, 다양한 대화 시나리오 타입을 깔끔하게 관리할 수 있습니다.
- **성능 개선**: 대규모 코드베이스에서 컴파일 속도가 개선돼 개발 생산성이 올라갑니다.
- **ESM 지원 강화**: 모듈화를 더 쉽게 해 마이크로서비스 아키텍처에 적합합니다.

예를 들어, 시뮬레이터에서 다루는 고객 문의 유형을 타입으로 선언할 때 `satisfies`를 활용할 수 있죠:

```typescript
const customerQueries = [
  { type: "order_delay", example: "내 주문이 왜 아직 안 왔나요?" },
  { type: "refund", example: "환불은 어떻게 받나요?" },
  { type: "menu_change", example: "주문한 메뉴를 바꾸고 싶어요." },
] as const satisfies ReadonlyArray<{ type: string; example: string }>;
```

이런 타입 선언 덕분에 시뮬레이터 로직에서 실수로 잘못된 타입을 넣는 걸 컴파일 타임에 잡아낼 수 있습니다.


## DoorDash가 선택한 모듈화 아키텍처, 우리도 써볼만 할까?

GitHub 엔지니어링 블로그에서는 대규모 시스템에서 LLM 통합을 위해 모듈화와 마이크로서비스 패턴을 활용하는 사례를 소개합니다.[GitHub Engineering Blog](https://github.blog/category/engineering/)

DoorDash도 이와 비슷하게 시뮬레이터를 여러 서비스로 분리했는데요, 예를 들면:

- **프롬프트 생성 서비스**: 다양한 고객 시나리오별로 프롬프트를 생성
- **LLM 호출 서비스**: OpenAI나 Anthropic API를 호출해 응답 생성
- **대화 로그 저장 서비스**: 시뮬레이션 결과를 DB에 저장 및 분석

이렇게 역할을 분리하면 각 컴포넌트를 독립적으로 확장하거나 교체하기 쉬워집니다. 예를 들어, LLM 모델이 바뀌어도 호출 서비스만 수정하면 되고, 프롬프트 변경은 별도 서비스에서 관리할 수 있죠.

하지만 단점도 있습니다. 서비스 간 통신 비용과 복잡도가 늘어나고, 분산 트랜잭션 관리가 까다로워질 수 있습니다. 따라서 팀 규모와 운영 환경에 맞게 적절히 조율해야 합니다.

## 직접 써보는 간단한 LLM 대화 시뮬레이터 백엔드 예시

마지막으로 TypeScript 환경에서 OpenAI API를 호출해 대화 시뮬레이터를 구현하는 아주 기본적인 예시를 보여드릴게요.

```typescript
import OpenAI from "openai";

const openai = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });

interface ConversationTurn {
  role: "user" | "assistant";
  content: string;
}

async function simulateConversation(scenarioPrompt: string): Promise<void> {
  const messages: ConversationTurn[] = [
    { role: "system", content: scenarioPrompt },
    { role: "user", content: "안녕하세요, 주문이 아직 도착하지 않았어요." },
  ];

  for (let i = 0; i < 3; i++) {
    const response = await openai.chat.completions.create({
      model: "gpt-4o-mini",
      messages: messages.map(m => ({ role: m.role, content: m.content })),
      max_tokens: 100,
      temperature: 0.8,
    });

    const assistantReply = response.choices[0].message.content;
    console.log(`Assistant: ${assistantReply}`);

    // 고객 역할 시뮬레이션 (간단히 반복)
    messages.push({ role: "assistant", content: assistantReply });
    messages.push({ role: "user", content: "더 궁금한 게 있어요." });
  }
}

simulateConversation("고객이 주문 지연에 대해 문의하는 시나리오입니다.");
```

이 코드는 시나리오 프롬프트를 주고, 고객과 챗봇 역할을 번갈아 가며 3턴 대화를 생성합니다. 실제로는 여기에 다양한 시나리오와 실패 케이스, 병렬 실행 로직, 로깅 등을 추가해야겠죠.

DoorDash 사례에서 보듯, LLM 대화 시뮬레이터는 고객 지원 챗봇 품질을 높이는 데 강력한 도구입니다. 하지만 좋은 프롬프트 설계, 확장 가능한 인프라, 타입 안정성 확보, 그리고 적절한 아키텍처 선택이 모두 맞물려야 실무에 성공적으로 적용할 수 있죠.

이 글에서 다룬 내용을 바탕으로, 여러분도 직접 대화 시뮬레이터를 만들어보고, 우리 서비스에 맞게 확장해보시길 추천합니다.
