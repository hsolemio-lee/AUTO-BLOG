## "내가 쓰는 보안 도구가 공격받는다면?" - Trivy 공급망 공격 사건

최근 오픈소스 보안 스캐너인 Trivy가 공급망 공격에 노출됐다는 소식이 퍼지면서, "내가 믿고 쓰던 도구도 뚫릴 수 있구나" 하는 생각이 들었어요. Trivy는 컨테이너 이미지 취약점 검사에 널리 쓰이는 툴인데, 공격자는 업데이트 서버를 타깃으로 해 악성 코드를 배포했다고 합니다. 이 사건은 단순한 취약점 노출이 아니라, 개발자가 직접 쓰는 도구 자체가 공격 벡터가 될 수 있다는 점에서 충격적이었죠.


## Trivy 공급망 공격, 어떻게 일어났나?

Trivy는 Aqua Security에서 개발한 오픈소스 취약점 스캐너로, Docker 이미지, 파일 시스템, 깃 저장소 등 다양한 소스의 취약점을 검사합니다. 이번 공격은 Trivy가 취약점 DB를 업데이트하는 과정에서 악성 데이터가 주입된 게 핵심입니다. 공격자는 업데이트 서버를 해킹해 악성 페이로드를 포함한 DB를 배포했고, 이걸 내려받은 사용자의 시스템에 악영향을 끼쳤죠.

사실 이런 공급망 공격은 최근 들어 점점 빈번해지고 있습니다. 오픈소스 생태계가 복잡해지고, 많은 도구가 자동화된 업데이트를 쓰다 보니 공격자가 한 군데만 뚫어도 광범위한 피해를 낼 수 있거든요.


## 백엔드 엔지니어가 당장 점검해야 할 부분들

이 사건을 보면서 우리 백엔드 팀에서 당장 점검해야 할 부분이 몇 가지 떠올랐어요.

### 1. 외부 도구와 라이브러리 신뢰성 검증

Trivy 같은 도구는 편리하지만, 자동 업데이트를 무조건 신뢰하면 안 됩니다. 특히 공급망 공격이 의심되는 상황이라면 다음과 같은 조치가 필요해요.

- **서명 검증**: 업데이트 파일이나 바이너리가 공식 서명으로 검증되는지 확인
- **고정 버전 사용**: 자동 최신 버전 대신, 검증된 특정 버전만 사용
- **의심스러운 변경 감지**: 업데이트 내역과 해시값을 비교해 이상 징후 탐지

### 2. 점진적 배포 전략 적용

신규 백엔드 기능이나 업데이트를 한꺼번에 다 밀어넣기보다, 작은 범위로 점진적으로 배포하는 게 리스크를 줄입니다. 예를 들어, 전체 서버 중 5%에만 먼저 배포해 문제 발생 시 빠르게 롤백할 수 있죠. 이런 점진적 배포는 OpenAI 문서에서도 운영 리스크 감소에 효과적이라고 명시돼 있습니다[OpenAI API Documentation](https://platform.openai.com/docs/overview).

### 3. 실패 유형 초기 계측과 모니터링

문제가 생겼을 때 빠르게 원인을 파악하려면, 실패 유형을 미리 정의하고 계측하는 게 중요합니다. Anthropic 가이드에 따르면, 초기부터 장애 유형을 세분화해서 계측하면 유지보수성과 대응 속도가 크게 개선된다고 해요[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).


## Trivy 공급망 공격 대응을 위한 실전 팁

### 업데이트 검증 자동화 스크립트 예시

아래는 Trivy 업데이트 DB 파일의 해시를 검증하는 간단한 Bash 스크립트 예시입니다. CI/CD 파이프라인에 넣어 자동화하면, 악성 업데이트 유입을 사전에 차단할 수 있어요.

```bash
#!/bin/bash

EXPECTED_HASH="abc123def456..."  # 공식 문서에서 확인한 해시값

curl -sSL https://example.com/trivy/db.tar.gz -o db.tar.gz

ACTUAL_HASH=$(sha256sum db.tar.gz | awk '{print $1}')

if [ "$ACTUAL_HASH" != "$EXPECTED_HASH" ]; then
  echo "[ERROR] 업데이트 파일 해시 불일치! 배포 중단"
  exit 1
fi

echo "업데이트 파일 검증 완료. 안전함."
# 이후 정상 업데이트 프로세스 진행
```

이 스크립트는 해시값을 미리 알고 있어야 하므로, 공식 채널에서 신뢰할 수 있는 해시값을 반드시 확인해야 합니다. 단점은 매번 수동으로 해시값을 업데이트해야 하는 불편함이 있다는 점이에요.


### 공급망 공격에 대비하는 조직 문화

기술적 조치 외에도, 조직 차원에서 공급망 공격 대응 문화를 만드는 게 중요합니다.

- **정기적인 보안 교육**: 최신 공격 기법과 방어법 공유
- **오픈소스 사용 정책 강화**: 승인된 도구 목록 관리 및 주기적 검토
- **사고 대응 시나리오 연습**: 실제 공격 발생 시 신속 대응 훈련


## 오픈소스 보안 도구, 앞으로 어떻게 써야 할까?

이번 사건은 오픈소스 도구가 무조건 안전하지 않다는 경고입니다. 하지만 그렇다고 해서 오픈소스 사용을 멈출 수는 없죠. 대신 다음과 같은 관점으로 접근하는 게 좋습니다.

- **투명성 적극 활용**: 오픈소스는 코드가 공개돼 있어 문제 발견 시 빠른 대응이 가능
- **커뮤니티 신뢰도 확인**: 활발히 관리되는 프로젝트인지, 보안 패치가 잘 되는지 검증
- **자체 보안 레이어 추가**: 자동화된 검증 절차, 서명 확인, 모니터링 도구 도입


## 개인적으로 겪은 공급망 공격 경험과 교훈

저도 한때 CI/CD에 외부 라이브러리 자동 업데이트를 무조건 허용했다가, 어느 날 갑자기 빌드가 실패하는 사고를 겪은 적이 있어요. 원인은 악성 코드가 포함된 의존성 패키지였죠. 그때부터는 반드시 해시 검증과 점진 배포를 도입했고, 장애 유형별 모니터링도 강화했습니다. 덕분에 지금은 비슷한 문제 발생 시 10분 내에 원인 파악과 롤백이 가능해졌어요.


## 마치며: 공급망 공격, "나만 아니겠지"는 없다

Trivy 사건은 우리 모두에게 "내가 쓰는 도구도 공격받을 수 있다"는 사실을 다시 한 번 일깨워줬습니다. 백엔드 엔지니어로서, 단순히 코드를 잘 짜는 걸 넘어서 보안 관점에서 도구와 프로세스를 점검하는 게 필수입니다. 작은 점진적 배포, 실패 유형 계측, 업데이트 검증 자동화 같은 실천 가능한 전략부터 시작해보세요. 이건 실제로 겪어보면, 사고 터졌을 때 얼마나 큰 차이가 나는지 몸소 느끼게 됩니다.
