## 갑자기 Spring Shell을 다시 보게 된 이유

최근에 우리 팀에서 내부 백엔드 작업 자동화에 쓰던 CLI 툴을 좀 더 다듬고 싶다는 얘기가 나왔어요. 기존에 쓰던 Spring Shell 3.x 버전이 꽤 오래돼서, 혹시 새 버전이 나왔나 찾아보니 4.0.3과 3.4.3 버전이 동시에 릴리즈됐더라고요. “이걸로 업그레이드하면 뭐가 좋아질까?”라는 궁금증이 바로 들었죠.

실제로 써보니, 단순히 버전만 올리는 게 아니라 명령어 자동 완성이나 커스텀 명령어 등록 방식이 훨씬 직관적이고 강력해졌더군요. 백엔드 개발자로서 반복 작업을 줄이고 생산성을 올리는 데 꽤 도움이 될 것 같아 오늘은 그 경험을 공유해보려 합니다.

---

## Spring Shell 4.0.3이 3.x 대비 좋아진 점은 뭘까?

먼저 4.0.3 버전은 최신 Spring Framework와의 호환성이 크게 강화됐어요. 3.x 버전은 Spring Boot 2.x, Spring Framework 5.x와 맞춰져 있었는데, 4.0.3은 Spring Boot 3.x, Spring Framework 6.x와 완벽하게 통합됩니다. 이 덕분에 안정성도 높아지고, 스프링 생태계 내 다른 컴포넌트와 충돌 없이 매끄럽게 작동하죠[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

그리고 명령어 자동 완성 기능이 눈에 띄게 좋아졌어요. 예전에는 커맨드 입력 시 자동 완성이 제한적이었는데, 4.0.3에서는 옵션별 자동 완성도 지원하고, 커스텀 명령어를 등록할 때도 자동 완성 로직을 더 쉽게 확장할 수 있습니다. 덕분에 CLI를 자주 쓰는 개발자 입장에서 오타 걱정도 줄고, 작업 속도가 체감상 20~30%는 빨라진 느낌이에요.

마지막으로, 커스텀 명령어 구현 API가 일부 변경됐는데, 이게 처음엔 귀찮지만 적응하면 훨씬 유연한 커맨드 구성이 가능해집니다. 예를 들어, 명령어 내 파라미터 검증이나 복잡한 입력 구조를 깔끔하게 처리할 수 있죠.

## 업그레이드할 때 꼭 챙겨야 하는 의존성 관리와 호환성 체크

Spring Shell 4.x로 넘어가면서 가장 신경 써야 할 부분은 의존성 버전 관리입니다. 특히 Spring Boot 버전과 맞지 않으면 빌드 에러나 런타임 충돌이 발생할 수 있으니, `spring-boot-starter-parent` 버전과 Spring Shell 버전을 함께 맞춰야 해요.

예를 들어, Spring Boot 3.0 이상을 쓴다면 Spring Shell 4.0.3을 사용하는 게 맞고, 만약 아직 2.x를 쓰고 있다면 3.4.3 버전이 안정적입니다. 아래는 4.0.3 버전 기준 Gradle 의존성 예시입니다:

```gradle
dependencies {
    implementation 'org.springframework.shell:spring-shell-starter:4.0.3'
}
```

그리고 커스텀 명령어 작성 시에는 API 변경을 꼭 확인해야 해요. 예전에는 `@ShellMethod`만 붙이면 됐지만, 4.x부터는 명령어 옵션을 더 세밀하게 제어할 수 있는 `@ShellOption`의 속성들이 추가됐습니다. 이걸 활용하면 기본값 설정, 필수 옵션 지정, 옵션 설명까지 한 번에 관리할 수 있죠.

## 실제로 커스텀 명령어 만들어보기: 자동 완성까지 챙기기

간단한 예제로, 사용자 이름과 나이를 입력받아 인사 메시지를 출력하는 명령어를 만들어볼게요. 4.0.3 버전 기준입니다:

```java
@ShellComponent
public class UserCommands {

    @ShellMethod(value = "사용자 인사 메시지 출력", key = "greet-user")
    public String greetUser(
        @ShellOption(help = "사용자 이름", defaultValue = "Guest") String name,
        @ShellOption(help = "나이", defaultValue = "0") int age) {
        return String.format("안녕하세요, %s님! 당신의 나이는 %d살이군요.", name, age);
    }
}
```

이 코드를 등록하면 `greet-user` 명령어가 생기고, `--name`과 `--age` 옵션을 받을 수 있어요. 더 좋은 점은, 터미널에서 `greet-user --`까지 입력하면 자동 완성으로 옵션 목록이 뜬다는 겁니다. 이걸로 CLI 사용성이 훨씬 좋아지죠.

## Spring Shell을 CI/CD 파이프라인에 녹여내는 실전 팁

우리 팀에서는 Spring Shell을 빌드 자동화와 배포 스크립트 실행용 툴로도 활용 중인데요, 최신 버전은 이런 자동화 시나리오에 더 적합하게 진화했습니다. 특히, 스크립트 실행 시 환경 변수 전달, 명령어 체인 구성, 에러 핸들링이 개선돼서 파이프라인 안정성이 올라갔어요.

예를 들어, Jenkins나 GitHub Actions에서 Spring Shell 명령어를 호출할 때 이렇게 쓰면 됩니다:

```bash
java -jar my-spring-shell-app.jar greet-user --name=CI --age=1
```

이 명령어가 파이프라인 내에서 바로 실행되고, 결과를 로그로 남겨서 문제 발생 시 빠르게 원인 분석이 가능하죠. 이런 점에서 Spring Shell은 단순한 CLI 도구를 넘어 백엔드 자동화의 핵심 툴로 자리매김하고 있습니다[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

## 마치며: Spring Shell 4.x 업그레이드, 꼭 해봐야 하는 이유

처음엔 API 변경이나 의존성 문제 때문에 업그레이드가 귀찮게 느껴질 수도 있어요. 하지만 실제로 써보면 자동 완성 기능과 명령어 확장성 덕분에 개발 생산성이 눈에 띄게 올라갑니다. 특히 반복적인 백엔드 작업을 CLI로 자동화하는 팀이라면, 최신 버전으로의 전환은 선택이 아닌 필수라고 봐요.

그리고 최신 Spring Framework와의 호환성 덕분에 앞으로도 안정적인 유지보수가 가능하니, 장기적으로도 이득이 큽니다.

한 가지 팁을 더 드리자면, 업그레이드 전에 반드시 기존 커스텀 명령어 코드를 점검하고, 새 API 문서에 맞춰 옵션 처리 방식을 검토하세요. 그래야 나중에 예기치 않은 버그 없이 매끄럽게 넘어갈 수 있습니다.
