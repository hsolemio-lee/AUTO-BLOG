### "서비스 설정 바꾸려면 재시작부터 해야 한다고? 그거 너무 비효율 아냐?"

내가 Kubernetes 기반 마이크로서비스를 운영하면서 가장 골치 아팠던 부분 중 하나가 바로 설정 변경이었다. 설정 하나 바꾸려면 배포를 다시 해야 하고, 그 사이 서비스가 잠시 불안정해지거나 다운되는 경우도 종종 있었으니까. 그런데 Airbnb가 공개한 [Sitar-Agent](https://kubernetes.io/docs/concepts/overview/) 아키텍처를 보면서 "이게 진짜 답이구나" 싶었다. 동적 설정 사이드카를 통해 설정 변경을 실시간으로 반영하면서도 서비스 중단 없이 안정적으로 운영하는 방법을 알려주더라.

이번 글에서는 Airbnb가 어떻게 Kubernetes 환경에서 Sitar-Agent라는 동적 설정 사이드카를 설계하고 운영했는지, 그리고 우리 팀이 이를 참고해 어떻게 적용할 수 있을지 이야기해보려 한다.

## Kubernetes에서 동적 설정 사이드카가 왜 필요한지

Kubernetes에서 보통 서비스 설정은 ConfigMap이나 Secret으로 관리한다. 하지만 이걸 Pod에 붙이고 나면 설정 변경 시 Pod를 재시작해야 변경 사항이 반영된다. 마이크로서비스가 수백, 수천 개로 늘어나면 이 재시작 과정이 서비스 가용성에 큰 영향을 미친다.

여기서 동적 설정 사이드카가 등장한다. 서비스 컨테이너 옆에 별도의 사이드카 컨테이너를 두고, 이 사이드카가 설정을 실시간으로 받아서 주 서비스에 전달하거나 프록시 역할을 하면서 설정 변경을 즉시 반영하는 방식이다. 이렇게 하면 설정 변경 시 서비스 재시작 없이도 바로 적용할 수 있다.

Airbnb는 Sitar-Agent를 통해 이 패턴을 실제 운영 환경에 적용했다. 이 사이드카는 서비스와 별개로 동작하면서 설정을 관리하고, 필요하면 설정을 즉시 업데이트해 서비스의 유연성과 확장성을 크게 높였다.

참고로, Kubernetes 공식 문서에서도 dynamic configuration sidecar가 주 서비스 컨테이너와 함께 배포되어 서비스 설정을 실시간 변경·관리할 수 있다고 명확히 설명한다. 이는 서비스의 유연성, 확장성, 장애 복구, 무중단 배포에 큰 도움이 된다[https://kubernetes.io/docs/concepts/overview/](https://kubernetes.io/docs/concepts/overview/).


## Sitar-Agent가 서비스 상태 모니터링과 설정 반영을 어떻게 조율하는지

설정을 실시간으로 바꾸는 건 좋은데, 이 과정에서 서비스가 불안정해지면 오히려 독이 된다. Airbnb는 Kubernetes의 Liveness, Readiness, Startup 프로브를 적극 활용해 이 문제를 해결했다.

- **Liveness Probe**: 서비스가 살아있는지 체크
- **Readiness Probe**: 서비스가 트래픽을 받을 준비가 되었는지 체크
- **Startup Probe**: 서비스가 정상적으로 시작됐는지 체크

Sitar-Agent는 설정 변경 후 이 프로브 상태를 모니터링하면서, 설정이 제대로 적용됐는지 확인한다. 만약 설정 반영으로 인해 서비스가 불안정해지면 프로브가 실패 신호를 보내고, Kubernetes는 자동으로 재시작하거나 롤백할 수 있다. 덕분에 무중단 배포와 안정적인 설정 변경이 가능해진다.

이 부분은 Kubernetes 공식 문서에서도 강조하는 부분으로, 프로브를 적절히 설정하는 것이 동적 설정 사이드카 운영의 핵심이다[https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/).


## Airbnb Sitar-Agent를 참고해 우리 팀에 적용해본 사례

우리 팀도 최근 몇 달간 비슷한 문제를 겪었다. 서비스 설정 변경 시마다 배포를 새로 해야 해서 배포 시간이 길어지고, 그 과정에서 잠깐씩 트래픽이 끊기는 경우가 있었다. 그래서 Airbnb Sitar-Agent를 참고해 Kubernetes 환경에 동적 설정 사이드카를 도입했다.

### 실제 적용한 사이드카 컨테이너 예시

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: example-service-pod
spec:
  containers:
  - name: main-service
    image: our-service:1.2.3
    ports:
    - containerPort: 8080
    readinessProbe:
      httpGet:
        path: /health/ready
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 10
    livenessProbe:
      httpGet:
        path: /health/live
        port: 8080
      initialDelaySeconds: 10
      periodSeconds: 20
  - name: config-sidecar
    image: our-config-agent:0.9.1
    env:
    - name: CONFIG_SOURCE
      value: "config-server"
    volumeMounts:
    - name: config-volume
      mountPath: /etc/service-config
  volumes:
  - name: config-volume
    emptyDir: {}
```

우리는 사이드카 컨테이너가 Config Server에서 설정을 폴링(polling)하거나 이벤트 기반으로 받아와서 `/etc/service-config`에 최신 설정 파일을 덮어쓰도록 했다. 주 서비스는 이 설정 파일을 주기적으로 읽거나, SIGHUP 신호를 받아 설정을 다시 로드한다.

### 여기서 배운 점

- 설정 변경 시 주 서비스 재시작 없이 바로 반영 가능
- Kubernetes 프로브 설정 덕분에 설정 반영 실패 시 자동 복구
- 사이드카가 설정 관리만 담당하니 서비스 코드가 단순해짐

하지만 단점도 있었다. 사이드카가 설정을 잘못 받아오거나 동기화가 지연되면, 주 서비스가 오래된 설정으로 동작할 위험도 존재한다. 그래서 설정 변경 이벤트와 동기화 상태를 꼼꼼히 모니터링하는 별도의 로깅 및 알림 체계가 반드시 필요했다.


## 사이드카 패턴이 마이크로서비스에 주는 의미

Martin Fowler도 언급했듯이, 마이크로서비스 아키텍처에서 각 서비스의 독립성과 복원력을 높이는 데 동적 설정 사이드카가 큰 역할을 한다[https://martinfowler.com/articles/microservices.html](https://martinfowler.com/articles/microservices.html). 설정 변경 시 서비스 재시작 없이 실시간 반영이 가능하니, 서비스 가용성과 확장성이 크게 개선된다.

또한 Microsoft의 클라우드 디자인 패턴 문서에서도 사이드카 패턴은 설정 관리, 로깅, 모니터링 같은 부가 기능을 서비스와 독립적으로 운영할 수 있게 해 서비스 복잡도를 줄이는 데 도움을 준다고 설명한다[https://learn.microsoft.com/en-us/azure/architecture/patterns/](https://learn.microsoft.com/en-us/azure/architecture/patterns/).

이처럼 사이드카 패턴은 단순히 설정만 바꾸는 기술이 아니라, 마이크로서비스를 더 견고하고 운영하기 쉽게 만드는 아키텍처적 선택인 셈이다.

### 마무리하며: 우리 서비스에 동적 설정 사이드카 도입할 때 꼭 기억할 점

- **프로브 설정은 필수!** 설정 변경 후 서비스 상태를 꼼꼼히 체크하지 않으면 오히려 장애 위험이 커진다.
- **설정 동기화 지연에 대비하라.** 사이드카와 주 서비스 간 설정 일관성을 모니터링하는 로깅과 알림 체계를 구축해야 한다.
- **서비스 코드와 설정 관리 분리**로 개발·운영 부담을 줄이고, 확장성을 확보하자.
- **무중단 배포와 장애 복구**가 가능해져 서비스 신뢰도가 올라간다.

처음엔 "사이드카 하나 더 띄우는 게 뭐가 대수냐" 싶지만, 실제로 운영 환경에 적용해보면 서비스 안정성과 개발 생산성에 미치는 영향이 엄청나다. Airbnb가 공개한 Sitar-Agent 아키텍처는 우리 같은 개발자에게 좋은 참고 사례가 될 것이다.
