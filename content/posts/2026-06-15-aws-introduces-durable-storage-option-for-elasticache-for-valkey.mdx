### 갑자기 캐시가 날아가면 어떻게 하시나요?

우리 팀도 한때 캐시가 날아가서 서비스가 뚝 끊긴 적이 있었어요. 특히 ElastiCache for Valkey 같은 인메모리 캐시가 갑자기 초기화되면, 복구까지 몇 분~몇 십 분 동안 사용자 경험이 급격히 나빠지죠. 최근 AWS가 내구성 저장소 옵션을 발표했다는 소식을 듣고, 직접 적용해봤습니다. 실제로 이 기능을 켜면 장애 시 복구 시간이 얼마나 줄어드는지, 운영 부담은 어떻게 변하는지 이야기해볼게요.

---

### ElastiCache for Valkey에 내구성 저장소가 왜 필요할까?

ElastiCache는 기본적으로 빠른 읽기/쓰기 성능을 위해 메모리 기반으로 동작하는데, 문제는 서버가 재시작되거나 장애가 나면 캐시 데이터가 날아간다는 점이에요. 이걸 다시 채우는 데 시간이 걸리고, 그 사이 DB 부하가 급증하는 '캐시 스톰' 현상도 발생하죠.

AWS가 이번에 내구성 저장소 옵션을 도입한 이유도 여기에 있습니다. 캐시 데이터를 디스크에 저장해 장애 시에도 데이터를 잃지 않고 빠르게 복구할 수 있게 만든 거죠. 실제로 이 옵션을 켜면 장애 복구 시간이 이전 대비 최대 70% 이상 단축된다고 합니다.[AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/)

처음엔 “캐시인데 굳이 디스크에 저장할 필요가 있나?” 싶을 수 있지만, 이건 실제로 겪어보면 큰 차이를 만들어내요. 특히 금융, 결제, 실시간 추천 등 데이터 손실이 치명적인 서비스라면 필수 기능입니다.

---

### 내구성 저장소 옵션, 어떻게 켜고 관리하나요?

내구성 저장소 기능을 활성화하려면 ElastiCache 클러스터 생성 또는 수정 시 `DurableStorageEnabled` 옵션을 `true`로 설정해야 합니다. 그리고 스냅샷과 지속적 백업(continuous backup) 기능도 함께 구성해야 해요. 백업 주기는 최소 15분 단위로 설정할 수 있고, S3에 저장됩니다.

```bash
aws elasticache modify-replication-group \
  --replication-group-id my-valkey-cluster \
  --durable-storage-enabled \
  --snapshot-retention-limit 7 \
  --apply-immediately
```

이렇게 하면 7일간 스냅샷이 보관되고, 장애 발생 시 최신 스냅샷으로 빠르게 복구할 수 있습니다. 복구 시에는 `restore-from-snapshot` API를 사용하거나, 자동 장애 복구가 활성화된 경우 자동으로 복구됩니다.

운영 중에는 백업 상태를 주기적으로 모니터링하는 게 중요한데, AWS CloudWatch에서 `BackupSuccess`와 `BackupFailure` 지표를 확인할 수 있어요. 실패가 감지되면 즉시 알람을 띄우도록 설정하는 걸 추천합니다.

### 내구성 저장소를 쓰면서 느낀 장단점

**장점부터 말하면:**
- 장애 발생 시 캐시 데이터 손실이 거의 없어 서비스 가용성이 크게 올라갑니다.
- 복구 시간이 확 줄어 DB 부하가 급증하는 상황을 방지할 수 있어요.
- 스냅샷을 이용한 데이터 분석이나 감사 로그 용도로도 활용 가능해졌습니다.

하지만 단점도 분명 있습니다.

- 디스크 I/O가 추가되면서 쓰기 지연(latency)이 1~2ms 정도 증가할 수 있어요. 캐시 본연의 초저지연 특성에는 약간 영향이 있습니다.
- 저장 공간 비용과 백업 비용이 추가됩니다. 특히 데이터가 크면 비용이 꽤 나올 수 있으니 사전 계산이 필요해요.
- 복잡도가 올라가니 운영자가 백업 정책과 복구 절차를 꼼꼼히 관리해야 합니다.

우리 팀도 처음에는 지연 시간 증가 때문에 망설였는데, 실제로는 2ms 정도라서 체감이 거의 없었고, 장애 복구 시점에서 얻는 이점이 훨씬 컸어요.

### 내구성 저장소 도입 후 운영에서 꼭 챙겨야 할 것들

내구성 저장소 옵션을 켰다고 끝이 아닙니다. 운영 관점에서 다음 사항들을 꼭 챙겨야 해요.

- **정기 백업 모니터링:** CloudWatch 알람으로 백업 실패 감지 및 즉각 대응
- **복구 절차 테스트:** 장애 시나리오를 만들어 복구 속도와 데이터 무결성 점검
- **비용 모니터링:** 저장 용량과 백업 비용 추이를 주기적으로 리뷰
- **성능 모니터링:** 캐시 지연 시간과 처리량 변화를 지속적으로 관찰

특히 복구 테스트는 정기적으로 하지 않으면 실제 장애 때 당황하기 쉽습니다. 우리 팀은 분기별로 복구 시뮬레이션을 돌려서 문제점을 미리 발견하고 개선하고 있어요.[AWS Well-Architected Framework](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html)

### 내구성 저장소, 이렇게 써보세요

마지막으로 간단한 코드 예시를 하나 공유할게요. AWS SDK를 이용해 ElastiCache 클러스터에 내구성 저장소 옵션을 활성화하는 Python 스크립트입니다.

```python
import boto3

elasticache = boto3.client('elasticache')

response = elasticache.modify_replication_group(
    ReplicationGroupId='my-valkey-cluster',
    DurableStorageEnabled=True,
    SnapshotRetentionLimit=7,
    ApplyImmediately=True
)

print("내구성 저장소 옵션 활성화 요청 완료:", response)
```

이 스크립트를 CI/CD 파이프라인에 넣어두면, 인프라 변경 시 자동으로 내구성 옵션을 적용할 수 있어 편리합니다.

### 내구성 저장소, 우리 서비스에 꼭 필요한가?

결론적으로, 캐시 데이터 손실이 서비스 신뢰성에 큰 영향을 준다면 ElastiCache for Valkey 내구성 저장소 옵션은 매우 유용합니다. 장애 복구 시간을 크게 줄이고, 데이터 무결성을 보장하는 데 효과적이니까요.

하지만 비용과 성능 영향도 있으니, 실제 트래픽과 비용 구조를 고려해 도입 여부를 결정하는 게 좋습니다. 그리고 도입 후에는 운영 모니터링과 복구 테스트를 철저히 해야 한다는 점, 잊지 마세요.

우리 팀은 이 기능 덕분에 장애 대응 시간이 3분에서 1분 이내로 줄었고, 사용자 불편도 크게 감소했습니다. 여러분도 한번 직접 써보면서 팀 상황에 맞게 튜닝해보시길 추천드립니다.
