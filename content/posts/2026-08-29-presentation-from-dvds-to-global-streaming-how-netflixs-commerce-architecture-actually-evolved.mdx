넷플릭스가 DVD 대여 서비스로 시작해 전 세계 수억 명이 사용하는 스트리밍 플랫폼으로 성장한 이야기는 이미 유명하죠. 그런데 그 성장 뒤에 숨겨진 커머스 백엔드 아키텍처의 변화는 생각보다 덜 알려져 있습니다. 오늘은 넷플릭스가 어떻게 단일 모놀리식 시스템에서 벗어나 마이크로서비스 기반, 클라우드 네이티브 아키텍처로 전환했는지, 그리고 그 과정에서 어떤 실용적인 엔지니어링 패턴과 운영 결정들이 있었는지 이야기해볼게요.

## DVD 대여 시스템에서 마이크로서비스로 전환한 이유

처음 넷플릭스는 DVD 우편 대여라는 단일 비즈니스 모델에 집중했기 때문에, 단일 모놀리식 애플리케이션으로 충분했습니다. 하지만 서비스가 글로벌 스트리밍으로 확장되면서 결제, 회원 관리, 콘텐츠 추천 등 다양한 도메인이 복잡하게 얽혔고, 단일 코드베이스는 점점 병목과 장애의 원인이 되었죠.

이때 넷플릭스가 선택한 해법은 마이크로서비스 아키텍처였습니다. 각 도메인을 독립된 서비스로 분리해 배포하고 확장할 수 있게 한 거죠. 예를 들어, 결제 서비스는 결제 처리에만 집중하고, 회원 관리 서비스는 사용자 데이터와 인증에만 집중합니다. 이렇게 하면 한 서비스에 문제가 생겨도 전체 시스템이 멈추지 않고, 각 서비스는 필요에 따라 독립적으로 확장할 수 있습니다.

마틴 파울러가 설명한 마이크로서비스 원칙과도 정확히 맞아떨어집니다. 넷플릭스 사례는 "단일 책임 원칙"과 "서비스 독립성"을 실무에서 구현한 좋은 예라고 볼 수 있어요[Martin Fowler - Microservices](https://martinfowler.com/articles/microservices.html).

## 클라우드 네이티브 설계로 글로벌 확장과 자동 복구 실현하기

넷플릭스가 마이크로서비스로 전환한 것만으로는 충분하지 않았습니다. 전 세계 사용자에게 안정적인 서비스를 제공하려면 클라우드 기반의 자동 확장과 장애 복구 메커니즘이 필수였죠.

여기서 넷플릭스가 도입한 게 바로 클라우드 디자인 패턴입니다. 서비스 디스커버리, 부하 분산, 회로 차단기(Circuit Breaker) 패턴을 적극 활용해 서비스 간 호출 실패가 전체 장애로 번지지 않도록 했죠. 예를 들어, 회로 차단기는 특정 서비스가 과부하 상태일 때 호출을 잠시 중단해 장애 확산을 막아줍니다.

또한, 클라우드 인프라의 자동 확장 기능을 활용해 트래픽이 급증하면 자동으로 인스턴스를 늘리고, 트래픽이 줄면 줄이는 식으로 비용 효율성과 성능을 동시에 잡았죠. 이런 패턴들은 마이크로서비스와 클라우드 인프라가 만나야 제대로 힘을 발휘한다는 걸 보여줍니다[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/).

## 실전에서 겪은 장애 격리와 운영 복잡성

마이크로서비스로 쪼개면 확장성과 장애 격리 측면에서 유리하지만, 운영 복잡성은 확실히 올라갑니다. 넷플릭스도 초기에 여러 서비스가 서로 호출하는 과정에서 장애가 전파되는 문제를 겪었고, 이를 해결하기 위해 서비스 디스커버리와 회로 차단기 도입을 서둘렀죠.

특히, 서비스 디스커버리는 각 서비스가 동적으로 위치를 파악하고 호출할 수 있게 해줘서, 배포와 확장 시마다 IP를 일일이 관리할 필요가 없어졌습니다. 넷플릭스는 자체적으로 Eureka라는 서비스 디스커버리 시스템을 만들어 운영했는데, 이 경험은 클라우드 네이티브 아키텍처 설계에 큰 참고가 됩니다.

운영팀 입장에서는 모니터링과 로깅도 훨씬 복잡해졌는데, 넷플릭스는 이를 해결하기 위해 중앙 집중식 로그 수집과 분산 추적 시스템을 구축했습니다. 덕분에 장애 원인 분석과 대응 속도가 크게 빨라졌죠.

## 실제 코드로 보는 회로 차단기 패턴 적용 예시

여기서 넷플릭스가 활용한 회로 차단기 패턴을 간단히 Java 코드로 살펴볼까요? Spring Cloud Netflix 라이브러리의 Hystrix를 활용한 예입니다.

```java
@Service
public class PaymentService {

    @HystrixCommand(
        fallbackMethod = "paymentFallback",
        commandProperties = {
            @HystrixProperty(name = "execution.isolation.thread.timeoutInMilliseconds", value = "2000")
        })
    public String processPayment(String userId, double amount) {
        // 결제 시스템 호출
        // 외부 결제 게이트웨이 호출 시도
        if (someExternalCallFails()) {
            throw new RuntimeException("결제 실패");
        }
        return "결제 성공";
    }

    public String paymentFallback(String userId, double amount) {
        // 결제 실패 시 대체 로직
        return "결제 서비스가 현재 불안정합니다. 잠시 후 다시 시도해주세요.";
    }

    private boolean someExternalCallFails() {
        // 외부 호출 실패 시뮬레이션
        return new Random().nextBoolean();
    }
}
```

이 코드는 결제 서비스가 외부 결제 게이트웨이 호출 중 문제가 생기면 자동으로 fallback 메서드를 호출해 사용자에게 친절한 메시지를 전달합니다. 이런 회로 차단기 패턴 덕분에 장애가 전체 시스템으로 번지지 않고 국소화됩니다.

## 넷플릭스 아키텍처에서 배울 수 있는 실용적 교훈

넷플릭스 사례를 보면서 느낀 점은, 단순히 최신 기술을 도입하는 것보다 실질적인 운영 경험과 장애 사례에서 얻은 교훈을 바탕으로 아키텍처를 진화시켰다는 점입니다. 마틴 파울러가 말한 소프트웨어 아키텍처 가이드와도 일맥상통하는 부분이 많죠[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

- **도메인별 독립 서비스 설계**: 각 커머스 기능을 독립된 마이크로서비스로 분리해 확장과 유지보수를 쉽게 했다.
- **클라우드 디자인 패턴 적극 활용**: 서비스 디스커버리, 회로 차단기, 부하 분산 등으로 장애 격리와 자동 복구를 구현했다.
- **운영과 모니터링에 집중**: 장애 원인 분석을 위한 분산 추적과 로그 수집 체계를 구축해 빠른 대응이 가능했다.

처음엔 이런 아키텍처가 복잡해 보이지만, 실제로 대규모 트래픽과 장애 상황을 겪어보면 왜 필요한지 몸으로 느끼게 됩니다. 그리고 넷플릭스처럼 점진적으로 도입하고 개선해나가는 게 가장 현실적인 접근법이라는 것도요.
