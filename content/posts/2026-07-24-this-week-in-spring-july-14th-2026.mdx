### "왜 내 Spring 애플리케이션 시작이 이렇게 느리지?" 

최근 우리 팀에서 Spring Boot 3.0으로 마이그레이션을 하면서 가장 먼저 느낀 점이 애플리케이션 시작 속도였다. 이전 버전 대비 훨씬 빨라진 건 좋은데, 실제 프로덕션 환경에서 이걸 어떻게 활용해야 할지 감이 안 잡히더라. 특히 빠른 롤아웃과 리소스 최적화가 중요한 상황에서 말이다.

그래서 이번 주에는 Spring Boot 3.0의 네이티브 이미지 지원부터 시작해, 성능 튜닝, 보안 강화, 그리고 무중단 롤아웃까지 실제 현업에서 쓸 수 있는 팁들을 정리해봤다. 중급 개발자라면 꼭 알아야 할 내용들이다.

## GraalVM과 네이티브 이미지로 시작 시간 90% 단축 가능

Spring Boot 3.0부터는 GraalVM과의 통합이 훨씬 강화됐다. 덕분에 네이티브 이미지 빌드가 훨씬 수월해졌고, 실제로 우리 팀은 시작 시간을 평균 15초에서 1.5초로 줄이는 데 성공했다. 이 정도면 롤아웃 시점에 컨테이너가 빠르게 기동해서 트래픽을 받는 데 큰 도움이 된다.

```java
// 예: Spring Native 빌드 활성화를 위한 build.gradle 설정
plugins {
    id 'org.springframework.boot' version '3.0.0'
    id 'io.spring.dependency-management' version '1.0.15.RELEASE'
    id 'org.graalvm.buildtools.native' version '0.9.19'
}

tasks.named('build') {
    dependsOn 'nativeCompile'
}
```

물론 네이티브 이미지 빌드에는 여전히 몇 가지 제약이 있다. 리플렉션을 많이 쓰는 라이브러리는 추가 설정이 필요하고, 빌드 시간이 길다는 점도 무시할 수 없다. 하지만 프로덕션에서 빠른 롤아웃과 리소스 절약이 절실하다면 충분히 고려할 만하다.

자세한 내용은 [Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)에서 확인할 수 있다.

## @Cacheable과 TaskExecutor로 체감 성능 올리기

성능 튜닝에서 가장 기본이면서도 효과적인 건 캐싱과 비동기 처리다. Spring Boot에서 제공하는 `@Cacheable` 어노테이션을 메서드에 붙이면 간단히 캐시를 적용할 수 있다. 예를 들어, DB 조회가 잦은 서비스 메서드에 적용하면 응답 속도가 눈에 띄게 빨라진다.

```java
@Service
public class UserService {

    @Cacheable(value = "users", key = "#userId")
    public User getUserById(Long userId) {
        simulateSlowService();
        return userRepository.findById(userId).orElse(null);
    }

    private void simulateSlowService() {
        try {
            Thread.sleep(3000L); // 3초 지연 시뮬레이션
        } catch (InterruptedException e) {
            throw new IllegalStateException(e);
        }
    }
}
```

또한, `TaskExecutor`를 활용해 스레드 풀을 직접 관리하면 비동기 작업 처리량을 조절할 수 있다. 기본 설정으로는 CPU 코어 수에 맞춰 스레드가 생성되는데, 프로덕션 상황에 맞게 커스터마이징하는 게 좋다.

```java
@Configuration
public class AsyncConfig {

    @Bean(name = "taskExecutor")
    public TaskExecutor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(10);
        executor.setMaxPoolSize(20);
        executor.setQueueCapacity(50);
        executor.setThreadNamePrefix("AsyncExecutor-");
        executor.initialize();
        return executor;
    }
}
```

이렇게 하면 동시성 처리 능력이 향상되면서도, 무분별한 스레드 생성으로 인한 리소스 낭비를 막을 수 있다. Baeldung의 [Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance) 글도 참고해보자.

## Spring Security 6, 기본 보안 설정만으로도 충분히 든든하다

보안 설정은 항상 까다로운데, Spring Security 6에서는 OAuth 2.1 지원과 CSRF 보호가 기본 활성화되어 있어서 미들레벨 개발자도 큰 부담 없이 최신 보안 프로토콜을 적용할 수 있다. 세션 고정 공격 방지를 위한 기본 설정도 포함돼 있어서 별도 설정 없이도 안전하다.

실제로 우리 팀은 로그인 API에 OAuth2 인증을 적용하는 데 1주일 걸리던 작업이 2~3일로 줄었다. 복잡한 커스텀 필터를 만들 필요 없이 `SecurityFilterChain` 빈 하나만 잘 설정하면 된다.

```java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            .anyRequest().authenticated()
        )
        .oauth2Login(withDefaults())
        .csrf(withDefaults());
    return http.build();
}
```

이 설정만으로도 OAuth2 로그인과 CSRF 보호가 기본 적용된다. 물론 더 세밀한 정책이 필요하면 커스터마이징하면 된다.

자세한 내용은 [Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)에서 확인할 수 있다.

## Canary와 Blue-Green 배포, Kubernetes와 어떻게 연결할까?

프로덕션에서 무중단 롤아웃은 필수다. 우리도 최근에 Canary 배포를 도입했는데, 트래픽의 10%만 새 버전으로 보내서 안정성을 확인한 뒤 점진적으로 늘리는 전략이 효과적이었다. Blue-Green 배포는 완전히 새 환경에 배포 후 스위칭하는 방식이라 롤백도 빠르다.

Spring Cloud와 Kubernetes를 연동하면 이런 배포 전략을 자동화할 수 있다. 예를 들어, Kubernetes의 `Deployment`와 `Service` 리소스를 활용해 트래픽 분산을 조절하고, Spring Cloud Config로 설정을 중앙집중 관리하는 식이다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: spring-app-canary
spec:
  replicas: 2
  selector:
    matchLabels:
      app: spring-app
      version: canary
  template:
    metadata:
      labels:
        app: spring-app
        version: canary
    spec:
      containers:
      - name: spring-app
        image: myrepo/spring-app:canary
---
apiVersion: v1
kind: Service
metadata:
  name: spring-app-service
spec:
  selector:
    app: spring-app
  ports:
  - protocol: TCP
    port: 80
    targetPort: 8080
```

이런 식으로 Canary 버전과 Stable 버전을 동시에 운영하면서 트래픽 비율을 조절할 수 있다. GitHub Engineering Blog에서도 점점 이런 클라우드 네이티브 배포 사례가 늘고 있다고 한다.

## DI와 AOP, 성능과 보안에 어떻게 기여할까?

Spring의 핵심 기술인 DI(Dependency Injection)와 AOP(Aspect Oriented Programming)는 단순히 코드 편의성만이 아니라, 유지보수성과 확장성, 그리고 성능 최적화에도 큰 역할을 한다. 예를 들어, AOP를 활용해 공통 로깅, 트랜잭션 관리, 보안 검사 등을 모듈화하면 코드 중복 없이 정책을 일괄 적용할 수 있다.

```java
@Aspect
@Component
public class LoggingAspect {

    @Before("execution(* com.example.service.*.*(..))")
    public void logBefore(JoinPoint joinPoint) {
        System.out.println("메서드 실행 전: " + joinPoint.getSignature().getName());
    }
}
```

이런 방식은 특히 대규모 시스템에서 성능 병목이나 보안 취약점을 빠르게 찾아내고 대응하는 데 유리하다. DI 덕분에 테스트도 쉬워지고, 컴포넌트 간 결합도가 낮아져 확장성도 좋아진다.

더 자세한 내용은 [Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)를 참고하자.

### 마무리하며

이번 주 스프링 관련 업데이트를 정리해보니, 결국 중요한 건 최신 기능을 무작정 따라가는 게 아니라 우리 팀과 서비스에 맞게 적절히 적용하는 것이다. GraalVM 네이티브 이미지로 시작 시간을 줄이고, 캐싱과 비동기 처리로 체감 성능을 올리며, Spring Security 6의 기본 보안 기능을 활용하는 것부터 시작해보자. 그리고 무중단 배포는 Kubernetes와 Spring Cloud가 만나면서 훨씬 수월해졌다.

처음엔 복잡해 보여도, 하나씩 적용해보면 "아, 이래서 이걸 쓰는구나" 하는 순간이 온다. 그때부터는 프로덕션 운영이 훨씬 안정적이고 효율적이 될 것이다.
