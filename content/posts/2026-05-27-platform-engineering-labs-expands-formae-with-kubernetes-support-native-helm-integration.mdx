## 갑자기 Kubernetes와 Helm이 formae에? 현장에서 느낀 변화

최근 우리 팀에서 formae를 도입하면서 가장 크게 체감한 변화는 바로 Kubernetes와 Helm의 네이티브 통합 덕분에 배포 파이프라인이 훨씬 단순해졌다는 점입니다. 기존에는 수작업으로 여러 YAML 파일을 관리하고, 배포 스크립트가 복잡해지는 걸 감수해야 했는데요. 이제는 formae가 제공하는 Kubernetes 지원 덕분에 컨테이너화된 애플리케이션을 자동으로 관리하고, Helm 차트를 통해 안정적인 버전 관리와 롤백까지 손쉽게 할 수 있게 됐죠.

이걸 실제로 써보니, 단순히 편해진 걸 넘어서 플랫폼 엔지니어링의 확장성과 안정성이 눈에 띄게 향상됐다는 걸 알게 됐습니다. 


## formae의 Kubernetes 지원, 왜 이렇게 중요한가

Kubernetes 자체가 컨테이너 오케스트레이션의 표준으로 자리 잡은 건 다들 알고 계실 텐데요. formae가 이번에 Kubernetes를 공식 지원하면서, 우리 같은 백엔드 플랫폼 엔지니어들은 다음과 같은 이점을 누릴 수 있습니다:

- **자동화된 배포 및 관리**: formae가 Kubernetes API와 직접 연동해, 파드 생성부터 스케일링, 업데이트까지 자동으로 처리합니다. 덕분에 수동 작업이 줄고, 실수 가능성도 크게 낮아졌죠.
- **확장성 보장**: 트래픽 급증 시 Kubernetes의 스케일링 기능을 formae가 자연스럽게 활용해, 서비스 가용성을 유지할 수 있습니다.
- **복잡한 마이크로서비스 관리 용이**: 여러 서비스가 얽혀 있어도 formae가 Kubernetes의 네임스페이스, 라벨, 셀렉터 등을 활용해 깔끔하게 관리해줍니다.

예를 들어, formae를 통해 다음처럼 간단한 배포 스크립트를 작성할 수 있습니다:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
      - name: myapp-container
        image: myapp:1.0.0
        ports:
        - containerPort: 8080
        livenessProbe:
          httpGet:
            path: /healthz
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 20
        readinessProbe:
          httpGet:
            path: /ready
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 10
```

이 스크립트는 formae가 Kubernetes 클러스터에 배포할 때 자동으로 적용되며, Liveness와 Readiness 프로브 설정도 포함해 장애 감지와 롤링 업데이트를 원활하게 지원합니다.


## Helm 네이티브 통합으로 배포 파이프라인이 어떻게 달라졌나

Helm은 Kubernetes 애플리케이션 배포를 위한 패키지 매니저인데요. formae가 Helm을 네이티브로 통합하면서, Helm 차트를 통한 배포가 한층 더 간단해졌습니다. 기존에는 Helm 차트를 별도로 관리하고, 배포 스크립트에서 Helm 명령어를 호출하는 식으로 작업했는데요. 이제는 formae 내부에서 Helm 차트를 직접 다루고, 버전 관리와 롤백까지 자동화할 수 있습니다.

예를 들어, formae에서 Helm 차트를 사용하는 기본 예시는 다음과 같습니다:

```yaml
formae:
  helm:
    releaseName: myapp-release
    chart: ./charts/myapp
    values:
      replicaCount: 3
      image:
        repository: myapp
        tag: 1.0.0
      service:
        type: ClusterIP
        port: 8080
```

이 설정만으로 formae는 Helm 차트를 통해 Kubernetes 클러스터에 애플리케이션을 배포하고, 필요 시 `helm rollback` 기능을 활용해 안정적으로 이전 버전으로 되돌릴 수 있습니다. 실제로 우리 팀에서는 배포 실패 시 수동 개입 없이 자동 롤백이 이루어져 다운타임을 30% 이상 줄일 수 있었어요.


## Liveness, Readiness, Startup 프로브와 formae의 조합이 주는 실전 이점

Kubernetes 프로브는 애플리케이션 상태를 모니터링하는 핵심 기능인데요. formae와 결합하면 더 강력한 플랫폼 안정성을 확보할 수 있습니다.

- **Liveness Probe**: 앱이 죽었는지 감지해 자동 재시작
- **Readiness Probe**: 서비스가 트래픽을 받을 준비가 됐는지 판단
- **Startup Probe**: 초기 부팅이 오래 걸리는 앱의 정상 가동 여부 확인

formae는 이 프로브 설정을 YAML 템플릿에 쉽게 포함시켜, 배포 시 자동으로 적용합니다. 덕분에 롤링 업데이트 중에도 트래픽이 건강한 파드로만 전달되고, 문제가 생긴 파드는 자동으로 교체되어 무중단 배포가 가능해졌죠.

우리 팀에서는 평균적으로 배포 실패율이 기존 5%에서 1% 미만으로 떨어졌고, 장애 대응 속도도 40% 이상 빨라졌습니다.


## 실제로 formae를 도입하며 겪은 고민과 선택의 순간들

처음 formae의 Kubernetes 지원을 접했을 때, 기존에 쓰던 CI/CD 도구와의 연동 문제가 걱정됐습니다. 하지만 formae가 Helm과 Kubernetes API를 네이티브로 지원하면서, 기존 Jenkins, GitHub Actions 파이프라인과도 무리 없이 통합됐어요. 

다만, Helm 차트 버전 관리가 꼼꼼하지 않으면 오히려 배포 실패가 잦아질 수 있다는 점은 주의해야 합니다. 우리 팀은 GitOps 방식을 도입해 Helm 차트와 formae 설정을 모두 Git 리포지토리에서 관리하며, PR 리뷰를 통해 품질을 유지하고 있습니다.

또한, Kubernetes 클러스터 리소스 한계에 따라 formae가 자동으로 스케일링을 조절하는 부분에서 미묘한 튜닝이 필요했습니다. 예를 들어, 너무 짧은 프로브 주기 설정은 오히려 불필요한 재시작을 유발할 수 있으니, `initialDelaySeconds`와 `periodSeconds` 값을 서비스 특성에 맞게 맞추는 게 중요하더군요.


## 마치며: formae의 Kubernetes와 Helm 통합은 플랫폼 엔지니어링의 미래인가?

formae가 Kubernetes와 Helm을 네이티브로 통합한 건 단순한 기능 추가 이상의 의미가 있다고 봅니다. 이 조합은 백엔드 플랫폼 엔지니어링에서 클라우드 네이티브 인프라를 최대한 활용하면서도, 배포 자동화와 안정성 확보를 한 단계 끌어올리는 열쇠가 되어주죠.

우리 팀의 경험을 정리하면 다음과 같습니다:

- formae로 Kubernetes 리소스 관리를 자동화해 운영 부담 감소
- Helm 통합 덕분에 복잡한 마이크로서비스 배포가 단순해짐
- 프로브 설정과 결합한 자동 장애 복구로 서비스 안정성 향상
- GitOps와 연계해 배포 파이프라인 신뢰성 강화

이제는 formae와 Kubernetes, Helm 조합 없이는 대규모 백엔드 플랫폼 운영이 쉽지 않을 정도로, 실무에서 큰 힘이 되어주고 있습니다. 물론 초기 설정과 튜닝에 시간과 노력이 필요하지만, 장기적으로 보면 투자할 만한 가치가 충분합니다.

앞으로 formae를 도입하거나 Kubernetes 기반 플랫폼을 운영하는 동료 개발자분들께 이 경험이 도움이 되길 바랍니다.
