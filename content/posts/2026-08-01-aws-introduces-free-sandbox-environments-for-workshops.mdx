## AWS 무료 샌드박스 환경, 진짜 써보니 어땠나?

"이거 그냥 데모용 아닌가?" 처음엔 나도 그랬다. AWS가 워크숍용으로 무료 샌드박스 환경을 내놨다는 소식을 듣고 ‘설마 실제 개발에 쓸 수 있을까?’ 반신반의했지. 그런데 직접 써보니, 기본 세팅부터 비용 걱정 없이 바로 백엔드 프로토타입을 띄우고, 테스트하는 데 진짜 편하더라. 특히 팀원들과 워크숍이나 코드 리뷰할 때 환경 맞추느라 고생하는 시간이 확 줄었다.

내가 직접 겪은 경험과 함께, 왜 이 무료 샌드박스 환경이 백엔드 개발자들한테 좋은지, 그리고 실제로 어떻게 활용하면 좋을지 이야기해보려고 한다.

---

## AWS 샌드박스 환경, 뭐가 무료고 얼마나 쓸 수 있길래?

AWS가 제공하는 워크숍용 무료 샌드박스 환경은 기본적으로 제한된 리소스 내에서 AWS 서비스들을 사용할 수 있게 해준다. 예를 들어, EC2 인스턴스 한두 개, Lambda 함수, DynamoDB 테이블, S3 버킷 등 기본적인 백엔드 컴포넌트를 무료로 쓸 수 있다. 물론, 완전 무제한은 아니고, 시간 제한(보통 몇 시간~몇 일 단위)과 리소스 제한이 있지만, 작은 프로토타입이나 테스트용으로는 충분하다.

내가 테스트했던 환경은 EC2 t3.micro 인스턴스 1대, Lambda 1GB 메모리 1분 실행 1000회, DynamoDB 읽기/쓰기 용량 단위 각각 5, S3 저장용량 1GB 정도를 기본으로 제공했다. 이 정도면 간단한 API 서버나 이벤트 기반 백엔드 로직을 돌리기에 꽤 괜찮은 스펙이다.

실제로 워크숍 참가자들이 각자 자신의 샌드박스 환경에서 코드를 배포하고, API를 호출해보면서 바로 피드백을 주고받는 게 가능했다. 환경을 따로 셋업하는 데 걸리는 시간이 1시간 이상에서 10분 내외로 줄어들었다는 점이 가장 큰 장점이었다.

## 백엔드 프로토타입 만들 때 AWS 샌드박스 환경을 이렇게 써봤다

내가 진행한 워크숍에서 사용한 간단한 예시 코드를 공유한다. 간단한 REST API를 Lambda + API Gateway 조합으로 만들었고, DynamoDB에 데이터를 저장하는 구조였다.

```typescript
import { APIGatewayProxyHandler } from 'aws-lambda';
import { DynamoDB } from 'aws-sdk';

const dynamo = new DynamoDB.DocumentClient();
const TABLE_NAME = process.env.TABLE_NAME || '';

export const handler: APIGatewayProxyHandler = async (event) => {
  try {
    const body = JSON.parse(event.body || '{}');
    const { id, message } = body;

    if (!id || !message) {
      return { statusCode: 400, body: 'Missing id or message' };
    }

    await dynamo.put({
      TableName: TABLE_NAME,
      Item: { id, message, createdAt: new Date().toISOString() },
    }).promise();

    return { statusCode: 200, body: JSON.stringify({ success: true }) };
  } catch (error) {
    console.error('Error:', error);
    return { statusCode: 500, body: 'Internal Server Error' };
  }
};
```

이 코드는 워크숍 참가자들이 Lambda 함수로 바로 배포해서 테스트해볼 수 있었다. 샌드박스 환경에서 DynamoDB 테이블 이름만 환경변수로 맞춰주면 바로 동작했다. 이런 식으로 작은 단위부터 시작해서 점진적으로 기능을 늘려가는 게 가능했다.

## 작은 범위로 점진적 배포하는 게 왜 운영 리스크를 줄이는지

AWS Well-Architected Framework에서도 강조하는 부분인데, 작은 범위의 점진적 배포 전략은 신규 백엔드 기능의 운영 리스크를 크게 낮춘다. 특히 샌드박스 환경에서 프로토타입을 충분히 검증한 뒤, 실제 운영 환경에 점진적으로 배포하면 장애나 버그 발생 가능성을 최소화할 수 있다.

내가 직접 겪은 케이스로는, 워크숍에서 만든 Lambda 함수에 신규 기능을 추가할 때, 샌드박스 환경에서 실패 유형을 미리 계측하고 로그를 꼼꼼히 남겼다. 덕분에 실제 운영 배포 때는 장애 대응 속도가 훨씬 빨라졌다. 이는 TypeScript 5.x 릴리즈 노트에서도 실패 유형을 초기부터 계측하면 유지보수성과 장애 대응 속도가 개선된다는 점과도 맞닿아 있다[TypeScript 5.x Release Notes](https://devblogs.microsoft.com/typescript/announcing-typescript-5-4/).

---

## AWS 샌드박스 환경을 쓸 때 주의할 점과 현실적인 한계

물론 무료라서 무조건 좋은 것만은 아니다. 샌드박스 환경은 리소스 제한이 분명하다 보니, 무거운 트래픽이나 대용량 데이터 처리에는 적합하지 않다. 그리고 워크숍용이다 보니, 환경이 일정 시간이 지나면 자동 종료되거나 초기화되는 경우도 있다.

또한, 실제 운영 환경과 완벽히 동일하지 않기 때문에, 샌드박스에서 잘 돌아가던 코드가 운영에서는 다르게 동작할 가능성도 염두에 둬야 한다. 그래서 샌드박스는 어디까지나 빠른 프로토타입과 초기 테스트용으로 쓰고, 운영 배포 전에는 별도의 스테이징 환경에서 충분히 검증하는 게 좋다.

---

## 당장 써보고 싶은 백엔드 엔지니어들을 위한 팁

1. **워크숍이나 팀 코드 리뷰 전에 미리 샌드박스 환경을 할당받아 세팅해두자.** 환경 맞추는 데 드는 시간을 확 줄일 수 있다.
2. **Lambda + DynamoDB 조합 같은 서버리스 아키텍처를 먼저 시도해보자.** 설정이 간단하고, 무료 한도 내에서 충분히 테스트 가능하다.
3. **작은 기능부터 점진적으로 배포하고, 실패 유형을 꼼꼼히 계측하자.** 운영 리스크를 줄이고 장애 대응 속도를 높일 수 있다.
4. **샌드박스 환경은 임시 환경임을 명심하고, 운영 전에는 별도 스테이징 환경에서 최종 검증하자.**

---

AWS 무료 샌드박스 환경은 생각보다 활용도가 높다. 비용 부담 없이 빠르게 프로토타입을 만들고, 팀원들과 협업하며, 점진적으로 기능을 확장해나가는 데 큰 도움이 된다. 특히 백엔드 개발자라면 이런 환경을 적극 활용해보길 추천한다.
