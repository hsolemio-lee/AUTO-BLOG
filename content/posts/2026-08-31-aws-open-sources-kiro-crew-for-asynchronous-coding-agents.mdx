## "왜 우리 시스템에 Kiro Crew 같은 비동기 코딩 에이전트를 붙여야 하지?"

얼마 전 우리 팀에서 AWS가 공개한 Kiro Crew를 실제 서비스에 붙여보자는 이야기가 나왔어요. 기존에 동기 호출 위주로 돌아가던 백엔드에, AI 기반 비동기 코딩 에이전트를 넣는다는 게 막상 해보니 생각보다 복잡하더라고요. 특히 호출 패턴, 에러 처리, 확장성, 그리고 보안까지 신경 써야 할 게 한두 가지가 아니었죠.

이 글은 그런 시행착오와 함께, AWS Well-Architected Framework에서 권장하는 핵심 설계 원칙을 참고해 어떻게 하면 Kiro Crew를 우리 백엔드에 자연스럽게 녹여낼 수 있을지 이야기해보려 합니다.


## Kiro Crew를 기존 백엔드에 붙일 때 가장 먼저 고려해야 할 점

Kiro Crew는 AWS가 오픈소스로 공개한 비동기 코딩 에이전트 프레임워크입니다. 단순히 AI 호출만 하는 게 아니라, 여러 에이전트가 비동기적으로 작업을 분담하고 협업하는 구조를 쉽게 만들 수 있죠. 하지만 이걸 기존 백엔드에 그냥 붙인다고 끝나는 게 아닙니다.

우선 AWS Well-Architected Framework가 강조하는 신뢰성, 확장성, 보안, 운영 우수성 같은 항목을 반드시 챙겨야 해요. 예를 들어, 에이전트 호출이 실패했을 때 재시도 로직이나 장애 격리, 그리고 인증과 권한 관리가 제대로 되어 있어야 한다는 거죠.

이런 부분을 간과하면, AI 호출이 갑자기 느려지거나 실패했을 때 전체 서비스가 영향을 받는 치명적인 문제가 발생할 수 있습니다. 그래서 Kiro Crew를 붙일 땐 이벤트 기반 아키텍처와 메시지 큐를 적극 활용하는 게 대세입니다.


## 이벤트 기반 아키텍처와 메시지 큐를 활용한 Kiro Crew 통합 패턴

AWS Architecture Blog에서도 소개하듯, Kiro Crew 같은 비동기 에이전트를 기존 시스템에 통합할 때는 메시지 큐(SQS, SNS, Kafka 등)를 중간에 두고 이벤트를 주고받는 패턴이 가장 안정적입니다. 이렇게 하면 에이전트가 느려지거나 오류가 나도 백엔드 전체가 멈추지 않고, 자연스럽게 확장도 가능하죠.

예를 들어, 사용자가 코딩 요청을 하면 백엔드는 그 요청을 메시지 큐에 넣고 바로 응답을 돌려줍니다. 그 뒤 Kiro Crew 에이전트가 큐에서 작업을 받아 처리하고, 결과를 다시 다른 큐에 넣으면 백엔드가 비동기적으로 결과를 받아서 사용자에게 전달하는 식입니다.

이 과정에서 각 큐의 처리량과 메시지 TTL(Time-To-Live), 재시도 정책 등을 꼼꼼히 설정해야 해요. 큐가 꽉 차거나 메시지가 손실되면 에이전트 호출이 꼬이기 때문입니다.


## TypeScript 기반 백엔드에서 Kiro Crew 호출 시 코드 가독성과 유지보수성을 높이는 방법

우리 팀 백엔드는 TypeScript로 되어 있어서, Kiro Crew 호출도 자연스럽게 TypeScript async/await 패턴으로 감쌌어요. TypeScript Handbook에서 권장하는대로 Promise 기반 비동기 코드를 쓰니까, 에이전트 호출 흐름이 훨씬 명확해지고 에러 핸들링도 깔끔해지더군요.

아래는 간단한 Kiro Crew 호출 예시입니다. 실제로는 메시지 큐 이벤트 핸들러 안에서 이런 코드를 쓰는 식이죠.

```typescript
async function callKiroCrewAgent(taskPayload: TaskPayload): Promise<AgentResult> {
  try {
    const response = await kiroCrewClient.sendTask(taskPayload);
    if (!response.success) {
      throw new Error(`Agent failed: ${response.errorMessage}`);
    }
    return response.data;
  } catch (error) {
    console.error('Kiro Crew 호출 중 에러 발생:', error);
    // 재시도 로직이나 대체 처리 로직 추가 가능
    throw error;
  }
}
```

이렇게 async/await를 쓰면 비동기 호출의 흐름이 한눈에 들어오고, 에러가 발생했을 때 어디서 잡을지 명확해집니다. 물론 호출 제한(rate limit)이나 타임아웃 설정도 신경 써야 하는데, OpenAI API 문서에서 제시하는 권장값을 참고해 적절히 조절하는 게 좋습니다.


## 운영 단계에서 마주친 의사결정 포인트들

Kiro Crew를 붙이고 나서도 운영 중에 여러 결정 포인트가 있었는데요. 그중 대표적인 게 다음과 같습니다.

- **에이전트 호출 실패 시 재시도 정책**: 무조건 재시도하면 메시지 중복 처리 문제가 생기고, 너무 적으면 데이터 누락 위험이 커집니다. 그래서 최대 3회 재시도, 그 이상은 관리자 알림으로 처리하는 정책을 세웠어요.

- **모니터링과 로깅**: 비동기 호출이라 호출 결과가 바로 안 나오니, 각 메시지의 상태를 추적할 수 있는 로그와 메트릭 수집이 필수입니다. AWS CloudWatch와 연동해 에이전트별 처리 시간, 실패율 등을 대시보드로 모니터링합니다.

- **보안 고려 사항**: Kiro Crew 호출 시 API 키나 인증 토큰을 안전하게 관리하고, 메시지 큐 접근 권한도 최소 권한 원칙에 맞게 설정해야 합니다. AWS IAM 역할과 정책을 꼼꼼히 분리했죠.

- **스케일 아웃 전략**: 에이전트가 처리해야 할 작업량이 급증할 때를 대비해, 메시지 큐와 에이전트 컨테이너를 자동 확장하도록 설정했습니다. 이 과정에서 큐 지연시간(p99 지연시간)을 기준으로 확장 트리거를 잡으니 안정적이었어요.


## "이렇게 하면 된다"보다 "왜 이렇게 했는지"를 이해하는 게 더 중요하다는 것

처음엔 Kiro Crew를 붙이는 게 단순히 AI 호출을 넣는 작업인 줄 알았는데, 실제로는 전체 백엔드 아키텍처를 다시 한 번 점검하고 개선하는 계기가 됐어요. 특히 비동기 메시징 패턴과 TypeScript async/await 활용, 그리고 AWS Well-Architected Framework에 맞춘 설계 원칙 준수가 큰 도움이 됐죠.

실제로 겪어보면, 단순히 코드를 붙이는 것보다 운영 중 발생할 수 있는 장애 시나리오를 미리 고민하고 대비하는 게 훨씬 중요합니다. Kiro Crew 같은 에이전트는 AI 호출 자체보다, 호출을 둘러싼 시스템 설계와 운영 정책이 서비스 품질을 좌우하니까요.
