## 페이지 전환이 느려서 답답했던 경험, Navigation API가 바꿔줄 수 있다면?

“왜 클릭했는데도 페이지가 느리게 뜨지?” 이런 경험, 프론트엔드 개발자라면 한 번쯤 겪어봤을 거예요. 특히 SPA가 아닌 전통적인 웹사이트에서 페이지 리로드가 잦으면 사용자 체감 속도가 확 떨어지죠. 최근 Baseline으로 정식 제공되기 시작한 Navigation API는 이런 문제를 해결하는 데 큰 도움이 될 수 있습니다.

내가 직접 써보면서 느낀 건, 단순히 빠른 페이지 전환뿐 아니라, 내비게이션 로직을 컴포넌트 단위로 깔끔하게 분리할 수 있어 유지보수성이 확실히 좋아진다는 점이에요. 이번 글에서는 Navigation API가 왜 주목받는지, 그리고 실제로 어떻게 적용하면 좋은지 사례와 함께 풀어볼게요.

## Navigation API가 기존 내비게이션과 다른 점은 뭘까?

기존 웹 내비게이션은 보통 전체 페이지를 새로고침하는 방식으로 작동해요. 사용자가 링크를 클릭하면 브라우저가 서버에 요청을 보내고, 서버는 완전한 HTML 페이지를 다시 내려주죠. 이 과정에서 불필요한 리소스 재요청과 렌더링이 발생해 느려질 수밖에 없었습니다.

Navigation API는 이런 방식을 완전히 바꿔요. 상태 기반 내비게이션을 지원해서, 페이지 전환 시 필요한 데이터나 컴포넌트만 업데이트하도록 설계됐죠. 덕분에 네트워크 요청을 최소화하고, 렌더링도 필요한 부분만 하게 됩니다. Cloudflare 사례를 보면, Navigation API 도입 후 네트워크 요청 수가 30% 이상 줄고, 페이지 로딩 속도가 눈에 띄게 빨라졌다고 해요[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

또한, 이 API는 브라우저의 내장 네비게이션 이벤트와 밀접하게 연동되기 때문에, 히스토리 관리도 자연스럽고 정확하게 처리할 수 있습니다. 이런 점들이 사용자 경험을 크게 개선하는 핵심 포인트죠.

---

## 컴포넌트 단위로 내비게이션 로직을 관리하는 게 왜 좋을까?

내가 Navigation API를 도입하면서 가장 흥미로웠던 부분은 바로 컴포넌트 기반 설계와의 궁합이었어요. 기존 라우팅 라이브러리는 주로 URL 매칭과 컴포넌트 렌더링을 한꺼번에 처리하는데, Navigation API는 내비게이션의 상태 변화 감지와 이벤트 처리에 집중합니다.

Martin Fowler의 아키텍처 가이드에서도 언급했듯이, 컴포넌트 단위로 내비게이션 로직을 분리하면 유지보수성과 확장성이 크게 올라갑니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/). 예를 들어, 특정 페이지 내에서 세부 섹션 이동이나 모달 오픈 같은 복잡한 내비게이션도 각각 독립된 컴포넌트로 관리할 수 있죠.

이 덕분에 팀 단위 개발 시 충돌도 줄이고, 새로운 내비게이션 요구사항이 생겨도 전체 코드를 뒤흔들지 않고 부분적으로 대응할 수 있었어요. 특히 대규모 프로젝트에서 점진적으로 도입하기에 적합한 구조입니다.

## 실제 코드로 보는 Navigation API 기본 사용법

직접 써보면 생각보다 간단합니다. 아래는 React 환경에서 Navigation API를 활용해 페이지 이동 이벤트를 감지하고, 사용자에게 알림을 띄우는 예제입니다.

```jsx
import React, { useEffect } from 'react';

function NavigationListener() {
  useEffect(() => {
    if (!('navigation' in window)) {
      console.warn('Navigation API를 지원하지 않는 브라우저입니다.');
      return;
    }

    const nav = window.navigation;

    function onNavigate(event) {
      console.log('페이지 내비게이션 감지:', event);
      alert(`이동: ${event.destination.url}`);
    }

    nav.addEventListener('navigate', onNavigate);

    return () => {
      nav.removeEventListener('navigate', onNavigate);
    };
  }, []);

  return <div>Navigation API 테스트 중...</div>;
}

export default NavigationListener;
```

이 코드에서 핵심은 `window.navigation` 객체의 `navigate` 이벤트를 구독하는 부분입니다. 사용자가 페이지 내에서 이동할 때마다 이벤트가 발생하고, 우리는 이를 활용해 적절한 처리(예: 데이터 프리페치, 상태 업데이트 등)를 할 수 있죠.

단, 아직 모든 브라우저에서 완벽히 지원되는 건 아니니, 지원 여부 체크와 폴리필 전략도 함께 고려해야 합니다.

## 기존 라우팅 라이브러리와 함께 쓰려면 어떤 점을 신경 써야 할까?

Navigation API가 아무리 좋아도, 이미 React Router, Vue Router 같은 성숙한 라우팅 라이브러리를 버리고 바로 갈아타기는 쉽지 않죠. 여기서 중요한 건 두 가지입니다.

첫째, 상태 관리 전략과의 조화입니다. Navigation API는 내비게이션 이벤트를 감지하지만, 실제로 URL 매칭과 컴포넌트 렌더링은 기존 라우터가 담당하는 경우가 많아요. 따라서 내비게이션 상태와 글로벌 상태(store) 간의 싱크를 잘 맞춰야 합니다.

둘째, 이벤트 중복 처리 문제입니다. Navigation API와 라우터가 동시에 내비게이션 이벤트를 처리하면 의도치 않은 부작용이 생길 수 있어요. 예를 들어, 두 번 렌더링이 발생하거나, 상태가 꼬이는 경우가 있죠.

InfoQ에서 다룬 사례에 따르면, 이런 문제를 해결하려면 Navigation API 이벤트를 라우터 이벤트와 명확히 분리하거나, 라우터가 지원하는 커스텀 훅과 함께 통합하는 방식이 효과적이라고 합니다[InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/).

## 실제 프로젝트에 적용하며 느낀 장단점과 팁

내가 Navigation API를 도입하면서 가장 만족스러웠던 건 사용자 경험이 눈에 띄게 좋아졌다는 점입니다. 특히 대용량 이미지나 복잡한 데이터가 많은 페이지에서, 필요할 때만 리소스를 불러오니 체감 속도가 확실히 개선됐어요.

하지만 단점도 분명합니다. 아직 브라우저 지원이 완전하지 않고, 기존 라우팅 시스템과의 통합에 신경 써야 해서 초기 도입 비용이 좀 있습니다. 그리고 API 자체가 상대적으로 저수준이라, 완전한 라우팅 솔루션이라기보다는 내비게이션 이벤트를 효율적으로 처리하는 도구로 이해하는 게 맞아요.

팁을 하나 드리자면, Navigation API를 도입할 때는 우선 프로젝트 내에서 내비게이션 이벤트에 따른 데이터 프리페치(pre-fetch)나 상태 동기화 같은 부분부터 적용해보세요. 그리고 점진적으로 컴포넌트 단위 내비게이션 로직 분리로 확장하면 부담을 줄일 수 있습니다.

## 마무리하며: Navigation API, 지금 당장 써볼 만한가?

내비게이션 성능과 사용자 경험을 개선하고 싶은 프론트엔드 개발자라면 Navigation API를 주목할 만합니다. 특히 컴포넌트 기반 아키텍처를 추구하는 프로젝트라면, 내비게이션 로직을 깔끔하게 분리해 확장성과 유지보수성을 높이는 데 큰 도움이 될 거예요.

다만 브라우저 지원과 기존 라우터와의 조합 문제는 반드시 고려해야 하니, 작은 단위에서 실험해보고 점진적으로 확장하는 전략을 추천합니다. 이 API가 앞으로 프론트엔드 내비게이션의 새로운 표준이 될 가능성도 충분히 있으니까요.
