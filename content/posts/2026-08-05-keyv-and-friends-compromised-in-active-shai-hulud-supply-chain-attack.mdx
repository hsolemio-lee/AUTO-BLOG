# Keyv가 뚫렸다니, 우리도 안전할까?

얼마 전, Node.js 생태계에서 꽤 유명한 `keyv` 패키지와 그 주변 친구들이 Shai-Hulud라는 이름의 공급망 공격에 노출됐다는 소식을 접했다. 처음엔 ‘설마 우리 프로젝트에 직접 영향이 있겠어?’라는 생각이 들었지만, 막상 내부 의존성 트리를 뜯어보니 꽤 많은 서비스가 이 패키지에 의존하고 있었다. 

이 공격은 단순한 취약점이 아니라, 패키지 배포 과정 자체를 해킹한 공급망 공격(Supply Chain Attack)이었다. 그래서 이 글에선 실제로 어떤 일이 벌어졌고, 우리 백엔드 엔지니어가 이런 공격에 어떻게 대비할 수 있을지 경험을 나누려고 한다.

---

## Shai-Hulud 공격, Keyv와 친구들은 어떻게 뚫렸나?

Shai-Hulud 공격은 패키지 배포 권한을 탈취해 악성 코드를 심는 전형적인 공급망 공격이다. Keyv는 경량 캐시 라이브러리로, Redis, MongoDB, SQLite 등 다양한 스토리지를 추상화해 쉽게 쓸 수 있게 해준다. 

공격자는 Keyv 및 그 파생 패키지의 NPM 계정을 탈취해 악성 코드를 포함한 새 버전을 배포했고, 이를 설치한 개발자들의 시스템에 백도어를 심었다. 문제는 Keyv가 많은 프로젝트에서 캐시 레이어로 쓰이고, 또 이 패키지에 의존하는 다른 라이브러리까지 포함하면 영향 범위가 훨씬 넓어진다는 점이다.

실제로 npmjs.com에서 Keyv의 다운로드 수는 주간 수십만 건에 달한다. 이런 인기 패키지가 뚫리면 수많은 서비스가 위험에 노출된다.

### 공격이 남긴 흔적

- 악성 코드가 포함된 Keyv 4.0.0 버전이 배포됨
- 내부적으로 민감한 환경변수를 외부로 전송하는 코드가 삽입됨
- 공격자는 권한 탈취 후 빠르게 악성 버전을 퍼뜨림

이 공격을 발견한 커뮤니티는 즉시 대응에 나섰고, NPM 측도 계정 보안 강화와 악성 패키지 삭제 조치를 시행했다.

---

## 우리 서비스 의존성 트리, 얼마나 안전한지 점검해봤나요?

사실 이런 공급망 공격이 무서운 이유는 ‘내가 직접 설치한 패키지가 아니어도’ 간접 의존성으로 인해 뚫릴 수 있다는 점이다. 예를 들어, `express`를 쓰는 프로젝트에서 `keyv`가 직접 들어가 있지 않아도, `express-session`이나 다른 미들웨어가 `keyv`를 내부 의존성으로 쓸 수 있다.

내가 관리하는 서비스에서 의존성 트리를 한 번 점검해보자. 아래는 `npm ls keyv` 명령어를 통해 현재 프로젝트에 `keyv`가 어떻게 연결되어 있는지 확인하는 예시다:

```bash
$ npm ls keyv
my-project@1.0.0 /path/to/my-project
├─┬ express-session@1.17.3
│ └── keyv@3.1.0
└── keyv@3.1.0
```

이런 식으로 의존성 트리를 파악하면, 직접적인 의존뿐 아니라 간접 의존까지 모두 확인할 수 있다.

---

## 공급망 공격을 막기 위한 현실적인 방어책

공급망 공격은 완벽하게 막기 어렵지만, 리스크를 줄일 수 있는 방법은 있다. 내가 실제로 적용하고 있는 몇 가지를 공유한다.

### 1. 의존성 최소화와 주기적 점검

필요 없는 패키지는 과감히 빼고, 의존성 트리를 주기적으로 `npm audit`이나 `yarn audit`으로 점검한다. 특히, 인기 많은 패키지라도 최근 배포 내역과 유지보수 상태를 확인하는 습관이 중요하다.

```bash
npm audit --json > audit-report.json
```

이렇게 JSON으로 리포트를 받아 자동화 도구와 연동해 위험 패키지를 모니터링하는 것도 좋은 방법이다.

### 2. 패키지 서명과 신뢰할 수 있는 출처만 쓰기

NPM은 아직 완전한 패키지 서명 체계를 제공하지 않지만, 앞으로 도입될 예정이다. 지금은 공식 레지스트리에서만 패키지를 받고, 개인 저장소나 미러링된 곳은 주의해서 사용해야 한다.

### 3. CI/CD 파이프라인에서 의존성 변경 감지

작은 범위의 점진적 배포 전략은 신규 백엔드 기능의 운영 리스크를 낮춘다. 의존성 업데이트가 있을 때마다 자동으로 빌드와 테스트를 돌리고, 의심스러운 변경이 발견되면 바로 롤백하는 체계를 갖추는 게 좋다. 

### 4. 실패 유형 초기 계측으로 빠른 대응

실패 유형을 초기부터 계측하면 유지보수성과 장애 대응 속도가 개선된다. 예를 들어, 의존성 문제로 인한 에러가 발생하면 로그에 상세히 기록하고, 알림을 통해 신속하게 대응할 수 있도록 한다.

## 실제로 Keyv 악성 버전 차단하는 코드 예시

만약 `keyv`를 꼭 써야 하는 상황이라면, 악성 버전이 설치되는 걸 방지하기 위해 버전 범위를 엄격히 지정하는 게 중요하다. 예를 들어, `package.json`에 다음처럼 명시한다:

```json
{
  "dependencies": {
    "keyv": ">=3.0.0 <4.0.0"
  }
}
```

그리고 CI 파이프라인에 다음 스크립트를 추가해 설치된 버전을 검사할 수도 있다:

```bash
installed_version=$(npm ls keyv --json | jq -r '.dependencies.keyv.version')
if [[ "$installed_version" == 4.* ]]; then
  echo "경고: Keyv 4.x 버전은 악성 코드가 포함되어 있습니다. 설치를 중단합니다."
  exit 1
fi
```

이렇게 하면 실수로라도 악성 버전이 배포되거나 설치되는 걸 막을 수 있다.

## 이번 사건에서 배운 점과 앞으로 우리가 해야 할 일

처음엔 ‘내가 관리하는 서비스는 괜찮겠지’ 했지만, 현실은 그렇지 않다. 공급망 공격은 대형 기업부터 개인 개발자까지 모두가 직면한 위협이다. 

- 의존성 관리에 더 많은 신경을 써야 한다.
- 자동화된 모니터링과 점검 시스템이 필수다.
- 작은 범위로 점진적 배포하며 문제 발생 시 빠르게 롤백할 수 있어야 한다.
- 실패 유형을 조기에 계측해 장애 대응 속도를 높여야 한다.

이런 조치들은 단순히 보안뿐 아니라 서비스 안정성에도 큰 도움을 준다. 

마지막으로, 공급망 공격은 기술적 대응뿐 아니라 조직 문화와 프로세스 개선도 함께 가야 한다는 점을 잊지 말자. 동료들과 정기적으로 의존성 현황을 공유하고, 보안 교육을 꾸준히 하는 것도 중요하다.
