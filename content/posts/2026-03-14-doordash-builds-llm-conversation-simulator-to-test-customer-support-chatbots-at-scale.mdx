## 고객 지원 챗봇, 진짜 대화처럼 테스트해본 적 있나요?

DoorDash가 대규모 고객 지원 챗봇 테스트를 위해 자체적으로 LLM 대화 시뮬레이터를 만들었다는 소식을 접했을 때, 솔직히 꽤 놀랐어요. 그냥 랜덤한 테스트 케이스 몇 개 돌리는 게 아니라, 실제 고객과 대화하는 것처럼 LLM 기반으로 대규모 시뮬레이션을 돌린다니. 이걸 백엔드에서 어떻게 확장 가능하게 설계했을지 궁금하지 않을 수 없었죠.

실제로 챗봇을 운영하면서 "이거 진짜 고객들이 쓰는 시나리오에서 잘 작동할까?" 하는 의문이 늘 있었는데, DoorDash 사례를 보며 우리도 좀 더 체계적이고 규모 있는 테스트 환경을 만들어야겠다는 생각이 들었어요.

## OpenAI API로 시작하는 대화 시뮬레이터 구축의 기술적 기반

먼저, LLM을 대화 시뮬레이션에 활용하려면 API가 얼마나 유연하고 확장 가능한지가 관건인데, OpenAI API 문서는 이 부분에서 꽤 탄탄한 지원을 해줍니다. 다양한 엔드포인트와 파라미터 덕분에 백엔드에서 원하는 방식으로 대화를 주고받으며 시뮬레이션을 돌릴 수 있거든요.

예를 들어, `chat.completions` 엔드포인트는 메시지 히스토리를 주고받으며 대화를 자연스럽게 이어갈 수 있게 해주고, `temperature`, `max_tokens` 같은 파라미터로 답변의 다양성과 길이를 조절할 수 있어요. 이런 세밀한 제어 덕분에 실제 고객과 비슷한 대화 흐름을 재현할 수 있죠.

```typescript
import OpenAI from "openai";

const openai = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });

async function simulateConversation() {
  const messages = [
    { role: "system", content: "You are a helpful customer support assistant." },
    { role: "user", content: "주문 상태를 확인하고 싶어요." }
  ];

  const response = await openai.chat.completions.create({
    model: "gpt-4o-mini",
    messages,
    temperature: 0.7,
    max_tokens: 150
  });

  console.log("챗봇 응답:", response.choices[0].message?.content);
}

simulateConversation();
```

이 코드는 실제로 DoorDash가 내부에서 구현한 것과 유사한 구조인데, 메시지 배열에 대화 히스토리를 쌓아가며 챗봇과 대화를 시뮬레이션할 수 있죠. 물론 여기서 중요한 건 이걸 수만, 수십만 건 단위로 병렬 처리하면서도 API 호출 비용과 속도를 적절히 관리하는 거예요.

## 프롬프트 엔지니어링이 대화 시뮬레이터 신뢰성에 미치는 영향

대화 시뮬레이터가 아무리 많아도, 프롬프트가 엉망이면 테스트 결과도 엉망이 됩니다. Anthropic의 프롬프트 엔지니어링 가이드를 보면, 원하는 출력을 얻기 위한 프롬프트 설계가 얼마나 중요한지 알 수 있어요.

DoorDash도 이 부분에 공을 들였는데, 단순히 "주문 상태 알려줘" 같은 단일 문장만 던지는 게 아니라, 다양한 고객 상황과 의도를 반영한 복합 시나리오를 프롬프트에 녹여냈죠. 예를 들어, 고객이 불만을 표현하거나, 주문 변경을 요청하거나, 환불 문의를 하는 등 여러 케이스를 시뮬레이터가 자연스럽게 생성할 수 있도록 설계했습니다.

이 과정에서 중요한 건 프롬프트를 너무 길게 만들면 API 비용과 응답 시간이 늘어난다는 점, 그리고 너무 짧으면 챗봇이 상황을 제대로 이해하지 못한다는 점이에요. 그래서 적절한 균형을 찾기 위해 여러 번 실험하고 튜닝해야 하죠.

## TypeScript 5.x로 대규모 시뮬레이터 코드 품질 높이기

대규모 시뮬레이터는 코드가 복잡하고 유지보수가 어려워질 수밖에 없는데, DoorDash도 이 부분을 고민했어요. 최신 TypeScript 5.x 버전을 활용해 타입 안정성과 코드 가독성을 높였다는 점이 인상적이었죠.

예를 들어, 아래처럼 타입 유틸리티를 활용해 메시지 객체 구조를 엄격하게 정의하면, 대화 흐름에서 발생할 수 있는 버그를 사전에 줄일 수 있습니다.

```typescript
type Role = "system" | "user" | "assistant";

interface Message {
  role: Role;
  content: string;
}

function addMessage(history: Message[], newMsg: Message): Message[] {
  return [...history, newMsg];
}

const conversation: Message[] = [
  { role: "system", content: "You are a helpful assistant." }
];

const updated = addMessage(conversation, { role: "user", content: "안녕하세요" });
console.log(updated);
```

TypeScript 5.x는 성능 향상과 새로운 문법 지원 덕분에, 이런 대규모 타입 정의와 복잡한 비즈니스 로직 구현에 특히 유리합니다. 우리도 최신 TS 버전을 적극 활용하면, 시뮬레이터의 안정성과 생산성을 크게 끌어올릴 수 있죠.

## 클라우드 환경에서 수십만 대화 동시 처리, DoorDash는 어떻게 했을까?

마지막으로, DoorDash가 이 시뮬레이터를 실제 프로덕션에서 안정적으로 운영하려면, 클라우드 기반의 확장성과 장애 대응 전략이 필수입니다. Cloudflare의 "How We Built It" 블로그를 보면, 대규모 분산 시스템을 설계할 때 고려해야 할 여러 가지 인사이트를 얻을 수 있어요.

예를 들어, API 호출을 병목 없이 분산 처리하기 위해 큐 시스템과 워커 풀을 적절히 조합하고, 장애가 발생하면 자동으로 재시도하거나 대체 노드로 트래픽을 분산하는 전략이 중요하죠. DoorDash도 이런 아키텍처적 원칙을 적용해, 수십만 건의 대화 시뮬레이션을 동시에 돌리면서도 안정적인 성능을 유지했다고 합니다.

이런 환경을 직접 구축해보면, 단순히 코드만 잘 짜는 게 아니라 인프라 설계와 모니터링, 비용 최적화까지 신경 써야 해서 꽤 까다롭다는 걸 알게 될 거예요.

## 직접 써본 후 느낀 점과 추천하는 접근법

저도 최근에 비슷한 시뮬레이터를 만들어 보면서, 다음과 같은 점이 특히 중요하다고 느꼈어요.

- **대화 히스토리 관리**: 메모리 사용량과 API 호출 비용을 줄이려면, 대화 히스토리를 잘 자르고 요약하는 로직이 필요합니다.
- **프롬프트 튜닝 반복**: 한두 번 테스트로 끝내지 말고, 다양한 고객 케이스를 반영해 프롬프트를 꾸준히 개선해야 합니다.
- **비동기 처리와 큐 활용**: 시뮬레이션 요청이 폭주할 때를 대비해, 비동기 큐 시스템을 도입해 호출을 분산시키세요.
- **타입스크립트 적극 활용**: 타입 안정성 덕분에 대화 메시지 포맷 변경 시 버그가 크게 줄었습니다.

이 중에서도 가장 처음 도전해볼 만한 건, OpenAI API를 활용한 간단한 시뮬레이터부터 만들어보는 거예요. 위에 올린 코드 예시처럼요. 그리고 Anthropic 가이드에서 프롬프트 설계법을 참고해, 우리 서비스에 맞게 시나리오를 다양화하면 테스트 신뢰도가 훨씬 올라갑니다.
