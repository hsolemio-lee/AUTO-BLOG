## 갑자기 운영 중인 서비스가 느려진다면? Spring Boot 3.5.16이 답이 될 수 있다

최근에 우리 팀에서 운영 중인 서비스가 갑자기 응답 속도가 느려지는 현상을 겪었어요. 원인을 찾아보니 JVM 힙 메모리 설정과 커넥션 풀 관리가 제대로 되어 있지 않더군요. 마침 Spring Boot 3.5.16이 출시되면서 공식 문서에 JVM 튜닝과 커넥션 풀 최적화 가이드가 업데이트된 걸 보고 바로 적용해봤습니다.

이 글에서는 Spring Boot 3.5.16에서 실제 운영 환경에 적용할 만한 성능 튜닝 팁과 보안 강화, 그리고 무중단 배포 전략까지 공유할게요.

## JVM 힙 메모리 조정과 쓰레드 풀 관리, 이 정도는 꼭 챙기자

Spring Boot 3.5.16 공식 문서와 Baeldung 블로그를 참고하면 JVM 힙 메모리 조정이 성능에 얼마나 큰 영향을 주는지 알 수 있어요. 기본적으로 JVM 옵션에 `-Xms`와 `-Xmx`를 적절히 맞춰주고, 가비지 컬렉션 로그를 남겨서 GC가 서비스에 미치는 영향을 모니터링하는 게 중요합니다.

```bash
# 예시 JVM 옵션
java -Xms2g -Xmx2g -XX:+UseG1GC -Xlog:gc*:file=gc.log:time,uptime,level,tags
```

특히 G1GC를 사용하면 대용량 힙에서도 GC 일시 중단 시간을 줄일 수 있어요. 우리 팀은 2GB 힙 사이즈에 G1GC를 설정했는데, 평균 응답 시간이 20% 이상 개선됐습니다.

그리고 Spring Boot 3.5.16부터는 `TaskExecutor` 빈을 커스터마이징해서 쓰레드 풀 크기와 큐 크기를 조절하는 걸 권장해요. 예를 들어:

```java
@Bean(name = "taskExecutor")
public ThreadPoolTaskExecutor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(10);           // 최소 쓰레드 수
    executor.setMaxPoolSize(50);            // 최대 쓰레드 수
    executor.setQueueCapacity(100);         // 대기 큐 크기
    executor.setThreadNamePrefix("MyAppExecutor-");
    executor.initialize();
    return executor;
}
```

이렇게 하면 비동기 작업 처리 시 과부하를 어느 정도 방어할 수 있습니다. 물론 너무 큰 풀 사이즈는 오히려 컨텍스트 스위칭 비용을 늘리니 적정선을 찾아야 해요.

## 커넥션 풀과 캐싱 전략, 데이터베이스 부하 줄이기

Spring Boot 3.5.16에서는 HikariCP 커넥션 풀 기본 설정이 더 안정적으로 바뀌었지만, 실제 서비스 환경에서는 직접 튜닝이 필수입니다. 커넥션 풀 크기를 데이터베이스 최대 연결 수와 맞추고, 커넥션 타임아웃, 유휴 커넥션 검사 주기를 적절히 설정해야 해요.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 30
      minimum-idle: 10
      idle-timeout: 600000  # 10분
      max-lifetime: 1800000 # 30분
      connection-timeout: 30000 # 30초
```

이 설정은 우리 서비스에서 DB 연결이 갑자기 끊기거나 커넥션이 부족해지는 문제를 줄여줬습니다.

또한 캐싱 전략도 빼놓을 수 없는데, Spring Boot 3.5.16은 캐시 추상화가 더 유연해져서 Redis나 Caffeine 같은 다양한 캐시 구현체를 쉽게 적용할 수 있어요. 예를 들어 Caffeine 캐시를 적용할 때는:

```java
@Bean
public CacheManager cacheManager() {
    CaffeineCacheManager cacheManager = new CaffeineCacheManager("users", "products");
    cacheManager.setCaffeine(Caffeine.newBuilder()
        .expireAfterWrite(10, TimeUnit.MINUTES)
        .maximumSize(1000));
    return cacheManager;
}
```

이렇게 하면 자주 조회하는 데이터에 대해 DB 부하를 크게 줄일 수 있습니다.

## 보안 설정, 기본값만 믿지 말고 꼭 확인하자

Spring Boot 3.5.16은 CSRF, CORS 같은 보안 설정이 기본 강화되어 나왔지만, 실제 서비스에 맞게 세밀하게 조정하는 게 중요합니다. 예를 들어 REST API를 제공하는 경우, 기본 CSRF 보호가 오히려 불편할 수 있으니 아래처럼 명시적으로 비활성화하거나 커스터마이징해야 해요.

```java
@Override
protected void configure(HttpSecurity http) throws Exception {
    http
        .csrf().disable()  // REST API 특성상 CSRF 비활성화
        .cors().configurationSource(request -> {
            CorsConfiguration config = new CorsConfiguration();
            config.setAllowedOrigins(List.of("https://myfrontend.com"));
            config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
            return config;
        });
}
```

또한 Spring Boot 3.5.16에서는 보안 패치가 최신 상태로 유지되어 있으니, 의존성 버전을 꼼꼼히 확인하고 취약점이 발견되면 빠르게 업데이트하는 게 좋습니다.

## 무중단 배포, 점진적 롤아웃과 블루-그린 전략을 어떻게 적용할까?

운영 중인 서비스에 새 버전을 배포할 때 무중단이 필수인데, Spring Boot 3.5.16 공식 문서에 따르면 점진적 롤아웃과 블루-그린 배포를 지원하는 설정 가이드가 포함되어 있습니다.

예를 들어 Kubernetes 환경에서 블루-그린 배포를 할 때, readinessProbe와 livenessProbe를 꼼꼼히 설정해서 새 버전이 준비되기 전까지 트래픽이 가지 않도록 하는 게 핵심입니다. 그리고 Spring Boot Actuator의 헬스 체크 엔드포인트를 활용하면 상태를 쉽게 모니터링할 수 있어요.

```yaml
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5

livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 15
  periodSeconds: 20
```

이렇게 하면 새 버전이 완전히 준비된 후에만 트래픽이 전달되어 무중단 배포가 가능해집니다.

또한, 점진적 롤아웃 시에는 트래픽의 일정 비율만 새 버전으로 보내면서 문제 발생 시 즉시 롤백할 수 있도록 모니터링과 알림 체계를 갖추는 게 중요해요.

## 직접 써본 후 느낀 점과 현실적인 조언

처음엔 JVM 튜닝이나 커넥션 풀 최적화가 별거 아닌 것처럼 느껴졌는데, 실제로 적용해보니 서비스 안정성과 응답 속도가 눈에 띄게 좋아졌어요. 특히 GC 로그 분석과 쓰레드 풀 조절은 의외로 간단하지만 효과가 큽니다.

보안 설정은 기본값에 의존하지 말고 꼭 서비스 요구사항에 맞게 커스터마이징하세요. CSRF, CORS 문제로 골머리 앓는 팀을 많이 봤거든요.

무중단 배포는 단순히 설정만 한다고 되는 게 아니라, 모니터링과 알림 시스템을 함께 구축해야 진짜 효과를 봅니다. Spring Boot 3.5.16이 제공하는 헬스 체크와 배포 가이드를 참고해 단계적으로 도입해보세요.
