## "실시간 코드 생성, 백엔드에서 어떻게 감당하지?"

최근 우리 팀에서 코딩 에이전트를 도입하면서 가장 먼저 부딪힌 질문입니다. 단순히 API 호출만 하면 끝날 줄 알았는데, 실제로는 실시간 스트리밍 응답, 비동기 처리, 그리고 안정적인 확장성까지 챙겨야 할 게 한두 가지가 아니더라고요. 특히 OpenAI API나 Anthropic Claude Code 같은 최신 에이전트들은 각각 지원하는 기능과 통신 방식이 달라서, 어떤 아키텍처를 선택하느냐에 따라 성능과 유지보수성에 큰 차이가 납니다.

### OpenAI API의 RESTful과 웹소켓, 언제 어떻게 써야 할까?

OpenAI API는 RESTful 호출과 웹소켓 기반 스트리밍 응답을 모두 지원합니다. 예를 들어, 코드 자동 완성이나 리팩토링 같은 작업에서 실시간으로 결과를 받아야 할 때는 웹소켓 스트리밍이 필수죠. 반면, 단발성 코드 생성 요청에는 REST API가 더 간단하고 안정적입니다.

우리 팀에서는 다음과 같은 패턴을 적용했어요:

- **REST API**: 코드 생성 요청을 큐에 넣고, 백그라운드 워커가 처리 후 DB에 저장
- **웹소켓 스트리밍**: 사용자 IDE와 직접 연결해 실시간 코드 조각을 즉시 전달

이렇게 하니까, API 호출 빈도가 급증해도 큐와 워커 덕분에 백엔드가 멈추지 않고 버텨주더라고요. 물론 웹소켓 연결을 관리하는 게 까다로워서, 클라이언트 재접속이나 네트워크 불안정 상황에 대비한 로직을 꼼꼼히 짜야 했습니다.

```java
// Spring WebFlux를 활용한 OpenAI API 스트리밍 예시
@RestController
public class CodeCompletionController {
    private final OpenAIClient openAIClient;

    public CodeCompletionController(OpenAIClient client) {
        this.openAIClient = client;
    }

    @GetMapping(value = "/stream-code", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<String> streamCode(@RequestParam String prompt) {
        return openAIClient.streamCompletion(prompt)
            .map(response -> response.getChoices().get(0).getText());
    }
}
```

이 예시는 Spring WebFlux로 OpenAI의 스트리밍 응답을 받아 클라이언트에 SSE(Server-Sent Events)로 전달하는 구조입니다. 실제 운영 환경에서는 연결 끊김 대비, 재시도 로직, 그리고 요청 제한(rate limiting)도 신경 써야 합니다.

### Anthropic Claude Code, 프롬프트 엔지니어링이 왜 이렇게 중요한가

Anthropic의 Claude Code는 안전성과 신뢰성에 초점을 맞춘 코딩 에이전트입니다. 단순히 코드를 생성하는 걸 넘어서, 복잡한 코드베이스와의 통합 시에도 안정적으로 동작하는 게 특징인데요. 이게 가능한 이유 중 하나가 바로 프롬프트 엔지니어링 덕분입니다.

Anthropic 문서에 따르면, 명확한 의도 전달과 컨텍스트 유지가 장기적인 코드 품질과 유지보수성에 핵심이라 하더군요. 저희도 초기에는 단순히 "이 함수 고쳐줘" 식으로 요청하다가, 점점 구체적인 역할 설명과 예외 처리 조건을 넣는 식으로 프롬프트를 다듬었어요. 그 결과, 코드 생성 정확도가 눈에 띄게 올라가고, 후처리 작업도 줄었습니다.

예를 들어, 아래처럼 프롬프트를 구성합니다:

```
"다음 자바 메서드는 사용자 입력을 검증하는 기능입니다. null 체크와 포맷 검증을 포함해 안전하게 수정해 주세요. 예외 발생 시 IllegalArgumentException을 던지도록 해 주세요."
```

이런 방식으로 의도를 명확히 하면 Claude Code가 더 신뢰할 만한 코드를 내놓는 걸 경험할 수 있었습니다. 다만, 프롬프트가 길어질수록 API 호출 비용과 응답 지연이 커지는 점은 트레이드오프입니다.

### GitHub Copilot과 Cursor는 백엔드 통합에서 어떻게 다를까?

GitHub Copilot은 주로 IDE 내 통합에 집중해서 개발자 경험을 극대화합니다. 하지만 백엔드 시스템과 연동할 때는 API 호출 빈도와 캐싱 전략을 잘 설계해야 해요. 예를 들어, 매번 새로 API를 호출하면 비용도 비용이지만, 응답 지연도 심해져서 전체 서비스 확장성에 악영향을 미칩니다.

반면 Cursor 플랫폼은 코드 생성과 편집 기능을 API 형태로 제공하면서, 마이크로서비스 아키텍처 내 독립적인 모듈로 배포할 수 있어 유지보수가 편합니다. 저희는 Cursor API를 별도의 서비스로 띄워서, 필요할 때마다 호출하고 결과를 캐싱하는 방식을 썼는데, 덕분에 전체 시스템 부하를 분산시키고 장애 격리도 가능했죠.

### 서버리스 환경에서 Vercel AI SDK를 활용하는 것도 고려해볼 만하다

마지막으로, Vercel AI SDK는 프론트엔드와 백엔드 간 원활한 통신을 지원하면서 서버리스 환경에 최적화되어 있습니다. 클라우드 플랫폼에서 자동 확장과 비용 효율성을 제공한다는 점이 매력적이었어요.

우리 팀은 일부 실험적 기능에 Vercel AI SDK를 도입해봤는데, 요청량이 갑자기 늘어도 서버리스가 알아서 스케일링해줘서 인프라 운영 부담이 확 줄었죠. 물론 서버리스 특성상 콜드 스타트가 발생할 수 있고, 복잡한 상태 관리는 별도 시스템으로 분리해야 하는 점은 감안해야 합니다.

### 정리하며: 코딩 에이전트 통합, 백엔드에서 꼭 챙겨야 할 것들

- **실시간 스트리밍 필요 시, OpenAI API의 웹소켓 활용은 필수**. Spring WebFlux 같은 리액티브 프레임워크와 조합하면 관리가 편하다.
- **프롬프트 엔지니어링은 코드 품질과 유지보수성에 직결된다**. 특히 Anthropic Claude Code처럼 안전성 중심 에이전트는 명확한 의도 전달이 필수.
- **API 호출 빈도와 캐싱 전략은 확장성의 핵심**. GitHub Copilot처럼 IDE 연동에 최적화된 에이전트도 백엔드 통합 시에는 별도 고민이 필요하다.
- **마이크로서비스로 분리 가능한 코딩 에이전트 기능은 유지보수와 장애 격리에 유리하다**. Cursor가 좋은 사례.
- **서버리스 환경에서 Vercel AI SDK를 활용하면 자동 확장과 비용 절감 효과가 크지만, 콜드 스타트와 상태 관리 이슈는 주의**.

코딩 에이전트 통합은 단순히 API 호출을 넘어서, 실시간성, 확장성, 안정성, 그리고 비용 효율성까지 고려해야 하는 복합적인 도전입니다. 저희 경험이 비슷한 고민하는 분들께 조금이나마 도움이 되길 바랍니다.
