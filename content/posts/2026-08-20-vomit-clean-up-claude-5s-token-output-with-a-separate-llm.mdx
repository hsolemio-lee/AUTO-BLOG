## Claude 5가 뱉는 토큰, 언제나 깔끔하지는 않다

"이번에 Claude 5 써봤는데, 출력물이 생각보다 엉뚱한 토큰을 섞어서 나와서 골치 아프더라"라는 얘기, AI 개발하는 동료들 사이에서 심심찮게 듣곤 합니다. Anthropic이 만든 Claude 5는 고품질 토큰 출력을 목표로 하지만, 아무리 잘 만들어도 완벽할 수는 없죠. 특히 긴 텍스트 생성이나 복잡한 대화 시나리오에서는 불필요한 토큰이 섞이거나, 문맥에 맞지 않는 오류가 발생할 수 있습니다. 

이런 문제는 AI 서비스 신뢰성에 치명적인데, 고객에게 이상한 답변이 가거나 후처리 로직이 꼬이는 바람에 전체 시스템이 불안정해질 수 있으니까요. 그래서 요즘은 Claude 5가 뱉은 토큰을 그대로 쓰지 않고, "클린업"을 위해 별도의 LLM을 한 번 더 거치는 방식을 많이 씁니다. 이게 바로 'Vomit' 처리라고 불리는 방식인데, 실제로 해보면 꽤 효과적입니다.


## 왜 두 번째 LLM으로 후처리해야 할까?

간단히 말해, Claude 5 한 대만 믿기엔 아직 불안하다는 겁니다. Anthropic 공식 문서에서도 Claude 5가 뛰어난 성능을 내지만, 여전히 출력 토큰에 잡음이 섞일 수 있다고 명시하고 있어요. 그래서 별도의 LLM으로 후처리를 권장합니다[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

두 번째 LLM을 투입하면 첫 번째 LLM이 생성한 텍스트를 다시 한 번 검증하고, 불필요하거나 부적절한 토큰을 걸러낼 수 있습니다. 예를 들어, 문법 오류 수정, 부적절한 단어 필터링, 혹은 의도와 맞지 않는 문장 재구성 등이 가능하죠. 이렇게 하면 최종 사용자에게 전달되는 답변 품질이 훨씬 안정적이고 예측 가능해집니다.

Martin Fowler의 소프트웨어 아키텍처 가이드에서도 복잡한 시스템에서 이런 다중 LLM 체인 구성이 신뢰성과 유지보수성을 높이는 좋은 방법이라고 소개하고 있습니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).


## 실제로 백엔드 파이프라인에서 어떻게 구성할까?

우리 팀에서 구현한 예를 들자면, Spring Boot 기반 백엔드에서 Claude 5 API를 호출한 뒤, 응답 토큰을 받자마자 별도의 후처리 LLM(예: OpenAI GPT-4)을 호출하는 구조를 만들었어요. 

이때 중요한 점은 두 번째 LLM 호출이 전체 응답 시간에 미치는 영향을 최소화하는 겁니다. 그래서 비동기 호출과 캐싱 전략을 적절히 섞었고, 후처리 LLM의 프롬프트를 최대한 경량화해서 응답 지연을 300ms 이하로 유지했습니다.

아래는 후처리 LLM 호출 부분을 단순화한 코드 예시입니다.

```java
@Service
public class LlmPipelineService {

    private final Claude5Client claude5Client;
    private final Gpt4Client gpt4Client;

    public LlmPipelineService(Claude5Client claude5Client, Gpt4Client gpt4Client) {
        this.claude5Client = claude5Client;
        this.gpt4Client = gpt4Client;
    }

    public CompletableFuture<String> generateCleanResponse(String prompt) {
        // 1. Claude 5 호출
        CompletableFuture<String> rawResponseFuture = claude5Client.generateText(prompt);

        // 2. Claude 5 응답을 받은 후, GPT-4로 후처리
        return rawResponseFuture.thenCompose(rawResponse -> {
            String cleanupPrompt = buildCleanupPrompt(rawResponse);
            return gpt4Client.generateText(cleanupPrompt);
        });
    }

    private String buildCleanupPrompt(String rawText) {
        return "다음 텍스트에서 부적절한 부분을 제거하고 문법을 교정해줘:\n" + rawText;
    }
}
```

이 예시에서 `Claude5Client`와 `Gpt4Client`는 각각 외부 LLM API 호출을 추상화한 컴포넌트입니다. 실제 운영 환경에서는 호출 실패 대비 재시도, 타임아웃 설정, 로깅, 모니터링 등도 필수로 넣어야 하죠.


## 클라우드 환경에서 확장성과 지연시간을 어떻게 맞출까?

LLM을 두 번 호출하는 구조는 분명히 비용과 지연시간 부담이 큽니다. 그래서 클라우드 기반 백엔드에서는 다음과 같은 설계가 중요합니다.

- **비동기 처리와 큐잉**: 요청이 몰릴 때도 안정적으로 처리하려면 메시지 큐(RabbitMQ, Kafka 등)를 활용해 후처리 작업을 분리합니다.
- **멀티스레드/멀티인스턴스 확장**: 후처리 LLM 호출을 여러 워커 인스턴스가 병렬 처리하도록 합니다.
- **캐싱과 결과 재활용**: 동일 질문에 대해 후처리 결과를 캐싱해 중복 호출을 줄입니다.
- **지연시간 SLA 설정**: 후처리 지연시간 목표를 300~500ms 내외로 잡고, 이를 넘기면 원본 출력도 일부 허용하는 전략을 씁니다.

Cloudflare 엔지니어링 블로그 사례를 보면, 대규모 분산 시스템에서 이런 후처리 파이프라인을 운영하며 지연시간과 비용을 균형 있게 맞추는 노하우가 잘 정리되어 있습니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).


## Spring 기반 백엔드에서 모듈화로 유지보수성 높이기

우리 팀은 Claude 5와 후처리 LLM 호출을 각각 별도 모듈로 분리했습니다. 이렇게 하면 새로운 LLM 서비스가 나와도 인터페이스만 맞추면 쉽게 교체할 수 있고, 후처리 로직만 따로 개선도 가능합니다. 

InfoQ 아키텍처 가이드에서도 이런 모듈화와 인터페이스 분리가 장기적으로 유지보수성과 확장성에 큰 도움이 된다고 강조합니다[InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/).

예를 들어, `LlmClient` 인터페이스를 두고 Claude5Client, Gpt4Client가 이를 구현하도록 하면, 다음처럼 호출 코드를 깔끔하게 유지할 수 있습니다.

```java
public interface LlmClient {
    CompletableFuture<String> generateText(String prompt);
}

@Service
public class Claude5Client implements LlmClient {
    @Override
    public CompletableFuture<String> generateText(String prompt) {
        // Claude 5 API 호출 구현
    }
}

@Service
public class Gpt4Client implements LlmClient {
    @Override
    public CompletableFuture<String> generateText(String prompt) {
        // GPT-4 API 호출 구현
    }
}
```

이런 구조는 테스트 코드 작성도 훨씬 수월해지고, 장애 발생 시 어느 LLM에서 문제가 생겼는지 빠르게 파악하기도 좋습니다.


## 마무리하며: 두 번째 LLM 후처리, 꼭 해보자

처음엔 "LLM을 두 번 쓰면 비용도 늘고, 응답 속도도 느려지지 않을까?" 걱정이 컸는데, 실제로 해보니 AI 서비스 품질과 신뢰도가 확실히 올라가서 투자할 만한 가치가 있더라고요. 특히 Claude 5처럼 출력이 뛰어나지만 완벽하지 않은 모델을 쓸 때는 후처리 LLM 체인이 거의 필수라고 봅니다.

물론 단점도 있습니다. 비용 증가, 아키텍처 복잡도 상승, 지연시간 관리가 어려워지는 점이죠. 하지만 적절한 캐싱, 비동기 처리, 모듈화 설계로 충분히 극복 가능하고, 무엇보다 사용자 경험이 크게 개선됩니다.

여러분도 AI 백엔드 파이프라인에 Claude 5를 쓴다면, 꼭 두 번째 LLM으로 출력 정제하는 'Vomit' 처리 전략을 고려해보세요. 실제 운영 환경에서 이게 얼마나 큰 차이를 만드는지 직접 느끼실 수 있을 겁니다.
