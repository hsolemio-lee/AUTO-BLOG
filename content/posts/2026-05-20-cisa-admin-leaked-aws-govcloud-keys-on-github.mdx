## 깜짝 놀랄 만한 실수, CISA 관리자 AWS 키가 GitHub에 노출됐다?

얼마 전 CISA(미국 사이버보안 및 인프라 보안국) 관리자 계정에서 AWS GovCloud 자격 증명이 GitHub에 공개된 사건이 있었어요. "설마 우리 조직엔 이런 일이 없겠지" 하면서도, 막상 겪어보면 이런 실수는 생각보다 흔하다는 걸 깨닫게 됩니다. 특히 클라우드 환경에서 자격 증명 관리는 정말 까다로운 문제죠.

이번 사건은 단순한 실수 이상의 교훈을 줍니다. 어떻게 하면 이런 민감한 키를 안전하게 관리할 수 있을까요? 그리고 우리 서비스 아키텍처에서 어떤 선택과 절충이 필요한지 함께 고민해보죠.

## AWS Well-Architected Framework가 말하는 자격 증명 관리의 기본

AWS 공식 문서인 [AWS Well-Architected Framework](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html)에서는 자격 증명 보호를 위해 다음 두 가지를 가장 중요하게 꼽습니다.

- **IAM 역할과 권한 최소화 원칙(Least Privilege)** 적용
- **자격 증명을 코드나 공개 저장소에 절대 포함시키지 않기**

즉, 키를 직접 코드에 박아넣거나, GitHub 같은 곳에 올리는 건 절대 금기라는 거죠. 처음엔 이게 별거 아닌 것 같지만, 실제로 코드에 키가 박혀 있으면 누군가가 저장소를 복제만 해도 바로 노출됩니다.

이 원칙을 지키려면, IAM 역할을 최대한 세분화해서 꼭 필요한 권한만 주고, 키 대신 역할(Role)을 부여해 임시 자격 증명을 사용하는 방식을 권장합니다. 특히 AWS GovCloud처럼 민감한 환경일수록 더욱 엄격한 권한 관리가 필수입니다.

## 비밀 관리 서비스와 자동화 파이프라인으로 자격 증명 노출 막기

AWS Architecture Blog에서는 [AWS Secrets Manager](https://aws.amazon.com/blogs/architecture/) 같은 비밀 관리 서비스를 활용하라고 강조합니다. 이 서비스들은 자격 증명을 안전하게 암호화된 저장소에 보관하고, 필요할 때만 애플리케이션에 주입해줍니다.

예를 들어, CI/CD 파이프라인에서 다음과 같은 패턴을 쓸 수 있죠.

```yaml
# GitHub Actions 예시
name: Deploy to AWS
on: [push]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v2
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: us-gov-west-1
      - name: Deploy
        run: |
          aws cloudformation deploy --template-file template.yaml --stack-name my-stack
```

GitHub Actions 문서에 따르면, `secrets` 기능을 통해 자격 증명을 환경 변수로 주입하고, 로그에는 절대 노출되지 않도록 기본 설정되어 있습니다([GitHub Actions Documentation](https://docs.github.com/en/actions)).

이렇게 하면 키를 코드에 직접 넣지 않고, 파이프라인 내에서만 안전하게 사용할 수 있어요. 물론, 비밀 관리 서비스도 키 회전, 접근 권한 관리, 감사 로그 등 운영이 잘 되어야 효과적입니다.

## 개발자가 실수로 키를 올리는 걸 막는 자동화 스캔과 정책

GitHub Engineering Blog에서는 내부적으로 비밀 탐지 도구를 도입해, 개발자가 실수로 자격 증명을 공개 저장소에 올리는 걸 사전에 차단하는 프로세스를 운영한다고 합니다([GitHub Engineering Blog](https://github.blog/category/engineering/)).

우리도 이런 자동화 스캔 도구를 CI 파이프라인에 넣으면 좋습니다. 예를 들어, `git-secrets` 같은 오픈소스 도구를 활용하거나, 상용 솔루션을 도입할 수도 있죠.

```bash
# git-secrets 설치 및 사용 예
brew install git-secrets
git secrets --install
git secrets --register-aws

# 커밋 전에 자동 검사
git secrets --scan
```

이걸 통해 실수로라도 키가 커밋되면 바로 경고를 받고, 푸시가 차단됩니다. 물론 완벽한 해결책은 아니고, 개발 문화와 정책이 함께 뒷받침되어야 합니다.

## 키 노출 사고 후 빠른 대응과 키 회전 전략이 생명

Cloudflare 사례를 보면, 비밀이 노출됐을 때 가장 중요한 건 빠른 키 회전과 모니터링 체계 구축입니다([Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/)).

실제로 CISA 사건도 키가 노출된 즉시 해당 키를 폐기하고, 새 키를 발급해 접근 권한을 재설정하는 절차가 중요했죠. 이 과정에서 자동화된 스크립트와 알림 시스템이 큰 힘을 발휘합니다.

예를 들어, AWS CLI를 이용해 키를 회전하는 간단한 스크립트는 다음과 같습니다.

```bash
# 기존 액세스 키 비활성화
aws iam update-access-key --access-key-id OLD_KEY_ID --status Inactive --user-name my-user

# 새 액세스 키 생성
aws iam create-access-key --user-name my-user
```

이걸 수동으로 하면 실수도 많고 시간이 오래 걸리니, 키 회전 정책과 자동화 스크립트를 미리 준비해두는 게 좋습니다.

## 직접 겪어보니 알게 된 IAM 역할과 권한 최소화의 중요성

우리 팀도 한때 AWS 키를 직접 코드에 박아넣고 배포하다가, 키가 유출된 적이 있었어요. 그때부터 IAM 역할을 적극 활용하고, 권한을 꼭 필요한 수준으로만 제한하는 정책을 엄격히 적용했습니다.

예를 들어, EC2 인스턴스 프로파일에 S3 접근 권한만 주고, 다른 서비스는 아예 접근 불가하도록 설정했죠. 이렇게 하면 키가 유출돼도 피해 범위를 최소화할 수 있습니다.

이건 실제로 겪어보면, "권한 최소화가 귀찮은 게 아니라 생명선"이라는 걸 몸소 깨닫게 됩니다.

## 마치며: 클라우드 자격 증명 보안, 결국은 사람과 프로세스의 문제

이번 CISA 관리자 키 유출 사건은 기술적 문제뿐 아니라, 조직 내 보안 문화와 프로세스의 중요성을 다시 한번 일깨워줍니다. 아무리 좋은 도구와 아키텍처를 써도, 개발자가 실수하면 사고는 발생하니까요.

- **코드에 키를 직접 넣지 말고 IAM 역할과 비밀 관리 서비스 활용하기**
- **CI/CD 파이프라인에서 비밀을 안전하게 주입하고, 로그 노출 방지하기**
- **자동화된 비밀 탐지 도구로 실수 예방하기**
- **키 노출 사고 시 빠른 키 회전과 모니터링 체계 갖추기**

이 네 가지를 꼭 실천해보세요. 처음엔 번거롭고 복잡해 보여도, 사고 나서 복구하는 것보다 훨씬 낫습니다.

우리 모두 이런 실수를 줄이고, 더 안전한 클라우드 환경을 만드는 데 힘써 봅시다.
