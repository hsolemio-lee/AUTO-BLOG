## "AI 통합, 그냥 라이브러리 하나 붙이면 끝일까?"

최근 우리 팀에서 Spring AI 2.0.0-M4와 1.1.4, 1.0.5 버전을 프로덕션 백엔드에 적용하면서 느낀 점이 있어요. AI 모델 호출이 단순히 API 호출하는 것 이상의 복잡성을 가진다는 걸 다시 한 번 실감했습니다. 특히 보안, 성능, 그리고 운영 안정성 측면에서 말이죠.

Spring Boot 3.x부터 AI 통합을 위한 새로운 모듈과 설정 옵션이 도입됐는데, 2.0.0-M4는 이걸 한 단계 더 발전시켜 AI 모델 호출과 관리, 보안 설정을 훨씬 간편하게 만들어줍니다. 하지만 실제로 프로덕션에 적용할 때는 단순히 의존성 추가하고 @Bean 등록하는 것만으로 끝나지 않아요. 이번 글에서는 제가 직접 겪은 시행착오와 함께, 어떻게 하면 최신 Spring AI를 안전하고 효율적으로 운영할 수 있는지 자세히 이야기해보겠습니다.

## Spring AI 2.0.0-M4가 기존 1.x 버전과 다른 점은?

먼저 Spring AI 1.1.4 및 1.0.5 버전은 기존 Spring Boot 프로젝트에 무리 없이 통합할 수 있는 안정적인 버전입니다. API 키 관리, 토큰 보안, 요청 제한(rate limiting) 등 프로덕션 환경에서 꼭 필요한 보안 기능이 기본적으로 포함되어 있죠. 

하지만 2.0.0-M4는 Spring Boot 3.x의 새로운 모듈 시스템과 설정 옵션을 적극 활용해 AI 모델 호출 로직을 더 깔끔하게 분리하고, 보안 설정도 훨씬 직관적으로 바꿨습니다. 예를 들어, AI 서비스별로 별도의 클라이언트 빈을 등록하고, 호출 시점에 AOP를 통해 트랜잭션과 예외 처리를 체계적으로 관리할 수 있어요[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

이전 버전에서는 AI 호출 코드가 비즈니스 로직에 섞여 유지보수가 까다로웠는데, 2.0.0-M4는 의존성 주입과 AOP를 적극 활용해 호출 로직을 완전히 분리할 수 있다는 점이 큰 장점입니다[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

## 프로덕션에서 AI 호출 성능과 안정성을 어떻게 챙길까?

AI 모델 호출은 보통 외부 API를 호출하는 형태라서 네트워크 지연과 호출 실패에 취약할 수밖에 없습니다. 그래서 스레드 풀 크기 조절, 비동기 처리, 캐싱 전략은 필수로 고려해야 해요.

예를 들어, 우리 팀은 스레드 풀 크기를 기본 10에서 50으로 늘리고, CompletableFuture 기반 비동기 호출을 도입했습니다. 덕분에 AI 호출이 많아져도 메인 스레드가 막히지 않고, 응답 지연이 30% 이상 줄었어요. 그리고 AI 응답 결과는 5분 단위 TTL 캐시를 걸어 중복 호출을 줄였습니다. 이렇게 하니 API 호출 비용도 절감되고, 사용자 체감 성능도 개선됐죠[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

```java
@Service
public class AiService {

    private final ExecutorService aiExecutor = Executors.newFixedThreadPool(50);
    private final Cache<String, String> responseCache = CacheBuilder.newBuilder()
            .expireAfterWrite(5, TimeUnit.MINUTES)
            .build();

    public CompletableFuture<String> callAiModelAsync(String prompt) {
        String cached = responseCache.getIfPresent(prompt);
        if (cached != null) {
            return CompletableFuture.completedFuture(cached);
        }

        return CompletableFuture.supplyAsync(() -> {
            // 실제 AI 모델 호출 코드 (예: OpenAI API)
            String response = callExternalAiApi(prompt);
            responseCache.put(prompt, response);
            return response;
        }, aiExecutor);
    }

    private String callExternalAiApi(String prompt) {
        // API 키 보안, 요청 제한 등은 별도 설정으로 관리
        // 호출 실패 시 재시도 로직도 추가 가능
        return "AI 응답 결과";
    }
}
```

이 코드는 AI 호출을 비동기로 처리하면서 동시에 캐싱까지 적용한 예입니다. 물론 스레드 풀 크기를 너무 크게 하면 자원 낭비가 될 수 있고, 캐시 TTL을 너무 길게 잡으면 최신 데이터를 못 받을 수 있으니 서비스 특성에 맞게 꼭 튜닝해야 합니다.

## API 키 관리와 보안, 어떤 점에 주의해야 할까?

AI API 키는 서비스의 생명줄과 같아서 노출되면 큰 사고로 이어집니다. Spring AI 1.1.4, 1.0.5 버전은 API 키를 안전하게 관리할 수 있는 기능을 제공합니다. 예를 들어, 키를 애플리케이션 프로퍼티에 직접 쓰지 않고, Vault나 AWS Secrets Manager 같은 외부 비밀관리 시스템과 연동해 불필요한 노출을 막을 수 있죠[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

또한 OpenAI API 문서에서는 요청 제한(rate limiting)과 에러 핸들링, 재시도 전략을 반드시 적용하라고 권고합니다. 우리 팀은 Spring Retry 라이브러리를 도입해 429 Too Many Requests 에러가 발생하면 3회까지 지수 백오프 방식으로 재시도하도록 했어요. 이렇게 하면 일시적인 호출 실패에도 서비스가 멈추지 않고 안정적으로 동작합니다[OpenAI API Documentation](https://platform.openai.com/docs/overview).

```yaml
spring:
  ai:
    openai:
      api-key: ${OPENAI_API_KEY}
      retry:
        max-attempts: 3
        backoff:
          delay: 1000
          multiplier: 2
```

이 설정은 Spring AI 모듈이 제공하는 재시도 옵션을 활용한 예시입니다. 실제로는 네트워크 상태나 API 호출 패턴에 따라 재시도 횟수와 대기 시간을 조절해야 합니다.

## 프롬프트 엔지니어링과 동적 관리가 왜 중요한가?

AI 모델과의 상호작용 품질은 프롬프트 설계에 크게 좌우됩니다. Anthropic 가이드에 따르면, 프롬프트를 어떻게 구성하고 튜닝하느냐에 따라 모델의 응답 정확도와 유용성이 달라진다고 하죠. 

Spring AI를 쓸 때는 프롬프트를 하드코딩하는 대신, 서비스 요구사항에 맞춰 동적으로 생성하고 관리하는 전략이 효과적입니다. 예를 들어, 사용자 입력을 기반으로 프롬프트 템플릿을 조합하거나, 최근 대화 이력을 포함해 컨텍스트를 풍부하게 만드는 방식이 있습니다[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

```java
public String buildPrompt(UserInput input) {
    String template = "당신은 친절한 상담사입니다. 다음 질문에 답해주세요: %s";
    return String.format(template, input.getQuestion());
}
```

이런 식으로 프롬프트를 분리해 관리하면, 나중에 AI 모델을 교체하거나 프롬프트를 개선할 때 훨씬 유연하게 대응할 수 있습니다.

## 현업에서 느낀 Spring AI 통합의 딜레마

처음엔 AI 통합이 단순히 외부 API 호출하는 것 같았는데, 막상 해보니 보안, 성능, 유지보수 모두 신경 쓸 게 한두 가지가 아니더군요. 특히 AI 호출이 많아질수록 호출 실패에 따른 장애 위험도 커지고, API 비용도 무시 못할 수준입니다.

그래서 우리 팀은 다음과 같은 원칙을 세웠습니다.

- AI 호출은 반드시 비동기 처리하고, 호출 실패 시 재시도와 대체 로직을 둔다.
- API 키와 민감 정보는 외부 비밀관리 시스템과 연동해 노출을 최소화한다.
- 프롬프트는 서비스별로 분리하고, 동적으로 생성해 관리한다.
- 캐싱과 스레드 풀 튜닝으로 성능 저하를 방지한다.

이 원칙들을 지키면서 Spring AI 2.0.0-M4와 1.x 버전을 조합해 쓰니, 안정적이고 확장성 있는 AI 통합 백엔드를 만들 수 있었습니다.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
