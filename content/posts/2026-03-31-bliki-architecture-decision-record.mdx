### "왜 이걸 선택했지?"라는 질문에 답할 준비가 되어 있나요?

팀에서 중요한 아키텍처 결정을 내릴 때, 나중에 "왜 이걸 선택했지?"라는 질문이 꼭 따라오죠. 특히 백엔드나 클라우드 플랫폼처럼 복잡한 시스템에서는 의사결정의 배경과 이유를 체계적으로 기록해두지 않으면, 나중에 혼란이 커집니다. 저도 초기에는 그냥 회의록이나 슬랙 메시지에 의존했는데, 시간이 지나면서 결정의 맥락이 사라져서 고생한 경험이 많아요.

이럴 때 효과적인 도구가 바로 Architecture Decision Record(ADR)입니다. ADR은 단순한 문서가 아니라, 설계 결정의 ‘역사’와 ‘이유’를 담는 살아있는 기록입니다. 오늘은 제가 실무에서 ADR을 어떻게 작성하고, 운영 환경 제약까지 녹여내는지 구체적으로 얘기해볼게요.

---

## ADR을 쓰면 정말 뭐가 좋아질까?

우선 ADR이 왜 필요한지부터 짚고 넘어가죠. Martin Fowler가 말했듯이, ADR은 설계 결정의 배경과 대안, 그리고 선택한 이유를 명확히 기록해서 팀 내 지식 공유와 유지보수에 필수적입니다[Martin Fowler - Microservices](https://martinfowler.com/articles/microservices.html). 

제가 경험한 가장 큰 장점은 신규 팀원이 합류했을 때 의사결정의 맥락을 빠르게 이해할 수 있다는 점이에요. 예를 들어, 어떤 API 게이트웨이 도입을 결정한 이유가 비용 절감인지, 성능 개선인지, 아니면 보안 때문인지 명확히 알 수 있으니 온보딩 시간이 확 줄더라고요. 

또한, ADR 덕분에 설계 변경의 히스토리를 추적할 수 있어서, “왜 이전에 이 방식을 버렸지?” 같은 질문에 바로 답할 수 있습니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

## 트레이드오프와 마이그레이션 경로까지 담아야 하는 이유

단순히 "이걸 선택했다"라고만 적으면 ADR의 가치가 반감됩니다. 설계 결정에는 항상 트레이드오프가 있기 때문이죠. 예를 들어, 마이크로서비스 아키텍처를 도입할 때는 서비스 간 통신 비용과 독립 배포의 장단점을 모두 고려해야 합니다. 

Microsoft의 클라우드 디자인 패턴 문서에서도 강조하듯이, ADR에는 이런 트레이드오프뿐 아니라 시스템 마이그레이션 경로, 즉 기존 모놀리식에서 마이크로서비스로 전환할 때 어떤 단계와 위험을 거쳤는지도 포함해야 합니다[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/).

제가 한 프로젝트에서는 기존 배치 처리 시스템을 실시간 스트리밍 처리로 바꾸면서 ADR에 마이그레이션 계획과 예상되는 다운타임, 롤백 전략을 상세히 기록했어요. 덕분에 실제 배포 때 예상치 못한 문제에 빠르게 대응할 수 있었습니다.

## 운영 환경 제약을 ADR에 녹여내는 방법

이건 실제로 겪어보면 꽤 중요한데, ADR에 현실적인 운영 제약을 포함시키는 걸 빼먹으면 문서가 공허해집니다. 예를 들어, 배포 자동화나 CI/CD 파이프라인과 어떻게 연동되는지, 특정 클라우드 서비스의 제한사항은 무엇인지 명시해야 합니다.

GitHub Actions를 사용한 CI/CD 파이프라인 통합 경험을 예로 들어볼게요. 우리 팀은 ADR에 다음과 같은 내용을 넣었습니다:

- 배포 스크립트가 GitHub Actions 워크플로우로 자동 실행됨
- 특정 서비스는 롤링 업데이트만 지원하며, 블루/그린 배포는 불가능
- 배포 실패 시 자동 롤백 조건과 알림 체계

```yaml
name: Deploy to Production
on:
  push:
    branches:
      - main
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v3
      - name: Deploy service
        run: |
          ./deploy.sh --env production
      - name: Notify on failure
        if: failure()
        uses: actions/github-script@v6
        with:
          script: |
            github.issues.createComment({
              issue_number: 123,
              body: '배포 실패! 즉시 확인 필요.'
            })
```

이런 구체적인 운영 제약과 자동화 흐름을 ADR에 명시하면, 설계 결정이 단순한 이론이 아니라 현실적인 실행 계획과 맞닿아 있음을 모두가 이해할 수 있습니다[GitHub Actions Documentation](https://docs.github.com/en/actions).

## ADR을 계속 업데이트하는 게 왜 중요한가

클라우드 환경은 계속 변합니다. 새로운 서비스가 나오고, 아키텍처 패턴도 발전하죠. 그래서 ADR도 한 번 쓰고 끝나는 게 아니라 살아있는 문서로 관리해야 합니다. 

Microsoft 문서에서는 ADR이 변화하는 인프라와 서비스 패턴에 맞춰 지속적으로 업데이트되어야 한다고 강조합니다[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/). 실제로 우리 팀도 매 분기마다 ADR 리뷰 세션을 갖고, 새로 적용한 패턴이나 기술 도입으로 인한 변경 사항을 반영합니다.

이 과정에서 중요한 건, ADR이 너무 장황해지지 않도록 핵심 내용 위주로 간결하게 유지하는 겁니다. 그래야 읽는 사람도 부담 없이 참고할 수 있거든요.

## 실전에서 쓸 수 있는 ADR 템플릿 예시

마지막으로, 제가 자주 쓰는 간단한 ADR 템플릿을 공유할게요. Markdown 형식으로 작성하며, 필요에 따라 확장하면 됩니다.

```markdown
# ADR 001: API Gateway 도입 결정

## 상태
승인됨

## 맥락
- 기존 모놀리식 서비스에서 마이크로서비스로 전환 중
- 인증, 라우팅, 로깅 일관성 필요

## 결정
- Kong API Gateway를 도입하기로 결정

## 고려한 대안
- 직접 구현: 개발 비용 및 유지보수 부담 큼
- AWS API Gateway: 비용 과다 예상

## 트레이드오프
- Kong 도입으로 초기 학습 비용 발생
- 자체 호스팅 필요, 운영 부담 증가

## 마이그레이션 경로
1. 내부 테스트 환경에 Kong 배포
2. 일부 서비스 트래픽만 라우팅
3. 점진적 전환 및 모니터링

## 운영 제약
- 배포는 GitHub Actions 파이프라인 통해 자동화
- 롤백 스크립트 준비 완료

## 참고
- Kong 공식 문서
- GitHub Actions 워크플로우 설정
```

이 정도만 갖춰도 팀원들이 의사결정 과정을 빠르게 이해하고, 실무에 바로 적용할 수 있습니다.

### 마치며

ADR은 단순히 문서화하는 작업이 아니라, 팀의 설계 철학과 운영 현실을 연결하는 다리입니다. 처음엔 "귀찮다" 싶지만, 한 번 제대로 만들어두면 나중에 팀 전체가 엄청난 시간을 절약할 수 있어요. 

꼭 기억할 점은, ADR에 트레이드오프와 마이그레이션 경로, 그리고 현실적인 운영 조건까지 담아야 실무에서 진짜 도움이 된다는 겁니다. 그리고 ADR은 한 번 쓰고 끝나는 게 아니라, 변화에 맞춰 계속 업데이트해야 한다는 것도요.

다음 프로젝트에서 중요한 아키텍처 결정을 내릴 때, 오늘 이야기한 내용을 떠올리며 ADR을 꼭 작성해보세요. 나중에 "왜 이걸 선택했지?"라는 질문이 와도 당당하게 답할 수 있을 겁니다.
