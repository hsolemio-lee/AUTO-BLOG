## 갑자기 Spring Boot를 3.5.13로 올려야 할 때, 어디서부터 시작해야 할까?

얼마 전 우리 팀에서 운영 중인 서비스에 Spring Boot 3.5.13 버전으로 업그레이드를 고민하다가 꽤 골치 아픈 상황을 마주쳤다. 최신 버전이니 당연히 성능도 좋아지고 보안도 강화됐겠지 싶은데, 막상 프로덕션에 적용하려니 어떤 설정을 조절해야 하고, 배포는 어떻게 하면 안전할지 감이 안 잡혔다. 그래서 직접 문서와 실무 경험을 뒤져가며 얻은 노하우들을 공유하려 한다.

## Spring Boot 3.5.13에서 실제로 달라진 성능 최적화 포인트

이번 3.5.13 버전은 기존보다 내장 캐싱 메커니즘이 훨씬 똑똑해졌다. 특히 `@Cacheable` 애노테이션을 붙인 메서드가 비동기 처리와 결합될 때, 캐시 적중률과 응답 속도가 눈에 띄게 개선됐다. 예를 들어, 다음과 같은 코드가 있다고 치자:

```java
@Service
public class ProductService {

    @Cacheable(value = "products", key = "#id")
    @Async
    public CompletableFuture<Product> getProductById(Long id) {
        // DB 호출 등 무거운 작업
        return CompletableFuture.completedFuture(productRepository.findById(id).orElse(null));
    }
}
```

이전 버전에서는 `@Async`와 `@Cacheable` 조합이 의도대로 동작하지 않거나 캐시 미스가 잦았는데, 3.5.13부터는 내부적으로 비동기 캐시 업데이트가 최적화되어 실제 운영 환경에서 CPU와 I/O 부하가 줄었다. 이건 문서에도 명확히 언급되어 있다.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)

또 JVM 힙 메모리 조정과 쓰레드 풀 설정도 이번 버전에서 중요해졌다. GC 튜닝을 조금만 소홀히 해도 전체 응답 지연이 급격히 늘어난다. 예를 들어, 운영 환경에서 다음과 같은 JVM 옵션을 권장한다:

```
-Xms4g -Xmx4g -XX:+UseG1GC -XX:MaxGCPauseMillis=200
```

G1 GC를 쓰면서 최대 GC 일시 중단 시간을 200ms로 제한하는 게 핵심이다. 쓰레드 풀도 기본값에서 벗어나 CPU 코어 수에 맞춰 조절하자. 예를 들어 8코어 서버라면:

```yaml
spring:
  task:
    execution:
      pool:
        core-size: 16
        max-size: 32
        queue-capacity: 100
```

이렇게 하면 비동기 작업이 몰려도 큐가 넘치지 않고 적절히 분산된다.[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance)

## 보안 강화는 기본, CSRF와 OAuth2 설정 꼼꼼히 챙기기

3.5.13 버전에서 보안 쪽도 꽤 신경 썼다. 특히 CSRF(Cross-Site Request Forgery) 보호가 기본적으로 강화되어, 별도 설정 없이도 POST, PUT, DELETE 요청에 대해 더 엄격한 검증이 들어간다. 만약 REST API 서버라면 다음처럼 Security 설정에 `csrf().disable()`을 꼭 명시해줘야 한다.

```java
@EnableWebSecurity
public class SecurityConfig extends WebSecurityConfigurerAdapter {
    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
            .csrf().disable() // REST API라면 비활성화 권장
            .authorizeRequests()
            .anyRequest().authenticated()
            .and()
            .oauth2Login();
    }
}
```

OAuth2 클라이언트 설정도 기본값이 강화되어, 외부 인증 서버와의 통신 시 토큰 검증 로직이 보다 엄격해졌다. 이 덕분에 토큰 탈취 공격에 대한 방어가 강화됐지만, 기존에 커스텀 토큰 검증 로직을 쓰던 경우에는 반드시 문서 확인 후 설정을 맞춰야 한다.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)

## 무중단 업그레이드를 위한 배포 전략, 카나리와 블루-그린 배포의 현실적 선택

실제 운영 환경에서 버전을 올릴 때 가장 고민되는 부분은 '서비스 중단 없이 안전하게 롤아웃하는 방법'이다. 3.5.13으로 업그레이드할 때 우리 팀이 택한 방법은 점진적 배포, 즉 카나리 배포였다. 새로운 버전을 소수의 서버에 먼저 올리고, 모니터링 후 문제가 없으면 점차 전체 서버로 확장하는 방식이다.

이 과정에서 트래픽 분산을 위해 다음과 같은 Nginx 설정을 썼다:

```nginx
upstream backend {
    server backend-v3.5.13-1:8080 weight=1;
    server backend-v3.5.13-2:8080 weight=1;
    server backend-v3.4.x-1:8080 weight=8;
}

server {
    listen 80;
    location / {
        proxy_pass http://backend;
    }
}
```

초기에는 10% 트래픽만 새 버전으로 보내고, 문제가 없으면 50%, 100%로 늘리는 식이다. 블루-그린 배포도 고려했지만, 인프라 리소스 부담과 DNS 캐시 문제 때문에 우리 환경에서는 카나리가 더 적합했다.[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance)

## 최신 자바 버전과의 호환성, 그리고 모듈화 강화는 어떻게 느껴질까?

3.5.13은 자바 17 이상을 공식 지원하면서, 모듈화와 의존성 주입 부분에서 내부적으로 더 견고해졌다. 예전에는 라이브러리 충돌이나 빈 등록 순서 문제로 애를 먹었는데, 이번 버전은 `@Configuration` 클래스가 더 명확하게 처리되고, 모듈 경계가 엄격해져서 디버깅 시간이 줄었다.

예를 들어 다음과 같이 `@Import`를 활용한 모듈화 구성이 더 안정적이다:

```java
@Configuration
@Import({UserModuleConfig.class, PaymentModuleConfig.class})
public class AppConfig {
    // 공통 빈 설정
}
```

이 덕분에 대형 프로젝트에서 의존성 주입 충돌 없이 각 모듈을 독립적으로 관리하기가 훨씬 수월해졌다.[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)

## 직접 겪어보니 알게 된, 업그레이드 전 꼭 체크해야 할 것들

- **캐시 정책 점검**: 캐시 키 생성 로직과 TTL 설정이 바뀌었는지 확인하자. 비동기 캐시 업데이트가 기본이지만, 잘못 설정하면 오히려 부하가 늘어난다.
- **JVM 튜닝**: GC 로그를 꼭 활성화해서, 프로덕션에서 GC가 너무 자주 발생하는지 모니터링하자.
- **보안 설정**: CSRF와 OAuth2 설정이 기본 강화됐으니, 기존 커스텀 보안 로직과 충돌하는 부분이 없는지 테스트가 필수다.
- **배포 전략**: 카나리 배포를 하더라도, 롤백 시나리오를 미리 준비해두자. 3.5.13에서 새롭게 추가된 기능이 기존 API와 호환되지 않는 경우가 있을 수 있다.

---

Spring Boot 3.5.13은 분명히 여러모로 진화한 버전이다. 하지만 "최신이라 무조건 좋다"는 생각보다는 실제 운영 환경 특성에 맞춰 튜닝하고, 보안 설정을 꼼꼼히 점검하며, 안전한 배포 전략을 세우는 게 더 중요하다. 이런 경험을 공유하는 게 나만의 팁이자, 우리 모두가 겪는 시행착오를 줄이는 길이라고 믿는다.
