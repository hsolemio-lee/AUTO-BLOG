## "내가 보낸 프롬프트와 모델 답변, 누가 훔쳐볼까?"

최근에 우리 팀이 외부 LLM API를 백엔드에 붙이면서 가장 걱정했던 게 바로 이거였다. 민감한 비즈니스 로직이나 고객 데이터가 API 요청과 응답에 포함되면, 그 정보가 외부 서버에 그대로 저장되거나 로그에 남아 유출될 수 있다는 점 말이다. 특히, 모델이 내부에서 어떻게 추론하는지 그 과정(추론 트레이스)이 프롬프트나 응답에 드러난다면, 더 심각한 정보 노출 위험으로 이어질 수 있다.

내가 직접 겪은 사례를 하나 들자면, 한 프로젝트에서 사용자 질문을 LLM에 넘길 때, 내부 상태를 설명하는 디버깅용 프롬프트를 함께 보내고 있었다. 그런데 나중에 확인해보니, 그 디버깅 정보가 API 응답에 포함되어 외부에 노출된 걸 발견했다. 이걸 보고 나서야 "아, 이게 단순한 텍스트 교환이 아니라, 추론 과정 자체가 데이터가 될 수 있구나" 싶었다.

## 왜 LLM API 호출 시 추론 데이터 유출 위험이 높을까?

OpenAI 공식 문서에 따르면, API 호출 시 우리가 보내는 프롬프트와 모델이 생성한 응답 모두가 서버로 전송되고 처리된다. 즉, 우리 데이터가 외부 클라우드에 그대로 노출될 가능성이 있다는 뜻이다. 특히, 민감한 정보가 포함된 경우엔 더 조심해야 한다고 명시되어 있다. 그래서 OpenAI 측도 API 호출 시 데이터 암호화와 최소한의 정보만 보내는 전략을 권장한다([OpenAI API Documentation](https://platform.openai.com/docs/overview)).

Anthropic의 프롬프트 엔지니어링 가이드를 보면, LLM 내부 추론 과정이 프롬프트와 응답에 포함될 수 있다는 점을 강조한다. 다시 말해, 우리가 의도하지 않아도 모델이 생각하는 과정의 일부가 노출될 수 있다는 거다. 그래서 프롬프트 설계 단계에서 추론 트레이스가 API 응답에 드러나지 않도록 신경 써야 한다고 한다([Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)).

## 로그에 민감한 추론 데이터가 남는다면?

GitHub 엔지니어링 블로그에서는 외부 LLM API를 백엔드에 통합할 때, API 요청과 응답이 로그에 기록되면서 민감 데이터가 노출될 수 있다고 경고한다. 실제로 로그에 프롬프트 전문이나 모델 응답이 그대로 남으면, 내부 개발자나 운영자가 접근할 수 있는 모든 곳에서 데이터가 노출될 위험이 있다. 그래서 로그 필터링과 접근 제어를 철저히 해야 한다고 조언한다([GitHub Engineering Blog](https://github.blog/category/engineering/)).

우리 팀도 로그에 프롬프트와 응답을 그대로 찍는 게 기본 설정이었는데, 민감한 정보가 포함된 요청은 별도의 마스킹 로직을 넣어 필터링하도록 개선했다. 예를 들어, 사용자 이름, 이메일 같은 개인정보는 `****`로 치환하고, 내부 코드나 비즈니스 로직이 담긴 부분은 로그에서 제외했다.

```python
# Python 예시 - 로그에 민감한 부분 마스킹하기
import re

def mask_sensitive_info(text):
    # 이메일 패턴 마스킹
    text = re.sub(r'\b[\w.-]+@[\w.-]+\.\w{2,4}\b', '****@****.***', text)
    # 전화번호 패턴 마스킹
    text = re.sub(r'\b\d{3}[-.]?\d{3}[-.]?\d{4}\b', '***-***-****', text)
    return text

# API 요청 로그 기록 시
raw_prompt = "사용자 이메일: user@example.com, 질문: ..."
safe_prompt = mask_sensitive_info(raw_prompt)
print(f"API 요청 프롬프트: {safe_prompt}")
```

이 간단한 마스킹만으로도 로그에 중요한 정보가 남는 걸 크게 줄일 수 있었다.

## 데이터 전송 과정과 저장을 어떻게 안전하게 할 수 있을까?

Cloudflare 블로그의 사례를 보면, 클라우드 기반 LLM API 통합 시 데이터 전송 과정에서 TLS 암호화를 기본으로 적용하고, 백엔드 내에서는 가능한 한 추론 데이터 저장을 최소화하는 전략을 쓴다. 그리고 API 호출 시점에 실시간 모니터링 시스템을 도입해 비정상적인 데이터 접근이나 유출 시도를 탐지한다는 점이 인상적이었다([Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/)).

우리도 HTTPS는 당연히 적용했고, API 응답을 DB에 저장하는 대신 캐시나 메모리에서만 잠깐 보관하도록 바꿨다. 또, API 호출 로그를 실시간으로 분석해 평소와 다른 패턴(예: 너무 긴 프롬프트, 반복적인 민감 데이터 포함 요청 등)이 감지되면 알림을 받도록 설정했다.

## 마이크로서비스 아키텍처에서 추론 데이터 유출을 막는 설계법

마틴 파울러는 외부 API 통합 시 데이터 캡슐화와 API 게이트웨이에서의 보안 정책 적용을 권장한다. 백엔드 시스템 내에서 LLM API를 호출하는 부분을 별도 서비스로 분리하고, 이 서비스가 외부와 주고받는 데이터를 엄격히 제한하는 방식이다. 이렇게 하면 추론 데이터가 전체 시스템에 퍼지는 걸 막고, 보안 정책 적용도 집중할 수 있다([Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/)).

우리 팀도 LLM API 호출을 담당하는 마이크로서비스를 따로 만들었고, 이 서비스는 내부 네트워크에서만 접근 가능하도록 설정했다. 그리고 API 게이트웨이에서 JWT 토큰 검증과 IP 화이트리스트를 적용해 승인된 요청만 처리하도록 했다. 이 덕분에 추론 데이터가 노출될 가능성이 크게 줄었다.

---

### 정리하며: 실제로 써보니 이런 점이 중요했다

- **프롬프트 설계에 신경 쓰자.** 내부 추론 과정이 노출되지 않도록 불필요한 디버깅 정보나 내부 상태를 프롬프트에 넣지 말자.
- **로그는 반드시 필터링하자.** 민감한 정보는 마스킹하거나 로그에 남기지 않는 게 기본이다.
- **데이터 전송과 저장은 최소화하고 암호화하자.** HTTPS/TLS는 필수고, DB 저장은 꼭 필요한 경우에만 하자.
- **마이크로서비스와 API 게이트웨이로 경계 설정하자.** 권한과 접근을 엄격히 관리하는 게 효과적이다.
- **실시간 모니터링과 알림 체계를 구축하자.** 이상 징후를 빨리 감지해야 대응이 가능하다.

처음엔 "API 쓰는 게 뭐 그리 복잡해?" 싶었는데, 직접 경험해보니 이게 생각보다 까다롭고 중요한 문제였다. 특히 민감한 추론 데이터가 외부에 노출되면, 법적·윤리적 문제는 물론 서비스 신뢰도에도 치명타가 될 수 있다. 그래서 LLM API를 백엔드에 통합할 때는 꼭 위에서 얘기한 여러 층위의 방어책을 함께 고민해야 한다.

여러분도 LLM API를 쓸 때, "내 데이터가 어떻게 흘러가는지" 한 번 꼼꼼히 점검해보길 추천한다.
