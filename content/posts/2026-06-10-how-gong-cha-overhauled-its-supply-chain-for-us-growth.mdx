## 미국 시장에서 Gong Cha가 공급망 시스템을 다시 설계한 이유

"왜 갑자기 Gong Cha가 미국에서 주문이 밀리면서 재고가 부족하다고?"라는 질문을 들었을 때, 저도 처음엔 단순한 수요 예측 실패 정도로 생각했어요. 그런데 실제로는 공급망 전반을 아우르는 시스템적 문제였다는 걸 알게 됐죠. 미국 시장은 한국과 달리 유통 구조, 물류 인프라, 고객 행동 패턴이 완전히 다르다 보니 기존 시스템을 그대로 쓰면 한계가 명확했습니다.

특히 Gong Cha처럼 프랜차이즈가 전국에 퍼져 있고, 원재료부터 컵, 빨대 같은 소모품까지 다양한 품목을 관리해야 하는 경우, 재고 관리와 주문 처리 시스템의 정확도가 사업 성패를 좌우해요. 이 과정에서 IT팀은 기존 백엔드 시스템을 전면 재검토하고, 점진적 배포 전략을 도입해 리스크를 줄이면서도 빠르게 개선해 나갔습니다.


## 점진적 배포 전략으로 신규 기능을 안전하게 도입한 사례

처음에 신규 백엔드 기능을 한꺼번에 다 바꾸는 건 너무 위험했어요. 특히 주문 처리 로직이나 재고 업데이트 같은 핵심 기능은 장애가 나면 매출에 바로 타격이 오니까요. 그래서 Gong Cha 팀은 작은 범위의 점진적 배포 전략을 선택했습니다. 예를 들어 전체 매장 중 5%만 새로운 재고관리 API를 사용하도록 설정하고, 모니터링을 강화했죠.

이렇게 하니 문제 발생 시 빠르게 롤백할 수 있었고, 운영 리스크가 크게 줄었습니다. 실제로 TypeScript 핸드북에서도 점진적 배포가 신규 백엔드 기능의 운영 리스크를 낮춘다고 명시하고 있죠[TypeScript Handbook](https://www.typescriptlang.org/docs/handbook/intro.html).

```typescript
// 재고 업데이트 API의 점진적 배포 예시
interface InventoryUpdate {
  productId: string;
  quantityChange: number;
}

// 기존 API
function updateInventoryLegacy(update: InventoryUpdate): boolean {
  // 기존 로직
  return true;
}

// 신규 API - 점진적 배포 대상
function updateInventoryNew(update: InventoryUpdate): boolean {
  // 개선된 트랜잭션 처리
  try {
    // DB 트랜잭션 시작
    // 재고 수량 업데이트
    // 트랜잭션 커밋
    return true;
  } catch (e) {
    // 롤백
    return false;
  }
}

// 배포 시점에 플래그로 제어
const useNewInventoryAPI = (storeId: string) => {
  const rolloutStores = new Set(['store-001', 'store-023', 'store-045']);
  return rolloutStores.has(storeId);
}

function updateInventory(storeId: string, update: InventoryUpdate): boolean {
  if (useNewInventoryAPI(storeId)) {
    return updateInventoryNew(update);
  } else {
    return updateInventoryLegacy(update);
  }
}
```

이 코드는 매장별로 새로운 API를 점진적으로 적용하는 예시입니다. 실제 운영 환경에서는 더 정교한 피처 플래그 관리 시스템과 장애 모니터링이 함께 동작하죠.


## 초기부터 장애 유형을 계측해 유지보수성을 높인 경험

Gong Cha 미국 법인에서 가장 크게 느낀 점 중 하나는, 장애가 났을 때 "왜"가 아니라 "어떤 종류의 장애인지"를 바로 파악하는 게 얼마나 중요한가였어요. 초기부터 실패 유형을 세분화해서 계측하지 않으면, 문제 원인 분석에만 몇 시간이 걸리기도 하더라고요.

그래서 팀에서는 API 호출 실패, DB 트랜잭션 롤백, 재고 불일치 등 주요 실패 유형을 로깅하고, 이를 대시보드로 실시간 모니터링했습니다. 덕분에 장애 대응 속도가 눈에 띄게 빨라졌고, 유지보수 작업도 체계적으로 진행할 수 있었죠.

이 부분은 TypeScript 5.x 릴리즈 노트에서도 실패 유형 초기 계측이 유지보수성과 장애 대응 속도 개선에 효과적이라고 강조합니다[TypeScript 5.x Release Notes](https://devblogs.microsoft.com/typescript/announcing-typescript-5-4/).


## 재고와 주문 처리 시스템 통합, 그리고 예상치 못한 트레이드오프

공급망 시스템을 전면 개편하면서 가장 까다로웠던 부분은 재고 시스템과 주문 처리 시스템의 통합이었어요. 재고 데이터는 여러 창고와 매장에서 실시간으로 업데이트되는데, 주문이 들어올 때마다 즉시 반영되어야 하거든요.

하지만 실시간 동기화는 네트워크 지연과 DB 락 문제를 유발할 수 있어서, 결국 이벤트 기반 비동기 처리 모델을 도입했습니다. 주문이 들어오면 메시지 큐에 이벤트를 보내고, 재고 업데이트는 별도 프로세스에서 처리하는 구조였죠.

이 방식 덕분에 시스템 부하가 분산되고 장애 시 영향 범위가 제한됐지만, 재고 정보가 약간 지연될 수 있다는 단점이 생겼어요. 그래서 고객 주문 시 "재고 있음" 상태라도 실제로는 품절될 가능성을 줄이기 위해 재고 예약(reservation) 시스템을 덧붙였습니다.

이처럼 좋은 점과 아쉬운 점이 공존하는 트레이드오프는 현실적인 엔지니어링 결정의 본질이라는 걸 다시 한 번 느꼈습니다.


## Gong Cha 사례에서 우리 팀에 적용할 수 있는 실질적인 교훈

- **작은 범위 점진 배포는 필수**: 신규 기능을 한꺼번에 바꾸지 말고, 5~10% 매장 단위로 점진 적용하며 문제 발생 시 빠른 롤백 경로를 확보하세요.

- **실패 유형 세분화 계측**: 장애 로그를 단순 실패/성공 구분에서 끝내지 말고, 실패 원인별로 나누어 실시간 모니터링 체계를 만드세요.

- **이벤트 기반 비동기 처리 도입**: 재고와 주문 처리 같이 실시간성이 중요한 시스템은 이벤트 큐를 활용해 부하를 분산하고 장애 영향을 최소화하는 게 효과적입니다.

- **재고 예약 시스템으로 사용자 경험 보완**: 재고 정보 지연으로 인한 주문 실패를 줄이려면, 재고 예약 로직을 꼭 추가하세요.

- **코드 배포 시 Feature Flag 활용**: 아래 예시처럼 플래그를 통해 신규 API를 제어하면, 운영 중에도 유연하게 기능을 조절할 수 있습니다.
