### "Spring Batch 6.x, 이제는 꼭 업그레이드해야 할까?"

얼마 전 우리 팀에서 Spring Batch를 5.x에서 6.x로 올리는 작업을 진행했는데요. 처음엔 ‘그냥 잘 쓰던 버전인데 왜 굳이?’라는 생각이 들었죠. 하지만 막상 6.0.5 버전을 프로덕션에 적용해보니, Java 17 이상 요구사항부터 Spring Boot 3.x와의 완벽한 호환성 덕분에 여러 모로 편해졌습니다. 물론 6.1.0-M1 같은 마일스톤 버전은 아직 테스트용으로만 쓰는 게 안전하다는 것도 깨달았고요.

이 글에서는 우리 팀이 직접 겪은 업그레이드 과정과, 프로덕션 환경에서 꼭 챙겨야 할 튜닝 포인트, 그리고 보안과 롤아웃 전략까지 차근차근 풀어보겠습니다.

---

## Spring Batch 6.x, Java 17과 Spring Boot 3.x 없인 시작도 못 한다

Spring Batch 6.x는 이제 Java 17 이상이 기본 요구사항입니다. 기존에 Java 8이나 11을 쓰던 환경이라면, 무조건 JDK 업그레이드부터 해야 한다는 뜻이죠. 우리도 처음엔 이 부분에서 꽤 시간을 썼습니다. 다행히 Spring Boot 3.x와 완벽하게 호환되기 때문에, Spring Boot 버전도 같이 올리면 호환성 문제는 거의 없었습니다.

6.0.5 버전은 안정적인 프로덕션 환경에서 쓰기에 적합한 릴리즈고, 6.1.0-M1은 아직 마일스톤 단계라 기능 테스트와 마이그레이션 준비용으로만 쓰는 게 좋습니다. 우리도 6.1.0-M1은 별도의 테스트 환경에서 돌려보고, 6.0.5를 프로덕션에 적용했어요. 안정성과 기능 사이에서 균형을 맞추는 게 중요합니다.

> 참고로 Spring Boot 공식 문서에서도 이 점을 명확히 하고 있습니다.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)

## XML 대신 자바 설정으로 갈아타야 하는 이유

기존 Spring Batch 프로젝트가 XML 설정으로 꽤 복잡하게 얽혀 있는 경우가 많을 겁니다. 우리도 마찬가지였는데, 6.x 업그레이드하면서 자바 기반 설정으로 전환하는 걸 강력히 추천합니다.

왜냐하면 자바 설정은 유지보수하기 훨씬 편하고, 보안 측면에서도 유리하거든요. XML은 설정 자체가 정적이어서, 보안 감사나 권한 관리가 어렵고 실시간으로 조정하기도 힘듭니다. 반면 자바 설정은 코드 리뷰도 가능하고, 컴파일 시점에 오류를 잡을 수 있어 안정성이 높아집니다.

간단한 예시로, 기존 XML에서 이렇게 쓰던 배치 잡 설정을:

```xml
<batch:job id="sampleJob">
    <batch:step id="step1">
        <batch:tasklet>
            <batch:chunk reader="itemReader" writer="itemWriter" commit-interval="10" />
        </batch:tasklet>
    </batch:step>
</batch:job>
```

자바로 바꾸면 이렇게 됩니다:

```java
@Configuration
@EnableBatchProcessing
public class BatchConfig {

    @Bean
    public Job sampleJob(JobBuilderFactory jobs, Step step1) {
        return jobs.get("sampleJob")
                   .start(step1)
                   .build();
    }

    @Bean
    public Step step1(StepBuilderFactory steps, ItemReader<String> reader, ItemWriter<String> writer) {
        return steps.get("step1")
                    .<String, String>chunk(10)
                    .reader(reader)
                    .writer(writer)
                    .build();
    }

    // reader, writer 빈 정의 생략
}
```

이렇게 하면 코드에서 바로 설정을 확인하고 수정할 수 있으니, 협업과 유지보수가 훨씬 수월해집니다.

> 자세한 내용은 Spring Boot 공식 문서에서 자바 설정 권장 사항을 참고하세요.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)

## 프로덕션에서 꼭 챙겨야 할 성능 튜닝 포인트

배치 작업은 무조건 빠르고 안정적이어야 하니까, 튜닝은 필수입니다. 우리 팀이 실제로 조정한 주요 설정은 크게 세 가지였어요.

### 1. 스레드 풀 크기 조절

Spring Batch 6.x는 병렬 처리 성능을 높이기 위해 스레드 풀을 적극 활용합니다. 기본값으로는 CPU 코어 수에 맞춰 설정되어 있는데, 우리 환경에서는 8코어 서버에 스레드 풀 크기를 16으로 늘렸더니 처리량이 약 30% 이상 증가했습니다.

```java
@Bean
public TaskExecutor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(16);
    executor.setMaxPoolSize(16);
    executor.setQueueCapacity(50);
    executor.setThreadNamePrefix("batch-thread-");
    executor.initialize();
    return executor;
}
```

이렇게 설정한 후 Step에 `taskExecutor()`를 주입하면 병렬 처리 효율이 좋아집니다.

### 2. 데이터베이스 커넥션 풀 최적화

Spring Batch는 데이터베이스와 자주 통신하기 때문에 커넥션 풀이 병목이 될 수 있습니다. 기본적으로 HikariCP를 쓰는데, 최대 커넥션 수를 워크로드에 맞게 조정하는 게 중요합니다.

우리 팀은 최대 50개 커넥션으로 설정했는데, 너무 적으면 대기 시간이 길어지고, 너무 많으면 DB 부하가 커져서 오히려 성능이 떨어지더라고요.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 50
      minimum-idle: 10
      idle-timeout: 30000
      max-lifetime: 600000
      connection-timeout: 30000
```

### 3. 청크 사이즈 조절

청크 사이즈는 한 번에 처리하는 데이터 단위 크기인데, 너무 작으면 트랜잭션 오버헤드가 크고, 너무 크면 메모리 사용량이 급증합니다. 우리 환경에서는 100~500 사이에서 테스트해봤는데, 250 정도가 가장 안정적이었어요.

## 민감한 데이터, Spring Batch 6.x 보안 설정에서 놓치지 말아야 할 것들

배치 작업은 종종 개인정보나 금융 데이터 같은 민감한 정보를 다루는데, Spring Batch 6.x는 최신 Spring Security와 기본 통합되어 있어 권한 관리가 훨씬 세밀해졌습니다.

예를 들어, 배치 잡 실행 권한을 특정 그룹에만 부여하거나, API 호출 시 JWT 토큰 검증을 강화하는 식으로 말이죠.

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig extends WebSecurityConfigurerAdapter {

    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
            .authorizeRequests()
                .antMatchers("/batch/run").hasRole("BATCH_OPERATOR")
                .anyRequest().authenticated()
            .and()
            .oauth2ResourceServer()
                .jwt();
    }
}
```

이렇게 하면 배치 잡 실행 API가 `BATCH_OPERATOR` 권한이 있는 사용자만 접근 가능하게 제한됩니다. 우리 팀은 이걸로 내부 보안 사고를 크게 줄일 수 있었어요.

더 자세한 보안 설정 팁은 공식 문서 참고하세요.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)

## 서비스 중단 없이 안전하게 Spring Batch 6.x를 적용하려면

새 버전으로 업그레이드할 때 가장 신경 쓰이는 게 바로 롤아웃 전략입니다. 우리 팀은 Canary 배포와 Blue-Green 배포 방식을 혼합해 사용했는데, 이게 생각보다 효과가 좋았습니다.

- **Canary 배포**: 전체 배치 작업 중 일부 노드에만 새 버전을 먼저 배포해서 모니터링 후 문제 없으면 점진적으로 확대
- **Blue-Green 배포**: 새 버전 환경(Blue)을 별도로 띄워서 테스트 후, 트래픽을 한꺼번에 전환

이 두 방식을 병행하면서, 배치 잡 실행 중단 없이 안전하게 전환할 수 있었고, 만약 문제가 생겨도 즉시 롤백이 가능했습니다.

GitHub 엔지니어링 블로그에서 이런 전략을 자세히 다루고 있으니 참고하면 좋습니다.[GitHub Engineering Blog](https://github.blog/category/engineering/)

### 마무리하며

처음엔 Spring Batch 6.x 업그레이드가 부담스러웠지만, Java 17 기반으로 전환하고 자바 설정으로 깔끔하게 정리한 덕분에 유지보수 시간이 크게 줄었고, 성능과 보안도 기대 이상이었습니다. 특히 스레드 풀과 커넥션 풀 튜닝, 청크 사이즈 조절 같은 작은 설정들이 실제 프로덕션 안정성에 큰 영향을 준다는 걸 몸소 느꼈죠.

롤아웃 전략도 무시하면 안 됩니다. 아무리 좋은 버전이라도 한꺼번에 바꾸다 장애 나면 큰일이니까요.

이 글이 Spring Batch 6.x 업그레이드 고민하는 동료들에게 조금이나마 도움이 되길 바랍니다. 궁금한 점 있으면 언제든 커피 한잔 하면서 얘기해요!
