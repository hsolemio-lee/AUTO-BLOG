### "왜 내 LLM 에이전트가 점점 엉뚱한 코드를 내놓는 걸까?"

최근 팀에서 LLM 기반 코드 생성 도구를 백엔드 개발에 도입했는데, 처음엔 꽤 쓸만했어요. 그런데 시간이 지나면서 점점 코드가 이상해지고, 심지어 비즈니스 로직이 꼬이거나 상태 관리가 엉망이 되는 일이 잦아졌죠. 이게 바로 업계에서 말하는 ‘Constraint Decay(제약 조건 붕괴)’ 현상입니다. 단순히 한두 번의 오류가 아니라, LLM 에이전트가 점진적으로 제약 조건을 잃어버리면서 코드의 일관성과 안정성이 떨어지는 문제인데요. 특히 복잡한 백엔드 로직에서는 치명적일 수밖에 없습니다.

---

## LLM 에이전트가 백엔드 코드에서 제약 조건을 잃는 이유

LLM은 본질적으로 거대한 확률 모델이죠. 그래서 처음에는 프롬프트에 명시된 제약 조건을 잘 따라도, 여러 단계에 걸쳐 코드를 생성하거나 복잡한 상태를 다룰 때 점점 제약 조건을 잊거나 왜곡하는 경향이 있습니다. 예를 들어, 인증, 권한, 트랜잭션 관리 같은 백엔드 핵심 로직에서 이런 현상이 심해지면, 코드가 의도와 다르게 동작하거나 보안 취약점이 생길 위험이 커져요.

OpenAI 공식 문서에서도 LLM 에이전트가 점진적인 제약 조건 붕괴로 인해 생성 코드의 안정성이 떨어질 수 있다고 명확히 언급하고 있습니다[OpenAI API Documentation](https://platform.openai.com/docs/overview).

이건 실제로 겪어보면 꽤 당황스러운데, 예를 들어 아래처럼 간단한 API 엔드포인트 생성 프롬프트를 줬는데도, 여러 호출을 거치며 점점 타입이 어긋나거나 상태 업데이트 로직이 누락되는 상황이 벌어집니다.

```typescript
// 초기 프롬프트 기반 생성 예시
// "사용자 인증 후, 주문 생성 API를 구현해줘. 주문은 주문 상태(orderStatus)를 관리해야 해."

interface Order {
  id: string;
  userId: string;
  orderStatus: 'pending' | 'completed' | 'cancelled';
}

function createOrder(userId: string): Order {
  // ... 주문 생성 로직
  return { id: generateId(), userId, orderStatus: 'pending' };
}

// 그런데 이후 LLM이 생성한 코드에서는 orderStatus가 string으로 바뀌거나,
// 상태 업데이트 함수가 누락되는 등 제약 조건이 점점 무너짐
```

이처럼 제약 조건 붕괴는 복잡한 비즈니스 로직과 상태 관리가 필수인 백엔드에서 특히 치명적입니다.


## TypeScript 5.x가 LLM 생성 코드 안정성에 도움 되는 이유

우리 팀은 이 문제를 해결하기 위해 TypeScript 5.x로 전면 업그레이드를 진행했어요. 왜냐하면 TypeScript 5.x에서는 타입 시스템이 한층 강화되고 빌드 성능도 개선되어, LLM이 생성한 코드 내 타입 불일치와 런타임 오류를 훨씬 빠르게 잡아낼 수 있기 때문입니다.

특히, 새로운 `satisfies` 연산자와 향상된 제네릭 추론 덕분에 LLM이 만든 코드가 타입 요구사항에 부합하는지 엄격히 검사할 수 있었죠. 예를 들어, 위 주문 상태 관리 코드를 TypeScript 5.x 기능을 활용해 작성하면 다음과 같습니다.

```typescript
const orderStatusValues = ['pending', 'completed', 'cancelled'] as const;

type OrderStatus = (typeof orderStatusValues)[number];

interface Order {
  id: string;
  userId: string;
  orderStatus: OrderStatus;
}

function createOrder(userId: string): Order {
  return {
    id: generateId(),
    userId,
    orderStatus: 'pending' satisfies OrderStatus,
  };
}
```

이처럼 타입 안정성이 확보되면, LLM이 제약 조건을 잃고 이상한 값을 넣는 일이 줄어들죠. Microsoft의 공식 블로그에서도 TypeScript 5.x가 코드 안정성과 빌드 속도 개선에 크게 기여한다고 밝히고 있습니다[TypeScript 5.x Release Notes](https://devblogs.microsoft.com/typescript/announcing-typescript-5-4/).

이건 단순히 타입스크립트를 쓰는 것 이상의 의미가 있어요. LLM이 생성한 코드에 엄격한 타입 검사를 적용하면, 제약 조건 붕괴를 조기에 발견하고 방지할 수 있는 실질적 방어선이 됩니다.


## 프롬프트 설계가 제약 조건 붕괴를 막는 첫걸음

LLM이 제약 조건을 잃는 가장 큰 이유 중 하나는 프롬프트가 명확하지 않거나 단계별 지침이 부족하기 때문입니다. Anthropic의 프롬프트 엔지니어링 가이드에 따르면, 명확한 제약 조건과 단계별 수행 절차를 포함하는 프롬프트를 설계하면 LLM의 코드 생성 품질을 크게 높일 수 있다고 해요[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

예를 들어, 단순히 "주문 API를 만들어줘"라고 하기보다 아래처럼 구체적으로 요구사항을 단계별로 나누는 거죠.

```
1. 사용자 인증을 확인한다.
2. 주문 생성 시 주문 상태(orderStatus)는 반드시 'pending'으로 초기화한다.
3. 주문 상태는 'pending', 'completed', 'cancelled' 중 하나여야 한다.
4. 주문 생성 후 상태 업데이트 함수가 반드시 포함되어야 한다.
```

이런 식으로 프롬프트를 짜면, LLM이 단계별로 제약 조건을 기억하며 코드를 생성하기 때문에 붕괴 현상이 줄어듭니다.

우리 팀에서도 이런 프롬프트를 도입한 뒤, 동일한 복잡한 API 생성 작업에서 오류율이 30% 이상 감소하는 효과를 봤어요.


## 인간 검토와 자동화 테스트 없이는 LLM 생성 코드 신뢰 못 한다

GitHub 엔지니어링 블로그에서도 LLM 에이전트를 활용한 코드 자동화 과정에서 발생하는 실패 모드를 분석하며, 지속적인 인간 검토와 자동화된 테스트 통합이 LLM 생성 코드의 신뢰성을 확보하는 핵심이라고 강조합니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

실제로 우리도 LLM이 생성한 코드를 바로 배포하는 게 아니라, 반드시 리뷰어가 코드를 검토하고, CI 파이프라인에서 타입 검사와 단위 테스트, 통합 테스트를 돌리도록 했어요. 특히 상태 관리나 보안 관련 로직은 수동 검토를 강화했죠.

이 과정에서 발견된 문제들은 대부분 LLM이 제약 조건을 놓친 부분에서 비롯됐어요. 예를 들어, 인증 토큰 검증 로직이 누락되거나, 주문 상태가 잘못 업데이트되는 부분 등입니다. 이런 문제는 자동화 테스트 커버리지를 90% 이상 확보하고, 리뷰어가 명확한 체크리스트를 갖고 검토할 때 크게 줄어들었습니다.


## 클라우드 환경 특성 반영과 다중 단계 검증도 필수

Cloudflare의 사례를 보면, 클라우드 백엔드 특유의 복잡한 네트워크 및 보안 제약 조건을 LLM 생성 코드에 명확히 반영하는 게 중요하다고 합니다. 이를 위해 다중 단계 검증과 모니터링 체계를 도입해 제약 조건 붕괴를 막는 전략을 썼다고 하네요[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

우리도 클라우드 환경에서 LLM 생성 코드를 운영할 때, 다음과 같은 추가 검증 단계를 넣었습니다.

- 네트워크 정책 및 방화벽 규칙에 맞는 코드인지 자동 검사
- 보안 취약점 스캐닝 도구 통합
- 실시간 모니터링으로 이상 징후 탐지

이런 다중 검증 체계가 없으면, LLM이 생성한 코드가 의도치 않게 클라우드 보안 정책을 무시하거나 네트워크 오류를 유발할 수 있거든요. 그래서 백엔드에서 LLM 활용 시에는 단순 코드 생성뿐 아니라, 운영 환경 특성을 반영한 검증과 모니터링이 필수입니다.

### 마무리하며: LLM 에이전트와 함께 일할 때 꼭 챙겨야 할 것들

- **제약 조건 붕괴는 자연스러운 현상**임을 인정하고, 단순 자동화 도구가 아닌 보조 도구로 활용하라.
- **최신 TypeScript 5.x 기능을 적극 활용해 타입 안정성을 확보**하라. `satisfies` 연산자와 엄격한 타입 검사는 필수다.
- **프롬프트는 명확하고 단계별로 설계**해 LLM이 제약 조건을 잃지 않도록 유도하라.
- **인간 리뷰와 자동화 테스트를 반드시 통합**해 코드 품질과 보안을 보장하라.
- **클라우드 환경 특성을 반영한 다중 단계 검증과 모니터링 체계**를 구축해 배포 후 문제를 빠르게 발견하고 대응하라.

이건 처음엔 별거 아닌 것 같지만, 실제로 겪어보면 LLM 에이전트를 백엔드에 도입하는 데 가장 큰 걸림돌이 바로 제약 조건 붕괴입니다. 하지만 위 전략들을 차근차근 적용하면, AI와 협업하는 백엔드 개발의 생산성과 안정성을 크게 높일 수 있어요.

여러분도 꼭 한번 시도해보시고, 경험담 공유해 주세요!
