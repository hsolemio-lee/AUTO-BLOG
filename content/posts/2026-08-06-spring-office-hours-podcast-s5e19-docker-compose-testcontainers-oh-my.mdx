### "왜 내 테스트는 항상 외부 환경에 발목 잡힐까?"

최근에 우리 팀에서 통합 테스트가 자꾸 실패하는 바람에 고생한 적이 있었어요. 데이터베이스 연결 문제, 메시지 큐 환경 불안정, 버전 차이 등등. 결국 테스트 신뢰도가 뚝 떨어지면서 개발 속도도 같이 느려졌죠. 이걸 해결하려면 어떻게 해야 할까? 바로 Docker와 Docker Compose, 그리고 Testcontainers를 제대로 활용하는 게 답이더라고요.

---

## Dockerfile, 그냥 쓰면 안 되는 이유

처음에 Dockerfile을 막 써봤는데, 이미지가 1GB가 넘더라고요. 빌드도 느리고, 배포할 때마다 시간이 너무 오래 걸렸죠. 그래서 Docker 공식 문서를 참고해보니, 이미지 크기를 줄이고 빌드 속도를 올리려면 레이어 수를 줄이고 캐시를 최대한 활용하는 게 중요하다고 합니다[Docker - Best practices for writing Dockerfiles](https://docs.docker.com/develop/develop-images/dockerfile_best-practices/).

예를 들어, 아래처럼 RUN 명령어를 여러 개로 나누지 말고 한 번에 묶는 게 좋습니다.

```dockerfile
FROM openjdk:17-jdk-slim
WORKDIR /app

# 의존성 설치를 한 번에 처리해서 레이어 최소화
COPY build.gradle settings.gradle ./
COPY gradle ./gradle
RUN ./gradlew build --no-daemon

COPY src ./src
RUN ./gradlew bootJar --no-daemon

EXPOSE 8080
CMD ["java", "-jar", "build/libs/myapp.jar"]
```

이렇게 하면 캐시가 잘 활용되어서 코드만 바뀌었을 때 재빌드 시간이 크게 줄어요. 실제로 우리 팀은 이미지 크기를 600MB에서 250MB로 줄이고, 빌드 시간도 40% 이상 단축했죠.

## Docker Compose로 개발·테스트 환경을 코드로 관리하기

혼자 개발할 때는 그냥 로컬에 DB 띄우고 했는데, 팀 프로젝트에서는 그게 통하지 않더라고요. 각자 환경이 달라서 "내 로컬에서는 되는데"가 너무 많았죠. 그래서 Docker Compose를 도입했습니다. 이걸로 Spring 백엔드, MySQL, Redis, Kafka 같은 여러 컨테이너를 한 번에 띄우니까 환경 세팅이 완전 편해졌어요[Docker Compose Overview](https://docs.docker.com/compose/).

```yaml
docker-compose.yml
version: '3.8'
services:
  app:
    build: .
    ports:
      - "8080:8080"
    depends_on:
      - db
      - redis
    environment:
      SPRING_DATASOURCE_URL: jdbc:mysql://db:3306/mydb
      SPRING_REDIS_HOST: redis
    deploy:
      resources:
        limits:
          cpus: '0.5'
          memory: 512M
  db:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: mydb
    ports:
      - "3306:3306"
  redis:
    image: redis:6
    ports:
      - "6379:6379"
```

특히 리소스 제한 설정도 해놨는데, 이게 없으면 내 로컬 머신이 버벅거리거나 컨테이너가 무한정 리소스를 쓸 수 있어서 위험하더라고요. Baeldung 가이드에 따르면 이런 설정이 컨테이너 환경에서 성능 튜닝에 도움이 된다고 합니다[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

## Testcontainers로 실제 컨테이너 환경에서 통합 테스트하기

테스트할 때 "내 로컬 DB랑 다르니까" 문제가 계속 있었는데, Testcontainers 라이브러리를 알게 되면서 이 고민이 싹 사라졌어요. Testcontainers는 테스트 코드에서 실제 Docker 컨테이너를 띄워서 DB, 메시지 큐 같은 외부 의존성을 격리된 환경에서 돌릴 수 있게 해줍니다. Spring Boot와도 찰떡궁합이라서 통합 테스트 신뢰도가 확 올라갔죠[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

아래는 JUnit 5와 함께 MySQL 컨테이너를 띄우고, Spring Data JPA Repository를 테스트하는 예제입니다.

```java
@Testcontainers
@SpringBootTest
public class UserRepositoryTest {

    @Container
    static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.0")
        .withDatabaseName("testdb")
        .withUsername("test")
        .withPassword("test");

    @Autowired
    private UserRepository userRepository;

    @DynamicPropertySource
    static void mysqlProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", mysql::getJdbcUrl);
        registry.add("spring.datasource.username", mysql::getUsername);
        registry.add("spring.datasource.password", mysql::getPassword);
    }

    @Test
    void testSaveAndFind() {
        User user = new User(null, "alice");
        userRepository.save(user);

        Optional<User> found = userRepository.findById(user.getId());
        assertTrue(found.isPresent());
        assertEquals("alice", found.get().getName());
    }
}
```

이렇게 하면 테스트가 항상 같은 환경에서 실행되니 "어제는 됐는데 오늘은 왜 안 돼?" 같은 문제를 크게 줄일 수 있어요.

## Spring의 모듈화와 의존성 주입, 그리고 컨테이너화의 시너지

Spring Framework가 제공하는 의존성 주입과 모듈화 덕분에 테스트 가능한 컴포넌트 분리가 쉬워졌어요. 여기에 Docker와 Testcontainers를 결합하면 개발부터 배포까지 환경 일관성을 확보할 수 있습니다. 예를 들어, 개발자는 로컬에서 Docker Compose로 여러 서비스를 띄우고, CI/CD 파이프라인에서는 Testcontainers로 통합 테스트를 돌리며, 프로덕션도 동일한 컨테이너 이미지로 배포하는 식이죠[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

하지만 단점도 있어요. 컨테이너 환경이 익숙하지 않은 팀원에게는 진입장벽이 될 수 있고, 초기 설정에 꽤 시간이 듭니다. 또, Testcontainers를 너무 과도하게 쓰면 테스트 실행 시간이 길어질 수 있으니, 단위 테스트와 통합 테스트를 적절히 분리하는 게 중요합니다.

### 마무리하며

- Dockerfile은 레이어 최소화와 캐시 활용을 꼭 신경 쓸 것
- Docker Compose로 개발·테스트 환경을 코드로 관리해 팀 간 환경 차이 줄이기
- Testcontainers로 실제 컨테이너 기반 통합 테스트 환경 구축하기
- Spring의 DI와 모듈화 덕분에 테스트와 컨테이너화가 자연스럽게 어우러짐
- 리소스 제한 설정과 테스트 실행 시간 등 현실적인 트레이드오프도 고려하기

이 조합을 제대로 활용하면 백엔드 개발 생산성과 테스트 신뢰도가 눈에 띄게 올라갑니다. 저희 팀도 이 과정을 거치면서 "내 로컬에서는 됐는데"라는 말이 한마디도 안 나오게 됐어요. 여러분도 한번 시도해보세요!
