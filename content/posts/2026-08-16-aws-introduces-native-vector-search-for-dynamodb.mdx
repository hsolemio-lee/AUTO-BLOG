### "벡터 검색, DynamoDB에서 바로 한다고?"

얼마 전 우리 팀에서 AI 추천 시스템을 고도화하면서 벡터 검색 처리 때문에 골머리를 앓고 있었어요. 기존에는 벡터를 별도 서비스에 저장하고, DynamoDB는 메타데이터만 관리했죠. 그런데 AWS가 DynamoDB에 네이티브 벡터 검색 기능을 공식 지원한다는 소식을 듣고 바로 테스트해봤습니다. 결과는? 생각보다 훨씬 간단하고, 확장성도 뛰어나서 놀랐어요.

---

## DynamoDB 벡터 검색, 왜 이제야?

벡터 검색은 AI, 특히 추천, 자연어 처리, 이미지 검색에서 핵심인데요. 벡터 공간에서 유사한 항목을 빠르게 찾는 게 목적입니다. 보통 벡터 DB나 별도 검색 엔진을 써야 했는데, AWS가 DynamoDB에 이 기능을 네이티브로 넣으면서 상황이 바뀌었죠.

DynamoDB는 원래 초당 수백만 요청을 감당하는 NoSQL 솔루션인데, 여기에 벡터 인덱싱이 더해지면서 복잡한 유사도 검색을 빠르게 할 수 있게 됐어요. 덕분에 AI 백엔드의 응답 속도가 눈에 띄게 개선되고, 유지보수도 간편해졌죠[1](https://aws.amazon.com/blogs/architecture/).

---

## Spring 백엔드에서 DynamoDB 벡터 검색 어떻게 붙이나?

우리 팀은 Spring Boot 기반 서비스라 AWS SDK for Java를 활용했습니다. 벡터 데이터를 저장할 땐 float 배열을 직렬화해서 DynamoDB의 새로운 벡터 타입 속성에 넣습니다. 쿼리할 때는 벡터 유사도 검색 API를 호출해요.

```java
// 벡터 데이터를 직렬화하는 간단한 예
public static ByteBuffer serializeVector(float[] vector) {
    ByteBuffer buffer = ByteBuffer.allocate(vector.length * 4).order(ByteOrder.LITTLE_ENDIAN);
    for (float v : vector) {
        buffer.putFloat(v);
    }
    buffer.flip();
    return buffer;
}

// DynamoDB에 벡터 저장 예시
PutItemRequest request = PutItemRequest.builder()
    .tableName("AiVectors")
    .item(Map.of(
        "id", AttributeValue.builder().s("item123").build(),
        "embedding", AttributeValue.builder().b(serializeVector(myVector)).build()
    ))
    .build();
dynamoDbClient.putItem(request);
```

검색 시에는 `Query` 대신 벡터 유사도 검색 API를 써서, 입력 벡터와 가장 가까운 항목을 빠르게 찾습니다. 이 과정에서 쿼리 최적화를 위해 벡터 차원 수, 인덱스 파라미터를 조절하는 게 중요해요[1](https://aws.amazon.com/blogs/architecture/).

## 벡터 인덱싱과 파티셔닝 전략, 이걸 놓치면 성능 폭망

DynamoDB 벡터 검색의 성능은 인덱싱과 파티셔닝 설계에 달렸습니다. 벡터 인덱스는 데이터 분산과 병렬 검색을 위한 핵심인데, 단순히 데이터를 한 테이블에 몰아넣으면 검색 속도가 급격히 느려지거든요.

AWS Well-Architected Framework에서는 벡터 인덱싱을 여러 파티션 키로 분산시키고, 각 파티션에서 병렬로 검색을 수행하는 방식을 권장합니다. 예를 들어, 사용자 ID나 카테고리별로 파티션 키를 나누고, 벡터 검색 쿼리를 병렬 호출해 결과를 합치는 식이죠[2](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html).

이 전략 덕분에 초당 수천 건의 벡터 검색도 무리 없이 처리할 수 있었고, DynamoDB 프로비저닝 용량도 효율적으로 쓸 수 있었습니다. 물론 파티셔닝이 너무 세분화되면 관리가 복잡해지니 적절한 균형이 필요합니다.

---

## 비용과 확장성, 모니터링 없인 답 없다

벡터 검색 쿼리는 계산량이 많아 비용이 빠르게 증가할 수 있어요. DynamoDB는 사용량 기반 과금이라 쿼리 빈도와 프로비저닝 용량에 따라 비용이 달라집니다.

그래서 우리 팀은 AWS CloudWatch와 DynamoDB 자동 스케일링 기능을 적극 활용했어요. 벡터 검색 쿼리의 지연 시간과 처리량을 실시간 모니터링하고, 임계치에 따라 프로비저닝 용량을 자동 조정하도록 했죠. 덕분에 트래픽 급증 시에도 서비스가 안정적으로 유지됐습니다[2](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html).

## 직접 써보니 느낀 장단점

### 장점
- 별도 벡터 DB 없이 DynamoDB 하나로 통합 가능
- AWS 인프라와 자연스럽게 연동돼 운영 부담 감소
- 초당 수천~만 건 검색도 무리 없이 처리

### 단점
- 벡터 차원 수가 너무 크면 인덱스 크기와 비용 급증
- 파티셔닝 설계가 복잡해질 수 있음
- 아직은 벡터 검색 기능이 초기 단계라 문서와 사례가 제한적

## 마무리하며: 실무에서 바로 써먹을 팁

1. 벡터 데이터는 128~512 차원 정도로 제한하는 게 현실적입니다. 그 이상은 비용과 성능 부담이 커져요.
2. 파티션 키 설계에 시간을 충분히 투자하세요. 사용자 그룹, 카테고리 등으로 나누면 병렬 검색 효율이 크게 올라갑니다.
3. AWS SDK에서 벡터 직렬화/역직렬화 유틸을 직접 만들어 재사용하면 코드가 깔끔해져요.
4. CloudWatch 경보와 자동 스케일링을 꼭 설정해 비용 폭탄을 막으세요.

처음엔 벡터 검색이 별거 아닌 것 같지만, 실무에서 대량 데이터 다루다 보면 이 기능 하나가 얼마나 큰 차이를 만드는지 체감할 겁니다. DynamoDB 네이티브 벡터 검색, AI 백엔드 설계에 꼭 한 번 도전해보세요!
