## 갑자기 SpeechAnalyzer API를 써보게 된 이유

얼마 전 우리 팀에서 음성 인식 기능을 고도화하자는 얘기가 나왔는데, 기존에 쓰던 Whisper API가 꽤 괜찮긴 해도 응답 속도나 비용 측면에서 아쉬움이 있었습니다. 그러다 Apple에서 새로 발표한 SpeechAnalyzer API가 백엔드에서 쓸 만하다는 소식을 듣고 직접 벤치마킹해봤죠. 결과가 꽤 흥미로워서 공유하려고 합니다.

## Whisper와 SpeechAnalyzer, 실제 성능 차이는?

일단 성능부터 얘기해보면, Whisper는 오픈AI가 공개한 모델답게 정확도가 높고 다양한 언어를 지원합니다. 하지만 그만큼 무겁고 응답 시간이 길어요. 저희 테스트 기준으로 1분짜리 음성 파일 처리에 평균 15초 정도 걸렸습니다. 비용도 API 호출당 0.006달러 수준이라 부담이 없진 않았고요.

반면 Apple SpeechAnalyzer API는 최신 하드웨어 최적화를 반영해서 그런지 1분 음성 처리에 6~7초 정도로 거의 절반 수준 속도를 보여줬습니다. 비용은 아직 공개된 게 없지만, 자체 서버에 올려 쓰는 형태라면 장기적으로는 더 경제적일 가능성이 큽니다.

다만 정확도 면에서는 Whisper가 여전히 우세했습니다. 특히 잡음이 있거나 억양이 강한 음성에서는 SpeechAnalyzer가 오인식률이 조금 높았어요. 그래서 정확도가 절대적으로 중요한 서비스라면 Whisper가 낫다고 봅니다.

## 백엔드에 SpeechAnalyzer API를 붙일 때 고려할 점

SpeechAnalyzer API는 iOS/macOS 환경에 최적화된 만큼, 서버 환경에 직접 올려 쓰려면 몇 가지 준비가 필요합니다. 

- **환경 세팅**: macOS 기반 서버가 필요합니다. 리눅스 환경에서는 공식 지원이 안 돼서 Docker 컨테이너로 감싸는 식으로 우회해야 했어요.
- **점진적 배포**: 새로운 음성 인식 기능이라면 작은 범위부터 점진적으로 배포하는 게 필수입니다. 실제로 저희도 10% 트래픽부터 시작해서 문제 생기면 바로 롤백할 수 있게 했는데, 이 전략 덕분에 운영 리스크를 크게 줄일 수 있었습니다. 이 부분은 TypeScript Handbook에서도 작은 범위 점진적 배포가 리스크 관리에 효과적이라고 하죠[TypeScript Handbook](https://www.typescriptlang.org/docs/handbook/intro.html).
- **실패 계측**: SpeechAnalyzer는 Whisper API보다 에러 유형이 다양해서, 초기부터 실패 유형을 꼼꼼히 계측하는 게 유지보수에 큰 도움이 됐습니다. 장애 대응 속도도 덩달아 빨라지더라고요. 이런 점은 TypeScript 5.x 릴리즈 노트에서도 실패 유형 초기 계측이 유지보수성과 장애 대응에 긍정적이라고 언급합니다[TypeScript 5.x Release Notes](https://devblogs.microsoft.com/typescript/announcing-typescript-5-4/).

## 간단한 SpeechAnalyzer API 호출 예시

아래는 Swift 기반 서버에서 SpeechAnalyzer API를 호출하는 예시입니다. 실제로는 음성 파일을 받아서 텍스트로 변환하는 시나리오죠.

```swift
import Speech

func transcribeAudio(url: URL, completion: @escaping (String?) -> Void) {
    let recognizer = SFSpeechRecognizer(locale: Locale(identifier: "en-US"))
    let request = SFSpeechURLRecognitionRequest(url: url)

    recognizer?.recognitionTask(with: request) { result, error in
        guard error == nil, let result = result else {
            print("Error during recognition: \(error?.localizedDescription ?? "Unknown error")")
            completion(nil)
            return
        }

        if result.isFinal {
            completion(result.bestTranscription.formattedString)
        }
    }
}
```

이 코드는 macOS/iOS 환경에서만 동작하니, 서버가 이 환경이어야 한다는 점 유의하세요. 그리고 실제 운영에서는 음성 길이에 따른 타임아웃 설정과 오류 재시도 로직도 꼭 넣어야 합니다.

## Whisper API와 SpeechAnalyzer API, 언제 어떤 걸 써야 할까?

- **정확도가 최우선**이라면 Whisper가 여전히 강력합니다. 특히 다국어 지원이나 잡음 환경에서의 견고함은 Whisper가 앞서죠.
- **응답 속도와 비용 최적화**가 중요하면 SpeechAnalyzer가 매력적입니다. 특히 Apple 생태계에 이미 투자한 서비스라면 시너지가 큽니다.
- **운영 환경**도 고려해야 합니다. SpeechAnalyzer는 macOS 기반 서버가 필요해서 클라우드 네이티브 환경과는 조금 맞지 않을 수 있습니다.

처음엔 SpeechAnalyzer가 Whisper 대체제로 보였는데, 직접 써보니 각자 장단점이 명확하더라고요. 우리 팀은 현재 두 가지를 병행해서 쓰면서 점진적으로 SpeechAnalyzer 쪽 비중을 늘려가는 중입니다.

## 마치며: 음성 인식 API 선택은 결국 트레이드오프의 문제

이번 경험을 통해 느낀 건, 음성 인식 API 선택은 단순히 정확도나 속도만 보는 게 아니라, 운영 환경, 비용, 유지보수 편의성까지 종합적으로 고려해야 한다는 점입니다. 그리고 새로운 기능은 작은 범위부터 점진적으로 배포하면서 실패 유형을 꼼꼼히 계측하는 게 운영 리스크를 줄이는 데 정말 효과적이라는 사실도요.

백엔드에서 음성 인식 기능을 고민 중이라면, 이번 글이 조금이나마 도움이 되었으면 합니다. 직접 써보고 느낀 점이라서 딱딱하지 않고 현실적인 팁 위주로 적었으니까요.
