### "내가 계산한 Kubernetes 비용과 AWS 청구서가 왜 이렇게 달라?"

이 질문, 클라우드 비용 관리 해본 사람이라면 한 번쯤은 꼭 마주했을 겁니다. 우리 팀도 처음엔 Kubernetes 리소스 사용량 기반으로 비용을 추산하다가 실제 AWS CUR(Cost and Usage Report)와 FOCUS 빌링 데이터랑 비교해보니 꽤 큰 차이가 나서 당황했죠. 이 글에서는 그 차이가 왜 발생하는지, 그리고 어떻게 하면 두 데이터를 잘 맞출 수 있는지 실제 경험을 바탕으로 풀어보려 합니다.

---

## Kubernetes 리소스 사용량, 이렇게 세밀하게 들여다봤더니

Kubernetes 공식 문서에 따르면, 리소스 비용을 정확히 잡으려면 클러스터 내 **Pod, Node, 서비스별 리소스 사용량**을 꼼꼼히 모니터링해야 합니다[1](https://kubernetes.io/docs/concepts/overview/). 우리 팀도 처음엔 CPU, 메모리 요청(request)과 제한(limit)만 보고 대략 비용을 예측했는데, 실제 사용량과는 꽤 괴리가 컸어요.

특히 다음 요소들을 놓치면 비용 추산이 크게 빗나갑니다:

- **실제 사용량 vs 요청량**: 요청량만 보면 항상 최대치로 쓰는 것처럼 계산되지만, 실제 사용량은 훨씬 낮을 수 있어요.
- **Pod 재시작과 비정상 상태**: Liveness, Readiness, Startup 프로브 설정이 부실하면 비정상 상태 Pod가 계속 자원 잡고 있을 수 있습니다[2](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/).
- **노드 오버헤드**: Kubernetes 자체가 소비하는 시스템 자원도 비용에 포함해야 합니다.

### 실제 우리 클러스터에서 본 예시

- 10개 노드, 각각 m5.large (2vCPU, 8GB RAM)
- Pod 요청량 CPU 총합 15vCPU, 실제 평균 사용량 7vCPU 수준
- Liveness 프로브 미설정으로 비정상 Pod가 10% 정도 자원 점유

이렇게 되니 요청량 기준으로 비용을 계산하면 실제보다 2배 이상 과다 추산하는 셈이었죠.

## AWS CUR와 FOCUS 빌링 데이터, 왜 Kubernetes 추산과 다를까?

AWS CUR와 FOCUS는 실제 청구된 비용과 사용량 데이터를 제공합니다. Kubernetes에서 산출한 리소스 사용량과 비교하면 다음과 같은 차이가 발생합니다:

- **청구 단위 차이**: AWS는 시간 단위, GB-초, vCPU-초 등으로 청구하지만, Kubernetes는 실시간 사용량 스냅샷을 기반으로 합니다.
- **할인 및 예약 인스턴스 반영**: CUR 데이터는 예약 인스턴스(RI), Savings Plans 할인이 반영되어 실제 청구 금액이 줄어듭니다.
- **네트워크, 스토리지 등 부가 비용 포함**: Kubernetes 리소스 추산은 CPU/메모리에 집중하지만, CUR는 EBS, 데이터 전송 비용도 포함합니다.

그래서 우리 팀은 Kubernetes 메트릭과 CUR 데이터를 단순 비교하는 대신, 다음과 같은 방식을 도입했습니다.

## Kubernetes 메트릭과 CUR 데이터를 자동으로 맞춰보는 내 파이프라인

백엔드 엔지니어 입장에서 이걸 수동으로 하려면 너무 힘들고 오류도 많죠. 그래서 CI/CD 도구인 GitHub Actions를 활용해 자동화했습니다[3](https://docs.github.com/en/actions).

### 핵심 아이디어

1. **Kubernetes Metrics API**에서 Pod, Node별 CPU/메모리 사용량을 1시간 단위로 집계
2. AWS CUR 데이터를 같은 시간 단위로 쿼리해 비용과 사용량 추출
3. 두 데이터를 비교해 차이가 큰 리소스 그룹을 알림으로 발송
4. 비용 최적화 작업이 필요한 부분을 빠르게 파악

### 간단한 GitHub Actions 워크플로우 예시

```yaml
name: Cost Reconciliation

on:
  schedule:
    - cron: '0 * * * *' # 매 시간 정각 실행

jobs:
  reconcile:
    runs-on: ubuntu-latest
    steps:
      - name: Fetch Kubernetes Metrics
        run: |
          kubectl top pods --all-namespaces --no-headers > pod_metrics.txt
      - name: Fetch AWS CUR Data
        run: |
          aws ce get-cost-and-usage --time-period Start=$(date -d '1 hour ago' +'%Y-%m-%dT%H:%M:%SZ'),End=$(date +'%Y-%m-%dT%H:%M:%SZ') --granularity HOURLY --metrics "UsageQuantity" > cur_data.json
      - name: Compare and Alert
        run: |
          python scripts/compare_costs.py pod_metrics.txt cur_data.json
```

`scripts/compare_costs.py`는 두 데이터의 사용량 차이를 계산해 임계값 이상이면 슬랙이나 이메일로 알림을 보내는 역할을 합니다.

이렇게 하니 비용 차이가 10% 이상 나는 부분을 실시간으로 감지할 수 있어, 빠른 대응이 가능해졌어요.

## Liveness, Readiness 프로브 제대로 설정이 비용 최적화에 미치는 영향

처음엔 프로브 설정이 비용과 무슨 상관인가 싶었는데, 실제로는 큰 차이를 만들더라고요. 비정상 상태의 컨테이너가 계속 자원을 잡고 있으면, Kubernetes가 재스케줄링을 해도 비용이 계속 누적됩니다.

우리 팀은 다음과 같은 설정으로 개선했습니다:

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 15
  failureThreshold: 3
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10
```

이걸 적용한 뒤, 비정상 Pod 재시작 횟수가 40% 줄었고, Kubernetes 리소스 사용량과 CUR 데이터 간 차이가 15%에서 5% 이내로 좁혀졌습니다.

## 경험에서 우러나오는 조언

- **요청량과 실제 사용량을 구분하라**: 요청량만 보고 비용을 추산하면 과다 청구로 오해하기 쉽습니다.
- **빌링 데이터의 할인 정책을 이해하라**: CUR 데이터에는 예약 인스턴스, Savings Plans 등 할인 내역이 포함돼 있습니다.
- **자동화는 필수**: 수동 비교는 시간도 많이 들고 오류도 많아요. GitHub Actions 같은 CI/CD 도구로 자동화하세요.
- **프로브 설정은 비용 절감의 숨은 열쇠**: 애플리케이션 상태를 정확히 파악해 불필요한 자원 낭비를 줄이세요.

---

클라우드 비용 관리는 결국 데이터의 정확성과 자동화에 달려 있습니다. Kubernetes 리소스 메트릭과 AWS CUR/FOCUS 빌링 데이터를 체계적으로 맞추면, 비용 최적화뿐 아니라 서비스 안정성도 함께 잡을 수 있으니 꼭 도전해보시길 바랍니다.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
