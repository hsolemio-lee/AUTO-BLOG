### "페이지 전환이 느려서 UX가 떨어진다" 이 말, 아직도 안 들어본 개발자 있을까요?

요즘 웹 앱들이 점점 더 복잡해지면서 페이지 전환 속도와 부드러운 내비게이션 경험이 사용자 만족도를 좌우하는 핵심 요소가 됐습니다. 저도 한참 SPA를 만들면서 느낀 건데, 뭔가 클릭했는데 화면이 멈칫하거나 깜빡임이 생기면 사용자 입장에선 금방 답답해지거든요. 

그런데 최근에 브라우저 차원에서 내비게이션을 더 똑똑하게 처리해주는 최신 Navigation API가 베이스라인으로 새롭게 등장했습니다. 이걸 써보니 기존의 페이지 전환 방식과는 확실히 다른 접근법이라서, 오늘은 실제 프로젝트에 어떻게 적용할 수 있는지, 그리고 이 API가 왜 성능과 UX를 동시에 잡는지 이야기해보려고 해요.

---

## Navigation API가 기존 내비게이션과 다른 점은 뭘까?

우리가 일반적으로 페이지를 이동할 때는 링크 클릭이나 `window.location` 변경 등으로 페이지 전체를 새로 로드하는 방식이었죠. SPA에서는 자바스크립트 라우팅을 통해 전체 페이지 리로드 없이 콘텐츠만 바꾸는 식으로 개선했지만, 여전히 네트워크 요청과 상태 관리가 복잡해질 수밖에 없었어요.

최신 Navigation API는 브라우저가 내비게이션 이벤트를 더 세밀하게 제어할 수 있도록 설계됐습니다. 비동기 내비게이션을 기본으로 지원해서 페이지 전환 중에도 사용자 인터랙션에 즉각 반응할 수 있고, 불필요한 리소스 로드를 줄여서 전체 성능을 끌어올려줍니다. 

GitHub 엔지니어링 블로그에 따르면, 이 API는 내비게이션 상태 관리 최적화와 이벤트 연동에 초점을 맞춰서, 기존 SPA에서도 겪던 상태 불일치 문제를 크게 완화했다고 해요[GitHub Engineering Blog](https://github.blog/category/engineering/).

## 실제 프로젝트에 Navigation API 어떻게 적용할까?

제가 최근에 작업한 프로젝트에서 Navigation API를 도입한 경험을 공유할게요. 아래는 기본적인 사용법 예시입니다.

```js
// navigation 객체는 window.navigation으로 접근 가능
window.navigation.addEventListener('navigate', event => {
  const destination = event.destination.url;

  // 비동기 내비게이션 처리
  event.intercept({
    async handler() {
      // 필요한 데이터 미리 fetch
      const response = await fetch(destination);
      const html = await response.text();

      // DOM 업데이트
      document.getElementById('app').innerHTML = html;

      // 히스토리 상태도 적절히 관리
      history.pushState({}, '', destination);
    }
  });
});
```

이 코드는 클릭한 링크의 URL을 받아서 fetch로 콘텐츠를 비동기 로드하고, 페이지 전체를 새로고침하지 않고 내부 DOM만 교체합니다. 핵심은 `event.intercept()` 메서드를 사용해서 내비게이션 이벤트를 가로채고, 원하는 로직을 실행할 수 있다는 점이에요.

이렇게 하면 브라우저가 기본적으로 페이지를 새로 로드하는 대신, 필요한 부분만 업데이트해서 훨씬 빠른 전환이 가능해집니다. 물론 이 과정에서 상태 관리도 신경 써야 하는데, Navigation API가 히스토리 API와 자연스럽게 연동되기 때문에 SPA 상태 유지에 유리하죠.

## Cloudflare 사례에서 배우는 네트워크 최적화

Cloudflare가 Navigation API를 도입하면서 얻은 가장 큰 성과 중 하나는 네트워크 요청 최적화였어요. 기존에는 페이지 전환 시마다 전체 HTML과 리소스를 다시 요청하는 경우가 많았는데, Navigation API를 활용해 필요한 데이터만 요청하고 캐시를 적극 활용하면서 클라이언트-서버 간 데이터 교환 비용을 크게 줄였다고 합니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

이게 실제로 어떤 의미냐면, 예를 들어 사용자가 빠르게 여러 페이지를 이동할 때 서버 부하가 줄어들고, 네트워크 지연도 최소화되어 체감 속도가 훨씬 좋아진다는 거죠. 

저도 이 부분을 경험하면서 느낀 건데, 단순히 API를 바꾸는 걸 넘어 네트워크와 캐시 전략을 함께 고민해야 진짜 효과를 볼 수 있다는 점이에요.

## Navigation API가 SPA 아키텍처에 주는 의미

마틴 파울러의 아키텍처 가이드에서도 언급하듯, Navigation API 도입은 프론트엔드와 백엔드 간 경계 설정을 명확히 하면서 SPA 내 상태 관리 일관성을 유지하는 데 큰 도움이 됩니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

기존 SPA에서는 클라이언트 라우팅과 서버 사이드 렌더링이 혼재되면서 상태 동기화가 복잡해지는 경우가 많았는데, Navigation API는 브라우저 차원에서 내비게이션 이벤트를 표준화하고 상태 변경을 관리해줍니다. 덕분에 개발자는 상태 관리 로직에 집중할 수 있고, 백엔드와의 데이터 계약도 더 명확해지죠.

## 도입 시 주의할 점과 현실적인 한계

이 API가 분명 매력적이지만, 처음 도입할 때는 몇 가지 고려해야 할 점이 있습니다.

- **브라우저 지원 현황**: 아직 모든 브라우저가 완벽히 지원하지 않아서, 폴리필이나 대체 로직을 준비해야 할 수도 있어요.

- **복잡한 상태 관리**: SPA 상태가 복잡할수록 Navigation API 이벤트 핸들러 내에서 상태 동기화가 까다로울 수 있습니다. 특히 전역 상태 관리 라이브러리와의 연동을 꼼꼼히 테스트해야 해요.

- **SEO 이슈**: 서버 사이드 렌더링과의 조합이 중요합니다. Navigation API만으로는 SEO 최적화가 완벽하지 않으니, SSR과 함께 쓰는 전략을 고민해야 합니다.

처음엔 이게 별거 아닌 것 같지만, 실제로 대규모 프로젝트에 적용해보면 이런 세세한 부분에서 시행착오가 꽤 많아요.

## 내비게이션 속도를 높이고 싶다면, Navigation API부터 써봐야 하는 이유

결론적으로, 최신 Navigation API는 단순히 페이지를 빠르게 바꾸는 걸 넘어서 사용자 경험 전반을 개선하는 도구입니다. 비동기 내비게이션, 네트워크 요청 최적화, 상태 관리 일관성 확보라는 세 마리 토끼를 동시에 잡을 수 있죠.

실제로 GitHub과 Cloudflare 같은 대형 서비스에서 도입해 성능과 사용자 만족도를 크게 끌어올린 사례가 이를 증명합니다. 물론 도입 초기에는 브라우저 호환성과 상태 관리 복잡성 같은 현실적인 문제도 있지만, 장기적으로 보면 충분히 투자할 가치가 있는 기술입니다.

프론트엔드 내비게이션을 한 단계 업그레이드하고 싶다면, Navigation API를 꼭 한번 시도해보세요.
