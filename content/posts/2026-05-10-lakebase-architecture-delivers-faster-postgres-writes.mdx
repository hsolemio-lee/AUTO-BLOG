# Postgres 쓰기 병목, 왜 아직도 답이 없을까?

최근에 우리 팀에서 Postgres 기반 서비스의 쓰기 성능 문제로 골머리를 앓았던 경험이 있어요. 초당 수천 건의 쓰기 요청이 몰리면 디스크 I/O가 병목이 되어 응답 지연이 눈에 띄게 커지더라고요. 흔히 알려진 튜닝 방법, 예를 들어 인덱스 최적화, WAL(Write-Ahead Logging) 설정 조정, 커넥션 풀링 등도 한계가 있었습니다.

그런데 최근에 Lakebase라는 새로운 아키텍처를 접하면서 "이게 우리가 찾던 해법일까?" 하는 생각이 들었어요. GitHub 엔지니어링 블로그에서 소개한 이 구조는 기존 Postgres의 I/O 병목을 분산 로그 기반 저장소로 해결한다고 하더군요[GitHub Engineering Blog](https://github.blog/category/engineering/).

이번 글에서는 Lakebase의 핵심 아이디어가 뭔지, 실제로 어떤 트레이드오프가 있는지, 그리고 기존 Postgres 시스템을 어떻게 마이그레이션할 수 있는지 제 경험을 섞어 이야기해보겠습니다.

---

## Lakebase가 Postgres 쓰기 속도를 2배 이상 끌어올리는 비밀

기존 Postgres는 쓰기 작업이 디스크에 직접 WAL을 기록하고, 데이터를 동기화하는 과정에서 I/O 병목이 발생합니다. 특히 디스크가 느리거나 동시 쓰기 요청이 많으면 지연이 크게 늘어나죠.

Lakebase는 여기에 근본적인 변화를 줬어요. 쓰기 요청을 전통적인 방식처럼 바로 DB에 반영하는 대신, 분산 로그에 순차적으로 기록합니다. 이 로그는 빠른 순차 I/O를 활용해 지연을 최소화하고, 그 뒤에 비동기적으로 실제 데이터베이스에 반영하는 방식입니다. 덕분에 쓰기 처리량이 크게 증가하고, 지연 시간은 눈에 띄게 줄어들죠.

이 구조 덕분에 초당 수만 건의 쓰기 요청도 감당할 수 있다고 하니, 우리 같은 대규모 서비스에 딱 맞는 솔루션 아닐까요?[GitHub Engineering Blog](https://github.blog/category/engineering/)

## 로그 기반 처리, 트랜잭션 일관성과 장애 복구는 어떻게?

"비동기적으로 반영하면 데이터 일관성은 괜찮을까?" 하는 의문이 들죠. Lakebase는 로그 재생(replay) 메커니즘을 도입해 이 문제를 해결합니다. 장애 발생 시 로그를 다시 재생해 데이터베이스 상태를 복구하는 거예요.

이 과정에서 트랜잭션 일관성을 유지하기 위해 로그의 순서를 엄격히 관리하고, 커밋 시점에 맞춰 읽기 작업이 최신 상태를 반영하도록 설계되어 있습니다. 물론 이 때문에 읽기 지연이 기존 Postgres보다 약간 증가하는 트레이드오프가 있죠.

즉, 쓰기 지연을 줄인 대신 읽기 지연이 올라가는 구조인데, 대부분 쓰기 부하가 높은 서비스에서는 이 정도 읽기 지연 증가는 감내할 만한 수준입니다. 실제로 Martin Fowler의 아키텍처 가이드에서도 이런 로그 기반 처리의 장단점을 자세히 설명하고 있어요[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

## 기존 Postgres 시스템에서 Lakebase로 넘어갈 때 꼭 확인해야 할 점

우리 팀도 마이그레이션을 고민하면서 몇 가지 중요한 점을 깨달았어요.

1. **데이터 일관성 모델 재검토**: 기존 Postgres는 강력한 동기식 커밋을 기본으로 하지만, Lakebase는 비동기 로그 반영 특성상 강한 일관성 모델을 그대로 유지하려면 애플리케이션 레벨에서 보완이 필요합니다.

2. **장애 복구 전략 수정**: 로그 재생 메커니즘에 맞춰 장애 복구 절차를 새로 설계해야 합니다. 예를 들어, 로그 손상 시 재생 불가 상황에 대비한 백업 정책 강화가 필요해요.

3. **애플리케이션 조정**: 로그 순차 기록 특성에 맞춰 트랜잭션 처리 방식과 쿼리 패턴을 일부 변경해야 하는 경우가 있습니다. 특히 트랜잭션 경계와 읽기 시점 일관성에 신경 써야 하죠.

이 부분들은 Martin Fowler의 아키텍처 가이드에서 마이그레이션 시 고려사항으로도 언급되어 있습니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

## 클라우드 네이티브 환경에서 Lakebase가 빛나는 이유

Lakebase는 클라우드 네이티브 환경에 최적화되어 있어, 컨테이너 오케스트레이션과 마이크로서비스 아키텍처와 궁합이 좋습니다. 분산 로그 스토리지를 활용하니 확장성도 뛰어나고, 서비스별 독립적 배포와 유지보수도 한결 수월해지죠.

우리 팀도 Kubernetes 위에서 Lakebase를 운영하며, 쓰기 부하가 급증해도 노드를 수평 확장해 대응할 수 있었어요. 덕분에 서비스 가용성과 성능이 크게 개선됐습니다.

Microsoft의 클라우드 디자인 패턴 문서에서도 이와 같은 분산 로그 기반 아키텍처가 클라우드 환경에서 확장성과 복원력을 높이는 좋은 사례로 소개되고 있습니다[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/).

## 실제로 Lakebase 쓰기 API를 호출하는 간단한 예시

아래는 Lakebase의 분산 로그에 쓰기 요청을 순차적으로 기록하는 간단한 코드 예시입니다. 실제로는 내부에서 비동기 반영이 일어나지만, API는 동기 커밋처럼 보이도록 설계되어 있어요.

```java
public class LakebaseWriter {
    private final DistributedLogClient logClient;

    public LakebaseWriter(DistributedLogClient client) {
        this.logClient = client;
    }

    // 로그에 순차적으로 쓰기 작업을 기록하고, 결과를 기다림
    public boolean writeRecord(String table, Map<String, Object> data) {
        WriteRequest req = new WriteRequest(table, data);
        try {
            // 로그에 비동기 기록, 내부적으로 DB 반영도 처리
            CompletableFuture<Boolean> future = logClient.append(req);
            // 최대 100ms 대기, 타임아웃 시 실패 처리
            return future.get(100, TimeUnit.MILLISECONDS);
        } catch (TimeoutException e) {
            // 로그 지연 시 재시도 로직 필요
            return false;
        } catch (Exception e) {
            // 기타 예외 처리
            return false;
        }
    }
}
```

이런 식으로 로그에 쓰기 요청을 순차적으로 기록하면, 내부적으로는 빠른 순차 I/O가 가능해져서 기존 Postgres 직접 쓰기보다 훨씬 낮은 지연과 높은 처리량을 달성할 수 있습니다.

## Lakebase 도입, 꼭 기억해야 할 현실적인 단점

처음엔 로그 기반 아키텍처가 너무 좋아 보여서 무조건 도입하고 싶었는데요, 몇 가지 현실적인 단점도 있었습니다.

- **읽기 지연 증가**: 앞서 말했듯이, 비동기 반영 구조 때문에 읽기 작업이 최신 상태를 반영하는 데 약간 시간이 걸립니다.

- **운영 복잡도 상승**: 로그 재생과 장애 복구를 위한 추가 운영 절차가 필요합니다. 로그 손상이나 불일치 문제는 전통적 DB 운영보다 더 신경 써야 해요.

- **애플리케이션 수정 부담**: 기존 트랜잭션 경계나 일관성 가정을 바꾸는 작업이 필요할 수 있습니다. 특히 복잡한 트랜잭션을 많이 쓰는 서비스는 조정이 까다로울 수 있죠.

이런 점들은 마이그레이션 계획 세울 때 반드시 고려해야 할 부분입니다.

# 마무리하며: Lakebase, 우리 서비스에 맞을까?

Lakebase는 전통적인 Postgres가 가진 I/O 병목 문제를 분산 로그 기반으로 혁신적으로 해결한 아키텍처입니다. 쓰기 처리량과 지연 시간 개선 효과가 크고, 클라우드 네이티브 환경에서 확장성도 뛰어나죠.

하지만 읽기 지연 증가, 운영 복잡도, 애플리케이션 수정 부담 같은 트레이드오프도 명확합니다. 우리 팀처럼 쓰기 부하가 많고 확장성이 중요한 서비스라면 도입을 고려해볼 만해요. 반면 읽기 지연에 민감하거나 복잡한 트랜잭션을 많이 쓰는 환경이라면 신중한 검토가 필요합니다.

마이그레이션 시에는 데이터 일관성 모델과 장애 복구 전략을 꼼꼼히 재검토하고, 애플리케이션 레벨 조정을 병행하는 게 필수입니다.

개인적으로는 Lakebase 같은 로그 기반 아키텍처가 앞으로 데이터베이스 설계의 중요한 방향 중 하나라고 생각해요. 직접 써보면서 얻은 경험을 공유할 수 있어 기쁩니다.
