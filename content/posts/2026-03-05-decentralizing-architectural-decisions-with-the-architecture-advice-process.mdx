## "우리 팀만의 아키텍처 결정, 어떻게 믿고 맡길 수 있을까?"

얼마 전 우리 조직에서 이런 질문이 나왔어요. 마이크로서비스가 늘어나면서 각 팀이 자기 서비스에 맞게 기술 스택이나 설계 방식을 선택하는 일이 잦아졌는데, 이게 과연 전체 시스템 품질에 악영향을 주지 않을까 하는 걱정이었죠. 사실 저도 처음엔 중앙에서 모든 아키텍처 결정을 통제하는 게 더 안전하다고 생각했어요. 그런데 마틴 파울러가 말한 것처럼, 이런 중앙 집중식 방식은 규모가 커질수록 병목과 비효율을 낳는다는 걸 경험하면서 생각이 바뀌었습니다[Martin Fowler - Microservices](https://martinfowler.com/articles/microservices.html).


## 왜 아키텍처 의사결정을 분산해야 할까?

마틴 파울러는 마이크로서비스 아키텍처에서 각 팀이 독립적으로 아키텍처 결정을 내릴 수 있도록 권한을 분산하는 게 확장성과 유지보수성에 큰 도움이 된다고 강조합니다. 각 팀은 자신의 도메인과 서비스 특성에 가장 적합한 기술과 설계를 선택할 수 있으니, 빠른 의사결정과 민첩한 대응이 가능하죠. 반면 중앙 집중식으로 모든 결정을 처리하면, 결정권자가 병목이 되고, 변화에 대한 대응 속도가 느려집니다.

하지만 이게 무조건 좋은 것만은 아니에요. 각 팀이 독립적으로 결정하다 보면, 시스템 전반의 일관성이나 품질 관리가 어려워질 수 있거든요. 그래서 "분산된 의사결정"을 실현하려면 적절한 가이드라인과 프로세스, 그리고 도구 지원이 필수입니다.


## Microsoft가 제안하는 'Advisor Pattern'으로 분산 의사결정 지원하기

Microsoft의 클라우드 디자인 패턴 문서에서는 'Advisor Pattern'이라는 개념을 소개합니다. 이 패턴은 각 팀이 자신의 도메인에 맞는 최적의 아키텍처 결정을 내릴 수 있도록 조언자 역할을 하는 시스템이나 프로세스를 둔다는 뜻이에요[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/).

예를 들어, 중앙 아키텍처 팀은 전체적인 가이드라인과 표준을 정의하고, 각 팀은 이 가이드라인을 참고해 자신만의 아키텍처를 설계합니다. 그리고 필요하면 중앙 팀이나 다른 전문가에게 조언을 구하는 거죠. 이렇게 하면 각 팀의 자율성과 전문성을 살리면서도, 전체 시스템의 일관성을 어느 정도 유지할 수 있습니다.

실제로 Microsoft 내부에서도 이 패턴을 활용해 대규모 클라우드 서비스들을 운영하고 있는데, 아키텍처 결정이 빠르고 유연해지는 동시에 품질 저하를 막는 데 효과적이었다고 합니다.


## 자동화된 CI/CD 파이프라인으로 분산된 결정의 품질을 담보하는 법

분산된 아키텍처 의사결정에서 가장 걱정되는 부분 중 하나가 바로 "변경사항들이 전체 시스템에 미치는 영향"이에요. 각 팀이 독립적으로 변경을 진행하다 보면, 예상치 못한 충돌이나 품질 저하가 발생할 수 있거든요.

이때 마틴 파울러가 제안하는 Continuous Integration(CI) 원칙이 큰 도움이 됩니다[Martin Fowler - Continuous Integration](https://martinfowler.com/articles/continuousIntegration.html). 각 팀이 변경한 코드를 자동화된 빌드와 테스트 파이프라인에 즉시 통합하고 검증하는 거죠. 이렇게 하면 문제를 조기에 발견할 수 있고, 전체 시스템의 품질을 일정 수준 이상으로 유지할 수 있습니다.

우리 팀도 GitHub Actions를 도입해서 각 서비스별 독립 워크플로우를 운영하고 있는데, 이게 분산된 아키텍처 결정과 완벽히 맞아떨어지더라고요. 각 팀은 자신만의 빌드, 테스트, 배포 파이프라인을 정의하고 실행할 수 있어서 자율성이 극대화됩니다[GitHub Actions Documentation](https://docs.github.com/en/actions).


```yaml
# 예시: 서비스 A의 GitHub Actions 워크플로우
name: CI/CD

on:
  push:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Set up JDK 17
        uses: actions/setup-java@v3
        with:
          java-version: '17'
      - name: Build with Gradle
        run: ./gradlew build
      - name: Run tests
        run: ./gradlew test

  deploy:
    needs: build
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - name: Deploy to staging
        run: ./deploy.sh staging
```

이 예시는 서비스 A가 main 브랜치에 푸시될 때마다 자동으로 빌드, 테스트, 그리고 스테이징 환경 배포까지 진행하는 워크플로우입니다. 각 팀이 이런 워크플로우를 독립적으로 관리하면서도, 공통된 품질 기준(예: 빌드 성공, 테스트 통과)을 충족해야 하니 자연스럽게 품질 통제가 됩니다.


## 분산된 의사결정에도 명확한 커뮤니케이션과 문서화가 필수인 이유

GitHub 엔지니어링 블로그에서는 대규모 분산 시스템에서 각 팀이 독립적으로 아키텍처 결정을 내리면서도 전체 시스템의 일관성을 유지하기 위해 명확한 커뮤니케이션과 문서화 프로세스를 도입한 사례를 소개합니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

처음엔 각 팀이 자기 마음대로 결정하는 것 같아도, 서로 어떤 선택을 했는지, 왜 그랬는지 공유하지 않으면 결국 충돌과 중복 작업이 생깁니다. 그래서 다음과 같은 실천이 중요해요:

- **아키텍처 결정 기록(ADR, Architecture Decision Records) 작성:** 각 팀은 주요 결정과 그 배경, 대안, 결과를 문서화해서 공유합니다.
- **정기적인 아키텍처 리뷰 미팅:** 팀 간 교차 리뷰를 통해 결정 사항을 검증하고 조율합니다.
- **공통 가이드라인과 표준 유지:** 최소한의 공통 규칙을 정해 시스템 전체의 일관성을 확보합니다.

이런 프로세스를 통해 분산된 의사결정이 혼란이 아닌 협업으로 작동하게 됩니다.


## 직접 겪어보니, 분산 의사결정은 결국 문화와 도구의 문제

제가 경험한 바로는, 분산된 아키텍처 결정은 기술적인 문제보다 조직 문화와 도구 활용이 더 중요합니다. 아무리 좋은 패턴과 프로세스를 도입해도, 팀 간 신뢰와 열린 커뮤니케이션이 없으면 실패하기 쉽죠.

또한, GitHub Actions 같은 자동화 도구를 적극 활용하지 않으면 품질 관리가 힘들고, 의사결정이 늦어져서 오히려 비효율이 커집니다. 반대로 잘 구축된 CI/CD 파이프라인과 문서화 프로세스가 있으면, 각 팀이 자신 있게 독립적인 결정을 내리면서도 전체 시스템 품질을 유지할 수 있습니다.


---

### 참고로, 분산 의사결정 도입 시 고려할 점

- **초기 가이드라인은 너무 엄격하지 않게:** 너무 빡빡하면 자율성이 떨어지고, 너무 느슨하면 품질 저하 우려
- **자동화 테스트 커버리지 확보:** 변경사항 검증을 위한 테스트는 필수
- **ADR 작성 문화 정착:** 결정 기록이 쌓여야 지식이 공유되고 재사용됨
- **주기적 교차 리뷰:** 팀 간 이해관계 조율과 기술 부채 방지

## 마무리하며

분산된 아키텍처 의사결정은 마이크로서비스 시대에 필수적인 패턴입니다. 하지만 단순히 권한을 나누는 것만으로는 성공할 수 없고, Microsoft의 Advisor Pattern, CI/CD 자동화, 그리고 GitHub의 커뮤니케이션 사례에서 보듯이 적절한 프로세스와 도구 지원이 뒷받침돼야 합니다.

우리 팀도 이 과정을 겪으면서 "분산된 의사결정은 곧 책임과 신뢰의 문화"임을 깨달았어요. 기술적으로는 GitHub Actions 같은 자동화 도구와 ADR 문서화가 큰 힘이 됐고요. 여러분도 팀 상황에 맞게 이런 패턴을 도입해 보시면, 아키텍처 결정의 병목을 줄이고 빠르게 변화에 대응하는 조직으로 거듭날 수 있을 겁니다.
