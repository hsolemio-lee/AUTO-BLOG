## 갑작스러운 모니터링 장애, Helm 차트 업그레이드가 답일까?

최근 우리 팀에서 Kubernetes 클러스터에 설치한 Grafana 모니터링이 자꾸 불안정해졌어요. 대시보드가 안 뜨거나 메트릭이 끊기는 현상에, 로그를 뒤져도 뾰족한 해결책이 없었죠. 그러다 Grafana에서 Kubernetes 모니터링 Helm 차트 v4가 나왔다는 소식을 듣고 업그레이드를 시도했습니다. 결과는? 여러 버그가 잡히고, 안정성이 눈에 띄게 좋아졌어요. 이 경험을 공유하려고 합니다.

---

## Helm 차트 v4가 실제로 뭐가 달라졌길래?

Grafana Helm 차트 v4는 단순한 버그 수정에 그치지 않고, 백엔드 시스템의 관측성과 안정성을 크게 개선하는 여러 업데이트를 포함하고 있어요. 특히 다음 세 가지가 눈에 띕니다:

- **Liveness, Readiness, Startup 프로브 설정 강화**: Kubernetes 기본 기능을 적극 활용해 애플리케이션 상태를 더 정확히 감지하고, 장애 복구를 자동화할 수 있게 되었죠.
- **OpenTelemetry 통합 지원 확대**: 분산 트레이싱과 메트릭 수집을 한층 강화해 클라우드 네이티브 환경에서의 관측성을 높였습니다.
- **네트워크 정책과 리소스 제한 설정 권장**: 클라우드 환경에 맞춰 안정성을 확보하는 데 필수적인 설정들이 기본값과 문서에 반영됐어요.

이 덕분에 우리 모니터링 시스템은 예전보다 훨씬 견고해졌습니다.[Grafana - Observability Best Practices](https://grafana.com/docs/grafana/latest/fundamentals/)

---

## Kubernetes 프로브 설정, 이렇게 하면 실패 확률이 줄어든다

Helm 차트 v4를 적용하면서 가장 신경 쓴 부분이 바로 Kubernetes의 프로브 설정입니다. Liveness, Readiness, Startup 프로브를 적절히 구성하지 않으면, 애플리케이션이 실제로는 살아있는데도 죽었다고 판단하거나, 반대로 장애를 감지하지 못해 복구가 늦어질 수 있어요.

우리 팀은 다음과 같은 설정을 기본으로 잡았습니다:

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 3000
  initialDelaySeconds: 30
  periodSeconds: 10
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /ready
    port: 3000
  initialDelaySeconds: 15
  periodSeconds: 5
  failureThreshold: 3

startupProbe:
  httpGet:
    path: /startup
    port: 3000
  failureThreshold: 30
  periodSeconds: 10
```

- **Liveness Probe**는 30초 뒤부터 10초 간격으로 체크하며, 3회 연속 실패 시 재시작합니다.
- **Readiness Probe**는 서비스가 준비됐는지 더 자주 확인해서 트래픽 분배를 조절합니다.
- **Startup Probe**는 초기 부팅 시 더 긴 시간을 주어, 초기화가 느린 컴포넌트가 문제로 오인되지 않도록 했죠.

이 설정 덕분에 실제로 배포 후 2주간 다운타임이 거의 없었고, 장애 발생 시 자동 복구도 확실히 체감됐습니다.[Kubernetes - Configure Liveness, Readiness and Startup Probes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)

## OpenTelemetry와의 만남: 분산 트레이싱이 이렇게 쉬웠다니

v4 차트에서 가장 반가웠던 건 OpenTelemetry 지원 강화였습니다. 기존엔 Prometheus 메트릭 수집 중심이었다면, 이제는 분산 트레이싱까지 자연스럽게 통합할 수 있어요. 덕분에 마이크로서비스 간 호출 흐름을 훨씬 쉽게 추적할 수 있었습니다.

설정 예시는 이렇습니다:

```yaml
opentelemetry:
  enabled: true
  collector:
    service:
      type: ClusterIP
    config:
      receivers:
        otlp:
          protocols:
            grpc: {}
            http: {}
      exporters:
        logging:
          loglevel: debug
      service:
        pipelines:
          traces:
            receivers: [otlp]
            exporters: [logging]
```

이렇게 하면 Grafana가 OpenTelemetry Collector를 통해 분산 트레이싱 데이터를 수집하고, 로그로도 확인할 수 있어 문제 원인 분석이 훨씬 수월해졌습니다. 다만, Collector 설정이 복잡해질 수 있으니, 작은 규모부터 단계적으로 적용하는 걸 추천합니다.[OpenTelemetry Documentation](https://opentelemetry.io/docs/)

## 클라우드 환경에서 네트워크 정책과 리소스 제한을 무시하면 무슨 일이?

우리 팀은 AWS EKS 환경에서 Grafana Helm 차트를 운영 중인데, 네트워크 정책과 리소스 제한 설정을 제대로 하지 않으면, 의외로 모니터링 자체가 불안정해지는 경험을 했어요. 특히, 클러스터 내 Pod 간 통신이 막히거나, 리소스 부족으로 Pod가 자주 재시작되는 상황이 발생했죠.

그래서 Helm 차트 values.yaml에 다음과 같은 설정을 추가했습니다:

```yaml
resources:
  limits:
    cpu: 500m
    memory: 512Mi
  requests:
    cpu: 250m
    memory: 256Mi

networkPolicy:
  enabled: true
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: prometheus
  egress:
    - to:
        - podSelector:
            matchLabels:
              app: grafana
```

이 설정으로 인해 리소스 부족으로 인한 OOMKill이나 CPU 스로틀링 현상이 줄었고, 네트워크 정책 덕분에 불필요한 외부 접근을 막아 보안도 강화됐습니다. 물론, 네트워크 정책은 클러스터 환경마다 달라질 수 있으니, 꼭 우리 환경에 맞게 세밀하게 조정해야 합니다.[Kubernetes Concepts Overview](https://kubernetes.io/docs/concepts/overview/)

## Helm 차트 업그레이드, 실제로는 이렇게 했다

우리 팀은 다음 절차로 Helm 차트 v4 업그레이드를 진행했어요:

1. **현재 설치된 차트 버전과 설정 백업**: `helm get values grafana-k8s > old-values.yaml`
2. **v4 차트 릴리즈 노트 확인 및 변경점 검토**
3. **새 values.yaml 파일 생성 및 프로브, 리소스, 네트워크 정책 설정 추가**
4. **`helm upgrade --install` 명령어로 배포**
5. **Pod 상태와 로그 모니터링, 대시보드 정상 작동 여부 확인**

특히, 프로덕션 환경에서는 한 번에 전체 업그레이드하지 말고, 스테이징에서 충분히 테스트하는 게 중요합니다. 우리도 처음에 프로브 설정을 실수해서 서비스가 계속 재시작되는 경험을 했거든요.

## 마치며: 업그레이드가 주는 작은 안정감, 그리고 관측성의 힘

처음엔 Helm 차트 버전 업그레이드가 번거롭고, 설정도 복잡해 보여서 미뤘는데, 막상 해보니 여러 버그가 잡히고 시스템 안정성이 확실히 올라갔습니다. 특히 Kubernetes 프로브 설정과 OpenTelemetry 통합은 관측성을 한 단계 끌어올려, 문제 발생 시 원인 파악과 대응이 훨씬 수월해졌죠.

한 가지 팁을 드리자면, Helm 차트 업그레이드 전후로 꼭 현재 설정을 꼼꼼히 비교하고, 클러스터 환경에 맞는 리소스와 네트워크 정책을 재점검하세요. 이게 의외로 안정성에 큰 차이를 만듭니다.
