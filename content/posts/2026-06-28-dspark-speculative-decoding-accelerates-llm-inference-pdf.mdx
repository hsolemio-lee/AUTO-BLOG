## "왜 LLM 추론이 이렇게 느리지?"에서 시작한 고민

최근 우리 서비스에 대형 언어 모델(LLM)을 도입하면서 가장 먼저 맞닥뜨린 난관은 바로 추론 속도였다. 특히 실시간 응답이 중요한 백엔드 API에서는 1초가 아쉬운 상황. DSpark 논문에서 소개한 speculative decoding 기법을 알게 된 후, "이걸 실제 서비스에 어떻게 적용할 수 있을까?"라는 질문이 자연스레 따라왔다.

Speculative decoding은 작은 보조 모델이 먼저 후보 토큰을 빠르게 예측하고, 큰 주 모델이 이를 검증하는 방식이다. 이 덕분에 전체 추론 시간이 크게 줄어든다고 하는데, 실제 백엔드 환경에선 네트워크 지연, 모델 간 통신, 캐싱 등 복잡한 문제가 얽혀 있다. 이번 글에서는 내가 직접 실험하고 경험한 내용을 바탕으로, 어떻게 speculative decoding을 백엔드에 통합하고 성능을 최적화했는지 공유하려 한다.

---

## 작은 모델과 큰 모델을 어떻게 조율해야 할까?

Speculative decoding의 핵심은 ‘작은 모델이 먼저 뛰고 큰 모델이 뒤따라 검증한다’는 점이다. DSpark에서는 작은 모델을 저비용으로 돌려 후보 토큰을 빠르게 뽑고, 큰 모델이 그 후보를 맞으면 바로 다음 토큰으로 넘어간다. 이렇게 하면 큰 모델이 모든 토큰을 직접 생성하는 것보다 훨씬 빠르다.

내가 적용해 본 환경에서는 작은 모델로 GPT-2 small(1.2억 파라미터급)을, 큰 모델로 GPT-3(175억 파라미터급)를 썼다. 작은 모델은 10~20ms 내에 후보 토큰 5개를 뽑아내고, 큰 모델은 이 후보 중 맞는 토큰을 검증하는 식이다. 이 과정에서 중요한 점은 작은 모델의 예측 정확도와 후보 토큰 수를 적절히 조절하는 것이다. 예를 들어 후보 토큰을 너무 적게 잡으면 큰 모델이 재계산할 확률이 높아져 오히려 속도가 떨어진다. 반대로 너무 많이 잡으면 작은 모델이 무의미한 후보를 많이 뽑아 네트워크 부하가 커진다.

내 경험상 후보 토큰 5~7개가 적당했고, 작은 모델의 품질은 실험을 통해 조정했다. 너무 작은 모델은 오히려 전체 추론 시간을 늘릴 수 있으니 주의해야 한다.

## 백엔드 아키텍처에서 비동기 통신과 캐싱은 필수

실제 서비스에 speculative decoding을 넣으려면 작은 모델과 큰 모델을 독립된 마이크로서비스로 분리하는 게 좋다. 이렇게 하면 각 모델의 부하를 독립적으로 조절할 수 있고, 장애가 났을 때도 격리가 가능하다. DSpark 방식도 이 점을 강조한다.

내가 구축한 시스템은 다음과 같다:

- 작은 모델 서비스: 빠른 응답과 후보 토큰 생성 담당
- 큰 모델 서비스: 후보 토큰 검증 및 최종 토큰 생성 담당
- 추론 조율기: 두 모델의 결과를 비동기적으로 받아 조합

특히 비동기 통신은 필수였다. 작은 모델의 응답을 기다리지 않고 큰 모델이 후보 검증을 병렬로 시작할 수 있어야 전체 지연 시간을 줄일 수 있다. 이를 위해 gRPC 스트리밍과 Redis 캐시를 활용했다. 후보 토큰 결과를 Redis에 캐싱해 같은 프롬프트에 대해 재사용하고, 네트워크 지연을 줄였다.

이 과정에서 가장 골치 아팠던 건 네트워크 지연과 모델 응답 시간 변동이었다. 작은 모델이 느려지면 큰 모델이 대기 상태에 빠져 전체 속도가 떨어지기 때문. 그래서 작은 모델 서비스는 CPU 인스턴스 2대, 큰 모델은 GPU 인스턴스 4대로 구성해 부하를 균형 있게 분산시켰다.

## 실제 코드로 보는 speculative decoding 기본 구조

아래는 Python으로 작성한 간단한 speculative decoding 추론 예시다. 작은 모델과 큰 모델을 비동기 호출하고, 작은 모델이 뽑은 후보를 큰 모델이 검증하는 흐름을 보여준다.

```python
import asyncio

async def small_model_predict(prompt):
    # 작은 모델에서 후보 토큰 5개 예측 (모의 응답)
    await asyncio.sleep(0.02)  # 20ms 대기
    return ['token1', 'token2', 'token3', 'token4', 'token5']

async def large_model_validate(prompt, candidates):
    # 큰 모델이 후보 중 맞는 토큰 검증 (모의 응답)
    await asyncio.sleep(0.1)  # 100ms 대기
    # 여기서는 첫 후보가 맞다고 가정
    return candidates[0]

async def speculative_decoding(prompt):
    small_task = asyncio.create_task(small_model_predict(prompt))
    # 작은 모델 후보 토큰을 기다리지 않고 큰 모델 검증 시작
    candidates = await small_task
    large_task = asyncio.create_task(large_model_validate(prompt, candidates))
    result = await large_task
    return result

if __name__ == '__main__':
    prompt = "Hello, how are you"
    result = asyncio.run(speculative_decoding(prompt))
    print(f"최종 토큰: {result}")
```

이 코드는 실제 서비스용으로는 너무 단순하지만, 핵심 흐름을 잡기에 충분하다. 여기서 중요한 점은 작은 모델의 후보 토큰을 기다리는 동안 큰 모델이 검증을 병렬로 준비할 수 있도록 비동기 태스크를 잘 분리하는 것이다.

## 작은 모델 정확도와 후보 토큰 수 조정이 성능의 열쇠

내가 직접 실험해보니 작은 모델의 예측 정확도가 떨어지면 큰 모델이 후보를 재계산하는 빈도가 높아져 속도 향상이 제한된다. 예를 들어 작은 모델이 70% 정확도를 보일 때는 추론 속도가 평균 1.8배 빨라졌지만, 50% 이하로 떨어지면 오히려 큰 모델 부하가 늘어나 전체 지연이 커졌다.

따라서 작은 모델을 너무 경량화하는 건 오히려 역효과다. DSpark 논문도 후보 토큰 수와 작은 모델 품질을 적절히 조절하라고 권고한다. 후보 토큰 수는 3~7개 사이가 현실적이고, 작은 모델은 적어도 중간급 크기 이상을 유지하는 게 좋다.

이 부분은 서비스 특성에 따라 튜닝이 필요하다. 예를 들어 응답 속도가 최우선이라면 후보 수를 늘려 작은 모델이 가능한 많은 후보를 뽑게 하고, 비용 절감이 목적이라면 후보 수를 줄여 네트워크 트래픽과 계산량을 낮추는 식이다.

## 대규모 트래픽 환경에서 장애 격리와 부하 분산은 어떻게 할까?

마이크로서비스 아키텍처에서 speculative decoding을 적용하려면 작은 모델과 큰 모델 간 역할 분담이 명확해야 한다. 특히 대규모 트래픽이 몰릴 때 작은 모델이 병목이 되면 전체 추론이 지연된다.

내가 운영하는 서비스에서는 작은 모델 서비스에 오토스케일링을 적용해 CPU 사용률 70%를 넘으면 인스턴스를 자동으로 늘리도록 했다. 큰 모델은 GPU 자원 비용이 커서 수동 조절하지만, 큐잉 시스템을 도입해 부하를 관리했다.

또한 장애 격리를 위해 작은 모델 서비스가 다운되면 큰 모델이 단독으로 추론을 수행하는 페일오버 로직도 넣었다. 이때는 속도가 느려지지만, 서비스 중단 없이 운영 가능하다.

이런 설계는 Martin Fowler의 아키텍처 가이드에서도 권장하는 바다. 역할 분담, 확장성 확보, 장애 격리는 대규모 시스템에서 필수적이다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

## DSpark speculative decoding, 실제 적용하면서 느낀 점

- **속도 향상은 확실하다.** 우리 서비스 기준으로 평균 1.7~2배 추론 속도가 빨라졌다.
- **작은 모델 품질과 후보 토큰 수 튜닝이 필수다.** 무작정 경량화하면 오히려 성능이 떨어진다.
- **비동기 통신과 캐싱 전략에 신경 써야 한다.** 네트워크 지연이 전체 성능을 좌우한다.
- **마이크로서비스 간 부하 균형과 장애 격리 설계가 중요하다.** 대규모 트래픽에서 안정성을 보장하려면 필수.

솔직히 처음엔 speculative decoding이 복잡해 보여서 도입을 망설였는데, 한 번 제대로 구축하니 LLM 추론 비용과 지연 시간 모두 크게 줄여줘서 만족스럽다. 특히 실시간 챗봇, 추천 시스템 등 응답 속도가 중요한 서비스에 강력히 추천한다.
