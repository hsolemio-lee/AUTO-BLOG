# 갑작스런 GCP 계정 정지, 우리도 당할 수 있다면?

2026년 5월 19일, 어느 날 갑자기 우리 팀의 GCP 계정이 정지됐다면? 상상만 해도 아찔하다. 실제로 그날, 한 스타트업은 예상치 못한 비용 급증과 함께 GCP 계정이 정지되는 사고를 겪었다. 이 사고는 단순히 비용 초과 문제를 넘어, 서비스 가용성에 큰 타격을 주었다. 

이 경험을 통해 내가 느낀 건, 클라우드 비용과 자원 관리는 단순히 청구서 숫자만 보는 게 아니라, 아키텍처와 운영 전략 전반에 걸쳐 고민해야 한다는 점이다.

---

## GCP 계정 정지, 비용 초과 감지가 왜 이렇게 중요한가

이번 사고의 핵심 원인은 비용 초과였다. GCP가 5월 중순부터 자동화된 비용 초과 알림 기능을 강화했음에도 불구하고, 알림을 받았을 때 이미 비용이 급증한 상태였고, 결국 계정 정지까지 이어졌다[https://cloud.google.com/release-notes].

이걸 보면, 단순히 비용 한도 설정만 해놓고 끝내면 안 된다는 걸 알 수 있다. 실시간으로 비용과 리소스 사용량을 모니터링하고, 이상 징후를 빠르게 감지하는 시스템이 필수다. 

Google Cloud Architecture Framework도 이 점을 강조한다. 자원 사용량과 비용을 모니터링하고, 이상 징후 탐지를 통해 사고를 미리 방지하는 전략을 권장한다[https://cloud.google.com/architecture/framework].

우리 팀도 이 사고 이후에 비용 모니터링을 강화하기 위해 다음과 같은 설정을 도입했다.

```yaml
# 예시: GCP 예산 알림 설정 (Terraform)
resource "google_billing_budget" "budget" {
  billing_account = "000000-000000-000000"
  display_name    = "Prod Budget"
  amount {
    specified_amount {
      currency_code = "USD"
      units         = 500
    }
  }

  threshold_rules {
    threshold_percent = 0.5
    spend_basis       = "CURRENT_SPEND"
  }

  threshold_rules {
    threshold_percent = 0.9
    spend_basis       = "CURRENT_SPEND"
  }

  notifications_rule {
    pubsub_topic = "projects/my-project/topics/budget-alerts"
  }
}
```

이렇게 50%, 90% 도달 시점에 알림을 받도록 설정해 두면, 비용 급증 초기 단계에서 대응할 수 있다.

## CI/CD 파이프라인에서 비용과 리소스 사용량을 모니터링하는 법

비용 관리는 단순히 클라우드 콘솔에서 보는 것만으로 끝나지 않는다. GitHub Actions 같은 CI/CD 파이프라인에 비용 모니터링을 통합하면, 배포 전후 리소스 사용 변화를 감지할 수 있다[https://docs.github.com/en/actions].

예를 들어, 아래는 GitHub Actions에서 GCP 비용 추정 API를 호출해 배포 전후 비용 변화를 체크하는 간단한 워크플로우 예시다.

```yaml
name: Cost Monitor

on:
  push:
    branches:
      - main

jobs:
  check-cost:
    runs-on: ubuntu-latest
    steps:
      - name: Set up gcloud
        uses: google-github-actions/setup-gcloud@v1
        with:
          project_id: ${{ secrets.GCP_PROJECT_ID }}
          service_account_key: ${{ secrets.GCP_SA_KEY }}

      - name: Estimate current cost
        id: cost
        run: |
          COST=$(gcloud beta billing budgets describe my-budget --format='value(amount.specified_amount.units)')
          echo "Current cost: $COST"
          echo "::set-output name=cost::$COST"

      - name: Fail if cost too high
        if: steps.cost.outputs.cost > 500
        run: |
          echo "Cost exceeded threshold, aborting deployment"
          exit 1
```

이렇게 하면 배포 과정에서 비용 임계치를 넘으면 자동으로 중단시켜, 무분별한 비용 증가를 막을 수 있다. 물론, 비용 API 호출이 항상 실시간은 아니므로 보완책이 필요하다.

## 권한 분리와 비용 관리, 사고 예방의 또 다른 열쇠

계정 정지 사고를 겪어보면, 권한 관리가 얼마나 중요한지 새삼 깨닫게 된다. GitHub Engineering Blog에서도 대규모 서비스에서 권한 분리와 비용 관리가 사고 예방에 핵심이라고 강조한다[https://github.blog/category/engineering/].

예를 들어, 모든 개발자가 프로젝트 결제 권한을 갖고 있으면, 실수로 비용 폭증을 초래할 위험이 크다. 그래서 다음과 같이 역할별 권한을 세분화하는 게 좋다.

- 비용 관리 전담 팀에게만 Billing Admin 권한 부여
- 개발자는 서비스 운영에 필요한 최소 권한만 부여
- 자동화 스크립트는 별도 서비스 계정으로 운영하며, 권한 최소화

또한, 비용 관련 알림을 받는 채널도 분리해, 담당자가 즉시 인지할 수 있도록 한다. 이런 권한 분리와 알림 체계는 사고 발생 시 빠른 대응으로 이어진다.

## 신뢰성과 비용 균형을 맞추는 아키텍처 설계는 어떻게 해야 할까?

Cloudflare의 "How We Built It" 시리즈에서는 대규모 클라우드 인프라 운영에서 비용과 신뢰성을 균형 있게 관리하는 사례를 소개한다[https://blog.cloudflare.com/tag/how-we-built-it/].

우리도 이 사고를 계기로, 무조건 자원을 많이 쓰는 게 아니라, 비용 대비 신뢰성을 극대화하는 방향으로 아키텍처를 재설계했다. 예를 들어:

- 오토스케일링 정책을 더 세밀하게 조정해, 트래픽 급증 시에도 과도한 리소스 낭비를 막음
- 캐싱 레이어를 도입해, 백엔드 부하와 비용을 동시에 줄임
- 장애 발생 시 빠른 롤백과 복구가 가능하도록 배포 전략 개선

이런 변화는 초기에는 복잡도가 늘어나고 설정 난이도가 올라가지만, 장기적으로 비용과 서비스 안정성 두 마리 토끼를 잡는 데 큰 도움이 됐다.

---

## 사고 이후 가장 먼저 챙긴 것들

1. **비용 알림 임계치 재설정**: 기존 90%만 알림 받던 걸 50%, 70%, 90%로 세분화
2. **실시간 모니터링 대시보드 구축**: Grafana와 Stackdriver를 연동해 비용과 리소스 사용량을 한눈에 볼 수 있게
3. **권한 재검토 및 분리**: Billing Admin 권한을 최소 인원으로 제한하고, 서비스 계정 권한도 점검
4. **배포 파이프라인에 비용 체크 추가**: 위 GitHub Actions 예시처럼 배포 전 비용 임계치 확인

## 마치며: 비용 초과 사고, 미리 막는 게 답이다

이번 GCP 계정 정지 사고는 우리에게 클라우드 비용과 신뢰성이 얼마나 밀접한 문제인지 다시 한 번 일깨워줬다. 특히 비용 모니터링과 권한 관리, 그리고 아키텍처 설계가 함께 맞물려야 사고를 예방할 수 있다는 점이 인상적이었다.

처음엔 이게 별거 아닌 것 같지만, 실제로 겪어보면 비용 초과로 인한 계정 정지는 서비스 전체를 멈추게 하는 치명적인 문제다. 그래서 다음과 같은 점을 꼭 기억하자.

- 비용 알림은 50%부터 세분화해서 받자
- CI/CD 파이프라인에 비용 체크를 넣어 배포 전후 변화를 감지하자
- 권한 관리를 철저히 해서 비용 폭주 위험을 줄이자
- 아키텍처 설계 시 비용과 신뢰성의 균형을 맞추자

이 글을 읽는 동료 엔지니어들도 우리 팀의 경험을 참고해, 자신의 클라우드 환경에서 비용과 신뢰성을 함께 챙기는 전략을 고민해보길 바란다.
