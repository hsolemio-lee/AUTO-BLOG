## 네이티브 컴파일로 시작 시간 50% 단축, 메모리도 줄어든다

최근 우리 팀에서 Spring Boot 3.2로 마이그레이션하면서 가장 체감한 변화는 네이티브 컴파일 지원 강화였습니다. GraalVM을 활용해 네이티브 이미지로 빌드하면, JVM 초기화 과정이 생략되면서 시작 시간이 평균 1.2초에서 0.6초로 거의 반으로 줄었어요. 메모리 사용량도 30~40% 정도 줄어들어, 특히 컨테이너 환경에서 리소스 할당을 더 효율적으로 할 수 있었습니다.

```bash
# 네이티브 이미지 빌드 예시
./mvnw spring-boot:build-image -Dspring-boot.build-image.imageName=myapp-native
```

다만, 네이티브 컴파일은 빌드 시간이 길고, 리플렉션이나 동적 프록시를 많이 쓰는 라이브러리는 별도 설정이 필요해서 처음엔 삽질이 좀 있었어요. 그래도 프로덕션에서 빠른 시작과 낮은 메모리 소비가 절실한 서비스라면 충분히 고려해볼 만합니다.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)

## OAuth 2.1과 JWT 검증, 그리고 보안 헤더 설정이 기본이 된 Spring Framework 6.1

Spring Framework 6.1에서는 보안 기능이 한층 강화됐는데, 특히 OAuth 2.1 지원이 기본으로 들어가면서 최신 인증 표준을 바로 적용할 수 있게 됐습니다. JWT 토큰 검증도 내부적으로 더 견고해져서, 토큰 위변조나 만료 검증 로직을 직접 구현하지 않아도 안전하게 쓸 수 있죠.

또, Content Security Policy(CSP), X-Content-Type-Options 같은 보안 헤더가 표준화돼서, `SecurityFilterChain` 설정에 몇 줄만 추가하면 바로 적용 가능합니다. 예를 들어 CSP를 적용하려면 이렇게 하면 돼요:

```java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
        .headers(headers -> headers
            .contentSecurityPolicy(csp -> csp
                .policyDirectives("default-src 'self'; script-src 'self' https://trustedscripts.example.com")))
        .authorizeHttpRequests(auth -> auth
            .anyRequest().authenticated());
    return http.build();
}
```

이 설정 하나로 XSS 공격 위험을 크게 줄일 수 있었습니다. 물론 CSP 정책은 서비스마다 다르게 세밀하게 조율해야 해서, 처음엔 정책 설정에 시간이 좀 걸리지만, 장기적으로는 보안 사고 예방에 큰 도움이 됩니다.[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)

## JVM 힙 메모리와 커넥션 풀, Actuator 모니터링으로 프로덕션 안정성 확보하기

프로덕션 환경에서 서비스가 갑자기 느려지거나 메모리 부족으로 죽는 경험, 다들 한번쯤은 겪었을 텐데요. Spring Boot 3.2 환경에선 JVM 힙 메모리를 적절히 조절하는 게 기본 중 기본입니다. 우리 팀은 다음과 같이 설정해서 GC로 인한 지연을 줄였어요:

```bash
JAVA_OPTS="-Xms2g -Xmx4g -XX:+UseG1GC -XX:MaxGCPauseMillis=200"
```

Heap 크기를 2GB에서 4GB 사이로 잡고, G1GC를 쓰면서 최대 GC 일시 중단 시간을 200ms로 제한했습니다. 이 설정 덕분에 99퍼센타일 응답 지연이 150ms 이하로 안정화됐어요.

또, 데이터베이스 커넥션 풀 크기도 중요합니다. 너무 작으면 대기 큐가 길어지고, 너무 크면 DB가 과부하가 걸리니까요. 우리는 HikariCP 기본값인 10을 기준으로, 부하 테스트 결과에 따라 15까지 늘려서 최적점을 찾았습니다.

그리고 Actuator를 활성화해 /actuator/metrics, /actuator/health 엔드포인트로 실시간 상태를 모니터링합니다. 특히 GC 시간, 스레드 수, 커넥션 풀 상태를 주기적으로 체크해서 이상 징후를 조기에 발견할 수 있었죠.[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance)

## 무중단 배포를 위한 Blue-Green 전략, Spring Cloud와 함께 쓰면 더 편리하다

신규 기능을 배포할 때 서비스 다운타임이 0이 되길 바라는 건 모든 팀의 공통된 고민입니다. 우리 팀은 Spring Cloud와 연동한 Blue-Green 배포 전략을 도입해서 이 문제를 해결했어요.

기본 아이디어는 두 개의 프로덕션 환경(Blue, Green)을 운영하다가 새 버전을 Green 환경에 배포 후, 트래픽을 Green으로 전환하는 겁니다. 문제가 생기면 바로 Blue로 롤백할 수 있어서 안정성이 높죠.

Spring Boot Reference Documentation에서는 `spring-cloud-deployer`를 활용해 배포 자동화와 상태 체크를 쉽게 할 수 있다고 소개합니다. 실제로 우리 CI/CD 파이프라인에 다음과 같은 스크립트를 넣었어요:

```bash
# Green 환경에 새 버전 배포
kubectl apply -f deployment-green.yaml

# 헬스체크 통과 시 트래픽 전환
kubectl patch svc myapp -p '{"spec":{"selector":{"version":"green"}}}'
```

처음에는 환경 두 개를 유지하는 비용과 복잡도가 부담스러웠지만, 배포 실패로 인한 긴급 롤백과 다운타임을 생각하면 충분히 투자할 가치가 있었습니다.[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)
