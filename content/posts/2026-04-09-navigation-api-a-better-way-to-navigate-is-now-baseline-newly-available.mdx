# Navigation API로 SPA 페이지 전환이 이렇게 달라질 줄이야

"왜 페이지 전환할 때마다 전체 페이지가 다시 로드되는 느낌일까?" 이 질문, 프론트엔드 하다 보면 한 번쯤은 꼭 하게 되죠. 특히 SPA(단일 페이지 애플리케이션)에서는 사용자 경험을 최적화하려고 노력하는데, 기존 네비게이션 방식은 여전히 한계가 있었습니다. 그런데 최근에 Baseline으로 정식 도입된 최신 Navigation API 덕분에 이 고민이 크게 줄었어요.

제가 직접 프로젝트에 적용해보면서 느낀 점과, 성능 최적화 팁, 그리고 어떻게 하면 확장성 있는 UX 컴포넌트를 만들 수 있는지 공유해볼게요.

## Navigation API가 SPA에서 페이지 리로드 없이 상태를 유지하는 비결

기존 SPA에서는 `history.pushState`나 `react-router` 같은 라우팅 라이브러리를 써서 URL을 바꾸고, 필요한 데이터를 별도로 fetch하는 식으로 페이지 전환을 구현했죠. 근데 이 과정에서 미묘한 깜빡임이나 상태 초기화 문제가 종종 발생했어요.

최신 Navigation API는 브라우저 네비게이션 이벤트를 직접 캡처하고 제어할 수 있게 해줍니다. 덕분에 전체 페이지를 다시 로드하지 않고도 URL 변경과 상태 업데이트를 자연스럽게 연결할 수 있어요. 예를 들어, 사용자가 뒤로 가기 버튼을 눌러도 컴포넌트 상태를 그대로 유지하면서 화면만 바뀌는 경험이 가능해졌죠.

이게 실제로 얼마나 부드러운지, GitHub Engineering Blog에서도 SPA에서의 부드러운 페이지 전환과 상태 유지가 Navigation API 덕분에 가능해졌다고 소개하고 있습니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

## Navigation API로 네트워크 비용 줄이고 빠른 전환 구현하기

Cloudflare가 Navigation API를 활용해 서버-클라이언트 간 데이터 전송을 최소화한 사례가 인상적이었는데요. 네트워크 대역폭을 아끼면서도 페이지 전환 속도를 크게 끌어올렸다고 해요. 특히 모바일 환경이나 불안정한 네트워크에서도 체감 성능이 좋아졌다는 점이 눈에 띕니다.

이들은 Navigation API로 필요한 데이터만 부분적으로 요청하고, 나머지는 클라이언트 상태로 처리하는 전략을 썼는데, 실제로 페이지 전환 시 네트워크 요청 횟수를 40% 이상 줄였다고 합니다. 덕분에 사용자 이탈률도 감소했죠[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

## 상태 관리 라이브러리와 Navigation API를 함께 쓰면 더 좋은 이유

Navigation API가 네비게이션 이벤트를 제어할 수 있다고 해도, 상태 관리가 제대로 안 되면 UX가 엉망이 될 수밖에 없어요. 그래서 React, Vue 같은 프레임워크에서 쓰는 상태 관리 라이브러리(예: Redux, MobX, Vuex)와 잘 통합하는 게 핵심입니다.

Martin Fowler도 복잡한 사용자 인터랙션과 비동기 데이터 흐름을 효율적으로 처리하려면 Navigation API와 상태 관리가 함께 가야 한다고 강조했어요[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

예를 들어, 사용자가 페이지를 이동하다가 중간에 데이터를 입력하고 뒤로 가기를 눌렀을 때, 입력한 내용이 날아가지 않고 그대로 남아 있어야 하죠. 이런 UX를 보장하려면 상태를 Navigation API 이벤트와 연동해 관리하는 게 필수입니다.

## 모듈화된 컴포넌트 설계로 대규모 웹앱 유지보수성 높이기

Navigation API 도입은 단순히 성능 개선뿐 아니라 아키텍처 측면에서도 큰 변화를 가져왔어요. InfoQ에서는 Navigation API가 프론트엔드 아키텍처를 모듈화하고 재사용 가능한 컴포넌트 설계를 촉진한다고 설명합니다[InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/).

실제로 저희 팀도 Navigation API를 쓰면서 네비게이션 관련 로직을 별도 훅(hook)과 컴포넌트로 분리했는데, 덕분에 신규 기능 추가나 버그 수정이 훨씬 수월해졌습니다. 코드 중복도 줄고, 테스트 커버리지도 자연스럽게 올라갔죠.

## 실제로 Navigation API를 이렇게 써봤습니다

아래는 React 환경에서 Navigation API를 활용해 페이지 전환 이벤트를 감지하고, 상태를 업데이트하는 간단한 예시입니다.

```jsx
import React, { useEffect, useState } from 'react';

function useNavigation() {
  const [currentUrl, setCurrentUrl] = useState(window.location.href);

  useEffect(() => {
    function onNavigate(event) {
      // event.destination.url로 이동할 URL 확인 가능
      setCurrentUrl(event.destination.url);
      // 필요한 추가 작업 (예: 데이터 fetch) 수행
    }

    // Navigation API 이벤트 리스너 등록
    window.navigation.addEventListener('navigate', onNavigate);

    return () => {
      window.navigation.removeEventListener('navigate', onNavigate);
    };
  }, []);

  return currentUrl;
}

export default function App() {
  const currentUrl = useNavigation();

  return (
    <div>
      <h1>현재 URL: {currentUrl}</h1>
      {/* URL에 따라 렌더링할 컴포넌트 분기 */}
    </div>
  );
}
```

이 코드는 `window.navigation` 객체의 `navigate` 이벤트를 구독해서 URL 변경을 감지합니다. 실제 프로젝트에서는 이 이벤트에서 받은 URL을 바탕으로 상태 관리 라이브러리와 연동해 데이터 로딩, 캐싱, UI 업데이트를 처리하면 됩니다.

단, Navigation API는 아직 모든 브라우저에서 완벽히 지원하지 않으니, 폴리필이나 기능 감지를 꼭 해줘야 해요. 그리고 이벤트 핸들러 내부에서 무거운 작업을 하면 오히려 성능 저하가 발생할 수 있으니, 비동기 작업과 스로틀링(throttling)을 적절히 조합하는 게 좋습니다.

# 마치며: Navigation API, 언제부터 본격 도입할까?

처음엔 이게 별거 아닌 것 같지만, 실제로 써보면 SPA의 페이지 전환 UX가 확 달라집니다. 특히 대규모 웹앱에서 네트워크 비용 절감과 상태 유지가 중요한 경우라면 Navigation API 도입을 적극 고려해볼 만해요.

다만 아직 신기술이라 브라우저 호환성, 기존 상태 관리 시스템과의 통합 난이도, 그리고 개발자 학습 곡선 같은 현실적인 고민도 있습니다. 그래서 저는 단계적으로 도입하면서 모듈화된 컴포넌트와 상태 관리 전략을 함께 다듬어가는 방식을 추천합니다.

이 글에서 소개한 사례와 코드를 참고해서, 여러분 팀 프로젝트에도 Navigation API를 슬쩍 적용해보세요. 분명히 "왜 이제야 알았지?" 하는 순간이 올 겁니다.
