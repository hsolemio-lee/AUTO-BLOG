## API 연결 보안, 왜 아직도 어려울까?

"우리 서비스 간 API 연결, 진짜 안전한 걸까?" 이런 고민, 한 번쯤은 해봤을 겁니다. 마이크로서비스가 대세가 되면서 서비스 간 호출이 폭발적으로 늘었고, 자연스레 보안 위협도 급증했죠. 단순히 방화벽이나 IP 화이트리스트만으로는 한계가 명확합니다. 마틴 파울러가 강조한 것처럼, 서비스 간 경계를 명확히 하고 분리하는 게 핵심인데요, 이걸 코드로 관리하지 않으면 운영도, 감사도, 문제 해결도 너무 힘들어집니다[Martin Fowler - Microservices](https://martinfowler.com/articles/microservices.html).

이번 글에서는 제가 최근에 직접 적용해본 아키텍처 코드(Architecture as Code) 기반의 안전한 API 연결 플랫폼 구축 경험을 공유하려고 합니다. 실무에서 마주친 선택지와 결정 포인트, 그리고 실제 코드 예시까지 담았으니, 커피 한잔 하면서 편하게 읽어주세요.

---

## 경계 설정과 서비스 분리, 그게 왜 중요한가

마이크로서비스 설계에서 가장 기본이 되는 원칙 중 하나가 ‘경계 설정(Boundary)’입니다. 서비스 간 API 호출이 많아질수록, 경계가 허술하면 공격 표면이 넓어져서 취약점이 생기기 쉽죠. 파울러는 "서비스 간 명확한 경계와 분리로 보안 위협을 최소화할 수 있다"고 말합니다. 실제로 우리 팀도 내부 네트워크라고 무조건 믿는 구조에서 Zero Trust 모델로 전환하면서 보안 사고가 크게 줄었어요.

이 경계는 단순히 네트워크 레벨 방화벽만 의미하는 게 아닙니다. API 게이트웨이, 인증 및 권한 부여, 네트워크 정책까지 아우르는 넓은 개념이죠. 경계가 명확해야만 각 서비스가 자신의 역할과 권한만 갖고 움직일 수 있어서, 보안 사고가 발생해도 피해를 국한할 수 있습니다.

## 아키텍처 코드로 API 보안 정책 자동화하기

"보안 정책을 코드로 쓴다"는 말, 처음엔 좀 낯설 수 있는데요. 마이크로소프트 클라우드 디자인 패턴 문서에서는 API 게이트웨이 패턴과 보안 토큰 패턴을 활용해 인증과 권한 부여를 코드로 정의하고, 이를 자동화하는 방식을 제안합니다[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/).

예를 들어, API 게이트웨이 설정을 YAML이나 JSON 같은 선언형 코드로 관리하면, 정책 변경 시 수동 작업 없이 CI/CD 파이프라인을 통해 배포할 수 있습니다. 이렇게 하면 정책 누락이나 설정 실수로 인한 보안 구멍을 크게 줄일 수 있죠.

우리 팀에서는 AWS API Gateway + Lambda Authorizer를 사용하면서, 정책을 AWS CloudFormation 템플릿으로 관리했는데, 정책 변경이 있을 때마다 수동으로 콘솔에 들어가서 설정하던 과거와 비교하면 생산성이 3배 이상 올라갔습니다. 게다가 코드 리뷰를 통해 보안 정책을 검증할 수 있으니 안정성도 높아졌고요.

## OAuth 2.0과 JWT를 CI/CD에 녹여낸 실제 사례

GitHub 엔지니어링 블로그에서 소개한 사례를 보면, 인프라를 코드로 관리하면서 OAuth 2.0과 JWT 기반 인증 체계를 API 연결에 적용하고, 이를 CI/CD 파이프라인에 통합해 운영 자동화를 실현했습니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

우리도 OAuth 2.0을 도입할 때 비슷한 고민을 했는데요. 인증 서버 설정부터 클라이언트 등록, 토큰 발급 정책, 그리고 JWT 서명 키 관리까지 모두 코드로 관리했습니다. 특히 JWT 서명 키를 AWS Secrets Manager에 저장하고, 배포 시점에 자동으로 갱신 및 배포하도록 CI/CD 파이프라인을 구성했는데, 이 과정에서 다음과 같은 점들이 인상적이었어요:

- **키 교체 주기**: 30일마다 자동 갱신 설정
- **비밀 관리**: 암호화된 상태로만 저장, 접근은 최소 권한 원칙 준수
- **배포 자동화**: 키 변경 시 API Gateway와 인증 서버 설정 자동 업데이트

이렇게 하니 키 교체 누락으로 인한 보안 사고 걱정이 확 줄었고, 운영 부담도 크게 줄었습니다.

```yaml
# 예시: GitHub Actions 워크플로우 일부
name: Deploy Auth Infrastructure

on:
  push:
    branches:
      - main

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Deploy CloudFormation Stack
        run: |
          aws cloudformation deploy \
            --template-file auth-infra.yaml \
            --stack-name auth-stack \
            --capabilities CAPABILITY_NAMED_IAM
      - name: Rotate JWT Signing Key
        run: |
          aws secretsmanager rotate-secret --secret-id jwt-signing-key
```

## Zero Trust와 선언적 네트워크 정책, 왜 꼭 필요한가

Cloudflare 블로그의 'How We Built It' 시리즈를 보면, Zero Trust 모델과 아키텍처 코드로 네트워크 정책을 선언적으로 관리하는 방법을 자세히 설명합니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/). 이게 왜 중요한지 실무 경험을 통해 말씀드리면,

- 내부 네트워크라서 무조건 믿는 구조는 이제 옛날 방식
- 모든 API 연결은 항상 인증, 권한 확인 후 허용
- 네트워크 정책도 코드로 관리해서 변경 내역 추적 가능

우리도 Zero Trust 도입 후, 네트워크 ACL과 API 권한 정책을 Terraform 코드로 관리합니다. 예를 들어, 특정 API 호출은 오직 특정 서비스 계정 토큰만 허용하도록 정책을 선언적으로 작성하고, 변경 시 PR 리뷰를 거쳐 배포합니다.

이 과정에서 "정책이 너무 복잡해지면 관리가 어려워진다"는 단점도 있었는데, 정책을 모듈화하고 공통 패턴을 추출하는 방식으로 극복했습니다. 처음엔 별거 아닌 것 같지만, 실제로 운영하면서 정책 누락으로 인한 보안 사고가 0건이라는 게 얼마나 큰 성과인지 체감했습니다.

## 아키텍처 코드로 보안 정책 관리할 때 꼭 기억할 점

마틴 파울러는 아키텍처를 코드로 관리할 때 보안 정책을 명확히 분리하고, 테스트 자동화와 코드 리뷰를 통해 보안 취약점 발생 가능성을 줄이는 실천법을 제시합니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/). 저도 이 부분에서 크게 공감하는데요,

- **보안 정책은 별도 모듈로 분리**: 서비스 코드와 보안 정책 코드를 분리해 관리해야 변경 시 영향 범위를 줄일 수 있습니다.
- **자동화된 테스트**: 정책 변경 시 시뮬레이션 테스트를 자동화해 의도치 않은 허용이나 차단을 미리 잡아냅니다.
- **코드 리뷰 프로세스**: 보안 정책 코드도 반드시 리뷰를 거쳐야 합니다. 보안에 대한 이해도가 높은 팀원이 참여하는 게 중요하죠.

## 마무리하며: 실무에서 직접 써본 나만의 팁

1. **정책은 최대한 선언적으로, 변경은 코드로**
   - 수동 설정은 결국 실수와 누락의 원인입니다.

2. **인증 토큰 관리 자동화는 필수**
   - JWT 서명 키 교체 주기를 30일 이하로 잡고, 자동화하세요.

3. **Zero Trust는 선택이 아닌 필수**
   - "우리 내부라서 괜찮아"는 이제 옛말입니다.

4. **CI/CD 파이프라인에 보안 정책 배포 통합**
   - 정책 변경마다 자동 배포, 실패 시 롤백 체계를 갖추세요.

5. **코드 리뷰와 테스트를 통한 안전망 구축**
   - 보안 정책 코드도 소프트웨어 코드만큼 꼼꼼히 다뤄야 합니다.

이 글이 여러분이 안전한 API 연결 플랫폼을 설계하고 운영하는 데 조금이나마 도움이 되었으면 합니다. 현장에서 겪은 시행착오와 배운 점을 공유하는 게 결국 우리 모두의 성장으로 이어지니까요. 궁금한 점이나 경험 공유는 언제든 환영입니다!
