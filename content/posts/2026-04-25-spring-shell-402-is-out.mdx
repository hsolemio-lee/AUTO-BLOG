### CLI 자동화, 왜 아직도 직접 만들고 계신가요?

"우리 서비스에 딱 맞는 커맨드라인 도구가 필요해." 이런 생각으로 직접 CLI를 만들기 시작한 경험, 다들 한 번쯤 있을 겁니다. 그런데 막상 만들다 보면 깔끔한 구조 잡기 어렵고, 유지보수도 힘들고, 사용자 편의 기능 넣자니 시간은 부족하고…

최근에 나온 Spring Shell 4.0.2를 써보면서 이런 고민이 많이 줄었어요. 특히 Spring Boot와 찰떡궁합이라서 기존 프로젝트에 자연스럽게 녹여 넣기 좋더라고요. 오늘은 제가 직접 써보고 생산 환경에서 튜닝해본 경험을 공유하려고 합니다.

## Spring Shell 4.0.2가 Spring Boot와 궁합이 좋은 이유

Spring Shell 4.0.2는 Spring Boot와 긴밀히 통합되어 있어서, Spring Boot 프로젝트 내에서 CLI를 빠르게 만들 수 있어요. 기존에 Spring Boot가 제공하는 IoC 컨테이너와 AOP 기능을 그대로 활용할 수 있어서, 커맨드 구현이 훨씬 깔끔해집니다.

예를 들어, 의존성 주입을 통해 서비스 로직을 쉽게 주입할 수 있고, AOP를 활용해 공통 로깅이나 트랜잭션 처리를 커맨드에 자연스럽게 적용할 수 있죠. 덕분에 CLI 코드가 비즈니스 로직과 섞이지 않고 유지보수가 쉬워집니다.

```java
@ShellComponent
public class UserCommands {

    private final UserService userService;

    public UserCommands(UserService userService) {
        this.userService = userService;
    }

    @ShellMethod("Create a new user")
    public String createUser(String username, String email) {
        userService.createUser(username, email);
        return "User created: " + username;
    }
}
```

이렇게 간단하게 작성하면, `createUser`라는 CLI 명령어가 만들어지고, 내부적으로는 `UserService`가 호출됩니다. Spring Boot 프로젝트에선 이게 기본 패턴이라, 새 기능 추가가 정말 빠릅니다.

더 자세한 내용은 [Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)에서 확인할 수 있습니다.

## 비동기 커맨드 실행과 캐싱으로 응답 속도 확 끌어올리기

실제 운영 환경에서 CLI가 느리면 개발자 생산성에 치명적입니다. Spring Shell 4.0.2는 이런 문제를 해결하기 위해 비동기 커맨드 실행과 캐싱 기능을 지원합니다.

비동기 실행은 특히 시간이 오래 걸리는 작업에 유용해요. 예를 들어, 대용량 데이터 처리나 외부 API 호출 같은 경우, CLI 응답을 기다리느라 멈춰 있으면 답답하잖아요? 비동기로 실행하면 명령어가 호출되자마자 바로 프롬프트로 돌아오고, 결과는 나중에 알림이나 로그로 확인할 수 있게 됩니다.

캐싱은 동일 커맨드에 대해 반복 호출 시 결과를 빠르게 반환해줍니다. 예를 들어, `getUserStats` 같은 명령어를 자주 쓰는 경우, 30초 정도 캐시를 걸어놓으면 서버 부하도 줄고 사용자 경험도 좋아집니다.

```java
@ShellComponent
public class StatsCommands {

    private final StatsService statsService;
    private final CacheManager cacheManager;

    public StatsCommands(StatsService statsService, CacheManager cacheManager) {
        this.statsService = statsService;
        this.cacheManager = cacheManager;
    }

    @ShellMethod("Get user stats asynchronously")
    public void getUserStatsAsync(String userId) {
        CompletableFuture.runAsync(() -> {
            String stats = statsService.getStats(userId);
            System.out.println("Stats for " + userId + ": " + stats);
        });
    }

    @ShellMethod("Get cached user stats")
    @Cacheable(value = "userStatsCache", key = "#userId", cacheManager = "cacheManager")
    public String getUserStats(String userId) {
        return statsService.getStats(userId);
    }
}
```

위 예시처럼 `CompletableFuture.runAsync()`를 쓰면 비동기 처리가 되고, `@Cacheable` 애노테이션으로 캐시를 적용할 수 있습니다. 캐시 TTL(Time To Live)은 스프링 설정에서 조절 가능하니, 실제 서비스 상황에 맞춰 튜닝하세요.

Baeldung의 [Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance) 글도 참고하면 좋습니다.

## Spring Framework 핵심 기술 덕분에 확장성과 유지보수가 쉬워졌다

Spring Shell 4.0.2는 Spring Framework의 IoC와 AOP를 적극 활용해서 확장성과 유지보수성을 높였습니다. 커맨드를 모듈화해서 관리하기도 편하고, 공통 로직을 AOP로 분리해 중복 코드를 줄일 수 있어요.

예를 들어, 모든 커맨드 실행 전후에 실행 시간을 로깅하고 싶다면, AOP로 한 번만 구현하면 됩니다.

```java
@Aspect
@Component
public class CommandLoggingAspect {

    @Around("execution(* com.example.shell.*.*(..))")
    public Object logExecutionTime(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.currentTimeMillis();
        Object proceed = joinPoint.proceed();
        long executionTime = System.currentTimeMillis() - start;

        System.out.println(joinPoint.getSignature() + " executed in " + executionTime + "ms");
        return proceed;
    }
}
```

이렇게 하면 모든 쉘 커맨드 실행 시 로그가 찍히고, 나중에 성능 이슈가 생겨도 원인 파악이 쉬워집니다. 이런 점이 Spring Framework의 핵심 기술과 호환되면서 얻는 큰 장점입니다.

관련 내용은 [Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)에서 더 자세히 볼 수 있습니다.

## 실무에서 Spring Shell 4.0.2를 도입하며 겪은 의외의 고비들

처음에 Spring Shell을 도입할 때 가장 당황스러웠던 건, 복잡한 입력 파라미터 처리와 커맨드 간 의존성 관리였어요. 기본적으로는 단순한 문자열 인자만 지원하는데, 복잡한 객체를 넘기려면 직접 컨버터를 만들어야 하더라고요.

예를 들어, JSON 형태로 옵션을 넘기고 싶을 때는 아래처럼 커스텀 컨버터를 등록해야 했습니다.

```java
@Component
public class JsonToUserConverter implements Converter<String, User> {

    private final ObjectMapper objectMapper = new ObjectMapper();

    @Override
    public User convert(String source) {
        try {
            return objectMapper.readValue(source, User.class);
        } catch (JsonProcessingException e) {
            throw new IllegalArgumentException("Invalid user JSON", e);
        }
    }
}
```

그리고 이걸 Spring Shell 설정에 등록해줘야 하죠. 이런 작업이 생각보다 번거로웠는데, 그래도 한 번 해놓으면 이후 커맨드 확장에 큰 도움이 됩니다.

또 한 가지는, CLI 자동 완성 기능이 기본 제공되긴 하지만, 복잡한 커맨드 트리에서는 직접 커스터마이징이 필요하다는 점입니다. 자동 완성 기능을 잘 활용하면 개발자 경험이 확 달라지니, 꼭 시간을 들여 세팅하시길 권합니다.

## 나만의 Spring Shell 4.0.2 활용법, 이렇게 해봤다

저는 사내 배포 자동화용 CLI를 Spring Shell 4.0.2로 만들었는데, 다음과 같은 설정으로 생산성을 크게 끌어올렸습니다.

- **비동기 커맨드 실행**: 배포 로그 조회, 빌드 상태 체크 같은 시간이 오래 걸리는 작업은 비동기로 처리해 CLI가 멈추지 않도록 함
- **결과 캐싱**: 자주 조회하는 서버 상태, 배포 이력 등은 1분 단위로 캐시해서 API 호출 횟수 줄임
- **AOP 로깅**: 모든 커맨드 실행 시간을 로그로 남겨 성능 병목 파악에 활용
- **커스텀 파라미터 변환기**: JSON, 날짜 포맷 등 복잡한 입력값도 편하게 받을 수 있도록 변환기 등록

이 덕분에 배포 담당자들이 CLI로 작업하는 시간이 30% 이상 줄었고, 자동화 스크립트 작성도 훨씬 쉬워졌어요. 처음엔 설정과 커스텀 코드가 부담스러웠지만, 한 번 제대로 세팅해두면 유지보수가 정말 편합니다.

### 마무리하며

Spring Shell 4.0.2는 단순히 CLI를 만드는 도구를 넘어서, Spring 생태계와의 긴밀한 통합 덕분에 백엔드 개발자가 생산성을 극대화할 수 있는 강력한 무기입니다. 특히 비동기 처리와 캐싱 기능은 실무에서 체감 성능을 크게 올려주니 꼭 써보시길 추천합니다.

단점이라면 복잡한 입력값 처리나 자동 완성 커스터마이징이 초반에 손이 많이 간다는 점인데, 이 부분만 넘기면 장기적으로 큰 이득이 됩니다.

다음 프로젝트에서 CLI 자동화가 필요하다면, Spring Shell 4.0.2 한 번 시험 삼아 써보세요. 생각보다 금방 익숙해지고, 동료들도 좋아할 겁니다.
