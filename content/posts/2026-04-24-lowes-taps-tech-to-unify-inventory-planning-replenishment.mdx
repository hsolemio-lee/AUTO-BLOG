## 재고 부족과 과잉, 이젠 시스템으로 잡아내자

"왜 이번 달 재고가 이렇게 남아돌지?" Lowe’s에서 일하는 동료가 한탄하던 게 기억난다. 재고 부족은 고객 이탈로, 과잉 재고는 비용 증가로 직결되니 이 문제는 단순히 숫자 맞추기가 아니다. Lowe’s는 Microsoft Dynamics 365 Supply Chain Management(이하 D365 SCM)를 도입해 재고 계획과 조달, 주문 이행을 하나로 묶는 통합 SCM 시스템을 구축했다. 덕분에 AI 기반 수요 예측과 자동화된 재고 보충으로 재고 최적화를 실현했다.

이 글에선 Lowe’s 사례를 통해 대규모 유통사의 SCM 시스템을 어떻게 설계하고, 백엔드 엔지니어로서 어떤 점을 고려해야 하는지 이야기해보려 한다.

---

## 통합 SCM 시스템, 왜 꼭 필요한가?

재고 계획, 조달, 주문 이행을 각각 따로 관리하면 데이터가 분산되고, 실시간 가시성이 떨어진다. 이러면 수요 변화에 민첩하게 대응하기 어렵고, 불필요한 재고가 쌓이거나 부족이 발생하기 쉽다.

Lowe’s는 D365 SCM을 활용해 이 세 가지 기능을 통합했다. AI 기반 수요 예측이 자동으로 재고 보충 시점을 계산하고, 조달 프로세스와 주문 이행까지 연결되니 운영 효율성이 크게 향상됐다. 실제로 재고 부족률이 15% 감소했고, 재고 회전율은 10% 이상 개선됐다고 한다[Microsoft Learn - Dynamics 365 Supply Chain Management](https://learn.microsoft.com/en-us/dynamics365/supply-chain/).

이처럼 통합 SCM 시스템은 단순한 IT 프로젝트가 아니라, 비즈니스 성과에 직접적인 영향을 준다.

---

## 마이크로서비스로 나누면 유지보수와 확장성이 확실히 좋아진다

통합된 SCM 시스템이라 해도 한 덩어리로 만들면 금방 복잡해진다. 그래서 Lowe’s뿐 아니라 SAP, Oracle 같은 대형 솔루션들도 재고 계획, 조달, 주문 이행을 각각 독립된 서비스로 분리하는 마이크로서비스 아키텍처를 채택한다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

이 구조는 각 서비스가 독립적으로 배포되고 확장될 수 있어, 예를 들어 주문 이행에 갑자기 트래픽이 몰려도 재고 계획 서비스에 영향 없이 대응 가능하다. 또 팀별로 책임 영역이 명확해져 개발 생산성도 올라간다.

하지만 서비스 간 통신이 많아지고, 데이터 일관성 유지가 까다로워지는 단점도 있다. Lowe’s는 이벤트 기반 메시징 시스템을 도입해 이 문제를 해결했다. 예를 들어 재고 계획 서비스가 보충 요청 이벤트를 발행하면, 조달 서비스가 이를 구독해 자동으로 발주를 진행하는 식이다.

---

## 실제로 이런 식으로 이벤트를 설계해봤다

아래는 재고 보충 요청을 이벤트로 발행하는 간단한 예시다. Java와 Spring Boot를 사용했고, Kafka를 메시지 브로커로 가정했다.

```java
// 재고 보충 요청 이벤트 데이터 클래스
public class ReplenishmentRequestEvent {
    private String productId;
    private int quantity;
    private Instant requestTime;

    // 생성자, getter, setter
}

// 재고 계획 서비스 내 이벤트 발행 메서드
@Service
public class InventoryPlanningService {

    private final KafkaTemplate<String, ReplenishmentRequestEvent> kafkaTemplate;

    public InventoryPlanningService(KafkaTemplate<String, ReplenishmentRequestEvent> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    public void requestReplenishment(String productId, int quantity) {
        ReplenishmentRequestEvent event = new ReplenishmentRequestEvent(productId, quantity, Instant.now());
        kafkaTemplate.send("replenishment-requests", productId, event);
        System.out.println("재고 보충 요청 이벤트 발행: " + event);
    }
}
```

이벤트 발행 후 조달 서비스는 `replenishment-requests` 토픽을 구독해 자동으로 발주를 처리한다. 이런 비동기 이벤트 기반 설계는 시스템 간 결합도를 낮추고, 장애 시에도 메시지를 재처리할 수 있어 안정성을 높인다.

## AI 기반 수요 예측, 실제 도입 시 주의할 점

Lowe’s 사례에서 가장 핵심적인 부분 중 하나가 AI 기반 수요 예측이다. D365 SCM은 과거 판매 데이터, 계절성, 프로모션 영향 등을 학습해 다음 달 수요를 예측한다. 이를 바탕으로 재고 보충 시점과 수량을 자동으로 조정한다.

하지만 처음 도입할 땐 예측 정확도가 낮아 혼란이 발생할 수 있다. Lowe’s도 초기에는 예측 결과를 그대로 믿기보다, 재고 담당자와 협업해 점진적으로 모델을 튜닝했다. 예측 결과를 대시보드로 시각화해 이상치를 쉽게 발견할 수 있게 한 것도 큰 도움이 됐다.

또, AI 예측 결과를 무조건 따르기보다 비즈니스 상황(예: 갑작스러운 공급 문제)을 반영할 수 있는 수동 조정 기능도 반드시 필요하다.

## Lowe’s 사례에서 얻은 나만의 교훈

1. **통합 SCM 시스템은 단순한 기능 통합이 아니라, 비즈니스 프로세스와 데이터 흐름을 재설계하는 작업이다.**
2. **마이크로서비스와 이벤트 기반 아키텍처는 확장성과 유연성을 위한 필수 조건이다.**
3. **AI 기반 수요 예측은 도입 초기부터 끝까지 지속적인 모니터링과 튜닝이 필요하다.**
4. **자동화와 수동 조정의 균형을 맞추는 UX 설계도 중요하다.**

개인적으로는 이벤트 설계가 가장 까다로웠는데, 메시지 스키마를 잘 설계하지 않으면 서비스 간 오해가 생기고 장애로 이어질 수 있다는 점을 뼈저리게 느꼈다.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
