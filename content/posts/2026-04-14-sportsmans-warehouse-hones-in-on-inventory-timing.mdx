## 재고 타이밍이 이렇게 중요할 줄 몰랐다, Sportsman’s Warehouse 이야기

"왜 우리 재고가 매번 너무 일찍 쌓이거나, 반대로 너무 늦게 들어오는 걸까?" 이런 질문은 누구나 한 번쯤 해봤을 겁니다. 특히 스포츠 용품처럼 시즌성 상품이 많은 곳에서는 재고 타이밍이 매출과 직결되죠. Sportsman’s Warehouse가 겪은 비슷한 고민과 이를 해결하기 위해 Microsoft Dynamics 365 Supply Chain Management를 도입한 이야기를 들으면, 공급망 관리가 단순히 ‘재고 쌓아두기’가 아니라 얼마나 정교한 엔지니어링 문제인지 감이 잡힙니다.


## 실시간 공급망 업데이트가 엔지니어링 의사결정을 어떻게 바꾸는가

Sportsman’s Warehouse는 기존에 재고 데이터가 계획, 조달, 이행 시스템 간에 지연되어 반영되면서, 실제 판매 상황과 재고 상태가 어긋나는 일이 많았다고 합니다. 이게 무슨 문제냐면, 예를 들어 재고가 충분한데도 시스템에는 부족하다고 찍혀서 불필요한 긴급 주문이 들어가거나, 반대로 재고가 부족한데도 시스템이 재고가 있다고 판단해 판매 기회를 놓치는 식이었죠.

이 문제를 해결하기 위해 도입한 게 바로 Microsoft Dynamics 365 Supply Chain Management입니다. 이 플랫폼은 계획, 조달, 재고, 이행 시스템 전반에 걸쳐 공급망 업데이트를 실시간으로 반영해줍니다. 덕분에 엔지니어링 팀은 데이터가 최신 상태라는 전제하에 정확한 의사결정을 할 수 있게 되었죠.

실제로 Sportsman’s Warehouse는 이 시스템을 통해 재고 타이밍을 정밀하게 조율할 수 있었고, 시즌별 수요에 맞춘 재고 배분이 훨씬 유연해졌습니다. 예를 들어, 사냥 시즌이 시작되기 직전 재고를 미리 과도하게 쌓지 않고, 수요 변화에 따라 조달 일정을 조절하는 식이죠. 


## Oracle과 SAP도 비슷한 길을 걷고 있다

Microsoft만 이런 기능을 제공하는 건 아닙니다. Oracle의 SCM 및 제조 클라우드 솔루션도 재고와 조달 데이터를 실시간으로 통합해 공급망 전반의 계획과 실행 단계를 자동화합니다. Oracle Docs에 따르면, 이 자동화는 재고 타이밍 개선에 직접적인 영향을 미친다고 하네요[Oracle Docs - SCM and Manufacturing](https://docs.oracle.com/en/cloud/saas/supply-chain-and-manufacturing/).

SAP 역시 비슷한 접근법을 취하는데, SAP Supply Chain Management 플랫폼은 재고 관리와 조달 프로세스에서 발생하는 데이터를 통합 분석해 엔지니어링 팀에게 필요한 인사이트를 제공합니다. 이렇게 하면 재고 타이밍을 개선하고 운영 효율성을 높일 수 있죠[ SAP Help Portal - Supply Chain Management](https://help.sap.com/docs/SAP_SUPPLY_CHAIN_MANAGEMENT).

이 세 가지 솔루션 모두 실시간 데이터 통합과 분석을 통해 공급망 전체를 하나의 유기체처럼 움직이게 하는 데 초점을 맞추고 있습니다.


## 실제로 재고 타이밍을 코드로 어떻게 다룰까? - 간단한 TypeScript 예시

실시간 재고 데이터를 받아서 재고 상태를 판단하고, 재고 보충 시점을 결정하는 로직은 의외로 간단할 수 있습니다. 아래는 TypeScript로 작성한 예시 코드입니다. 

```typescript
interface InventoryUpdate {
  productId: string;
  quantityOnHand: number;
  lastUpdated: Date;
}

interface ReplenishmentDecision {
  productId: string;
  orderQuantity: number;
  reason: string;
}

// 재고 임계값 설정
const REORDER_THRESHOLD = 20;
const MAX_STOCK_LEVEL = 100;

function decideReplenishment(update: InventoryUpdate): ReplenishmentDecision | null {
  if (update.quantityOnHand < REORDER_THRESHOLD) {
    const orderQty = MAX_STOCK_LEVEL - update.quantityOnHand;
    return {
      productId: update.productId,
      orderQuantity: orderQty,
      reason: `재고 부족: 현재 재고 ${update.quantityOnHand}개, ${REORDER_THRESHOLD}개 미만`
    };
  }
  return null;
}

// 실시간 재고 업데이트가 들어올 때마다 호출
function onInventoryUpdate(update: InventoryUpdate) {
  const decision = decideReplenishment(update);
  if (decision) {
    console.log(`주문 필요: ${decision.productId}, 수량: ${decision.orderQuantity}`);
    // 실제 주문 API 호출 로직 등 추가 가능
  } else {
    console.log(`${update.productId} 재고 충분`);
  }
}

// 예시
onInventoryUpdate({ productId: 'bow-123', quantityOnHand: 15, lastUpdated: new Date() });
```

이 코드는 재고가 임계값 이하로 떨어졌을 때, 최대 재고 수준까지 보충 주문을 결정하는 아주 기본적인 로직입니다. 실제 환경에서는 여기에 수요 예측, 공급 리드 타임, 시즌성 변수 등을 더해 복잡도를 높이죠. 

처음엔 이런 단순 로직도 실제 운영에 적용하면 재고 과잉이나 부족 문제를 크게 줄일 수 있다는 걸 느끼게 됩니다.


## 실시간 공급망 데이터 통합의 숨겨진 어려움

이렇게 멋진 시스템도 도입 초기에는 여러 난관이 있습니다. Sportsman’s Warehouse 사례에서도 보듯, 실시간 데이터 통합은 단순히 API 연결만으로 끝나지 않습니다. 

- **데이터 품질 문제**: 여러 시스템에서 들어오는 데이터가 형식이나 타이밍이 다르니, 정합성 확보가 쉽지 않습니다.
- **레거시 시스템과의 호환성**: 기존 ERP나 WMS(창고관리시스템)와 완벽히 연동하려면 커스텀 미들웨어 개발이 필요할 때가 많죠.
- **운영 중단 최소화**: 실시간 반영을 위해 시스템을 바꾸면서도, 기존 운영에 지장 없어야 하니 배포 전략이 까다롭습니다.

이런 점들 때문에 엔지니어링 팀은 단순히 코딩만 하는 게 아니라, 공급망 운영팀과 긴밀하게 협업하면서 점진적으로 시스템을 개선해 나가야 합니다.


## Sportsman’s Warehouse가 얻은 가장 큰 교훈

가장 인상 깊었던 점은 "데이터가 실시간으로 반영되니, 의사결정 속도가 확실히 빨라졌다"는 겁니다. 예전에는 재고 데이터가 하루 이틀 늦게 들어와서 대응이 늦었는데, 이제는 변화가 생기면 바로바로 대응할 수 있으니 불필요한 비용도 줄고, 고객 만족도도 올라갔죠.

또한, 엔지니어링 팀이 공급망 전반을 이해하게 되면서, 단순히 시스템 개발자에서 비즈니스 파트너로 역할이 확장된 점도 주목할 만합니다. 기술과 비즈니스가 만나는 지점에서 진짜 가치가 나온다는 걸 보여준 사례입니다.
