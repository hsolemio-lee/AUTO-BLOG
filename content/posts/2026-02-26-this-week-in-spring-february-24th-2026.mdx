## 부트스트랩 속도가 느려서 야근한 경험, 이젠 좀 다를까?

"아니, 왜 서버 시작하는 데 30초나 걸려?" 이런 말 들어본 적 있죠? 저도 최근에 Spring Boot 3.2로 마이그레이션하면서 부트스트랩 속도 개선이 얼마나 중요한지 다시 깨달았어요. 이번 버전에서는 JVM 튜닝 옵션과 메모리 관리가 한층 좋아졌는데, 특히 GC 설정을 자동화해서 개발자가 일일이 신경 쓰지 않아도 된다는 점이 반가웠습니다.

실제로 Spring Boot 3.2에서는 기본적으로 G1 GC를 권장하고, `-XX:MaxGCPauseMillis=200` 같은 옵션을 자동으로 적용해요. 이게 무슨 뜻이냐면, GC가 너무 오래 걸려서 애플리케이션 응답이 느려지는 걸 방지해준다는 거죠. 그리고 부트스트랩 단계에서 빈 초기화 최적화도 눈에 띄게 개선됐습니다. 덕분에 저희 서비스는 평균 시작 시간이 25% 정도 빨라졌어요.

```java
// application.properties 예시
spring.main.lazy-initialization=true
spring.aot.enabled=true

# JVM 옵션은 빌드 스크립트나 배포 스크립트에 추가
JAVA_OPTS="-XX:+UseG1GC -XX:MaxGCPauseMillis=200"
```

이 설정들은 실제 프로덕션 환경에서 GC가 과도하게 발생하지 않게 도와주고, 부트스트랩 시점에 불필요한 빈 초기화를 지연시켜서 시작 시간을 단축합니다.

## OAuth 2.1과 CSRF 기본 활성화, 보안 설정이 이렇게 쉬워졌다고?

Spring Framework 6.1로 넘어오면서 보안 관련 변화가 꽤 큽니다. OAuth 2.1 지원이 공식적으로 들어가면서, 인증 플로우를 직접 구현하지 않아도 최신 표준을 바로 쓸 수 있게 됐어요. 그리고 CSRF 보호가 기본으로 켜져서 "보안 설정 안 해서 걱정"이라는 말이 옛말이 됐죠.

이전에는 CSRF 토큰을 직접 생성하고 검증 로직을 넣어야 했는데, 이제는 `@EnableWebSecurity`만 붙이면 기본적으로 CSRF 방어가 활성화됩니다. 물론 필요에 따라 특정 엔드포인트에서 CSRF를 비활성화할 수도 있고요.

```java
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf
                .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
            )
            .oauth2Login(withDefaults());
        return http.build();
    }
}
```

이 코드는 기본 CSRF 토큰을 쿠키에 저장하면서 OAuth 2.1 로그인도 설정한 예시입니다. 실무에서 이 정도만 해도 기본 공격 벡터는 충분히 막을 수 있습니다.

## 응답시간 30% 줄인 Baeldung의 비동기 처리와 커넥션 풀 최적화

성능 튜닝은 말처럼 쉽지 않죠. Baeldung에서 권장하는 방법 중 하나가 비동기 처리와 커넥션 풀 최적화입니다. 저도 이걸 적용해보니, 특히 DB 커넥션 풀 사이즈 조절만으로도 서버 리소스 사용률이 눈에 띄게 줄었어요.

예를 들어, HikariCP를 쓰는 경우 기본 커넥션 풀 크기는 CPU 코어 수 * 2 + 1인데, 이걸 서비스 특성에 맞게 조정하는 게 중요합니다. 너무 작으면 요청이 대기하고, 너무 크면 DB가 버티기 힘들거든요.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20  # CPU 코어 8개 서버라면 20 정도가 적당
      minimum-idle: 10
      idle-timeout: 30000
      max-lifetime: 1800000
```

그리고 `@Async` 어노테이션을 활용해 CPU 바운드 작업이나 외부 API 호출을 비동기로 처리하면, 메인 쓰레드가 블로킹되지 않아 응답 속도가 확실히 개선됩니다.

```java
@Service
public class NotificationService {

    @Async
    public void sendEmailAsync(EmailRequest request) {
        // 이메일 전송 로직
    }
}
```

이렇게 하면 사용자 요청 처리와 이메일 발송이 분리돼서 사용자 입장에선 체감 속도가 빨라집니다.

## 대규모 서비스는 카나리 릴리즈와 모니터링 자동화 없인 못 버틴다

GitHub 엔지니어링 블로그에서 소개한 대규모 서비스 롤아웃 사례는 우리에게도 큰 시사점을 줍니다. 신규 기능을 한꺼번에 모든 사용자에게 노출하는 대신, 카나리 릴리즈로 일부 사용자에게만 점진적으로 배포하고, 모니터링 자동화로 이상 징후를 실시간 감지하는 전략이죠.

이 과정에서 실패가 감지되면 자동으로 롤백하는 시스템을 갖추면, 장애 확산을 막고 빠르게 정상화할 수 있습니다. 저희 팀도 최근 이 방식을 도입했는데, 실제로 신규 API 배포 후 5% 사용자 대상으로 먼저 노출하고, 문제가 없으면 점차 100%로 확대하는 식으로 운영 중입니다.

```yaml
# 예: Spinnaker 카나리 설정 일부
canary:
  baseline:
    cluster: stable-v1
  canary:
    cluster: canary-v2
  metrics:
    - name: error_rate
      threshold: 0.01
      direction: increase
```

이런 설정을 통해 에러율이 1% 이상 증가하면 자동으로 배포를 중단하거나 롤백할 수 있습니다.

## 엣지 컴퓨팅과 CDN 연동으로 DDoS 걱정 덜기

Cloudflare 블로그 사례를 보면, Spring 백엔드 앞단에 CDN과 엣지 컴퓨팅을 두어 트래픽 분산과 DDoS 공격 방어를 강화하는 방법을 소개합니다. 실제로 저희도 Nginx와 Cloudflare를 연동해 놓으니, 갑작스러운 트래픽 폭증에도 서버 다운 없이 버티는 경험을 했어요.

이런 구조는 인증이나 간단한 캐시 처리 같은 작업을 엣지에서 처리하게 해서 백엔드 부하를 줄여줍니다. 다만, 엣지에서 처리할 수 없는 복잡한 비즈니스 로직은 여전히 백엔드에서 처리해야 하니 설계 시 역할 분담이 중요합니다.

### 마무리하며

이번 주 스프링 업데이트를 살펴보면서 느낀 건, "성능과 보안은 한 번에 끝나는 게 아니라 계속 다듬어가는 과정"이라는 점입니다. Spring Boot 3.2와 Spring Framework 6.1은 그런 점에서 개발자가 부담을 덜고 더 안정적인 서비스를 만들 수 있도록 도와주는 좋은 도구들이죠.

특히 JVM GC 튜닝 자동화, OAuth 2.1과 CSRF 기본 활성화, 비동기 처리와 커넥션 풀 조절, 그리고 카나리 릴리즈와 모니터링 자동화까지, 실무에서 바로 적용 가능한 팁들이 많으니 꼭 한 번씩 점검해보시길 권합니다.

여러분도 이번 기회에 부트스트랩 속도 느려서 야근하는 악몽에서 벗어나고, 보안 걱정 줄이고, 성능 튜닝으로 쾌적한 서버 환경 만드시길 바랍니다!
