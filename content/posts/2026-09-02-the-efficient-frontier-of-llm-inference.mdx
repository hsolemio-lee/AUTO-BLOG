### "이거 너무 느린데, 비용은 왜 이렇게 많이 나와?"

최근 우리 팀에서 LLM 기반 챗봇 서비스를 운영하면서 가장 많이 들었던 질문입니다. 모델 응답 속도는 느리고, API 호출 비용은 쌓여가는데, 어디서부터 손을 대야 할지 막막했죠. LLM 추론은 단순히 API 호출만 하는 게 아니라, 비용과 성능 사이에 미묘한 균형이 존재합니다. 오늘은 그 균형점, 즉 ‘효율적 프런티어(efficient frontier)’를 어떻게 찾고 관리할 수 있는지 경험을 공유해 보려 합니다.

## OpenAI API 모델 선택과 비용-성능 트레이드오프

OpenAI API를 처음 접할 때 가장 당황스러웠던 게 모델마다 가격과 응답 속도가 다르다는 점이었어요. 예를 들어 GPT-4는 GPT-3.5 대비 훨씬 똑똑하지만, 토큰당 가격이 4~5배 정도 높습니다. 그리고 응답 지연(latency)도 더 길죠. 

우리 팀은 아래와 같은 기준으로 모델을 선택했습니다:

- **실시간성이 중요한 기능**: GPT-3.5 turbo 사용, 평균 응답 시간 500ms 내외
- **복잡한 질의 처리**: GPT-4 사용, 평균 응답 시간 1.5~2초

이런 식으로 API 호출 단위 비용과 응답 지연 시간 간에 명확한 트레이드오프를 두고, 요구사항에 맞춰 모델을 분리해 썼죠. 실제로 OpenAI API 문서에도 "다양한 모델과 파라미터로 비용과 성능을 조절할 수 있다"고 명시되어 있습니다[OpenAI API Documentation](https://platform.openai.com/docs/overview).

## 프롬프트 엔지니어링으로 토큰 비용과 응답 속도 줄이기

처음엔 프롬프트 길이가 길면 좋은 답변이 나올 거라 생각했는데, 이건 오히려 비용과 지연 시간을 늘리는 지름길이더군요. Anthropic 가이드에 따르면, 불필요한 토큰을 줄이고 명확한 지시문을 작성하는 게 핵심이라고 합니다[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

예를 들어, 아래 두 프롬프트를 비교해 보죠:

```plaintext
// 비효율적 프롬프트
"안녕하세요, 저는 오늘 날씨에 대해 궁금한 게 있는데, 혹시 지금 서울 날씨가 어떤지 알려줄 수 있을까요?"

// 효율적 프롬프트
"서울 현재 날씨 알려줘"
```

두 번째가 훨씬 짧고 명확해서 토큰 수도 줄고, 모델이 핵심 정보를 빠르게 파악해 응답 속도도 개선됩니다. 우리 서비스에선 이런 식으로 프롬프트를 계속 다듬으면서 비용이 20% 이상 절감됐고, 응답 속도도 평균 300ms 빨라졌어요.

## GitHub Actions로 LLM 추론 워크플로우 자동화하기

LLM 모델 업데이트나 프롬프트 변경, 테스트, 배포를 수동으로 하다 보면 실수도 잦고 시간이 많이 낭비됩니다. 우리 팀은 GitHub Actions를 활용해 자동화 파이프라인을 구축했는데요, 덕분에 운영 효율이 눈에 띄게 좋아졌습니다.

간단한 예시를 보여드리면:

```yaml
name: LLM Inference CI/CD

on:
  push:
    branches: [ main ]

jobs:
  test-and-deploy:
    runs-on: ubuntu-latest

    steps:
    - uses: actions/checkout@v3
    - name: Run inference tests
      run: |
        python tests/test_inference.py
    - name: Deploy if tests pass
      if: success()
      run: |
        ./deploy.sh
```

이렇게 하면 코드나 프롬프트가 바뀔 때마다 자동으로 테스트를 돌리고, 문제가 없으면 바로 배포까지 이어집니다. Martin Fowler가 강조한 지속적 통합 원칙을 LLM 서비스에 적용하는 셈이죠[Martin Fowler - Continuous Integration](https://martinfowler.com/articles/continuousIntegration.html).

## 클라우드 인프라 최적화: 캐싱과 엣지 컴퓨팅 활용하기

Cloudflare가 LLM 추론을 클라우드 인프라에 최적화한 사례를 보면, 캐싱과 엣지 컴퓨팅을 적극 활용해서 지연 시간과 비용을 동시에 줄였다고 합니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

우리도 비슷한 접근을 했는데요, 예를 들어 자주 묻는 질문(FAQ) 답변은 캐시에 저장해 두고, 같은 요청이 오면 바로 반환하도록 했습니다. 이러면 API 호출 횟수를 크게 줄일 수 있죠. 또한, 사용자와 가까운 리전에 엣지 서버를 두어 네트워크 왕복 시간을 최소화했습니다.

이런 최적화는 특히 사용자가 많은 글로벌 서비스에서 효과가 크고, 비용 절감도 15~30% 수준으로 체감됐습니다.

## 직접 써본 LLM 추론 최적화 코드 예시

아래는 Python으로 OpenAI API 호출 시 프롬프트를 최소화하고, 실패 시 재시도 로직을 넣은 간단한 예제입니다.

```python
import openai
import time

openai.api_key = "YOUR_API_KEY"

PROMPT_TEMPLATE = "서울 현재 날씨 알려줘"

MAX_RETRIES = 3


def call_llm(prompt):
    for attempt in range(MAX_RETRIES):
        try:
            response = openai.ChatCompletion.create(
                model="gpt-3.5-turbo",
                messages=[{"role": "user", "content": prompt}],
                max_tokens=50,
                temperature=0.5
            )
            return response.choices[0].message.content.strip()
        except Exception as e:
            print(f"Attempt {attempt + 1} failed: {e}")
            time.sleep(2 ** attempt)  # 지수 백오프
    raise RuntimeError("LLM 호출 실패")


if __name__ == "__main__":
    answer = call_llm(PROMPT_TEMPLATE)
    print(f"LLM 응답: {answer}")
```

- `max_tokens`를 50으로 제한해 불필요한 토큰 생성을 줄였습니다.
- `temperature`를 0.5로 낮춰 응답의 일관성을 높였습니다.
- 실패 시 지수 백오프 재시도를 넣어 안정성을 확보했습니다.

이런 작은 조정들이 모여 비용과 성능 최적화에 큰 도움이 됩니다.

## 마치며: 비용과 성능 사이에서 계속 조율하는 일

LLM 추론은 한 번 세팅하고 끝나는 게 아니라, 서비스 상황에 맞게 끊임없이 조율해야 하는 작업입니다. 모델 선택, 프롬프트 다듬기, 자동화, 인프라 최적화까지 여러 축에서 균형을 찾아야 하죠. 

처음엔 이게 별거 아닌 것 같지만, 실제로 겪어보면 작은 최적화 하나가 비용을 수십, 수백만 원 단위로 바꾸기도 합니다. 그리고 무엇보다 사용자 경험을 해치지 않으면서 비용을 줄이는 게 핵심입니다.

여러분도 우리 팀처럼 직접 실험하고, 데이터를 보고, 자동화하며 최적의 효율적 프런티어를 찾아보시길 바랍니다.
