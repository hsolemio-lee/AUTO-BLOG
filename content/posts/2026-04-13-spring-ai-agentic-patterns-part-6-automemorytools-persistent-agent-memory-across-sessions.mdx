## 세션이 바뀌어도 AI가 내 말을 기억한다면?

최근 AI 에이전트를 개발하면서 가장 골치 아팠던 부분 중 하나가 ‘메모리’ 문제였어요. 특히 사용자와 대화가 길어질수록, 혹은 세션이 끊겼다가 다시 시작할 때 이전 대화 맥락을 잃어버리는 상황이 너무 아쉽더라고요. 단순히 '이번 대화에서만 기억해'가 아니라, ‘이전에 어떤 얘기를 나눴는지’ AI가 알아야 더 자연스럽고 똑똑한 응답이 나오니까요.

그래서 이번에는 Spring 백엔드 환경에서 AutoMemoryTools 패턴을 활용해 어떻게 에이전트의 메모리를 세션을 넘어 지속시키는지 실제로 구현해본 경험을 나누려고 합니다.

---

## Spring Boot가 제공하는 세션 간 상태 관리, AI 에이전트에 딱 맞는 이유

Spring Boot는 기본적으로 HTTP 세션 관리 외에도 Redis, JDBC, MongoDB 같은 다양한 저장소와 쉽게 연동할 수 있는 메커니즘을 제공해요. 이걸 이용하면 단순히 세션이 끊겨도 메모리 상태를 DB에 저장해두고 다시 불러올 수 있죠. 

예를 들어, Redis를 세션 저장소로 쓰면 빠른 읽기/쓰기가 가능하고, 분산 환경에서도 상태 관리가 수월해집니다. 이런 점이 AI 에이전트에겐 엄청난 강점인데, 세션 단위가 아니라 사용자 단위로 기억을 저장할 수 있기 때문입니다.

```java
// Redis를 통한 세션 저장 설정 예시
@Configuration
@EnableRedisHttpSession(maxInactiveIntervalInSeconds = 3600) // 1시간 세션 유지
public class RedisSessionConfig {
    @Bean
    public LettuceConnectionFactory connectionFactory() {
        return new LettuceConnectionFactory();
    }
}
```

위처럼 설정하면 Spring 세션이 Redis에 저장되고, 세션이 끊겨도 1시간 내에는 메모리가 유지됩니다. 물론 AI 에이전트의 메모리는 세션 ID뿐 아니라 사용자 ID를 키로 해서 더 명확히 관리할 수 있어요.

이런 Spring Boot의 강력한 상태 관리 기능 덕분에 AutoMemoryTools 같은 패턴을 구현할 때 저장소 선택과 상태 복원 로직에 집중할 수 있었습니다.

[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)에서 자세한 설정법을 참고할 수 있어요.

## AutoMemoryTools, Spring의 핵심 기술과 어떻게 만났나

AutoMemoryTools는 에이전트가 이전 대화 내용을 자동으로 기억하고, 필요할 때 꺼내 쓰는 도구입니다. 이걸 Spring Framework의 의존성 주입(DI)과 상태 관리 기술과 결합하면 어떻게 될까요?

Spring의 DI 덕분에 메모리 저장소(예: Redis, DB)와 AI 에이전트 서비스가 느슨하게 결합됩니다. 즉, 메모리 저장 로직을 바꾸고 싶을 때 에이전트 코드는 거의 손대지 않아도 된다는 뜻이죠. 이게 얼마나 편한지 직접 써보면 압니다.

```java
@Service
public class AgentMemoryService {

    private final MemoryRepository memoryRepository;

    public AgentMemoryService(MemoryRepository memoryRepository) {
        this.memoryRepository = memoryRepository;
    }

    public void saveMemory(String userId, String memoryData) {
        memoryRepository.save(new MemoryEntity(userId, memoryData));
    }

    public Optional<String> loadMemory(String userId) {
        return memoryRepository.findByUserId(userId).map(MemoryEntity::getMemoryData);
    }
}
```

위처럼 `MemoryRepository` 인터페이스만 바꾸면 Redis, RDB, MongoDB 등 어떤 저장소든 쉽게 바꿀 수 있습니다. 그리고 이 서비스는 AI 에이전트가 대화 도중 기억을 저장하거나 불러올 때 호출됩니다.

이게 바로 Spring Framework의 핵심 기술들이 AutoMemoryTools 구현에 필수적인 이유입니다.

더 자세한 내용은 [Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)에서 확인할 수 있어요.

## OpenAI API와 연동해 세션별 대화 상태를 토큰 단위로 관리하기

OpenAI API는 기본적으로 stateless합니다. 하지만 대화형 AI를 만들려면 이전 메시지들을 컨텍스트로 계속 넘겨줘야 하죠. 이걸 어떻게 하면 효율적으로 관리할 수 있을까요?

Spring 백엔드에서 AutoMemoryTools를 구현할 때, 저는 대화 기록을 토큰 단위로 쪼개서 저장하고 필요할 때만 다시 합치는 방식을 썼어요. 이렇게 하면 저장 공간을 절약하면서도 중요한 정보는 놓치지 않을 수 있습니다.

```java
public class ConversationMemory {
    private List<String> tokenizedMessages = new ArrayList<>();

    public void addMessage(String message) {
        // 간단히 토큰화
        String[] tokens = message.split(" ");
        Collections.addAll(tokenizedMessages, tokens);
        // 토큰 수가 일정 이상이면 오래된 토큰 삭제
        if (tokenizedMessages.size() > 1000) {
            tokenizedMessages = tokenizedMessages.subList(tokenizedMessages.size() - 800, tokenizedMessages.size());
        }
    }

    public String getContext() {
        return String.join(" ", tokenizedMessages);
    }
}
```

이런 식으로 토큰을 관리하면서, OpenAI API 호출 시 `getContext()`로 이전 대화 내용을 넘겨주면 세션 간에도 자연스러운 대화가 가능해집니다.

OpenAI API 문서에서 대화 상태 관리에 대해 더 자세히 다루고 있으니 참고하세요: [OpenAI API Documentation](https://platform.openai.com/docs/overview)

## 메모리 지속성 구현 시 성능과 비용, 그리고 프롬프트 설계까지 고려해야 할 점

이론적으로는 완벽해 보여도, 실제로는 메모리를 너무 많이 저장하거나 너무 자주 불러오면 성능 저하가 심해집니다. 

Baeldung의 Spring Boot 성능 튜닝 가이드에 따르면, 캐싱 전략을 잘 세우고 메모리 접근 빈도를 조절하는 게 필수입니다. 예를 들어, Redis 캐시 TTL(Time To Live)을 10분 정도로 설정해두고, 10분 이내 요청은 캐시에서 바로 처리하도록 하면 성능이 훨씬 안정적이에요.

또한, Anthropic의 프롬프트 엔지니어링 가이드에서 강조하는 것처럼, AI에게 넘기는 프롬프트도 ‘이전 대화 중 핵심만 요약해서 넘기기’가 중요합니다. 너무 긴 대화 기록을 그대로 넘기면 토큰 비용이 늘어나고, AI가 핵심을 파악하기 어려워지거든요.

이런 점들을 고려해서 저는 아래와 같은 전략을 써봤습니다.

- **핵심 정보만 요약해서 저장**: 매 5~10 메시지마다 자동 요약 API를 호출해 메모리 내용을 압축
- **TTL 기반 캐싱**: Redis 캐시 TTL을 600초로 설정해 불필요한 DB 호출 최소화
- **프롬프트 템플릿에 메모리 요약 삽입**: API 호출 시 메모리 요약을 프롬프트 앞부분에 넣어 AI가 참고하도록 유도

이렇게 하니 세션 간 기억 유지가 가능하면서도 응답 속도와 비용 모두 적절히 관리할 수 있었습니다.

## 직접 써본 AutoMemoryTools 간단 구현 예시

아래는 Spring Boot 프로젝트에서 Redis를 활용해 간단한 에이전트 메모리 저장소를 구현한 코드입니다.

```java
@Service
public class AutoMemoryTools {

    private final StringRedisTemplate redisTemplate;
    private static final String MEMORY_KEY_PREFIX = "agent-memory:";

    public AutoMemoryTools(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    public void saveMemory(String userId, String memoryData) {
        String key = MEMORY_KEY_PREFIX + userId;
        redisTemplate.opsForValue().set(key, memoryData, Duration.ofMinutes(30)); // 30분 TTL
    }

    public Optional<String> loadMemory(String userId) {
        String key = MEMORY_KEY_PREFIX + userId;
        String memory = redisTemplate.opsForValue().get(key);
        return Optional.ofNullable(memory);
    }
}
```

이걸 AI 대화 흐름에 이렇게 연결하면 됩니다.

```java
public String generateResponse(String userId, String userMessage) {
    Optional<String> memoryOpt = autoMemoryTools.loadMemory(userId);
    String prompt = memoryOpt.map(mem -> mem + "\n" + userMessage).orElse(userMessage);

    String aiResponse = openAiClient.chatCompletion(prompt);

    // 대화 내용 메모리에 저장
    autoMemoryTools.saveMemory(userId, prompt + "\n" + aiResponse);

    return aiResponse;
}
```

이 간단한 구조만으로도 사용자가 다시 접속했을 때 이전 대화가 어느 정도 기억된 상태로 자연스러운 대화를 이어갈 수 있었어요.

물론 이 방법은 메모리 크기가 커지면 Redis 저장 비용과 읽기 성능에 영향을 줄 수 있으니, 앞서 말한 요약과 TTL 전략을 함께 쓰는 게 좋습니다.

## 마치며: AutoMemoryTools, 꼭 써봐야 하는 이유

처음엔 ‘메모리 지속성’이 별거 아닌 것 같지만, 실제로 AI 에이전트를 실서비스에 적용하다 보면 이게 얼마나 중요한지 뼈저리게 느끼게 됩니다. 사용자 경험은 물론이고, AI가 더 똑똑해지는 핵심 열쇠가 바로 ‘기억’이니까요.

Spring Boot와 같은 강력한 백엔드 프레임워크 덕분에 다양한 저장소와 쉽게 연동할 수 있고, 의존성 주입으로 설계도 깔끔해집니다. OpenAI API와 같은 외부 AI 서비스와도 자연스럽게 연결할 수 있죠.

단, 메모리 저장 전략, 캐싱, 프롬프트 설계 등 여러 측면에서 균형을 맞추는 게 관건입니다. 너무 많이 저장하면 비용과 성능이 문제고, 너무 적게 저장하면 대화가 끊긴 느낌이 들 테니까요.

지금 당장 AutoMemoryTools 패턴을 적용해보고, 여러분 서비스에 맞는 최적의 메모리 전략을 찾아보시길 추천합니다. 분명 AI 에이전트의 품질이 한 단계 올라가는 걸 경험할 수 있을 겁니다.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
