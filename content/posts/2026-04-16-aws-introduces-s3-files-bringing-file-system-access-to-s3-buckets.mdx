## S3 버킷을 파일처럼 다룰 수 있다면 얼마나 편할까?

"우리 서비스가 S3에 저장된 데이터를 마치 로컬 파일 시스템처럼 다룰 수 있으면 얼마나 좋을까?"

이 질문은 꽤 오랫동안 백엔드 엔지니어들 사이에서 회자됐던 고민입니다. 기존에는 S3에 저장된 객체를 다루려면 API 호출을 통해 직접 데이터를 PUT, GET 해야 했고, 파일 시스템처럼 탐색하거나 수정하는 건 불가능했죠. 그런데 AWS가 최근 발표한 S3 Files 기능은 이런 불편을 꽤 깔끔하게 해결해줍니다.

내가 직접 써보면서 느낀 점과, 기존 워크플로우에 어떻게 녹여내면 좋을지, 그리고 성능과 운영 면에서 신경 써야 할 부분까지 이야기해보려고 합니다.

---

## AWS S3 Files, 왜 이제야 나온 거야?

S3는 2006년 출시된 이후로 클라우드 스토리지의 표준이 됐지만, 여전히 객체 스토리지라 파일 시스템과는 근본적으로 다릅니다. 그래서 파일 탐색, 수정, 동시성 제어 같은 작업은 애플리케이션 레벨에서 직접 구현해야 했죠.

S3 Files는 이 간극을 메우는 기능입니다. S3 버킷을 마운트 가능한 파일 시스템으로 노출해서, 리눅스나 윈도우 애플리케이션이 로컬 파일처럼 읽고 쓸 수 있게 해줍니다. 덕분에 기존에 NFS나 EFS 같은 네트워크 파일 시스템을 쓰던 워크로드도 S3로 전환할 수 있는 길이 열렸죠.

하지만 "파일 시스템처럼 보인다"고 해서 모든 게 똑같은 건 아닙니다. 내부적으로는 여전히 객체 스토리지 기반이라 성능 특성과 제약이 존재합니다.

## 실제로 S3 Files를 백엔드에 붙여봤더니

우리 팀은 최근 이미지 처리 파이프라인 일부를 S3 Files 기반으로 전환했습니다. 기존에는 S3 API를 직접 호출해 이미지를 다운로드하고, 변환 후 다시 업로드하는 구조였는데, 이걸 S3 Files로 마운트해서 로컬 파일 경로를 그대로 쓰도록 바꿨죠.

### 코드 예시
```java
// AWS SDK 대신 로컬 파일처럼 경로 지정
Path imagePath = Paths.get("/mnt/s3bucket/images/photo.jpg");

// 기존처럼 파일 읽기
byte[] imageBytes = Files.readAllBytes(imagePath);

// 이미지 변환 로직
byte[] converted = ImageConverter.convert(imageBytes);

// 변환 후 바로 저장
Files.write(imagePath, converted);
```

이렇게 하니까 코드가 훨씬 간결해졌고, 기존 라이브러리도 수정 없이 쓸 수 있었습니다.

### 성능은?

처음엔 "파일 시스템이라서 빠르겠지" 기대했는데, 실제로는 네트워크 지연과 S3 객체 PUT/GET 특성 때문에 로컬 SSD만큼 빠르진 않았습니다. 특히 작은 파일을 자주 읽고 쓰는 작업은 오히려 API 직접 호출보다 느릴 때도 있었어요.

그래서 우리 팀은 다음과 같은 최적화 전략을 썼습니다.

- 자주 쓰는 파일은 로컬 캐시에 저장하고, 주기적으로 S3와 동기화
- 대용량 파일은 스트리밍 방식으로 처리해 메모리 부담 최소화
- 점진적 배포로 일부 워커에만 S3 Files 적용해 운영 리스크 분산

이렇게 하니 전체 파이프라인 처리 시간이 15% 정도 줄었고, 코드 유지보수성도 크게 개선됐습니다.

## S3 Files 도입 시 놓치기 쉬운 운영 포인트

S3 Files는 편리하지만, 운영 관점에서 주의할 점이 몇 가지 있습니다.

### 1. 실패 유형을 초기에 계측하자

파일 시스템 인터페이스라 장애가 나면 "파일이 없어요" 같은 에러가 뜨는데, 실제 원인은 네트워크 문제, 권한 문제, API 제한일 수 있죠. 이런 실패 유형을 초기부터 꼼꼼히 로깅하고 계측해야 장애 대응 속도가 빨라집니다. 

TypeScript 5.x 릴리즈 노트에서도 "초기부터 실패 유형을 계측하는 것이 유지보수성과 장애 대응을 크게 개선한다"고 강조하는데, 이 원칙이 클라우드 스토리지에도 그대로 적용됩니다[TypeScript 5.x Release Notes](https://devblogs.microsoft.com/typescript/announcing-typescript-5-4/).

### 2. 점진적 배포 전략으로 리스크 줄이기

S3 Files는 아직 완전히 검증된 기술이 아니므로, 작은 범위에서 점진적으로 배포하는 게 좋습니다. 우리 팀도 10% 워커부터 시작해 점차 확대했는데, 문제 생기면 즉시 롤백 가능해서 운영 리스크가 확실히 줄더군요.

이 역시 "작은 범위의 점진적 배포 전략은 신규 백엔드 기능의 운영 리스크를 낮춘다"는 좋은 사례입니다[TypeScript Handbook](https://www.typescriptlang.org/docs/handbook/intro.html).

### 3. 권한과 보안 설정 꼼꼼히

파일 시스템처럼 쓰는 만큼, 권한 설정이 헐렁하면 보안 사고로 직결됩니다. IAM 역할과 버킷 정책을 최소 권한 원칙에 맞게 설정하고, 접근 로그도 반드시 활성화하세요.

## S3 Files가 기존 EFS, FSx 대비 나은 점과 아쉬운 점

많은 분들이 궁금해하는 부분일 텐데요, 우리 팀 경험과 AWS 아키텍처 블로그를 참고해 간단히 정리해봅니다.

### 장점
- 비용 효율성: S3 기반이라 저장 비용이 EFS나 FSx보다 저렴합니다.
- 확장성: S3의 무제한 확장성을 그대로 활용할 수 있습니다.
- 관리 편의성: 서버리스 스토리지라 관리 부담이 적습니다.

### 아쉬운 점
- 지연 시간: EFS/FSx 대비 지연 시간이 높아 실시간 처리에는 부적합할 수 있습니다.
- POSIX 완전 지원 아님: 일부 파일 시스템 기능(예: 파일 잠금)이 제한적입니다.
- 네트워크 대역폭 의존: 네트워크 상태에 따라 성능 편차가 큽니다.

이 부분은 서비스 특성에 맞게 선택해야 합니다. 이미지 처리처럼 대용량 파일을 순차적으로 처리하는 작업에는 S3 Files가 딱 맞지만, 초저지연이 필요한 트랜잭션 처리에는 아직 EFS가 낫죠.

## 마치며: AWS S3 Files, 언제 어떻게 써야 할까?

S3 Files는 "클라우드 객체 스토리지를 파일 시스템처럼 쓸 수 있다"는 점에서 백엔드 개발자에게 신선한 경험을 줍니다. 다만, 성능과 운영 특성을 이해하고 적절히 최적화하지 않으면 기대만큼 효과를 못 볼 수 있어요.

우리 팀이 겪은 경험을 정리하면 다음과 같습니다.

- 작은 범위부터 점진적 배포로 안정적으로 도입하라
- 실패 유형을 꼼꼼히 계측해 장애 대응 속도를 높여라
- 자주 쓰는 파일은 로컬 캐시로 보완해 성능을 끌어올려라
- 권한과 보안 설정은 필수, 절대 대충하지 마라

마지막으로, S3 Files는 아직 초기 단계라 앞으로 더 개선될 가능성이 큽니다. 최신 AWS Well-Architected Framework 가이드도 참고하면서, 우리 서비스에 맞는 최적의 클라우드 스토리지 아키텍처를 꾸준히 고민해보시길 권합니다[AW SWell-Architected Framework](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html).
