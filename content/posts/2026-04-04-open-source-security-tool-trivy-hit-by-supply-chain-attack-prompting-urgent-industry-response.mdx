### "내가 쓰는 오픈소스가 해킹당했다고?"

얼마 전, 우리 팀에서 중요한 보안 스캐너로 쓰던 Trivy가 공급망 공격에 노출됐다는 소식을 접했을 때 솔직히 좀 멘붕이었어요. ‘설마 우리도 당할까?’ 하는 불안감이 엄습했죠. 오픈소스 도구는 편리하지만, 이렇게 직접적인 공격 표적이 될 수도 있다는 현실을 뼈저리게 느꼈습니다.

이번 사건은 단순히 Trivy만의 문제라기보다, 오픈소스 생태계 전반과 우리 백엔드 시스템 보안에 던지는 경고라고 생각해요. 그래서 오늘은 이 사건을 짚어보면서, 우리 백엔드 환경에서 공급망 공격 위험을 어떻게 줄일 수 있을지 실전 감각으로 이야기해보려 합니다.

---

## Trivy 공급망 공격, 도대체 어떻게 일어났나?

Trivy는 컨테이너 이미지 취약점 스캐너로, 개발자와 보안팀 사이에서 널리 쓰이는 도구입니다. 그런데 최근 공격자는 Trivy의 배포 경로에 악성 코드를 심어 사용자들이 감염된 버전을 설치하도록 유도했어요. 즉, 공식 릴리즈 프로세스에 침투해 정상 소프트웨어처럼 위장한 거죠.

이런 공급망 공격은 패키지 매니저, CI/CD 파이프라인, 심지어 개발자 개인 계정까지 노릴 수 있어요. Trivy 사례에서 공격자는 배포 자동화 과정에 침투해 악성 코드를 심었습니다. 이 때문에 단순히 도구를 설치하는 것만으로도 백엔드 인프라에 악영향을 끼칠 수 있었죠.

---

## 우리 백엔드에 바로 적용할 수 있는 공급망 공격 방어법

### 1. 서명 검증과 해시 체크는 기본 중 기본

패키지나 바이너리 설치 시 무조건 서명 검증을 하세요. Trivy 같은 도구도 공식 서명 키를 제공하는데, 이를 검증하지 않으면 변조된 파일을 받을 위험이 큽니다. 해시 체크도 병행하면 더 좋고요.

```bash
# 예: Trivy 바이너리 설치 시
curl -sfL https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/install.sh | sh -
# 설치 후 서명 및 해시 검증 절차 (예시)
```

물론 서명 키 관리가 까다롭긴 하지만, 이걸 무시하면 공급망 공격에 무방비로 노출됩니다.

### 2. 의존성 관리에 자동화 도구 적극 활용

의존성 그래프를 자동으로 분석하고, 취약점이나 이상 징후를 조기에 감지하는 도구를 도입하세요. 예를 들어 Dependabot, Renovate 같은 도구가 대표적입니다. 이들은 의존성 업데이트 시점에 보안 이슈를 알려줘 미리 대응할 수 있게 해줍니다.

### 3. CI/CD 파이프라인에 보안 계측 도입하기

배포 전에 모든 아티팩트에 대해 서명 검증, 스캐닝, 무결성 체크를 자동화합니다. 실패 유형을 초기부터 계측하면 유지보수성과 장애 대응 속도가 개선된다는 점도 기억하세요[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

```yaml
# GitHub Actions 예시
jobs:
  security-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Run Trivy Scan
        uses: aquasecurity/trivy-action@v0.0.20
      - name: Verify artifact signature
        run: |
          gpg --verify artifact.sig artifact.tar.gz
```

### 4. 점진적 배포 전략으로 리스크 최소화

새로운 백엔드 기능이나 도구 업데이트는 전체 서비스에 한꺼번에 적용하지 말고, 작은 범위부터 점진적으로 배포하세요. 이렇게 하면 문제가 생겨도 영향 범위가 작아 빠르게 롤백할 수 있습니다. 실제로 작은 범위의 점진적 배포 전략은 신규 백엔드 기능의 운영 리스크를 낮춘다는 연구 결과도 있습니다[OpenAI API Documentation](https://platform.openai.com/docs/overview).

## 공급망 공격 대응, 단순한 보안 절차 그 이상

공급망 공격은 단순히 ‘보안 도구를 잘 쓰자’ 수준을 넘어섭니다. 개발부터 운영까지 전 과정에 걸친 신뢰 체계 구축이 필수예요. 예를 들어, 개발자 개인 계정 보안 강화, 자동화된 감사 로그, 그리고 이상 징후 탐지 시스템까지 포함됩니다.

그리고 이런 공격은 한 번 당하면 파급력이 크기 때문에, 평소에 실패 유형을 꼼꼼히 기록하고 분석하는 습관이 중요합니다. 장애 대응 속도가 빨라지고 유지보수성도 좋아지니까요[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

## Trivy 공급망 공격에서 얻은 교훈과 앞으로의 준비

- **오픈소스 도구도 절대 안심하지 말자.** 공식 릴리즈 경로를 통한 공격 가능성을 항상 염두에 둬야 합니다.
- **서명과 해시 검증은 ‘귀찮아도’ 반드시 하자.** 자동화 도구와 결합하면 부담이 줄어듭니다.
- **CI/CD 파이프라인에 보안 계측을 심어라.** 실패 유형을 조기에 파악하는 게 장애 대응의 핵심입니다.
- **점진적 배포 전략으로 위험을 분산하자.** 한꺼번에 다 바꾸지 말고, 작은 단위로 검증하며 확장하세요.

처음엔 이게 별거 아닌 것 같지만, 실제로 겪어보면 이런 작은 습관들이 큰 사고를 막는 방패가 됩니다. 우리 모두 이번 Trivy 사건을 계기로 공급망 보안에 대한 경각심을 높이고, 더 탄탄한 백엔드 환경을 만들어 가야겠습니다.
