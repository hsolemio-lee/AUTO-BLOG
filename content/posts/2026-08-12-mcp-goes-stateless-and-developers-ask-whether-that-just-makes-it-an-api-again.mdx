## 무상태 MCP, 진짜 API랑 뭐가 다른가?

"MCP가 무상태로 간다고? 그럼 결국 API랑 다를 게 뭐야?"

최근 우리 팀에서 MCP(Model Control Plane)를 무상태로 전환하는 작업을 하면서 이런 질문이 자주 나왔어요. 사실 처음엔 저도 단순히 "서버에 상태 안 두고 요청마다 필요한 모든 정보를 담아 보내는 거구나" 정도로만 이해했는데, 직접 설계하고 운영해보니 생각보다 훨씬 복잡하고 재미있는 문제들이 많더라고요.

무상태 아키텍처는 확장성과 장애 복구에 유리한 패턴입니다. Martin Fowler가 말한 것처럼, 서버가 상태를 갖지 않으면 부하 분산이 쉬워지고, 장애가 나도 다른 인스턴스가 바로 대체할 수 있거든요[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/). 하지만 MCP가 무상태가 되면서 내부적으로는 API 호출 패턴과 거의 동일해졌다는 점이 흥미로웠어요. 

## 왜 MCP 무상태 전환이 API처럼 느껴질까?

MCP가 무상태가 된다는 건, 각 요청이 완전한 컨텍스트를 포함해야 한다는 뜻입니다. 예를 들어, 이전에 서버가 세션이나 상태로 관리하던 모델 버전, 사용자 설정, 세션 히스토리 등을 클라이언트가 직접 요청에 담아 보내야 하죠. 이게 바로 API 호출 방식과 다를 바 없다는 거예요.

InfoQ에서도 이런 점을 지적했는데, 무상태 MCP는 결국 요청마다 필요한 모든 정보를 포함해야 하므로 설계적으로는 API와 매우 유사하다고 하네요[InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/).

우리 팀도 이 부분에서 고민이 많았어요. "그럼 MCP가 API랑 뭐가 다르냐"는 질문에, 사실상 MCP가 API의 한 형태로 진화하는 과정이라고 답할 수밖에 없었죠.

## Cloudflare가 무상태 아키텍처 도입하며 배운 운영 팁

Cloudflare가 무상태 아키텍처를 도입하면서 얻은 운영 경험도 큰 도움이 됐습니다. 그들은 상태 저장 부담을 줄이고, 전 세계 엣지 네트워크에서 빠른 확장과 장애 대응이 가능하도록 설계했거든요. 이 과정에서 상태를 서버에 두지 않고 클라이언트나 외부 스토리지에 위임하는 전략을 썼습니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

우리 MCP 전환에도 이런 패턴을 참고했는데, 특히 글로벌 분산 환경에서 무상태 설계가 얼마나 강력한지 체감했어요. 예를 들어, 장애가 난 서버 인스턴스를 즉시 교체해도 클라이언트가 요청에 모든 상태를 담고 있으니 서비스가 끊기지 않았죠.

## GitHub 엔지니어링 팀이 권장하는 무상태 설계 패턴

GitHub 엔지니어링 블로그에서는 무상태 설계 시 세션 상태나 사용자 컨텍스트를 외부 스토리지(예: Redis, 데이터베이스)로 분리하는 패턴을 추천합니다. 이렇게 하면 백엔드 서버는 요청 처리에만 집중할 수 있고, 마이크로서비스 간 결합도 느슨해져 유지보수가 쉬워지거든요[GitHub Engineering Blog](https://github.blog/category/engineering/).

우리도 세션 상태를 Redis 클러스터에 두고, MCP 서버는 요청에 포함된 토큰이나 세션 ID로 상태를 조회하는 방식을 썼습니다. 이 과정에서 주의할 점은 외부 스토리지 접근이 병목이 되지 않도록 캐싱과 타임아웃 정책을 잘 설계하는 거예요.

## OpenAI API 문서가 말하는 무상태 호출 원칙과 MCP 적용

OpenAI API 문서에서는 stateless API 호출 시 클라이언트가 프롬프트와 세션 상태를 모두 포함해 요청해야 한다고 명확히 설명합니다. 이는 MCP가 무상태로 전환될 때도 동일한 원칙이 적용됩니다[OpenAI API Documentation](https://platform.openai.com/docs/overview).

예를 들어, 대화형 모델을 호출할 때 이전 대화 내역을 모두 요청에 포함시켜야 하는데, 이걸 서버가 따로 기억하지 않는다는 거죠. 우리 MCP도 이런 식으로, 모델 컨트롤 플레인에 필요한 모든 컨텍스트를 클라이언트가 들고 오도록 설계했습니다.

### 실제 코드 예시: 무상태 MCP 요청 핸들러 (Node.js Express)

```javascript
const express = require('express');
const app = express();
app.use(express.json());

// 요청에 모든 상태 포함되어야 함
app.post('/mcp/control', async (req, res) => {
  const { modelVersion, userContext, sessionHistory, command } = req.body;

  if (!modelVersion || !command) {
    return res.status(400).json({ error: '필수 필드 누락' });
  }

  // 외부 스토리지에서 세션 상태 조회 (예: Redis)
  // const sessionData = await redisClient.get(userContext.sessionId);

  // MCP 비즈니스 로직 수행
  const result = await processCommand({ modelVersion, userContext, sessionHistory, command });

  res.json({ result });
});

app.listen(3000, () => console.log('MCP 서버 실행 중...'));
```

위 예시처럼, 요청에 모든 상태를 포함시키고 서버는 단순히 명령을 처리하는 역할만 하도록 설계합니다. 이렇게 하면 서버는 상태 관리 부담에서 자유로워지고, 수평 확장도 쉬워집니다.

## 무상태 MCP가 주는 자유와 그 이면의 고민

무상태 설계는 확장성과 장애 대응에 큰 장점을 주지만, 클라이언트가 모든 상태를 들고 다녀야 하니 요청 크기가 커지고, 네트워크 비용이 늘어나는 단점도 있습니다. Anthropic의 프롬프트 엔지니어링 가이드에서도 각 요청에 필요한 문맥을 모두 포함하는 게 중요하지만, 너무 커지면 성능 저하가 올 수 있다고 경고하죠[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

또한, 상태를 외부 스토리지에 위임하면 그 스토리지의 가용성과 성능이 전체 시스템에 영향을 미칩니다. 우리 팀도 Redis 장애가 발생했을 때 MCP 호출 지연이 심해져서, 장애 대응 매뉴얼과 이중화 구성을 강화한 경험이 있어요.

## 결론: 무상태 MCP는 결국 API, 하지만 그 안에 숨은 운영 노하우가 중요하다

무상태 MCP 전환은 단순히 "서버에 상태를 안 둔다"는 것 이상의 의미가 있습니다. 요청마다 완전한 컨텍스트를 포함하는 API 호출 패턴으로의 진화이며, 이를 뒷받침하는 외부 상태 관리, 캐싱, 네트워크 최적화, 장애 대응 전략이 함께 가야 비로소 성공할 수 있죠.

처음엔 "무상태 MCP가 결국 API라면 뭐가 다르냐"는 의문이 들지만, 직접 설계하고 운영하면서 알게 된 건 무상태 아키텍처가 주는 확장성과 유연성은 개발 속도와 운영 안정성에 큰 도움이 된다는 점입니다.

무상태 MCP로 전환을 고민하는 동료 엔지니어라면, 클라이언트-서버 간 상태 관리 책임 분배, 외부 상태 저장소 설계, 그리고 네트워크 비용 최적화에 집중해보시길 권합니다. 그리고 장애 상황에서 빠르게 복구할 수 있는 운영 전략도 반드시 준비하세요.
