## AWS 인프라가 커질수록 관리가 왜 이렇게 어려워질까?

"아니, AWS 콘솔에서 클릭 몇 번이면 되잖아?" 처음엔 다들 그렇게 생각하죠. 저도 그랬습니다. 그런데 Pinterest처럼 수천 개의 리소스, 수백 개의 서비스가 얽혀 있는 환경에서는 콘솔 클릭 몇 번이 아니라, 그야말로 '관리의 지옥'이 펼쳐집니다. 하나 잘못 건드리면 보안 구멍이 생기고, 컴플라이언스 위반이 발생할 수 있죠.

이런 상황에서 Pinterest는 어떻게 AWS 인프라를 안전하게, 그리고 효율적으로 관리할 수 있었을까요? 답은 중앙 집중식 Terraform 파이프라인에 있었습니다.

## AWS Well-Architected Framework가 강조하는 중앙 집중식 관리

AWS 공식 Well-Architected Framework는 대규모 인프라를 안전하게 운영하려면 인프라 코드를 중앙에서 관리하고, 자동화된 파이프라인으로 배포하는 걸 권장합니다. 이게 왜 중요하냐면, 이렇게 하면 보안 정책이나 컴플라이언스 요구사항을 모든 인프라에 일관되게 적용할 수 있기 때문이죠.[AWS Well-Architected Framework](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html)

Pinterest도 이 원칙을 따랐고, Terraform을 IaC(Infrastructure as Code) 도구로 선택해 인프라를 코드로 관리했습니다. 코드를 통해 인프라를 정의하면 변경 이력을 추적할 수 있고, 코드 리뷰를 통해 잠재적 문제를 미리 걸러낼 수 있거든요.

## 중앙 집중식 Terraform 파이프라인이 실제로 어떤 역할을 할까?

Pinterest의 핵심은 모든 인프라 변경 사항을 중앙 저장소에 모아서 관리하는 겁니다. 예를 들어, 새로운 S3 버킷을 만들거나, IAM 정책을 수정할 때도 반드시 Terraform 코드로 작성하고, PR(Pull Request)을 통해 팀원들의 리뷰를 받습니다.

이 과정에서 GitHub Actions 같은 CI/CD 도구가 자동으로 Terraform 플랜을 실행해 변경 사항을 검증하고, 문제가 없으면 자동으로 배포까지 진행합니다. 이렇게 하면 사람이 직접 콘솔에서 실수로 잘못 설정하는 위험이 줄어들죠.[GitHub Actions Documentation](https://docs.github.com/en/actions)

이 방식의 장점은 크게 세 가지입니다.

1. **보안 취약점 사전 차단**: 코드 리뷰와 자동화된 테스트를 통해 실수나 악의적인 변경을 미리 발견합니다.
2. **일관성 유지**: 모든 인프라가 같은 코드 베이스에서 관리되니, 환경 간 차이가 줄어듭니다.
3. **변경 이력 추적**: 누가 언제 어떤 변경을 했는지 명확하게 기록되어 문제 발생 시 빠른 대응이 가능합니다.

## CI/CD 파이프라인에서 Terraform을 어떻게 자동화했을까?

Pinterest가 사용한 GitHub Actions 기반 Terraform 배포 파이프라인은 다음과 같은 흐름을 가집니다.

- PR 생성 시 Terraform Init, Validate, Plan 실행
- 결과를 PR 코멘트로 자동 게시
- 리뷰어 승인 후 머지되면 Terraform Apply 자동 실행

예를 들어, GitHub Actions 워크플로우 YAML 일부는 이렇게 생겼습니다:

```yaml
name: Terraform CI

on:
  pull_request:
    paths:
      - 'terraform/**'

jobs:
  terraform:
    runs-on: ubuntu-latest

    steps:
    - uses: actions/checkout@v3
    - name: Setup Terraform
      uses: hashicorp/setup-terraform@v1
      with:
        terraform_version: 1.5.0

    - name: Terraform Init
      run: terraform init terraform/

    - name: Terraform Validate
      run: terraform validate terraform/

    - name: Terraform Plan
      id: plan
      run: terraform plan -input=false -out=tfplan terraform/

    - name: Upload Plan
      uses: actions/upload-artifact@v3
      with:
        name: tfplan
        path: terraform/tfplan
```

이렇게 하면 PR마다 자동으로 인프라 변경 가능성을 검증할 수 있고, 리뷰어가 안전하게 코드를 검토할 수 있습니다. 머지 후에는 별도의 프로덕션 배포 워크플로우가 `terraform apply`를 실행해 실제 인프라에 반영합니다.

## 자동화 덕분에 보안 사고가 줄었지만, 완벽한 해결책은 아니다

이런 중앙 집중식 파이프라인이 모든 문제를 해결해주진 않습니다. Pinterest도 초기 도입 시 몇 가지 어려움을 겪었죠.

- **파이프라인 병목 현상**: 모든 인프라 변경이 한 파이프라인을 거치다 보니, 배포 대기 시간이 길어질 수 있습니다.
- **권한 분리 문제**: 너무 중앙 집중화하면 개발자 권한이 제한돼 자율성이 떨어질 수 있습니다.
- **복잡한 모듈 관리**: 여러 팀이 각자 다른 모듈을 만들면 의존성 관리가 어려워집니다.

그래서 Pinterest는 팀별로 필요한 권한과 책임을 명확히 나누고, 모듈화된 Terraform 코드를 잘 관리하는 데 공을 들였습니다. 또한, 파이프라인 실행 시간을 줄이기 위해 병렬화와 캐싱 전략을 도입했죠.

## Terraform 코드로 AWS IAM 정책을 안전하게 관리하는 실제 예시

아래는 Pinterest가 자주 쓰는 IAM 정책을 Terraform 코드로 정의한 예입니다. 이 코드는 최소 권한 원칙을 지키면서도, 필요한 리소스에만 접근 권한을 줍니다.

```hcl
resource "aws_iam_policy" "s3_read_only" {
  name        = "PinterestS3ReadOnly"
  description = "S3 버킷 읽기 전용 권한"

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Action = ["s3:GetObject", "s3:ListBucket"]
        Resource = [
          "arn:aws:s3:::pinterest-data-bucket",
          "arn:aws:s3:::pinterest-data-bucket/*"
        ]
      }
    ]
  })
}
```

이 코드를 통해 정책 변경이 필요할 때마다 PR을 만들고, 리뷰와 자동화 테스트를 거쳐 안전하게 배포합니다. 이 과정 덕분에 권한 남용이나 과도한 권한 부여 사고를 줄일 수 있었습니다.

## 인프라 코드에 CI/CD를 적용하는 게 왜 꼭 필요한가?

Martin Fowler가 말한 지속적 통합(Continuous Integration) 원칙을 인프라 코드에도 적용하는 게 핵심입니다.[Martin Fowler - Continuous Integration](https://martinfowler.com/articles/continuousIntegration.html) 인프라 변경을 자주, 그리고 자동화된 검증 절차를 통해 통합하면 다음과 같은 효과가 있습니다.

- 문제 조기 발견: 작은 변경 단위로 자주 통합하니, 오류 발생 시 원인 추적이 쉽습니다.
- 신속한 대응: 문제가 있으면 바로 고치고 배포할 수 있어 다운타임을 줄입니다.
- 보안 강화: 자동화된 테스트가 보안 설정 누락이나 취약점을 빠르게 찾아냅니다.

Pinterest 사례처럼, 인프라 코드도 애플리케이션 코드처럼 다뤄야 한다는 점이 점점 더 명확해지고 있습니다.

### 마무리하며

Pinterest가 AWS 인프라를 중앙 집중식 Terraform 파이프라인으로 관리하는 사례는 대규모 서비스 운영에서 인프라 보안과 안정성을 어떻게 확보할지 고민하는 우리에게 좋은 참고가 됩니다. 물론 모든 조직에 똑같이 맞는 해법은 아니지만, 다음 세 가지는 꼭 기억하세요.

- 인프라 코드 관리는 중앙 집중화하되, 팀 권한과 책임은 명확히 분리하라.
- 변경 사항은 반드시 코드 리뷰와 자동화된 CI/CD 파이프라인으로 검증하라.
- 최소 권한 원칙을 지키면서, 정책은 Terraform 코드로 관리해 변경 이력을 남겨라.

이걸 실제로 경험해보면, "아 이게 진짜 보안과 안정성의 기본이구나" 하는 생각이 듭니다. 그리고 무엇보다도, 인프라 관리가 더 이상 두려운 일이 아니라는 점이 가장 큰 수확이었죠.
