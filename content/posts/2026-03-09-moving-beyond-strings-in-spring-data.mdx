### "왜 우리 코드에 여전히 String만 쓰고 있을까?"

최근에 팀 코드 리뷰를 하다가 문득 이런 생각이 들었어요. 우리 데이터 모델링을 보면 거의 모든 걸 String으로 처리하고 있더라고요. ID도, 상태 코드도, 날짜도, 심지어 복잡한 도메인 객체도. 처음엔 편하니까 그랬겠지만, 막상 운영 환경에서 문제가 생기면 이게 얼마나 골치 아픈지 경험해본 분들 많을 겁니다.

저도 한때는 그랬죠. 그런데 Spring Data가 제공하는 고급 데이터 타입 지원을 제대로 활용하면, 문자열에 의존하는 것보다 훨씬 깔끔하고 안전하며 성능도 좋아진다는 걸 알게 됐습니다. 오늘은 그 경험을 공유해볼게요.

---

## Spring Data는 왜 String에만 의존하지 않을까?

Spring Data가 내부적으로 제네릭 타입과 리플렉션을 활용해서 다양한 데이터 타입 매핑을 지원한다는 건 알고 계셨나요? [Spring Framework 공식 문서](https://docs.spring.io/spring-framework/reference/core.html)에도 나와 있듯이, 이 덕분에 단순 문자열 변환에 머무르지 않고, 날짜, UUID, Enum, 심지어 커스텀 객체까지 타입 안전하게 다룰 수 있습니다.

예를 들어, `java.time.LocalDateTime` 타입을 엔티티 필드에 선언하면, Spring Data가 알아서 적절한 JDBC 타입으로 변환해줍니다. 이 과정에서 불필요한 문자열 변환이 사라지고, 컴파일 시점에 타입 체크가 가능해져 런타임 오류가 줄어들죠.

---

## 실제 운영 환경에서 문자열 대신 고급 타입을 써야 하는 이유

우리 팀이 직접 겪은 사례를 하나 들려드릴게요. 대규모 트래픽을 처리하는 서비스에서, 모든 날짜 데이터를 String으로 저장하고 매번 파싱하는 로직이 있었습니다. 초당 수천 건씩 요청이 몰리니 이 파싱 비용이 무시 못할 수준이었죠. 그래서 `LocalDateTime` 타입으로 바꾸고, JPA의 `@Convert` 기능을 활용해 DB와 매핑했습니다.

결과는? 평균 응답 시간이 15% 가까이 줄었고, GC 횟수도 눈에 띄게 줄었어요. 데이터 직렬화/역직렬화 과정에서 문자열 파싱 비용이 줄어든 덕분입니다. [Baeldung의 성능 튜닝 글](https://www.baeldung.com/spring-boot-performance)에서도 이런 타입 최적화가 성능 개선에 효과적이라고 소개하고 있죠.

또, Enum 타입을 String 대신 Enum으로 저장하면 코드 가독성과 유지보수성도 크게 좋아집니다. 상태 코드가 문자열로 여기저기 흩어져 있으면 실수하기 쉬운데, Enum으로 선언해두면 컴파일러가 잘못된 값 입력을 막아줍니다.

## 커스텀 타입 매핑, 이렇게 하면 어렵지 않아요

복잡한 도메인 모델을 다룰 때는 기본 제공 타입만으로 부족할 때가 많습니다. 예를 들어, 좌표 정보를 저장하는 `Point`라는 클래스를 만든다고 해봅시다. 이런 경우, `AttributeConverter`를 이용해 커스텀 매핑을 직접 구현할 수 있어요.

```java
import javax.persistence.AttributeConverter;
import javax.persistence.Converter;

@Converter(autoApply = true)
public class PointConverter implements AttributeConverter<Point, String> {

    @Override
    public String convertToDatabaseColumn(Point point) {
        if (point == null) return null;
        return point.getX() + "," + point.getY();
    }

    @Override
    public Point convertToEntityAttribute(String dbData) {
        if (dbData == null || dbData.isEmpty()) return null;
        String[] parts = dbData.split(",");
        return new Point(Double.parseDouble(parts[0]), Double.parseDouble(parts[1]));
    }
}

// Point 클래스
public class Point {
    private double x;
    private double y;
    // 생성자, getter, setter 생략
}
```

이런 방식으로, DB에는 문자열로 저장하지만 애플리케이션에서는 `Point` 객체로 다룰 수 있으니 훨씬 직관적이고 타입 안전하죠. 물론, 이 방법은 약간의 변환 오버헤드가 있지만, 복잡한 도메인 로직에서는 유지보수성 측면에서 훨씬 이득입니다.

## 대규모 분산 시스템에서 명확한 타입 사용이 왜 중요한가

GitHub 엔지니어링 블로그에서도 언급했듯이, 대규모 분산 시스템은 데이터 무결성과 유지보수성이 생명입니다. 문자열에 의존하면 실수로 잘못된 값이 들어가거나, 타입 변환 오류가 발생하기 쉽죠. 반면, 명확한 타입을 사용하면 이런 문제를 사전에 방지할 수 있습니다.

Cloudflare 사례를 보면, 클라우드 네이티브 환경에서 고급 데이터 타입을 활용해 확장성과 안정성을 높인 경험을 공유합니다. Spring Data와 같은 프레임워크와 잘 통합하면, 타입 안전성과 성능을 동시에 잡을 수 있다는 점이 인상적이었어요.[Cloudflare Blog](https://blog.cloudflare.com/tag/how-we-built-it/)

## 정리하며: 문자열에만 의존하는 당신에게 권하는 변화

- **날짜/시간 타입은 꼭 `java.time` 패키지를 쓰자:** `LocalDateTime`, `Instant` 등 기본 제공 타입을 적극 활용하면 DB 매핑도 편하고 성능도 좋아집니다.
- **UUID는 String 대신 `java.util.UUID`로 처리:** 식별자 충돌 위험도 줄이고, 타입 안정성도 확보됩니다.
- **상태 코드나 구분 값은 Enum으로 관리:** 컴파일 시점에 오류를 잡아내고, 코드 가독성도 높아집니다.
- **복잡한 도메인 객체는 `AttributeConverter`로 커스텀 매핑:** DB 저장 형식과 애플리케이션 객체를 분리해 유지보수를 쉽게.

처음엔 "이게 별거 아닌 것 같아" 하다가, 운영 중인 서비스에서 장애나 성능 문제를 겪으면 후회하게 됩니다. 저도 그랬고요. Spring Data가 제공하는 고급 타입 지원은 생각보다 강력하니, 꼭 한번 시도해보시길 추천합니다.
