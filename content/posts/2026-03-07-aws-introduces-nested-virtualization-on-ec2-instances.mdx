## "한 대 서버에 VM 여러 개? AWS 중첩 가상화로 가능해졌어요"

최근 프로젝트에서 테스트 환경을 확장하려는데, VM을 여러 대 띄우려니 인스턴스 수가 금세 늘어나더라고요. 비용도 비용이지만 관리 부담이 엄청났죠. 그러다 AWS가 EC2 인스턴스에 중첩 가상화(nested virtualization)를 지원한다는 소식을 접했습니다. 이걸 활용하면 한 대 인스턴스 안에 여러 가상 머신을 띄워서 자원 활용도를 극대화하고, 운영 비용도 확 줄일 수 있겠더라고요.

이게 단순히 "한 서버에 VM 여러 개"라는 개념을 넘어, 백엔드 아키텍처 설계에 어떤 변화를 가져올지, 그리고 실제로 어떻게 셋업하는지 경험을 공유해볼게요.

---

## AWS 중첩 가상화, 왜 백엔드 개발자한테 중요한가?

중첩 가상화는 말 그대로 가상 머신 안에서 다시 가상 머신을 구동하는 기술입니다. AWS EC2가 이걸 공식 지원하면서, 우리가 기존에 물리 인스턴스 하나당 VM 하나만 돌리던 한계를 깼어요. 

백엔드 아키텍처에서 이게 왜 중요하냐면:

- **자원 활용 극대화**: 물리 인스턴스 하나에 여러 VM을 올려서 CPU, 메모리, 네트워크 자원을 더 촘촘히 쓸 수 있어요.
- **운영 비용 절감**: 인스턴스 개수를 줄이니 AWS 요금도 줄고, 관리해야 할 인스턴스 수도 줄어듭니다.
- **복잡한 테스트 환경 구축 가능**: 서로 다른 OS나 소프트웨어 스택을 동시에 돌려야 할 때, 중첩 가상화가 특히 유용해요.

AWS 공식 아키텍처 블로그에서도 "중첩 가상화는 백엔드 아키텍처에서 여러 가상 머신을 하나의 물리적 인스턴스 내에서 실행할 수 있어 자원 활용도를 극대화하고 운영 비용을 절감할 수 있다"고 명확히 언급하고 있습니다[1].


## 실제로 어떤 EC2 인스턴스에서 중첩 가상화가 가능할까?

중첩 가상화를 지원하는 EC2 인스턴스 유형은 제한적입니다. 예를 들어 `m5`, `m6i`, `c5`, `c6i` 같은 최신 세대 인스턴스에서 주로 지원하는데, 이걸 선택하는 게 첫 번째 관문이에요.

그리고 단순히 인스턴스 유형만 맞춘다고 끝나는 게 아니라, AMI(아마존 머신 이미지)도 커널 모듈과 드라이버가 중첩 가상화를 지원하도록 구성되어 있어야 합니다. 

예를 들어, KVM 기반 가상화를 쓴다면 `kvm_intel` 또는 `kvm_amd` 모듈이 로드되어 있어야 하죠. 

```bash
# 중첩 가상화 활성화 확인
cat /sys/module/kvm_intel/parameters/nested
# 출력이 'Y'이면 활성화됨

# 만약 비활성화 상태면 모듈 재로드 필요
sudo modprobe -r kvm_intel
sudo modprobe kvm_intel nested=1
```

이런 설정을 자동화하는 스크립트를 만들어두면 배포가 훨씬 편해집니다. AWS Well-Architected Framework에서도 이런 자동화와 최적화가 중첩 가상화 운영의 핵심이라고 강조하고 있어요[2].


## 네트워크와 리소스 분배, 성능 저하 없이 운영하려면?

처음 중첩 가상화를 도입할 때 가장 걱정했던 게 성능 저하와 네트워크 복잡성이었어요. 하이퍼바이저가 두 겹이 되니까 네트워크 패킷이 여러 단계를 거쳐야 해서 지연이 생길까 봐요.

그래서 다음 세 가지를 꼭 챙겼습니다:

1. **하이퍼바이저 호환성 체크**: AWS에서 제공하는 하이퍼바이저와 VM 내부에서 쓰는 하이퍼바이저가 충돌하지 않는지 검증
2. **네트워크 설정 최적화**: VM 내부 가상 네트워크 인터페이스를 브리지 모드로 구성해서 패킷 전송 경로를 최소화
3. **리소스 분배 정책 설계**: CPU 코어, 메모리 할당을 VM 단위로 명확히 나누고, 오버커밋을 최소화

예를 들어, `virsh`를 써서 VM CPU를 4코어로 고정하고 메모리 8GB를 할당하는 설정은 아래처럼 합니다:

```xml
<vcpu placement='static'>4</vcpu>
<memory unit='MiB'>8192</memory>
```

이렇게 하면 물리 인스턴스 자원을 과도하게 공유하지 않아서 성능 변동폭을 줄일 수 있어요. 물론, 자원 낭비가 일부 발생할 수 있는 트레이드오프는 있습니다.

AWS 아키텍처 블로그에서도 "하이퍼바이저 호환성, 네트워크 설정, 리소스 분배 정책이 성능 저하 없이 안정적인 운영의 핵심"이라고 말합니다[1].


## 개발과 테스트 환경에서 중첩 가상화를 쓴 실제 사례

우리 팀은 다양한 OS와 미들웨어 버전을 테스트해야 했는데, 매번 인스턴스 여러 개를 띄우는 게 부담이었어요. 그래서 중첩 가상화를 도입해 한 EC2 인스턴스 안에 3~4개의 VM을 올려서 테스트 환경을 만들었죠.

이렇게 하니까:

- 테스트 케이스별로 VM을 빠르게 재설정 가능
- 환경별 네트워크 설정도 VM 단위로 격리 가능
- 비용은 기존 대비 40% 이상 절감

아래는 간단한 `libvirt` 기반 VM 생성 스크립트 예시입니다. 이걸 중첩 가상화가 활성화된 EC2 인스턴스에서 돌리면 바로 VM이 생성돼요.

```bash
virt-install \
  --name test-vm1 \
  --memory 4096 \
  --vcpus 2 \
  --disk size=20 \
  --os-variant ubuntu20.04 \
  --network bridge=br0 \
  --cdrom /var/lib/libvirt/images/ubuntu-20.04.iso
```

이 스크립트는 2코어, 4GB 메모리 할당된 Ubuntu 20.04 VM을 생성하는데, 네트워크는 브리지 모드로 설정해 외부와 직접 통신하게 했습니다.


## 중첩 가상화 도입 전후, 꼭 점검해야 할 부분들

중첩 가상화가 매력적이지만, 무턱대고 도입하면 오히려 관리가 더 복잡해질 수 있어요. 다음 사항들은 꼭 사전 점검하세요:

- **EC2 인스턴스 세대와 AMI 호환성**: 중첩 가상화 지원 여부 확인
- **커널 및 하이퍼바이저 설정 자동화**: 재부팅 후에도 설정 유지되도록 스크립트화
- **네트워크 구성 복잡성 관리**: VM 간 통신 및 외부 접속 경로 명확히 설계
- **모니터링 체계 강화**: VM과 호스트 인스턴스 모두 자원 사용량과 성능 지표 모니터링

이걸 소홀히 하면, 중첩 가상화가 오히려 장애의 원인이 될 수 있습니다.


## 마치며: 중첩 가상화, 우리 팀에선 이렇게 활용 중

처음엔 "중첩 가상화? 그냥 복잡한 거 아니야?" 싶었는데, 직접 써보니 운영 효율이 확실히 올라가더라고요. 특히 개발 및 테스트 환경에서 자원 낭비를 줄이고, 다양한 환경을 빠르게 띄워야 할 때 정말 유용했습니다.

다만, 하이퍼바이저 설정과 네트워크 구성에서 실수가 없도록 꼼꼼히 준비해야 하고, 모니터링도 필수입니다. 

요즘은 자동화 도구와 IaC(Infrastructure as Code)를 활용해 중첩 가상화 환경을 관리하는 게 대세라, 스크립트 하나 잘 만들어두면 운영 부담도 크게 줄어듭니다.

여러분도 백엔드 아키텍처에서 자원 활용과 비용 최적화 고민이라면, AWS EC2 중첩 가상화 한 번 고려해보세요. 생각보다 쉽게 도입할 수 있고, 효과는 꽤 큽니다.
