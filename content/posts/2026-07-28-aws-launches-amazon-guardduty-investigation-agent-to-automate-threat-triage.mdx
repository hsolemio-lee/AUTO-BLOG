### 갑자기 쏟아지는 보안 경고, 어떻게 빠르게 분류하고 대응하지?

최근 우리 팀에서 AWS GuardDuty 알림이 폭증하면서 쌓인 경고를 일일이 사람이 분류하는 게 너무 벅찼어요. 하루 100건 넘는 위협 탐지 결과를 모두 사람이 분석하려니 업무가 마비될 지경이었죠. 이럴 때 AWS가 새로 발표한 **GuardDuty Investigation Agent**가 딱이라는 소식을 듣고 바로 도입해봤습니다.

이 에이전트는 GuardDuty가 감지한 위협을 자동으로 조사하고, 연관 이벤트를 추적해 위협의 심각도와 유형을 분류해 줍니다. 덕분에 보안팀이 진짜 중요한 알림에만 집중할 수 있게 됐죠.

---

## GuardDuty Investigation Agent, 실제로 어떻게 작동하길래?

GuardDuty Investigation Agent는 GuardDuty의 위협 탐지 결과를 받아서 자동으로 추가 조사를 수행합니다. 예를 들어, 특정 IP에서 비정상적인 API 호출이 감지되면, 에이전트는 해당 IP의 다른 활동 내역, 연관된 IAM 역할, 네트워크 흐름 등을 파악해 위협의 범위와 심각도를 평가합니다.

이 과정에서 여러 AWS 서비스 로그와 메타데이터를 크로스체크하기 때문에, 사람이 일일이 찾아볼 필요 없이 자동으로 맥락을 파악할 수 있죠. 

에이전트가 제공하는 주요 기능은 다음과 같습니다:

- 위협 탐지 결과에 대한 상세 조사 자동화
- 관련 리소스 및 이벤트 연관 분석
- 조사 결과를 기반으로 한 우선순위 분류

이걸 백엔드 운영 파이프라인에 연결하면, 위험도가 낮은 알림은 자동으로 무시하거나 별도 저장소로 분류하고, 위험도가 높은 알림만 알림 시스템이나 티켓팅 시스템으로 넘길 수 있습니다.

## 실제 환경에 도입하면서 겪은 점진적 배포 전략

처음부터 모든 인스턴스에 에이전트를 깔고 돌리면, 예상치 못한 장애가 날 수도 있잖아요? 그래서 우리 팀은 AWS Well-Architected Framework에서 권장하는 대로 **작은 범위의 점진적 배포**를 택했습니다[1].

예를 들어, 먼저 개발 환경과 QA 환경에서 에이전트를 설치해 실제 위협 탐지 시나리오를 시뮬레이션해봤고, 문제 없으면 프로덕션의 10% 인스턴스에만 적용했습니다. 

이렇게 하면 만약 에이전트가 과도한 API 호출로 인해 성능 저하를 일으키거나, 조사 로직에 버그가 있어 잘못된 분류가 발생해도 전체 서비스에 미치는 영향이 제한적이라서 빠르게 롤백할 수 있거든요.

점진적 배포 덕분에 실제 운영 리스크를 크게 낮출 수 있었고, 새로운 보안 자동화 기능을 안정적으로 도입할 수 있었습니다.

---

## 실패 유형을 초기에 계측하고 대응 속도를 높인 경험

에이전트 도입 초기에, 조사 로직 중 특정 조건에서 무한 루프에 빠지는 버그가 발견됐는데요. 이걸 조기에 발견할 수 있었던 건, AWS Architecture Blog에서 강조하는 것처럼 실패 유형을 **초기부터 계측**했기 때문입니다[2].

우리 팀은 에이전트 로그와 조사 결과를 CloudWatch에 상세하게 기록하고, 비정상 탐지 시 알림을 자동으로 받도록 설정했습니다. 덕분에 장애가 발생하자마자 담당자가 바로 알 수 있었고, 문제 원인을 빠르게 파악해 2시간 이내에 패치를 배포할 수 있었죠.

이런 경험을 하면서, 보안 자동화 도구도 장애 대응 체계를 갖추는 게 얼마나 중요한지 다시 한 번 깨달았습니다. 실패 유형을 명확히 나누고, 모니터링과 알림 체계를 잘 설계하는 게 유지보수성과 대응 속도를 결정하더라고요.

## GuardDuty Investigation Agent를 백엔드 워크플로우에 연결하는 코드 예시

우리 팀은 Investigation Agent의 조사 결과를 Lambda 함수에서 받아 후속 조치를 자동화하고 있습니다. 간단한 예시 코드를 공유할게요.

```python
import json
import boto3

sns_client = boto3.client('sns')

# GuardDuty Investigation Agent가 조사 완료 후 이벤트를 SNS로 발행한다고 가정

def lambda_handler(event, context):
    # 이벤트에서 위협 심각도와 관련 리소스 정보 추출
    investigation_result = event['detail']['investigationResult']
    severity = investigation_result['severity']
    resource = investigation_result['resource']

    # 심각도가 7 이상인 경우에만 알림 발송
    if severity >= 7:
        message = f"High severity threat detected on resource {resource['type']}:{resource['id']} with severity {severity}."
        sns_client.publish(
            TopicArn='arn:aws:sns:ap-northeast-2:123456789012:SecurityAlerts',
            Message=message,
            Subject='GuardDuty High Severity Alert'
        )
    else:
        print(f"Low severity threat detected: {severity}, no action needed.")

    return {
        'statusCode': 200,
        'body': json.dumps('Investigation processed')
    }
```

이 코드는 위협 심각도가 7 이상인 경우에만 별도 SNS 주제로 알림을 보내서, 보안팀이 즉시 대응하도록 돕습니다. 낮은 수준 위협은 로그에만 남겨두고 무시해 업무 부담을 줄였죠.

## GuardDuty Investigation Agent 도입 시 고려할 점과 한계

에이전트가 모든 위협을 완벽히 분류하지는 않습니다. 특히 복잡한 공격 시나리오는 추가 조사가 필요하고, 오탐도 있을 수 있죠. 따라서 자동화 후에도 보안 전문가의 주기적인 리뷰와 튜닝이 필수입니다.

또한, 에이전트가 AWS 내부 로그와 메타데이터를 많이 참고하기 때문에, 로그 수집과 권한 설정이 제대로 되어 있지 않으면 제대로 작동하지 않을 수 있습니다. 권한 설정에 신경 써야 하죠.

마지막으로, 자동화된 조사 결과를 후속 조치에 연결하는 워크플로우 설계도 쉽지 않습니다. 무조건 자동화하기보다는, 위험도에 따라 사람 개입 여부를 조절하는 하이브리드 방식을 추천합니다.

## 마치며: 보안 자동화, 작은 단계부터 시작하는 게 답

이번 GuardDuty Investigation Agent 도입 경험을 통해 느낀 건, 보안 자동화도 결국은 **작은 범위부터 차근차근 적용하는 점진적 접근법**이 가장 안전하다는 겁니다. 

그리고 실패를 초기에 잘 계측하고, 빠르게 대응할 수 있는 체계를 갖추는 게 운영 안정성의 핵심이죠. 이 두 가지 원칙만 잘 지켜도 신규 보안 기능 도입에 따른 리스크를 크게 줄일 수 있습니다.

만약 여러분도 GuardDuty Investigation Agent를 도입할 계획이라면, 먼저 개발 환경에서 충분히 테스트하고, 점진적으로 프로덕션에 적용해 보세요. 그리고 조사 결과를 Lambda, SNS, 티켓팅 시스템 등과 잘 연결해 자동화 워크플로우를 구축하는 데 집중하면 좋겠습니다.

보안 알림에 쫓기던 예전과 달리, 이제는 정말 중요한 위협에만 집중할 수 있는 환경을 만들어 보시길 바랍니다.
