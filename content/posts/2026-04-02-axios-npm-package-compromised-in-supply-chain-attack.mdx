### "내 서비스가 갑자기 이상해졌다고?" Axios 공급망 공격이 던진 경고

얼마 전 우리 팀에서 Axios를 사용하는 서비스에서 이상 징후가 포착됐습니다. 갑자기 API 요청이 실패하거나, 이상한 네트워크 트래픽이 감지됐죠. 원인을 찾아보니, Axios npm 패키지에 악성 코드가 포함된 공급망 공격이 발생했다는 소식이 들려왔습니다. 이 사건은 단순히 라이브러리 하나의 문제가 아니라, 우리의 전체 배포 파이프라인과 보안 체계에 경종을 울렸습니다.

이 글에서는 Axios 공급망 공격 사례를 통해, 백엔드 개발자가 실무에서 어떻게 이런 공격을 감지하고, 완화하며, 복구할 수 있는지 현실적인 팁과 코드를 공유하려고 합니다.

## 공급망 공격, Axios 사건에서 우리가 배워야 할 첫 번째 교훈

Axios는 2023년 말 npm 패키지 공급망 공격에 노출됐습니다. 공격자는 정상 Axios 패키지에 악성 코드를 심어, 사용자 환경에서 민감 정보를 탈취하거나 백도어를 설치할 수 있게 했죠. 

이 사건은 단순히 패키지 하나를 교체하는 문제가 아니라, 우리의 배포 환경 전반을 점검해야 한다는 신호였습니다. 특히, 다음과 같은 문제들이 드러났습니다.

- **자동 의존성 업데이트의 위험성**: `^0.27.2` 같은 버전 지정이 공격 코드가 포함된 패치까지 자동으로 받아들이게 함
- **패키지 무결성 검증 부재**: npm 설치 시 서명이나 해시 검증을 하지 않아 변조된 패키지를 몰랐음
- **모니터링의 한계**: 런타임 이상 징후 감지가 없었고, 공격 후에도 문제 인지를 늦춤

이걸 겪으면서 "내가 쓰는 라이브러리도 안전할까?"라는 불안감이 커졌습니다. 실제로 공급망 공격은 점점 더 지능화되고 있으니까요.


## 공급망 공격을 실시간으로 감지하려면 어떻게 해야 할까?

공격을 사전에 완벽히 막기는 어렵지만, 빠른 감지는 가능합니다. 우리 팀에서 도입한 몇 가지 방법을 소개합니다.

1. **패키지 해시 및 서명 검증 자동화**

   패키지 설치 시 공식 저장소에서 제공하는 해시값과 비교하는 스크립트를 CI/CD 파이프라인에 넣었습니다. 예를 들어, `npm ci` 후 다음과 같이 해시 체크를 자동화할 수 있습니다.

   ```bash
   # package-lock.json에서 특정 패키지 버전 해시 추출
   EXPECTED_HASH="sha512-abcdef..."
   ACTUAL_HASH=$(npm pack axios@0.27.2 | shasum -a 512 | awk '{print $1}')

   if [ "$EXPECTED_HASH" != "$ACTUAL_HASH" ]; then
     echo "[ERROR] Axios 패키지 해시 불일치! 설치 중단"
     exit 1
   fi
   ```

   이 방법은 해시값을 신뢰할 수 있는 출처에서 미리 확보해둬야 하며, 번거롭지만 보안 수준을 크게 높여줍니다.

2. **런타임 이상 징후 모니터링**

   Axios를 통해 외부 API 호출 시 비정상적인 트래픽 패턴이나 응답 지연, 에러율 증가를 감지하는 로깅 시스템을 강화했습니다. 예를 들어, 에러율이 평소 0.1%였는데 갑자기 5% 이상으로 뛰면 경고를 띄우는 식이죠.

3. **의존성 업데이트 전 사전 테스트 강화**

   자동 의존성 업데이트 도구(Dependabot 등)를 쓰더라도, 업데이트가 들어오면 별도의 샌드박스 환경에서 통합 테스트를 반드시 돌려서 이상 여부를 검증합니다.


## 공급망 공격 피해를 줄이기 위한 실전 대응법

공격이 의심되거나 확진됐을 때, 어떻게 대응해야 할까요? 우리 팀이 실제로 쓴 절차를 공유합니다.

- **즉시 해당 패키지 버전 사용 중단 및 롤백**

  `package.json`과 `package-lock.json`에서 문제 버전을 명시적으로 제거하고, 안전한 이전 버전으로 고정합니다.

  ```json
  {
    "dependencies": {
      "axios": "0.27.1"
    }
  }
  ```

- **배포 파이프라인 내 모든 캐시 삭제 및 재설치**

  CI/CD 캐시, Docker 레이어 캐시 등 모든 캐시를 지우고 클린 설치를 진행해 악성 코드 잔존 위험을 제거합니다.

- **비밀 정보(환경 변수, API 키 등) 긴급 회수 및 재발급**

  공격자가 탈취했을 가능성이 있으므로, 관련 키를 모두 폐기하고 재발급합니다.

- **로그 및 트래픽 기록 전면 조사**

  공격 시점 전후의 로그를 꼼꼼히 분석해 피해 범위와 공격 경로를 파악합니다.

- **내부 개발자 및 운영팀에 신속한 공지 및 대응 협조 요청**


## 공급망 공격 이후, Axios를 안전하게 쓰는 법

공격 이후에도 Axios는 여전히 인기 있는 HTTP 클라이언트입니다. 완전히 배제하기보다 안전하게 쓰는 방법을 고민해봤습니다.

- **버전 고정과 패키지 무결성 확인 병행**

  `package.json`에서 버전을 엄격히 고정(`"axios": "0.27.2"`)하고, CI에서 해시 검증을 반드시 수행합니다.

- **대체 라이브러리 고려**

  만약 보안 우려가 계속된다면, `node-fetch`, `got` 같은 대체 라이브러리를 평가해보는 것도 방법입니다.

- **네트워크 레벨 방어 강화**

  API 호출 시 프록시 서버를 두고, 외부 요청 패턴을 통제하며 이상 징후를 탐지합니다.

- **정기적인 보안 감사와 교육**

  개발자 대상 공급망 보안 교육과 정기적인 의존성 보안 점검을 습관화합니다.


## Axios 공급망 공격에서 얻은 교훈과 앞으로의 방향

이 사건을 겪으면서 가장 크게 느낀 점은 "우리 개발자가 직접 보안의 최전선에 서야 한다"는 사실입니다. 단순히 패키지를 쓰는 소비자가 아니라, 공급망 전체를 이해하고 관리하는 주체가 되어야 한다는 거죠.

또한 AI 모델이나 외부 API를 쓸 때도 마찬가지입니다. OpenAI API 문서에서 말하듯, API 응답 스키마, 지연시간, 비용 같은 백엔드 계약을 꼼꼼히 점검하지 않으면 서비스 안정성이 크게 흔들릴 수 있습니다[OpenAI API Documentation](https://platform.openai.com/docs/overview). 그리고 Anthropic 가이드에서 강조하는 것처럼, 장애 전파를 줄이려면 모델 게이트웨이 계층에서 fallback 모델과 타임아웃 정책을 분리하는 전략도 적극 도입해야 합니다[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

## 실제로 우리 팀이 쓴 Axios 설치 후 무결성 체크 스크립트 예시

```js
const crypto = require('crypto');
const fs = require('fs');

// package-lock.json에서 axios 버전과 integrity 값 가져오기
const packageLock = JSON.parse(fs.readFileSync('package-lock.json', 'utf-8'));
const axiosEntry = packageLock.packages['node_modules/axios'];
const expectedIntegrity = axiosEntry.integrity; // 예: 'sha512-xxxx...'

// node_modules/axios/index.js 파일 해시 계산
const fileBuffer = fs.readFileSync('node_modules/axios/index.js');
const hash = crypto.createHash('sha512').update(fileBuffer).digest('base64');
const actualIntegrity = `sha512-${hash}`;

if (actualIntegrity !== expectedIntegrity) {
  console.error('[ERROR] Axios 패키지 무결성 검증 실패!');
  process.exit(1);
} else {
  console.log('Axios 패키지 무결성 검증 성공');
}
```

이 스크립트는 CI 파이프라인에서 설치 직후 실행해, 변조된 파일이 있는지 빠르게 감지합니다. 물론 모든 파일을 다 검사하려면 더 확장해야 하지만, 핵심 파일부터 점검하는 것만으로도 큰 도움이 됩니다.

공급망 공격은 이제 선택이 아니라 필수로 대비해야 하는 위험입니다. Axios 사건처럼 우리도 언제든 피해자가 될 수 있죠. 하지만 현명하게 감지 체계를 만들고, 빠르게 대응하며, 꾸준히 보안 문화를 키워나간다면 피해를 최소화할 수 있습니다.

다음에 또 비슷한 일이 터졌을 때, "아 이번에도 빠르게 잡았다"라고 말할 수 있길 바랍니다.
