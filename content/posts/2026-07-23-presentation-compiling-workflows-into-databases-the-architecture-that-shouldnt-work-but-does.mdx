## "이걸 DB에서 다 처리한다고?" 처음 들었을 때 내 반응

처음 이 아키텍처를 접했을 때 솔직히 좀 의심스러웠다. 보통은 복잡한 워크플로우를 애플리케이션 레이어에서 처리하고, DB는 단순히 데이터를 저장하고 조회하는 역할에 집중하는 게 상식 아닌가? 그런데 이 방식은 그 반대다. 워크플로우를 SQL 쿼리나 저장 프로시저 같은 DB 내부 로직으로 컴파일한다니, "이게 과연 확장성과 유지보수에 도움이 될까?" 라는 생각이 들었다.

하지만 실제 운영 환경에서 이 아키텍처를 도입한 사례들을 보면서, 생각보다 꽤 실용적이고 효과적이라는 걸 깨달았다. 특히 GitHub과 Cloudflare 같은 대규모 시스템에서 이 방식을 적용해 API 호출을 줄이고, 데이터 일관성을 높이며, 시스템 복잡도를 낮췄다는 점은 꽤 인상적이었다.[GitHub Engineering Blog](https://github.blog/category/engineering/), [Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/)


## 마틴 파울러가 말하는 데이터베이스 중심 워크플로우 컴파일의 딜레마

마틴 파울러는 마이크로서비스 아키텍처에서 서비스 간 명확한 데이터 분리와 독립성을 강조한다. 이런 관점에서 보면, 데이터베이스 내에 워크플로우 로직을 몰아넣는 건 전통적인 서비스 분리 원칙과 충돌할 수 있다.[Martin Fowler - Microservices](https://martinfowler.com/articles/microservices.html)

그럼에도 불구하고, 그는 이 접근법이 복잡한 비즈니스 로직을 데이터베이스 내에서 직접 실행해 성능 최적화와 운영 단순화를 가능케 한다고 설명한다. 즉, 트랜잭션 경계를 명확히 관리하고, 데이터 일관성을 확보하는 데 큰 도움이 된다는 것이다. 특히 트랜잭션이 여러 서비스에 걸쳐 분산될 때 발생하는 복잡성을 줄일 수 있다는 점에서 매력적이다.

하지만 이게 만능은 아니다. 데이터베이스에 과도한 로직이 몰리면 유지보수가 어려워지고, 특정 DBMS에 종속될 위험도 있다. 그래서 적절한 설계와 패턴 적용, 그리고 트랜잭션 관리가 필수다.[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/)


## 마이크로소프트가 제안하는 데이터베이스 내 워크플로우 처리 패턴

마이크로소프트 클라우드 디자인 패턴 문서에서는 이 아키텍처를 좀 더 체계적으로 다룬다.[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/)

특히 이벤트 소싱(Event Sourcing)과 CQRS(Command Query Responsibility Segregation) 패턴과 결합해, 데이터베이스 내에서 복잡한 워크플로우를 처리하는 방식을 강조한다. 이런 조합은 데이터 일관성을 유지하면서도 높은 처리량을 보장하는 데 효과적이다.

예를 들어, 이벤트 소싱을 통해 상태 변화를 이벤트로 기록하고, CQRS를 통해 읽기와 쓰기 모델을 분리하면, 데이터베이스 내에서 워크플로우를 컴파일해 실행해도 확장성과 무결성을 유지할 수 있다. 이 방식은 특히 대규모 분산 시스템에서 유용하다.


## 실전에서 만난 데이터베이스 워크플로우 컴파일, 코드 예시와 함께

우리 팀도 최근에 비슷한 아키텍처를 실험해봤다. 복잡한 주문 처리 워크플로우를 애플리케이션 서버가 아니라 PostgreSQL 내 저장 프로시저로 구현했다. 이유는 API 호출 횟수를 줄이고, 트랜잭션 경계를 데이터베이스 안에서 명확히 관리하기 위해서였다.

```sql
CREATE OR REPLACE FUNCTION process_order(order_id INT) RETURNS VOID AS $$
DECLARE
  order_status TEXT;
BEGIN
  SELECT status INTO order_status FROM orders WHERE id = order_id;

  IF order_status = 'PENDING' THEN
    -- 재고 확인
    PERFORM check_inventory(order_id);
    -- 결제 처리
    PERFORM process_payment(order_id);
    -- 주문 상태 업데이트
    UPDATE orders SET status = 'COMPLETED' WHERE id = order_id;
  ELSE
    RAISE NOTICE 'Order % is not in PENDING state.', order_id;
  END IF;
END;
$$ LANGUAGE plpgsql;
```

이 함수는 단순해 보이지만, 실제로는 재고 확인, 결제 처리, 상태 업데이트 등 여러 단계를 하나의 트랜잭션 안에서 처리한다. 덕분에 네트워크 왕복이 줄고, 중간 상태 불일치 문제도 줄었다.

하지만 단점도 있다. 저장 프로시저가 복잡해지면 디버깅이 어렵고, DBMS에 종속적이 된다. 또, 개발자들이 익숙하지 않은 SQL 기반 로직 작성 부담도 있다. 그래서 모든 워크플로우를 DB에 몰아넣기보다는, 핵심 트랜잭션 경계나 데이터 일관성이 중요한 부분에만 적용하는 게 현실적이다.


## Cloudflare와 GitHub 사례에서 배운 운영적 이점과 트레이드오프

Cloudflare는 네트워크 운영 시스템에서 복잡한 워크플로우를 DB 쿼리로 변환하는 아키텍처를 도입해, 애플리케이션 서버 로직 의존도를 낮추고 실시간 처리 성능을 크게 개선했다.[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/)

GitHub도 비슷한 접근법으로 API 호출 횟수를 줄이고, 데이터 일관성을 높이며, 시스템 확장성을 확보했다.[GitHub Engineering Blog](https://github.blog/category/engineering/)

이 두 사례에서 공통적으로 느낀 건, 데이터베이스 내 워크플로우 컴파일은 단순히 성능 향상뿐 아니라 운영 복잡도 감소에도 큰 도움이 된다는 점이다. 하지만 반대로, DBMS에 대한 의존도가 높아지고, 복잡한 로직이 DB 내부에 숨겨져서 개발자 온보딩과 유지보수가 어려워질 수 있다는 점도 명확히 인지해야 한다.


## 결국, 언제 이 아키텍처를 고민해야 할까?

- **트랜잭션 무결성이 최우선인 경우**: 여러 서비스에 걸친 분산 트랜잭션이 복잡할 때, DB 내 워크플로우 컴파일로 경계를 명확히 하는 게 효과적이다.
- **API 호출 비용과 네트워크 레이턴시가 문제일 때**: DB 내에서 로직을 처리하면 호출 횟수와 네트워크 왕복을 줄일 수 있다.
- **복잡한 비즈니스 로직이 데이터와 밀접하게 연관된 경우**: 데이터와 로직이 분리되면 일관성 유지가 어려울 때 DB 내 처리로 해결할 수 있다.

하지만, 모든 시스템에 무조건 적용하기보다는, 위 조건에 부합하는지 꼭 따져봐야 한다. 그리고 DBMS 종속성, 유지보수 난이도, 개발자 역량 등을 충분히 고려해야 한다.
