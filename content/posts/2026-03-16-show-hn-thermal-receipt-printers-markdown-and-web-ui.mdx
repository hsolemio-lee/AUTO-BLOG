## 영수증 프린터 UI, 왜 이렇게 복잡할까?

회사에서 POS 시스템을 개발하면서 열전사 영수증 프린터를 다뤄야 했던 경험이 있어요. 그런데 막상 UI를 설계하려니 생각보다 까다롭더라고요. 영수증은 고정된 포맷이 아니라 주문에 따라 가변적이고, 프린터 특성상 텍스트 기반이면서도 시각적 요소가 제한적이죠. 게다가 실시간으로 주문 상태에 맞춰 출력 명령을 보내야 해서 반응성도 중요하고요.

처음엔 HTML이나 복잡한 UI 프레임워크로 하려다가, Markdown을 활용해보면 어떨까 하는 생각이 들었어요. Markdown은 간단한 문법으로 텍스트 포맷팅이 가능해서 영수증처럼 단순하지만 구조적인 출력에 딱 맞거든요. 여기에 웹 UI 기술을 접목해 실시간 상호작용까지 가능하게 하면 꽤 괜찮겠다는 판단이었죠.

## Markdown으로 영수증 포맷을 정의하면 얻는 이점

Markdown을 쓰면 영수증 포맷을 직관적으로 설계할 수 있어요. 예를 들어, 주문 목록을 `-` 리스트로, 가격은 `**굵게**` 표시하고, 구분선은 `---` 로 넣는 식이죠. 이 단순함 덕분에 프론트엔드 개발자가 아닌 사람도 쉽게 포맷을 수정할 수 있어요. 실제로 우리 팀에서는 디자이너가 Markdown 템플릿을 직접 고쳐가면서 빠르게 요구사항을 반영할 수 있었습니다.

```markdown
# 주문 내역

- 아메리카노 x2  **4,000원**
- 치즈케이크  **3,500원**

---
총 합계: **7,500원**
```

이걸 렌더링해서 프린터에 넘기면, 복잡한 HTML/CSS 없이도 깔끔한 영수증이 출력돼요. Markdown 덕분에 프론트엔드 개발 생산성이 눈에 띄게 올라갔죠. GitHub 엔지니어링 블로그에서도 Markdown이 단순 문서 작성뿐 아니라 UI 구성에도 생산성을 높이는 데 효과적이라고 언급한 바 있습니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

## 웹 UI와 실시간 상호작용, 어떻게 구현했나

영수증은 단순 출력만 하는 게 아니라, 주문 상태나 결제 진행 상황에 따라 실시간으로 바뀌어야 하잖아요? 그래서 웹 UI를 통해 프린터와 실시간으로 소통하는 방식을 선택했습니다. WebSocket을 이용해 서버에서 상태 변화를 즉시 클라이언트에 전달하고, 클라이언트는 Markdown 템플릿을 다시 렌더링해 프린터에 보냈죠.

이 과정에서 React 같은 프레임워크를 썼는데, 상태 관리 라이브러리로는 Redux 대신 Recoil을 선택했어요. 이유는 상태가 복잡하지 않고, 비동기 업데이트가 많아서 간단한 상태 관리가 더 효율적이었거든요.

```jsx
import React, { useEffect } from 'react';
import { useRecoilState } from 'recoil';
import { receiptState } from './state';

function ReceiptPrinter() {
  const [receiptMarkdown, setReceiptMarkdown] = useRecoilState(receiptState);

  useEffect(() => {
    const ws = new WebSocket('wss://example.com/receipt');
    ws.onmessage = (event) => {
      const data = JSON.parse(event.data);
      setReceiptMarkdown(data.markdown);
    };
    return () => ws.close();
  }, [setReceiptMarkdown]);

  return (
    <div>
      <pre>{receiptMarkdown}</pre>
      {/* 실제 프린터로 출력하는 로직은 별도 처리 */}
    </div>
  );
}

export default ReceiptPrinter;
```

이렇게 하면 서버에서 주문 변경이 생길 때마다 클라이언트가 바로 업데이트되고, 사용자는 즉시 반영된 영수증을 확인할 수 있어요. Cloudflare 블로그에서도 웹 UI를 활용해 실시간 상호작용을 구현하는 사례가 많이 소개되어 있는데, 우리도 비슷한 패턴을 썼습니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

## 프론트엔드와 백엔드 분리, 유지보수에 얼마나 도움이 될까?

우리 프로젝트에서 가장 신경 쓴 부분 중 하나가 아키텍처 분리였어요. 프론트엔드와 백엔드를 명확히 나누면 각자 독립적으로 개발, 테스트, 배포가 가능하니까요. 예를 들어, 백엔드는 주문 데이터 처리와 프린터 명령 전송을 담당하고, 프론트엔드는 Markdown 렌더링과 UI 업데이트에 집중합니다.

이렇게 분리하면 프린터 드라이버나 하드웨어가 바뀌어도 백엔드만 수정하면 되고, UI 개선은 프론트엔드만 건드리면 돼서 확장성과 유지보수성이 크게 올라가더군요. Martin Fowler도 이런 아키텍처가 소프트웨어를 더 견고하게 만든다고 강조합니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

## 클라우드 기반 백엔드와 비동기 처리로 반응성 높이기

우리 시스템은 AWS Lambda와 API Gateway를 백엔드로 쓰고, DynamoDB에서 주문 데이터를 관리합니다. 프론트엔드는 서버리스 백엔드와 WebSocket으로 연결해 비동기 업데이트를 받죠. 이렇게 하면 서버 부하 분산도 잘 되고, 프린터 UI 반응성도 좋아집니다.

특히, 비동기 데이터 처리 덕분에 UI가 무거워지지 않고, 네트워크 지연에도 유연하게 대처할 수 있었어요. InfoQ 기사에서도 클라우드 플랫폼과 비동기 처리가 프론트엔드 성능 최적화에 핵심이라고 언급합니다[InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/).

## 실제로 겪은 문제와 해결법

처음엔 Markdown 렌더링 라이브러리마다 출력 결과가 미묘하게 달라서 프린터가 이상하게 찍히는 문제가 있었어요. 그래서 프린터 용 폰트 크기와 줄 간격을 고정하고, 커스텀 Markdown 파서를 만들어서 출력 포맷을 엄격하게 통제했습니다.

또, WebSocket 연결이 끊겼을 때 재연결 로직을 넣지 않으면 사용자가 모르게 업데이트가 멈추는 문제가 있었는데, 이 부분도 클라이언트에서 자동 재접속 기능을 넣어 해결했죠.

## Markdown+웹 UI 조합, 언제 써야 할까?

- 출력물이 텍스트 기반이고 구조가 단순할 때
- 비개발자도 쉽게 포맷을 수정해야 할 때
- 실시간 상태 반영이 중요한 인터페이스일 때

반대로, 그래픽 요소가 많거나 복잡한 레이아웃이 필요한 경우엔 HTML/CSS가 더 적합합니다. Markdown은 어디까지나 단순하고 빠른 프로토타입과 유지보수에 강점이 있다는 점을 기억하세요.

Markdown과 웹 UI를 활용해 열전사 영수증 프린터 인터페이스를 만들면서 느낀 건, 의외로 단순한 도구들이 큰 생산성 향상과 유지보수 편의성을 가져온다는 겁니다. 물론 하드웨어 특성상 제약도 많지만, 소프트웨어 아키텍처와 클라우드 기술을 잘 결합하면 충분히 사용자 친화적이고 반응성 좋은 시스템을 만들 수 있어요.

앞으로도 이런 조합을 더 다양한 분야에 적용해보고 싶네요. 혹시 비슷한 경험 있으면 같이 이야기 나눠요!
