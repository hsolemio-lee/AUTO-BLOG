# Kubernetes 위에 오픈 웨이트 AI를 올리면 진짜 편할까?

얼마 전 우리 팀에서 오픈 웨이트 AI 모델을 Kubernetes 클러스터에 올려서 운영하기 시작했는데, 처음엔 '컨테이너화만 시키면 다 되겠지' 싶었어요. 근데 막상 해보니 생각보다 세밀한 설정과 운영 노하우가 필요하더군요. 특히 AI 모델 특성상 무거운 연산과 불규칙한 부하 패턴 때문에, Kubernetes의 기본 기능만으로는 부족한 부분도 있었고요.

오늘은 제가 직접 겪은 시행착오와 함께, Kubernetes 환경에서 오픈 웨이트 AI 모델을 어떻게 효율적이고 안정적으로 운영하고 있는지 구체적인 팁을 공유해 보려고 합니다.

---

## Kubernetes가 AI 분산 운영에 딱 맞는 이유

Kubernetes는 컨테이너화된 애플리케이션을 배포하고 관리하는 데 특화된 오픈소스 플랫폼인데요, AI 모델을 여러 대 분산해서 운영할 때도 꽤 좋은 인프라가 됩니다. 왜냐하면 다음과 같은 장점이 있거든요:

- **확장성**: 필요에 따라 Pod 수를 늘리거나 줄이기 쉽습니다. AI 모델 부하가 갑자기 늘어날 때 빠르게 대응 가능하죠.
- **자동 복구**: Pod가 죽으면 자동으로 재시작해 줍니다.
- **서비스 디스커버리와 로드밸런싱**: 여러 AI 모델 인스턴스에 부하를 분산할 수 있습니다.

실제로 Kubernetes 공식 문서에서도 "Kubernetes는 분산 AI 모델 운영에 적합한 인프라를 제공한다"고 명시하고 있어요[1](https://kubernetes.io/docs/concepts/overview/).

우리 팀은 AI 모델을 컨테이너 이미지로 빌드해서, Kubernetes 클러스터에 배포했습니다. 예를 들어, 모델 추론 API를 제공하는 컨테이너를 3개씩 띄우고, Horizontal Pod Autoscaler(HPA)를 이용해 CPU 사용률이 70%를 넘으면 자동으로 6개까지 확장하도록 설정했죠.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: ai-model-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: ai-model-deployment
  minReplicas: 3
  maxReplicas: 6
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
```

이렇게 하면 부하가 갑자기 몰려도 AI 모델 서비스가 끊기지 않고 유연하게 대처할 수 있었습니다.

## AI 모델 컨테이너 상태는 어떻게 감시해야 할까?

AI 모델은 무거운 연산을 수행하다가 가끔 메모리 누수나 예외로 인해 멈출 수 있는데, 이때 Kubernetes의 Liveness, Readiness, Startup 프로브가 정말 큰 도움이 됩니다.

- **Liveness Probe**: 컨테이너가 살아있는지 주기적으로 체크해서 죽었으면 재시작합니다.
- **Readiness Probe**: 트래픽을 받을 준비가 됐는지 확인해서 준비되지 않으면 서비스에서 제외합니다.
- **Startup Probe**: 초기 부팅이 오래 걸릴 때, 정상적으로 시작했는지 판단합니다.

우리 팀은 AI 모델이 내부 헬스 체크 API(`/healthz`)를 제공하도록 해서, Liveness와 Readiness 프로브에 연결했습니다. 예를 들어, 10초마다 `/healthz` 엔드포인트를 호출해서 200 OK가 아니면 재시작하도록 했죠.

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5
```

이 설정 덕분에 AI 모델 컨테이너가 비정상 상태에 빠졌을 때 빠르게 복구되어, 서비스 중단 시간을 최소화할 수 있었습니다. Kubernetes 공식 문서에도 이렇게 프로브를 잘 활용하는 게 오픈 웨이트 AI 모델 안정화에 필수적이라고 나와 있어요[2](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/).

## OpenAI API를 Kubernetes에서 어떻게 활용할까?

우리 팀은 자체 AI 모델뿐 아니라 OpenAI API도 Kubernetes 환경에서 통합해서 운영 중인데요, RESTful 인터페이스 덕분에 서비스 간 연동이 매우 편리하더라고요.

예를 들어, AI 모델 서비스에서 OpenAI API를 호출해 텍스트 생성 결과를 받아오고, 그 결과를 다시 클라이언트에 전달하는 구조입니다. 아래는 Python FastAPI에서 OpenAI API를 호출하는 간단한 예시입니다.

```python
from fastapi import FastAPI
import httpx

app = FastAPI()
OPENAI_API_KEY = "your_openai_api_key"

@app.post("/generate")
async def generate_text(prompt: str):
    async with httpx.AsyncClient() as client:
        response = await client.post(
            "https://api.openai.com/v1/completions",
            headers={"Authorization": f"Bearer {OPENAI_API_KEY}"},
            json={
                "model": "text-davinci-003",
                "prompt": prompt,
                "max_tokens": 100
            },
        )
        response.raise_for_status()
        data = response.json()
        return {"text": data["choices"][0]["text"]}
```

이런 식으로 OpenAI API를 Kubernetes 내 여러 Pod에서 호출하면, 자연스럽게 부하 분산과 확장성 관리가 가능해집니다. OpenAI 공식 문서에서도 Kubernetes 환경에서 API를 활용하는 게 확장성과 관리 측면에서 유리하다고 설명하고 있죠[3](https://platform.openai.com/docs/overview).

## 여러 AI 모델을 한 클러스터에서 깔끔하게 관리하려면?

분산 AI 운영에서 가장 골치 아픈 부분 중 하나가 여러 종류의 AI 모델을 한꺼번에 관리하는 일입니다. 우리 팀은 Kubernetes의 **네임스페이스(namespace)**와 **레이블(label)**을 적극 활용해서 이 문제를 해결했어요.

- **네임스페이스**: 프로젝트별, 팀별로 리소스를 분리해서 격리
- **레이블 셀렉터**: 같은 네임스페이스 내에서도 모델별로 Pod와 서비스를 그룹핑

예를 들어, `namespace: ai-project1` 안에 `model: openweight-v1` 레이블을 붙인 Deployment와 Service를 모아 관리합니다. 이렇게 하면 명령어 한 줄로 특정 모델만 모니터링하거나 스케일링할 수 있어서 운영이 훨씬 수월해지더군요.

```bash
kubectl get pods -n ai-project1 -l model=openweight-v1
kubectl scale deployment ai-model-deployment -n ai-project1 --replicas=5
```

이런 네임스페이스와 레이블 활용법은 Kubernetes 공식 문서에서도 분산 워크로드 관리 효율성을 높이는 방법으로 소개되고 있습니다[1](https://kubernetes.io/docs/concepts/overview/).

## 운영하면서 겪은 고충과 해결책

처음엔 Liveness 프로브를 너무 엄격하게 설정해서, AI 모델이 잠시 무거운 연산 중일 때도 죽는 현상이 있었어요. 그래서 `initialDelaySeconds`를 30초 이상으로 늘리고, `failureThreshold`도 3으로 설정해서 여유를 주니 훨씬 안정적이었습니다.

또, OpenAI API 호출 시 트래픽 급증으로 인해 API rate limit에 걸리는 문제도 있었는데, Kubernetes의 자동 스케일링과 함께 자체 큐잉 시스템을 도입해 부하를 조절했더니 한결 원활해졌습니다.

마지막으로, 여러 AI 모델을 한 클러스터에서 돌리다 보니 네임스페이스 관리가 필수라는 걸 뼈저리게 느꼈고, 지금은 네임스페이스별 리소스 쿼터도 엄격히 설정해서 무분별한 리소스 사용을 막고 있습니다.

# 마무리하며

Kubernetes 위에 오픈 웨이트 AI를 올리는 건 단순히 컨테이너만 띄우는 게 아니라, 프로브 설정, 네임스페이스 관리, 자동 스케일링, 외부 API 연동까지 고려해야 하는 복합 작업입니다. 하지만 제대로만 하면 AI 모델을 안정적이고 확장 가능하게 운영할 수 있어요.

제가 추천하는 핵심은 다음과 같습니다:

- AI 모델 컨테이너에 `/healthz` 같은 헬스 체크 엔드포인트를 꼭 만들고, Liveness/Readiness/Startup 프로브를 세밀하게 조정할 것
- Kubernetes 네임스페이스와 레이블로 AI 워크로드를 논리적으로 분리해서 관리할 것
- OpenAI API 같은 외부 AI 서비스는 RESTful 인터페이스를 활용해 쉽게 통합하고, 부하 분산 전략을 마련할 것
- 자동 스케일링과 헬스 체크를 조합해 부하 변화와 장애에 유연하게 대응할 것

이 글이 분산 AI 모델을 Kubernetes에서 운영하는 동료 엔지니어분들께 조금이나마 도움이 되길 바랍니다. 실제로 겪어보면 작은 설정 하나가 서비스 안정성에 큰 차이를 만듭니다. 꼭 직접 실험해 보면서 최적의 설정을 찾아가세요.
