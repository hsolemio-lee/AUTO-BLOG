## 실제 프로젝트에서 마주한 JavaScript 스트림의 한계

"왜 이렇게 느리지?" 처음 Node.js 백엔드에서 대용량 데이터 스트림을 다룰 때마다 느꼈던 답답함입니다. 기본 제공되는 `stream` 모듈을 써도, 비동기 처리 중 에러가 터지면 복구가 어렵고, backpressure 관리도 까다로웠죠. GitHub 엔지니어링 블로그에서도 기존 JavaScript 스트림 API가 백엔드 데이터 처리에서 비효율성을 낳는다고 지적합니다. 특히 비동기 처리와 에러 핸들링 부분이 명확하지 않아 확장성에 제약이 크다고 하더군요[GitHub Engineering Blog](https://github.blog/category/engineering/).

이걸 개선하지 않으면, 대규모 트래픽이나 복잡한 데이터 파이프라인에서 병목이 생길 수밖에 없습니다. 그래서 직접 더 나은 스트림 API를 만들고, 기존 문제를 어떻게 해결했는지 경험을 나누려 합니다.

## Cloudflare가 말하는 병목 줄이기: 파이프라인 병렬 처리와 backpressure

Cloudflare는 대규모 네트워크 트래픽을 처리하면서 JavaScript 스트림 API의 병목 현상을 줄이기 위한 전략을 소개했는데요, 여기서 배울 점이 많았습니다. 그들은 파이프라인 내에서 병렬 처리를 적극 활용하고, backpressure(압력 역전) 관리를 강화해 데이터 흐름을 원활하게 유지했습니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

간단히 말해, 스트림이 한 단계에서 느려지면 전체 파이프라인이 멈추는 걸 방지하기 위해 여러 처리 단계를 병렬로 돌리고, 각 단계가 처리할 수 있는 데이터 양을 조절하는 거죠. 예를 들어, 아래 코드는 Node.js 기본 스트림에서 병렬 변환(transform) 단계를 구현한 간단한 예입니다:

```js
const { Transform, pipeline } = require('stream');

class ParallelTransform extends Transform {
  constructor(concurrency, transformFn, options) {
    super({ ...options, objectMode: true });
    this.concurrency = concurrency;
    this.transformFn = transformFn;
    this.running = 0;
    this.queue = [];
  }

  _transform(chunk, encoding, callback) {
    if (this.running >= this.concurrency) {
      this.queue.push({ chunk, encoding, callback });
    } else {
      this.running++;
      this.transformFn(chunk, encoding, (err, data) => {
        if (err) return callback(err);
        this.push(data);
        this.running--;
        if (this.queue.length > 0) {
          const next = this.queue.shift();
          this._transform(next.chunk, next.encoding, next.callback);
        }
        callback();
      });
    }
  }

  _flush(callback) {
    if (this.running === 0) callback();
    else {
      const interval = setInterval(() => {
        if (this.running === 0) {
          clearInterval(interval);
          callback();
        }
      }, 10);
    }
  }
}

// 사용 예시
const parallelTransform = new ParallelTransform(4, (chunk, encoding, cb) => {
  // 비동기 작업 시뮬레이션
  setTimeout(() => cb(null, chunk.toString().toUpperCase()), 100);
});

pipeline(
  process.stdin,
  parallelTransform,
  process.stdout,
  (err) => {
    if (err) console.error('파이프라인 에러:', err);
    else console.log('처리 완료');
  }
);
```

위 코드는 최대 4개의 비동기 변환 작업을 병렬로 처리해 전체 처리 속도를 끌어올립니다. 하지만 단점도 있는데, 병렬도가 너무 높으면 메모리 사용량이 급증하고, 순서 보장이 어려울 수 있습니다. 그래서 적절한 concurrency 값을 찾는 게 중요합니다.

## 함수형 패턴과 결합하면 유지보수성도 쑥쑥 올라간다

Martin Fowler가 말한 것처럼, 스트림 API를 함수형 프로그래밍 패턴과 결합하면 데이터 흐름이 더 명확해지고 유지보수가 쉬워집니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/). 예를 들어, `map`, `filter`, `reduce` 같은 함수형 연산을 스트림에 자연스럽게 적용하는 거죠.

이걸 Node.js 스트림에 직접 적용하려면, Transform 스트림을 래핑하는 유틸 함수를 만들어서 함수형 스타일로 체이닝할 수 있게 하면 좋습니다. 간단한 예를 보시죠:

```js
const { Transform } = require('stream');

function mapStream(mapper) {
  return new Transform({
    objectMode: true,
    transform(chunk, encoding, callback) {
      try {
        const mapped = mapper(chunk);
        callback(null, mapped);
      } catch (err) {
        callback(err);
      }
    }
  });
}

function filterStream(predicate) {
  return new Transform({
    objectMode: true,
    transform(chunk, encoding, callback) {
      try {
        if (predicate(chunk)) callback(null, chunk);
        else callback();
      } catch (err) {
        callback(err);
      }
    }
  });
}

// 사용 예
// inputStream.pipe(mapStream(x => x * 2)).pipe(filterStream(x => x > 10))
```

이런 식으로 스트림을 함수형 연산처럼 조합하면, 처리 로직이 훨씬 읽기 쉽고 테스트하기도 편해집니다. 물론, 복잡한 비동기 작업에는 별도의 에러 핸들링과 backpressure 관리가 추가로 필요합니다.

## 클라우드 환경에서 스트림 API를 최적화하려면 무엇을 고려해야 할까?

InfoQ에서는 클라우드 플랫폼 환경에서 JavaScript 스트림 API를 최적화하기 위해 표준화된 API 개선과 비동기 이벤트 처리 모델의 재설계를 강조합니다[InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/). 실제로 서버리스 함수나 컨테이너 기반 마이크로서비스에서 스트림 처리 성능이 곧 비용 절감과 직결되기 때문이죠.

예를 들어, AWS Lambda 같은 환경에서는 스트림 처리 중에 발생하는 이벤트를 최대한 비동기적으로 빠르게 처리하고, 오류 발생 시 재시도 로직이 내장되어야 합니다. 또한, 네트워크 지연과 리소스 제한을 고려해 스트림 버퍼 크기와 concurrency를 조절하는 게 필수입니다.

이런 환경에서 저는 RxJS 같은 리액티브 프로그래밍 라이브러리를 도입해, 스트림 이벤트를 Observable로 다루면서 복잡한 비동기 흐름을 선언적으로 제어하는 방식을 추천합니다. 아래는 RxJS로 간단한 스트림 변환을 구현한 예시입니다:

```js
const { from, map, filter } = require('rxjs');

const source$ = from([1, 2, 3, 4, 5]);

source$
  .pipe(
    map(x => x * 3),
    filter(x => x > 10)
  )
  .subscribe({
    next: val => console.log('처리된 값:', val),
    error: err => console.error('에러:', err),
    complete: () => console.log('완료')
  });
```

물론 RxJS를 도입하면 러닝커브가 있고, 간단한 스트림에는 오히려 과할 수 있지만, 복잡한 클라우드 환경에서는 유지보수와 확장성 면에서 큰 도움이 됩니다.

## 내 경험상 가장 중요한 건 ‘에러와 backpressure를 어떻게 다루느냐’

스트림 API를 개선할 때 가장 까다로운 부분이 에러 처리와 backpressure 관리입니다. 기본 Node.js 스트림은 에러가 발생하면 파이프라인 전체가 멈추거나, 에러 이벤트를 놓치기 쉽습니다. 제가 겪은 프로젝트에서는 이 부분 때문에 몇 주를 허비했죠.

그래서 다음과 같은 원칙을 세웠습니다:

- **에러는 반드시 스트림 내부에서 처리하거나, 적절한 콜백/이벤트로 외부에 알린다.**
- **backpressure는 최대 동시 처리량(concurrency)과 내부 큐 크기로 조절하며, 무한 큐 누적을 막는다.**
- **에러 발생 시 재시도 로직과 타임아웃을 반드시 구현한다.**

이 원칙을 지키면 스트림 파이프라인이 훨씬 안정적이고 예측 가능해집니다.

---

스트림 API 개선은 단순히 성능만 올리는 게 아니라, 유지보수성과 개발 생산성에도 큰 영향을 미칩니다. JavaScript 생태계에서 아직 완벽한 스트림 솔루션은 없지만, 병렬 처리, 함수형 패턴, 클라우드 환경 최적화, 그리고 무엇보다 에러와 backpressure 관리에 집중하면 훨씬 나은 경험을 만들 수 있습니다.

이 글이 여러분의 다음 프로젝트에 작은 힌트가 되길 바랍니다.
