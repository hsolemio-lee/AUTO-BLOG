### "페이지가 느려서 사용자가 이탈하는 것 같아" — 네비게이션 성능 문제, 어떻게 해결할까?

최근 프로젝트에서 SPA를 쓰면서도 페이지 전환이 느려서 고민이 많았어요. 전체 페이지를 새로고침하지 않고도 상태를 유지하면서 빠르게 화면을 바꾸고 싶었는데, 기존의 `history.pushState` 기반 라우팅은 한계가 있더라고요. 그러다 우연히 최신 Navigation API가 베이스라인으로 지원된다는 소식을 접했죠. 이 API가 실제로 어떻게 프론트엔드 네비게이션을 바꾸는지, 그리고 우리 코드에 어떻게 적용할 수 있는지 직접 써보며 정리한 내용을 공유합니다.

---

## Navigation API가 기존 SPA 라우팅과 다른 점은?

기존 SPA에서는 보통 `react-router`, `vue-router` 같은 라이브러리를 쓰면서 URL 변경과 컴포넌트 상태 관리를 직접 처리했죠. 하지만 이 방식은 브라우저의 네비게이션 이벤트와 완전히 분리되어 있어서, 페이지 전환 시 불필요한 리렌더링이나 상태 초기화가 발생하기도 했어요.

최신 Navigation API는 브라우저 네이티브에서 페이지 전환을 제어할 수 있게 해줍니다. 덕분에 전체 페이지 리로드 없이도 URL 변경, 네트워크 요청, 캐싱, 렌더링 상태를 훨씬 세밀하게 다룰 수 있죠. GitHub 엔지니어링 팀도 "페이지 전환 시 전체 페이지 리로드 없이 상태 유지와 빠른 렌더링이 가능해 UX와 성능이 크게 향상됐다"고 평가했습니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

이 API를 쓰면 SPA와 MPA의 장점을 모두 살린 하이브리드 네비게이션도 구현할 수 있는데, InfoQ에서도 다양한 사용자 시나리오에 대응 가능하다고 분석했어요[InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/).


## 실제로 Navigation API를 어떻게 써야 할까? 간단한 코드 예시

```js
// 네비게이션 이벤트를 직접 제어하는 예제
const navigation = window.navigation;

navigation.addEventListener('navigate', event => {
  const destination = event.destination.url;
  event.intercept({
    async handler() {
      // fetch 필요한 데이터
      const response = await fetch(destination);
      const html = await response.text();

      // 기존 DOM을 교체하거나 필요한 부분만 업데이트
      document.getElementById('app').innerHTML = html;

      // 상태 관리, 애니메이션 등 추가 처리 가능
      console.log('Navigation to', destination, 'handled by Navigation API');
    }
  });
});
```

이 코드는 `navigate` 이벤트를 가로채서 네트워크 요청과 DOM 업데이트를 직접 처리하는 예입니다. 기존 SPA 라우터처럼 URL 변경에 따른 상태 관리뿐 아니라, 네트워크 요청 최적화나 캐싱 전략도 직접 구현할 수 있죠.

Cloudflare는 이 방식을 도입해 네트워크 요청을 줄이고 캐싱 전략을 개선해 사용자 응답 속도를 단축하는 데 성공했습니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).


## 컴포넌트 기반 아키텍처에서 Navigation API가 주는 확장성

Martin Fowler도 지적했듯이, Navigation API는 컴포넌트 단위로 네비게이션 상태를 세밀하게 제어할 수 있게 해줘서 유지보수성과 확장성이 뛰어난 프론트엔드 구조 설계에 큰 도움이 됩니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

예를 들어, 특정 컴포넌트가 페이지 전환 시 자신의 상태를 보존하거나 새로 데이터를 불러오는 시점을 직접 결정할 수 있어요. 기존 SPA처럼 전체 앱 상태를 한꺼번에 관리하는 게 아니라, 각 컴포넌트가 독립적으로 네비게이션 이벤트를 처리할 수 있죠.

이런 구조는 대규모 프로젝트에서 특히 유리한데, 팀별로 컴포넌트 책임 구분이 명확해지고 네비게이션 로직이 분산되면서 병목 현상이 줄어듭니다. 물론 처음에는 이런 설계가 복잡해 보일 수 있지만, 실제로 써보면 컴포넌트 재사용성과 테스트 편의성이 크게 올라가는 걸 느낄 수 있어요.


## Navigation API 도입 시 주의할 점과 현실적인 한계

처음 Navigation API를 도입할 때는 브라우저 호환성 문제를 꼭 확인해야 합니다. 아직 모든 브라우저에서 완전하게 지원하지는 않으니, 폴리필이나 점진적 도입 전략이 필요해요.

또한, 네비게이션 이벤트를 직접 가로채고 처리하는 만큼, 개발자가 상태 관리와 네트워크 요청 최적화에 더 신경 써야 합니다. 자동으로 처리해주던 SPA 라우터와 달리, 잘못 구현하면 오히려 성능 저하나 상태 불일치가 발생할 수 있죠.

마지막으로, SEO나 접근성 측면에서도 기존 MPA와 다르게 서버 사이드 렌더링과 클라이언트 렌더링 간의 균형을 맞추는 작업이 필요합니다. 이 부분은 프로젝트 요구사항에 맞춰 적절히 설계해야 합니다.


## 내일부터 바로 써볼 수 있는 Navigation API 체크리스트

- 브라우저 지원 현황 확인 및 폴리필 적용 여부 결정
- 네비게이션 이벤트(`navigate`)를 가로채서 직접 처리할 핸들러 작성
- 컴포넌트별 네비게이션 상태 관리 전략 수립
- 네트워크 요청 최적화 및 캐싱 전략 설계
- SEO와 접근성 요구사항 반영

---

Navigation API는 단순히 빠른 페이지 전환을 넘어서, 프론트엔드 아키텍처를 한 단계 업그레이드할 수 있는 강력한 도구입니다. 직접 써보면 "이게 진짜 게임 체인저구나" 하는 느낌을 받을 거예요. 특히 대규모 서비스에서 사용자 경험과 유지보수성을 동시에 잡고 싶다면 꼭 한 번 시도해보시길 추천합니다.
