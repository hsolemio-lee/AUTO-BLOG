자율 AI 에이전트를 쿠버네티스에 올려서 운영하다 보면, "내 AI가 뭔가 이상한 행동을 하면 어떻게 감지하지?" 또는 "API 키 같은 중요한 정보는 어떻게 안전하게 관리하지?" 같은 질문이 자연스럽게 떠오릅니다. 특히 AI가 스스로 의사결정을 하면서 클라우드 리소스를 사용하는 새로운 유형의 워크로드라면, 기존 서비스와는 또 다른 보안과 관측성 고민이 필요하죠.

## 쿠버네티스 네임스페이스와 RBAC로 신뢰 경계 세우기

자율 AI 에이전트는 여러 서비스와 통신하고, 때로는 외부 API 키를 사용합니다. 이때 가장 먼저 생각해야 할 건 최소 권한 원칙입니다. 쿠버네티스는 네임스페이스와 RBAC(Role-Based Access Control)를 활용해 권한을 세밀하게 나눌 수 있어요. 예를 들어, AI 에이전트가 사용하는 워크로드만 별도의 네임스페이스에 배치하고, 그 네임스페이스 내에서만 필요한 권한만 부여하는 식입니다.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: ai-agent
  name: ai-agent-role
rules:
- apiGroups: [""]
  resources: ["pods", "secrets"]
  verbs: ["get", "list", "watch"]
```

위 예시는 `ai-agent` 네임스페이스에서 Pod와 Secret을 조회할 수 있는 권한만 부여한 Role입니다. 이렇게 하면 AI 에이전트가 다른 네임스페이스의 리소스에 접근하는 걸 원천 차단할 수 있죠. 이런 신뢰 경계 설정은 [Kubernetes 공식 문서](https://kubernetes.io/docs/concepts/overview/)에 상세히 나와 있는데, 실제로 적용해보면 권한이 너무 광범위하게 열려 있어서 보안 사고가 날 위험이 꽤 크다는 걸 느낄 겁니다.

## 시크릿 관리: API 키와 인증 토큰 안전하게 다루기

AI 에이전트는 보통 외부 API 호출용 키나 토큰을 사용합니다. 이걸 코드에 하드코딩하거나 환경변수로 그냥 두면 보안 구멍이 됩니다. 쿠버네티스 시크릿(Secrets)은 이런 민감 정보를 안전하게 저장하고 Pod에 주입할 수 있는 방법을 제공합니다.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: ai-agent-api-keys
  namespace: ai-agent
type: Opaque
data:
  openai-api-key: bXktc2VjcmV0LWFwaS1rZXk=
```

위 시크릿은 base64로 인코딩된 API 키를 저장합니다. Pod 스펙에서 이렇게 참조할 수 있죠:

```yaml
containers:
- name: ai-agent
  image: my-ai-agent:latest
  env:
  - name: OPENAI_API_KEY
    valueFrom:
      secretKeyRef:
        name: ai-agent-api-keys
        key: openai-api-key
```

이렇게 하면 API 키가 컨테이너 내부 환경변수로 안전하게 주입되어, 코드에 직접 키를 넣지 않아도 됩니다. 물론 시크릿 자체에 접근 권한도 RBAC로 엄격히 제한해야 합니다. 이 부분도 [Kubernetes 공식 문서](https://kubernetes.io/docs/concepts/overview/)에서 기본 원칙을 잘 설명하고 있으니 참고하세요.

## AI 에이전트 컨테이너 상태 감시: Liveness, Readiness, Startup 프로브 활용하기

AI 에이전트가 자율적으로 동작하다가 갑자기 멈추거나 응답하지 않으면 큰 문제가 됩니다. 쿠버네티스는 Liveness, Readiness, Startup 프로브를 제공해서 컨테이너 상태를 주기적으로 체크하고, 문제가 있으면 자동으로 재시작하거나 트래픽을 차단할 수 있어요.

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 15
  periodSeconds: 20
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10
startupProbe:
  httpGet:
    path: /startup
    port: 8080
  failureThreshold: 30
  periodSeconds: 10
```

이 설정은 AI 에이전트가 8080 포트에서 `/healthz`, `/ready`, `/startup` 엔드포인트를 통해 상태를 알려주도록 합니다. 특히 `startupProbe`는 초기 부팅이 오래 걸리는 AI 에이전트에 유용한데, 실패 허용 횟수를 30번 정도로 넉넉하게 줘서 충분히 시작할 시간을 줍니다. 이런 프로브 설정은 [쿠버네티스 공식 가이드](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)를 참고하면 좋습니다.

## AI 에이전트 로그와 메트릭 통합으로 실시간 관측성 확보하기

AI 에이전트가 동작 중에 무슨 일이 벌어지는지 파악하는 건 생각보다 어렵습니다. 특히 보안 이벤트나 비정상 행위를 빨리 감지하려면 로그와 메트릭을 한데 모아 실시간으로 모니터링해야 해요. 쿠버네티스는 Fluentd, Prometheus, Grafana 같은 도구와 쉽게 연동됩니다.

예를 들어, AI 에이전트 컨테이너에서 다음과 같이 JSON 형식 로그를 출력한다고 가정해봅시다.

```typescript
// TypeScript 예시: AI 에이전트 내부에서 로그 출력
console.log(JSON.stringify({
  timestamp: new Date().toISOString(),
  event: "api_call",
  api: "OpenAI",
  status: "success",
  latency_ms: 120
}));
```

이 로그를 Fluentd가 수집해 Elasticsearch로 보내고, Prometheus는 AI 에이전트가 노출하는 메트릭(예: API 호출 횟수, 에러율)을 스크랩합니다. Grafana 대시보드에서 이 데이터를 실시간으로 시각화하면, "최근 API 호출 지연이 200ms 이상으로 늘었다"거나 "비정상적인 인증 실패가 급증했다" 같은 이상 징후를 즉시 알 수 있죠.

이렇게 통합 관측성을 갖추면 AI 에이전트가 예상치 못한 행동을 하거나 보안 사고가 발생했을 때 빠르게 대응할 수 있습니다.

### 마무리하며: 실무에서 꼭 챙겨야 할 세 가지

1. **네임스페이스와 RBAC로 권한 최소화하기**: AI 에이전트 전용 네임스페이스를 만들고, 꼭 필요한 권한만 Role과 RoleBinding으로 부여하세요.

2. **시크릿은 절대 코드에 직접 넣지 말고, 쿠버네티스 시크릿으로 안전하게 관리하기**: 그리고 시크릿 접근 권한도 꼼꼼히 통제해야 합니다.

3. **프로브와 관측성 도구로 AI 에이전트 상태와 보안 이벤트를 실시간 모니터링하기**: 장애와 이상 징후를 빠르게 감지하는 게 관건입니다.

처음엔 이게 번거롭고 설정할 게 많아 보이지만, 실제로 AI 에이전트를 운영하면서 장애나 보안 사고가 터지면 얼마나 큰 피해가 나는지 경험하면 이게 얼마나 중요한지 절실히 느끼게 됩니다. 나중에 후회하지 말고 지금부터 신뢰 경계와 시크릿, 관측성에 투자하세요.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
