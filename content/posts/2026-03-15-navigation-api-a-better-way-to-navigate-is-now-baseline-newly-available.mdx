### 내비게이션이 느려서 사용자 이탈률이 올라간 경험, 있나요?

"페이지 전환이 너무 느려서 사용자가 금방 떠나버려요." 이런 얘기, 한두 번쯤은 들어보셨을 겁니다. 저도 비슷한 문제로 골머리를 앓다가 최근에 Navigation API를 도입하면서 꽤 큰 변화를 경험했어요. 단순히 페이지를 빠르게 바꾸는 걸 넘어서, 컴포넌트 단위로 상태를 효율적으로 관리하고, 불필요한 리렌더링을 줄여서 사용자 체감 성능을 확실히 끌어올렸거든요.

이번 글에서는 최신 Navigation API가 왜 프론트엔드 내비게이션을 개선하는 데 강력한 도구인지, 그리고 실제 프로젝트에 어떻게 적용할 수 있는지 제 경험을 바탕으로 풀어보려 합니다.

## Navigation API가 기존 내비게이션과 다른 점은 뭘까?

사실 전통적인 SPA 내비게이션은 URL이 바뀌면 라우터가 전체 페이지나 큰 컴포넌트 트리를 다시 렌더링하는 방식이 많았죠. 이 과정에서 불필요한 리렌더링과 네트워크 요청이 발생해 사용자 경험이 떨어질 수밖에 없었어요. 반면 최신 Navigation API는 브라우저 내비게이션 이벤트를 더 세밀하게 제어할 수 있게 해주고, 상태 변화에 따른 최소한의 업데이트만 수행하도록 설계됐습니다.

Martin Fowler가 설명한 소프트웨어 아키텍처 가이드에서도 이 API가 내비게이션 성능과 UX를 크게 향상시키는 핵심 요소로 꼽히고 있는데요, 실제로 페이지 전환 시 불필요한 리렌더링을 최소화하고 빠른 반응성을 제공한다고 명확히 짚고 있습니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

이게 왜 중요한가 하면, 대규모 컴포넌트 트리 안에서 한두 컴포넌트 상태만 바뀌었을 때 전체 페이지를 다시 그리는 게 아니라 해당 부분만 업데이트하면, 사용자 입장에선 훨씬 부드럽고 빠른 내비게이션 경험을 할 수 있기 때문입니다.

## 컴포넌트 기반 아키텍처에서 Navigation API가 주는 진짜 이점

저희 팀은 원래 리액트 기반으로 컴포넌트 단위로 UI를 쪼개서 개발하는데, 내비게이션 상태 관리가 점점 복잡해지면서 유지보수가 어려워졌어요. Navigation API를 도입하고 나서 이 부분이 훨씬 깔끔해졌죠.

API 덕분에 내비게이션 상태를 컴포넌트 트리 내에서 자연스럽게 관리할 수 있게 됐는데, 이는 확장성과 유지보수성을 크게 높여줍니다. InfoQ의 아키텍처 관련 자료에서도 Navigation API가 모듈화된 컴포넌트 설계와 결합될 때 복잡한 사용자 흐름 관리가 쉬워지고, 코드 재사용성이 향상된다고 설명하고 있어요[InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/).

예를 들어, 탭 이동이나 모달 오픈 같은 UI 상태를 URL과 동기화시키면서도, 전체 페이지 리렌더링 없이 해당 컴포넌트만 상태를 바꾸는 식으로 처리할 수 있습니다. 이게 실제로 해보면 생각보다 훨씬 편하고, 나중에 기능 추가나 버그 수정할 때도 부담이 적어요.

## 실제 코드로 보는 Navigation API 기본 사용법

아래는 React 프로젝트에서 Navigation API를 간단히 활용하는 예시입니다. 이 코드는 페이지 전환 시 불필요한 리렌더링을 줄이고, 상태를 효율적으로 관리하는 데 중점을 뒀어요.

```jsx
import { useState, useEffect } from 'react';

function useNavigation() {
  const [currentPath, setCurrentPath] = useState(window.location.pathname);

  useEffect(() => {
    function onPopState() {
      setCurrentPath(window.location.pathname);
    }
    window.addEventListener('popstate', onPopState);

    return () => {
      window.removeEventListener('popstate', onPopState);
    };
  }, []);

  function navigate(to) {
    if (to !== currentPath) {
      window.history.pushState({}, '', to);
      setCurrentPath(to);
    }
  }

  return { currentPath, navigate };
}

function App() {
  const { currentPath, navigate } = useNavigation();

  return (
    <div>
      <nav>
        <button onClick={() => navigate('/')}>Home</button>
        <button onClick={() => navigate('/about')}>About</button>
      </nav>
      <main>
        {currentPath === '/' && <Home />}
        {currentPath === '/about' && <About />}
      </main>
    </div>
  );
}

function Home() {
  return <h1>홈페이지</h1>;
}

function About() {
  return <h1>소개 페이지</h1>;
}
```

이 예시는 브라우저의 `popstate` 이벤트를 활용해 사용자가 뒤로 가기 버튼을 눌렀을 때도 상태를 제대로 반영합니다. `navigate` 함수는 URL을 바꾸고 상태를 업데이트해, 필요한 컴포넌트만 렌더링하도록 돕죠. 물론 실제 프로젝트에선 라우팅 라이브러리와 결합하거나, 상태 관리 라이브러리와 함께 쓰면서 더 복잡한 내비게이션 로직을 구현하게 될 겁니다.

하지만 이 기본 구조만 잘 잡아도, 내비게이션 성능과 UX가 확실히 달라지는 걸 체감할 수 있을 거예요.

## Navigation API 도입 시 고려할 점과 한계

좋은 점만 있는 건 아닙니다. Navigation API는 아직 브라우저별 지원 상태가 완벽하지 않을 수 있고, 복잡한 내비게이션 상태를 모두 커버하려면 추가적인 상태 관리 로직이 필요합니다. 예를 들어, URL 쿼리 파라미터나 해시값 변경에 따른 세밀한 제어는 별도로 구현해야 하죠.

그리고 기존 라우팅 라이브러리와 섞어 쓰면 충돌 가능성도 있으니, 도입 전에 팀 내에서 충분한 테스트와 검증이 필요합니다. 특히 SSR(Server Side Rendering) 환경에서는 클라이언트 내비게이션과 서버 렌더링 간 상태 일치 문제도 신경 써야 해요.

하지만 이런 단점들을 감수할 만큼, Navigation API가 주는 성능과 유지보수성 향상 효과는 분명히 큽니다.
