## 페이지 전환이 이렇게 빨라질 수 있다고? Navigation API를 쓰면 가능한 이야기

얼마 전, 우리 팀에서 SPA처럼 부드러운 내비게이션 경험을 주면서도 초기 로딩 속도와 SEO 문제를 해결하는 방법을 찾다가 최신 Navigation API를 접했어요. 기존에 `window.location`이나 `history.pushState`를 직접 다루면서 느꼈던 불편함과 성능 한계가 확실히 개선될 수 있겠다는 확신이 들었죠.

특히 페이지 전체를 다시 로드하지 않고 필요한 부분만 바꾸는 방식이라, 실제로 체감할 만큼 빠르고 자연스러운 전환이 가능하더라고요. 이건 단순히 ‘빠르다’ 수준이 아니라, UX가 한 단계 업그레이드되는 경험이었어요.

## Navigation API가 기존 SPA와 어떻게 다를까?

SPA에서는 보통 자바스크립트 라우터가 URL 변화를 감지해서 화면을 바꾸는데, 이 과정에서 초기 로딩이 무거워지고 SEO 최적화가 까다로운 문제가 있었죠. Navigation API는 브라우저 차원에서 내비게이션 이벤트를 더 세밀하게 제어할 수 있게 해줍니다.

예를 들어, Navigation API를 쓰면 다음과 같은 장점이 있어요:

- **전체 페이지 리로드 없이 필요한 리소스만 교체**: 네트워크 비용과 렌더링 시간을 줄여줍니다.
- **SEO 친화적**: 서버에서 렌더링된 HTML을 그대로 활용하면서도 SPA같은 UX를 제공합니다.
- **내비게이션 이벤트를 세밀하게 다룰 수 있음**: `navigate` 이벤트를 통해 사용자 행동에 맞춘 최적화가 가능하죠.

GitHub 엔지니어링 팀도 이 점을 높이 평가하며, Navigation API 도입 후 사용자 반응성과 성능이 크게 개선됐다고 밝혔습니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

## 실제 코드로 보는 Navigation API 활용법

```js
// 기본적인 Navigation API 사용 예시
// 페이지 이동 시 전체 리로드 없이 필요한 데이터만 fetch하고 컴포넌트 업데이트

window.navigation.addEventListener('navigate', event => {
  event.intercept({
    async handler() {
      const url = event.destination.url;
      // API 호출 혹은 필요한 리소스 fetch
      const response = await fetch(url, { headers: { 'X-Requested-With': 'NavigationAPI' } });
      const html = await response.text();

      // DOM 업데이트 (간단한 예)
      document.getElementById('app').innerHTML = html;

      // 히스토리 스택에 상태 저장
      window.history.pushState({}, '', url);
    }
  });
});
```

이 코드는 페이지 이동이 감지되면 전체 페이지를 다시 불러오는 대신, 필요한 HTML만 비동기로 받아서 `#app` 요소를 교체합니다. `event.intercept()` 덕분에 브라우저 기본 동작을 막고 우리가 원하는 방식으로 내비게이션을 제어할 수 있죠.

처음에는 이게 별거 아닌 것 같지만, 실제로 대규모 프로젝트에서 전체 페이지 리로드가 줄어들면 네트워크 비용과 렌더링 부담이 크게 줄어듭니다. Cloudflare도 Navigation API를 도입해 서버-클라이언트 간 데이터 전달을 최적화하고 네트워크 비용을 절감했다고 하네요[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

## 컴포넌트 구조도 이렇게 바뀌더라

Navigation API를 쓰면 컴포넌트 단위로 페이지를 쪼개고 재사용하는 패턴이 자연스럽게 자리 잡습니다. 예전에는 라우터가 URL에 따라 컴포넌트를 교체하는 식이었다면, 이제는 내비게이션 이벤트에 맞춰 필요한 컴포넌트만 다시 렌더링하거나 상태를 유지하는 게 훨씬 쉬워졌어요.

Martin Fowler도 이런 모듈화와 재사용성 강화가 대규모 프론트엔드 유지보수에 큰 도움이 된다고 강조합니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

예를 들어, 사용자 프로필 페이지를 이동할 때 전체 페이지가 아니라 프로필 컴포넌트만 교체하도록 하면, 상태 관리도 간단해지고 렌더링 비용도 확 줄어듭니다. 덕분에 기능 추가나 버그 수정 시 영향 범위를 좁힐 수 있죠.

## Navigation API 도입 시 주의할 점

- **브라우저 호환성**: 아직 모든 브라우저에서 완벽히 지원하지 않으니, 폴리필이나 대체 로직을 준비해야 합니다.
- **복잡한 상태 관리**: 내비게이션 상태를 세밀하게 관리해야 하므로, 상태 관리 라이브러리와 잘 결합하는 설계가 필요합니다.
- **SEO와 초기 로딩**: 서버 사이드 렌더링(SSR)과 함께 써야 SEO와 초기 로딩 문제를 해결할 수 있습니다. Navigation API만으로는 부족할 수 있어요.

## 내비게이션 경험을 한 단계 올리고 싶다면 Navigation API를 꼭 써보자

처음엔 Navigation API가 생소하고, 기존 SPA 라우터를 대체하는 게 부담스러울 수 있습니다. 하지만 직접 써보면 페이지 전환 속도와 UX가 눈에 띄게 좋아지는 걸 느낄 수 있어요. 특히 대규모 프로젝트에서 컴포넌트 재사용성과 유지보수성이 크게 향상되는 점도 무시할 수 없습니다.

우리 팀도 Navigation API 도입 후 사용자 이탈률이 줄고, 개발 생산성이 올라가는 걸 경험했습니다. 물론 도입 초반에는 브라우저 지원 이슈와 상태 관리 복잡성 때문에 애를 먹었지만, 그만큼 얻은 게 훨씬 컸죠.

만약 여러분도 SPA의 한계나 복잡한 내비게이션 문제로 고민 중이라면, Navigation API를 적극 고려해보시길 추천합니다.
