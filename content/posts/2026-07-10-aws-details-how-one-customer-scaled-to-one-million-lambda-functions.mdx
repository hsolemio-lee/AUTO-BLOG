### 갑자기 100만 개 Lambda 함수라니, 이게 가능한 이야기인가요?

얼마 전 AWS Architecture Blog에서 한 고객이 무려 100만 개의 Lambda 함수를 운영한다는 글을 봤어요. 서버리스가 얼마나 확장성이 뛰어난지 다시 한번 실감했죠. 그런데 이걸 실제로 운영한다는 건 말처럼 쉽지 않습니다. 함수 하나하나가 독립적으로 돌아가야 하고, 배포부터 모니터링, 비용 관리까지 신경 써야 할 게 한두 가지가 아니니까요.

그래서 이번 글에서는 그 사례를 바탕으로 대규모 Lambda 운영에서 어떤 설계와 운영 패턴이 핵심인지, 그리고 우리가 실제로 적용할 수 있는 팁들을 나눠보려고 해요.

---

## Lambda 함수 100만 개, 어떻게 설계했을까? - 상태 비저장과 이벤트 중심 아키텍처

AWS Architecture Blog에 따르면, 이 고객은 Lambda 함수를 최대한 상태 비저장(stateless)으로 설계했다고 해요. 함수가 상태를 갖고 있으면 확장성에 제약이 생기고, 함수 간 의존성이 높아져 장애 전파 위험도 커지거든요.

대신 각 Lambda 함수는 독립적으로 이벤트를 받아 처리하는 구조를 택했어요. 예를 들어, 메시지 큐나 이벤트 버스 같은 AWS EventBridge, SNS 등을 통해 비동기 이벤트를 주고받으며 함수 호출 간 결합도를 낮췄죠. 이 덕분에 함수가 수백만 개라도 서로 간섭 없이 병렬로 실행할 수 있었답니다.

이런 설계는 AWS Well-Architected Framework에서도 권장하는 패턴입니다. 모듈화된 마이크로서비스 설계와 이벤트 기반 비동기 처리가 서버리스 확장성의 핵심이라는 점을 명확히 짚고 있죠[https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html).

### 이걸 우리 프로젝트에 적용하려면?

- 함수는 최대한 외부 상태에 의존하지 않도록 설계
- 이벤트 소스(예: SQS, EventBridge) 활용해 함수 호출 분리
- 함수 간 직접 호출 최소화, 메시지 기반 통신 권장

## 배포 자동화 없이는 100만 함수 관리 불가능하다

함수 수가 수십, 수백 개만 되어도 수동 배포는 지옥인데, 100만 개라면 아예 불가능하죠. 그래서 이 고객은 CI/CD 파이프라인을 철저히 자동화했습니다.

AWS CloudFormation, CDK, 그리고 SAM(Serverless Application Model)을 활용해 인프라와 코드를 코드로 관리하고, Git 기반 변경 감지 시 자동 배포가 이루어지도록 했어요. 특히, Lambda 버전 관리와 별칭(alias)을 적극 활용해 무중단 배포를 구현했죠.

아래는 AWS CDK로 Lambda 함수를 배포하는 간단한 예시입니다. 실제 운영 환경에서는 이보다 훨씬 복잡한 스택과 파이프라인이 쓰이겠지만, 기본적인 구조는 이렇습니다.

```typescript
import * as cdk from 'aws-cdk-lib';
import * as lambda from 'aws-cdk-lib/aws-lambda';

export class LambdaStack extends cdk.Stack {
  constructor(scope: cdk.App, id: string) {
    super(scope, id);

    const myFunction = new lambda.Function(this, 'MyFunction', {
      runtime: lambda.Runtime.NODEJS_18_X,
      handler: 'index.handler',
      code: lambda.Code.fromAsset('lambda'),
      memorySize: 512, // 메모리 크기 조정으로 비용과 성능 밸런스 맞추기
      timeout: cdk.Duration.seconds(10),
    });

    // 버전 관리
    const version = myFunction.currentVersion;
    // 별칭 생성으로 트래픽 분산 및 롤백 지원
    new lambda.Alias(this, 'MyFunctionAlias', {
      aliasName: 'prod',
      version,
    });
  }
}
```

이처럼 코드로 모든 걸 관리하면, 수백만 개 함수도 체계적으로 배포하고 롤백할 수 있습니다.

## CloudWatch와 X-Ray로 운영 복잡도 줄이기

100만 개 함수가 돌아가면 장애가 나도 어디서부터 손을 대야 할지 막막하죠. 그래서 이 고객은 AWS CloudWatch와 X-Ray를 적극 활용해 모니터링과 트레이싱을 자동화했습니다.

- **CloudWatch Logs**: 각 함수의 로그를 중앙 집중식으로 수집해 필터링과 알람 설정
- **CloudWatch Metrics**: 함수별 호출 수, 오류율, 지연 시간 등 실시간 지표 모니터링
- **X-Ray**: 함수 간 호출 흐름을 시각화해 병목 구간과 오류 지점 빠르게 파악

이 조합 덕분에 문제 발생 시 원인 분석과 대응 속도가 크게 빨라졌다고 하네요. 특히 X-Ray는 이벤트 기반 아키텍처에서 복잡하게 얽힌 함수 호출 관계를 한눈에 볼 수 있어 필수 도구입니다.

## 비용 최적화를 위한 메모리와 실행 시간 튜닝

100만 개 함수면 비용도 엄청나게 나올 텐데, 이 고객은 AWS Well-Architected Framework 권고사항대로 메모리 크기와 실행 시간을 세밀하게 조정해 비용을 절감했습니다.

Lambda는 메모리 크기에 따라 CPU 성능도 비례해서 올라가는데, 무조건 큰 메모리를 할당하는 게 아니라 함수별로 적절한 메모리와 타임아웃을 찾아야 해요. 예를 들어, CPU 집약적인 작업은 1024MB 이상, 간단한 데이터 처리 함수는 256MB로 설정하는 식이죠.

또한, 불필요한 함수 호출을 줄이기 위해 이벤트 필터링과 조건부 실행 로직을 도입했다고 합니다. 이건 처음엔 별거 아닌 것 같지만, 호출 수가 수백만 단위가 되면 비용 차이가 엄청납니다.

## 내가 직접 적용해본 작은 팁들

- **함수별 메모리 프로파일링 자동화**: CloudWatch 지표를 기반으로 Lambda 메모리/실행 시간 조정 스크립트를 만들어 주기적으로 튜닝
- **이벤트 버스 필터링 강화**: EventBridge 필터링 규칙을 세분화해 불필요한 함수 호출 최소화
- **배포 시 Canary 배포 전략 활용**: AWS Lambda 별칭과 트래픽 분산 기능으로 점진적 배포 및 빠른 롤백 지원

---

100만 개 Lambda 함수 운영 사례는 우리에게 서버리스 아키텍처가 단순히 작은 서비스에만 적합한 게 아니라, 제대로 설계하고 운영하면 엄청난 규모도 감당할 수 있다는 걸 보여줍니다. 물론 그만큼 설계와 운영에 신경 써야 할 부분도 많고, 자동화 없이는 불가능하다는 점도 명심해야겠죠.

여러분도 서버리스 확장성을 고민할 때 이번 사례에서 배운 설계 원칙과 운영 전략을 참고하면 큰 도움이 될 거예요.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
