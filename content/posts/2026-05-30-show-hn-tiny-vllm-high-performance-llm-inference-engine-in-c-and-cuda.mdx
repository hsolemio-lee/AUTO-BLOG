## LLM 추론, 왜 이렇게 느릴까?

요즘 LLM(대규모 언어 모델) 서비스가 많아지면서 "우리 서비스에 바로 적용해보자" 하는 팀이 많죠. 그런데 막상 돌려보면 느리고, GPU 자원도 금방 바닥나고, 응답 지연이 심해서 사용자 경험이 엉망이 되는 경우가 허다합니다. 저도 비슷한 문제로 골머리를 앓다가 Show HN에 올라온 Tiny-vLLM 프로젝트를 발견했어요. C++과 CUDA로 만들어진 이 추론 엔진은 "진짜 빠르다"는 평이 많더군요.

이번 글에서는 Tiny-vLLM을 실제 백엔드 서비스에 붙여보고, 어떻게 최적화하고 확장할 수 있는지 경험을 공유하려고 합니다. 특히 C++과 CUDA를 직접 다루면서 얻은 노하우와 한계도 솔직히 풀어볼게요.

## Tiny-vLLM, 왜 C++와 CUDA로 만들었을까?

사실 Python 기반 LLM 라이브러리가 많지만, 성능 면에서 한계가 분명합니다. Python은 인터프리터 언어라서 CPU 자원 관리가 까다롭고, GPU 연산을 최대한 활용하려면 CUDA 커널 최적화가 필수거든요. Tiny-vLLM은 이걸 C++로 구현해서 메모리 관리부터 GPU 스레드 동기화까지 직접 제어합니다.

CUDA를 활용해 GPU에서 병렬로 토큰 생성과 확률 계산을 수행하는데, 덕분에 초당 처리량이 기존 Python 라이브러리 대비 3~5배 이상 증가하는 걸 체감할 수 있었습니다. 특히, 작은 배치 크기(예: 1~4)에서도 지연 시간을 50ms 이하로 유지하는 게 인상적이었어요.

## Tiny-vLLM 백엔드에 붙여볼 때 주의할 점

### 1) 모델 로딩과 메모리 관리

Tiny-vLLM은 모델을 GPU 메모리에 직접 로딩하는데, 7B급 모델 하나만 해도 VRAM 12GB 이상을 요구합니다. 따라서 여러 모델을 동시에 서비스하려면 GPU가 여러 대 필요하죠. 혹은 모델을 CPU 메모리에 올리고 필요할 때마다 일부만 GPU로 옮기는 전략도 고민해야 합니다.

예를 들어, 13B 모델을 한 대 GPU에서 돌리려면 최소 24GB VRAM이 필요해서 보통 A100 40GB급 GPU를 씁니다. Tiny-vLLM은 이런 대형 모델도 메모리 최적화 덕분에 기존보다 20% 이상 적은 메모리로 돌릴 수 있어요.

### 2) 배치 처리와 동시성

초당 요청이 100건 정도면 배치 사이즈를 4~8로 묶는 게 효율적입니다. 너무 작으면 GPU 활용률이 떨어지고, 너무 크면 지연 시간이 늘어나니까요. Tiny-vLLM은 내부에 배치 큐잉 메커니즘이 있어서 적절한 타이밍에 배치를 묶어 GPU에 넘깁니다.

```cpp
// Tiny-vLLM에서 배치 큐잉 예시 (의사코드)
std::vector<Request> batch;
while (true) {
    auto req = request_queue.pop_with_timeout(10ms);
    if (req) batch.push_back(*req);
    if (batch.size() >= 8 || timeout_elapsed()) {
        model.infer(batch);
        batch.clear();
    }
}
```

이렇게 하면 요청이 몰릴 때는 GPU를 최대한 활용하고, 요청이 적을 땐 지연 시간을 최소화하는 절충점을 찾을 수 있습니다.

### 3) CUDA 최적화는 어디까지 해야 하나?

Tiny-vLLM은 CUDA에서 커널을 직접 작성해 토큰 생성, softmax, top-k 샘플링 등을 구현합니다. 처음엔 "내가 CUDA까지 건드려야 하나?" 싶었는데, 실제로 병목 구간을 프로파일링해보면 GPU 메모리 접근과 스레드 동기화가 가장 큰 영향을 줍니다.

예를 들어, softmax 계산을 warp 단위로 병렬 처리하면서 shared memory를 적극 활용하면 30% 이상 속도 향상을 체감할 수 있었어요. 하지만 너무 복잡하게 최적화하면 유지보수가 어려워지니, 적당한 선에서 멈추는 게 중요합니다.

## 실제 서비스에 Tiny-vLLM 붙여보니 생긴 변화들

우리 팀은 기존 Python 기반 LLM API 서버를 Tiny-vLLM C++ 엔진으로 교체했는데, 체감 성능이 확 달라졌습니다. 응답 지연이 평균 200ms에서 50ms 이하로 줄었고, GPU 사용률도 70% 이상으로 안정화됐어요. 덕분에 서버 대수를 30% 줄일 수 있었죠.

또한, 작은 범위의 점진적 배포 전략을 써서 신규 백엔드 기능을 도입했는데, 운영 리스크가 크게 줄었습니다. 장애가 발생해도 빠르게 롤백 가능했고, 실패 유형을 초기에 계측해 문제 원인을 신속히 파악할 수 있었죠. 이런 점은 OpenAI API 문서와 Anthropic 가이드에서도 강조하는 부분입니다[OpenAI API Documentation](https://platform.openai.com/docs/overview), [Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

## Tiny-vLLM을 쓰면서 겪은 한계와 앞으로의 고민

- **GPU 자원 한계**: 아무리 최적화해도 VRAM 한계는 피할 수 없고, 대형 모델에선 여러 GPU 분산이 필수입니다.
- **개발 복잡도 증가**: C++과 CUDA 코드를 직접 관리하니 개발 속도가 느려지고, 신규 개발자 온보딩 비용이 올라갑니다.
- **배포와 모니터링**: 실시간 추론에서 실패 유형을 초기에 정확히 계측하는 로깅 시스템 구축이 필수인데, 이 부분이 아직 미흡합니다.

그래도 Tiny-vLLM 덕분에 "LLM 추론도 엔터프라이즈급 성능과 안정성으로 운영할 수 있겠다"는 자신감이 생겼어요.

# 코드 예시: Tiny-vLLM 기본 추론 호출

```cpp
#include "tiny_vllm.h"

int main() {
    // 모델 경로와 설정
    std::string model_path = "/models/llama-7b/ggml-model.bin";
    TinyVLLM::Model model(model_path);

    // 프롬프트 준비
    std::string prompt = "안녕하세요, Tiny-vLLM!";

    // 추론 옵션
    TinyVLLM::InferenceOptions options;
    options.max_tokens = 50;
    options.top_k = 40;
    options.temperature = 0.8;

    // 추론 실행
    auto result = model.infer(prompt, options);

    // 결과 출력
    std::cout << "Generated Text: " << result.text << std::endl;

    return 0;
}
```

이 간단한 예시에서도 알 수 있듯, Tiny-vLLM은 C++ API를 통해 GPU 자원을 직접 제어하며 빠른 추론을 지원합니다. 실제 서비스에서는 배치 처리, 동시 요청 관리, 오류 계측 등을 추가로 구현해야 하죠.

## 마무리하며: LLM 추론, 속도와 안정성 사이에서

Tiny-vLLM은 LLM 추론을 C++과 CUDA로 직접 최적화해 성능을 극대화한 좋은 사례입니다. 다만, 이런 접근은 개발 복잡도를 높이고 GPU 자원 관리에 신경 써야 하는 트레이드오프가 있죠.

실제 서비스에 적용할 땐 작은 범위의 점진적 배포 전략으로 리스크를 줄이고, 실패 유형을 초기부터 꼼꼼히 계측하는 게 필수입니다. 이런 운영 노하우가 결국 안정적이고 빠른 LLM 서비스를 만드는 열쇠니까요.

LLM 추론 최적화에 관심 있는 분들은 Tiny-vLLM 코드를 직접 살펴보고, CUDA 프로파일링 도구로 병목을 찾아가며 개선하는 경험을 꼭 해보시길 추천합니다.
