## Spring Boot 3.x로 업그레이드하면서 마주친 첫 걸림돌

얼마 전 우리 팀에서 Spring Boot 2.x에서 3.x로 메이저 업그레이드를 진행했는데, 처음에 "Java 17 이상 필수"라는 조건을 보고 살짝 당황했어요. 기존에 Java 11로 돌리던 서비스라 JDK 업그레이드부터 시작해야 했거든요. 그런데 막상 Java 17로 올리고 나니, JDK 모듈화 덕분에 불필요한 라이브러리 의존성이 줄고, 새로운 API 덕분에 코드도 더 깔끔해졌습니다. 성능도 체감될 정도로 좋아졌고, 보안 패치도 최신 상태로 유지할 수 있었죠.

이 과정에서 가장 중요한 건 Spring Framework 6 기반과의 호환성 점검이었어요. Deprecated된 API를 찾아서 대체하는 작업이 꽤 손이 많이 갔는데, 이걸 안 하면 런타임 에러나 보안 취약점으로 이어질 수 있거든요. 그래서 업그레이드 전에는 꼭 [Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html) 문서를 꼼꼼히 보면서 호환성 체크를 했습니다.

## JVM 튜닝과 캐시 전략, 그리고 비동기 처리까지 챙겨야 하는 이유

Spring Boot 업그레이드만 하면 끝? 그게 아니더라고요. 성능 튜닝은 필수입니다. 특히 JVM 튜닝은 꼭 해야 하는데, 저희는 힙 메모리 크기를 2GB에서 4GB로 늘리고, GC 옵션을 G1 GC로 바꿨더니 응답 지연이 15% 이상 줄었어요. 

캐시 전략도 재점검했는데, Redis 캐시 TTL을 서비스 특성에 맞게 5분에서 10분으로 늘리니까 DB 부하가 눈에 띄게 줄었습니다. 그리고 Spring의 `@Async` 어노테이션을 적극 활용해 비동기 처리를 늘렸는데, 이게 생각보다 효과가 컸어요. 예를 들어, 이메일 발송 같은 후처리 작업을 비동기로 돌리니 사용자 요청 처리 속도가 훨씬 빨라졌죠.

커넥션 풀은 HikariCP 기본 설정에서 maxPoolSize를 10에서 30으로 늘렸는데, 너무 크게 하면 오히려 DB가 부담될 수 있으니 모니터링하면서 조절하는 게 중요합니다. 저희는 APM 도구(New Relic)를 도입해서 실시간으로 성능 지표를 모니터링하며 튜닝했어요. [Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance) 글도 많이 참고했습니다.

## 오픈소스 보안, Dependabot으로 자동화하지 않으면 후회한다

오픈소스 라이브러리 보안은 그냥 넘기기 쉽지만, 실제로는 치명적일 수 있어요. 저희는 GitHub의 Dependabot을 도입해서 매주 의존성 스캔과 보안 패치를 자동으로 받도록 설정했습니다. 덕분에 취약점이 발견되면 바로 PR이 올라오고, 테스트 통과 후 바로 머지하는 워크플로우가 자리 잡았죠.

한 번은 log4j 취약점이 터졌을 때, Dependabot 덕분에 1시간 만에 패치를 배포할 수 있었어요. 이 경험이 얼마나 큰 차이를 만드는지 몸소 느꼈습니다. 물론 자동화가 만능은 아니고, 수동으로도 정기 점검하면서 이상 징후를 체크하는 게 중요합니다. [GitHub Engineering Blog](https://github.blog/category/engineering/)에서 관련 사례를 참고하면 도움이 됩니다.

## 다운타임 없이 점진적 롤아웃, IaC로 배포 자동화까지

대규모 시스템 업그레이드는 언제나 긴장되죠. 저희는 이번 업그레이드에서 카나리 배포 전략을 도입했는데, 신규 버전을 5% 트래픽부터 시작해 점차 100%로 늘리는 방식을 썼습니다. 덕분에 문제가 생겨도 빠르게 롤백할 수 있었고, 전체 서비스 안정성을 확보할 수 있었어요.

클라우드 환경이라서 Terraform으로 인프라 코드를 작성해 배포 프로세스를 완전 자동화했는데, 이게 생각보다 큰 도움이 됐습니다. 수동으로 서버 세팅하고 배포하던 예전과 비교하면 오류가 거의 없고, 배포 속도도 3배 이상 빨라졌어요.

Martin Fowler의 [Software Architecture Guide](https://martinfowler.com/architecture/)에서 소개하는 모범 사례를 참고해, 배포 전후 모니터링과 알람 체계도 강화했습니다. 덕분에 업그레이드 당일에도 긴장하지 않고 배포를 마칠 수 있었습니다.

## 실제로 적용한 Spring Boot 3.x 업그레이드 코드 예시

```java
// Java 17 이상에서만 컴파일 가능
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.scheduling.annotation.EnableAsync;

@SpringBootApplication
@EnableAsync
public class MyApplication {

    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

// 비동기 서비스 예시
import org.springframework.scheduling.annotation.Async;
import org.springframework.stereotype.Service;

@Service
public class EmailService {

    @Async
    public void sendEmail(String to, String subject, String body) {
        // 이메일 발송 로직
        System.out.println("Sending email to " + to);
        // 실제 이메일 API 호출 코드
    }
}
```

이 예시는 Java 17 이상 환경에서 Spring Boot 3.x 기반으로 비동기 처리를 활성화한 간단한 구조입니다. 실제 서비스에서는 비동기 작업이 많을수록 메인 스레드 부담이 줄고, 사용자 경험이 개선됩니다.

## 마무리하며: 업그레이드는 단순히 버전 올리기가 아니다

처음엔 "그냥 버전만 올리면 되겠지" 했는데, 실제로는 JDK 업그레이드, 코드 호환성 점검, 성능 튜닝, 보안 자동화, 배포 전략까지 종합적으로 준비해야 하는 큰 작업이었어요. 하지만 이렇게 꼼꼼히 준비하고 실행하니까, 결과적으로 서비스 안정성과 개발 생산성이 크게 올라갔습니다.

여러분도 Spring Boot 3.x로 업그레이드할 때는 꼭 Java 17 이상 환경을 준비하고, Deprecated API 점검과 JVM 튜닝을 병행하세요. 그리고 보안 자동화 도구를 적극 활용하고, 점진적 롤아웃과 IaC로 배포를 자동화하면 다운타임 걱정 없이 안정적인 서비스 운영이 가능합니다.

작은 변화가 큰 차이를 만듭니다. 이번 업그레이드 경험이 여러분 팀에도 도움이 되길 바랍니다.
