## 클라우드 네이티브 환경에서 공급망 보안, 왜 갑자기 중요해졌을까?

최근에 우리 팀에서 신규 백엔드 기능을 배포하면서 문득 ‘이 코드가 어디서 왔지?’라는 질문이 머리를 스쳤어요. 오픈소스 라이브러리, 컨테이너 이미지, CI/CD 파이프라인까지, 클라우드 네이티브 환경은 수많은 외부 요소가 얽혀있거든요. 그런데 이 중 하나라도 악성코드나 취약점이 숨어 있다면? 바로 그게 ‘소프트웨어 공급망 공격’의 시작입니다.

CNCF(Cloud Native Computing Foundation)와 Kusari가 최근 손잡고 이 문제를 해결하겠다고 나섰는데요, 실제로 우리가 백엔드 개발자로서 어떤 패턴과 운영 전략을 써야 할지 고민해봤습니다.


## 작은 범위의 점진적 배포 전략, 왜 공급망 보안에 도움이 될까?

처음엔 배포 전략이 보안이랑 무슨 상관인가 싶었는데, 생각보다 깊은 연관이 있더라고요. 예를 들어, 신규 백엔드 기능을 한꺼번에 모든 사용자에게 노출하는 대신, 5% 혹은 10% 사용자에게만 점진적으로 배포하는 거죠. 이렇게 하면 문제가 생겨도 피해 범위를 최소화할 수 있거든요.

이 전략은 단순히 장애 대응뿐 아니라, 공급망 내에 숨어있는 의심스러운 코드나 이미지가 실제 운영 환경에 미치는 영향을 실시간으로 관찰할 수 있게 해줘요. 

실제로 TypeScript 커뮤니티에서도 작은 범위의 점진적 배포 전략이 운영 리스크를 크게 낮춘다고 강조합니다. [TypeScript Handbook](https://www.typescriptlang.org/docs/handbook/intro.html)에서도 이 점진적 배포가 안정적인 기능 추가에 핵심이라고 하죠.


## 실패 유형을 초기에 계측하는 게 왜 그렇게 중요한가?

우리 팀도 한때 장애 대응이 너무 느려서 고생한 적이 있어요. 근데 실패 유형을 초기에 잘 계측해두면 유지보수성도 좋아지고 장애 대응 속도도 확실히 빨라집니다. 예를 들어, API 호출 실패가 단순 네트워크 문제인지, 아니면 인증 토큰 만료인지, 혹은 이미지 스캔에서 발견된 취약점 때문인지 정확히 구분할 수 있어야 하죠.

Kusari가 CNCF와 협력하면서 이 부분에 집중하는 이유도 여기에 있습니다. 공급망 내에서 발생할 수 있는 다양한 실패 시나리오를 미리 정의하고, 이를 자동으로 감지 및 분류하는 것이죠.

TypeScript 5.x 릴리즈 노트에서도 실패 유형을 초기부터 계측하는 것이 유지보수성과 장애 대응 속도를 개선하는 핵심이라고 강조합니다. [TypeScript 5.x Release Notes](https://devblogs.microsoft.com/typescript/announcing-typescript-5-4/) 참고하세요.


## 실제로 백엔드에서 Kusari를 활용해 공급망 보안을 강화하는 방법

Kusari는 CNCF 프로젝트들과 연동해 소프트웨어 공급망의 취약점을 탐지하고, 악성코드 삽입을 막는 데 도움을 줍니다. 예를 들어, CI/CD 파이프라인에 Kusari 스캔을 추가하면, 컨테이너 이미지 빌드 단계에서부터 보안 검증을 자동화할 수 있어요.

아래는 GitHub Actions 워크플로우에 Kusari 스캔을 넣는 간단한 예시입니다.

```yaml
name: CI
on:
  push:
    branches: [ main ]

jobs:
  build-and-scan:
    runs-on: ubuntu-latest

    steps:
    - name: Checkout code
      uses: actions/checkout@v3

    - name: Build Docker image
      run: |
        docker build -t myapp:latest .

    - name: Run Kusari scan
      run: |
        kusari scan --image myapp:latest --policy ./kusari-policy.yaml
```

위 예시에서 `kusari scan` 명령어는 이미지 내 알려진 취약점, 불필요한 권한, 의심스러운 파일 등을 검사합니다. 정책 파일(`kusari-policy.yaml`)로 허용/차단 기준을 세밀하게 조정할 수 있죠.

이렇게 하면 배포 전에 보안 리스크를 자동으로 걸러낼 수 있어서, 운영 환경에 악성 이미지가 올라가는 걸 원천 차단할 수 있습니다.


## 공급망 보안 강화, 운영팀과 백엔드팀이 꼭 맞춰야 하는 이유

보안은 결국 사람과 프로세스 문제입니다. Kusari 같은 도구를 도입해도, 운영팀과 백엔드팀이 협업하지 않으면 효과가 반감돼요. 예를 들어, 보안 스캔에서 발견된 문제를 누가 언제 어떻게 해결할지 명확한 책임 소재가 필요합니다.

또한, 신규 기능을 점진적으로 배포하면서 발생하는 문제를 빠르게 감지하려면, 실패 유형을 정확히 정의하고 로그와 모니터링 체계를 공유하는 게 필수입니다.

우리 팀에서는 매주 보안 스탠드업 미팅을 만들어서, 공급망 보안 이슈와 배포 현황을 함께 점검하는 문화를 만들었어요. 이게 생각보다 효과가 크더라고요.


## 마무리하며: 공급망 보안, 그냥 도구만 도입한다고 끝나는 게 아니다

CNCF와 Kusari의 협력은 클라우드 네이티브 생태계에 큰 전환점이 될 겁니다. 하지만 이걸 우리 실무에 적용하려면 단순히 도구 설치만으로는 부족해요. 점진적 배포 전략, 실패 유형 계측, 팀 간 협업 문화까지 모두 같이 가야 하죠.

한 가지 팁을 드리자면, 처음부터 모든 걸 완벽하게 하려 하지 말고, 작은 범위부터 시작해 점진적으로 확장하세요. 그리고 실패 데이터를 꾸준히 모으고 분석하는 습관을 들이면, 보안뿐 아니라 전체 서비스 품질도 자연스레 올라갑니다.
