## 전자잉크 UI, 왜 이렇게 다르게 접근해야 할까?

얼마 전 전자책 단말기 프로젝트에 참여하면서 전자잉크(e-ink) UI 개발이 얼마나 까다로운지 새삼 깨달았어요. 일반 LCD나 OLED 화면과는 완전히 다른 특성을 지니고 있어서, 기존 프론트엔드 개발 방식 그대로 적용하면 성능 저하나 사용자 경험 문제로 고생하기 십상이더라고요.

전자잉크는 화면 갱신 속도가 느리고, 잔상이 남는 특성 때문에 UI를 설계할 때부터 ‘최소한의 화면 리프레시’와 ‘효율적인 업데이트 전략’을 세워야 합니다. 예를 들어, 1초에 60프레임을 뽑는 게 아니라, 1초에 1~2번만 화면을 갱신하는 게 정상일 정도죠.

이번 글에서는 제가 실제 프로젝트에서 겪은 시행착오와 그걸 극복하기 위해 적용한 실전 관례들을 공유해볼게요. 전자잉크 UI 개발에 뛰어들 예정이거나 고민 중인 동료분들께 조금이나마 도움이 되길 바랍니다.

## 전자잉크 UI에서 화면 갱신을 최소화하는 게 왜 중요한가?

전자잉크 디스플레이는 전력 소모가 적고 눈에 부담이 적다는 장점이 있지만, 화면을 바꾸는 데 걸리는 시간이 일반 디스플레이보다 훨씬 깁니다. 보통 한 번 화면을 전환하는 데 300~500ms 정도 걸리는데, 이게 누적되면 UI가 답답해지고, 잔상(ghosting) 현상도 심해져 사용자 경험이 급격히 떨어져요.

그래서 전자잉크 UI 개발에서는 ‘변경이 필요한 영역만 부분적으로 업데이트’하거나 ‘화면 전체를 자주 리프레시하지 않는’ 전략이 필수입니다. 예를 들어, 전자책 페이지를 넘길 때는 전체 화면을 새로 그려야 하지만, 시계 앱처럼 초 단위로 변하는 UI는 초침만 부분적으로 갱신하는 식으로요.

실제로 저희 팀은 페이지 전환 시 전체 리프레시를 1초에 1회로 제한했고, 부분 갱신은 5초에 1회 이하로 유지하는 정책을 세웠는데, 이게 사용자 만족도를 크게 올렸습니다.

## 전자잉크 UI에서 자주 쓰는 최적화 패턴들

### 1. 더티 렉트(Dirty Rect) 업데이트

화면 전체를 다시 그리는 대신 변경된 영역만 다시 그리는 기법입니다. 예를 들어, 화면 오른쪽 상단에 알림 아이콘이 바뀌었다면 그 부분만 다시 그리는 거죠. 이렇게 하면 불필요한 리프레시를 줄일 수 있어요.

```javascript
// React 기반 전자잉크 UI 예시
function DirtyRectUpdater({ dirtyRegion, children }) {
  useEffect(() => {
    if (dirtyRegion) {
      // e-ink 디스플레이 API를 호출해 dirtyRegion 부분만 다시 그리기
      window.eInkAPI.refreshRegion(dirtyRegion);
    }
  }, [dirtyRegion]);

  return <>{children}</>;
}
```

이 코드는 변경된 영역(dirtyRegion)만 e-ink API를 통해 갱신하는 예시입니다. 실제로는 디스플레이 드라이버와 긴밀히 연동해야 해요.

### 2. 프레임 제한 및 배치 업데이트

전자잉크는 빠른 프레임 업데이트가 불가능하니, UI 상태 변화가 잦을 때는 이벤트를 모아서 일정 주기로 한꺼번에 화면을 갱신하는 게 좋습니다. 예를 들어, 500ms 단위로 상태 변화를 모아 화면을 한 번만 업데이트하는 식이죠.

```javascript
let pendingUpdate = false;
let dirtyRegion = null;

function scheduleUpdate(region) {
  dirtyRegion = dirtyRegion ? mergeRegions(dirtyRegion, region) : region;

  if (!pendingUpdate) {
    pendingUpdate = true;
    setTimeout(() => {
      window.eInkAPI.refreshRegion(dirtyRegion);
      dirtyRegion = null;
      pendingUpdate = false;
    }, 500); // 500ms 단위 배치 업데이트
  }
}
```

이 코드는 여러 번 발생하는 UI 변경을 500ms 단위로 묶어서 처리하는 예시입니다. 이렇게 하면 불필요한 잦은 화면 리프레시를 막을 수 있어요.

### 3. UI 단순화와 명확한 피드백

전자잉크 특성상 화면 갱신이 느리니, 애니메이션이나 복잡한 트랜지션은 피하는 게 좋습니다. 대신 상태 변화가 명확히 보이도록 큰 글씨, 대비 높은 색상(흑백 대비)으로 UI를 설계해야 해요. 예를 들어, 버튼 클릭 시 즉시 색이 바뀌거나, 로딩 상태를 텍스트로 명확히 알려주는 방식이죠.

## 유지보수성과 장애 대응을 위해 꼭 계측부터 하자

전자잉크 UI는 하드웨어 특성 때문에 예상치 못한 오류가 나기 쉽습니다. 예를 들어, 화면이 제대로 갱신되지 않거나, 부분 리프레시가 실패하는 경우가 있죠. 이런 문제를 빠르게 잡으려면 초기부터 실패 유형을 계측하는 게 필수입니다.

우리 팀은 화면 리프레시 API 호출 성공 여부, 리프레시 시간, 실패 시 재시도 횟수 등을 로그로 남기고, 장애 발생 시 알림을 받도록 했어요. 이 덕분에 문제 재현과 원인 분석이 훨씬 빨라졌습니다.

이런 점은 [Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/)에서 실패 유형 초기 계측이 유지보수성과 장애 대응 속도를 높인다는 점과도 맞닿아 있죠.

## 작은 범위 점진적 배포 전략으로 운영 리스크 줄이기

전자잉크 UI는 하드웨어와 밀접하게 연결되어 있어서, 새 기능이나 UI 변경 시 운영 리스크가 큽니다. 저희는 신규 기능을 한꺼번에 전체 디바이스에 배포하지 않고, 소규모 사용자 그룹에서 점진적으로 배포하는 전략을 썼어요.

예를 들어, 1000대 중 처음 50대에만 배포해 문제 없으면 점차 확대하는 방식입니다. 이렇게 하면 예상치 못한 버그가 전체 사용자에게 퍼지는 걸 막을 수 있어요.

이 방법은 [GitHub Engineering Blog](https://github.blog/category/engineering/)에서도 작은 범위 점진적 배포가 운영 리스크를 낮춘다고 소개한 바 있습니다.

## 전자잉크 UI 개발, 이렇게 시작해보세요

- **화면 리프레시 최소화**: 전체 화면 대신 꼭 필요한 영역만 부분 갱신하세요.
- **배치 업데이트 적용**: UI 변경 이벤트를 모아서 500ms~1초 단위로 묶어 처리하면 성능과 사용자 경험 모두 좋아집니다.
- **단순하고 명확한 UI**: 복잡한 애니메이션은 피하고, 대비 높은 디자인으로 상태 변화를 명확히 보여주세요.
- **장애 계측을 초기부터**: 리프레시 실패 등 주요 이벤트를 로그로 남겨 장애 대응 속도를 높이세요.
- **점진적 배포 전략**: 신규 기능은 소규모 대상부터 배포해 운영 리스크를 줄이세요.

전자잉크 UI는 처음엔 ‘이게 별거 아닌 것 같지만’ 실제로 겪어보면 꽤 까다로운 영역입니다. 하지만 적절한 패턴과 관례를 적용하면 꽤 쾌적하고 유지보수 쉬운 UI를 만들 수 있으니, 꼭 위 팁들을 참고해서 프로젝트에 적용해보시길 바랍니다.
