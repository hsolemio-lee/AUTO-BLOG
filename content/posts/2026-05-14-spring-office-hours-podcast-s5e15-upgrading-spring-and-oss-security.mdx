### "업그레이드하다가 서비스가 멈췄다" 경험, 다들 한 번쯤 있죠?

최근에 우리 팀에서 Spring Boot 2.7에서 3.0으로 마이그레이션하면서 겪은 일입니다. 공식 문서만 꼼꼼히 읽으면 충분할 줄 알았는데, 실제로는 의존성 충돌, Bean 설정 변경, 그리고 보안 컴포넌트 취약점 대응까지 신경 쓸 게 한두 가지가 아니더라고요. 오늘은 이 과정을 겪으면서 깨달은 점과 실무 팁을 공유해보려 합니다.

---

## Spring Boot 업그레이드, 공식 문서만 믿으면 안 되는 이유

Spring Boot Reference Documentation에서는 업그레이드 시 마이그레이션 가이드를 철저히 검토하라고 권장합니다. 실제로 저희도 [공식 문서](https://docs.spring.io/spring-boot/reference/)를 기본으로 삼았지만, 여기서 말하는 "주요 의존성 버전 호환성" 체크를 놓쳤다가 한참 고생했어요.

예를 들어, Spring Boot 3.0부터는 Java 17 이상이 필수인데, 저희 일부 서브모듈이 아직 Java 11을 타겟으로 빌드되고 있었죠. 이걸 몰랐으면 빌드가 깨졌을 겁니다. 그리고 Spring Data, Spring Security 같은 하위 의존성들도 버전 맞춤이 필요합니다.

롤아웃 단계에서는 점진적 배포와 기능 플래그 활용이 정말 중요해요. 저희는 Canary 배포를 통해 전체 트래픽의 10%부터 시작해 50%, 100%로 늘려가면서 모니터링 했습니다. 문제 발생 시 즉시 롤백할 수 있었죠.

---

## Spring Framework 코어 업그레이드, Bean 설정과 라이프사이클 변화에 주목하라

Spring Framework 코어 업그레이드는 단순히 버전만 올리는 게 아닙니다. [Spring Framework 공식 문서](https://docs.spring.io/spring-framework/reference/core.html)에 따르면, 빈(Bean) 설정과 의존성 주입 방식에 미묘한 변화가 있는데요. 특히 새로운 라이프사이클 관리 기능을 활용하면 애플리케이션 안정성을 크게 높일 수 있습니다.

예를 들어, `@PostConstruct` 대신 `SmartLifecycle` 인터페이스를 적극 활용해 빈 초기화 순서를 제어하거나, `@ConfigurationProperties` 바인딩 방식 변경에 따라 설정값을 검증하는 로직을 추가하는 식이죠.

```java
@Component
public class CustomLifecycleBean implements SmartLifecycle {
    private boolean running = false;

    @Override
    public void start() {
        // 초기화 로직
        running = true;
        System.out.println("CustomLifecycleBean started");
    }

    @Override
    public void stop() {
        // 종료 로직
        running = false;
        System.out.println("CustomLifecycleBean stopped");
    }

    @Override
    public boolean isRunning() {
        return running;
    }

    @Override
    public int getPhase() {
        return 0; // 초기화 순서 제어
    }

    @Override
    public boolean isAutoStartup() {
        return true;
    }
}
```

이렇게 하면 복잡한 빈 의존성 사이클에서 초기화 순서를 명확히 할 수 있어, 의도치 않은 NullPointerException이나 초기화 실패를 줄일 수 있습니다.

## 오픈소스 보안 컴포넌트, CVE 자동 스캐닝과 충분한 테스트 없이는 위험하다

보안 패치 적용은 무조건 빨리 해야 하는데, 문제는 프로덕션에 바로 올리면 예상치 못한 부작용이 생길 수 있다는 점입니다. Baeldung의 [Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance) 글에서도 언급했듯, CVE 데이터베이스와 연동된 자동화된 보안 스캐닝 도구를 도입해 취약점을 사전에 탐지하는 게 필수입니다.

저희는 OWASP Dependency-Check를 CI 파이프라인에 넣어, PR 단계에서 취약점 보고서를 받도록 했습니다. 그리고 보안 컴포넌트 버전 업그레이드는 별도의 스테이징 환경에서 실제 부하 테스트와 통합 테스트를 충분히 거친 후 프로덕션에 배포했습니다.

---

## JVM 튜닝과 커넥션 풀 최적화, 그리고 캐싱 전략이 없으면 프로덕션에서 버틴다 장담 못 한다

성능 튜닝은 업그레이드 후 안정적인 운영을 위한 필수 작업입니다. 저희는 JVM 힙 메모리를 2GB에서 4GB로 늘리고, G1 GC 튜너를 기본값으로 사용했습니다. 커넥션 풀은 HikariCP를 쓰는데, 최대 커넥션 수를 50으로 설정해 DB 부하를 조절했죠.

캐싱 전략도 빼놓을 수 없습니다. Redis를 활용해 자주 조회하는 데이터를 캐싱하고, TTL(Time To Live)을 10분으로 설정해 데이터 신선도와 캐시 효율을 적절히 맞췄습니다.

롤아웃 시에는 트래픽을 점진적으로 늘리면서 CPU, 메모리, 응답 시간, 에러율 등을 모니터링했습니다. 이 과정에서 문제가 발견되면 즉시 롤백하거나 설정을 조정했죠.

## 대규모 오픈소스 업그레이드, 블루-그린과 카나리 배포 전략으로 다운타임 없이

GitHub 엔지니어링 블로그에서 소개한 [블루-그린 배포](https://github.blog/category/engineering/)와 카나리 릴리즈 전략은 정말 유용합니다. 저희도 이 방식을 도입해, 새 버전 배포 시 기존 버전과 병행 운영하며 트래픽을 점진적으로 넘겼습니다.

이렇게 하면 문제가 생겨도 즉시 이전 버전으로 롤백할 수 있어 다운타임을 최소화할 수 있습니다. 다만, 인프라 비용이 늘고 운영 복잡도가 올라가는 단점이 있으니, 팀 상황에 맞게 조율해야 합니다.

---

## 마틴 파울러가 강조한 모듈화와 의존성 관리, OSS 업그레이드 리스크 줄이기

마틴 파울러의 아키텍처 가이드([Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/))에서는 모듈화된 아키텍처와 명확한 의존성 관리가 OSS 업그레이드 시 리스크를 크게 줄인다고 합니다.

실제로 저희는 서비스별로 모듈을 분리하고, 각 모듈의 의존성을 엄격히 관리했습니다. 덕분에 특정 모듈만 독립적으로 업그레이드하거나 롤백하는 게 가능해졌죠. 이게 처음엔 귀찮아 보여도, 나중에 업그레이드 실패 시 복구 속도가 확실히 빨라집니다.

### 정리하며

- Spring Boot 업그레이드 전, 공식 문서 마이그레이션 가이드와 의존성 호환성 철저 확인
- Spring Framework 업그레이드 시 Bean 라이프사이클과 의존성 주입 방식 변화 주의
- CVE 자동 스캐닝 도구 도입과 충분한 테스트로 보안 컴포넌트 안정성 확보
- JVM, 커넥션 풀, 캐싱 튜닝 후 점진적 롤아웃과 모니터링 필수
- 블루-그린, 카나리 배포 전략으로 다운타임 최소화 및 빠른 롤백 준비
- 모듈화 아키텍처와 명확한 의존성 관리로 업그레이드 리스크 줄이기

업그레이드는 언제나 긴장되는 작업이지만, 이 과정을 통해 더 안정적이고 빠른 서비스 운영이 가능해집니다. 저도 이번 경험 덕분에 다음 업그레이드는 좀 더 여유롭게 준비할 수 있을 것 같아요. 여러분도 꼭 한 번 차근차근 준비해보시길 바랍니다.
