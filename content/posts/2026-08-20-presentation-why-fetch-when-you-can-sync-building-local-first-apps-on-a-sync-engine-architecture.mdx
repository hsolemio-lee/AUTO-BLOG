## 네트워크가 불안정한데, 왜 굳이 서버에서 데이터를 바로 가져오려고 할까?

최근에 팀에서 로컬 퍼스트 앱을 만들면서 문득 든 생각입니다. 인터넷 연결이 자주 끊기거나 느린 환경에서, 사용자 경험을 포기하지 않고 어떻게 하면 좋을까? 전통적인 fetch 요청 방식은 네트워크 상태에 따라 UI가 멈추거나 오류가 나기 십상이죠. 그래서 우리는 "왜 fetch 대신 sync를 선택해야 할까?"라는 질문에서 출발했습니다.

## 로컬 퍼스트 앱, 클라이언트에 데이터 우선 저장하는 이유

로컬 퍼스트 앱은 말 그대로 데이터를 클라이언트에 우선 저장하고, 네트워크 연결이 가능할 때 백엔드와 동기화하는 방식을 택합니다. 이 방식은 단순히 오프라인 모드를 지원하는 걸 넘어서, 네트워크 지연이 심한 환경에서도 UI 반응 속도를 확실히 개선해 줍니다. 

마틴 파울러가 정리한 소프트웨어 아키텍처 가이드에서도 "로컬 퍼스트 앱은 네트워크 연결이 불안정하거나 오프라인 상태에서도 사용자 경험을 유지하기 위해 클라이언트에 데이터를 우선 저장하고, 이후 백엔드와 동기화하는 방식을 사용한다"고 명확히 언급하고 있죠[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

이게 실제로 겪어보면, fetch로 서버에서 매번 데이터를 받아오는 것보다 사용자 입장에서 훨씬 빠르고 부드럽게 느껴집니다. 물론, 클라이언트 데이터가 서버와 일치하지 않을 수 있다는 점에서 동기화 로직이 복잡해지긴 합니다.

## 동기화 엔진 아키텍처가 어떻게 데이터 일관성을 보장할까?

그렇다면 클라이언트와 서버 데이터가 서로 어긋나지 않게 하려면 어떻게 해야 할까요? 여기서 동기화 엔진 아키텍처가 등장합니다. 이 아키텍처는 변경 사항을 추적하고, 충돌 해결 메커니즘을 내장해서 효율적이고 견고한 데이터 동기화를 지원합니다.

예를 들어, 사용자가 오프라인 상태에서 여러 번 데이터를 수정한 후 다시 온라인이 되었을 때, 서버에 변경 사항을 순차적으로 보내고, 서버에서 변경 충돌이 발생하면 이를 해결하는 로직이 필요합니다. Microsoft 클라우드 디자인 패턴에서도 "동기화 엔진 아키텍처는 클라이언트와 서버 간의 데이터 일관성을 유지하기 위해 변경 사항을 추적하고 충돌 해결 메커니즘을 내장하여, 효율적이고 견고한 데이터 동기화를 지원한다"고 설명합니다[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/).

이 과정에서 이벤트 소싱(event sourcing)과 CQRS 패턴이 큰 역할을 합니다. 이벤트 소싱은 데이터 변경 이력을 이벤트 형태로 저장해 언제든 상태를 재구성할 수 있도록 하고, CQRS는 읽기와 쓰기 작업을 분리해 확장성과 일관성을 동시에 달성합니다. 마틴 파울러의 마이크로서비스 아티클에 자세히 나와 있죠[Martin Fowler - Microservices](https://martinfowler.com/articles/microservices.html).

## 실전에서 쓰는 동기화 엔진, 코드로 보면 이런 느낌

아래는 간단한 이벤트 소싱 기반 동기화 엔진의 핵심 로직 예시입니다. 클라이언트에서 발생한 변경 이벤트를 서버에 보내고, 서버는 이를 이벤트 스토어에 저장한 뒤 상태를 재구성합니다.

```java
// 이벤트 인터페이스
interface Event {
    String getType();
    long getTimestamp();
}

// 간단한 이벤트 구현
class UpdateNameEvent implements Event {
    private final String newName;
    private final long timestamp;

    public UpdateNameEvent(String newName, long timestamp) {
        this.newName = newName;
        this.timestamp = timestamp;
    }

    public String getType() { return "UpdateName"; }
    public long getTimestamp() { return timestamp; }
    public String getNewName() { return newName; }
}

// 이벤트 스토어
class EventStore {
    private final List<Event> events = new ArrayList<>();

    public synchronized void append(Event event) {
        events.add(event);
    }

    public synchronized List<Event> getEvents() {
        return new ArrayList<>(events);
    }
}

// 상태 재구성
class UserProfile {
    private String name = "";

    public void apply(Event event) {
        if (event instanceof UpdateNameEvent) {
            this.name = ((UpdateNameEvent) event).getNewName();
        }
    }

    public void rebuildFromEvents(List<Event> events) {
        for (Event event : events) {
            apply(event);
        }
    }

    public String getName() { return name; }
}

// 사용 예
EventStore store = new EventStore();
UserProfile profile = new UserProfile();

// 클라이언트에서 이름 변경 이벤트 발생
UpdateNameEvent event = new UpdateNameEvent("Alice", System.currentTimeMillis());
store.append(event);

// 서버에서 이벤트를 받아 상태 재구성
profile.rebuildFromEvents(store.getEvents());
System.out.println(profile.getName()); // Alice
```

이 예시는 아주 단순화한 버전이지만, 실제로는 이벤트 버전 관리, 충돌 해결, 동기화 주기 관리 등 훨씬 복잡한 로직이 추가됩니다.

## 운영 환경에서 동기화 주기와 충돌 해결 전략 선택하기

동기화 엔진을 운영하다 보면 "실시간 동기화가 항상 좋은가?"라는 고민이 생깁니다. 실시간 동기화는 사용자 경험을 최적화하지만, 네트워크 비용과 서버 부하가 커집니다. 반대로 주기적 배치 동기화는 부하를 줄이지만, 데이터 일관성 지연이 발생할 수 있죠.

Microsoft 클라우드 디자인 패턴에서는 "운영 트레이드오프로는 실시간 동기화의 복잡성과 비용 대비, 주기적 배치 동기화가 있으며, 애플리케이션 요구사항에 따라 적절한 동기화 주기와 충돌 해결 전략을 선택하는 것이 중요하다"고 조언합니다[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/).

우리 팀도 처음엔 1초 단위 실시간 동기화를 시도했는데, 서버 부하가 급격히 증가해 10초 단위 배치 동기화로 조정했습니다. 이 과정에서 사용자에게 동기화 상태를 알리는 UI 피드백을 넣어, "동기화 중"임을 명확히 보여줌으로써 혼란을 줄였죠.

## 동기화 엔진 도입 후 사용자 경험과 시스템 신뢰성 변화

로컬 퍼스트 아키텍처를 도입하고 나서 가장 크게 느낀 점은 UI 반응 속도가 눈에 띄게 빨라졌다는 겁니다. 네트워크가 불안정해도 사용자는 앱이 멈추지 않고, 데이터를 즉시 수정할 수 있죠. 백엔드에서는 비동기 동기화 덕분에 데이터 신뢰성이 확보되면서도 서버 부하를 조절할 수 있었습니다.

GitHub 엔지니어링 블로그에서도 "로컬 퍼스트 아키텍처는 네트워크 지연과 서버 부하를 줄여 사용자 인터페이스 반응 속도를 개선하며, 동기화 엔진은 비동기적으로 데이터를 백엔드와 교환해 데이터 신뢰성을 확보한다"고 언급한 바 있습니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

하지만, 이 모든 게 마냥 좋은 것만은 아닙니다. 동기화 충돌을 처리하는 로직이 복잡하고, 클라이언트와 서버 간 버전 관리가 까다롭습니다. 또한, 네트워크가 완전히 끊긴 상태에서 너무 오래 작업하면 데이터 불일치가 커질 수 있으니 적절한 동기화 주기 설정과 사용자 안내가 필수입니다.

## 직접 써보니 알게 된 동기화 엔진 아키텍처의 숨은 매력과 한계

처음엔 동기화 엔진이 복잡하고 귀찮아서 그냥 fetch로 서버에서 바로 데이터를 가져오는 게 낫지 않을까 싶었어요. 그런데 실제로 구현해보니, 네트워크 상태에 관계없이 일관된 사용자 경험을 제공한다는 점에서 큰 매력을 느꼈습니다.

단, 동기화 주기를 너무 짧게 잡으면 서버 부하가 급증하고, 너무 길게 잡으면 데이터 불일치가 커져 사용자 혼란이 생깁니다. 그래서 우리 팀은 5~10초 간격으로 배치 동기화를 하면서, 충돌이 발생하면 사용자에게 선택권을 주는 전략을 택했습니다.

또한, 이벤트 소싱과 CQRS를 도입하면서 읽기 성능과 쓰기 일관성 간 균형을 맞출 수 있었는데, 이 부분은 마이크로서비스 아키텍처 설계 경험이 있다면 이해가 빠를 겁니다.

## 마무리하며: 로컬 퍼스트 앱에 동기화 엔진을 도입할 때 꼭 기억할 점

- 네트워크 상태가 불안정한 환경에서 사용자 경험을 우선시하려면 로컬 퍼스트 아키텍처가 답이다.
- 동기화 엔진 아키텍처는 변경 사항 추적과 충돌 해결을 내장해 데이터 일관성을 보장한다.
- 이벤트 소싱과 CQRS를 활용하면 확장성과 일관성을 동시에 잡을 수 있다.
- 실시간 동기화와 주기적 배치 동기화 사이에서 애플리케이션 특성에 맞는 적절한 주기를 선택해야 한다.
- 충돌 해결 로직과 사용자 피드백 UI는 필수로 설계해야 한다.

이런 점들을 염두에 두고 동기화 엔진을 설계하면, fetch 방식에 비해 훨씬 견고하고 사용자 친화적인 로컬 퍼스트 앱을 만들 수 있습니다.
