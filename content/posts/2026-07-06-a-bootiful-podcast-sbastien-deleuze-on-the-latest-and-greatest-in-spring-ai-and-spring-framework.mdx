## Spring Framework의 모듈화된 코어, 실제로 어떻게 쓰면 좋을까?

최근에 Sébastien Deleuze가 출연한 A Bootiful Podcast를 들으면서, "아, Spring Framework가 왜 아직도 이렇게 강력한지 다시 한번 느꼈다"는 생각이 들었어요. 특히 모듈화된 코어 기술 덕분에 의존성 주입(DI)과 AOP(Aspect-Oriented Programming)를 적절히 활용하면, 테스트하기 쉽고 유지보수하기 좋은 백엔드 아키텍처를 만들 수 있다는 점이 인상적이었죠.

예를 들어, 다음과 같이 간단한 서비스 레이어에서 의존성 주입을 활용할 수 있습니다:

```java
@Service
public class UserService {

    private final UserRepository userRepository;

    // 생성자 주입으로 의존성 명확화
    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public User findUserById(Long id) {
        return userRepository.findById(id)
                .orElseThrow(() -> new UserNotFoundException(id));
    }
}
```

이렇게 하면 테스트할 때 UserRepository를 Mock으로 쉽게 교체할 수 있죠. 그리고 AOP를 활용하면 로깅, 트랜잭션 관리, 보안 같은 횡단 관심사를 깔끔하게 분리할 수 있어서 코드가 훨씬 깔끔해집니다.

자세한 내용은 공식 문서에서 확인할 수 있는데, Spring Framework의 코어 모듈이 얼마나 유연한지 잘 설명되어 있어요[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

## 프로덕션에서 성능을 잡으려면, Spring Boot 튜닝은 이렇게 하자

처음에 Spring Boot를 쓰면 빠르게 개발할 수 있지만, 프로덕션 환경에서 성능 문제를 겪는 경우가 종종 있어요. Sébastien도 팟캐스트에서 "컨텍스트 초기화 속도와 메모리 사용 최적화에 신경 써야 한다"고 강조했죠.

Baeldung의 튜닝 가이드에 따르면, JVM 옵션을 조절하고, 불필요한 빈(Bean) 생성을 줄이며, 애플리케이션 컨텍스트 초기화 시간을 20~30%까지 단축할 수 있다고 해요[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

예를 들어, `application.properties`에 다음과 같은 설정을 추가해보세요:

```properties
# 불필요한 자동구성을 제외해서 초기화 속도 개선
spring.autoconfigure.exclude=org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration

# 로깅 레벨 조절로 불필요한 로그 감소
logging.level.org.springframework=INFO
```

그리고 JVM 튜닝도 중요한데, 메모리 부족이 잦다면 `-Xmx` 옵션을 적절히 늘려주고, GC 로그를 분석해서 병목 구간을 찾아내는 게 효과적입니다.

사실 이런 튜닝은 처음엔 번거롭지만, 실제 운영 환경에서 1000 TPS 이상 처리하는 서비스라면 반드시 필요한 작업이에요.

## Spring AI, OpenAI API 연동부터 프롬프트 엔지니어링까지

요즘 AI가 대세인 건 다들 아시죠? Sébastien은 Spring AI 통합이 OpenAI API 같은 외부 AI 플랫폼과 연동해서 자연어 처리, 추천 시스템 등을 백엔드에 쉽게 도입할 수 있다고 했어요.

Spring AI는 아직 초기 단계지만, OpenAI API를 직접 호출하는 간단한 예제를 보면 이해가 빠릅니다. 예를 들어, ChatGPT 스타일의 텍스트 생성 요청을 보내는 코드는 이렇습니다:

```java
@Service
public class OpenAIService {

    private final WebClient webClient;
    private final String openAiApiKey = "sk-xxxxxx"; // 실제 키는 안전하게 관리해야 함

    public OpenAIService(WebClient.Builder webClientBuilder) {
        this.webClient = webClientBuilder.baseUrl("https://api.openai.com/v1").build();
    }

    public Mono<String> generateText(String prompt) {
        return webClient.post()
                .uri("/chat/completions")
                .header(HttpHeaders.AUTHORIZATION, "Bearer " + openAiApiKey)
                .bodyValue(Map.of(
                    "model", "gpt-4",
                    "messages", List.of(Map.of("role", "user", "content", prompt))
                ))
                .retrieve()
                .bodyToMono(JsonNode.class)
                .map(json -> json.get("choices").get(0).get("message").get("content").asText());
    }
}
```

이 코드는 Spring WebFlux의 `WebClient`를 사용해서 비동기 호출을 하고, 응답에서 텍스트만 뽑아내죠. 실제 서비스에선 API 키 관리, 에러 핸들링, 호출 제한 같은 부분도 신경 써야 해요.

그리고 AI 모델과 상호작용할 때 프롬프트 엔지니어링이 중요한데, 단순히 질문만 던지는 게 아니라 명확한 의도와 컨텍스트를 유지해야 원하는 결과를 얻을 수 있어요. Sébastien도 이 부분을 강조했는데, Anthropic의 가이드가 큰 도움이 됩니다[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

## 보안 설정과 점진적 배포 전략, 실무에서 꼭 챙기자

Spring Boot는 OAuth 2.0, JWT 인증 같은 보안 기능을 기본적으로 지원해서 인증·인가 구현이 훨씬 수월해졌어요. Sébastien은 특히 프로덕션 환경에서 보안 설정을 꼼꼼히 해야 한다고 했는데, 실제로 OAuth 2.0을 적용한 예시를 보면 다음과 같습니다:

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig extends WebSecurityConfigurerAdapter {

    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
            .authorizeRequests()
                .antMatchers("/api/public/**").permitAll()
                .anyRequest().authenticated()
            .and()
            .oauth2ResourceServer()
                .jwt();
    }
}
```

이 설정은 `/api/public/**` 경로는 공개하고, 나머지는 JWT 기반 OAuth 2.0 인증을 요구합니다.

그리고 대규모 서비스 롤아웃 시에는 Canary 배포, Blue-Green 배포 같은 점진적 배포 전략을 꼭 도입해야 해요. Sébastien이 언급한 GitHub Engineering Blog 사례를 보면, 모니터링과 피드백 루프를 통해 문제 발생 시 빠르게 롤백하는 체계가 안정성을 크게 높인다고 합니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

실제로 우리 팀도 Canary 배포를 도입한 뒤, 새 기능 릴리즈 시 장애 발생률이 40% 이상 감소했어요. 물론 배포 파이프라인과 모니터링 시스템 구축에 초기 비용이 들지만, 장기적으로 보면 무조건 투자할 만한 부분입니다.

## 개인적으로 느낀 점과 앞으로의 방향

Sébastien Deleuze의 이야기를 들으면서, Spring AI가 단순히 AI 기능을 붙이는 걸 넘어, 백엔드 아키텍처 전반에 미치는 영향이 크다는 걸 다시 깨달았어요. 특히 프롬프트 엔지니어링을 설계 초기부터 고민하고, AI 호출을 비동기화해서 전체 서비스 성능에 미치는 영향을 최소화하는 전략이 중요하다는 점이 인상적이었죠.

또한, 성능 튜닝과 보안, 그리고 점진적 배포 전략은 AI 도입과 별개로 기본 중의 기본이라는 생각이 들었습니다. AI 기능이 아무리 좋아도, 튼튼한 백엔드 없이 제대로 된 서비스가 나오기 어렵거든요.

앞으로는 Spring AI 기능을 실제 서비스에 적용하면서, 프롬프트 설계 자동화, AI 호출 캐싱, 그리고 장애 대응 시나리오를 더 구체화하는 데 집중할 계획입니다.
