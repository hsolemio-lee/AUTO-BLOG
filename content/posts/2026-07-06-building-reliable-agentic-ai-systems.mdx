### "우리 AI 에이전트가 갑자기 멈췄어요" — 그때 알게 된 안정성의 중요성

얼마 전, 프로덕션에서 운영 중이던 AI 에이전트가 갑자기 응답을 멈추는 사고를 겪었어요. 원인은 API 호출 제한 초과와 예외 처리 미흡이었죠. 이 사건을 계기로 에이전트 AI 시스템을 설계할 때 안정성과 확장성을 어떻게 보장할지 진지하게 고민하게 됐습니다. 오늘은 그 과정에서 제가 직접 경험하고 배운 것들을 공유하려고 해요.

## OpenAI API가 알려주는 확장성과 신뢰성의 기본

OpenAI API는 확장성과 안정성을 염두에 둔 설계 덕분에, 다양한 서비스 규모에 맞춰 유연하게 대응할 수 있어요. 예를 들어, 엔드포인트가 여러 개로 나뉘어 있어 특정 모델 버전이나 기능별로 호출을 분리할 수 있죠. 이 덕분에 점진적 마이그레이션도 가능하고, 새 모델 도입 시 기존 시스템과 충돌 없이 운영할 수 있습니다.

저희 팀은 한 프로젝트에서 GPT-3.5에서 GPT-4로 모델을 전환할 때, OpenAI가 제공하는 `model` 파라미터만 바꿔서 쉽게 마이그레이션했어요. 물론, 호출량이 늘면서 API rate limit에 걸리는 일이 잦아졌는데, OpenAI가 제공하는 요청 제한 관련 헤더(`X-RateLimit-Limit`, `X-RateLimit-Remaining`)를 활용해 호출 빈도를 조절하는 로직을 추가했죠.

```python
import requests
import time

API_KEY = "your_openai_api_key"

headers = {"Authorization": f"Bearer {API_KEY}"}

url = "https://api.openai.com/v1/chat/completions"

payload = {
    "model": "gpt-4",
    "messages": [{"role": "user", "content": "안녕하세요, 에이전트 AI 설계에 대해 알려주세요."}]
}

while True:
    response = requests.post(url, headers=headers, json=payload)
    if response.status_code == 429:  # Rate limit exceeded
        print("요청 제한 초과, 10초 대기 후 재시도")
        time.sleep(10)
        continue
    elif response.status_code != 200:
        print(f"오류 발생: {response.status_code} - {response.text}")
        break
    else:
        print(response.json()['choices'][0]['message']['content'])
        break
```

이렇게 간단한 재시도 로직만 넣어도 프로덕션 안정성이 크게 올라갔어요. 물론, 무작정 재시도만 하면 지연시간이 길어질 수 있으니, 점진적 백오프(backoff) 전략을 섞는 게 좋습니다.

[OpenAI API Documentation](https://platform.openai.com/docs/overview)에서 자세한 가이드도 참고할 수 있어요.

## Anthropic Claude의 프롬프트 엔지니어링으로 에이전트 행동 제어하기

AI 에이전트라 하면 "내가 시킨 대로 안 해!" 하는 경우가 많죠. Anthropic의 Claude 모델은 프롬프트 엔지니어링을 통해 이런 문제를 어느 정도 해결할 수 있어요. 프롬프트를 잘 설계하면 에이전트가 수행할 작업의 의도와 범위를 명확히 할 수 있고, 결과적으로 예측 가능성과 유지보수성이 좋아집니다.

저희는 복잡한 업무 자동화 에이전트를 만들 때, 단순히 "이 작업 해줘"가 아니라 "이 작업을 이렇게, 저렇게 순서대로 해줘"라고 명확히 지시하는 프롬프트 템플릿을 만들었어요. 예를 들어, 아래와 같이 작업 단계를 구분해서 프롬프트를 구성합니다.

```
당신은 데이터 처리 에이전트입니다. 아래 지침을 따라 주세요.

1. 입력 데이터를 검증합니다.
2. 이상치가 있으면 보고합니다.
3. 정상 데이터만 다음 단계로 넘깁니다.

입력 데이터: {data}

처리 결과를 JSON 형식으로 출력하세요.
```

이렇게 하면 에이전트가 작업 흐름을 벗어나지 않고, 예외 상황에 대해 명확히 응답할 수 있어 유지보수가 훨씬 수월해졌어요. 물론 프롬프트가 길어질수록 호출 비용과 지연시간이 늘어날 수 있으니, 적절한 균형이 필요합니다.

Anthropic의 공식 문서에서 프롬프트 엔지니어링 전략을 자세히 다루고 있으니 참고해보세요.

[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)

## Cursor 플랫폼으로 모듈화된 AI 에이전트 아키텍처 만들기

AI 시스템이 커질수록 프론트엔드와 백엔드 간 역할 분담이 중요해지는데, Cursor 플랫폼은 이 부분을 모듈화해서 깔끔하게 관리할 수 있게 도와줍니다. 예를 들어, 프론트엔드에서는 사용자 인터페이스와 간단한 상태 관리만 담당하고, 복잡한 AI 로직과 데이터 처리는 백엔드 모듈에서 처리하는 구조죠.

이런 아키텍처 덕분에 다음과 같은 장점이 있었어요:

- 기능별 책임이 명확해져 유지보수가 쉬워짐
- 백엔드 AI 모듈을 교체하거나 확장할 때 프론트엔드 영향 최소화
- 테스트와 배포 자동화가 용이

실제로 Cursor 문서에 따르면, 각 AI 에이전트 모듈은 독립적으로 배포 가능하고, API 계약을 통해 통신하기 때문에 팀 간 협업 생산성이 크게 올라간다고 해요.

[Cursor Documentation](https://docs.cursor.com/)

## 에이전트 코드 실행 환경에서 안전성과 신뢰성 확보하기

AI 에이전트가 코드를 생성하고 실행하는 환경을 만들 때, 의도치 않은 동작이나 보안 이슈가 걱정될 수밖에 없죠. Anthropic의 Claude Code는 이런 문제를 완화하는 안전한 코드 실행 환경을 제공합니다.

우리 팀도 AI가 생성한 코드를 바로 프로덕션에 적용하기 전에 Claude Code 환경에서 먼저 실행해보고, 예상치 못한 오류나 사이드 이펙트를 사전에 잡을 수 있었어요. 특히, 무한 루프나 과도한 자원 사용 같은 문제를 제한하는 정책이 있어 안정적입니다.

이런 접근법은 복잡한 AI 시스템에서 장애를 줄이고, 유지보수 비용을 크게 낮추는 데 효과적이었어요.

[Anthropic - Claude Code Overview](https://docs.anthropic.com/en/docs/claude-code/overview)

## 마이그레이션 시 고려해야 할 현실적인 트레이드오프

새로운 AI 모델이나 API 버전으로 마이그레이션할 때, 무조건 최신 기술만 쫓는 게 능사는 아니더라고요. 저희 경험상 다음과 같은 트레이드오프를 꼭 고려해야 합니다:

- **호환성 문제**: 새 모델이 기존 프롬프트나 파이프라인과 완벽히 맞지 않을 수 있음
- **비용 증가**: 최신 모델은 호출 비용이 더 높고, 호출 빈도에 따라 비용 폭증 가능성
- **성능 변화**: 응답 속도나 지연시간이 달라져 사용자 경험에 영향
- **운영 복잡도**: 다중 버전 운영 시 모니터링과 장애 대응이 더 어려워짐

예를 들어, GPT-4 도입 후 호출 비용이 2배 이상 늘었지만, 정확도와 안정성이 크게 개선돼 결국 투자 대비 효과가 좋았어요. 반면, 너무 잦은 모델 변경은 팀의 혼란만 키우니 분기별이나 반기별 주기로 계획하는 게 좋습니다.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
