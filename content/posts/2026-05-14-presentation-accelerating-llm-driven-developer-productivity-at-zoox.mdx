### "이 자동화, 진짜 개발 생산성에 얼마나 도움 될까?"

최근 Zoox에서 진행한 LLM(대규모 언어 모델) 기반 개발 생산성 가속화 프로젝트를 보면서 이런 생각이 들었어요. 자동화가 많아지면 정말 개발자가 더 편해질까? 아니면 또 다른 관리 포인트만 늘어나는 건 아닐까?

저도 처음엔 비슷한 의문이 있었는데, 실제 Zoox 팀이 겪은 시행착오와 아키텍처 설계, 그리고 운영 노하우를 보면서 꽤 현실적인 해답을 얻었죠. 오늘은 그 이야기를 풀어볼게요.

---

## Zoox가 LLM 자동화에 백엔드 아키텍처를 이렇게 설계한 이유

Zoox는 자율주행차 개발 스타트업인데, 소프트웨어 개발 속도를 올리기 위해 LLM을 적극 활용했어요. 단순히 챗봇처럼 쓰는 게 아니라, 백엔드 시스템에 LLM을 녹여서 반복 작업을 자동화하고, 코드 리뷰나 문서 생성까지 일부 맡기려는 시도였죠.

그런데 여기서 중요한 건 '확장성'과 '운영 안정성'이에요. LLM API 호출이 많아지면 지연 시간이나 장애가 전체 개발 파이프라인에 영향을 줄 수 있거든요. 그래서 Zoox는 마이크로서비스 아키텍처를 도입해 LLM 호출을 별도 서비스로 분리했고, 장애가 발생해도 전체 개발 프로세스가 멈추지 않도록 설계했어요.

이 방식은 GitHub 엔지니어링 블로그에서도 비슷하게 소개되는데, LLM 자동화 도입 시 서비스 확장성과 장애 대응을 위해 마이크로서비스 패턴을 적극 활용하는 걸 권장합니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

---

## 프롬프트 엔지니어링, 이건 진짜 핵심이다

LLM을 백엔드에서 자동화 도구로 쓰려면 결국 '프롬프트'가 핵심이에요. Zoox도 초기에는 단순한 자연어 질문만 던졌는데, 결과가 들쭉날쭉해서 신뢰도가 낮았죠.

그래서 Anthropic의 프롬프트 엔지니어링 가이드를 참고해 명확하고 구조화된 프롬프트를 만들기 시작했어요. 예를 들어, 코드 리뷰 자동화용 프롬프트는 "이 코드를 어떤 기준으로 평가할지"를 구체적으로 명시하고, 출력 형식도 JSON으로 고정하는 식이었죠.

이렇게 하니까 응답 품질이 크게 개선됐고, 자동화 신뢰도가 올라가면서 개발자들이 실제로 쓰기 시작했어요. Anthropic 가이드에 따르면 이런 명확한 프롬프트 설계가 LLM 응답의 일관성과 품질을 크게 높인다고 합니다[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

## 실시간 요청 처리와 캐싱 전략, Zoox가 선택한 방법

LLM 호출은 비용도 비용이지만, 응답 지연 시간이 문제될 때가 많아요. Zoox는 이를 줄이기 위해 Cloudflare가 소개한 실시간 요청 처리와 캐싱 전략을 참고했어요[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

예를 들어, 반복적으로 비슷한 프롬프트가 들어오는 경우, 캐시된 응답을 바로 반환하게 했죠. 캐시 키는 프롬프트 해시값과 모델 버전으로 구성해, 모델이 업데이트되면 자동으로 캐시가 무효화되도록 했어요.

또 API 게이트웨이를 통해 요청을 분산시키고, 백엔드 서비스가 과부하에 걸리지 않도록 큐잉 시스템도 도입했습니다. 이 덕분에 p95 지연시간이 1.2초 이하로 유지됐고, 장애 발생 시에도 빠르게 롤백이 가능했어요.

## 도메인 주도 설계(DDD)와 이벤트 중심 아키텍처가 왜 필요한가

LLM 자동화가 단순한 스크립트 호출이 아니라면, 비즈니스 로직과 데이터 흐름을 체계적으로 관리해야 해요. Zoox는 Martin Fowler의 조언을 따라 DDD와 이벤트 중심 아키텍처를 결합했는데, 이게 꽤 효과적이었어요[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

예를 들어, 코드 리뷰 요청이 들어오면 도메인 이벤트를 발생시키고, 이 이벤트를 처리하는 별도의 마이크로서비스가 LLM API를 호출해 결과를 저장합니다. 이렇게 하면 각 서비스가 독립적으로 확장 가능하고, 장애가 나도 이벤트 재처리로 복구할 수 있죠.

이 구조 덕분에 Zoox는 LLM 자동화 시스템을 점진적으로 확장하면서도 복잡도를 관리할 수 있었어요.

## 실제 코드 예시: LLM 호출을 위한 백엔드 서비스 일부

```python
import hashlib
import json
import requests
from cachetools import TTLCache

# 단순 캐시: 최대 100개, TTL 300초
cache = TTLCache(maxsize=100, ttl=300)

OPENAI_API_KEY = 'your-api-key'
OPENAI_API_URL = 'https://api.openai.com/v1/chat/completions'


def get_cache_key(prompt: str, model: str) -> str:
    key_str = f'{model}:{prompt}'
    return hashlib.sha256(key_str.encode()).hexdigest()


def call_llm_api(prompt: str, model: str = 'gpt-4') -> dict:
    cache_key = get_cache_key(prompt, model)
    if cache_key in cache:
        print('캐시에서 응답 반환')
        return cache[cache_key]

    headers = {
        'Authorization': f'Bearer {OPENAI_API_KEY}',
        'Content-Type': 'application/json'
    }
    data = {
        'model': model,
        'messages': [{'role': 'user', 'content': prompt}],
        'temperature': 0.2
    }

    response = requests.post(OPENAI_API_URL, headers=headers, data=json.dumps(data))
    response.raise_for_status()
    result = response.json()

    cache[cache_key] = result
    return result


# 실제 사용 예
if __name__ == '__main__':
    prompt_text = "Please review this Python function for potential bugs and suggest improvements."
    response = call_llm_api(prompt_text)
    print(json.dumps(response, indent=2))
```

이 코드는 간단한 캐싱과 함께 OpenAI API를 호출하는 예시입니다. Zoox도 이런 식으로 캐싱을 도입해 지연 시간을 줄이고, API 비용을 절감했어요. 물론 캐시 무효화 정책과 에러 핸들링은 더 복잡하게 관리해야 하지만, 기본적인 패턴은 이렇습니다.

## CI/CD와 클라우드 네이티브 기능 활용은 필수

InfoQ에서 강조하는 것처럼, LLM 기반 백엔드 자동화는 단순히 API만 붙이는 게 아니라, 클라우드 네이티브 환경에서 CI/CD 파이프라인을 자동화하고 빠른 피드백 루프를 확보해야 진짜 생산성 향상이 가능해요[InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/).

Zoox도 Kubernetes 위에 마이크로서비스를 배포하고, GitOps 방식으로 LLM 관련 서비스와 프롬프트 템플릿을 관리합니다. 덕분에 프롬프트 변경이나 모델 업데이트가 곧바로 자동화 파이프라인에 반영돼, 개발자가 손쉽게 개선 작업을 할 수 있었죠.

## 마무리하며: LLM 자동화, "이렇게" 준비해야 한다

Zoox 사례에서 배운 점을 정리하면 다음과 같아요:

- **마이크로서비스 분리**로 장애 격리와 확장성 확보
- **명확한 프롬프트 설계**가 자동화 신뢰도의 핵심
- **캐싱과 API 게이트웨이**로 지연 시간과 비용 관리
- **DDD와 이벤트 중심 아키텍처**로 복잡한 비즈니스 로직 분리
- **클라우드 네이티브 CI/CD**로 빠른 피드백과 안정적 배포

처음엔 LLM 자동화가 단순한 신기술처럼 느껴지지만, 실제로는 기존 백엔드 아키텍처 원칙과 운영 노하우를 잘 녹여내야 성공할 수 있다는 걸 알게 됐어요. 여러분도 새로운 프로젝트에 LLM을 도입할 때, Zoox 사례를 참고해 차근차근 준비해보시길 바랍니다.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
