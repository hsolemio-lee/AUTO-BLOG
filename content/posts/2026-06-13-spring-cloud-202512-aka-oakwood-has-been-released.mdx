### "왜 아직도 스프링 클라우드 업그레이드가 두려운가?"

최근 우리 팀에서 Spring Cloud 2025.1.2, 코드네임 Oakwood 버전으로 마이크로서비스를 전면 업그레이드하는 작업을 진행했어요. 처음엔 그냥 버전 하나 올리는 거라 생각했는데, 의존성 충돌부터 JVM 튜닝, 보안 설정까지 챙길 게 한두 가지가 아니더라고요. 여러분도 이런 경험 있지 않나요? 특히 프로덕션 환경에서는 작은 실수 하나가 서비스 중단으로 이어질 수 있어서 조심스럽죠.

이번 글에서는 Oakwood 버전의 주요 변화와 함께, 실제로 프로덕션에 적용하며 겪은 시행착오와 노하우를 공유해 보려고 합니다.

---

## Spring Cloud Oakwood가 왜 주목받는지, 실제로 무엇이 달라졌을까?

Oakwood는 Spring Boot 3.x와 완벽하게 호환되면서 서비스 디스커버리, 구성 관리, 분산 트레이싱 기능을 한층 강화했어요. 특히 내부적으로 리액티브 프로그래밍 지원을 크게 개선해 비동기 처리 성능이 눈에 띄게 향상됐다는 점이 인상적입니다. 덕분에 클라우드 네이티브 환경에서 확장성과 반응성이 더 좋아졌죠[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/), [Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

우리 팀에서는 Eureka 대신 Spring Cloud Discovery Client를 쓰는데, Oakwood에서는 이 부분이 더 안정적이고 가벼워졌어요. 게다가 분산 트레이싱도 Sleuth와 Zipkin 연동이 더 자연스러워져서, 장애 원인 분석이 한결 수월해졌습니다.

---

## 프로덕션에 도입할 때 제일 먼저 체크해야 할 건 의존성 충돌과 JVM 프로파일링

실제로 업그레이드를 하면서 가장 골치 아팠던 게 의존성 문제였어요. Oakwood가 Spring Boot 3.x 기반이라 기존에 쓰던 라이브러리 중 Java 17 이상을 요구하는 게 많더라고요. 그래서 기존 서비스에서 쓰던 하위 호환성 라이브러리를 모두 점검했고, Gradle 의존성 트리도 꼼꼼히 확인했습니다.

그리고 JVM 튜닝도 병행했는데, 메모리 사용량과 CPU 프로파일링을 통해 힙 사이즈를 2GB에서 4GB로 늘리고, G1 GC 옵션을 기본으로 세팅했어요. 특히 `-XX:MaxGCPauseMillis=200` 옵션을 넣어 GC로 인한 지연 시간을 줄인 게 효과적이었습니다. 이런 튜닝 덕분에 서비스가 갑자기 메모리 부족으로 죽는 일이 크게 줄었죠[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

---

## OAuth2와 JWT 인증 통합, 그리고 TLS 암호화 - 보안이 한층 강화된 Oakwood

Oakwood에서 가장 반가웠던 변화 중 하나는 보안 관련 개선입니다. OAuth2 및 JWT 기반 인증이 훨씬 간편해졌고, 기본적으로 서비스 간 통신에 TLS 암호화를 권장하는 정책이 추가됐어요.

우리 팀은 기존에 인증 서버와 리소스 서버를 분리해 운영했는데, Oakwood에서는 `spring-security-oauth2-client`와 `spring-security-oauth2-resource-server` 설정이 더 직관적으로 바뀌어서 설정 난이도가 확실히 낮아졌어요. 예를 들어, 아래처럼 간단하게 JWT 토큰 검증을 설정할 수 있습니다:

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig extends WebSecurityConfigurerAdapter {

    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
            .authorizeRequests()
                .antMatchers("/public/**").permitAll()
                .anyRequest().authenticated()
            .and()
            .oauth2ResourceServer()
                .jwt();
    }

}
```

이 설정만으로도 JWT 토큰 기반 인증이 가능해지고, 서비스 간 통신 시에는 TLS를 기본으로 활성화했어요. 실제로 TLS를 적용하고 나서 네트워크 레벨 공격에 대한 걱정이 줄었고, 내부 감사 로그도 더 깔끔해졌습니다[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

## 서비스 중단 없이 업그레이드하려면? 점진적 배포 전략이 답이다

대규모 마이크로서비스 환경에서 새로운 버전을 한꺼번에 올리는 건 거의 자살행위나 마찬가지죠. 그래서 우리는 Canary Release와 Blue-Green Deployment 전략을 활용했어요. 처음에는 전체 트래픽의 5%만 새 버전으로 돌리고, 모니터링 결과 이상 없으면 점차 50%, 100%로 늘려가는 식이었죠.

이 과정에서 GitHub Engineering Blog에서 소개한 대규모 서비스 배포 모범 사례가 큰 도움이 됐습니다. 특히 롤백 시나리오를 미리 준비해두고, 자동화된 헬스 체크를 통해 이상 징후 발견 즉시 이전 버전으로 복구할 수 있게 한 점이 인상적이었어요[GitHub Engineering Blog](https://github.blog/category/engineering/).

실제로 우리도 한 번 Canary 배포 중 메모리 누수 문제를 발견해 즉시 롤백했는데, 서비스 중단 없이 문제를 해결할 수 있었습니다.

## Oakwood 업그레이드 후, 실제로 달라진 점과 아쉬운 점

### 좋아진 점
- 리액티브 프로그래밍 지원 강화로 비동기 처리 성능 향상
- OAuth2/JWT 인증 설정 간소화 및 TLS 기본 권장으로 보안 강화
- 서비스 디스커버리 및 분산 트레이싱 안정성 향상

### 아쉬운 점
- Java 17 이상과 Spring Boot 3.x 의존성으로 하위 호환성 문제 발생 가능
- JVM 튜닝과 의존성 점검에 예상보다 많은 시간 소요
- TLS 적용 시 초기 설정 복잡도 증가

## 정리하며: Oakwood 도입할 때 꼭 챙겨야 할 3가지

1. **의존성 충돌부터 꼼꼼히!**
   - Gradle/Maven 의존성 트리 확인 필수
   - Java 17 이상 환경에서 테스트 완료

2. **JVM 튜닝은 선택 아닌 필수**
   - 힙 메모리 조정 및 G1 GC 설정 권장
   - 프로파일링 도구로 CPU/메모리 사용량 감시

3. **점진적 배포 전략으로 무중단 전환**
   - Canary Release, Blue-Green Deployment 적극 활용
   - 자동 헬스 체크 및 롤백 시나리오 준비

처음에는 Oakwood 업그레이드가 부담스럽게 느껴질 수 있지만, 제대로 준비하고 단계별로 적용하면 안정성과 보안 모두 챙길 수 있습니다. 우리 팀 경험이 여러분에게도 도움이 되길 바랍니다!
