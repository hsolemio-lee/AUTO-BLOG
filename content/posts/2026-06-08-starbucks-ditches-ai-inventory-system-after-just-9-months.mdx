## 스타벅스 AI 재고 시스템, 왜 9개월 만에 포기했을까?

우리도 한 번쯤은 겪어봤을 법한 상황이다. 대규모 유통망에 AI를 도입해 재고 관리를 자동화하려 했는데, 생각보다 결과가 신통치 않아 결국 철회하는 경우. 스타벅스가 바로 그런 케이스다. 2023년 말 도입한 AI 재고 시스템을 불과 9개월 만에 접었다는 뉴스가 떴다. 이걸 보면서 "우리도 AI 도입할 때 똑같은 함정에 빠지지 않으려면 어떻게 해야 할까?"라는 생각이 들었다.

스타벅스 사례는 단순히 "AI가 아직 준비 안 됐다"는 수준을 넘어, 실제 운영 환경에서 AI와 기존 SCM 시스템이 어떻게 충돌하는지, 그리고 그걸 어떻게 대비해야 하는지에 대한 좋은 교훈을 준다.


## AI SCM 통합, 기존 시스템과 어떻게 맞춰야 할까?

공급망 관리 시스템은 이미 Microsoft Dynamics 365, Oracle SCM, SAP SCM 같은 복잡하고 안정적인 소프트웨어들이 시장을 장악하고 있다. 이런 시스템에 AI를 덧붙이는 건 마치 오래된 기계에 새로운 부품을 끼우는 것과 같다. 잘 맞아야 하는데, 그렇지 않으면 전체 기계가 멈춰버린다.

Microsoft Dynamics 365 SCM 문서에 따르면, AI 통합 시 기존 SCM 소프트웨어와의 긴밀한 연동과 안정성 보장이 필수적이다. AI가 예측을 잘못하면 재고 과잉 혹은 부족이 발생해 공급망 전체가 흔들릴 수 있기 때문이다[Microsoft Learn - Dynamics 365 Supply Chain Management](https://learn.microsoft.com/en-us/dynamics365/supply-chain/).

즉, AI가 단독으로 작동하는 게 아니라 기존 SCM 데이터와 실시간으로 교환하며, 오류 발생 시 즉시 fallback할 수 있는 구조가 필요하다. 스타벅스의 실패 사례를 보면, 아마 이런 fallback 전략이 미흡했던 게 큰 원인 중 하나일 가능성이 크다.


## AI 예측 정확도와 실시간 데이터 반영, 균형 잡기가 관건

Oracle의 클라우드 SCM 문서에서는 AI 모델의 예측 정확도와 실시간 재고 데이터 반영 속도 간 균형을 맞추는 게 얼마나 중요한지 강조한다. AI가 아무리 똑똑해도 최신 재고 상태가 반영 안 되면 예측 자체가 무용지물이 된다[Oracle Docs - SCM and Manufacturing](https://docs.oracle.com/en/cloud/saas/supply-chain-and-manufacturing/).

실제로 스타벅스의 AI 시스템도 실시간 데이터 반영이 늦거나, 예상치 못한 운영 변수(예: 매장별 고객 유동성, 지역별 날씨 변화 등)를 반영하지 못해 예측 오차가 커졌을 가능성이 크다. 이런 경우, 재고 부족으로 고객 불만이 생기고, 과잉 재고로 비용이 증가하면서 결국 시스템 신뢰도가 떨어진다.

이걸 막으려면 AI 모델을 단순히 학습시키고 끝내는 게 아니라, 운영 환경에서 지속적으로 피드백 받고 보정하는 루프가 반드시 필요하다.


## AI 실패에도 서비스가 멈추지 않도록 백엔드와 프론트엔드에서 대비해야 한다

GitHub 엔지니어링 블로그에서 다룬 AI 시스템 빠른 롤백 사례들을 보면, AI 모델 불안정성뿐 아니라 사용자 경험 미흡도 큰 문제였다. AI가 갑자기 응답을 못 하거나 이상한 결과를 내면, 백엔드가 이를 감지하고 즉시 기존 SCM 시스템으로 전환하는 fallback이 필수다[GitHub Engineering Blog](https://github.blog/category/engineering/).

특히 Spring 기반 백엔드에서는 다음과 같은 방식으로 AI 호출을 래핑해 장애 시 자동으로 기존 로직을 사용하도록 할 수 있다.

```java
@RestController
public class InventoryController {

    private final AIInventoryService aiService;
    private final LegacyInventoryService legacyService;

    public InventoryController(AIInventoryService aiService, LegacyInventoryService legacyService) {
        this.aiService = aiService;
        this.legacyService = legacyService;
    }

    @GetMapping("/inventory/predict")
    public ResponseEntity<InventoryPrediction> getInventoryPrediction(@RequestParam String productId) {
        try {
            InventoryPrediction prediction = aiService.predictInventory(productId);
            if (prediction == null || !prediction.isValid()) {
                throw new RuntimeException("Invalid AI prediction");
            }
            return ResponseEntity.ok(prediction);
        } catch (Exception e) {
            // AI 실패 시 기존 시스템 fallback
            InventoryPrediction fallbackPrediction = legacyService.getInventoryPrediction(productId);
            return ResponseEntity.ok(fallbackPrediction);
        }
    }
}
```

이처럼 AI 호출 부분을 try-catch로 감싸고, 실패 시 기존 시스템 결과를 반환하는 패턴은 운영 중 장애가 발생해도 서비스가 멈추지 않도록 하는 기본 중의 기본이다.

프론트엔드에서도 AI 결과가 늦거나 오류가 나면 사용자에게 적절히 안내하고, 기존 데이터를 보여주는 UX 설계가 필요하다. 스타벅스 사례에서 이런 부분이 부족했다면 현장 매장 직원이나 고객이 혼란을 겪었을 가능성이 크다.


## 프롬프트 엔지니어링과 API 최적화가 AI 성능 좌우한다

AI를 SCM에 통합할 때 흔히 간과하는 게 바로 프롬프트 설계와 API 호출 최적화다. OpenAI와 Anthropic의 최신 문서에 따르면, 정확한 프롬프트를 설계하는 게 AI 모델의 신뢰성과 반응속도를 결정짓는다[OpenAI API Documentation](https://platform.openai.com/docs/overview), [Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

예를 들어, 재고 예측을 요청할 때 단순히 "재고 예측해줘"라고 하면 AI가 막연하게 답할 수밖에 없다. 대신 "제품ID와 최근 3개월 판매량, 현재 재고량을 바탕으로 다음 주 예상 재고량을 95% 신뢰도로 예측해줘"처럼 구체적이고 명확한 프롬프트가 필요하다.

아래는 Java에서 OpenAI API를 호출하는 간단한 예시다. 실제로는 이걸 SCM 데이터와 연동해 실시간으로 호출한다.

```java
OpenAIClient client = new OpenAIClient("API_KEY");

String prompt = "제품ID: 12345, 최근 3개월 판매량: 500개, 현재 재고: 200개. 다음 주 예상 재고량을 95% 신뢰도로 예측해줘.";

ChatCompletionRequest request = ChatCompletionRequest.builder()
    .model("gpt-4")
    .messages(Collections.singletonList(new ChatMessage("user", prompt)))
    .temperature(0.2) // 예측 안정성을 위해 낮게 설정
    .maxTokens(100)
    .build();

ChatCompletionResponse response = client.chatCompletion(request);
String prediction = response.getChoices().get(0).getMessage().getContent();
System.out.println("AI 예측 결과: " + prediction);
```

프롬프트를 잘 설계하고, API 호출 시 temperature, maxTokens 같은 파라미터를 조절해 예측의 일관성과 정확도를 높이는 게 중요하다. 물론 이렇게 하면 비용과 호출 지연이 늘어날 수 있다는 트레이드오프가 있다.


## 클라우드 확장성과 장애 복구 기능을 적극 활용해야 하는 이유

SAP SCM 문서에서는 클라우드 플랫폼의 확장성과 장애 복구 기능을 적극 활용해야 한다고 명확히 말한다. AI 시스템은 예측 모델 업데이트, 트래픽 급증 등으로 부하가 변동하기 때문에 탄력적인 확장이 필수다. 또한 장애 발생 시 빠른 복구와 데이터 일관성 유지가 공급망 전체 안정성에 직결된다[SAP Help Portal - Supply Chain Management](https://help.sap.com/docs/SAP_SUPPLY_CHAIN_MANAGEMENT).

예를 들어, AWS Lambda나 Azure Functions 같은 서버리스 아키텍처를 활용하면 AI API 호출을 자동으로 스케일링할 수 있고, DynamoDB나 Cosmos DB 같은 분산 DB로 데이터 일관성을 유지할 수 있다. 하지만 이런 구조도 설계가 복잡하고 비용 관리가 까다로운 단점이 있다.


## 마치며: 스타벅스 사례가 우리에게 던지는 질문들

- AI SCM 통합 시 기존 시스템과 얼마나 긴밀하게 연동하고 있나?
- AI 예측 오류나 지연에 대비한 fallback 전략은 충분히 준비되어 있나?
- AI 프롬프트와 API 호출은 최적화되어 신뢰성 높은 결과를 내고 있나?
- 클라우드 확장성과 장애 복구 기능을 적극 활용하고 있나?

스타벅스가 9개월 만에 AI 재고 시스템을 접은 건 단순히 기술 부족이 아니라, 운영 환경에서 AI와 SCM 시스템이 어떻게 조화를 이루어야 하는지에 대한 현실적인 경고다. 우리도 비슷한 시도를 할 때는 이 점들을 꼭 기억해야 한다.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
