## 페이지 전환이 느릴 때, Navigation API가 답일까?

“왜 우리 앱에서 페이지 전환할 때마다 깜빡임이 심하지?”

이 질문, 프론트엔드 개발자라면 한 번쯤은 꼭 마주하게 되는 고민입니다. SPA를 쓰더라도 네비게이션 처리 로직이 복잡해지고, 데이터 페칭과 상태 관리가 엉키면 사용자 경험이 뚝 떨어지죠. 그런데 최근에 나온 Navigation API가 이 문제를 꽤 깔끔하게 해결해준다는 이야기를 듣고 직접 써봤습니다.

이번 글은 제가 Navigation API를 실제 프로젝트에 도입하면서 느낀 점과, 어떻게 하면 기존 history API보다 더 직관적이고 성능 좋은 네비게이션을 구현할 수 있는지 공유하려고 해요.


## Navigation API, 기존 history API와 뭐가 다른가?

사실 history API는 꽤 오래전부터 있었고, SPA 라우팅의 기본이었죠. 하지만 직접 써보면 이벤트 핸들링이 번거롭고, 네비게이션 상태를 세밀하게 제어하기 어렵다는 단점이 있습니다. 예를 들어, 뒤로 가기 버튼을 누를 때마다 페이지 상태를 일일이 관리해줘야 해서 코드가 복잡해지곤 하죠.

최신 Navigation API는 브라우저가 네비게이션 이벤트를 더 세밀하게 제어할 수 있게 설계됐습니다. `navigate` 이벤트를 중심으로 사용자의 네비게이션 의도를 잡아내고, 비동기 작업과 상태 업데이트를 자연스럽게 연결할 수 있죠. 덕분에 페이지 전환 시 깜빡임 없이 필요한 데이터만 바꾸거나, 심지어 페이지를 새로 로드하지 않고도 콘텐츠를 업데이트할 수 있습니다.

GitHub 엔지니어링 팀도 이 API를 도입하면서 라우팅 처리 과정을 크게 단순화했다고 하네요. 기존에는 복잡한 라우팅 로직과 상태 동기화에 골머리를 앓았지만, Navigation API 덕분에 코드가 훨씬 깔끔해졌다고 합니다[GitHub Engineering Blog](https://github.blog/category/engineering/).


## Cloudflare 사례로 본 Navigation API의 실전 효과

Cloudflare 엔지니어링 팀은 Navigation API를 활용해 서버와 클라이언트 간 네비게이션 상태 동기화를 최적화했습니다. 예를 들어, 사용자가 페이지를 이동할 때마다 전체 페이지를 다시 로드하는 대신, 필요한 데이터만 비동기로 받아서 렌더링하는 방식을 썼죠. 이렇게 하니 네트워크 지연이 눈에 띄게 줄고, 사용자 경험이 훨씬 부드러워졌다고 합니다.

이 과정에서 Navigation API의 `navigate` 이벤트를 적극 활용해 네비게이션 흐름을 제어했고, 비동기 데이터 페칭과 상태 관리를 자연스럽게 결합할 수 있었다고 해요. 덕분에 코드 복잡도는 줄면서도 유지보수성은 오히려 올라갔다는 점이 인상적입니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).


## 직접 써본 Navigation API 기본 사용법

아래는 Navigation API에서 가장 핵심인 `navigate` 이벤트를 활용해, 사용자가 링크를 클릭하거나 뒤로 가기 버튼을 눌렀을 때 네비게이션을 제어하는 간단한 예제입니다.

```javascript
if ('navigation' in window) {
  navigation.addEventListener('navigate', event => {
    event.intercept({
      async handler() {
        // 예: 비동기 데이터 페칭
        const response = await fetch(event.destination.url);
        const html = await response.text();

        // 페이지 콘텐츠를 동적으로 업데이트
        document.getElementById('app').innerHTML = html;

        // 히스토리 상태도 자동으로 관리됨
      }
    });
  });
} else {
  // fallback: 기존 history API 사용
  window.addEventListener('popstate', () => {
    // 기존 라우팅 처리
  });
}
```

이 코드는 사용자가 네비게이션을 시도할 때 브라우저가 이를 가로채서, 전체 페이지를 새로고침하지 않고도 필요한 데이터를 비동기로 받아와서 화면을 업데이트합니다. 기존에 SPA에서 복잡하게 관리하던 히스토리 상태도 Navigation API가 알아서 처리해줘서 개발자가 신경 쓸 부분이 줄어들죠.


## Navigation API 도입하면서 겪은 의외의 함정들

처음에는 이 API가 너무 만능처럼 느껴졌는데, 실제로 써보면 몇 가지 주의할 점도 있습니다.

- **브라우저 지원 문제**: 아직 모든 브라우저에서 완벽히 지원하지 않아요. 특히 구형 브라우저나 일부 모바일 환경에서는 fallback 처리가 필수입니다.

- **복잡한 상태 관리**: 네비게이션 자체는 쉽게 제어되지만, 페이지 내부 상태가 복잡하면 여전히 별도의 상태 관리 라이브러리와 결합해야 합니다.

- **SEO 고려**: SPA처럼 동작하지만, 서버 사이드 렌더링(SSR)과 조합할 때는 네비게이션 이벤트가 SEO에 미치는 영향도 신경 써야 합니다.

- **비동기 처리 타이밍**: `navigate` 이벤트 핸들러 내에서 비동기 작업이 길어지면 사용자 경험이 오히려 나빠질 수 있으니, 로딩 상태 표시 등의 UX 보완이 필요합니다.


## Navigation API를 도입할 때 꼭 기억해야 할 점

- **이벤트 기반 네비게이션 관리가 핵심**: `navigate` 이벤트를 활용해 네비게이션 흐름을 완전히 제어할 수 있다는 점을 이해하세요.

- **비동기 데이터 페칭과 결합하면 효과 극대화**: 필요할 때만 데이터를 가져와서 화면을 업데이트하는 패턴을 만들면, 네트워크 비용과 렌더링 비용을 줄일 수 있습니다.

- **기존 history API와 병행 지원 필수**: 아직은 완전한 대체제가 아니므로, fallback 로직을 꼭 구현해야 합니다.

- **상태 관리 전략과 함께 설계**: Navigation API가 네비게이션 이벤트를 다루지만, 앱 상태 관리는 별도로 고민해야 합니다.


## 마무리하며: 내 프로젝트에 Navigation API가 맞을까?

처음엔 "이게 별거 아닌 것 같은데?" 했던 게, 직접 써보니 SPA에서 네비게이션 처리 로직이 얼마나 깔끔해질 수 있는지 체감할 수 있었습니다. 특히 사용자 경험 측면에서 페이지 전환 시 깜빡임이 줄고, 필요한 데이터만 빠르게 불러오는 게 큰 장점이었어요.

하지만 아직은 브라우저 지원과 복잡한 상태 관리 문제 때문에, 모든 프로젝트에 무조건 도입하긴 어렵습니다. 대신 점진적으로 도입하면서 기존 라우팅과 병행해보는 걸 추천합니다. 

실제 코드도 간단하고, GitHub과 Cloudflare 같은 대형 서비스가 이미 도입해 효과를 보고 있으니, 앞으로 프론트엔드 네비게이션의 표준으로 자리잡을 가능성이 큽니다.
