### AI가 이메일을 대신 쓴다? 그럼 어떻게 설계해야 할까?

"우리 이메일 시스템이 AI와 직접 대화해서 알아서 답장도 하고, 일정도 조율하고, 심지어는 고객 문의도 처리할 수 있다면?" 이런 생각은 한때 먼 미래 같았는데, 요즘은 꽤 현실적인 얘기가 됐죠. 그런데 막상 agentic 이메일 시스템을 만들려고 보면, AI 모델 통합부터 API 호출 안정성, 사용자 경험을 위한 실시간 처리, 그리고 운영 중 마이그레이션까지 생각보다 까다로운 문제들이 한가득입니다.

제가 직접 agentic 이메일 프로젝트를 진행하면서 경험한 내용과 고민들을 공유하려고 해요. 특히 AI와 API 통합, 프롬프트 설계, 비동기 처리, 서버리스 배포, 그리고 마이그레이션 전략에 대해 실제 숫자와 코드 예시를 곁들여 풀어볼게요.

## AI 모델과 OpenAI API 통합, 안정성과 확장성은 어떻게 챙겼나

agentic 이메일에서 AI가 핵심 역할을 하다 보니, OpenAI API 같은 외부 AI 서비스와의 통합이 가장 먼저 부딪히는 벽입니다. API 호출이 실패하거나 지연되면 사용자 경험이 바로 무너지고, 대량 트래픽을 감당하지 못하면 서비스가 불안정해지죠.

OpenAI API 문서에 따르면 인증은 Bearer 토큰 방식으로, 요청 제한(rate limiting)이 엄격히 적용됩니다. 우리 팀은 초당 20건 요청 제한을 넘지 않도록 큐잉 시스템을 도입했고, 실패 시 자동 재시도(backoff) 로직도 넣었어요. 예를 들어, 아래처럼 axios 인터셉터로 재시도 로직을 구현했습니다:

```javascript
import axios from 'axios';

const apiClient = axios.create({
  baseURL: 'https://api.openai.com/v1',
  headers: { Authorization: `Bearer ${process.env.OPENAI_API_KEY}` },
  timeout: 5000,
});

// 재시도 인터셉터
apiClient.interceptors.response.use(null, async error => {
  const config = error.config;
  if (!config || config._retry) return Promise.reject(error);

  config._retry = true;
  await new Promise(res => setTimeout(res, 1000)); // 1초 대기 후 재시도
  return apiClient(config);
});

export default apiClient;
```

이렇게 하면 일시적인 네트워크 문제나 API 제한 초과 시에도 자동으로 복구하는 효과가 있었어요. 그리고 응답을 캐싱해서 같은 질문에 대해 반복 호출을 줄인 것도 큰 도움이 됐죠.

무엇보다 API 호출 시 동시성(concurrency) 조절이 중요했습니다. OpenAI 문서가 권장하는 최대 동시 호출 수를 5로 제한해, 서버 부하와 API 제한에 안전하게 대응했어요[OpenAI API Documentation](https://platform.openai.com/docs/overview).


## 프롬프트 설계가 AI 의도 파악과 행동 유도에 미치는 영향

agentic 이메일에서 AI가 제대로 행동하려면 프롬프트 설계가 생명입니다. Anthropic의 프롬프트 엔지니어링 가이드를 참고해, 단순 질문-응답을 넘어서 AI가 의도를 명확히 이해하고 적절한 행동을 유도하도록 설계했습니다.

예를 들어, 고객이 "이번 주 금요일 회의 일정 변경 가능할까요?"라고 물으면 AI가 단순 답변 대신 캘린더 API 호출을 유도하는 식이죠. 프롬프트 내부에 "고객 문의에 대해 가능한 행동을 제안하고, 필요 시 외부 API를 호출하라"는 명시적 지시를 넣었습니다.

프롬프트 예시:

```
You are an intelligent email assistant. When the user asks about scheduling, check the calendar and propose new times if needed. If unsure, ask clarifying questions.

User: "Can we move the meeting on Friday?"
Assistant:
```

이런 방식으로 프롬프트를 짰더니 AI가 더 정확하게 의도를 파악하고, 불필요한 반복 질문 없이 바로 행동을 제안하는 빈도가 30% 이상 증가했어요. 사용자 신뢰도도 덩달아 올라갔죠.

하지만 프롬프트가 너무 길거나 복잡하면 응답 속도가 느려지고, AI가 혼란스러워하는 경우도 있었습니다. 그래서 핵심 행동 지시만 간결하게 유지하는 게 중요해요[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).


## 실시간 인터랙션 지연 최소화, 비동기 처리와 상태 관리 최적화

agentic 이메일 시스템은 사용자와 AI 간 실시간 대화가 핵심입니다. Cursor 문서에 나와 있듯, AI 응답 지연이 길어지면 사용자 경험이 크게 떨어집니다. 우리 팀도 여기서 고생했는데, 결국 비동기 처리와 상태 관리에 집중해서 문제를 해결했어요.

백엔드에서는 API 호출을 비동기로 처리하고, 프론트엔드에서는 React Query 같은 상태 관리 라이브러리로 응답 상태를 관리했습니다. 이렇게 하면 사용자는 AI가 답변을 준비하는 동안에도 UI가 멈추지 않고, 로딩 상태를 직관적으로 볼 수 있죠.

예를 들어, React Query를 활용한 간단한 코드:

```jsx
import { useQuery } from 'react-query';

function useAgenticEmailResponse(userInput) {
  return useQuery(['agenticEmail', userInput], () =>
    fetch('/api/agentic-email', {
      method: 'POST',
      body: JSON.stringify({ prompt: userInput }),
    }).then(res => res.json())
  , {
    staleTime: 10000, // 10초간 캐싱
    retry: 2,
  });
}

function EmailChat() {
  const [input, setInput] = React.useState('');
  const { data, isLoading, error } = useAgenticEmailResponse(input);

  return (
    <div>
      <input value={input} onChange={e => setInput(e.target.value)} />
      {isLoading && <p>AI가 답변을 준비 중입니다...</p>}
      {error && <p>문제가 발생했습니다.</p>}
      {data && <p>AI 답변: {data.reply}</p>}
    </div>
  );
}
```

이렇게 하니 사용자 인터랙션이 훨씬 부드러워졌고, AI 응답 지연으로 인한 불만도 크게 줄었어요[Cursor Documentation](https://docs.cursor.com/).


## 서버리스 아키텍처로 마이그레이션하면서 겪은 현실적인 문제들

agentic 이메일 시스템을 기존 VM 기반 서비스에서 Vercel AI SDK를 이용한 서버리스 환경으로 옮길 때, 기대보다 복잡한 문제들이 많았습니다. 서버리스는 확장성과 유지보수성 측면에서 매력적이지만, cold start 지연, 상태 관리, 그리고 마이그레이션 다운타임 최소화가 골칫거리였죠.

우선 cold start 문제를 완화하기 위해, Vercel의 서버리스 함수에 대해 요청이 없을 때도 5분마다 ping을 보내는 '워밍업' 전략을 썼습니다. 덕분에 사용자 요청 시 평균 응답 시간이 300ms 이하로 유지됐어요.

마이그레이션은 단계별로 진행했습니다. 기존 시스템과 서버리스 시스템을 병렬 운영하면서 트래픽을 점진적으로 이전했죠. 이 과정에서 데이터 동기화 문제를 피하기 위해 이메일 상태 정보를 Redis를 중앙 캐시로 사용해 공유했습니다.

마지막으로, 서버리스 함수의 타임아웃(기본 10초)을 감안해 AI 호출 로직을 최적화했고, 긴 처리 시간이 필요한 작업은 별도의 비동기 워커로 분리했습니다. 이 덕분에 서버리스 환경에서도 안정적인 운영이 가능했어요[Vercel AI SDK Documentation](https://sdk.vercel.ai/docs/introduction).

### 마치며: agentic 이메일 시스템, 결국은 균형의 문제

agentic 이메일 시스템을 구축하면서 느낀 건, AI 통합부터 프롬프트 설계, 실시간 처리, 서버리스 배포, 마이그레이션까지 모든 게 트레이드오프의 연속이라는 점입니다. 예를 들어, 프롬프트를 복잡하게 하면 정확도가 올라가지만 응답 속도가 느려지고, 서버리스는 확장성이 좋지만 cold start가 발목을 잡죠.

그래서 저는 다음 세 가지를 항상 염두에 두고 있습니다:

- **API 호출 안정성 확보:** 재시도, 큐잉, 캐싱으로 실패율 줄이기
- **프롬프트 간결성 유지:** 핵심 행동만 지시해서 응답 속도와 정확성 균형 맞추기
- **비동기 처리와 상태 관리 최적화:** 사용자 경험 저하 없이 AI와 실시간 인터랙션 지원

이 글이 agentic 이메일 설계와 운영에 대해 고민하는 분들께 조금이나마 도움이 되길 바랍니다.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
