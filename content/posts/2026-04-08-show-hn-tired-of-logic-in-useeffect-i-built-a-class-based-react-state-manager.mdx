### useEffect 안에 로직이 너무 많아진 경험, 다들 있죠?

“이거 왜 이렇게 꼬였지?”

React를 쓰면서 useEffect 훅에 상태 변화, API 호출, 타이머 설정, 이벤트 리스너 등록까지 한꺼번에 몰아넣다 보면 어느 순간 코드가 미궁에 빠집니다. 저도 한참 그렇게 고생했는데, 그때마다 "이걸 더 깔끔하게 관리할 방법은 없을까?" 고민하게 되더라고요.

React 공식 문서에서도 useEffect가 부수 효과(side effects)를 처리하는 데 주로 쓰이지만, 복잡한 상태 관리와 비동기 로직이 섞이면 코드가 난해해지고 유지보수가 어려워질 수 있다고 명시하고 있어요. ([React - Thinking in React](https://react.dev/learn/thinking-in-react))

그래서 저는 직접 클래스 기반의 상태 관리자를 만들어봤습니다. 이번 글에서는 그 과정과 결과, 그리고 느낀 점을 솔직하게 나누려고 해요.

## 왜 useEffect에 모든 걸 몰아넣으면 안 되는 걸까?

처음에는 useEffect 훅 하나로 "컴포넌트가 마운트될 때 API 호출", "특정 상태 바뀔 때 데이터 가공", "타이머 설정" 같은 걸 처리하면 편해 보입니다. 그런데 실제로 프로젝트가 커지고 요구사항이 복잡해지면 문제점이 확 와 닿아요.

- **의존성 배열 관리가 까다로워진다**: 작은 실수로 무한 루프가 돌거나, 반대로 업데이트가 안 되는 버그가 생깁니다.
- **로직이 뒤섞여서 가독성이 떨어진다**: 한 useEffect 안에 여러 역할이 섞이면, 나중에 누가 봐도 무슨 일이 벌어지는지 한눈에 파악하기 어렵죠.
- **테스트하기 어렵다**: 부수 효과가 컴포넌트 안에 깊숙이 박혀있으면 단위 테스트 작성이 까다롭습니다.

이런 문제는 Next.js 최신 App Router 문서에서도 언급하는데요, 상태 관리와 라우팅을 통합하면서 복잡한 상태 변화를 useEffect에 의존하지 않고 컴포넌트 외부에서 관리하는 패턴이 대규모 애플리케이션 유지보수에 훨씬 유리하다고 합니다. ([Next.js App Router Docs](https://nextjs.org/docs/app/building-your-application/routing))

## 클래스 기반 상태 관리, 왜 다시 주목받나?

함수형 컴포넌트와 훅이 대세지만, 의외로 클래스 기반 설계가 상태 관리 복잡도를 줄이는 데 도움이 되는 경우가 있습니다. GitHub Engineering Blog에서도 대규모 프론트엔드 프로젝트에서 클래스 기반 또는 객체지향 설계 패턴을 도입해 useEffect에 의존한 함수형 로직의 복잡도를 완화하는 사례를 소개했어요. ([GitHub Engineering Blog](https://github.blog/category/engineering/))

Martin Fowler도 소프트웨어 아키텍처 가이드에서 명확한 책임 분리와 객체지향적 설계가 유지보수성과 확장성에 핵심이라고 강조하는데, 이 역시 useEffect 복잡도를 줄이기 위한 좋은 힌트입니다. ([Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/))

즉, 상태와 부수 효과를 한데 묶어 클래스로 캡슐화하면, 상태 변화가 언제 어떻게 일어나는지 명확히 추적할 수 있고, 컴포넌트는 그저 상태 관리자에서 제공하는 데이터를 구독만 하면 됩니다.

## 내가 만든 클래스 기반 React 상태 관리자, 어떻게 동작하나?

제가 만든 상태 관리자는 간단히 말해 이런 구조입니다:

- 상태와 상태를 변경하는 메서드를 클래스로 묶음
- 상태 변경 시 구독자(컴포넌트)를 자동으로 업데이트
- useEffect 대신 클래스 내부에서 비동기 로직과 부수 효과 처리

예를 들어, 다음은 카운터 상태 관리자의 핵심 코드입니다:

```jsx
import React, { useState, useEffect } from 'react';

class CounterManager {
  constructor() {
    this.count = 0;
    this.subscribers = new Set();
  }

  subscribe(callback) {
    this.subscribers.add(callback);
    // 초기 상태 전달
    callback(this.count);
    return () => this.subscribers.delete(callback);
  }

  increment() {
    this.count += 1;
    this.notify();
  }

  notify() {
    this.subscribers.forEach(cb => cb(this.count));
  }

  // 비동기 예: 1초 후 자동 증가
  async autoIncrement() {
    await new Promise(r => setTimeout(r, 1000));
    this.increment();
  }
}

const counterManager = new CounterManager();

function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const unsubscribe = counterManager.subscribe(setCount);
    counterManager.autoIncrement();
    return unsubscribe;
  }, []);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => counterManager.increment()}>Increment</button>
    </div>
  );
}

export default Counter;
```

이 코드는 다음과 같은 장점이 있습니다:

- 컴포넌트는 상태 변경 구독과 UI 렌더링에만 집중
- 상태 변경과 부수 효과(자동 증가)는 클래스로 깔끔히 분리
- useEffect 내에 복잡한 의존성 배열 관리가 필요 없음

## 이 방식의 단점과 실제 적용 시 고민거리

물론 클래스 기반 상태 관리가 만능은 아닙니다. 제가 겪은 단점도 솔직히 공유할게요.

- **초기 진입 장벽**: 함수형 훅에 익숙한 팀원에게는 클래스 패턴이 낯설 수 있습니다. 코드 스타일이 혼재하면 오히려 복잡해질 위험도 있어요.
- **추가 추상화 비용**: 상태 클래스가 많아지면 관리해야 할 인스턴스도 많아지고, 상태 간 의존성 관리가 까다로워질 수 있습니다.
- **React 최신 기능과의 충돌 가능성**: React 18 이후 Concurrent Mode나 Suspense 같은 기능과 잘 맞는지 충분히 검증이 필요합니다.

그래서 저는 대규모 상태 변화가 많고, useEffect가 너무 복잡해지는 컴포넌트에만 점진적으로 도입하는 방식을 추천합니다. 모든 컴포넌트에 무작정 적용하기보다는, 문제를 명확히 진단하고 필요한 곳에만 도입하는 게 현실적이에요.

## 실무에서 클래스 기반 상태 관리가 통할까?

저희 팀에서는 최근 Next.js App Router를 도입하면서, 라우팅과 상태 관리를 분리하는 패턴을 적극 활용 중입니다. 이 과정에서 useEffect에 의존한 상태 관리가 한계에 부딪히자, 클래스 기반 상태 관리자를 도입해 유지보수성과 확장성을 크게 개선했습니다.

이 방식 덕분에 복잡한 비동기 흐름과 상태 변화를 한눈에 파악할 수 있게 되었고, 테스트 코드 작성도 훨씬 수월해졌습니다. 물론 초기 설계와 문서화에 신경 써야 하지만, 장기적으로는 개발 생산성에 긍정적 영향을 미쳤어요.

### 마무리하며

useEffect 훅은 정말 유용하지만, 모든 상태 관리와 부수 효과를 다 떠맡기면 코드가 금세 꼬입니다. 클래스 기반 상태 관리자를 직접 만들어보니, 상태와 로직을 명확히 분리하고 관리하는 데 큰 도움이 되더군요.

다만, 이 방식도 완벽하지 않으니 팀 상황과 프로젝트 규모를 고려해 점진적으로 도입하는 걸 추천합니다. 저처럼 useEffect 로직에 지친 분이라면 한 번 시도해볼 만한 대안입니다.
