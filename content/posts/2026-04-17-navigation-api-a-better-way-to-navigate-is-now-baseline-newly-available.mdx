## 페이지 전환이 이렇게 부드러워질 줄이야, Navigation API 이야기

"왜 내 앱은 페이지 전환할 때마다 깜빡거리지?" 이런 경험, 프론트엔드 개발자라면 한 번쯤은 겪었을 거예요. 특히 SPA를 쓰면서도 네트워크 요청이나 상태 관리가 꼬여서 사용자 경험이 떨어질 때가 많죠. 최근에 나온 최신 Navigation API를 써보니, 이런 문제들이 꽤 깔끔하게 해결되더라고요. 실제로 GitHub 엔지니어링 블로그에서도 이 API가 페이지 리로드 없이도 부드러운 내비게이션을 가능하게 해 성능과 UX를 크게 개선한다고 했어요[GitHub Engineering Blog](https://github.blog/category/engineering/).


## Navigation API가 기존 SPA 내비게이션과 다른 점

SPA에서 페이지 전환은 보통 라우터가 URL을 바꾸고 필요한 데이터를 직접 fetch해서 렌더링을 다시 하는 방식이었죠. 그런데 이 과정에서 상태 관리가 복잡해지고, 브라우저 기본 내비게이션 이벤트와 충돌하는 경우도 많았어요. Navigation API는 브라우저 네이티브 내비게이션 이벤트를 직접 제어할 수 있게 해줘서, 이런 복잡함을 덜어줍니다. 

예를 들어, 사용자가 뒤로 가기 버튼을 눌렀을 때 단순히 URL만 바꾸는 게 아니라, 이전 페이지 상태를 세밀하게 복원할 수 있게 해주죠. 그래서 상태 관리 로직이 훨씬 단순해지고, 사용자 인터랙션도 더 자연스러워집니다. 이 점은 GitHub 엔지니어링 블로그에서도 강조한 부분이에요[GitHub Engineering Blog](https://github.blog/category/engineering/).


## Cloudflare 사례에서 본 Navigation API의 실제 효과

Cloudflare의 "How We Built It" 블로그를 보면, Navigation API 도입 후 네트워크 요청 최적화와 리소스 사전 로딩으로 초기 로딩 시간이 눈에 띄게 줄었다고 해요. 예를 들어, 이전에는 페이지 전환 시 전체 리소스를 다시 받아와서 1~2초 정도 걸렸다면, Navigation API를 쓰고 나서는 필요한 리소스만 미리 불러와서 300~500ms 수준으로 반응 속도가 빨라졌다고 합니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

이건 실제로 겪어보면 체감이 엄청 나요. 사용자 입장에선 거의 즉각 반응하는 느낌이라, 서비스 만족도가 확 올라가죠. 물론, 사전 로딩 전략을 잘 설계해야 리소스 낭비를 막을 수 있으니, 무턱대고 다 미리 불러오는 건 피해야 합니다.


## Navigation API를 적용하는 간단한 코드 예시

```js
// 페이지 전환 시 Navigation API 활용 예시
if ('navigation' in window) {
  const nav = window.navigation;

  nav.addEventListener('navigate', event => {
    const destination = event.destination.url;
    event.intercept({
      async handler() {
        // 필요한 데이터만 fetch
        const response = await fetch(destination);
        const html = await response.text();
        // DOM 업데이트
        document.getElementById('app').innerHTML = html;
        // 히스토리 상태 관리
        history.pushState({}, '', destination);
      }
    });
  });
}
```

이 코드는 브라우저가 내비게이션 이벤트를 감지하면, 전체 페이지 리로드 없이 필요한 데이터만 가져와서 DOM을 업데이트하는 방식입니다. 이렇게 하면 네트워크 비용과 렌더링 비용을 줄일 수 있죠. 물론, SPA 라우터와 함께 쓰거나 상태 관리 라이브러리와 조합할 때는 더 복잡해질 수 있으니, 단계적으로 적용하는 걸 추천합니다.


## 모듈화된 아키텍처와 Navigation API는 찰떡궁합

Martin Fowler의 아키텍처 가이드에서도 Navigation API를 활용해 프론트엔드 모듈을 명확히 분리하고 유지보수성을 높이는 사례를 소개했어요. 각 모듈이 독립적으로 내비게이션 이벤트를 처리하면, 기능 추가나 수정할 때 영향 범위를 최소화할 수 있죠[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

이걸 실제로 해보면, 초기 설계가 좀 더 복잡해질 수 있지만 장기적으로는 코드가 훨씬 깔끔해지고, 여러 개발자가 동시에 작업할 때 충돌도 줄어드는 걸 느낄 수 있습니다. 


## Navigation API 도입 시 주의할 점

- **브라우저 호환성**: 아직 모든 브라우저가 완벽히 지원하는 건 아니어서, 폴리필이나 대체 로직을 준비해야 합니다.
- **상태 동기화**: 내비게이션 이벤트와 앱 상태가 꼬이지 않도록 신경 써야 합니다. 특히 SPA에서 전역 상태 관리 라이브러리와 조합할 때 테스트가 필수예요.
- **리소스 사전 로딩 전략**: 무조건 다 미리 불러오면 오히려 네트워크 낭비가 발생할 수 있으니, 사용자 행동 패턴을 분석해 적절히 설계해야 합니다.


## 정리하며: 내비게이션 성능과 사용자 경험, Navigation API가 답이다

처음엔 이게 별거 아닌 것 같지만, 실제로 적용해보면 내비게이션이 얼마나 사용자 경험에 큰 영향을 주는지 새삼 느끼게 됩니다. 최신 Navigation API는 불필요한 전체 페이지 리로드를 없애고, 네이티브 내비게이션 이벤트를 직접 다루면서 SPA의 복잡한 상태 관리 문제도 줄여줍니다. 

Cloudflare 사례처럼 네트워크 요청 최적화와 리소스 사전 로딩으로 초기 로딩 시간을 획기적으로 줄일 수 있고, Martin Fowler가 말한 것처럼 모듈화된 아키텍처 설계에도 큰 도움을 줍니다.
