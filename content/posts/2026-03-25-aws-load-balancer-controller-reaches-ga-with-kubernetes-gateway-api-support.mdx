## Gateway API가 왜 기존 Ingress를 넘어서는 선택지가 되었을까?

얼마 전 우리 팀에서 Kubernetes 환경의 트래픽 라우팅을 다시 설계할 일이 있었는데, 기존 Ingress 리소스가 너무 단순하고 확장성에 한계가 있더라고요. 특히 다양한 백엔드 서비스에 세밀한 라우팅 정책을 적용하려니 불가능에 가까웠죠. 그러다 Kubernetes Gateway API가 GA를 맞았다는 소식을 듣고, AWS Load Balancer Controller가 이를 공식 지원한다는 점에 꽂혔습니다.

Gateway API는 기존 Ingress API를 대체하는 차세대 네트워킹 API로, 더 유연하고 확장 가능한 트래픽 라우팅을 지원합니다. 예를 들어, HTTPRoute, TCPRoute 같은 리소스를 통해 프로토콜별 세밀한 제어가 가능하고, 여러 Gateway 리소스를 조합해 복잡한 네트워크 경로를 구성할 수 있죠. 이 덕분에 클라우드 네이티브 환경에서 서비스 연결성이 훨씬 개선됩니다.[Kubernetes Concepts Overview](https://kubernetes.io/docs/concepts/overview/)

## AWS Load Balancer Controller와 Gateway API 통합 시 고려해야 할 설계 원칙

AWS Well-Architected Framework를 보면, 클라우드 인프라 설계 시 신뢰성, 보안성, 성능 효율성, 비용 최적화, 운영 우수성 이렇게 5가지 핵심 요소를 강조합니다. 이걸 백엔드 트래픽 관리에 그대로 적용하면 꽤 도움이 되더라고요.[AWS Well-Architected Framework](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html)

- **신뢰성**: Gateway API와 AWS Load Balancer Controller가 연동될 때, 장애가 발생해도 트래픽이 멈추지 않도록 다중 Gateway와 다중 TargetGroup 구성을 고민해야 합니다.

- **보안성**: HTTPS 리스너 설정과 함께 인증서 관리, 그리고 Gateway API의 필터 기능을 활용해 세밀한 접근 제어를 구현할 수 있습니다.

- **성능 효율성**: 각 서비스별로 적절한 로드 밸런서 타입(ALB/NLB)과 리스너 설정을 선택해 비용과 성능을 최적화합니다.

- **비용 최적화**: 불필요한 Load Balancer 생성 방지, 리소스 중복 최소화에 신경 써야 하죠.

- **운영 우수성**: 모니터링과 로깅 체계를 강화하고, Kubernetes Probe를 활용해 서비스 상태를 정확히 반영하는 게 필수입니다.

## Liveness, Readiness, Startup Probe 설정이 왜 더 중요해졌나

Gateway API와 AWS Load Balancer Controller가 결합되면, 백엔드 서비스의 상태를 정확하게 감지하는 게 더 중요해집니다. Kubernetes의 Liveness, Readiness, Startup Probe 설정을 잘못하면, 트래픽이 죽은 서비스로 흘러가거나, 반대로 준비 안 된 서비스에 요청이 전달될 수 있거든요.[Kubernetes - Configure Liveness, Readiness and Startup Probes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)

예를 들어, Readiness Probe가 실패하면 해당 파드는 Gateway API가 관리하는 TargetGroup에서 자동으로 제외됩니다. 덕분에 무중단 배포가 훨씬 수월해지고, 장애 복구도 빠릅니다. 우리 팀에서는 HTTP GET /health/readiness 엔드포인트를 5초 간격으로 체크하고, 실패 시 3회 연속 실패하면 트래픽에서 제외하도록 설정했어요.

```yaml
readinessProbe:
  httpGet:
    path: /health/readiness
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5
  failureThreshold: 3
```

이 설정 덕분에, 배포 중에도 트래픽이 정상적으로 분산되고, 서비스 중단 없이 롤링 업데이트를 할 수 있었습니다.

## 실무에서 AWS Load Balancer Controller와 Gateway API 조합이 주는 이점과 한계

AWS Architecture Blog에서는 이 조합이 백엔드 서비스 간 네트워크 경로를 세밀하게 제어하고, 확장성과 장애 복원력을 높이는 데 큰 도움이 된다고 소개합니다.[AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/)

우리 팀도 실제로 다음과 같은 패턴을 적용했는데요:

- **다중 Gateway 리소스 활용**: 서비스별로 별도의 Gateway를 만들어 관리 부담을 줄이고, 팀별 권한 분리가 쉬워졌습니다.

- **Protocol-specific Route 사용**: HTTPRoute와 TCPRoute를 적절히 나눠서, 웹 서비스와 데이터베이스 트래픽을 분리해 보안과 성능을 동시에 챙겼죠.

- **TargetGroup 세분화**: 각 서비스 버전별로 TargetGroup을 분리해 Canary 배포가 가능해졌습니다.

하지만 단점도 있습니다. 설정이 복잡해지고, 초기 진입 장벽이 꽤 높아요. 특히 기존 Ingress 리소스에 익숙한 팀원들에게는 Gateway API의 리소스 모델과 CRD가 낯설 수 있습니다. 그리고 AWS Load Balancer Controller가 아직 모든 Gateway API 기능을 100% 지원하지는 않아서, 일부 고급 기능은 직접 커스텀하거나 기다려야 하는 상황입니다.

## 실전에서 바로 써먹는 Gateway API + AWS Load Balancer Controller 예시

아래는 HTTPRoute를 사용해 ALB(Application Load Balancer)로 트래픽을 라우팅하는 간단한 예시입니다. 이걸 통해 특정 호스트와 경로에 따라 백엔드 서비스를 분리할 수 있습니다.

```yaml
apiVersion: gateway.networking.k8s.io/v1beta1
kind: Gateway
metadata:
  name: example-gateway
  namespace: default
spec:
  gatewayClassName: aws-load-balancer
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: All
---
apiVersion: gateway.networking.k8s.io/v1beta1
kind: HTTPRoute
metadata:
  name: example-route
  namespace: default
spec:
  parentRefs:
    - name: example-gateway
  hostnames:
    - "example.com"
  rules:
    - matches:
        - path:
            type: Prefix
            value: "/app1"
      backendRefs:
        - name: app1-service
          port: 80
    - matches:
        - path:
            type: Prefix
            value: "/app2"
      backendRefs:
        - name: app2-service
          port: 80
```

이 구성을 적용하면, ALB가 example.com 도메인의 /app1 요청은 app1-service로, /app2 요청은 app2-service로 각각 라우팅합니다. 기존 Ingress와 비교해 훨씬 명확하고 유연한 라우팅 정책을 만들 수 있죠.

## 마치며: Gateway API 도입, 꼭 준비해야 할 것들

처음엔 Gateway API가 너무 복잡해 보일 수 있지만, 실제로 써보면 서비스별 세밀한 트래픽 제어와 운영 안정성에서 큰 장점이 있습니다. AWS Load Balancer Controller와 함께 쓰면, AWS 인프라와도 자연스럽게 연동되어 클라우드 네이티브 환경에 최적화된 아키텍처를 만들 수 있죠.

꼭 기억할 점은 Kubernetes Probe 설정을 꼼꼼히 하고, AWS Well-Architected Framework의 다섯 가지 핵심 원칙에 맞춰 설계하는 것입니다. 그리고 팀 내에서 Gateway API 리소스 모델에 대한 교육과 문서화를 충분히 진행해 초기 진입 장벽을 낮추는 것도 중요합니다.

이제 우리 팀은 Gateway API 덕분에 신규 서비스 배포 속도가 30% 빨라졌고, 장애 발생 시 복구 시간도 크게 줄었어요. 여러분도 한번 시도해보시길 추천합니다!
