# Agentic AI, 데이터 준비가 이렇게 다르다고?

얼마 전 우리 팀에서 Agentic AI 프로젝트를 시작하면서 데이터 파이프라인과 저장소를 전면 재설계해야 했어요. 기존에 쓰던 배치 처리 위주의 정형 데이터 저장소가 AI의 대규모 컨텍스트 활용에는 너무 답답하더라고요. 실시간 스트리밍 데이터와 벡터 검색이 필수인 상황에서, 어떻게 아키텍처를 짜야 할지 한참 고민했습니다. 이 글은 그때 겪은 시행착오와 배운 점을 공유하려고 해요.

---

## 실시간과 배치, 둘 다 잡아야 하는 이유

Agentic AI 워크로드는 실시간 데이터 처리와 배치 처리를 동시에 요구합니다. 예를 들어, 사용자의 실시간 행동 데이터를 빠르게 반영해야 하면서도, 대규모 로그를 정기적으로 분석해 모델에 반영하는 작업도 필요하죠. 여기서 가장 큰 고민은 데이터 지연(latency)과 처리량(throughput) 사이의 트레이드오프입니다.

우리 팀은 처음에 Kafka 기반 스트리밍 파이프라인과 Airflow 배치 작업을 병행하는 구조를 택했어요. 실시간 데이터는 Kafka 토픽에 쌓아 빠르게 소비하고, 배치는 하루 한 번씩 대용량 분석을 돌리는 식이었죠. 이렇게 하니 실시간 반응성은 확보되지만, 배치 데이터와 실시간 데이터 간에 일관성을 맞추는 게 꽤 까다로웠습니다.

Cursor 문서에도 이런 하이브리드 아키텍처가 권장되는데, 결국엔 데이터 지연과 처리량 요구사항을 명확히 정의하고, 그에 맞춰 파이프라인을 조율해야 한다고 하더군요[Cursor Documentation](https://docs.cursor.com/).

## 벡터 데이터베이스, AI 컨텍스트를 위한 필수 선택

Agentic AI가 대규모 컨텍스트를 활용한다는 건, 단순 텍스트 검색이 아니라 의미 기반 검색이 필요하다는 뜻입니다. 그래서 우리도 벡터 데이터베이스를 도입했어요. Pinecone이나 Weaviate 같은 솔루션도 고려했지만, 결국은 클라우드 네이티브 환경에서 쉽게 확장 가능한 벡터 DB를 선택했습니다.

이 벡터 DB는 고속 인덱싱과 검색을 지원하는데, 수백만 건의 임베딩 데이터도 밀리초 단위로 쿼리할 수 있어야 하거든요. OpenAI 문서에서도 벡터 검색 인프라가 Agentic AI에서 핵심 인프라라고 강조합니다[OpenAI API Documentation](https://platform.openai.com/docs/overview).

우리 사례로, 하루 평균 500만 건의 사용자 문장 임베딩을 처리하는데, 벡터 DB 클러스터를 3노드로 구성해 99.9% 가용성을 확보했습니다. 물론 비용이 꽤 들어가긴 했지만, AI 응답 속도와 정확도 향상에 큰 도움이 됐죠.

## 프롬프트 엔지니어링과 데이터 정합성 유지가 생각보다 어렵다

Agentic AI에서 프롬프트는 단순한 입력값이 아니라, 모델의 성능을 좌우하는 핵심 요소입니다. 그래서 데이터 파이프라인에서 프롬프트에 쓰이는 데이터의 정합성과 최신성을 유지하는 게 정말 중요해요.

우리 팀은 데이터 버전 관리와 메타데이터 추적 기능을 파이프라인에 포함시켰습니다. 예를 들어, 각 데이터 배치마다 버전 태그를 붙이고, 언제 어떤 데이터가 업데이트됐는지 로그를 남기도록 했죠. 이렇게 해야 모델 학습과 추론 시점에 어떤 데이터가 쓰였는지 추적할 수 있어서, 문제 발생 시 원인 분석이 훨씬 수월해집니다.

Anthropic 문서에서도 이 부분을 강조하는데, 프롬프트 엔지니어링 단계에서 데이터 정합성 없이는 좋은 결과를 기대하기 어렵다고 하네요[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

## 기존 데이터 저장소에서 벡터 검색 시스템으로 어떻게 옮길까?

기존에 정형화된 RDBMS나 데이터 웨어하우스만 쓰던 조직이라면, 벡터 검색과 비정형 데이터 처리가 가능한 시스템으로 전환하는 게 큰 도전입니다. 우리도 이걸 한 번에 다 바꾸려다 큰 사고를 칠 뻔했어요.

그래서 점진적 마이그레이션 전략을 택했습니다. 먼저 일부 데이터만 벡터 DB로 옮기고, 실시간 파이프라인에서 벡터화 작업을 병행했죠. 이후 점차 범위를 넓히면서 기존 시스템과 벡터 DB 간 데이터 동기화를 맞췄습니다. 이렇게 하면 운영 중단 없이 AI 워크로드를 확장할 수 있어요.

Cursor 문서에서도 점진적 전환을 권장하는데, 무리한 한 번에 마이그레이션은 리스크가 크다고 합니다[Cursor Documentation](https://docs.cursor.com/).

## 클라우드 네이티브 아키텍처로 내결함성과 확장성 확보하기

Agentic AI 백엔드는 확장성과 내결함성이 필수입니다. 우리 팀은 서버리스 함수(AWS Lambda)와 컨테이너 기반 마이크로서비스(Kubernetes)를 혼합해 썼어요. 서버리스는 이벤트 기반 실시간 처리에, 컨테이너는 배치 작업과 복잡한 비즈니스 로직에 적합했습니다.

Vercel AI SDK 문서에서도 서버리스와 컨테이너 아키텍처가 Agentic AI에 잘 맞는다고 소개하더군요[Vercel AI SDK Documentation](https://sdk.vercel.ai/docs/introduction).

이런 아키텍처 덕분에, 갑작스러운 트래픽 급증에도 자동 확장으로 대응할 수 있었고, 한 노드 장애 시에도 서비스가 끊기지 않았습니다. 다만 서버리스는 콜드 스타트 지연이 있고, 컨테이너는 관리 오버헤드가 있으니 둘 다 적절히 조합하는 게 중요합니다.

---

## 실제 코드 한 번 볼까요? 벡터 DB에 임베딩 저장하기

아래는 Python으로 OpenAI 임베딩을 생성하고, 벡터 DB에 저장하는 간단한 예제입니다. 실시간으로 사용자 쿼리를 임베딩화해 벡터 DB에 넣는 과정이죠.

```python
import openai
from my_vector_db_client import VectorDBClient

openai.api_key = 'YOUR_OPENAI_API_KEY'

vector_db = VectorDBClient(endpoint='https://myvectordb.example.com')

def store_user_query(user_id: str, query: str):
    # 1. 임베딩 생성
    response = openai.Embedding.create(
        input=query,
        model='text-embedding-ada-002'
    )
    embedding_vector = response['data'][0]['embedding']

    # 2. 벡터 DB에 저장
    vector_db.upsert(
        collection='user_queries',
        id=user_id,
        vector=embedding_vector,
        metadata={'query': query}
    )

# 사용 예
store_user_query('user123', 'Agentic AI 데이터 준비 어떻게 하지?')
```

이 코드는 실시간 데이터 파이프라인에서 바로 사용할 수 있는데, 중요한 건 임베딩 생성 속도와 벡터 DB 쓰기 지연을 최소화하는 겁니다. 우리 팀은 임베딩 생성에 평균 50ms, 벡터 DB 쓰기 지연은 20ms 이내로 맞췄어요.

## 데이터 프라이버시와 보안, AI에서도 절대 놓치면 안 돼

Agentic AI에선 민감 데이터가 AI 모델에 들어가고, 결과가 다시 사용자에게 노출되기 때문에 보안과 프라이버시가 특히 중요합니다. 데이터 암호화, 접근 제어, 감사 로깅은 기본이고, AI 추론 시에도 이 정책들이 엄격히 지켜져야 합니다.

OpenAI 문서에도 이런 보안 요구사항을 명확히 하고 있어요[OpenAI API Documentation](https://platform.openai.com/docs/overview). 우리 팀은 데이터 저장 시 AES-256 암호화를 적용하고, API 호출 로그를 모두 중앙 감사 시스템에 기록했습니다. 덕분에 컴플라이언스 요구사항도 충족할 수 있었죠.

## 마치며: Agentic AI 데이터 준비, 결국은 균형과 점진적 개선

Agentic AI 데이터 준비는 단순히 기술 스택 바꾸는 게 아니라, 실시간성과 대용량 처리, 보안, 확장성 등 여러 요구사항을 균형 있게 맞추는 작업입니다. 처음엔 복잡해 보여도, 작은 단위부터 실험하고 점진적으로 확장하는 게 가장 안전한 길이에요.

그리고 벡터 데이터베이스 도입과 메타데이터 관리 같은 세부 요소가 AI 성능에 큰 영향을 미친다는 점, 꼭 기억하세요. 마지막으로, 클라우드 네이티브 아키텍처를 적극 활용해 내결함성과 확장성을 확보하는 것도 필수입니다.

이 글이 Agentic AI 도입을 준비하는 여러분께 조금이나마 도움이 되었으면 합니다. 궁금한 점 있으면 언제든 커피 한 잔 하면서 얘기해요!
