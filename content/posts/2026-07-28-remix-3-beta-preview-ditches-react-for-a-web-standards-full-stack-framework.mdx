## Remix 3 베타, React 없이도 가능한 풀스택 개발? 이게 가능한 이유

얼마 전 Remix 3 베타 소식을 듣고 솔직히 좀 놀랐어요. 기존까지 Remix 하면 React와 뗄 수 없는 관계였는데, 이번 버전은 React를 아예 내려놓고 웹 표준 API 위주로 풀스택 프레임워크를 재설계했다는 거죠. "React 없이도 프론트엔드와 백엔드를 자연스럽게 연결할 수 있을까?"라는 의문이 들었는데, 직접 써보니 백엔드 개발자 입장에서도 꽤 매력적인 변화더군요.

이전까지는 React 컴포넌트 단위로 UI를 쪼개고, 상태 관리와 데이터 페칭을 클라이언트 쪽에서 꽤 신경 써야 했잖아요. 그런데 Remix 3는 서버와 클라이언트 경계를 명확히 하면서도, 웹 표준을 활용해 라우팅과 데이터 페칭을 처리해요. 덕분에 백엔드 API 설계에 더 집중할 수 있게 됐죠. 

## 웹 표준 기반 라우팅과 데이터 페칭, 백엔드가 더 편해진 이유

React 중심의 SPA에서는 클라이언트가 직접 API를 호출하고 상태를 관리하는 일이 많았는데, Remix 3는 라우팅부터 데이터 페칭까지 웹 표준 API를 적극 활용합니다. 예를 들어, `fetch` API와 HTML의 `<form>` 요소를 기본으로 삼고, 서버에서 직접 데이터를 렌더링하는 SSR(Server-Side Rendering) 방식을 자연스럽게 지원하죠.

이 덕분에 백엔드 개발자가 RESTful API나 GraphQL 설계에 집중하기 훨씬 좋아졌어요. 복잡한 클라이언트 상태 관리 코드를 줄이고, 서버에서 필요한 데이터만 쏙쏙 뽑아내서 보내는 구조가 되니까요. 

```js
// Remix 3 데이터 로더 예시
export async function loader({ params }) {
  const userId = params.userId;
  const user = await getUserFromDB(userId); // 서버에서 데이터 조회
  return json({ user });
}

// React 컴포넌트는 서버가 제공한 데이터를 바로 사용
export default function UserProfile() {
  const { user } = useLoaderData();
  return <div>{user.name}님의 프로필</div>;
}
```

이처럼 `loader` 함수는 서버에서 데이터를 가져와 JSON 형태로 반환하고, 클라이언트는 이 데이터를 바로 렌더링합니다. React가 여전히 UI 렌더링에 쓰이긴 하지만, 데이터 흐름이 훨씬 명확해졌죠.

## 서버리스와 엣지 컴퓨팅에 최적화된 배포 전략

Remix 3가 웹 표준에 집중하면서 배포 전략도 많이 달라졌어요. 서버리스 환경이나 Cloudflare 같은 엣지 컴퓨팅 플랫폼에 바로 올릴 수 있도록 설계되어 있거든요. 덕분에 인프라 관리 부담이 줄고, 글로벌 사용자에게 더 빠른 응답 속도를 제공할 수 있죠.

예를 들어, Cloudflare Workers에 Remix 앱을 배포하면, 요청이 가장 가까운 엣지 노드에서 처리돼서 지연 시간이 눈에 띄게 줄어듭니다. 이런 아키텍처는 CI/CD 파이프라인과도 잘 어울려서, 자동화된 테스트와 배포가 훨씬 수월해졌어요. 

```json
// package.json 일부
"scripts": {
  "build": "remix build",
  "deploy": "wrangler publish"
},
"dependencies": {
  "@remix-run/cloudflare": "^3.0.0-beta"
}
```

`wrangler` CLI를 이용해 빌드 후 바로 Cloudflare Workers에 배포하는 흐름이 자연스럽게 연결되죠. 물론 서버리스 특성상 cold start 문제나 상태 유지가 까다로운 점은 있지만, 빠른 확장성과 글로벌 분산 처리라는 장점이 더 크다고 봐요.

## 백엔드 개발자가 Remix 3를 선택할 때 고려할 점

Remix 3는 확실히 백엔드 친화적인 풀스택 프레임워크로 거듭났지만, 모든 팀과 프로젝트에 무조건 맞는 건 아닙니다. React 생태계에 익숙한 프론트엔드 개발자가 적거나, 복잡한 클라이언트 상태 관리가 필요한 앱이라면 기존 방식이 더 나을 수도 있거든요.

또한, 웹 표준 API를 적극 활용하는 만큼, 브라우저 호환성이나 서버 환경에 대한 이해가 필요해요. 서버리스 환경에 배포할 때는 함수 실행 시간 제한이나 메모리 제약도 신경 써야 하고요. 

하지만 서버와 클라이언트 경계를 명확히 나누고, 데이터 페칭과 라우팅을 표준 API로 해결하는 패턴은 장기적으로 유지보수와 확장성에 큰 도움이 됩니다. 특히 RESTful API 설계에 집중하는 백엔드 개발자라면 Remix 3의 접근법이 훨씬 직관적일 거예요.

## 마치며: Remix 3가 보여준 웹 표준 풀스택의 미래

Remix 3 베타를 직접 써보면서 느낀 건, "웹 표준에 충실한 풀스택 프레임워크가 이렇게까지 실용적일 수 있구나" 하는 점이었어요. React에 얽매이지 않고, 서버와 클라이언트가 각자의 역할에 집중하면서도 유기적으로 연결되는 구조가 인상적입니다.

배포도 서버리스와 엣지 컴퓨팅 환경에 최적화되어 있어, 앞으로 클라우드 네이티브 아키텍처와도 자연스럽게 융합될 것 같고요. 물론 아직 베타 단계라 완성도가 100%는 아니지만, 백엔드 개발자 입장에서 충분히 주목할 만한 변화입니다.

만약 여러분이 다음 프로젝트에서 풀스택 프레임워크를 고민 중이라면, Remix 3 베타를 한 번 시험 삼아 써보길 추천해요. 특히 API 설계와 배포 전략에 신경 쓰는 팀이라면, 꽤 신선한 경험이 될 겁니다.
