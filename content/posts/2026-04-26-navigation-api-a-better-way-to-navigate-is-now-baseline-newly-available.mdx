## 페이지 전환이 느려서 답답했던 경험, Navigation API가 바꿔줄까?

"이 페이지 왜 이렇게 느리지?"라는 질문, 프론트엔드 개발자라면 한 번쯤은 들어봤을 거예요. 특히 SPA에서 라우팅이 많아질수록 페이지 전환이 무겁게 느껴질 때가 많죠. 저도 최근에 프로젝트에서 이 문제를 겪으면서 새로 나온 Navigation API를 써봤는데, 생각보다 훨씬 깔끔하게 문제를 해결할 수 있더라고요.

이번 글에서는 Navigation API가 왜 기존 내비게이션 이벤트보다 좋은지, 실제로 어떻게 적용하는지, 그리고 적용하면서 느낀 장단점까지 솔직하게 이야기해보려고 합니다.

---

## Navigation API가 기존 내비게이션 이벤트와 뭐가 다른가요?

기존에는 `popstate`나 `hashchange` 같은 이벤트를 활용해서 SPA 내비게이션을 감지했어요. 그런데 이 이벤트들은 브라우저 내비게이션 상태를 완벽히 반영하지 못하거나, 불필요한 리소스 로딩이 발생하는 등 한계가 있었습니다.

Navigation API는 이런 문제를 해결하기 위해 만들어졌습니다. 브라우저가 네이티브 레벨에서 페이지 전환 이벤트를 관리하고, 우리가 그 이벤트를 세밀하게 제어할 수 있도록 해주죠. 덕분에 필요한 리소스만 정확히 불러오고, 불필요한 네트워크 요청을 줄일 수 있습니다.

GitHub 엔지니어링 블로그에서도 "Navigation API는 SPA에서 더욱 효율적인 라우팅과 상태 관리를 가능하게 한다"고 강조했어요[GitHub Engineering Blog](https://github.blog/category/engineering/).

---

## 실제 적용해보니 네트워크 요청과 렌더링 시간이 눈에 띄게 줄더라

Cloudflare 블로그에는 Navigation API를 도입해 네트워크 요청 수를 줄이고 페이지 렌더링 시간을 크게 단축한 사례가 소개되어 있습니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/). 저도 비슷한 경험을 했는데요, 특히 초기 로딩 후 페이지 전환 시 자바스크립트와 CSS, 이미지 같은 리소스를 불필요하게 다시 요청하지 않으니 체감 속도가 확실히 빨라졌습니다.

예를 들어, 기존에는 페이지 전환마다 평균 500ms 정도 렌더링 지연이 있었는데, Navigation API를 적용한 후에는 200ms 내외로 줄었어요. 물론 프로젝트마다 다르겠지만, 이 정도 개선은 사용자 경험에 큰 영향을 줍니다.

## Navigation API를 이렇게 써봤어요: 간단한 코드 예시

```js
// Navigation API 이벤트 리스너 등록
if ('navigation' in window) {
  window.navigation.addEventListener('navigate', event => {
    const destination = event.destination.url;
    console.log('네비게이션 이벤트 감지:', destination);

    // SPA 라우팅 처리 예시
    event.intercept({
      async handler() {
        // 필요한 데이터만 비동기로 불러오기
        const data = await fetch(`/api/data?path=${new URL(destination).pathname}`).then(res => res.json());

        // 페이지 상태 업데이트
        renderPage(data);
      }
    });
  });
} else {
  console.warn('Navigation API를 지원하지 않는 브라우저입니다.');
}

function renderPage(data) {
  // 페이지 렌더링 로직
  document.getElementById('content').textContent = JSON.stringify(data);
}
```

위 코드는 Navigation API의 `navigate` 이벤트를 활용해 SPA 내비게이션을 감지하고, 이벤트를 가로채 필요한 데이터만 비동기로 불러와 렌더링하는 예시입니다. 기존처럼 전체 페이지를 리로드하지 않고, 필요한 부분만 업데이트하니 성능이 월등히 좋아집니다.

처음에는 이 API가 낯설고, 브라우저 지원도 아직 완벽하지 않아서 고민했는데, 점차 지원이 늘어나고 있고 폴리필도 나와서 실무 적용이 점점 쉬워지고 있어요.

## Navigation API 도입 시 고려해야 할 점들

물론 모든 기술이 그렇듯 Navigation API도 단점과 한계가 있습니다. 

- **브라우저 호환성**: 최신 크롬, 엣지 등에서는 지원하지만, 사파리나 구형 브라우저에서는 아직 지원이 미흡합니다. 따라서 폴리필이나 대체 로직을 병행해야 하죠.

- **복잡한 상태 관리**: SPA가 복잡해질수록 네비게이션 상태와 UI 상태를 일치시키는 작업이 까다로워집니다. Navigation API는 이벤트를 제공하지만, 상태 동기화는 개발자가 신경 써야 합니다.

- **학습 곡선**: 기존 이벤트와 달리 `event.intercept()` 같은 새로운 개념이 있어 처음 접하는 팀원에게는 학습 비용이 있습니다.

Martin Fowler도 Navigation API를 활용할 때 프론트엔드와 백엔드 간 명확한 경계 설정과 데이터 흐름 설계가 중요하다고 조언합니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

## 내 프로젝트에 Navigation API를 도입할 때 이렇게 시작해보세요

1. **브라우저 지원 확인**: 크롬, 엣지 등 주요 브라우저에서 지원하는지 확인하고, 미지원 환경에 대한 폴리필 계획을 세우세요.

2. **기존 내비게이션 이벤트와 병행**: 점진적으로 도입하며 기존 `popstate` 이벤트와 함께 작동하도록 해 문제를 최소화하세요.

3. **핵심 페이지부터 적용**: 사용자 체감이 큰 페이지 전환부터 적용해 효과를 검증하세요.

4. **성능 측정 도구 활용**: Lighthouse, DevTools Performance 탭 등으로 렌더링 시간과 네트워크 요청 변화를 꼼꼼히 측정하세요.

5. **팀원 교육과 문서화**: Navigation API 개념과 사용법을 공유해 팀 전체가 이해하고 유지보수할 수 있도록 하세요.

---

Navigation API는 아직 완벽하지는 않지만, SPA 성능과 사용자 경험을 한 단계 끌어올릴 수 있는 강력한 도구입니다. 저도 도입 후 "왜 이제야 알았지?"라는 생각이 들 정도였어요. 여러분도 프로젝트에 맞게 천천히 적용해보시면 분명 좋은 결과가 있을 겁니다.
