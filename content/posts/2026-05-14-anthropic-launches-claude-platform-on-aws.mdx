## AWS에 Claude AI 플랫폼을 올리면서 마주친 첫 번째 고민

"AI 플랫폼을 AWS에 올릴 때, 어떻게 하면 안정성과 확장성을 동시에 잡을 수 있을까?" 이 질문은 Claude 플랫폼을 도입하면서 우리 팀이 처음 마주한 숙제였습니다. Anthropic의 Claude는 강력한 AI 모델을 제공하지만, 이를 실무 환경에 잘 녹여내려면 단순히 VM 하나 띄우는 것 이상의 고민이 필요하더라고요.

특히, AI 서비스는 요청량 변동이 심하고, 모델 업데이트도 잦아서 배포와 운영 전략이 서비스 품질에 직결됩니다. 그래서 AWS 인프라 위에 Claude를 올릴 때는 AWS Well-Architected Framework를 기반으로 설계하는 게 가장 현명하다는 결론을 내렸습니다. 이 프레임워크는 안정성, 보안, 비용 효율, 운영 우수성이라는 네 가지 축을 균형 있게 챙기도록 가이드해주거든요[AWS Well-Architected Framework](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html).

## 컨테이너와 서버리스 조합으로 확장성 확보하기

AWS Architecture Blog에서 자주 보이는 패턴 중 하나가 바로 컨테이너화와 서버리스 아키텍처의 조합입니다[https://aws.amazon.com/blogs/architecture/](https://aws.amazon.com/blogs/architecture/). Claude 같은 AI 플랫폼은 CPU/GPU 자원 요구량이 큰 편이라, 컨테이너 오케스트레이션으로 리소스 할당을 효율적으로 관리하는 게 필수입니다.

우리 팀도 EKS(EKS Kubernetes Service)를 활용해 Claude API 서버를 컨테이너로 띄웠는데, 이렇게 하니 다음과 같은 장점이 있더라고요:

- **자동 스케일링**: 요청량 급증 시 노드 추가 없이도 파드 수를 늘려 대응 가능
- **격리성 보장**: 각 버전별 컨테이너 분리로 롤백과 테스트가 편리
- **배포 유연성**: 블루/그린 배포나 카나리아 릴리즈를 쉽게 적용 가능

또, 이벤트 기반 서버리스 컴포넌트(Lambda, EventBridge)를 일부 보조적으로 활용해 비동기 처리와 알림 시스템을 구축했습니다. 예를 들어, 모델 학습 완료 알림이나 로그 집계 작업을 Lambda 함수로 처리해 시스템 부하를 분산시켰죠.

## 마이크로서비스와 CI/CD로 빠른 업데이트 주기 맞추기

Claude 플랫폼은 AI 모델뿐 아니라, 이를 감싸는 백엔드 서비스가 여러 개로 나뉘어 있습니다. GitHub Engineering Blog에서도 대규모 AI 서비스 운영 시 마이크로서비스 아키텍처와 CI/CD 파이프라인이 핵심이라고 강조하는데[GitHub Engineering Blog](https://github.blog/category/engineering/), 우리도 이 패턴을 적극 도입했습니다.

Spring Boot 기반의 각 마이크로서비스를 독립적으로 개발하고, Jenkins와 GitHub Actions를 활용해 자동 빌드, 테스트, 배포 파이프라인을 구축했어요. 이 덕분에 모델 업데이트나 API 변경 사항을 고객에게 빠르게 제공할 수 있었죠.

아래는 Spring Boot REST API를 간단히 컨테이너화하는 Dockerfile 예시입니다. 이걸 기반으로 CI/CD 파이프라인에서 자동 빌드 후 ECR에 이미지를 푸시하고, EKS 클러스터에 배포합니다.

```dockerfile
# Dockerfile
FROM openjdk:17-jdk-slim

ARG JAR_FILE=target/*.jar
COPY ${JAR_FILE} app.jar

ENTRYPOINT ["java", "-jar", "/app.jar"]
```

이렇게 하면 각 서비스가 독립적으로 배포되고, 문제가 생겨도 빠르게 롤백할 수 있어서 운영 안정성이 크게 올라갔습니다.

## 도메인 주도 설계(DDD)와 이벤트 소싱으로 서비스 결합도 낮추기

AI 플랫폼이 점점 커지면서 서비스 간 의존성이 복잡해지는 문제도 겪었는데, Martin Fowler의 아키텍처 가이드에서 힌트를 얻었어요[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/). 도메인 주도 설계(DDD)를 적용해 각 서비스가 자신의 도메인 로직에 집중하게 하고, 이벤트 소싱 패턴으로 상태 변화를 이벤트로 기록하면서 서비스 간 결합도를 낮췄죠.

예를 들어, Claude 플랫폼에서 사용자 요청 처리와 모델 추론을 담당하는 서비스가 분리되어 있는데, 요청 처리 서비스가 완료 이벤트를 발행하면 추론 서비스가 이를 구독해서 처리하는 방식입니다. 이렇게 하면 두 서비스가 직접 호출하지 않고 이벤트로 느슨하게 연결되어, 한쪽에 문제가 생겨도 전체 시스템이 멈추지 않아요.

## 실제 운영에서 겪은 배포 전략과 비용 최적화

InfoQ에서 추천하는 블루/그린 배포와 카나리아 릴리즈 전략도 적극 활용했습니다[InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/). 특히, AI 모델 업데이트 시 다운타임 없이 새 버전을 배포하는 게 핵심인데, 이 전략이 딱 맞더라고요.

실제로는 다음과 같은 절차를 따릅니다:

1. 새 버전 컨테이너를 블루 환경에 배포
2. 일부 트래픽을 블루 환경으로 라우팅해 안정성 확인
3. 문제 없으면 전체 트래픽을 블루로 전환
4. 이전 그린 환경은 종료

이 과정에서 AWS ALB(Application Load Balancer)와 EKS의 서비스 디스커버리를 활용해 트래픽 전환을 자동화했습니다.

비용 측면에서는 Spot 인스턴스를 적극 활용해 GPU 자원 비용을 30% 이상 절감했는데, 대신 인스턴스가 갑자기 종료될 수 있으니 중요 작업은 온디맨드 인스턴스에서 처리하도록 이중화 전략을 썼습니다.

## 마치며: Claude AI 플랫폼 AWS 운영에서 꼭 기억할 점

처음에는 "그냥 AI 모델만 잘 돌리면 되지"라고 생각했는데, 실제로는 인프라 설계부터 배포, 운영까지 전반적인 아키텍처 패턴과 자동화 전략이 서비스 품질을 좌우한다는 걸 뼈저리게 느꼈습니다.

- AWS Well-Architected Framework를 기본으로 삼아 안정성, 보안, 비용, 운영을 균형 있게 챙기기
- 컨테이너와 서버리스 조합으로 유연하고 확장 가능한 인프라 구축
- 마이크로서비스와 CI/CD로 빠른 배포와 롤백 지원
- DDD와 이벤트 소싱으로 서비스 결합도 낮추기
- 블루/그린 배포, 카나리아 릴리즈로 무중단 업데이트 실현

이 중 하나라도 소홀하면 AI 플랫폼의 민첩성과 안정성이 크게 떨어질 수 있으니, 실제로 적용할 때는 팀 상황과 요구사항에 맞게 조율하는 게 중요합니다. 우리 팀 경험이 비슷한 고민을 하는 분들께 조금이나마 도움이 되길 바랍니다.
