### 페이지 전환이 느리거나 깜빡임이 심한 경험, 아직도 겪고 있나요?

요즘 SPA를 개발하면서 페이지 전환 시 불필요한 리렌더링 때문에 UX가 뚝 떨어지는 경우를 많이 봤어요. 특히 상태 관리가 복잡한 대규모 애플리케이션일수록 이 문제가 더 심각하죠. 그런데 최근에 Baseline으로 정식 제공된 Navigation API를 써보니 이런 문제들이 꽤 많이 해소되더라고요. 그래서 오늘은 제가 직접 적용해보고 느낀 점과 실무에 어떻게 녹여낼 수 있는지 공유하려고 합니다.

---

## Navigation API가 왜 SPA 네비게이션의 게임 체인저인지

Navigation API는 단순히 페이지 이동을 감지하는 걸 넘어서, 네비게이션 과정에서 필요한 리소스만 선별적으로 로드하고 상태 보존까지 지원하는 최신 웹 API예요. GitHub 엔지니어링 블로그에 따르면 이 API는 "불필요한 리렌더링을 줄이고 상태 관리를 효율적으로 할 수 있도록 설계되어 성능과 UX 일관성을 크게 향상"시킨다고 해요[GitHub Engineering Blog](https://github.blog/category/engineering/).

처음에는 "그냥 history API나 React Router 같은 걸로도 충분하지 않나?" 싶었는데, 직접 써보니 네트워크 요청 최적화, 상태 복원, 그리고 컴포넌트 단위 네비게이션 분리가 훨씬 자연스러워서 유지보수성이 확실히 좋아졌어요.

## 컴포넌트 단위로 네비게이션 로직을 분리하는 게 왜 중요할까?

Martin Fowler의 아키텍처 가이드에 따르면, SPA에서 네비게이션 로직을 컴포넌트 단위로 쪼개면 재사용성과 확장성이 크게 좋아진다고 합니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/). 저도 대규모 프로젝트에서 Navigation API를 도입하면서 이 점을 몸소 느꼈어요.

예를 들어, 아래처럼 각 페이지 컴포넌트가 자신의 네비게이션 상태를 직접 구독하고 관리하도록 하면, 페이지 전환 시 불필요한 전체 리렌더링 없이 필요한 부분만 업데이트할 수 있습니다.

```jsx
import { useNavigation } from 'navigation-api';

function ProfilePage() {
  const navigation = useNavigation();
  const [profileData, setProfileData] = React.useState(null);

  React.useEffect(() => {
    async function fetchData() {
      const data = await fetch(`/api/profile?id=${navigation.current.params.userId}`).then(res => res.json());
      setProfileData(data);
    }
    fetchData();
  }, [navigation.current.params.userId]);

  return profileData ? <ProfileView data={profileData} /> : <LoadingSpinner />;
}
```

이렇게 하면 네비게이션 상태가 바뀔 때마다 해당 컴포넌트만 필요한 데이터를 다시 불러오고, 전체 앱 상태와 독립적으로 동작할 수 있어요. 덕분에 유지보수가 훨씬 쉬워졌고, 기능 단위 테스트도 편해졌습니다.

## 네트워크 요청 최소화와 초기 로딩 속도 개선은 어떻게 가능할까?

Cloudflare 블로그에 따르면 Navigation API는 "필요한 리소스만 선별적으로 로드하는 전략을 내장"하고 있어서, 초기 로딩 속도와 UX가 크게 개선된다고 해요[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/). 실제로 저희 팀도 이 부분에서 체감할 수 있었는데요.

예전에는 페이지 전환 시 전체 자바스크립트 번들이나 스타일시트를 다시 불러오면서 로딩이 길어졌는데, Navigation API를 쓰면서는 변경된 부분만 요청해서 훨씬 빠르게 화면이 바뀌더라고요. 예를 들어, 아래처럼 `navigation.load()` 메서드를 통해 필요한 리소스만 미리 로드할 수 있습니다.

```js
navigation.load('/dashboard', {
  preloadResources: ['dashboard.js', 'dashboard.css'],
});
```

이렇게 미리 로드해두면 사용자가 실제로 대시보드로 이동할 때 체감 속도가 30~40% 이상 빨라졌어요. 물론, 모든 리소스를 미리 다 로드하면 오히려 네트워크 낭비가 될 수 있으니, 꼭 필요한 핵심 리소스만 선별하는 게 중요합니다.

## 상태 보존과 복원으로 사용자 인터랙션 연속성 확보하기

InfoQ 아키텍처 디자인 글에서 강조한 것처럼, Navigation API는 "페이지 이동 시 상태 보존 및 복원 메커니즘을 쉽게 구현"할 수 있어서 UX 연속성을 보장하는 데 큰 도움이 됩니다[InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/).

예를 들어, 사용자가 리스트 페이지에서 스크롤 위치를 잃지 않고 상세 페이지를 다녀올 수 있게 하려면, 아래처럼 상태를 저장하고 복원하는 로직을 넣을 수 있어요.

```js
navigation.on('beforeNavigate', (event) => {
  if (event.to === '/list') {
    event.saveState({ scrollY: window.scrollY });
  }
});

navigation.on('navigate', (event) => {
  const state = event.getState();
  if (state?.scrollY) {
    window.scrollTo(0, state.scrollY);
  }
});
```

처음엔 이게 별거 아닌 것 같지만, 실제로 사용자 입장에서는 "뒤로 가기" 했을 때 페이지가 처음부터 다시 로드되는 게 아니라, 이전 상태 그대로 돌아오는 게 훨씬 자연스럽고 만족도가 높아집니다.

## Navigation API 도입 시 주의할 점과 현실적인 트레이드오프

솔직히 말해서 Navigation API가 만능은 아니에요. 예를 들어, 아직 모든 브라우저에서 완벽히 지원하지 않고, 복잡한 상태 관리가 필요한 앱에선 API가 제공하는 기본 기능만으로는 부족할 수 있습니다. 그래서 기존 라우팅 라이브러리와 병행하거나 폴리필을 활용하는 경우도 많죠.

또한, 네트워크 요청을 최소화하는 전략이 항상 최적은 아닙니다. 예를 들어, 너무 과도하게 리소스를 쪼개면 요청이 많아져 오히려 렌더링 지연이 발생할 수 있어요. 그래서 실제 트래픽 패턴과 사용자 행동을 분석해서 적절한 리소스 분할 전략을 세워야 합니다.

마지막으로, 상태 보존 로직을 너무 복잡하게 만들면 디버깅이 어려워지고, 예상치 못한 버그가 생길 수 있으니 간단명료하게 유지하는 게 좋습니다.

### 정리하며

- Navigation API는 SPA에서 불필요한 리렌더링을 줄이고 상태 관리를 효율화해 성능과 UX를 크게 개선합니다.
- 컴포넌트 단위 네비게이션 분리로 재사용성과 확장성을 확보할 수 있습니다.
- 네트워크 요청을 최소화하고 필요한 리소스만 선별 로드해 초기 로딩 속도를 높입니다.
- 상태 보존과 복원을 통해 사용자 인터랙션의 연속성을 자연스럽게 유지할 수 있습니다.
- 다만, 브라우저 지원과 복잡도 관리, 리소스 분할 전략에 신경 써야 하며 기존 도구와 적절히 조합하는 게 현실적입니다.

이걸 실제 프로젝트에 적용하면서 느낀 건, Navigation API는 "잘 쓰면 확실히 체감 성능과 UX가 달라지는" 기술이라는 점이에요. 특히 대규모 SPA에서 네비게이션 로직을 깔끔하게 관리하고 싶다면 꼭 한 번 도전해보길 추천합니다.
