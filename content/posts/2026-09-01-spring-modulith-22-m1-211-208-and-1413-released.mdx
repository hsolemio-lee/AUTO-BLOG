### "이 모듈이랑 저 모듈이랑 서로 뒤엉켜서 유지보수 지옥인데, 어떻게 정리할까?"

최근에 이런 고민을 하던 중에 Spring Modulith 최신 버전들이 나왔다는 소식을 접했어요. 2.2 M1부터 2.1.1, 2.0.8, 그리고 1.4.13까지, 꽤 다양한 버전이 릴리즈됐는데요. 이번 기회에 직접 써보고, 모듈러 아키텍처를 실무에 어떻게 적용할지, 그리고 프로덕션 환경에서 성능과 보안을 어떻게 챙길지 정리해봤습니다.

---

## Spring Modulith 2.2 M1, 2.x, 그리고 1.x 사이의 차이점은 뭘까?

처음 Modulith를 접할 때는 1.x 버전을 많이 썼는데, 2.x로 넘어오면서 모듈 간 의존성 관리가 훨씬 명확해졌어요. Spring Boot Reference Documentation에서도 최신 버전에서 모듈 간 의존성 관리와 자동 구성 기능이 강화되었다고 명시하고 있죠[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

예를 들어, 2.2 M1에서는 모듈 경계가 더 엄격해져서 한 모듈이 다른 모듈의 내부 구현에 직접 접근하는 걸 컴파일 타임에 차단해줍니다. 덕분에 모듈 간 인터페이스만 신경 쓰면 되고, 내부가 바뀌어도 영향 범위를 최소화할 수 있죠. 

반면 1.4.13 같은 1.x 버전은 상대적으로 느슨한 경계 설정이라, 대규모 프로젝트에선 의존성 꼬임이 발생하기 쉬웠어요. 물론 1.x 버전도 안정적이고 가벼워서 작은 프로젝트에는 여전히 괜찮습니다.

## "모듈러 아키텍처가 대체 왜 필요한가?"

Martin Fowler가 강조한 것처럼, 복잡한 백엔드 시스템에서 모듈러 아키텍처는 변경 용이성과 테스트 용이성을 크게 높여줍니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/). 

실제로 우리 팀에서 Modulith 2.x로 전환하면서, 각 모듈을 독립적으로 개발하고, 테스트 커버리지를 높이는 게 훨씬 수월해졌어요. 예를 들어, 주문 처리, 결제, 알림 모듈을 완전히 분리해서 배포 및 롤백 전략도 모듈 단위로 할 수 있게 됐죠.

또한 Spring Framework Core Technologies 문서에 따르면, 2.x 버전은 이벤트 기반 통신 방식을 기본으로 채택해 모듈 간 결합도를 낮추고, 보안성도 강화했다고 합니다[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html). 이게 실제로는 생산 환경에서 장애 전파를 줄이고, 보안 취약점을 최소화하는 데 큰 도움이 됩니다.

## 성능 최적화는 어떻게 해야 할까? JVM 튜닝부터 캐싱까지

Baeldung의 Spring Boot Performance Tuning 가이드에서 소개한 여러 기법이 Modulith 최신 릴리즈와도 잘 맞아요[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

- **JVM 튜닝**: 힙 사이즈, GC 설정을 프로덕션 환경에 맞게 조절해서 지연시간을 줄입니다. 예를 들어, G1 GC를 기본으로 쓰면서 `-Xms2g -Xmx2g`로 고정하는 식이죠.
- **캐싱 전략**: 모듈별로 자주 쓰는 데이터를 Redis나 Caffeine 캐시에 분산해서 읽기 부하를 낮춥니다.
- **비동기 처리**: 이벤트 기반 통신 덕분에 모듈 간 호출을 비동기로 처리해 응답성을 개선할 수 있어요.
- **프로파일링 도구 활용**: JProfiler, VisualVM 같은 툴로 병목 구간을 찾아내고 개선합니다.

### 실전 코드 예시: 모듈 간 이벤트 발행과 구독

```java
// 주문 모듈에서 주문 생성 이벤트 발행
@Component
public class OrderService {
    private final ApplicationEventPublisher publisher;

    public OrderService(ApplicationEventPublisher publisher) {
        this.publisher = publisher;
    }

    public void createOrder(Order order) {
        // 주문 생성 로직
        publisher.publishEvent(new OrderCreatedEvent(this, order.getId()));
    }
}

// 결제 모듈에서 이벤트 구독
@Component
public class PaymentListener {

    @EventListener
    public void handleOrderCreated(OrderCreatedEvent event) {
        // 결제 처리 시작
        System.out.println("주문 생성 이벤트 감지, 결제 처리 시작: " + event.getOrderId());
    }
}
```

이렇게 하면 모듈 간 직접 호출이 아니라 이벤트로 느슨하게 연결돼서, 결제 모듈이 없어도 주문 모듈은 독립적으로 동작할 수 있습니다. 단, 이벤트 처리 실패 시 재시도 로직이나 장애 대응책을 꼭 설계해야 한다는 점은 잊지 마세요.

## 보안은 어떻게 강화됐을까? 최신 릴리즈의 변화

GitHub Engineering Blog에서 대규모 분산 시스템에서 모듈화와 보안 강화를 어떻게 하는지 사례를 많이 다루는데요, Spring Modulith 최신 버전도 이런 트렌드를 반영해 보안 취약점 최소화에 신경 썼다고 합니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

특히, 모듈 간 통신을 이벤트 기반으로 엄격히 제한하면서, 각 모듈의 공개 API를 최소화하고, 인증·인가 로직을 모듈 내에 캡슐화하는 방식을 권장해요. 덕분에 한 모듈이 뚫려도 전체 시스템으로 피해가 확산되는 걸 막을 수 있습니다.

또한, Spring Security와의 통합도 강화돼서 OAuth2, JWT 토큰 기반 인증을 모듈별로 쉽게 적용할 수 있게 됐어요. 예를 들어, 다음과 같이 각 모듈에 `@PreAuthorize` 어노테이션을 붙여 세밀한 권한 관리를 할 수 있습니다.

```java
@Service
public class NotificationService {

    @PreAuthorize("hasRole('NOTIFICATION_ADMIN')")
    public void sendSystemAlert(String message) {
        // 시스템 경고 전송
    }
}
```

이런 보안 설정은 모듈별로 다르게 적용 가능해서, 민감한 결제 모듈은 더 엄격한 정책을, 덜 민감한 알림 모듈은 좀 더 유연한 정책을 쓸 수 있죠.

## 실제로 적용할 때 주의할 점

처음엔 모듈 경계 설정이 까다롭고, 이벤트 기반 통신이 익숙하지 않아서 개발 속도가 느려질 수 있어요. 그리고 이벤트 실패 처리, 트랜잭션 경계 설정 같은 복잡한 문제도 맞닥뜨리게 됩니다.

또, 모듈이 너무 많아지면 오히려 관리 포인트가 늘어나니, 적절한 규모로 나누는 게 중요해요. 그리고 프로덕션 모니터링도 모듈별로 해야 하니, 로깅과 메트릭 수집 체계를 잘 갖춰야 합니다.

## 정리하며: 최신 Spring Modulith, 언제 어떻게 써야 할까?

- **대규모 백엔드에서 유지보수와 확장성을 고민한다면**: 2.x 버전으로 업그레이드해서 엄격한 모듈 경계와 이벤트 기반 통신을 적극 활용하세요.
- **성능 최적화는 JVM 튜닝과 캐싱, 비동기 이벤트 처리로**: Baeldung 가이드에 나온 설정들을 참고해 프로덕션에 맞게 조정하면 효과가 큽니다.
- **보안은 모듈별 인증·인가 정책과 최소 권한 원칙으로**: Spring Security와 함께 쓰면서 보안 사고 위험을 줄이세요.
- **초기 도입 시 학습 곡선과 복잡성 증가에 대비**: 충분한 테스트와 모니터링 체계 마련이 필수입니다.

이 글을 통해 저도 모듈러 아키텍처가 단순히 구조를 나누는 걸 넘어서, 실제 운영과 유지보수에서 얼마나 큰 힘이 되는지 다시 한번 느꼈어요. 여러분도 최신 Spring Modulith로 한 단계 업그레이드된 백엔드 개발 경험을 해보시길 바랍니다.
