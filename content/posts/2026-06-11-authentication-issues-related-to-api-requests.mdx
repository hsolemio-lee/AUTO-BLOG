## "왜 내 API가 자꾸 인증 실패하지?" 실제로 겪은 인증 문제 이야기

얼마 전 우리 서비스에서 API 요청이 갑자기 인증 실패를 뿜어내기 시작했어요. 사용자들은 "로그인했는데 왜 자꾸 인증 안 됐다고 뜨죠?"라며 문의가 빗발쳤죠. 로그를 뒤져보니 토큰이 아예 없거나, 만료됐거나, 서명이 틀린 경우가 대부분이었는데요. 이걸 계기로 API 인증 문제를 어떻게 진단하고, 또 어떻게 해결할 수 있는지 정리해봤습니다.

---

## API 요청에서 인증 토큰, 어디까지 확인해야 할까?

API 인증 문제를 진단할 때 가장 기본이 되는 건 요청 헤더에 토큰이 제대로 포함되어 있는지, 그리고 그 토큰이 유효한지 확인하는 거예요. 여기서 유효하다는 건 크게 두 가지를 뜻합니다.

1. **만료기간 확인**: 토큰이 아직 만료되지 않았는지 체크해야 해요. 예를 들어 JWT라면 `exp` 클레임을 보고 현재 시간과 비교하는 거죠.

2. **서명 검증**: 토큰이 변조되지 않았는지 서명을 검증해야 합니다. 서명이 틀리면 누군가 토큰을 조작했다는 뜻이니 인증 실패 처리해야 하죠.

이 두 가지가 기본 중의 기본입니다. 실제로 GitHub 엔지니어링 팀도 API 인증 문제를 잡을 때 이 패턴을 가장 먼저 적용한다고 하네요[GitHub Engineering Blog](https://github.blog/category/engineering/).

```java
// Spring Boot 예시 - JWT 토큰 검증 필터
public class JwtAuthenticationFilter extends OncePerRequestFilter {
    private final JwtTokenProvider tokenProvider;

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain filterChain)
            throws ServletException, IOException {
        String token = resolveToken(request);
        if (token != null && tokenProvider.validateToken(token)) {
            Authentication auth = tokenProvider.getAuthentication(token);
            SecurityContextHolder.getContext().setAuthentication(auth);
        } else {
            logger.warn("Invalid or missing JWT token");
        }
        filterChain.doFilter(request, response);
    }

    private String resolveToken(HttpServletRequest request) {
        String bearerToken = request.getHeader("Authorization");
        if (StringUtils.hasText(bearerToken) && bearerToken.startsWith("Bearer ")) {
            return bearerToken.substring(7);
        }
        return null;
    }
}
```

이 필터는 요청 헤더에서 Bearer 토큰을 꺼내고, `validateToken` 메서드에서 만료와 서명을 검증합니다. 만약 검증에 실패하면 인증이 안 된 상태로 넘어가서 적절한 에러가 발생하죠.

## 인증 실패가 많다면, 로그와 모니터링부터 제대로 하자

인증 실패가 빈번하면 그냥 "토큰이 잘못됐나보다" 하고 넘어가기 쉽지만, 사실 문제의 근본 원인을 찾으려면 로그와 모니터링이 필수예요. 인증 토큰 발급부터 검증까지 어느 단계에서 문제가 생겼는지 추적해야 하니까요.

Cloudflare 팀은 인증 실패 문제를 잡을 때, 발급 서버 로그와 검증 서버 로그를 모두 모니터링해서 문제를 빠르게 찾는다고 합니다. 예를 들어, 토큰 발급 시점에 키가 잘못 세팅됐거나, 토큰 포맷이 달라진 경우를 이렇게 잡아내죠[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

우리 팀도 로그에 다음과 같은 정보를 남겨서 문제를 추적했어요:

- 토큰 발급 시각과 클레임 정보
- 클라이언트 IP와 요청 경로
- 토큰 검증 실패 시점과 실패 사유(만료, 서명 불일치 등)

이렇게 하면 "어느 클라이언트에서 언제 어떤 이유로 인증 실패가 발생했는지" 한눈에 파악할 수 있습니다.

## 사용자 경험을 살리는 인증 실패 메시지와 재시도 전략

인증 실패가 잦으면 사용자 경험이 확 떨어지는데, 이걸 조금이라도 완화하려면 에러 메시지와 재시도 로직을 잘 설계해야 해요. 단순히 "인증 실패"만 던지면 사용자는 뭘 해야 할지 모르니까요.

Martin Fowler는 인증 실패 시 명확한 에러 코드와 메시지를 내려주고, 클라이언트가 재시도할 수 있는 로직을 구현하길 권장합니다. 예를 들어 토큰 만료라면 "토큰이 만료되었습니다. 자동으로 갱신 중입니다." 같은 메시지와 함께 재발급 API를 호출하는 식이죠[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

```typescript
// TypeScript 예시 - 토큰 만료 시 자동 갱신
async function fetchWithAuth(url: string) {
  let token = localStorage.getItem('accessToken');
  let response = await fetch(url, {
    headers: { 'Authorization': `Bearer ${token}` }
  });

  if (response.status === 401) { // 인증 실패
    const refreshToken = localStorage.getItem('refreshToken');
    const refreshResponse = await fetch('/auth/refresh', {
      method: 'POST',
      body: JSON.stringify({ token: refreshToken }),
      headers: { 'Content-Type': 'application/json' }
    });

    if (refreshResponse.ok) {
      const data = await refreshResponse.json();
      localStorage.setItem('accessToken', data.accessToken);
      // 재시도
      response = await fetch(url, {
        headers: { 'Authorization': `Bearer ${data.accessToken}` }
      });
    } else {
      // 재로그인 유도
      window.location.href = '/login';
    }
  }

  return response;
}
```

이런 재시도 로직은 처음엔 복잡해 보이지만, 실제로 사용자 불편을 크게 줄여줘요.

## 클라우드 환경에서 인증 토큰 보안, 키 관리가 생명

요즘 대부분 백엔드는 클라우드 환경에서 돌아가는데, 여긴 인증 토큰 암호화와 키 관리가 특히 중요합니다. 키가 노출되면 토큰 위조가 가능해져서 보안 사고로 직결되거든요.

Cloudflare는 키 관리를 위해 다음과 같은 정책을 쓴다고 합니다:

- 키를 주기적으로 교체하고 롤링 업데이트
- 키를 HSM(Hardware Security Module) 같은 별도 보안 장비에 저장
- 토큰 암호화에 강력한 알고리즘 사용

이런 정책 덕분에 인증 보안이 한층 강화되죠[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

우리도 AWS KMS 같은 키 관리 서비스를 적극 활용해서 키 노출 위험을 줄이고 있어요. 물론 키 관리가 까다로워서 초기 세팅과 운영에 신경을 많이 써야 하지만, 보안 사고 대비에는 필수입니다.

## 토큰 갱신 시점과 만료 토큰 처리, 일관성 있게 설계해야 한다

마지막으로, 토큰 갱신 시점과 만료된 토큰 처리 로직을 명확히 정의하는 게 중요합니다. 예를 들어 액세스 토큰은 15분, 리프레시 토큰은 7일로 설정했다고 하면, 만료된 액세스 토큰은 리프레시 토큰으로 갱신하고, 리프레시 토큰마저 만료되면 재로그인 유도하는 식으로요.

이걸 안 하면 클라이언트가 토큰 만료 상태를 제대로 인지하지 못해 무한 인증 실패가 발생할 수 있습니다. Martin Fowler도 이런 일관성 있는 설계를 강조하고 있죠[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

우리가 적용한 정책 예시는 다음과 같아요:

- 액세스 토큰 만료 1분 전에 클라이언트가 자동 갱신 시도
- 서버는 만료된 액세스 토큰 요청 시 401과 함께 `token_expired` 코드 반환
- 클라이언트는 이 코드 받으면 리프레시 토큰으로 재발급 시도
- 리프레시 토큰 만료 시 403과 함께 재로그인 유도

이렇게 하면 인증 상태가 명확하게 관리되고 사용자도 덜 불편해집니다.

## 마치며: 인증 문제는 단순하지 않다, 체계적 접근이 답

API 인증 문제는 단순히 "토큰이 맞나?"를 넘어서, 토큰 발급부터 검증, 갱신, 보안 관리까지 복합적으로 봐야 하는 영역입니다. 실제로 겪어보면 "아 이거 별거 아닌 것 같은데 왜 이렇게 꼬이지?" 싶은 경우가 많죠.

이번 경험을 통해 느낀 건, 기본적인 토큰 검증부터 로그 모니터링, 사용자 경험 개선, 그리고 키 관리 정책까지 한꺼번에 챙겨야 한다는 점입니다. 그리고 무엇보다 실시간으로 문제를 추적할 수 있는 로그와 모니터링 시스템이 없으면 문제 해결이 늦어집니다.

동료 개발자 여러분도 인증 문제로 골치 아플 때, 이 글에서 소개한 패턴과 사례가 조금이나마 도움이 되길 바랍니다.
