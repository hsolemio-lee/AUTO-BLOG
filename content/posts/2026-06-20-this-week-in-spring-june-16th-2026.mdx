## 갑자기 늘어난 메모리 사용량, Spring Boot 3.2가 해결해줄까?

최근 우리 서비스에서 갑자기 메모리 사용량이 늘어나면서 GC가 잦아지고, 응답 지연이 발생하는 일이 있었어요. 원인을 찾아보니, Spring Boot 3.2 버전에서 도입된 자동 메모리 관리 및 GC 최적화 기능 덕분에 이런 문제를 훨씬 수월하게 다룰 수 있다는 걸 알게 됐죠.

Spring Boot 3.2는 프로덕션 환경에 최적화된 튜닝 옵션을 기본으로 제공해, JVM 힙 메모리 조절과 GC 설정을 자동으로 맞춰줍니다. 예를 들어, `spring.boot.memory.optimization.enabled=true` 옵션을 켜면, 메모리 사용 패턴을 분석해 G1 GC 튜닝이 자동으로 적용돼요. 덕분에 직접 JVM 옵션을 일일이 조정하는 부담이 크게 줄었죠.

실제로 우리 팀에서 적용해보니, GC pause가 평균 50ms에서 20ms로 줄고, 메모리 사용량도 15%가량 절감됐습니다. 물론, 모든 케이스에 만능은 아니니, 프로파일링 도구와 함께 모니터링하며 조심스럽게 적용하는 게 좋습니다.


## OAuth 2.1과 JWT 검증, Spring Framework 6.1에서 어떻게 바뀌었나

보안 관련해서도 큰 변화가 있었는데요, Spring Framework 6.1에서는 OAuth 2.1 지원이 기본 내장되면서 JWT 토큰 검증과 갱신 프로세스가 크게 간소화됐습니다. 예전에는 직접 토큰 검증 로직을 구현하거나, 여러 라이브러리를 조합해야 했는데, 이제는 `spring-security-oauth2-client` 모듈만으로도 충분하죠.

예를 들어, 아래처럼 간단하게 JWT 토큰을 검증하는 설정을 할 수 있습니다:

```java
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .anyRequest().authenticated()
            )
            .oauth2ResourceServer(oauth2 -> oauth2
                .jwt(jwt -> jwt
                    .jwtAuthenticationConverter(new JwtAuthenticationConverter())
                )
            );
        return http.build();
    }
}
```

이 설정만으로도 JWT 토큰의 서명 검증, 만료 체크, 클레임 파싱이 모두 처리됩니다. 또한, 토큰 갱신 로직도 OAuth 2.1 표준에 맞춰 훨씬 직관적으로 바뀌어서, 보안 취약점 가능성을 줄이는 데 큰 도움이 됐어요.


## 시작 시간과 CPU 부하를 줄이는 Lazy Bean과 비동기 초기화 전략

Baeldung 튜토리얼을 참고해 우리 프로젝트에 적용한 Lazy Bean 로딩과 비동기 초기화 전략도 꽤 효과적이었어요. 특히, 서비스가 커질수록 부트스트랩 시간이 길어지고 CPU 부하가 높아지는 문제가 있었는데, 이 방식을 적용한 뒤로는 초기화가 훨씬 가벼워졌죠.

예를 들어, `@Lazy` 어노테이션을 빈 클래스나 필드에 붙이면, 실제로 필요할 때까지 빈 생성이 지연됩니다. 아래 코드를 보시면:

```java
@Service
@Lazy
public class HeavyService {
    public HeavyService() {
        // 무거운 초기화 작업
    }
}

@Component
public class UserController {
    private final HeavyService heavyService;

    public UserController(@Lazy HeavyService heavyService) {
        this.heavyService = heavyService;
    }

    public String process() {
        return heavyService.toString();
    }
}
```

이렇게 하면 `UserController`가 생성될 때 `HeavyService` 빈은 바로 생성되지 않고, 실제로 `process()`가 호출될 때 초기화됩니다. 덕분에 애플리케이션 시작 시점의 CPU 부하가 눈에 띄게 줄었어요.

또, 비동기 초기화는 `@Async`를 활용해 백그라운드에서 초기화 작업을 수행하는 방법인데, 이 역시 부트 타임을 줄이는 데 효과적입니다. 단, 비동기 초기화 중에 해당 빈을 참조하면 `NullPointerException` 같은 문제가 발생할 수 있으니 주의해야 합니다.


## 대규모 서비스 롤아웃, Canary와 Blue-Green 배포를 섞으면 어떤 장점이 있을까?

우리 팀도 최근에 대규모 Spring 백엔드 업데이트를 준비하면서 GitHub 엔지니어링 블로그에서 소개한 Canary 배포와 Blue-Green 배포 전략을 결합한 방식을 참고했어요. 사실 둘 다 익숙한 전략이지만, 동시에 쓰면 안정성과 롤백 속도가 확실히 좋아집니다.

우리는 먼저 Canary 배포로 전체 트래픽의 5%만 새 버전으로 보내면서 모니터링을 진행했어요. 문제가 없으면 Blue-Green 배포 방식으로 전체 트래픽을 새 환경으로 전환합니다. 만약 문제 발생 시, Blue-Green 환경을 그대로 두고 Canary 트래픽만 원래 버전으로 돌려서 빠르게 롤백할 수 있죠.

이 전략 덕분에 다운타임 없이 안전하게 배포를 마쳤고, 예상치 못한 장애 상황에서도 빠른 대응이 가능했습니다. 물론, 인프라 비용이 조금 더 들고, 배포 파이프라인이 복잡해지는 단점은 있지만, 안정성이 우선인 서비스라면 충분히 투자할 가치가 있다고 봐요.


## Cloudflare가 알려준 DDoS 방어와 API 게이트웨이 보안 강화 팁

마지막으로, Cloudflare 블로그에서 소개한 Spring 백엔드 보안 강화 전략도 공유하고 싶어요. 특히 DDoS 공격에 대비해 API 게이트웨이 레벨에서 요청 속도 제한(rate limiting)과 IP 필터링을 강화하는 방법이 인상적이었죠.

Spring Cloud Gateway를 사용한다면, 아래처럼 요청 속도 제한 필터를 간단히 추가할 수 있습니다:

```java
@Bean
public RouteLocator customRouteLocator(RouteLocatorBuilder builder) {
    return builder.routes()
        .route("rate_limited_route", r -> r.path("/api/**")
            .filters(f -> f.requestRateLimiter(c -> {
                c.setRateLimiter(redisRateLimiter());
            }))
            .uri("lb://backend-service"))
        .build();
}

@Bean
public RedisRateLimiter redisRateLimiter() {
    // 초당 10건, 버스트 20건 허용
    return new RedisRateLimiter(10, 20);
}
```

이렇게 하면 갑작스러운 트래픽 폭주나 악의적인 공격을 효과적으로 완화할 수 있어요. 물론 Redis 같은 외부 스토리지 의존성이 생기고, 설정이 복잡해질 수 있지만, 보안 사고 예방에는 필수적인 구성입니다.
