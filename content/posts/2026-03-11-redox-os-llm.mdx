## "내가 올린 코드, 정말 그 사람이 맞아?"

오픈소스 프로젝트를 하다 보면 이런 의문 한 번쯤은 들어봤을 겁니다. 특히 보안에 민감한 커널이나 OS 프로젝트라면 더욱 그렇죠. Redox OS가 최근에 기여자 서명 정책과 더불어 LLM(대형 언어 모델) 사용 금지 정책을 도입한 배경도 바로 이런 신뢰 문제에서 출발했습니다.

### Redox OS가 기여자 서명 정책을 도입한 이유, 왜 지금일까?

Redox OS는 Rust로 작성된 마이크로커널 기반 OS로, 보안과 안정성을 최우선으로 합니다. 그런데 기여자가 많아지면서 커밋 출처를 명확히 확인해야 할 필요가 커졌죠. 단순히 GitHub 계정만으로는 충분하지 않다는 걸 경험한 겁니다.

기여자 서명 정책은 커밋이나 태그에 GPG 서명을 요구하는 방식입니다. 이걸 도입하면 누가 어떤 코드를 올렸는지, 그 코드가 변조되지 않았는지 검증할 수 있어요. 

실제로 GitHub 엔지니어링 블로그에서도 대형 오픈소스 프로젝트들이 이런 서명 정책을 도입하면서 보안 사고를 크게 줄였다는 사례가 있습니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

### LLM 금지 정책, AI가 코드를 대신 짜도 되는 걸까?

재미있는 점은 Redox OS가 LLM 사용을 금지한 겁니다. 요즘 AI 코딩 도우미가 워낙 잘 돼서 많은 개발자가 도움을 받는데, 왜 금지했을까요?

첫째, LLM이 생성한 코드는 저작권 문제나 라이선스 위반 소지가 있습니다. 둘째, AI가 작성한 코드는 보안 취약점이나 의도치 않은 버그를 포함할 가능성이 높아요. Redox OS처럼 보안이 생명인 프로젝트에서는 이런 위험을 감수할 수 없죠.

물론, AI가 완전히 나쁘다기보단, 프로젝트의 특성상 엄격한 검증과 책임 소재가 명확해야 한다는 의미입니다.

### 실제 적용 방법: GPG 서명 설정과 정책 강제화

기여자 서명을 요구한다면, 개발자 입장에서는 GPG 키를 만들고 Git에 등록하는 과정이 필수입니다. 간단한 예를 들어볼게요.

```bash
# GPG 키 생성
$ gpg --full-generate-key

# Git에 GPG 키 등록
$ gpg --list-secret-keys --keyid-format LONG
# 출력된 키 ID를 복사해서
$ git config --global user.signingkey <키ID>

# 커밋 시 자동 서명 설정
$ git config --global commit.gpgsign true
```

이렇게 하면 커밋할 때마다 자동으로 서명이 붙습니다. Redox OS 저장소에서는 서명 없는 커밋은 CI 빌드에서 자동으로 실패 처리하도록 설정해 두었죠.

### 정책 도입 후 겪은 현실적인 문제들

처음엔 "GPG 서명? 복잡한데?"라는 반응이 많았습니다. 실제로 신규 기여자들이 키 생성과 등록 과정에서 어려움을 겪었고, 이로 인해 PR 제출이 지연되기도 했죠. 

하지만 시간이 지나면서 서명 없는 커밋을 걸러내는 자동화 덕분에 코드 출처가 명확해지고, 보안 사고 위험이 눈에 띄게 줄었습니다. 

LLM 금지 정책은 내부 개발자들에게도 AI 코딩 도우미 사용을 자제시키는 문화가 필요했습니다. 다행히도 Redox OS 커뮤니티는 이 부분을 투명하게 공유하며 서로 감시하는 분위기가 만들어졌습니다.

### AI 모델 변경 시 백엔드 계약 점검이 왜 중요한지

여담으로, AI 관련 백엔드 개발하시는 분들은 아실 텐데, OpenAI API 문서에 따르면 AI 모델이 바뀔 때 단순히 모델 이름만 바꾸는 게 아니라 API 응답 스키마, 지연시간, 비용까지 꼼꼼히 점검해야 안정적인 서비스가 가능합니다[OpenAI API Documentation](https://platform.openai.com/docs/overview).

Redox OS의 LLM 금지 정책도 결국은 이런 "예측 불가능성"과 "책임 소재 불분명" 문제를 미리 차단하는 셈이죠.

### Redox OS 정책에서 배울 수 있는 점

- **서명 정책은 보안 강화의 기본**: 대형 오픈소스 프로젝트라면 기여자 서명은 필수라고 봐야 합니다.
- **자동화된 검증 파이프라인 구축**: CI에서 서명 여부를 강제하고, 실패 시 PR을 막는 게 현실적인 방법입니다.
- **LLM 사용에 대한 명확한 가이드라인 필요**: AI가 코드를 생성하는 시대에, 프로젝트 특성에 맞는 정책을 세우고 커뮤니티 합의를 이루는 게 중요합니다.

### 마무리하며

Redox OS의 사례는 단순히 "보안 정책 강화"를 넘어, 오픈소스 생태계에서 신뢰를 어떻게 지키고, AI 시대에 어떻게 대응할지에 대한 좋은 참고가 됩니다. 

개발자 입장에서는 GPG 서명 같은 보안 절차가 번거롭지만, 결국은 우리 코드와 사용자를 지키는 최소한의 안전장치라는 점을 기억했으면 해요.

---

참고로, 아래는 Redox OS 프로젝트에 기여할 때 사용할 수 있는 GPG 서명 커밋 예시입니다.

```bash
# 변경 사항을 스테이징
$ git add src/kernel/main.rs

# 서명된 커밋 생성
$ git commit -S -m "Fix memory leak in scheduler"

# 푸시
$ git push origin main
```

이렇게 하면 CI가 서명을 확인하고, 서명 없으면 빌드가 실패합니다.
