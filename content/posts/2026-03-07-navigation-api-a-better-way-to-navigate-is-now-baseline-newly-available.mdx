## 페이지 전환이 느려서 UX가 망가진 경험, 다들 있죠?

한 번 생각해보세요. SPA(싱글 페이지 애플리케이션)를 쓰면서도 페이지 전환할 때마다 전체가 리로드되거나, 불필요하게 많은 네트워크 요청이 발생해서 렌더링이 지연된 적 있나요? 저도 한때 그런 문제로 골머리를 앓았는데, 최근에 새로 나온 Navigation API 덕분에 그 고민이 많이 줄었어요.

이 API는 단순히 페이지를 이동하는 걸 넘어서, 네비게이션 이벤트를 세밀하게 제어할 수 있게 해줍니다. 덕분에 필요한 부분만 업데이트하고, 상태 관리도 훨씬 깔끔하게 할 수 있죠. 실제로 Cloudflare 같은 대형 서비스에서는 이걸 도입하고 초기 로딩 시간과 네트워크 요청 수가 눈에 띄게 줄었다고 해요[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).


## Navigation API가 SPA 네비게이션 방식을 어떻게 바꾸는 걸까?

기존 SPA에서는 URL이 바뀌어도 실제 페이지 전체를 다시 불러오는 게 아니라, 자바스크립트가 클라이언트 사이드에서 라우팅을 처리했죠. 그런데 문제는 이 과정에서 상태 관리가 복잡해지고, 불필요한 렌더링이 발생하기 쉬웠다는 겁니다.

Navigation API는 이걸 개선해줍니다. 네비게이션 이벤트를 브라우저가 직접 관리하면서, 개발자는 이벤트 훅을 통해 언제, 어떤 데이터를 로드할지, 어떤 컴포넌트를 업데이트할지 세밀하게 제어할 수 있어요. 덕분에 전체 페이지 리로드 없이 필요한 부분만 바꾸고, 렌더링 시간을 단축할 수 있죠[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).


## 실제 코드로 보는 Navigation API 사용법

아래는 React 프로젝트에서 Navigation API를 사용하는 간단한 예입니다. 페이지 전환 시 네비게이션 이벤트를 감지해, 필요한 데이터만 비동기로 불러오고 상태를 업데이트하는 패턴이에요.

```jsx
import React, { useEffect, useState } from 'react';

function useNavigationData() {
  const [data, setData] = useState(null);

  useEffect(() => {
    function onNavigate(event) {
      // 네비게이션이 시작될 때 필요한 데이터만 비동기로 로드
      event.intercept({
        async handler() {
          const response = await fetch(`/api/data${window.location.pathname}`);
          const json = await response.json();
          setData(json);
          event.transitionWhile(Promise.resolve());
        }
      });
    }

    window.navigation.addEventListener('navigate', onNavigate);

    return () => {
      window.navigation.removeEventListener('navigate', onNavigate);
    };
  }, []);

  return data;
}

export default function App() {
  const data = useNavigationData();

  if (!data) return <div>Loading...</div>;

  return <div>{data.content}</div>;
}
```

이 예시는 `window.navigation` 객체의 `navigate` 이벤트를 활용해, 페이지 전환 시점에 필요한 API 데이터를 미리 받아오고 상태를 업데이트합니다. 기존처럼 전체 페이지를 다시 그리는 대신, 필요한 부분만 바꾸기 때문에 렌더링 비용이 크게 줄어듭니다.


## 컴포넌트 기반 아키텍처에서 Navigation API가 왜 좋은 선택일까?

컴포넌트 단위로 상태를 관리하는 요즘 프론트엔드 아키텍처에서는, 네비게이션 이벤트를 세밀하게 제어하는 게 매우 중요합니다. Navigation API는 이런 요구에 딱 맞아요. 왜냐하면:

- **상태 일관성 유지가 쉬워짐**: 네비게이션 이벤트마다 상태를 명확히 갱신할 수 있고, 불필요한 리렌더링을 줄일 수 있어요.
- **동적 데이터 로딩 최적화**: 사용자가 실제로 필요할 때만 데이터를 로드해 네트워크 비용을 줄입니다.
- **확장성 높은 구조**: 네비게이션 이벤트를 훅으로 분리하면, 복잡한 라우팅 로직도 깔끔하게 관리할 수 있죠.

이 덕분에 대규모 SPA 프로젝트에서도 컴포넌트 재사용성과 유지보수성이 크게 향상됩니다[GitHub Engineering Blog](https://github.blog/category/engineering/).


## 도입할 때 주의할 점과 현실적인 한계

물론 Navigation API가 만능은 아닙니다. 몇 가지 고려할 점이 있는데요:

- **브라우저 지원 현황**: 아직 모든 브라우저가 완벽하게 지원하지 않으니, 폴리필이나 대체 로직을 준비해야 할 수 있어요.
- **학습 곡선**: 기존 라우팅 라이브러리와 다르게 이벤트 기반이라 익숙해지기까지 시간이 걸릴 수 있습니다.
- **복잡한 상태 관리**: 네비게이션 이벤트가 많아지면 오히려 상태 관리가 복잡해질 수 있으니, 명확한 구조 설계가 필수입니다.

이 점들은 실제 프로젝트에 도입하기 전에 충분히 테스트하고, 점진적으로 적용하는 게 좋습니다.


## 현업에서 Navigation API로 얻은 성능 개선 사례

Cloudflare 팀은 이 API를 도입하고 초기 로딩 시간과 네트워크 요청 수가 20% 이상 줄었다고 보고했어요. 특히 클라우드 플랫폼처럼 사용자 트래픽이 많고, 빠른 응답이 중요한 환경에서 큰 효과를 봤다고 합니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

이처럼 네비게이션 처리 방식을 브라우저와 협력해 최적화하면, UX가 눈에 띄게 좋아지고 서버 부하도 줄어드는 선순환이 만들어집니다.

### 마무리하며

처음엔 Navigation API가 별거 아닌 새 이벤트처럼 보일 수 있지만, SPA에서 페이지 전환 성능과 UX를 개선하는 데는 꽤 강력한 도구입니다. 특히 컴포넌트 기반 아키텍처를 유지하면서 동적 데이터 로딩과 상태 관리를 효율적으로 하려면 꼭 알아둬야 하죠.

저도 도입하면서 브라우저 지원과 상태 관리 복잡성 때문에 고생했지만, 점차 프로젝트 규모가 커질수록 그 가치가 분명히 느껴졌습니다. 여러분도 한번 실제 프로젝트에 적용해보시고, 네비게이션 이벤트를 직접 컨트롤하는 경험을 해보시길 추천합니다.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
