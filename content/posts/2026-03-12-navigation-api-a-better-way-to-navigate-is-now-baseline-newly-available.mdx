## "페이지가 왜 이렇게 느리지?" - 전통적인 내비게이션의 한계

프론트엔드 개발하다 보면 한 번쯤은 이런 이야기를 들어봤을 거예요. “페이지 전환할 때마다 전체가 새로고침되니 UX가 너무 떨어져.” 특히 다중 페이지 애플리케이션(MPA)에서 페이지가 무겁거나 네트워크가 느릴 때 이 문제는 극명하게 드러나죠. 전통적인 방식은 새 페이지를 요청하면 서버가 전체 HTML을 다시 내려주고, 브라우저가 새로 렌더링하는데, 이 과정에서 불필요한 자원 낭비와 사용자 체감 지연이 발생합니다.

이걸 개선하려고 SPA(싱글 페이지 애플리케이션) 프레임워크들이 등장했고, React, Vue 같은 라이브러리로 부분 업데이트를 시도했지만 상태 관리가 복잡해지면서 또 다른 골치가 생기곤 했죠. 그러다 최근에 Navigation API가 새롭게 Baseline으로 지원되면서, 프론트엔드 내비게이션 경험을 한 단계 업그레이드할 수 있는 기회가 왔습니다.


## Navigation API가 기존 내비게이션과 다른 점은?

Navigation API는 브라우저 내비게이션을 제어할 수 있는 새로운 표준 API예요. 이걸 쓰면 페이지 전환 시 전체 페이지를 리로드하지 않고, 필요한 부분만 업데이트할 수 있습니다. 즉, 서버에서 전체 HTML을 다시 받지 않고도 사용자가 보는 화면을 바꿀 수 있다는 뜻이죠. 

GitHub 엔지니어링 블로그에 따르면 이 방식은 사용자 경험을 크게 향상시키면서도, 불필요한 리소스 낭비를 줄여 성능 최적화에 효과적이라고 해요[GitHub Engineering Blog](https://github.blog/category/engineering/). 실제로 Cloudflare도 이 API를 도입해 네트워크 요청을 최적화하고 캐싱 전략을 개선, 서버 부하를 줄이고 응답 속도를 빠르게 만들었다고 합니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).


## 컴포넌트 기반 구조와 Navigation API의 궁합이 좋은 이유

SPA에서 컴포넌트 단위로 UI를 쪼개다 보면 상태 관리가 복잡해지는 문제가 흔히 발생하죠. 상태가 여러 컴포넌트에 분산되면, 페이지 전환 시 상태 동기화가 어렵고, 버그가 생기기 쉽습니다. Martin Fowler의 아키텍처 가이드에 따르면, Navigation API는 이런 상태 관리 문제를 완화하는 데 도움을 줍니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

왜냐하면 Navigation API는 브라우저의 내비게이션 이벤트를 직접 다루면서, 필요한 컴포넌트만 선택적으로 업데이트할 수 있기 때문입니다. 예를 들어, 전체 페이지를 다시 렌더링할 필요 없이, 변경된 데이터가 바뀐 컴포넌트에만 반영되도록 할 수 있죠. 이게 결국 확장성 높은 프론트엔드 아키텍처를 만드는 데 큰 힘이 됩니다.


## 실제로 Navigation API를 써서 페이지 전환을 제어해보기

아래는 Navigation API를 활용해 간단히 페이지 내비게이션을 제어하는 예시입니다. 이 코드는 사용자가 링크를 클릭했을 때 전체 페이지를 다시 로드하지 않고, 필요한 부분만 비동기적으로 가져와서 업데이트하는 패턴을 보여줍니다.

```javascript
// navigationHandler.js

// Navigation API가 지원되는지 먼저 확인
if ('navigation' in window) {
  window.navigation.addEventListener('navigate', async (event) => {
    event.intercept({
      async handler() {
        // 새 URL에서 필요한 데이터만 fetch
        const response = await fetch(event.destination.url, { headers: { 'X-Requested-With': 'fetch' } });
        if (response.ok) {
          const html = await response.text();
          // 특정 DOM 영역만 교체
          document.getElementById('app-root').innerHTML = html;
          // 히스토리 상태도 수동으로 관리
          window.history.pushState({}, '', event.destination.url);
        } else {
          // 실패하면 기본 내비게이션
          window.location.href = event.destination.url;
        }
      }
    });
  });
} else {
  console.warn('Navigation API를 지원하지 않는 브라우저입니다.');
}
```

이 예시는 SPA 라이브러리를 쓰지 않고도, Navigation API를 통해 부분 업데이트를 구현한 간단한 사례입니다. 물론 실제 서비스에서는 상태 관리, 에러 처리, 캐싱, 애니메이션 등 여러 부분을 더 신경 써야 하지만, 기본 아이디어는 이렇습니다.


## Navigation API 도입 시 고려해야 할 현실적인 한계

처음 이 API를 접하면 "와, 완전 혁신적이다!" 싶지만, 현실은 늘 그렇듯 복잡합니다. 

- **브라우저 호환성**: 아직 모든 브라우저에서 완벽 지원하지 않아요. 따라서 폴리필이나 대체 로직이 필요할 수 있습니다.
- **SEO 문제**: 서버 사이드 렌더링(SSR)을 병행하는 경우, 클라이언트 내비게이션과 SSR 결과가 충돌하지 않도록 신경 써야 합니다.
- **상태 동기화**: Navigation API가 상태 관리를 돕긴 하지만, 복잡한 애플리케이션에서는 여전히 전역 상태 관리 라이브러리와의 조합이 필요합니다.
- **학습 곡선**: 기존 내비게이션 방식과 다르다 보니 팀 내에서 개념 공유와 코드 리뷰에 시간이 좀 더 들어갑니다.


## Navigation API로 사용자 체감 성능을 얼마나 개선할 수 있을까?

InfoQ 아키텍처 기사에 따르면, Navigation API를 활용하면 초기 로드 이후 페이지 전환 비용을 30~50% 이상 줄일 수 있다고 해요[InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/). 물론 이 수치는 애플리케이션 구조, 네트워크 환경, 캐싱 전략 등에 따라 달라지지만, 체감 속도가 확실히 개선되는 건 분명합니다.

실제로 Cloudflare는 Navigation API 도입 후 평균 페이지 응답 시간이 20% 이상 개선되었고, 서버 요청 수도 15% 줄어들었다고 보고했습니다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).


## 내비게이션 API를 적용할 때 추천하는 컴포넌트 구조 설계

저희 팀에서는 Navigation API를 도입하면서 컴포넌트를 다음과 같이 설계했어요.

- **페이지 단위 컴포넌트**: URL 별로 최상위 페이지 컴포넌트를 구분하고, Navigation API 이벤트 발생 시 해당 컴포넌트만 교체합니다.
- **상태 격리**: 페이지별로 상태를 최대한 격리해서, 페이지 전환 시 상태 충돌을 최소화합니다.
- **공통 레이아웃 컴포넌트 유지**: 헤더, 푸터 등 공통 영역은 유지하면서, 콘텐츠 영역만 교체하는 방식으로 렌더링 비용을 줄입니다.

이런 구조는 Navigation API가 제공하는 부분 업데이트 기능과 찰떡궁합입니다. 실제로 저희는 이 구조 덕분에 페이지 전환 속도가 평균 300ms 이하로 안정화되었고, 사용자 이탈률도 눈에 띄게 줄었어요.


---

Navigation API는 아직 완벽한 해답은 아니지만, 점점 더 많은 브라우저에서 지원하고 있고, 실제 대형 서비스에서 효과가 입증되고 있습니다. 복잡한 SPA 상태 관리 문제를 해결하고, 사용자 경험을 개선하는 데 관심 있다면 꼭 한번 시도해볼 만한 기술이에요.
