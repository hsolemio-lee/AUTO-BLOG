### "왜 또 String만 쓰냐고요?"

처음 Spring Data를 접했을 때, 저도 그냥 편해서 거의 모든 걸 String으로 처리했었어요. 근데 어느 순간부터 쿼리 성능이 떨어지고, 코드가 헷갈리기 시작하더라고요. 특히 날짜나 숫자 같은 타입이 섞일 때, String으로 다루면 변환도 번거롭고, 실수도 잦고요. 이걸 어떻게 하면 좀 더 깔끔하고 빠르게 할 수 있을까 고민하다가, Spring Data가 제공하는 고급 데이터 타입 지원 기능을 제대로 활용해보기로 했습니다.

---

## Spring Data에서 String을 넘어서야 하는 진짜 이유

단순히 "문자열 대신 다른 타입을 쓰자"는 게 아니라, 그게 왜 중요한지부터 짚어볼게요. Spring Data는 기본적으로 String 타입을 많이 쓰지만, 숫자(Integer, Long), 날짜(LocalDate, Instant), 컬렉션(List, Set), 그리고 사용자 정의 객체 같은 복잡한 타입도 매핑할 수 있어요. 

이게 중요한 이유는 크게 세 가지입니다.

1. **타입 안정성 확보**: String으로 모든 걸 처리하면, 예를 들어 날짜를 "2023-06-01" 이런 식으로 넣고 빼는 과정에서 포맷이 틀리거나, 숫자가 아닌 값이 들어오는 오류가 생기기 쉽죠. 반면에 LocalDate나 Integer 같은 타입을 쓰면 컴파일 타임에 오류를 잡을 수 있어요.

2. **쿼리 성능 향상**: 데이터베이스에 숫자나 날짜 타입으로 저장하면, 인덱스 활용이나 범위 쿼리가 훨씬 빠릅니다. String으로 저장하면 내부적으로 변환 작업이 추가되고, 쿼리 최적화도 어렵죠.

3. **코드 가독성과 유지보수성 개선**: 명확한 타입 덕분에 코드가 직관적이고, 동료가 코드를 읽을 때도 의도가 명확해집니다. 대규모 프로젝트에서 이게 얼마나 중요한지는 말 안 해도 아시죠?

이런 점들은 [Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)에서도 명확히 언급되어 있습니다.

## Spring Framework 코어가 제공하는 타입 변환과 제네릭의 힘

Spring Data가 다양한 타입을 지원하는 건 Spring Framework 코어의 강력한 타입 변환 기능 덕분이에요. 제네릭과 Converter 인터페이스 덕분에, 복잡한 데이터 타입도 손쉽게 다룰 수 있죠.

예를 들어, 엔티티 클래스에서 다음과 같이 날짜 타입을 바로 매핑할 수 있습니다.

```java
@Entity
public class Event {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    private LocalDate eventDate; // String 대신 LocalDate 사용

    // getters, setters
}
```

이렇게 하면, Spring Data가 내부적으로 `LocalDate`를 데이터베이스의 `DATE` 타입으로 변환해주고, 쿼리 결과도 `LocalDate` 객체로 받아올 수 있어요. 따로 변환 로직을 짤 필요가 없다는 점이 정말 편합니다.

그리고 제네릭 덕분에, 예를 들어 컬렉션 타입을 필드로 쓸 때도 타입 안정성을 잃지 않고 깔끔하게 표현할 수 있죠.

이 부분은 [Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html) 문서에서 자세히 다루고 있으니 참고해보세요.

## 실전에서 만난 고급 타입 활용 예시: 숫자, 날짜, 컬렉션 그리고 커스텀 객체

제가 최근에 참여한 프로젝트에서는 사용자 주문 정보를 저장하는 도메인 모델을 설계하면서, String 대신 다음과 같은 타입을 적극 활용했습니다.

- 주문 금액은 `BigDecimal` 타입으로 정확한 소수점 연산을 보장
- 주문 날짜는 `Instant` 타입으로 타임존 이슈 최소화
- 주문 상태는 enum 타입으로 상태 관리 명확화
- 주문 내역은 `List<OrderItem>` 컬렉션으로 주문 상품 목록 표현

아래는 간단한 예시 코드입니다.

```java
@Entity
public class Order {
    @Id
    @GeneratedValue
    private Long id;

    private BigDecimal amount; // 금액

    private Instant orderTime; // 주문 시각

    @Enumerated(EnumType.STRING)
    private OrderStatus status; // 주문 상태

    @OneToMany(cascade = CascadeType.ALL, fetch = FetchType.LAZY)
    private List<OrderItem> items = new ArrayList<>();

    // getters, setters
}

@Entity
public class OrderItem {
    @Id
    @GeneratedValue
    private Long id;

    private String productName;

    private Integer quantity;

    // getters, setters
}

public enum OrderStatus {
    PENDING, PAID, SHIPPED, CANCELLED
}
```

이렇게 하면 주문 상태를 String으로 관리할 때보다 오타나 잘못된 상태값 입력이 줄어들고, 쿼리 작성 시에도 `status = 'PAID'` 대신 enum 상수를 활용해 타입 안전성을 확보할 수 있습니다.

또한, 컬렉션인 `items` 필드를 통해 주문 내역을 자연스럽게 표현할 수 있어서, 복잡한 조인 쿼리를 줄이고 객체지향 설계에 충실할 수 있었어요.

## 문자열만 쓰다가 고급 타입 도입할 때 주의할 점

처음에는 "이거 별거 아니네" 싶지만, 실제로 적용하다 보면 몇 가지 걸림돌이 있습니다.

1. **데이터베이스 스키마와 매핑 문제**: DB 컬럼 타입과 Java 타입이 정확히 맞아야 합니다. 예를 들어, MySQL에서 `DATETIME` 컬럼을 `LocalDateTime`으로 매핑하려면, Hibernate Dialect 설정이 필요할 수 있어요.

2. **직렬화/역직렬화 비용**: JSON 직렬화 시, 복잡한 객체나 컬렉션은 기본 String보다 무겁습니다. 그래서 REST API 응답에 쓸 때는 DTO로 변환하거나 필요한 필드만 골라 보내는 전략이 필요합니다.

3. **쿼리 작성의 복잡성 증가**: 컬렉션이나 임베디드 객체를 쿼리할 때 JPQL이나 QueryDSL 문법이 좀 더 복잡해질 수 있습니다. 특히 성능 튜닝 시 주의가 필요해요.

4. **타입 변환기 등록 필요성**: 사용자 정의 타입을 쓰면, Spring Converter나 AttributeConverter를 직접 구현해서 등록해야 하는 경우가 있습니다.

이런 점들은 [Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance) 문서에서도 언급되어 있으니 참고하세요.

## 실제로 고급 타입 쓰고 나서 느낀 변화들

제가 직접 경험한 변화는 크게 세 가지였어요.

- **쿼리 성능 개선**: 날짜 범위 쿼리나 숫자 기반 정렬이 훨씬 빨라졌습니다. String으로 처리할 때는 인덱스 활용이 제한적이었거든요.

- **코드 품질 향상**: 타입 안정성 덕분에 컴파일 타임에 오류를 잡을 수 있었고, 코드 리뷰 시 의도가 명확해졌습니다.

- **유지보수 시간 감소**: 새로운 기능 추가나 버그 수정 시, 타입 덕분에 실수가 줄고 리팩터링이 쉬워졌어요.

GitHub 엔지니어링 블로그에서도 이런 사례들이 소개되는데, 명확한 도메인 객체와 컬렉션 타입 활용이 대규모 서비스 유지보수에 큰 도움이 된다고 합니다([GitHub Engineering Blog](https://github.blog/category/engineering/)).

## 마무리하며: 지금 당장 시도해볼 수 있는 간단한 팁

- **엔티티 필드에 String 대신 적합한 타입을 써보세요.** 숫자면 Integer, 날짜면 LocalDate 또는 Instant로.
- **Enum 타입을 적극 활용해 상태값을 관리하세요.** 오타 걱정 끝.
- **컬렉션 매핑은 꼭 필요할 때만, 그리고 LAZY 로딩 설정으로 성능 관리하세요.**
- **복잡한 타입은 AttributeConverter를 만들어서 명확하게 변환하세요.**

예를 들어, 커스텀 타입을 DB에 저장할 때는 이렇게 간단히 만들 수 있습니다.

```java
@Converter(autoApply = true)
public class MoneyConverter implements AttributeConverter<Money, String> {
    @Override
    public String convertToDatabaseColumn(Money attribute) {
        return attribute == null ? null : attribute.toString();
    }

    @Override
    public Money convertToEntityAttribute(String dbData) {
        return dbData == null ? null : Money.parse(dbData);
    }
}
```

이런 작은 노력들이 쌓여서, 결국 더 빠르고 유지보수하기 좋은 백엔드 시스템이 만들어집니다.
