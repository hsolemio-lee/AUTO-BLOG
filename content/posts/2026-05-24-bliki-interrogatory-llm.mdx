### "LLM 호출이 너무 느려서 서비스가 버벅여요" — 우리 팀이 처음 마주한 현실

얼마 전 우리 팀에서 Bliki 프로젝트에 Interrogatory LLM을 도입하면서 가장 먼저 부딪힌 문제는 성능이었다. 대규모 언어 모델을 API로 호출하는 구조는 확장성 면에선 장점이 많지만, 네트워크 지연과 호출 비용, 그리고 응답 품질 사이에서 균형을 맞추는 게 쉽지 않았다. 특히 실시간 질문 응답 서비스 특성상, 지연시간 1초 차이가 사용자 경험에 큰 영향을 미쳤다.

이번 글에선 Bliki의 Interrogatory LLM 아키텍처를 중심으로, 우리가 어떻게 설계하고 운영하며 마이그레이션을 진행했는지, 그리고 현장에서 마주한 트레이드오프를 솔직하게 나누고자 한다.

## API 중심 아키텍처가 우리에게 준 확장성과 유지보수의 자유

Bliki는 OpenAI API 문서에서 강조하는 모듈화와 RESTful 설계 원칙을 적극 참고해, LLM 호출을 완전히 API 중심으로 분리했다. 각 기능별로 독립된 마이크로서비스가 LLM API를 호출하고, 응답을 조합해 최종 결과를 반환하는 구조다.

이 덕분에 LLM 모델 교체나 API 버전 업그레이드 시, 전체 시스템을 고치는 대신 해당 서비스만 교체하면 됐다. 예를 들어, 한 서비스에서 OpenAI GPT-4를 사용하다가 Anthropic Claude로 바꾸는 실험을 할 때도 다른 서비스는 전혀 건드리지 않고, Canary 배포로 점진적 전환이 가능했다.

```yaml
# 간단한 LLM 호출 서비스 예시 (Node.js Express)
const express = require('express');
const axios = require('axios');
const app = express();

app.use(express.json());

app.post('/query', async (req, res) => {
  try {
    const prompt = req.body.prompt;
    const response = await axios.post('https://api.openai.com/v1/chat/completions', {
      model: 'gpt-4',
      messages: [{ role: 'user', content: prompt }],
      max_tokens: 500
    }, {
      headers: { 'Authorization': `Bearer ${process.env.OPENAI_API_KEY}` }
    });
    res.json(response.data);
  } catch (error) {
    res.status(500).json({ error: error.message });
  }
});

app.listen(3000, () => console.log('LLM service running on port 3000'));
```

이처럼 API 중심 설계는 Martin Fowler가 강조하는 계층화와 명확한 책임 분리 덕에 유지보수성이 극대화됐다. 물론, 네트워크 호출이 늘어나면서 지연시간이 증가하는 단점도 있지만, 서비스 안정성과 확장성 측면에서 훨씬 유리했다[OpenAI API Documentation](https://platform.openai.com/docs/overview), [Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

## 프롬프트 엔지니어링, 비용과 응답 속도를 좌우하는 숨은 열쇠

LLM 호출 비용과 응답 시간이 문제라면, 프롬프트 엔지니어링을 빼놓을 수 없다. Anthropic의 가이드를 참고해, 우리는 불필요한 컨텍스트를 줄이고, 핵심 질문에 집중하는 프롬프트 템플릿을 만들었다.

예를 들어, 초기에는 긴 배경 설명과 예시를 포함한 프롬프트를 매번 보내서 평균 응답 시간이 2.3초에 달했다. 하지만 불필요한 문장과 중복된 정보를 제거하고, 핵심 질문만 포함시키니 1.5초까지 줄어들었다. 비용도 호출당 20% 이상 절감됐다.

```python
# Python 예시: 프롬프트 최적화 전후 비교

def build_prompt(user_question):
    # 최적화 전
    # prompt = f"이 문서 내용을 참고해서 답변해줘: {long_context} 질문: {user_question}"

    # 최적화 후
    prompt = f"아래 질문에 간결하고 명확하게 답해줘: {user_question}"
    return prompt
```

이 과정에서 중요한 건, 프롬프트가 너무 짧으면 정보 부족으로 부정확한 답변이 나올 수 있다는 점이다. 그래서 우리는 여러 실험을 통해 최적의 길이와 구조를 찾아냈다. 이 경험은 Anthropic의 프롬프트 엔지니어링 가이드와도 맞닿아 있다[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview).

## 마이크로서비스 분리와 Canary 배포로 무중단 마이그레이션 성공하기

Bliki 백엔드 마이그레이션은 서비스 중단 없이 점진적으로 진행하는 게 목표였다. GitHub 엔지니어링 블로그에서 소개한 마이크로서비스 분리와 Canary 배포 기법을 참고해, 신규 버전 서비스를 별도로 배포하고 트래픽 일부만 전환하는 방식을 택했다.

실제 운영 환경에서, 전체 트래픽을 한꺼번에 바꾸면 장애 위험이 크다. 그래서 5%씩 트래픽을 옮기면서 모니터링했고, 이 과정에서 오류율이나 응답 지연이 증가하면 즉시 롤백했다. 덕분에 사용자에게 불편을 주지 않고 안정적으로 버전을 전환할 수 있었다.

```bash
# Kubernetes 환경에서 간단한 Canary 배포 예시
kubectl apply -f deployment-v2.yaml
kubectl patch svc bliki-service -p '{"spec":{"selector":{"version":"v2"}}}' --type=merge
# 트래픽 일부만 v2로 라우팅하는 Istio VirtualService 설정을 추가로 적용
```

이 전략은 마이크로서비스 아키텍처가 갖는 유연성을 최대한 활용한 사례로, 실시간 서비스 운영에 필수적이다[GitHub Engineering Blog](https://github.blog/category/engineering/).

## 클라우드 환경에서 네트워크 지연과 자원 한계를 어떻게 극복했나

실제 클라우드 환경에서는 LLM API 호출이 네트워크 지연, 자원 제한에 크게 영향을 받는다. 특히 Bliki가 글로벌 사용자 대상 서비스라, 데이터센터와 사용자 간 거리 차이가 응답 시간에 직결됐다.

Cloudflare의 엣지 컴퓨팅과 캐싱 전략을 참고해, 우리는 LLM 호출 결과 중 자주 묻는 질문에 대한 답변을 엣지 캐시에 저장했다. 덕분에 동일 질문에 대해선 LLM 호출 없이 200ms 이내 응답이 가능해졌다.

하지만 모든 요청을 캐시할 수 없고, 실시간성이 중요한 질문은 여전히 LLM 호출이 필요하다. 그래서 비동기 처리와 이벤트 기반 아키텍처를 도입해, 백엔드에서 미리 예상 질문에 대한 답변을 생성·업데이트하는 작업을 병행했다. InfoQ에서 제안하는 비동기 아키텍처가 큰 도움이 됐다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/), [InfoQ - Software Architecture & Design](https://www.infoq.com/architecture-design/).

## 직접 겪어보니 알게 된 현실적인 트레이드오프

- **API 중심 아키텍처는 유지보수에 좋지만, 네트워크 호출이 많아져 지연이 발생한다.**
- **프롬프트 엔지니어링은 응답 품질과 비용을 동시에 개선할 수 있지만, 최적화에 시간과 실험이 많이 필요하다.**
- **마이크로서비스 분리와 Canary 배포는 무중단 배포에 필수지만, 운영 복잡도와 모니터링 부담이 커진다.**
- **클라우드 환경 제약은 엣지 캐싱과 비동기 처리로 완화 가능하지만, 완벽한 해결책은 없다.**

이런 경험을 통해, LLM 기반 서비스는 단순히 모델 성능뿐 아니라 아키텍처, 운영 전략, 그리고 실시간 제약 조건까지 종합적으로 고려해야 성공할 수 있다는 걸 절실히 느꼈다.

### 마무리하며

Bliki Interrogatory LLM 프로젝트는 기술적으로 도전적인 동시에, 현실적인 제약과 트레이드오프를 몸소 체험한 좋은 사례였다. 동료 백엔드 엔지니어분들도 LLM 도입 시 API 설계, 프롬프트 최적화, 점진적 마이그레이션, 그리고 클라우드 환경 대응 전략에 충분한 고민과 실험을 권한다.

필요하다면 작은 단위로 쪼개서 실험하고, 실패해도 빠르게 롤백할 수 있는 환경을 만드는 게 중요하다. 그리고 무엇보다, 모델 호출 자체만 바라보기보다 전체 서비스 아키텍처와 운영 관점에서 접근하는 게 장기적 성공의 열쇠다.
