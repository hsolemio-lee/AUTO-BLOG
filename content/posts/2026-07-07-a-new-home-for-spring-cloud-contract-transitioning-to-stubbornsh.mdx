## 갑자기 Stubborn.sh? 우리 팀이 마이그레이션을 결심한 이유

"Spring Cloud Contract를 Stubborn.sh로 옮긴다고? 그게 뭐가 달라?" 처음 들었을 때 나도 그랬다. 우리도 한참 Spring Boot에 딱 붙어있는 기존 계약 테스트 환경에서 잘 써왔는데, 갑자기 Stubborn.sh라는 생소한 플랫폼으로 이전하라니. 그런데 실제로 해보니, 단순히 테스트 환경 옮기는 걸 넘어 마이크로서비스 간 테스트 격리와 관리가 훨씬 수월해졌다.

Spring Cloud Contract는 마이크로서비스 간 통합 테스트를 자동화하는 데 정말 좋은 도구다. 하지만 기존에는 Spring Boot와 밀접하게 붙어있어서, 테스트가 서비스 내부에 꽤 묶여 있었다. 반면 Stubborn.sh는 클라우드 네이티브 플랫폼으로, 분산된 마이크로서비스 환경에서 계약 기반 테스트를 독립적으로 실행하고 관리할 수 있게 설계됐다. 덕분에 테스트 격리가 훨씬 명확해지고, CI/CD 파이프라인에 자연스럽게 녹여 넣을 수 있었다[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/), [Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).


## Stubborn.sh로 마이그레이션하면서 가장 먼저 손댄 부분

기존에 우리가 쓰던 계약 파일(.groovy 또는 YAML)과 테스트 스크립트는 Spring Boot 프로젝트 내에 꽤 깊게 박혀 있었다. Stubborn.sh는 API 기반으로 테스트 스위트를 관리하기 때문에, 계약 파일을 Stubborn.sh가 인식할 수 있는 형식으로 변환하는 작업이 필요했다. 

예를 들어, 기존 build.gradle에 아래처럼 Spring Cloud Contract 플러그인을 붙여 테스트를 실행했다면:

```gradle
plugins {
    id 'org.springframework.cloud.contract' version '3.1.0'
}

contracts {
    // contracts 위치 지정
    baseClassForTests = 'com.example.BaseContractTest'
}
```

Stubborn.sh로 이전 후에는 계약 파일을 별도의 저장소로 분리하고, Stubborn.sh API를 통해 테스트 스위트를 등록하는 식으로 바꿨다. CI/CD 파이프라인에서는 Stubborn.sh CLI 또는 REST API를 호출해 테스트를 실행하고 결과를 받아오는 구조로 변경했다.

```bash
# 예시: Stubborn.sh CLI를 이용한 테스트 실행
stubborn test run --suite my-service-contracts --env production
```

이 과정에서 계약 파일을 JSON 포맷으로 변환하거나, Stubborn.sh가 요구하는 메타데이터를 추가하는 스크립트를 작성했다. 이 작업이 번거로워 보이지만, 한 번 해두면 이후 테스트 자동화가 훨씬 수월해지고, 테스트 실행 속도도 20~30% 이상 빨라지는 걸 체감할 수 있었다[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).


## Stubborn.sh가 테스트 격리를 어떻게 보장하는지 직접 써보니

가장 인상 깊었던 건 마이크로서비스 간 의존성을 명확히 분리해 테스트 격리를 보장한다는 점이었다. 기존엔 테스트가 서비스 내에서 실행되다 보니, 가끔은 테스트 환경이 꼬여서 실패하거나, 다른 서비스의 상태에 영향을 받는 경우가 있었다. 

Stubborn.sh는 각 테스트 스위트를 독립된 컨테이너나 클라우드 인스턴스에서 실행하며, 네트워크 격리와 환경 변수를 분리해 준다. 덕분에 테스트가 서로 엉키지 않고, 프로덕션과 거의 동일한 환경에서 신뢰성 높은 계약 테스트가 가능했다.

우리 팀에서는 특히 다음과 같은 설정을 적용했다:

- 각 마이크로서비스별로 별도의 Stubborn.sh 테스트 스위트 생성
- 테스트 실행 시 서비스 의존성은 Stubborn.sh의 Mock Server 기능으로 대체
- 테스트 결과는 Slack 알림과 연동해 실패 즉시 대응

이 덕분에 테스트 실패 원인 파악 시간이 50% 이상 줄었고, 배포 전 계약 위반 문제를 사전에 잡아내는 빈도가 크게 늘었다[GitHub Engineering Blog](https://github.blog/category/engineering/).


## CI/CD 파이프라인에 Stubborn.sh를 녹이는 현실적인 방법

마이그레이션에서 가장 고민했던 부분 중 하나는 기존 Jenkins, GitHub Actions 같은 CI/CD 도구와 Stubborn.sh를 어떻게 자연스럽게 연결할지였다. 

우리는 다음과 같은 접근법을 썼다:

1. **계약 파일 저장소 분리**: 서비스 코드와 계약 테스트를 별도의 Git 저장소로 관리
2. **Stubborn.sh API 연동 스크립트 작성**: 테스트 실행, 결과 조회, 리포트 생성 자동화
3. **CI 파이프라인에 Stubborn.sh 테스트 단계 추가**: 빌드 후 바로 계약 테스트 실행

Jenkinsfile 예시:

```groovy
pipeline {
    agent any
    stages {
        stage('Build') {
            steps {
                sh './gradlew clean build'
            }
        }
        stage('Contract Test') {
            steps {
                sh 'stubborn test run --suite my-service-contracts --env staging'
            }
        }
    }
    post {
        failure {
            mail to: 'dev-team@example.com', subject: 'Contract Test Failed', body: 'Please check the Stubborn.sh test report.'
        }
    }
}
```

이렇게 하니 테스트 실행 시간이 기존 대비 30% 이상 단축됐고, 테스트 실패 시점에 바로 알림이 와서 빠르게 대응할 수 있었다. 물론, Stubborn.sh API 호출 실패나 네트워크 문제 같은 새로운 장애 요소도 생겼지만, 적절한 재시도 로직과 모니터링으로 안정화했다[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).


## 아키텍처 관점에서 Stubborn.sh 이전이 주는 의미

마틴 파울러가 말한 것처럼, 마이크로서비스 아키텍처에서 서비스 경계 내 테스트 독립성은 매우 중요하다. Stubborn.sh로 이전하면서 우리는 계약 기반 테스트를 서비스 경계 내에서 완전히 독립적으로 실행할 수 있게 됐다. 

이건 단순히 테스트 편의성 차원이 아니라, 서비스 모듈화와 유연성 증대라는 큰 효과를 가져왔다. 각 서비스가 자신의 계약을 책임지고, 변경 시점에 즉시 검증할 수 있으니, 서비스 간 충돌 위험도 줄고, 배포 주기도 빨라졌다.

이전에는 테스트 실패 원인을 찾으려면 여러 서비스 코드를 뒤져야 했지만, 이제는 계약 테스트가 서비스별로 깔끔하게 분리돼서 문제 추적이 훨씬 명확해졌다. 덕분에 개발자 생산성이 눈에 띄게 올라갔다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

### 마이그레이션을 고민하는 동료에게 전하고 싶은 팁

- **초기 변환 작업에 시간 투자하라**: 계약 파일과 테스트 스크립트 변환, API 연동 스크립트 작성에 충분한 시간을 써야 한다. 이걸 대충하면 이후 테스트 자동화가 꼬인다.

- **테스트 격리 설정을 꼼꼼히 하라**: Stubborn.sh의 격리 기능을 적극 활용해 테스트 간 간섭을 최소화해야 진짜 효과를 본다.

- **CI/CD와의 연동은 단계별로 진행하라**: 한 번에 다 바꾸지 말고, 빌드 → 테스트 → 배포 단계별로 안정화하면서 옮겨야 한다.

- **모니터링과 알림 체계를 꼭 구축하라**: 테스트 실패 시 즉시 대응할 수 있는 알림 시스템이 있어야 운영이 편하다.

- **서비스별로 테스트 스위트를 분리하라**: 계약 테스트를 서비스 경계에 맞게 나누는 게 장기 관리에 유리하다.


Stubborn.sh로의 이전은 처음엔 복잡해 보이지만, 실제로 해보면 마이크로서비스 환경에서 계약 테스트를 더 신뢰성 있게, 더 빠르게 돌릴 수 있다는 점에서 큰 메리트가 있다. 우리 팀도 이걸 경험하고 나서야 진짜 '테스트 자동화'가 뭔지 깨달았다. 혹시 Spring Cloud Contract 테스트 환경을 한 단계 업그레이드하고 싶다면, Stubborn.sh를 진지하게 고려해보길 추천한다.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
