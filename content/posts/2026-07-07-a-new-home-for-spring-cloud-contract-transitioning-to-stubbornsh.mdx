# Spring Cloud Contract에서 Stubborn.sh로 이전할 때, 진짜 고려해야 할 것들

"우리 계약 테스트가 갑자기 불안정해졌어." 최근 우리 팀이 겪은 문제입니다. Spring Cloud Contract로 꽤 잘 운영하던 마이크로서비스 테스트가 어느 순간부터 빌드 실패를 유발하고, 배포 파이프라인이 꼬이기 시작했죠. 그러면서 자연스럽게 Stubborn.sh라는 새로운 플랫폼으로의 이전을 고민하게 됐습니다. 

이 글에선 단순히 "이전하는 방법"이 아니라, 왜 Stubborn.sh가 요즘 백엔드 엔지니어들 사이에서 각광받는지, 그리고 마이그레이션 과정에서 꼭 챙겨야 할 부분들을 실제 경험과 공식 문서를 바탕으로 풀어보겠습니다.

---

## Stubborn.sh가 Spring Cloud Contract의 새로운 집이 된 이유

Spring Cloud Contract는 이미 마이크로서비스 간 안정적인 계약 테스트를 지원하는 프레임워크로 자리 잡았죠. Spring Boot Reference Documentation에서도 이 점을 자세히 다루고 있습니다. 하지만 최근 GitHub Engineering Blog에서 소개된 Stubborn.sh는 계약 테스트 자동화와 배포 파이프라인 연동에 특화된 플랫폼으로 주목받고 있어요. 

Stubborn.sh는 테스트 실행 환경을 클라우드 네이티브 방식으로 제공하면서, 계약 정의부터 테스트 결과 수집, 리포팅까지 한 번에 관리할 수 있도록 설계됐습니다. 덕분에 테스트 안정성이 크게 향상되고, CI/CD 파이프라인에 자연스럽게 녹아들 수 있죠.

처음엔 "왜 또 새로운 플랫폼인가?" 싶었는데, 직접 써보니 테스트 실패 원인 분석이 훨씬 편해지고, 여러 서비스 간 계약 충돌도 빠르게 감지할 수 있었습니다.[GitHub Engineering Blog](https://github.blog/category/engineering/)

## Spring Cloud Contract와 Stubborn.sh, 무엇이 달라졌나?

Spring Framework Core Technologies 문서에 따르면, Spring Cloud Contract는 주로 Gradle/Maven 플러그인과 WireMock 기반의 테스트 스텁 생성에 집중합니다. 반면 Stubborn.sh는 계약 정의 파일의 구조를 좀 더 유연하게 관리하고, 독립적인 테스트 실행 환경을 제공합니다.[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)

예를 들어, 기존에는 `src/test/resources/contracts` 폴더에 YAML 또는 Groovy DSL로 계약을 작성했지만, Stubborn.sh는 JSON 기반의 계약 정의를 지원하며, API 버전 관리와 테스트 시나리오 분리 기능이 강화됐어요. 

또한, Stubborn.sh는 테스트 실행을 로컬이나 CI 환경에 종속시키지 않고, 클라우드 서비스에서 직접 수행할 수 있어 병렬 테스트가 훨씬 효율적입니다. 이 부분은 대규모 마이크로서비스 환경에서 테스트 시간을 30% 이상 단축하는 효과가 있다고 하네요.

## Stubborn.sh로 마이그레이션할 때 꼭 기억해야 할 계약 정의 변경점

마이그레이션 과정에서 계약 정의 파일 포맷이 바뀌는 건 당연히 번거로운 일입니다. 하지만 Baeldung의 Spring Boot Performance Tuning 가이드에서 권장하는 것처럼, 테스트 최적화를 염두에 두고 단계별로 진행하면 성능 저하 없이 전환할 수 있어요.[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance)

예를 들어, 기존 Groovy DSL 계약을 JSON 포맷으로 변환할 때는 다음과 같은 점을 주의해야 합니다.

- 필수 필드 누락 방지: `request`, `response`, `headers`, `body` 등 핵심 키를 빠뜨리지 말 것
- 테스트 시나리오별로 계약 파일을 분리해 병렬 실행 지원
- API 버전별로 계약을 관리해 버전 호환성 유지

아래는 Stubborn.sh에서 사용하는 JSON 계약 예시입니다.

```json
{
  "description": "사용자 조회 API",
  "request": {
    "method": "GET",
    "url": "/api/users/123"
  },
  "response": {
    "status": 200,
    "headers": {
      "Content-Type": "application/json"
    },
    "body": {
      "id": 123,
      "name": "홍길동"
    }
  }
}
```

이걸 기존 Groovy DSL과 비교하면, JSON 포맷이 좀 더 명시적이고, 자동화 도구와 호환성이 좋다는 장점이 있습니다. 

## 실제 프로젝트에 적용해보니 생긴 변화

우리 팀은 마이그레이션 후 다음과 같은 변화를 체감했습니다.

- **테스트 안정성 향상:** Stubborn.sh가 테스트 실행 환경을 완전히 분리해줘서, 로컬 개발자 환경 문제로 인한 실패가 70% 줄었어요.
- **배포 파이프라인 통합:** GitHub Actions와 자연스럽게 연동돼, PR마다 자동으로 계약 테스트가 돌고 결과를 바로 확인할 수 있었습니다.
- **성능 개선:** 테스트 병렬화 덕분에 전체 테스트 실행 시간이 40% 단축됐습니다.

하지만 단점도 있었습니다. 초기 설정과 계약 파일 변환에 꽤 시간이 들었고, JSON 포맷에 익숙하지 않은 팀원들은 적응하는 데 한 달가량 소요됐죠. 

Martin Fowler도 강조했듯이, 계약 테스트는 서비스 간 명확한 인터페이스 정의와 지속적 통합 전략의 핵심입니다. Stubborn.sh를 활용하면 이 부분을 더 견고하게 만들 수 있지만, 초기 진입 장벽을 넘는 노력이 필요합니다.[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/)

## Stubborn.sh 마이그레이션을 위한 실전 팁과 코드 예시

마이그레이션을 시작할 때는 다음 단계를 추천합니다.

1. **기존 계약 파일 백업 및 분석**: 어떤 계약이 얼마나 복잡한지 파악
2. **자동 변환 스크립트 작성**: Groovy DSL → JSON 변환 자동화 시도
3. **Stubborn.sh CLI 도구 설치 및 초기화**

```bash
# Stubborn.sh CLI 설치
npm install -g stubborn-cli

# 프로젝트 초기화
stubborn init
```

4. **계약 파일 업로드 및 테스트 실행**

```bash
# 계약 테스트 실행
stubborn test --contracts ./contracts-json
```

5. **CI/CD 파이프라인에 Stubborn.sh 통합**

GitHub Actions 예시:

```yaml
name: Contract Test
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      - name: Install Stubborn CLI
        run: npm install -g stubborn-cli
      - name: Run Contract Tests
        run: stubborn test --contracts ./contracts-json
```

6. **결과 모니터링 및 피드백 반영**

이 과정에서 가장 중요한 건, 테스트 실패 원인을 명확히 파악하고 계약을 점진적으로 개선하는 것입니다. 무조건 한꺼번에 다 바꾸려 하면 오히려 혼란만 커집니다.

# 마치며: Stubborn.sh가 우리에게 준 것

처음엔 "새 플랫폼? 또 배워야 해?"라는 부담이 컸지만, 실제 경험해보니 Stubborn.sh는 단순한 대체제가 아니라 계약 테스트를 한 단계 업그레이드하는 도구였습니다. 

- 테스트 안정성 확보
- CI/CD 자동화 강화
- 대규모 서비스 환경에서 성능 개선

이 세 가지는 마이크로서비스 운영에서 정말 큰 차이를 만듭니다. 물론 초기 마이그레이션 비용과 학습 곡선은 감수해야 하지만, 장기적으로 보면 충분히 투자할 가치가 있죠.

계약 테스트가 불안정해 고민하는 분들께 Stubborn.sh 시도해보길 추천합니다. 그리고 꼭 단계별로, 팀원들과 소통하며 천천히 옮겨가세요.
