## "API 호출이 갑자기 막혔다고?"

얼마 전 우리 팀에서 AI 에이전트 시스템을 운영하다가 한밤중에 갑자기 API 호출이 막히는 일이 있었어요. 원인은 간단했습니다. OpenAI API의 레이트 리밋(rate limit)에 걸린 거였죠. 그때 깨달았죠. "아, AI 에이전트 시스템도 결국은 네트워크와 API 한계에 발목 잡힐 수밖에 없구나" 하고요.

이 경험을 시작으로, 신뢰성 높은 에이전트 AI 시스템을 만들려면 어떤 아키텍처 결정이 필요한지, 어떤 트레이드오프가 있는지, 그리고 실제 운영 환경에서 어떻게 대응해야 하는지 정리해봤습니다.

---

## OpenAI API 아키텍처가 알려준 확장성과 신뢰성 설계

OpenAI API는 확장성과 신뢰성을 고려한 설계가 돋보입니다. API 호출에 대해 명확한 레이트 리밋 정책이 있고, 오류가 발생하면 적절한 HTTP 상태 코드와 함께 재시도 가능 여부를 알려줍니다. 이 덕분에 대규모 에이전트 시스템에서 부하 분산과 장애 복구 전략을 세우기 수월하죠.

예를 들어, 우리 시스템에서는 초당 60회 호출 제한이 있는데, 이를 초과하면 429 Too Many Requests 오류가 옵니다. 이럴 때는 지수 백오프(exponential backoff) 알고리즘을 적용해 재시도를 하게 했어요.

```python
import time
import requests

API_KEY = 'your_api_key'

headers = {'Authorization': f'Bearer {API_KEY}'}

url = 'https://api.openai.com/v1/chat/completions'


def call_openai_api(payload):
    max_retries = 5
    backoff = 1
    for attempt in range(max_retries):
        response = requests.post(url, headers=headers, json=payload)
        if response.status_code == 200:
            return response.json()
        elif response.status_code == 429:
            print(f"Rate limit hit, retrying in {backoff} seconds...")
            time.sleep(backoff)
            backoff *= 2
        else:
            response.raise_for_status()
    raise Exception("Max retries exceeded")
```

이런 식으로 하면 갑작스런 호출 폭주에도 어느 정도 버틸 수 있죠. 물론, 너무 많은 재시도는 전체 시스템 지연을 키우니 적절한 한도 내에서 조절해야 합니다.

더 중요한 건, 이런 API 한계가 결국 아키텍처 설계에 영향을 미친다는 겁니다. 예를 들어, 에이전트를 여러 서비스로 분산시키거나, 호출 큐잉(queueing) 시스템을 도입해 요청을 조절하는 식이죠.

[OpenAI API Documentation](https://platform.openai.com/docs/overview)에서 이런 점을 명확히 안내하고 있어서 실제로 큰 도움이 됐습니다.

## Anthropic Claude 에이전트에서 배우는 프롬프트 엔지니어링과 신뢰성

Anthropic의 Claude 에이전트는 프롬프트 설계가 신뢰성에 얼마나 중요한지 잘 보여줍니다. 단순히 질문을 던지는 게 아니라, 명확한 지침과 충분한 컨텍스트를 주는 게 핵심이에요.

예를 들어, 아래처럼 프롬프트를 짜면 에이전트가 더 예측 가능하게 동작합니다.

```
You are a helpful assistant. Please answer the user's question concisely and politely.
User: {user_input}
Assistant:
```

이렇게 명확한 역할과 기대 행동을 지정하면, 에이전트가 엉뚱한 답변을 줄 확률이 줄어들어요. 실제로 우리 팀도 프롬프트를 계속 다듬으면서 오류율이 15%에서 5% 이하로 떨어졌습니다.

또한, Claude는 프롬프트에 상태 정보를 포함시켜서 대화 맥락을 유지하는데, 이게 없으면 에이전트가 이전 대화를 잊고 엉뚱한 답변을 할 수 있습니다.

프롬프트 엔지니어링은 단순히 "잘 물어보는" 문제를 넘어서, 에이전트의 예측 가능성과 신뢰성을 높이는 핵심 수단이라는 점, 꼭 기억하세요.

[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)에서 자세한 예시와 방법론을 참고할 수 있습니다.

## Cursor처럼 실시간 상태 관리가 필요한 이유

AI 에이전트가 코드 작성이나 복잡한 작업을 수행할 때는 상태 관리가 필수입니다. Cursor 플랫폼 문서에 따르면, 실시간 피드백 루프와 상태 관리는 에이전트가 작업 중간에 잘못된 방향으로 가는 걸 막고, 정확성을 보장하는 데 큰 역할을 합니다.

우리도 비슷한 경험이 있는데, 에이전트가 코드를 생성할 때 중간 중간 실행 결과를 확인하고, 오류가 있으면 바로 수정하도록 하는 피드백 루프를 넣었더니 실패율이 30%에서 10%로 크게 줄었어요.

이런 구조는 아래처럼 이벤트 기반으로 상태를 업데이트하면서 에이전트가 다음 행동을 결정하게 할 수 있습니다.

```python
class AgentState:
    def __init__(self):
        self.code = ""
        self.errors = []

    def update_code(self, new_code):
        self.code = new_code

    def add_error(self, error_msg):
        self.errors.append(error_msg)


def agent_loop(state: AgentState):
    while True:
        action = decide_next_action(state)
        if action == 'generate_code':
            code = generate_code_from_prompt()
            state.update_code(code)
        elif action == 'run_tests':
            errors = run_code_tests(state.code)
            for e in errors:
                state.add_error(e)
        elif action == 'finish':
            break
```

이런 상태 기반 접근법은 에이전트가 "내가 지금 뭘 하고 있는지" 정확히 인지하게 만들어서, 복잡한 작업에서 신뢰도를 크게 올려줍니다.

[Cursor Documentation](https://docs.cursor.com/)에서 이 아키텍처를 자세히 설명하고 있으니 참고해보세요.

## GitHub Copilot과 Vercel AI SDK가 보여주는 클라우드 기반 에이전트의 현실

GitHub Copilot은 클라우드 기반 AI 에이전트로, 사용자의 코드 작성 패턴을 실시간으로 학습해 적응합니다. 덕분에 개발 생산성이 크게 향상되지만, 개인정보 보호와 코드 품질 이슈가 항상 따라다니죠.

우리도 Copilot을 도입할 때, 사내 코드가 외부로 노출되는 걸 최소화하기 위해 프록시 서버를 두고, 중요한 프로젝트는 별도의 검증 절차를 추가했습니다. 이런 실무적 제약이 결국 아키텍처와 운영 정책에 큰 영향을 미치더군요.

한편, Vercel AI SDK는 서버리스 환경에 최적화된 경량 AI 에이전트 아키텍처를 제공합니다. 빠른 배포와 확장성이 강점인데, 서버리스 특성상 상태 관리가 어렵고, 긴 작업에는 부적합한 단점도 있습니다.

즉, 클라우드 기반 AI 에이전트 아키텍처는 확장성과 편리함을 주지만, 상태 관리, 개인정보 보호, 긴 작업 처리 같은 현실적 제약을 반드시 고려해야 합니다.

[Vercel AI SDK Documentation](https://sdk.vercel.ai/docs/introduction)와 [GitHub Copilot Documentation](https://docs.github.com/en/copilot)에서 각각의 특징과 한계를 자세히 알 수 있습니다.

## 실제로 마이그레이션할 때 고려해야 할 점들

처음부터 완벽한 에이전트 시스템을 만들기란 불가능합니다. 저희 팀도 OpenAI API 기반에서 Anthropic Claude로 일부 워크플로우를 옮길 때 여러 시행착오를 겪었죠.

- **API 호출 패턴 차이**: OpenAI는 토큰 기반 과금, Claude는 프롬프트 길이와 응답 길이에 민감합니다.
- **프롬프트 스타일 차이**: Claude는 더 명확한 지침이 필요해 기존 프롬프트를 대폭 수정해야 했어요.
- **상태 관리 방식**: Claude는 세션 관리가 더 엄격해서 별도의 상태 저장소를 도입했습니다.

마이그레이션은 단순히 API 교체가 아니라, 에이전트 행동과 신뢰성에 직접 영향을 주는 아키텍처 전환이라는 걸 명심해야 합니다.

## 마치며: "완벽한" 에이전트 AI는 없지만, 신뢰성은 설계에서 나온다

에이전트 AI 시스템을 운영하면서 가장 크게 느낀 점은, 신뢰성은 결국 아키텍처 설계와 운영 정책에서 나온다는 겁니다. API 한계, 프롬프트 설계, 상태 관리, 클라우드 환경 특성 등 현실적인 제약을 무시하면 어느 순간 시스템이 무너집니다.

처음엔 "그냥 API 호출 몇 번 하면 되겠지" 싶지만, 실제 운영해보면 레이트 리밋, 오류 처리, 상태 동기화, 개인정보 보호 등 고려할 게 한두 가지가 아니에요.

그래서 저는 다음 네 가지를 꼭 권합니다.

1. **API 호출에 대한 명확한 제한과 재시도 로직 설계**
2. **프롬프트 엔지니어링으로 에이전트 동작 예측 가능하게 만들기**
3. **상태 관리와 실시간 피드백 루프로 작업 신뢰성 확보**
4. **클라우드 환경 특성에 맞는 아키텍처 선택과 개인정보 보호 고려**

이걸 바탕으로 점진적 마이그레이션과 운영 정책을 세우면, 복잡한 에이전트 AI 시스템도 충분히 신뢰성 있게 운영할 수 있습니다.
