### "왜 이 결정이 이렇게 된 거지?"라는 질문에 답할 수 있어야 한다

팀에서 새로운 아키텍처를 도입하거나 기존 방식을 바꿀 때, "왜 하필 이걸 선택했지?"라는 질문이 꼭 나온다. 경험상 이런 질문에 명확한 답이 없으면 나중에 같은 논쟁이 반복되고, 신규 입사자도 혼란스러워한다. 그래서 저는 Architecture Decision Record, 줄여서 ADR을 적극 추천한다. ADR은 단순히 "이렇게 했다"를 넘어서, "왜 이렇게 했고, 어떤 대안이 있었으며, 어떤 트레이드오프가 있었는지"를 꼼꼼하게 기록하는 문서다. 이걸 잘 써두면 팀 내 합의도 빨라지고, 미래에 의사결정 근거를 찾는 데 큰 도움이 된다.

---

### ADR에 꼭 들어가야 하는 내용, 그리고 실제로 쓸 때 놓치기 쉬운 부분

ADR을 처음 접하면 "결정만 적으면 되지"라고 생각하기 쉽다. 하지만 좋은 ADR은 다음 네 가지를 명확히 담아야 한다고 봐요.

1. **배경과 문제 정의**: 왜 이 결정을 내려야 했는지 상황 설명
2. **대안과 선택 이유**: 고려했던 옵션들과 최종 선택 근거
3. **트레이드오프**: 성능, 유지보수성, 보안, 확장성 등 어떤 점을 희생하거나 얻었는지
4. **마이그레이션 경로 및 운영 제약**: 기존 시스템에서 새 아키텍처로 어떻게 옮길지, 운영 중 주의할 점

특히 네 번째 항목은 간과하기 쉬운데, 마이그레이션 계획과 운영 제약 조건을 기록하지 않으면 실제 적용 시 큰 혼란이 생긴다. 예를 들어, 클라우드 환경에서는 서비스 다운타임을 최소화하기 위해 점진적 전환 전략을 명확히 해야 한다는 점이 중요하다[Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/).

---

### 백엔드에서 ADR을 쓸 때 꼭 고민해야 할 기술적 트레이드오프

백엔드 아키텍처 결정은 단순히 기술 스택을 고르는 것보다 훨씬 복잡하다. 예를 들어, 마이크로서비스를 도입할 때는 다음과 같은 트레이드오프를 반드시 문서화해야 한다:

- **성능 vs 유지보수성**: 마이크로서비스는 독립 배포와 확장이 쉽지만, 네트워크 호출 증가로 지연시간이 늘어날 수 있다.
- **보안 요구사항**: 서비스 간 통신 암호화, 인증 방식 등을 명확히 해야 한다.
- **배포 전략**: 롤링 업데이트, 카나리 배포 등 어떤 방식을 쓸지

이런 내용을 ADR에 기록하면, 단순히 "마이크로서비스로 바꿨다"가 아니라 "왜, 어떻게, 어떤 위험을 감수하며 바꿨는지"가 투명해져서 팀원들끼리 합의가 쉽다[Martin Fowler - Microservices](https://martinfowler.com/articles/microservices.html).

### 실제로 ADR 작성할 때 이렇게 해봤더니 효과적이었다

제가 최근에 작성했던 ADR 예시를 하나 보여드릴게요. 우리 팀에서 기존 모놀리식 API를 GraphQL 게이트웨이로 전환할 때 썼던 문서 일부입니다.

```markdown
# ADR 007: GraphQL 게이트웨이 도입

## 배경
- 기존 REST API가 클라이언트별로 과도한 데이터 요청과 중복 호출 문제 발생

## 고려한 대안
- REST 개선 (필터링, 페이징 강화)
- GraphQL 도입

## 결정
- GraphQL 게이트웨이 도입으로 클라이언트 요청 최적화

## 트레이드오프
- GraphQL 서버 추가로 인한 운영 복잡성 증가
- 초기 학습 비용 발생

## 마이그레이션 경로
- 1단계: 기존 REST API 유지, GraphQL 서버 병행 운영
- 2단계: 클라이언트 점진적 전환
- 3단계: REST API 단계적 폐기

## 운영 제약
- GraphQL 서버 장애 시 fallback REST API 호출 로직 필요
- 모니터링 강화 필요
```

이렇게 작성해두니, 나중에 문제가 생겨도 "왜 이렇게 했는지"가 명확해서 대응이 빨랐어요.

### ADR을 팀 문화로 정착시키려면 어떻게 해야 할까?

처음 ADR을 도입하면 "문서 쓰는 게 너무 귀찮다"는 반응이 많아요. 그래서 저는 다음 두 가지를 강조합니다.

- **가볍게 시작하기**: 처음부터 완벽한 문서가 아니라, 핵심 결정과 이유만 간단히 적어도 충분하다.
- **정기 리뷰**: 매주 혹은 매월 팀 회의 때 최근 ADR을 리뷰하며 보완한다.

또한, ADR을 코드 저장소와 함께 관리하면 변경 이력 추적도 쉽고, PR 리뷰 과정에서 자연스럽게 논의가 이뤄져서 실효성이 높아집니다.

---

### 마무리하며

ADR은 단순 문서가 아니라, 팀의 의사결정 근거를 투명하게 만드는 도구입니다. 특히 백엔드 아키텍처처럼 복잡한 영역에서는 선택의 이유와 트레이드오프, 마이그레이션 계획을 명확히 기록하는 것이 운영 안정성과 팀 협업에 큰 도움이 됩니다. 처음엔 귀찮아도, 한두 번 써보면 "이건 실제로 겪어보면 왜 중요한지 알게 된다"는 걸 느끼실 거예요.

## 운영에서 바로 점검할 항목 1

- **Architecture Decision Record(ADR)는 소프트웨어 아키텍처에서 중요한 결정 사항을 문서화하는 방법으로, 각 결정의 배경, 대안, 선택 이유, 그리고 트레이드오프를 명확히 기록하여 팀 내 공유와 미래 참조에 유용하다.** ([Martin Fowler - Microservices](https://martinfowler.com/articles/microservices.html))
  실제 적용에서는 트래픽 패턴, 장애 허용 범위, 팀의 온콜 역량을 같이 봐야 합니다. 초기에는 전체 전환보다 일부 기능에 먼저 도입하고, 지표가 안정화되는지 확인한 다음 확장하는 방식이 안전합니다. 특히 롤백 기준을 사전에 숫자로 정의해 두면 운영 중 의사결정 속도가 크게 좋아집니다.

- **효과적인 ADR 문서에는 선택한 아키텍처 결정의 마이그레이션 경로와 운영상 제약 조건을 포함하여, 변경 시 발생할 수 있는 영향과 복구 방안도 함께 기술하는 것이 중요하다.** ([Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/))
  실제 적용에서는 트래픽 패턴, 장애 허용 범위, 팀의 온콜 역량을 같이 봐야 합니다. 초기에는 전체 전환보다 일부 기능에 먼저 도입하고, 지표가 안정화되는지 확인한 다음 확장하는 방식이 안전합니다. 특히 롤백 기준을 사전에 숫자로 정의해 두면 운영 중 의사결정 속도가 크게 좋아집니다.

- **백엔드 엔지니어는 ADR 작성 시, 기술적 트레이드오프(예: 성능 vs 유지보수성), 보안 요구사항, 확장성, 그리고 배포 전략 등을 명확히 하여 의사결정의 근거를 투명하게 해야 하며, 이를 통해 팀 내 합의 형성과 운영 안정성을 높일 수 있다.** ([Martin Fowler - Microservices](https://martinfowler.com/articles/microservices.html))
  실제 적용에서는 트래픽 패턴, 장애 허용 범위, 팀의 온콜 역량을 같이 봐야 합니다. 초기에는 전체 전환보다 일부 기능에 먼저 도입하고, 지표가 안정화되는지 확인한 다음 확장하는 방식이 안전합니다. 특히 롤백 기준을 사전에 숫자로 정의해 두면 운영 중 의사결정 속도가 크게 좋아집니다.

- **운영 환경의 제약 조건과 마이그레이션 경로는 ADR에서 반드시 다뤄야 할 요소로, 특히 클라우드 플랫폼을 활용하는 경우에는 서비스 중단 최소화와 점진적 전환 전략을 명시하는 것이 권장된다.** ([Microsoft - Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/))
  실제 적용에서는 트래픽 패턴, 장애 허용 범위, 팀의 온콜 역량을 같이 봐야 합니다. 초기에는 전체 전환보다 일부 기능에 먼저 도입하고, 지표가 안정화되는지 확인한 다음 확장하는 방식이 안전합니다. 특히 롤백 기준을 사전에 숫자로 정의해 두면 운영 중 의사결정 속도가 크게 좋아집니다.

추가로, 배포 전에는 성능과 안정성뿐 아니라 로그 품질까지 확인해야 합니다. 에러 로그가 충분히 구조화되어 있지 않으면 원인 분석 시간이 길어지고, 같은 장애가 반복될 가능성이 높아집니다. 배포 후 24시간 관찰 구간에서 경보 임계치를 임시로 강화해 두는 것도 실무에서 자주 쓰는 방법입니다.
