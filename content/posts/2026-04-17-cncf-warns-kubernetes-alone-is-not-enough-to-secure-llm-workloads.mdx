## "Kubernetes만 믿었는데, LLM 보안은 전혀 다른 이야기더라"

최근 우리 팀에서 LLM(대규모 언어 모델) 서비스를 Kubernetes 위에 올려 운영하면서 겪은 일이에요. Kubernetes가 워낙 강력한 컨테이너 오케스트레이션 툴이라서, ‘보안도 다 알아서 해주겠지’ 싶었죠. 근데 막상 운영 중에 민감한 데이터 유출 위험, API 남용, 네트워크 공격 등 다양한 보안 이슈가 터지면서 Kubernetes만으로는 한계가 명확하다는 걸 뼈저리게 느꼈습니다.

사실 CNCF에서도 공식적으로 "Kubernetes만으로 LLM 워크로드 보안을 완벽히 보장할 수 없다"고 경고했어요. LLM 특유의 복잡한 데이터 처리와 확장성 문제, 그리고 민감한 정보 보호 요구 때문에, 단순한 컨테이너 관리 이상의 다층 보안 전략이 필요하다는 겁니다.[Kubernetes Concepts Overview](https://kubernetes.io/docs/concepts/overview/)

---

## LLM 워크로드에서 Kubernetes의 한계가 왜 이렇게 크게 느껴질까?

Kubernetes는 기본적으로 컨테이너 배포, 스케일링, 헬스체크를 자동화하는 데 최적화되어 있습니다. Liveness, Readiness, Startup 프로브 설정으로 서비스 상태를 감시하고, 장애 시 자동 복구하는 기능도 훌륭하죠.[Kubernetes - Configure Liveness, Readiness and Startup Probes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)

하지만 이 프로브들은 어디까지나 ‘서비스가 살아있는지’ ‘준비됐는지’를 확인하는 수준이지, 데이터 유출 방지나 권한 관리 같은 보안 기능은 아닙니다. LLM 워크로드는 API 호출마다 민감한 텍스트 데이터를 주고받고, 모델 내부에는 개인정보가 포함될 수 있어요. 이런 부분을 Kubernetes가 자동으로 막아주진 않는다는 점이 문제입니다.

게다가 LLM은 요청 패턴이 복잡하고, 공격자가 악의적인 프롬프트를 넣어 모델을 오용하려는 시도도 많습니다. 단순히 컨테이너 상태만 체크하는 Kubernetes 프로브로는 이런 위협을 탐지하거나 차단할 수 없죠.

## LLM 보안을 위해 꼭 챙겨야 할 다층 보안 전략

### 1. API 인증과 권한 관리부터 철저히

OpenAI API 문서에서는 인증 토큰 관리, 권한 분리, 요청 제한(rate limiting) 같은 기본 보안 가이드라인을 강조합니다.[OpenAI API Documentation](https://platform.openai.com/docs/overview) Kubernetes 위에서 LLM 서비스를 운영해도, 애플리케이션 레벨에서 이런 보안 조치를 반드시 구현해야 해요.

예를 들어, 다음은 Node.js Express 서버에서 API 키 검증과 간단한 요청 제한을 구현한 코드입니다:

```javascript
const express = require('express');
const rateLimit = require('express-rate-limit');

const app = express();

// 간단한 API 키 검증 미들웨어
function apiKeyMiddleware(req, res, next) {
  const apiKey = req.headers['x-api-key'];
  if (apiKey !== process.env.API_KEY) {
    return res.status(401).json({ error: 'Unauthorized' });
  }
  next();
}

// 초당 10회 요청 제한
const limiter = rateLimit({
  windowMs: 1000,
  max: 10,
  message: 'Too many requests, please try again later.',
});

app.use(apiKeyMiddleware);
app.use(limiter);

app.post('/llm-query', (req, res) => {
  // LLM 처리 로직
  res.json({ result: 'Processed' });
});

app.listen(3000, () => console.log('Server running on port 3000'));
```

이렇게 애플리케이션 레벨에서 인증과 요청 제한을 직접 구현하지 않으면, Kubernetes만으로는 공격자 접근을 막을 수 없습니다.

### 2. 네트워크 레벨 방어와 API 게이트웨이 활용

Cloudflare 사례를 보면, 네트워크 방화벽, DDoS 방어, API 게이트웨이 보안, 실시간 위협 탐지 시스템을 통합하는 것이 LLM 워크로드 보호에 효과적이라고 합니다.[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/)

Kubernetes 클러스터 외부에 WAF(Web Application Firewall)를 두거나, Istio 같은 서비스 메쉬를 활용해 마이크로서비스 간 트래픽을 암호화하고 세밀한 정책을 적용하는 것도 좋은 방법입니다. 이렇게 하면 내부 네트워크 침입이나 비인가 접근을 더 촘촘히 막을 수 있어요.

### 3. 입력 데이터 검증과 프롬프트 안전성 확보

Anthropic의 프롬프트 엔지니어링 가이드에서는 LLM에 들어가는 입력 데이터 검증과 안전한 프롬프트 설계가 보안의 중요한 축이라고 강조합니다.[Anthropic - Prompt Engineering Guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)

예를 들어, 악의적인 명령어 삽입, 민감정보 노출을 막기 위해 입력 텍스트를 사전에 필터링하거나, 모델에게 허용된 범위 내에서만 응답하도록 제약을 두는 식입니다. 이 단계에서 보안 사고를 예방하면, 인프라 보안 부담도 줄일 수 있습니다.

### 4. 지속적인 모니터링과 자동화된 보안 정책 적용

GitHub 엔지니어링 블로그에서는 클라우드 네이티브 서비스 운영 시 다층 보안 모델과 함께 지속적인 모니터링, 자동화된 보안 정책 적용이 필수라고 합니다.[GitHub Engineering Blog](https://github.blog/category/engineering/)

실시간 로그 분석, 이상 징후 탐지, 자동화된 취약점 스캔 등을 통해 보안 위협을 조기에 발견하고 대응할 수 있어요. Kubernetes Audit 로그와 Prometheus, Grafana 같은 도구를 활용해 모니터링 체계를 구축하는 걸 추천합니다.

## 실제로 우리 팀이 적용한 보안 레이어 구성

- **Kubernetes 네임스페이스별 네트워크 정책**: 민감한 LLM 서비스는 별도 네임스페이스에 배치하고, 네트워크 폴리시로 외부 접근을 엄격히 제한했습니다.
- **API Gateway (Kong) 도입**: 인증, 권한, 요청 제한을 API 게이트웨이에서 처리해 애플리케이션 부담을 줄였어요.
- **입력 텍스트 필터링 모듈**: 프롬프트에 금지어 필터링과 패턴 분석을 적용해 악성 입력을 사전에 차단했습니다.
- **모니터링 및 알림 체계**: Prometheus와 ELK 스택으로 로그를 수집하고, 이상 탐지 시 슬랙 알림을 받도록 했습니다.

이렇게 다층으로 보안을 쌓으니, Kubernetes만으로 운영할 때보다 사고 발생률이 눈에 띄게 줄었고, 대응 속도도 빨라졌습니다.

## Kubernetes 보안 설정, 이것만은 꼭 기억하자

Kubernetes 자체 보안 설정도 무시할 수 없어요. 특히 아래를 꼭 챙기세요:

- **Pod Security Policies (PSP) 혹은 Pod Security Admission**: 권한이 과도한 컨테이너 실행 금지
- **RBAC(Role-Based Access Control)**: 최소 권한 원칙에 따라 사용자와 서비스 계정 권한 제한
- **네트워크 폴리시**: 서비스 간 통신 제한으로 내부 공격 표면 축소
- **시크릿 관리**: Kubernetes 시크릿을 외부 Vault와 연동해 안전하게 관리

하지만 이 모든 걸 해도 LLM 워크로드 특유의 보안 위협을 막기엔 역부족이니, 반드시 애플리케이션과 네트워크 보안 레이어를 추가해야 합니다.

## 마무리하며: 보안은 Kubernetes 위에 또 다른 보안이 필요하다

처음엔 Kubernetes가 워낙 잘 만들어져서, 여기만 잘 쓰면 LLM 서비스도 안전할 거라 생각했어요. 그런데 실제 운영을 해보니, 민감 데이터 보호, API 남용 방지, 악성 입력 대응 등은 Kubernetes가 기본 제공하는 기능 범위를 훨씬 넘어서는 문제였습니다.

CNCF가 경고한 것처럼, Kubernetes는 LLM 워크로드 보안의 한 축일 뿐, 다층 보안 전략과 운영 최적화 없이는 완전한 보호가 어렵습니다.

동료 백엔드 엔지니어분들께는 꼭 말씀드리고 싶어요. LLM 서비스를 운영한다면 Kubernetes 설정에만 의존하지 말고, 애플리케이션 레벨 인증, 네트워크 방어, 입력 검증, 모니터링까지 포괄하는 보안 설계를 하시길 바랍니다. 이건 실제로 겪어보면 ‘아, 이게 왜 필요한지’ 바로 느껴지실 거예요.
