### 갑자기 마주한 시스템 확장, 어디서부터 손대야 할까?

"우리 서비스가 갑자기 사용자 수가 10배로 늘었는데, DB부터 API, 캐시, 큐까지 어디부터 손대야 할까요?"

이런 질문, 한 번쯤은 들어봤을 거예요. 저도 비슷한 상황에서 한참 헤맸죠. 대규모 시스템 설계는 마치 고고학자가 유물을 발굴하듯, 과거 결정들을 파헤쳐 현재와 미래를 위한 최적의 길을 찾아야 하는 작업 같아요. 그래서 저는 이걸 ‘고고학자의 조수’ 역할이라고 부릅니다. 과거의 선택과 현재의 제약, 그리고 미래의 확장성을 함께 살펴가야 하니까요.

이번 글에서는 Cursor, GitHub Copilot 같은 AI 기반 도구가 어떻게 이런 복잡한 아키텍처 결정 과정을 도와주는지, 그리고 실제 운영 환경에서 마주치는 제약들을 어떻게 극복하는지 경험을 나눠볼게요.

## 아키텍처 결정, 단순히 좋은 기술 고르는 게 아니다

아키텍처 결정은 "이 기술이 좋으니까 쓰자" 수준이 아니에요. 확장성, 유지보수성, 성능, 비용, 운영 난이도 등 수많은 요소를 동시에 고려해야 하죠. 예를 들어, 데이터베이스를 샤딩할지, 캐시를 어디에 둬야 할지, 메시지 큐를 도입할지 고민할 때, 이 모든 선택은 서로 영향을 미칩니다.

Cursor Documentation에서는 이런 복잡한 트레이드오프를 분석하고, 마이그레이션 경로를 설계하는 데 필요한 도구와 가이드라인을 제공해요. 특히 기존 시스템을 완전히 갈아엎지 않고 점진적으로 바꾸는 전략을 세우는 데 큰 도움이 됩니다. 

제가 직접 경험한 사례를 하나 들자면, 한 대형 e커머스 플랫폼에서 RDBMS에서 NoSQL로 전환하는 작업을 했는데, Cursor의 가이드라인 덕분에 데이터 일관성과 성능 저하 문제를 최소화하며 6개월에 걸쳐 단계별 마이그레이션을 성공시킬 수 있었어요.[Cursor Documentation](https://docs.cursor.com/)

## AI 코드 제안, 아키텍처 설계에도 쓸 수 있을까?

GitHub Copilot을 쓰면서 "이걸 단순히 코드 작성 보조로만 써야 하나?" 하는 의문이 들었어요. 그런데 Copilot Documentation을 보면, 실제로 복잡한 아키텍처 설계 결정에도 도움을 준다고 하더군요. 예를 들어, 백엔드 API 설계 시 실시간으로 확장성 문제를 고려한 코드 패턴을 제안해주고, 프론트엔드와 백엔드 간 데이터 흐름 설계에 따른 운영 제약들을 해결할 아이디어를 얻을 수 있어요.[GitHub Copilot Documentation](https://docs.github.com/en/copilot)

아래는 제가 Copilot과 함께 작업하면서 얻은 간단한 예시입니다. 마이크로서비스 간 API 호출 시 타임아웃과 재시도 로직을 자동으로 제안받아, 운영 중 네트워크 지연에 따른 장애를 줄인 코드예요.

```typescript
// 마이크로서비스 간 API 호출 시 재시도 로직 예시
async function fetchWithRetry(url: string, retries = 3): Promise<Response> {
  for (let i = 0; i < retries; i++) {
    try {
      const response = await fetch(url, { timeout: 2000 });
      if (!response.ok) throw new Error('네트워크 오류');
      return response;
    } catch (e) {
      if (i === retries - 1) throw e;
      await new Promise(res => setTimeout(res, 1000));
    }
  }
  throw new Error('재시도 실패');
}
```

이런 코드는 직접 짜려면 의외로 까다로운데, Copilot 덕분에 빠르게 프로토타입을 만들고 운영 환경에 맞게 튜닝할 수 있었어요.

## 마이그레이션 경로 설계, AI가 알려주는 현실적인 선택지

Anthropic의 Claude Code Overview 문서에서는 AI가 다양한 마이그레이션 시나리오와 운영 제약을 분석하는 데 어떻게 활용될 수 있는지 소개합니다. 특히 복잡한 시스템에서 여러 경로 중 어떤 걸 선택해야 할지 판단하기 어려울 때, AI가 시뮬레이션과 트레이드오프 평가를 도와줘요.[Anthropic - Claude Code Overview](https://docs.anthropic.com/en/docs/claude-code/overview)

저도 실제로 큰 시스템 리팩토링 프로젝트에서 Claude를 써봤는데, 예를 들어 "캐시 계층을 Redis에서 Memcached로 바꿀 때 예상되는 성능 변화와 운영 비용 차이" 같은 질문을 던지면, AI가 관련 문서와 이전 사례를 참고해 현실적인 장단점을 정리해줍니다. 물론 전적으로 AI를 믿기보단 참고 자료로 삼고, 최종 결정은 운영팀과 협의하는 식으로요.

## 프론트엔드 확장성과 사용자 경험, AI SDK가 돕는 부분

Vercel AI SDK Documentation에서는 프론트엔드 중심 시스템에서 AI 도구를 활용해 사용자 경험을 최적화하고, 클라우드 플랫폼과의 통합을 통해 실시간 운영 제약을 극복하는 방법을 설명합니다.[Vercel AI SDK Documentation](https://sdk.vercel.ai/docs/introduction)

예를 들어, 실시간 사용자 행동 데이터를 AI가 분석해 추천 콘텐츠를 즉시 바꾸거나, 네트워크 상태에 따라 적절한 UI 컴포넌트를 동적으로 로드하는 기능을 구현할 때 유용하죠. 이런 부분은 백엔드 확장성뿐 아니라 프론트엔드의 민첩성도 같이 고려해야 하니, 전체 아키텍처를 보는 시야가 필요합니다.

## 실제 사례에서 배우는 ‘트레이드오프’와 ‘운영 제약’의 무게

GitHub Engineering Blog와 Cloudflare Blog - How We Built It 시리즈는 대규모 시스템 운영 현장에서 부딪히는 현실적인 문제들과 이를 해결한 전략을 생생하게 다룹니다.[GitHub Engineering Blog](https://github.blog/category/engineering/), [Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/)

예를 들어, GitHub에서는 대규모 분산 저장소를 운영하며 데이터 일관성과 응답 속도 사이에서 균형을 맞추는 경험을 공유하는데, 이 과정에서 여러 마이그레이션 경로를 시도하고 실패하며 얻은 교훈이 많아요. Cloudflare는 클라우드 기반 아키텍처를 빠르게 확장하면서도 네트워크 지연과 장애를 최소화하는 방법을 구체적인 수치와 함께 설명합니다.

이런 실제 사례들은 이론과 달리 ‘현장에서 살아남는’ 설계가 무엇인지 깨닫게 해줘서, 꼭 한 번씩 읽어보길 추천합니다.

### 마무리하며: ‘고고학자의 조수’처럼 천천히, 그러나 치밀하게

대규모 시스템 아키텍처 설계는 단순히 좋은 기술을 고르는 게 아니라, 과거 선택과 현재 제약, 미래 확장성을 모두 고려하는 복합적인 작업입니다. AI 도구들이 이런 과정에서 점점 더 중요한 조력자가 되고 있죠. 하지만 AI가 알려주는 답을 무조건 믿기보단, 실제 운영 환경과 팀 상황을 반영해 최종 판단을 내려야 합니다.

제가 배운 점은 다음과 같아요:

- **트레이드오프를 명확히 하라:** 성능, 비용, 유지보수성 중 무엇을 우선시할지 팀 내 합의가 필수
- **마이그레이션은 단계적으로:** 한꺼번에 바꾸려다 실패하는 경우가 많으니, 점진적 전환 경로 설계가 안전
- **AI 도구는 보조 수단:** 빠른 프로토타입과 아이디어 도출에 도움되지만, 최종 결정은 경험과 데이터에 기반해야
- **운영 제약을 무시하지 말 것:** 실제 네트워크 지연, 장애 시나리오를 반영한 설계가 장기적으로 안정성 보장

이 글이 여러분의 ‘고고학자’ 같은 아키텍처 결정에 조금이나마 도움이 되길 바랍니다. 다음에 또 현장에서 겪은 재미난 사례로 만나요!
