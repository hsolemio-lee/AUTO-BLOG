## "왜 내 라우팅은 아직도 느리지?" - Navigation API가 답이다

한 번쯤은 이런 생각 해봤을 거예요. SPA에서 페이지 이동할 때마다 뭔가 끊기고, 느리고, 상태 관리가 복잡해서 코드도 지저분해지고... 기존에 `history.pushState`나 `window.location`을 쓰면서도 뭔가 부족하다 느꼈다면, 최신 Navigation API가 그 해답일 수 있습니다.

요즘 프론트엔드 개발자들 사이에서 Navigation API가 뜨거운 이유는 단순히 성능 개선뿐 아니라, 네비게이션 흐름을 이벤트 기반으로 더 직관적이고 깔끔하게 관리할 수 있기 때문이에요. Cloudflare 같은 대형 서비스도 도입 후 라우팅 속도와 UI 반응성이 눈에 띄게 좋아졌다고 하니, 그냥 지나칠 수 없죠[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).


## Navigation API가 기존 라우팅과 진짜 다른 점

기존에는 `history.pushState`를 직접 호출하고, `popstate` 이벤트를 감지해서 라우팅 상태를 관리했죠. 그런데 이 방식은 비동기 데이터 로딩이나 복잡한 네비게션 플로우를 다루기엔 한계가 있었습니다. 

Navigation API는 네비게이션 이벤트를 중심으로 설계되어, 페이지 이동 시 발생하는 다양한 상태(시작, 완료, 실패 등)를 명확하게 구분해줍니다. 

예를 들어, `navigate` 메서드를 호출하면, 내부적으로는 네비게이션이 시작되고, `navigation` 이벤트 리스너를 통해 상태 변화를 감지할 수 있어요. 이렇게 되면 비동기 로딩 상태나 에러 처리도 훨씬 간결해집니다[GitHub Engineering Blog](https://github.blog/category/engineering/).

이벤트 기반이라서 다음과 같은 장점이 있어요:

- 네비게이션 시작부터 완료까지 세밀한 상태 추적 가능
- 중복 네비게이션 방지 및 취소 기능 내장
- 비동기 데이터 패칭과 상태 관리 분리 가능

실제로 Martin Fowler도 최신 소프트웨어 아키텍처 가이드에서 Navigation API가 프론트엔드 라우팅 성능과 사용자 경험을 크게 향상시킨다고 평가했습니다[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).


## Navigation API를 실제 프로젝트에 적용할 때 이렇게 써보자

아래는 간단한 SPA에서 Navigation API를 활용해 페이지 이동을 처리하는 예시입니다.

```javascript
// 네비게이션 이벤트 리스너 등록
navigation.addEventListener('navigate', event => {
  // 기본 네비게이션 동작 막기
  event.intercept({
    async handler() {
      const url = event.destination.url;
      console.log('Navigating to:', url);

      // 비동기 데이터 로딩 시뮬레이션
      await fetchDataForUrl(url);

      // 실제 페이지 전환 처리 (예: 상태 업데이트, 렌더링)
      renderPage(url);
    }
  });
});

// 페이지 이동 함수
function goToPage(path) {
  navigation.navigate(path);
}

// 데이터 로딩 함수 (예시)
async function fetchDataForUrl(url) {
  // 실제 API 호출 등
  return new Promise(resolve => setTimeout(resolve, 500));
}

// 렌더링 함수 (예시)
function renderPage(url) {
  document.getElementById('app').textContent = `현재 페이지: ${url}`;
}
```

이 코드에서 중요한 점은 `navigation.navigate()` 호출만으로도 네비게이션이 시작되고, `navigate` 이벤트 리스너에서 비동기 작업을 처리할 수 있다는 것. 기존처럼 복잡한 상태 관리나 `history` API 직접 조작 없이도 깔끔하게 라우팅 로직을 구현할 수 있죠.


## history API와 함께 쓸 때 주의할 점

Navigation API가 새롭다고 해서 기존 `history.pushState`를 완전히 버릴 필요는 없습니다. 오히려 호환성을 고려해 점진적으로 도입하는 게 실무에서는 더 현실적이에요. 

예를 들어, Navigation API 이벤트에서 `event.intercept()`를 호출하지 않으면 기본적으로 `history`가 업데이트되므로, 기존 라우팅 로직과 충돌하지 않게 설계할 수 있습니다. 

하지만, Navigation API로 네비게이션을 완전히 제어하려면 `event.intercept()`를 꼭 써야 하니, 이 부분에서 기존 코드와 조율이 필요합니다. 

또한, 비동기 데이터 로딩과 상태 관리를 Navigation API 이벤트 안에서 처리하면, 렌더링 타이밍을 더 정확히 제어할 수 있어 사용자 경험이 좋아집니다. 


## 도입 후 체감 성능과 사용자 경험은 얼마나 좋아질까?

Cloudflare 사례를 보면, Navigation API 도입 후 라우팅 처리 속도가 눈에 띄게 개선되었고, UI 반응성도 좋아져 사용자 만족도가 상승했다고 합니다. 

실제로 페이지 전환 시 불필요한 리렌더링을 줄이고, 네트워크 요청과 렌더링 타이밍을 최적화할 수 있으니, 사용자 입장에서는 훨씬 부드럽고 빠른 경험을 하게 되죠[Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/).

물론, 모든 프로젝트에 무조건 맞는 건 아닙니다. Navigation API가 아직은 최신 브라우저에서만 완전 지원되는 점, 그리고 기존 라우팅 라이브러리와의 호환성 문제 등은 고려해야 합니다. 

하지만, 점점 더 많은 브라우저가 지원하고 있고, 복잡한 네비게이션 흐름을 다루는 대규모 SPA라면 적극 도입할 가치가 충분합니다.


## 내 프로젝트에 Navigation API를 언제, 어떻게 도입할까?

- **브라우저 호환성 체크**: 현재 지원하지 않는 브라우저가 많다면 폴리필이나 점진적 도입 전략 필요
- **점진적 마이그레이션**: 기존 history API 기반 라우팅과 병행하며, 특정 부분부터 Navigation API로 전환
- **비동기 로딩 최적화**: 네비게이션 이벤트 내에서 데이터 패칭과 상태 업데이트를 처리해 렌더링 타이밍 최적화
- **에러 및 취소 처리 구현**: 네비게이션 중단이나 실패 시 사용자 피드백 로직 추가


이건 실제로 써보면, 네비게이션 흐름을 이벤트 단위로 세밀하게 관리할 수 있어서 디버깅도 훨씬 편해지고, 코드도 깔끔해집니다.
