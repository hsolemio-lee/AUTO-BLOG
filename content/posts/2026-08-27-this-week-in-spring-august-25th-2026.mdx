## "왜 GC 튜닝이 프로덕션에서 이렇게 중요한지 알게 된 이야기"

최근에 Spring Boot 3.2로 마이그레이션하면서 JVM 튜닝 옵션을 좀 더 적극적으로 만져봤는데, 이게 생각보다 애플리케이션 응답 속도에 꽤 큰 영향을 주더라고요. 특히 GC(가비지 컬렉션) 지연 시간을 줄이는 게 핵심인데, Spring Boot 3.2에서는 메트릭 수집 기능이 강화되면서 JVM 튜닝과 연동해 실시간으로 성능 지표를 모니터링하기가 훨씬 편해졌어요.

제가 적용한 설정 중 하나는 `-XX:MaxGCPauseMillis=200` 옵션인데, 이걸 통해 GC가 200ms 이상 멈추지 않도록 제한했죠. 그리고 Spring Boot의 Actuator 메트릭을 활용해 GC 빈도와 지연 시간을 모니터링했습니다. 실제로 이 설정을 적용한 후 평균 응답 시간이 15% 정도 줄었고, p95 지연시간도 눈에 띄게 개선됐어요.

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics
  metrics:
    enable:
      all: true
spring:
  jmx:
    enabled: true
```

이렇게 메트릭을 켜두면, `/actuator/metrics/jvm.gc.pause` 같은 엔드포인트에서 GC 지연 시간 데이터를 실시간으로 볼 수 있습니다. 처음엔 이게 별거 아닌 것 같지만, 실제 프로덕션에서 문제 원인 파악할 때 엄청 도움이 됩니다.

[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/)에 자세한 내용이 있으니 참고하세요.

## "OAuth 2.1, 이젠 Spring Framework 6.1에서 기본으로 쓴다니 믿겨져?"

보안 쪽은 늘 신경 써야 하는데, 이번에 Spring Framework 6.1이 OAuth 2.1 지원을 기본 내장했어요. OAuth 2.1은 이전 버전 대비 보안 정책이 훨씬 강화됐는데, 예를 들어 토큰 재사용 방지, PKCE(Proof Key for Code Exchange) 기본 적용 같은 부분이 추가됐죠.

실제로 저희 팀에서 인증 서버를 구축할 때, Spring Security 6.1의 OAuth 2.1 지원 덕분에 별도 플러그인 없이도 세밀한 권한 정책을 쉽게 구현할 수 있었습니다. 특히 클라이언트별 롤아웃 전략을 짤 때, 새로운 인증 정책을 점진적으로 적용하는 게 훨씬 수월해졌어요.

```java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
        .oauth2Login(oauth2 -> oauth2
            .authorizationEndpoint(authorization -> authorization
                .authorizationRequestResolver(new CustomAuthorizationRequestResolver())
            )
        )
        .oauth2ResourceServer(OAuth2ResourceServerConfigurer::jwt);
    return http.build();
}
```

위 예제는 커스텀 권한 요청 리졸버를 넣어서 특정 클라이언트에만 새로운 정책을 적용하는 방법인데, OAuth 2.1 덕분에 이런 확장이 훨씬 자연스러워졌어요.

더 자세한 내용은 [Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html)에서 확인할 수 있습니다.

## "HikariCP 커넥션 풀, 제대로 튜닝 안 하면 프로덕션에서 낭패 봅니다"

데이터베이스 커넥션 풀 설정은 늘 고민거리인데, Baeldung 가이드에 나온 것처럼 Spring Boot에서 HikariCP를 쓸 때 커넥션 타임아웃과 최대 풀 크기를 적절히 조정하는 게 중요해요.

예를 들어, 기본 최대 풀 크기인 10이 작은 서비스라면 충분하지만, 동시 요청이 많으면 30~50 정도로 늘려야 합니다. 그리고 커넥션 타임아웃은 너무 짧으면 연결이 자주 끊기고, 너무 길면 문제 감지가 늦어지니 30000ms(30초) 정도가 적당하더군요.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 40
      connection-timeout: 30000
      idle-timeout: 600000
      max-lifetime: 1800000
```

이 설정으로 저희 서비스는 커넥션 부족으로 인한 장애가 크게 줄었고, 응답 지연도 안정화됐습니다. 물론 풀 크기를 너무 크게 하면 DB 부하가 커질 수 있으니, 모니터링과 함께 조절하는 게 필수입니다.

[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance)에서 더 많은 팁을 볼 수 있어요.

## "Canary와 Blue-Green 배포를 섞으면 롤아웃이 이렇게 편해진다"

GitHub 엔지니어링 블로그를 보면서 우리 팀도 배포 전략을 재정비했는데, Canary 배포와 Blue-Green 배포를 조합하는 게 생각보다 효과적이었어요. 예전에는 한 번에 다 바꾸거나 Canary만 썼는데, 둘을 합치니 점진적 배포와 빠른 롤백 두 마리 토끼를 잡을 수 있더라고요.

예를 들어, 먼저 Blue-Green 배포로 새 버전을 준비해두고, Canary 배포로 일부 트래픽만 새 버전으로 돌려본 다음 문제가 없으면 점차 늘려가는 식입니다. 이렇게 하면 장애 발생 시 Green 환경으로 바로 롤백 가능해서 다운타임을 최소화할 수 있어요.

```bash
# 예시: kubectl을 이용한 Canary 배포
kubectl set image deployment/myapp myapp=myapp:v2 --record
kubectl rollout status deployment/myapp

# 문제가 생기면
kubectl rollout undo deployment/myapp
```

이 전략은 서비스 규모가 크고 트래픽이 많은 곳에서 특히 효과적입니다. 물론 배포 자동화 파이프라인과 모니터링 시스템이 잘 갖춰져 있어야 하니, 처음 도입할 때는 준비 기간이 필요해요.

관련 내용은 [GitHub Engineering Blog](https://github.blog/category/engineering/)에서 확인할 수 있습니다.

## "API 게이트웨이에서 트래픽 필터링과 DDoS 방어까지, 보안은 이렇게 강화하세요"

Cloudflare 사례를 참고하면, Spring 백엔드 앞단에 API 게이트웨이를 두고 트래픽 필터링과 DDoS 방어 기능을 통합하는 게 보안 강화에 정말 효과적입니다. 저희도 최근에 이 방식을 적용했는데, 악성 트래픽이 눈에 띄게 줄고 서비스 가용성이 크게 올라갔어요.

예를 들어, IP 화이트리스트, 레이트 리미팅, JWT 검증 등을 API 게이트웨이 레벨에서 처리하면 백엔드 서버 부담이 줄고, 공격에 대한 방어가 더 체계적으로 됩니다.

```yaml
# Spring Cloud Gateway 예시
spring:
  cloud:
    gateway:
      routes:
      - id: secure-route
        uri: http://backend-service
        predicates:
        - Path=/api/**
        filters:
        - name: RequestRateLimiter
          args:
            redis-rate-limiter.replenishRate: 10
            redis-rate-limiter.burstCapacity: 20
```

이 설정은 초당 10건 요청을 기본으로 허용하고, 최대 20건까지 버스트를 허용하는 레이트 리미터입니다. 이런 기본적인 방어책만 잘 써도 DDoS 공격에 훨씬 강해지죠.

더 자세한 사례는 [Cloudflare Blog - How We Built It](https://blog.cloudflare.com/tag/how-we-built-it/)에서 참고하세요.

## "마이크로서비스와 이벤트 기반 통신, 롤아웃 시 장애 격리에 진짜 도움 된다"

마지막으로, Martin Fowler의 아키텍처 가이드에서 강조하는 것처럼, Spring 백엔드를 마이크로서비스 구조로 설계하고 이벤트 기반 비동기 통신 패턴을 도입하면 롤아웃 과정에서 서비스 간 의존성을 최소화할 수 있습니다.

이게 왜 중요하냐면, 한 서비스에 문제가 생겨도 전체 시스템이 멈추지 않고 장애를 격리할 수 있기 때문이에요. 예를 들어, Kafka 같은 메시지 브로커를 통해 이벤트를 비동기 처리하면, 롤아웃 중에도 각 서비스가 독립적으로 동작할 수 있습니다.

```java
// Spring Kafka 리스너 예제
@KafkaListener(topics = "order-events", groupId = "inventory-group")
public void handleOrderEvent(OrderEvent event) {
    // 재고 업데이트 로직
}
```

이런 구조를 잘 설계해두면, 롤아웃 중인 서비스가 다운돼도 메시지는 큐에 쌓여있다가 복구 후 처리되니 안정성이 크게 올라가죠.

관련 내용은 [Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/)에서 심도 깊게 다루고 있습니다.
