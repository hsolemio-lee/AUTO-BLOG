## 갑자기 터진 CVE, 우리 서비스도 안전할까?

얼마 전 우리 팀에서 사용하는 Spring Cloud Function과 Config에서 중요한 CVE(보안 취약점) 패치가 발표됐다는 소식을 들었어요. ‘아, 또 업그레이드 해야 하나’ 하는 생각과 함께, 바로 적용하지 않으면 보안 위험에 노출될 수 있다는 불안감이 들었죠. 그런데 막상 적용하려니 버전 호환성 문제도 있고, 갑자기 서비스 장애가 나면 어쩌나 걱정도 되고요.

이 경험을 공유하려고 합니다. 실제로 어떻게 업그레이드하고, 어떤 점을 조심해야 하는지, 그리고 보안 강화는 어떻게 하는 게 좋은지 단계별로 이야기해볼게요.

---

## Spring Boot 3.x와 호환되는 최신 Spring Cloud Function과 Config 버전부터 확인하자

이번 보안 패치는 Spring Cloud Function과 Config가 Spring Boot 3.x와 호환되도록 맞춰 나오면서 여러 CVE를 해결했어요. 단순히 버전만 올린 게 아니라, 내부적으로 보안 취약점들을 집중적으로 패치한 거죠. 

우리 서비스가 아직 Spring Boot 2.x 기반이라면, 바로 최신 버전으로 올리면 의존성 충돌이 발생할 수 있어요. 그래서 먼저 Spring Boot 3.x로 마이그레이션하는 작업부터 차근차근 준비해야 합니다.

```gradle
// build.gradle 예시
implementation 'org.springframework.boot:spring-boot-starter:3.0.5'
implementation 'org.springframework.cloud:spring-cloud-function-context:4.0.3'
implementation 'org.springframework.cloud:spring-cloud-config-client:4.0.3'
```

버전은 4.0.x대가 Spring Cloud Function과 Config의 최신 라인입니다. 공식 문서에 따르면 이 버전들이 Spring Boot 3.x와 호환되며, 보안 패치가 포함되어 있다고 하니 꼭 맞춰야 해요[Spring Boot Reference Documentation](https://docs.spring.io/spring-boot/reference/).

---

## 단계별 롤아웃 전략으로 갑작스러운 장애 리스크 줄이기

우리 팀은 대규모 서비스라서 한 번에 모든 서버에 업데이트를 적용하는 건 위험했어요. 그래서 Canary 배포 전략을 썼습니다. 전체 서버 중 5%에만 먼저 배포해서 모니터링을 집중했죠. 

이때 중요한 건 모니터링과 로깅 강화입니다. 보안 패치 후에 예상치 못한 예외가 발생할 수 있으니, 로그를 꼼꼼히 체크하고 CPU, 메모리 사용량도 주시했어요. 

만약 문제가 없으면 점진적으로 50%, 100%까지 늘렸고, 중간에 문제가 발견되면 바로 롤백했습니다. 이런 배포 방식은 Martin Fowler의 아키텍처 가이드에서도 추천하는 방법이에요[Martin Fowler - Software Architecture Guide](https://martinfowler.com/architecture/).

## 보안 강화는 단순 업그레이드만으로 끝나지 않는다

최신 버전으로 올리는 게 기본이지만, 여기서 한발 더 나아가야 해요. 우리 서비스에서 적용한 보안 강화 전략을 공유할게요.

- **불필요한 함수 노출 최소화**: Spring Cloud Function은 기본적으로 함수가 외부에 노출될 수 있어요. 필요한 함수만 export하고, 나머지는 숨겨서 공격 표면을 줄였습니다.

- **Config 서버 접근 제한**: Config 서버는 민감한 설정을 담고 있어서 IP 화이트리스트와 인증을 걸었어요. 내부 네트워크에서만 접근 가능하도록 방화벽 설정도 강화했습니다.

- **환경별 프로파일 세분화**: dev, staging, prod 환경별로 프로파일을 나누고, 각 환경에 맞는 최소 권한 설정을 적용했습니다.

이런 전략들은 Spring Framework 코어 문서에서 권장하는 보안 설정과도 일치합니다[Spring Framework - Core Technologies](https://docs.spring.io/spring-framework/reference/core.html).

## 보안 패치 후 성능 변화, 어떻게 체크하고 대응했나

보안 패치를 적용하면 내부 로직이 바뀌거나 추가 검증이 생기면서 성능에 영향을 줄 수 있어요. 우리도 패치 후 부하 테스트를 꼭 진행했는데, 다행히 큰 성능 저하는 없었지만 JVM 튜닝과 캐시 설정을 조금 조정했어요.

예를 들어, JVM 힙 메모리를 기존 2GB에서 3GB로 늘리고, 가비지 컬렉션 옵션을 G1GC로 바꿨죠. 캐시 TTL(Time To Live)도 10분에서 15분으로 연장해서 DB 호출을 줄였습니다.

```java
// 간단한 함수 노출 최소화 예시
@Bean
public Function<String, String> uppercase() {
    return value -> value.toUpperCase();
}

// 이 함수만 외부에 노출, 나머지는 빈으로 등록하지 않거나 private 처리
```

성능 튜닝 관련해서는 Baeldung의 가이드가 많은 도움이 됐어요[Baeldung - Spring Boot Performance Tuning](https://www.baeldung.com/spring-boot-performance).

## 마무리하며

이번 보안 패치 적용은 단순히 버전 업그레이드 이상의 의미가 있었어요. 실제 서비스에 적용하면서 의존성 문제, 배포 전략, 보안 강화, 성능 튜닝까지 종합적으로 고민해야 했죠. 

무엇보다 중요한 건 ‘급하게 한 번에 끝내려 하지 말고, 단계별로 안전하게 적용하자’는 점입니다. 그리고 보안은 한 번의 패치로 끝나는 게 아니라, 지속적으로 관리하고 점검해야 하는 작업이라는 것도 다시 느꼈어요.

혹시 지금 Spring Cloud Function이나 Config를 사용 중이라면, 이번 기회에 꼭 최신 보안 패치 확인하고, 우리처럼 단계별 롤아웃과 보안 설정 강화 전략을 세워보시길 추천합니다.
