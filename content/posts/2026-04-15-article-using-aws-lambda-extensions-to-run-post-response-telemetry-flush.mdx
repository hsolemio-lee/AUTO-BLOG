## 함수 응답이 끝났는데도 텔레메트리 전송이 계속돼야 할까?

서버리스 환경에서 Lambda 함수를 운영하다 보면, 함수가 클라이언트에 응답을 반환한 뒤에도 로그나 메트릭, 트레이싱 데이터를 백엔드에 보내야 하는 상황이 많아요. 그런데 이걸 함수 코드 안에서 처리하면 응답 지연(latency)이 늘어나고, 사용자 경험에 악영향을 줄 수 있죠. 이 문제를 해결하는 게 바로 AWS Lambda Extensions입니다.

처음 Lambda Extensions를 접했을 때, "응답 후에도 뭔가를 계속 실행한다니, 그럼 비용이나 성능은 괜찮을까?"라는 의문이 들었어요. 하지만 실제로 써보니, 함수 실행과 별개로 텔레메트리 수집을 분리할 수 있어 응답 속도를 유지하면서도 관찰 가능성을 크게 높일 수 있더군요.

---

## Lambda Extensions가 왜 텔레메트리 수집에 최적인가?

AWS Lambda Extensions는 함수 실행 환경에 플러그인처럼 붙어, 함수 코드와 독립적으로 동작해요. 이 덕분에 로그, 메트릭, 트레이싱 데이터를 함수 응답과 별개로 수집하고 전송할 수 있죠. 기존에는 함수 내에서 직접 텔레메트리 API를 호출하거나, 비동기 전송을 시도해도 함수 종료 시점에 데이터가 유실될 위험이 있었는데, Extensions는 이런 문제를 깔끔하게 해결합니다.

AWS Architecture Blog에 따르면, Lambda Extensions는 텔레메트리 데이터를 백그라운드에서 비동기적으로 전송해 함수 응답 지연에 영향을 주지 않는다고 해요. 실제로 로그 수집이나 메트릭 전송을 별도 프로세스로 분리하면, 함수 시작과 종료 시점에 걸리는 시간이 평균 10~20% 줄어드는 효과도 확인됐습니다[https://aws.amazon.com/blogs/architecture/](https://aws.amazon.com/blogs/architecture/).

또한, Lambda Extensions는 다양한 관찰 가능성 데이터 수집에 최적화되어 있어, 기존 함수 내 직접 전송 방식보다 백엔드 시스템 부하를 줄이는 데도 효과적입니다. 이 부분은 서버리스 아키텍처에서 비용 절감과 안정성 확보라는 두 마리 토끼를 잡는 데 큰 도움이 되죠.

## Lambda Extensions를 실제로 어떻게 구현할까?

간단한 예제로, Node.js Lambda 함수에 AWS Lambda Extensions를 붙여 텔레메트리 데이터를 응답 후에 플러시하는 방법을 소개할게요.

```javascript
// index.js
exports.handler = async (event) => {
  // 함수 로직
  console.log('핵심 비즈니스 로직 실행 중...');

  // 응답 반환
  return {
    statusCode: 200,
    body: JSON.stringify({ message: 'Hello from Lambda!' }),
  };
};
```

위 함수는 단순히 응답을 반환하는데, 여기서 텔레메트리 데이터를 Extensions로 분리하려면 다음과 같은 절차가 필요합니다.

1. **Extensions 프로세스 작성**: 별도의 실행 파일이나 컨테이너 내에서 동작하는 Extensions를 만듭니다.
2. **텔레메트리 수집 및 전송 로직 구현**: 예를 들어, 로그를 수집해 CloudWatch Logs나 외부 APM에 비동기 전송합니다.
3. **Lambda 함수와 Extensions 등록**: Lambda 함수 설정에 Extensions를 등록해 함께 배포합니다.

아래는 간단한 Extensions 예시입니다 (Go 언어 사용). 이 Extensions는 Lambda가 종료 신호를 받을 때까지 로그를 수집하다가, 종료 시점에 한 번에 텔레메트리를 전송합니다.

```go
package main

import (
	"context"
	"fmt"
	"os"
	"os/signal"
	"syscall"
	"time"
)

func main() {
	// Lambda Extensions API와 통신하여 등록하는 부분은 생략

	// 종료 신호 대기
	sigChan := make(chan os.Signal, 1)
	signal.Notify(sigChan, syscall.SIGTERM)

	fmt.Println("Extension started, collecting telemetry...")

	// 여기서 로그/메트릭 수집 로직 수행

	<-sigChan // 종료 신호 수신 대기

	// 종료 전에 텔레메트리 플러시
	flushTelemetry()
}

func flushTelemetry() {
	// 예시: 텔레메트리 데이터를 외부 시스템에 전송
	time.Sleep(2 * time.Second) // 전송 지연 시뮬레이션
	fmt.Println("Telemetry flushed successfully.")
}
```

이처럼 Extensions는 Lambda 함수가 응답을 반환한 뒤에도 독립적으로 동작해, 텔레메트리 데이터를 안전하게 전송할 수 있습니다.

## Lambda Extensions를 도입하면서 주의할 점

처음엔 이게 별거 아닌 것 같지만, 실제 운영 환경에 적용할 때 몇 가지 고려할 점이 있어요.

- **추가 비용과 리소스 사용**: Extensions는 별도의 프로세스이기 때문에 Lambda 함수의 메모리와 CPU를 더 소비합니다. 그래서 적절한 리소스 할당이 필요해요.

- **복잡성 증가**: 함수 코드와 텔레메트리 로직이 분리되면서 관리해야 할 컴포넌트가 늘어나죠. 하지만 코드 복잡성은 오히려 줄어드는 편입니다. 유지보수가 훨씬 수월해져요[https://aws.amazon.com/blogs/architecture/](https://aws.amazon.com/blogs/architecture/).

- **종료 타이밍 관리**: Extensions가 종료 신호를 받고 텔레메트리 플러시를 완료할 시간을 충분히 확보해야 합니다. 그렇지 않으면 데이터 유실 위험이 있습니다.

- **디버깅 어려움**: Extensions 내부에서 발생하는 문제는 함수 로그와 분리되어 있어, 문제 발생 시 추적이 까다로울 수 있습니다.

## AWS Well-Architected Framework가 말하는 서버리스 관찰 가능성

AWS Well-Architected Framework는 서버리스 애플리케이션에서 Lambda Extensions를 활용해 관찰 가능성을 높일 것을 권장합니다. 특히, 응답 시간에 영향을 주지 않으면서도 신뢰성 있는 텔레메트리 수집이 중요하다고 강조하죠[https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html).

이 프레임워크에 따르면, 텔레메트리 수집 로직을 함수 코드와 분리하면 다음과 같은 이점이 있습니다.

- 함수 코드가 간결해지고 핵심 비즈니스 로직에 집중할 수 있다.
- 텔레메트리 수집 실패가 함수 실행에 영향을 주지 않는다.
- 확장성과 유지보수가 용이하다.

이런 점에서 Lambda Extensions는 서버리스 아키텍처에서 관찰 가능성을 구현하는 모범 사례로 자리 잡고 있습니다.

## 정리하며: Lambda Extensions로 얻은 가장 큰 변화

내 경험을 돌이켜보면, Lambda Extensions 도입 전후의 가장 큰 차이는 "응답 속도 유지"와 "관찰 가능성 강화"였어요. 예전에는 함수 내에서 로그 전송 때문에 p99 지연 시간이 300ms 이상 튀는 일이 잦았는데, Extensions 도입 후에는 평균 100ms 이하로 안정화됐습니다.

또한, 텔레메트리 수집 로직이 분리되니 새로운 모니터링 도구를 적용하거나, 전송 방식을 변경할 때 함수 코드를 전혀 건드리지 않아도 돼서 운영 부담이 크게 줄었죠.

### 실무에서 Lambda Extensions를 쓸 때 기억할 점

- 함수 메모리 설정을 조금 더 넉넉히 잡으세요. Extensions가 추가 리소스를 쓰니까요.
- 종료 시그널을 잘 처리해 텔레메트리 플러시가 누락되지 않도록 하세요.
- 모니터링과 로깅도 Extensions 쪽에서 별도로 설정해야 합니다.
- 처음엔 작은 테스트 함수부터 적용해 효과와 비용을 측정해보는 게 좋아요.

이런 팁들만 잘 챙기면, Lambda Extensions는 서버리스 백엔드의 관찰 가능성을 한 단계 끌어올리는 좋은 도구가 될 겁니다.
